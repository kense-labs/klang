# K 编译器自举回归测试

这是一个用 K 编写的 K 语言子集编译器。它是主编译器的一个大型集成测试夹具（fixture），而非测试套件承诺维持特性覆盖率的第二个编译器。`main.k` 导入了其余十三个模块。此处仅包含编译器源码；探索性探测代码、报告以及独立的构建/测试脚本均不属于该测试夹具。

该实现完全依据 `docs/k_spec.md`、`docs/implementation.md`、K 库接口/测试以及黑盒宿主编译器行为编写，未参考 `src/` 下的 C++ 实现。其内嵌的 C 运行时也是独立的。它涵盖了足以自编译的语言子集：语法解析、类型与泛型、语义检查、特化（specialization）以及 C 代码生成。生命周期分析以及许多语言特性仍不完整。请勿以其能否通过编译作为 K 语言的预期行为标准。

常规测试套件会自动运行此测试夹具。若仅单独运行此回归测试：

```sh
python test/run_tests.py --k-in-k-only --exe build/Release/k.exe --cc native
```

请根据你的构建产物使用相应的 `--exe` 路径。该测试使用测试套件所选定的原生 C 编译器和配置档（profile）：

1. 真正的编译器从 `main.k` 生成第 1 阶段（stage 1）代码；经原生 C 编译后生成第一个用 K 编写的编译器可执行文件。
2. 第 1 阶段编译器将同一套源码编译为第 2 阶段（stage 2）代码；原生 C 编译随后构建出第 2 阶段可执行文件。
3. 第 2 阶段编译器再将源码编译为第 3 阶段（stage 3）代码，该阶段同样会进行构建和链接。
4. 第 2 阶段与第 3 阶段生成的 C 代码必须逐字节完全一致。第 2 阶段编译器会在同一进程内对其自身源码检查两次，同时生成并构建第 3 阶段；两次编译都必须成功且结果一致。这一不动点（fixed point）确保第 2 阶段编译器与第 3 阶段编译器完全等价。
5. 当 TinyCC 可用时，真正的编译器还会通过其 JIT 执行这个用 K 编写的编译器。它生成的 C 代码必须与原生自举流程的产出一致。

基线配置档（baseline profile）会分别在宿主/原生 O0 与 O2 优化级别下运行整条链路，并要求两种配置产出完全相同的自编译 C 代码。Sanitizer 配置档则使用宿主 O2 与原生 Clang O1，并在每个原生阶段附加测试套件的 ASan/UBSan 编译标志。`--no-jit` 会跳过 JIT 对比；`--nocgen` 会保留宿主检查与可用的 JIT 自编译，但显式跳过原生编译链路。

生成的文件及各阶段日志均保存在 `build/gen/<profile>/k_in_k/O<level>/` 目录下。每条命令都必须执行成功，且每次代码生成都必须产出非空的 C 文件；过期的旧输出不能用于满足某阶段的校验。在平台允许的情况下，编译器可执行文件会获得 64 MiB 的栈空间预算。测试运行器会报告具体到某个阶段的失败信息，包括超时与 Sanitizer 诊断输出。这些模块被排除在常规独立测试夹具发现流程之外，因为它们依赖模块导入以及编译器命令行参数。
