# PCM 音频

<!-- Adapted for K. -->

`audio.k` 暴露了一套小巧的音效 API。它不在 K 中持有 PCM 数据：
`create_sound` 会校验并将切片复制到原生层，由原生层一直保留，直到调用
`release_sound` 或 `close`。释放音效时会停止所有引用该音效的声部（voice）。
这使得源数组的生命周期独立于异步播放。

其实现位于 `src/audio/audio.c`；`audio_api.h` 是其紧凑打包（packed）的 extern 边界
及 JIT 符号列表。`test/api_check.py audio` 用于检查 C 与 K 的声明一致性。
编译器会追踪原生音频调用并禁止在 `thread_fn` 中调用它们，这与 gfx、physics 和 ui 的处理方式一致。原生回调仅使用 C 实现。

<a id="mixing-and-ownership"></a>
## 混音与所有权

混音器拥有固定大小的表，最多容纳 256 个音效和 64 个声部。ID 单调递增且永不重置，即使跨 close/open 亦然。资源耗尽会显式体现：创建音效或声部时会返回零。播放完成的声部会释放其表槽位，而不会在音频线程上释放 PCM 数据。对已失效的声部执行停止或查询操作是无害的。系统不存在声部抢占（voice stealing）、向用户代码的回调或无界限的回调工作负载。

每个声部都带有小数源位置、音量、立体声平衡、音高和循环标志。步进值为 `source_rate / output_rate * pitch`。线性插值会混合相邻的源帧；循环播放会将末尾混合回第一帧，而单次播放（one-shot）则会在最后一个小数帧期间保持其最终采样值。单声道会复制到双声道立体声中。声像（Pan）调节会衰减对侧声道。所有声部叠加汇总为立体声 f32 格式，结果会被限幅到 `[-1, 1]`。该模块特意设计为一个音效混音器，而非带限音乐重采样器或效果器引擎。

`seek` 在流锁保护下设置源位置；若超出末尾，循环声部会回绕，其他声部则会停留在最后一帧。`voice_position` 报告的是实际听到的位置而非正在混音的位置：即源位置减去流中和设备缓冲区里排队的帧数（按该声部的步进值缩放），再加上自上次回调以来经过的时间（最多不超过该次回调所混音的量），从而在两次回调之间使位置平滑过渡。离线模式下中间没有缓冲队列，因此该值就是源位置本身。

`open` 仅初始化 SDL 的音频子系统，并向默认播放设备打开一个立体声 f32 流。SDL 负责向物理设备格式的转换。其拉取（get）回调以每次最多 256 帧的分块填充请求。流锁用于保护资源表和错误文本。主线程上的 PCM 分配/复制与释放均在该锁之外进行；只有表的发布与移除发生在锁内。关闭操作会销毁该流（并与其回调同步），随后释放 PCM 数据，并仅递减 SDL 音频子系统的引用计数。gfx 可以独立关闭。

`open_offline` 不启动任何 SDL 子系统、设备或线程。`render` 会同步推进同一个混音器，为测试提供精确的采样输出和精确的完成边界。它还允许程序为其自有的文件写入器生成 PCM 数据。

<a id="builds-and-validation"></a>
## 构建与验证

Audio 是 gfx 包的一个模块（`audio.k`，以及位于 `src/audio/` 中的实现层），它在 gfx、audio 和 ui 之间共享同一个 SDL 构建（参见 `docs/gfx.md`）；使用 `-DK_BUILTIN_LIBS=all` 可将其编译进编译器，随后 `--audio-link msvc|cc` 会打印该包的响应文件（response file）。

常规测试运行器在 JIT 和生成 C 代码的运行模式中均包含 `test/audio/audio_mixer.k` 和 `audio_errors.k`。它们测试 PCM 所有权、立体声、采样率转换、插值、增益、声像、音高、循环边界、重叠播放、削波限幅、资源耗尽、失效句柄、关闭/打开以及无效输入。`audio_err_thread.k` 则测试主线程调用限制。

显式的 `k_audio_test` CMake 目标使用 SDL 的 dummy 驱动来测试真实回调、设备打开失败与恢复、非有限值（nonfinite）输入、紧凑未对齐切片、并发访问资源表、播放期间释放资源以及关闭/重新打开。例如，运行 `cmake --build build --config Release --target k_audio_test`，然后在 Windows 上运行 `build/Release/k_audio_test.exe`（或在使用单配置生成器时运行 `build/k_audio_test`）。它不需要窗口、GPU、扬声器或音频会话。物理设备的实际表现仍取决于平台后端；dummy 和离线测试无法验证听觉音质、设备丢失恢复能力或真实延迟。
