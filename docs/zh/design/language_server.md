本文记录了将 `vscode/` 中的 VS Code 扩展（目前在保存时运行 `k check` 并解析其文本输出）演进为语言服务器所需的工作：在编译器中新增 `k lsp` 子命令，使其通过 stdio 使用 Language Server Protocol（语言服务器协议），而该扩展则作为其客户端之一。文档记录了扩展和编译器目前的做法、支撑设计的性能实测数据、拟议的设计方案、所需的编译器改动（按规模排序）、各项编辑器特性分别依赖哪些改动，以及分阶段的实施计划——其中第一阶段本身即可直接改善现有扩展的体验。

<a id="1-what-there-is-today"></a>
## 1. 现状

该扩展（位于 `vscode/`，包含约 730 行 JavaScript 代码与 600 行测试代码，无运行时依赖，使用 `vsce package --no-dependencies` 打包）分为两部分。

**客户端侧（仅基于源码文本）：** 一套 TextMate 语法高亮规则（同时注入到 Markdown 的 ` ```klang ` 代码块中）、括号与注释配置、代码片段、通过小型词法扫描构建的大纲（`language.js`：`declarations` 按大括号深度查找顶层 `fn`/`struct`/`enum`/`type`/`let`/`var`/`namespace` 声明头），以及在 `import` 行上按 `StdlibDirs` 规则解析模块的文档链接。

**通过编译器：** 当打开或保存受信任工作区中的文件时，会以带超时的形式运行 `k check <entry>`（`diagnostics.js`）。若设置了 `klang.entryFile`，入口即为该文件；否则为当前文件本身。编译器标准错误输出通过正则表达式解析：`file:line[:col]: error|warning: message`，词法错误下方两行附带插入符（caret）指示行，而 `in f instantiated from file:line` 栈帧则作为关联位置（related locations）展示。由于类型检查错误仅给出行号，客户端会在该行首个标识符下画波浪线。检查结果按入口文件保存（`CheckQueue`），在发生编辑时标记为过期（stale），当不再有已打开文档检查该入口时丢弃，并展示在“问题（Problems）”面板、状态栏条目以及输出通道中。用于运行、构建和生成 C 代码的任务也使用同一个可执行文件，并配有面向任务终端的问题匹配器（problem matcher）。

该扩展目前无法做到的事情，正是由这种前后端划分方式决定的：客户端自身无法判断某个名称引用了什么。目前没有悬停提示（hover）、除导入链接外的跳转到定义（go to definition）、除代码片段与编辑器词表外的自动补全（completion）、查找引用（references）或重命名（rename），也没有语义高亮（semantic highlighting）。诊断信息仅在保存时出现、只显示程序的第一个错误、仅定位到行，且每个工作区文件夹一次只覆盖一个程序。上述清单中的每一项特性都需要编译器的名称解析与类型检查，而只有编译器拥有这些信息。LSP 协议正是编辑器向编译器提出这些问题的桥梁；一旦编译器能够回答这些问题，任何支持 LSP 客户端的编辑器（Neovim、Emacs、Zed、Helix、JetBrains）只需几行配置即可获得对 K 语言的支持。

<a id="2-what-the-compiler-gives-a-server-and-what-it-lacks"></a>
## 2. 编译器能为服务器提供什么，又缺少什么

编译器的前端结构使得语言服务器的大多数问题都能在 `k check` 运行后已有的数据中找到答案。当前的主要缺口在于位置信息、错误的输出方式，以及遇到第一个错误之后的处理行为。

**位置信息。** `Line`（`ast.h`）仅包含行号与文件索引；所有节点均没有列号或结束位置。`Parser::CurLine` 是唯一创建 `Line` 的位置（22 处调用，通过 `Parser::New` 构造 48 种节点），其来源为 `Lexer::tokline`。词法分析器其实已有列号信息（`attr.data() - toklinestart`），但只有 `FunVal::col` 为生成实例化调用链记录了它。每个声明（`SFunction`、`SStruct`、`SEnum`、`SAlias`、`VarDef`、`VarDecl`）以及每个 `TypeExpr` 都有一个 `Line`；而 `Field`、`Param`、`GenericParam` 和 `SVariant` 均没有。标识符名称是指向源码缓冲区的 `string_view`（由 `Ast::sources` 保持存活），因此非限定名称的字节偏移已经可以通过指针算术恢复。但限定名称（`ns::x`）经过了驻留（`Ast::Intern`），而合成名称（`result#1`）在源码中根本不存在，因此位置信息必须显式记录，而不能事后推导。

**诊断信息。** 编译错误是一个 `CompileError { string msg }`，在抛出时文本就已经渲染好了。`Lexer::ErrorAt` 输出 `file:line: error: msg`、源码行和插入符。`TypeCheck::ErrorIn` 输出相同的头部、不带插入符的源码行，以及实例化调用链（`InstantiationChain`、`DumpInstance`，每一帧输出一条 `in fn f<T = u8>(i64) instantiated from file:line`）。警告在发生时直接输出到 stderr（`PrintWarning`），按节点和文本去重。BCE 的 `checkfree` 报告则是另一种直接渲染好的字符串。遇到第一个错误就会终止编译，且解析器还会利用同一异常进行试探性解析的回溯（泛型调用前缀和函数值前缀中的 `catch (CompileError &)`）。测试套件中的 1,800 个 `errors_tc/` 和 60 个 `errors/` 测试用例均带有 `// error: message` 标记，测试运行器会将其与 `file:line[:col]: error: message` 形式的行匹配。测试运行器既不比对回显的源码行，也不比对插入符或调用链，并且已经接受列号。因此，无论服务器如何演进，头部格式和报错消息都可以保持不变，而头部还可以增加列号且无需修改任何测试用例。

**类型与解析注解。** 函数体会按每次特化（specialization）以克隆体的形式检查一次（`FnSpec::body`），而这个克隆体携带了服务器想要的一切信息：`Node::exprtype`、`Ident::vdef` 或 `fnref`、`Dot::fieldidx`、`member`、`variantconst` 与 `einst`、`Call::spec`、`dispatch`、`builtin`、`fvbody` 与 `rettypes`，以及每个带有具体类型的 `VarDef`。`TypeExpr::Dump` 和 `DumpInstance` 可以像诊断信息那样渲染出类型或特化的签名。每个克隆节点都记录了其源码节点（`Node::origin`），而 `Node::Children` 可以遍历任意子树，因此可以通过遍历 `ast.fnspecs` 和 `Ast::ForEachRootTree` 来建立从源码节点到克隆体、以及从源码位置到节点的映射。模板函数体本身从不加注解。未被任何代码实例化的泛型函数，或未被调用的嵌套函数，都没有克隆体，因此也没有类型信息（`docs/implementation.md` §3.1；服务器的样本实例化机制，见 §11，会为泛型函数提供一个克隆体）。未被任何代码到达的非泛型、全注解顶层函数会独立接受检查（`CheckUnreached`），且 `check` 模式下允许没有 `main` 的模块（`nomain`）——这正是当前扩展能够单独检查模块文件的原因。

**作用域。** 词法作用域仅在类型检查器运行时存在（`frames`、`scopes`、`vars`、`LookupVar`）；没有任何结构记录变量作用域从何处开始、在何处结束。名称自动补全要么需要记录这类信息，要么需要自行遍历解析树。

**注释。** 词法分析器会直接丢弃注释（`Lexer::Next` 中的 `goto again`），因此在悬停提示时没有文档注释可展示。

**源码来源。** `ParseProgram` 从磁盘加载所有文件，唯有根文件允许 `--roundtrip` 以文本形式传入（`rootsource`）。而语言服务器在内存中持有编辑器对任意文件的未保存缓冲区。

**进程模型。** 编译器已经能够在单进程内运行多次编译：`--multi-test` 会像独立运行那样分别编译每个文件，各自拥有独立的 `Ast` 和编译线程，且类型检查器没有任何全局状态（除了一个 `thread_local`，即栈底保护）。单次编译运行在一个拥有 64 MB 栈的线程上（`RunOnCompilerStack`），服务器也会沿用这一机制。编译中有两件事会阻塞服务器：`ParseProgram` 会拉取尚未缓存的已声明包（`FetchPackage`，在解析过程中通过网络执行 git），而检查器会编译 `embed_shader` 源码（`CompileShader`，仅缓存在 `Ast::shaders` 中，因此仅在单个 `Ast` 内有效）。

**性能开销。** 编辑器服务器能否成立的核心问题，在于每次源码修改后是否可以重新分析整个程序。以下数据在本机（Windows，Release 构建，2026 年 10 月）测得：进程内耗时通过 `--multi-test` 将同一文件连续编译二十次测得，独立进程耗时通过 `time` 测得：

| | 文件数 | 行数 | 进程启动 | 解析与名称解析 | 类型检查与优化 | 含 BCE |
|---|---|---|---|---|---|---|
| `samples/18_json.k`（含 `std` 和 `os`） | 3 | 1,780 | 34 ms | 4 ms | | 10 ms |
| `test/k_in_k/main.k` | 14 | 3,318 | 34 ms | 10 ms | 82 ms | 104 ms |
| `samples/31_mini_doom.k`，首次运行 | | | | 15.3 s | | |
| `samples/31_mini_doom.k`，之后 | | | | 53 ms | | 75 ms |

其中的 15 秒消耗在解析阶段拉取 `gfx` 包。其余数据表明，对于自举编译器规模的程序，一次完整的进程内分析大约耗时十分之一秒；对于典型程序则约为百分之一秒。两者均处于扩展当前 180 ms 防抖（debounce）延迟之内。因此，第一版无需增量分析。此外，只追加（append-only）的 `Ast` 按次编译分配并整体释放，也使得整份分析结果的替换非常容易。

<a id="3-decisions"></a>
## 3. 设计决策

1. **服务器即编译器本身。** `k lsp` 是单一编译器可执行文件的一个子命令，因此服务器永远与其服务的编译器保持同一版本、无需单独分发，并且直接复用前端而非对其进行近似模拟。另一种方案是用 TypeScript 或 K 编写独立的服务器来重新实现名称解析——Zig 的 ZLS 对 `comptime` 就是这么做的，结果依靠启发式规则在复杂处不得不放弃，其维护者也正计划改为复用编译器自身的分析结果。K 的检查器按包含引用根与字面量参数的键来为每次实例化决定类型（§3.1）；任何重写都不可能保持完全一致。

2. **每次变更时重新分析整个程序。** 属于某个根的任意文件发生修改时，经过防抖（并支持取消）后，基于编辑器内存缓冲区重新解析并重新检查该根；新生成的 `Ast` 替换旧的 `Ast`，所有请求均基于最近一次完成的分析结果作答。这与 clangd 对每个翻译单元的做法相同（仅缓存 preamble），且在这里成本很低（§2）。如果日后确实需要增量能力，也会在单个根的粒度上实现：可以按内容哈希缓存单文件的解析结果，而无需改动整体架构。

3. **程序即根（root），沿用扩展现有概念。** 一个根就是一个入口文件：可以是配置的入口（`klang.entryFile`，后续将扩展为列表），也可以是不被任何已配置根导入的已打开文件。上一次分析所得的导入图决定了一个文件属于哪些根，因此编辑 `stdlib/json.k` 会重新分析导入了它的所有程序。不被任何程序导入的模块会像 `check` 一样单独分析（`nomain`）：检查其全注解函数，而不检查泛型函数。

4. **内部位置采用字节偏移与长度。** 节点与声明记录起始列和结束位置；服务器在协议边界处将其转换为行号与 UTF-16 列号，因为 VS Code 客户端要求 UTF-16（协商 UTF-8 的客户端则直接得到字节列，见 §10）。编译器内部从不处理协议所用的位置单位。

5. **诊断信息数据优先、文本其次。** `CompileError` 携带一条结构化的诊断信息（文件、范围、消息、严重级别，以及作为关联位置的实例化调用链），并由单一函数从中渲染文本，从而保证 CLI 与测试用例的文本输出逐字节一致。同一份结构也可在特定命令行参数下以 JSON 格式输出，供当前扩展在语言服务器完成之前直接消费。

6. **错误恢复分阶段引入且绝不静默。** 最初服务器沿用现有行为，只报告第一个错误，同时利用该错误之前已完成的注解来回答查询（函数克隆体会注解至出错节点为止）。随后解析器按语句和声明进行恢复，接着检查器按根进行恢复。每个阶段都只会报告更多错误，绝不会减少；直到最后一个阶段完成前，CLI 在出错时的行为保持不变，而之后 `k check` 也能输出所有错误。

7. **服务器绝不等待网络请求或着色器编译。** 遇到尚未拉取的包时，会在其导入位置报出诊断错误并附带拉取命令；着色器二进制则按源码文本跨分析缓存。

8. **扩展在无服务器时依然可用。** 语法高亮、代码片段、大纲、导入链接与任务继续留在客户端侧（语法高亮不应该依赖服务器是否启动；Lobster 扩展在 2023 年也作出了同样的选择），而保存时执行 `k check` 的路径保留作为旧版或无 `k lsp` 子命令编译器的回退方案。

<a id="4-the-server"></a>
## 4. 服务器架构

**代码位置。** 服务器是一组头文件，像编译器其他部分一样在各 pass 之后被 `main.cpp` 包含，并在 `Main` 中增加 `verb == "lsp"` 分支（`k lsp` 仅接受 `--stdlib` 参数；客户端通过协议传递设置）。共分为四个文件：

| 文件 | 职责 |
|---|---|
| `lsp_rpc.h` | 传输层：stdin/stdout（均为二进制模式）上的 `Content-Length` 帧封装、与 `json.h` 读取器对应的 JSON 写入器、请求 ID、`$/cancelRequest`、读取线程以及消息队列 |
| `lsp_workspace.h` | `Overlay`（已打开文档：路径、文本、版本）、`Root`（入口文件、最近一次 `Analysis`、导入文件集合）、基于配置与已打开文档的根选择、`workspace/didChangeWatchedFiles`，以及调度逻辑：防抖、取消标志、在编译器栈上运行分析 |
| `lsp_analysis.h` | `Analysis`：`Ast`、按文件归类的诊断信息，以及在检查完成后构建一次的索引（按偏移排序的每文件节点列表、源码节点到克隆体的映射、声明及其位置）；查询接口 `NodeAt`、`DeclOf`、`TypeOf`、`ReferencesTo`、`ScopeAt` |
| `lsp_features.h` | 每个请求一个处理函数，将查询结果映射为协议结构：悬停提示、跳转到定义、查找引用、重命名、调用层次结构、文档与工作区符号、自动补全、签名帮助、语义标记、内嵌提示、折叠与选区范围、代码透镜 |

**线程模型。** 一个读取线程负责把消息解析进队列。一个工作线程负责其余所有工作：将通知应用到覆盖层（overlay）、基于最近一次分析结果响应请求，以及执行分析任务——每次分析在编译器栈线程（`RunOnCompilerStack`）上运行，在此期间工作线程处于等待状态。当分析正在进行时若收到 `didChange`，读取逻辑会置位取消标志（解析器和检查器会轮询该标志，见 §5 F），工作线程在清空队列后重新开始分析。分析期间到达的请求会等待其完成。由于一次分析大约只需要十分之一秒，不需要第二个并发读取 `Ast` 的线程，因此也不需要任何锁。

当某份文档的变更尚处于防抖等待期，或某请求紧跟在尚未开始分析的 `didOpen` 之后到达时，该文档的相关请求会先触发这一次分析运行，并且请求之后到达的变更不会取消本次分析：因为基于变更前分析返回的答案对应的是旧文本，或者此时根本还没有可用分析结果。对于支持刷新通知的客户端，代码透镜、语义标记和内嵌提示属于例外：客户端会在分析完成后重新请求它们。仍在队列中的请求可被 `$/cancelRequest` 丢弃。

**单次分析流程。** 分析一个根时，服务器依次运行以下 pass：

1. `ParseProgram`：优先从覆盖层读取文件，再回退到磁盘（§5 B），且禁用包拉取（§5 E）。
2. `ResolveTypeNames`，随后以 `nomain` 模式运行 `TypeCheckProgram`。
3. 优化器与 BCE，用于报告 `checkfree` 错误。这两步占分析时间的五分之一，可通过设置跳过。

诊断信息会被收集起来而非直接抛出或打印（§5 C），随后构建索引。被取消的分析结果会被丢弃。如果解析错误导致分析在尚未生成任何注解前就中止，查询会继续使用上一次的分析结果，同时服务器发布最新的诊断信息。与现有扩展一致，诊断信息覆盖从该根可达的所有文件，无论文件当前是否打开；当根不再引用某文件时，会清除该文件的诊断信息。

**根管理。** `initialize` 会带入每个工作区文件夹配置好的入口列表。对不被任何当前分析所覆盖的文件触发 `didOpen` 时，该文件会成为一个独立的新根，并在文件关闭时移除。被多个根同时引用的文件在查询时归属于配置顺序中的第一个根，而当它发生变更时，所有引用它的根都会重新分析。标准库会被每个导入它的根各自解析一遍，性能实测表明这完全可以承受（解析耗时仅占检查耗时的十分之一）。

**位置转换。** 服务器持有每次分析中所有文件的文本（`Ast` 原本就持有它们）。协议位置通过沿行扫描并统计 UTF-16 代码单元转换为字节偏移；反向扫描则得到协议范围。对于协商采用 UTF-8 的客户端，列号本身就是字节偏移。`LoadSource` 会剥离字节序标记（BOM），服务器也会从覆盖层文本中剥离 BOM，从而使偏移量与从不显示 BOM 的编辑器保持一致。

<a id="5-compiler-additions"></a>
## 5. 编译器新增能力

以下按改动规模从小到大排列；每一项都可独立产生价值，且无需通过 LSP 协议即可单独测试。

**A. 位置信息。** 向 `Line` 添加 `int col`：1-based 的字节列号，与现行 `FunVal::col` 一致。在 `Parser::CurLine` 中通过 `lex.attr.data() - lex.toklinestart` 设置它，并移除 `FunVal::col`。为 `Field`、`Param`、`GenericParam`、`SVariant` 与 `Import` 添加 `Line`；`VarDef` 已经拥有该字段。

随后记录结束位置。词法分析器将上一个 token 的结束位置记入 `prevend`。`Node` 增加 `int end`，存储文件内的字节偏移或结束行列号。38 个解析函数分别使用 `Finish(node)` 辅助函数将其设置到返回的节点上。`SFunction` 与各类类型的声明解析器也做同样处理。

此后，实例化调用链只需通过 `Line` 即可定位一个代码块，而类型检查错误也能覆盖节点的完整范围。`Line` 在每个节点和类型中从 8 字节增长到 12 字节，没有可测量的性能开销。

**B. 源码提供器。** 将 `ParseProgram` 的 `rootsource` 改为 `function<const string *(const string &path)>`，在加载任意文件前优先咨询该回调，未命中再调用 `LoadSource`。`--roundtrip` 传入一个将转储结果作为根文件返回的提供器；服务器则传入覆盖层。

**C. 结构化诊断信息。** `Diagnostic` 包含文件索引、起止位置、严重级别、消息以及关联位置（实例化调用链中的各帧，每帧携带其渲染后的头部文本作为消息，与现行扩展展示方式一致）。`CompileError` 在保留文本的同时携带一个 `Diagnostic`。`Lexer::ErrorAt`、`TypeCheck::ErrorIn`、`ParseProgram` 中的导入错误、`BCE::CheckfreeReport` 以及驱动自身的错误都填充该结构，并由单一函数 `Render(ast, diagnostic)` 生成现行文本，确保其头部和消息继续与测试用例匹配。警告不再自行打印：`PrintWarning` 将警告交给驱动设置的接收器（sink）。CLI 的接收器沿用现行做法立即输出，服务器则将其收集起来。为 `check` 新增 `--diagnostics json` 标志，将结构化诊断作为单个 JSON 数组输出到 stdout（复用 `lsp_rpc.h` 中的写入器），供脚本和扩展的回退路径使用。

**D. 错误恢复。** 分为相互独立的两部分。

*D1，解析器恢复。* `ParseBlockBody` 和 `ParseTopDecl` 捕获来自语句或声明的 `CompileError`，记录错误后跳过至当前语句结尾（同一块深度下、大括号配对后的下一个 `;` 或 `}`）或当前声明结尾（函数体/定义体的匹配 `}`，或下一个 `;`）。丢失过语句的代码块标记为 `broken`。函数体损坏的函数仍保留其签名并获得 `SFunction::broken` 标记，使得文件中的其他声明仍可继续解析。检查器会检查损坏的函数体直到丢失的语句为止，之后不再报错。对损坏函数的调用按其签名进行检查，其返回值的根取最宽松情形，避免单处错误引发连锁误报。试探性解析不受影响：它们会在自身作用域内捕获错误，随后正式解析在外部再次失败时才由恢复逻辑接管。另外还有一种恢复对自动补全至关重要：后面没有标识符的 `.` 会被解析为一个名称为空、标记为未完成的 `Dot`。检查器会检查其对象表达式的类型，然后静默地在该处停止检查当前函数体（§6）。

*D2，检查器恢复。* 构造函数按顺序检查各个根：全局初始化器、`main`、每个 `thread_fn`、每个未到达函数（`CheckUnreached`）、导出函数，然后是全程序收尾检查（fixups）。每个根都被包在恢复边界内。遇到错误时，检查器会：

* 记录该错误；
* 将 `frames`、`scopes`、`vars` 以及每函数体状态恢复到进入该根时的状态（它们都是普通 vector，只需截断到入口大小即可；`CheckSpecBody` 由自身而非 RAII 守卫来压入和弹出 `frames`，以便由 catch 块负责弹出）；
* 将自该根开始以来创建的所有 `FnSpec` 标记为 `failed`；
* 继续检查下一个根。

失败的特化绝不会被复用：`GetOrCreateSpec` 在匹配时会跳过它们，而原本会复用它的调用自身也是一个错误，但因为属于衍生错误而不予报告。全程序收尾检查（`SettleParamRootExactness`、`VerifyLiterals`、`CheckGlobalShrinks`）仅在成功完成的特化上运行。借此，某个函数中的错误只会导致依赖它的函数失去诊断信息，这正符合编辑器用户对全程序检查器的预期。在此项改动落地前，CLI 仍会在第一个错误处停止；落地后，`k check` 也会按根顺序打印所有错误。`errors_tc/` 测试用例原本就按每个文件仅含一个错误编写，保持不变。

**E. 禁用拉取。** 每次工作区分析都向程序加载器传入 `PackageFetchMode::Offline`。包解析遇到未缓存的包时，会在其 `import` 处报错。`k check --offline` 复用同一模式，用户可通过 `k fetch` 填充缓存。

**F. 分析取消。** 为 `Ast` 添加 `const atomic<bool> *cancel`，由 `ParseTopDecl`、`CheckSpecBody` 和 `CheckStmt` 轮询。当该标志置位时，它们抛出专用的 `Cancelled` 类型。它不是 `CompileError`，因此既不会被试探性解析捕获，也不会被 D1 和 D2 捕获。

**G. 着色器缓存。** `CompileShader` 和 `CompileShaderFile` 在真正编译前先查询一个进程级映射表（以着色器阶段和源码文本为键），而 `Ast::shaders` 继续保存供代码生成读取的单程序映射表。

**H. 文档注释。** 词法分析器将紧邻某个 token 上方、各自独立成行的连续 `//` 注释文本保留为 `Lexer::doc`（遇到空行或任何 token 即结束该段注释）。声明解析器将其保存到 `SFunction`、`SStruct`、`SEnum`、`SAlias`、`VarDecl`、`Field` 和 `SVariant` 中（作为指向源码的 `string_view doc`）。无需引入新语法：标准库中现有的注释只要直接位于声明上方就会自动成为悬停提示文档，而后面隔着空行的横幅注释则不会附着到任何声明上。

**I. `k lsp`。** 即服务器本体（§4）：在包含 §6 全部特性后，代码体量大致与 `bce.h` 相当，且除 `lsp_analysis.h` 外几乎没有编译器耦合逻辑。

无需构建的部件：增量解析器、独立的符号数据库、改动特化键或克隆机制的设计，以及自建代码格式化器（`Dump` 会丢弃注释且会把 `guard` 打印成降级后的 `if`，因此不能用作格式化器；`k format` 才是，它基于 token 而非语法树构建，且 `format.h` 中的 `Format` 是纯函数，服务器直接调用即可）。

<a id="7-the-extension"></a>
## 7. VS Code 扩展

`src/client.js` 通过 `vscode-languageclient` 以配置的 `compilerPath` 启动 `k lsp`（当前协议版本为 LSP 3.18；这里所需的一切特性 3.17 均已满足）。它将设置作为 `initializationOptions` 传入，并在后续配置变更时通过 `didChangeConfiguration` 同步，新增重启命令，并复用现有的输出通道记录服务器日志。语言客户端库将成为该扩展的第一个运行时依赖，因此扩展会使用 esbuild 打包进 `dist/extension.js`，而 `vsce package` 仍保留 `--no-dependencies`。`build_vsix.py` 会在打包前执行构建打包步骤。语法规则、代码片段、语言配置、任务、运行与构建命令以及快捷键均保持不变。状态栏条目改为根据服务器发布的诊断信息推算状态，而不再依赖检查队列。

回退机制：激活时客户端会执行 `k lsp --probe`，该命令打印协议版本号并退出。若编译器尚未提供该子命令，扩展将保持原有行为，其中 `diagnostics.js` 在编译器支持时读取 `check --diagnostics json`，否则回退到解析文本输出。基于正则表达式的大纲和导入链接仅在没有服务器时才注册。这使得同一个扩展在过渡期内能兼容所有版本的编译器；待服务器随正式版发布后，便可移除回退逻辑。

其他编辑器：Neovim 的 `lspconfig` 配置与 Helix 的 `languages.toml` 配置各自只需几行，将与扩展的 README 一起放入 `docs/`。

<a id="8-testing"></a>
## 8. 测试方案

**编译器侧（不走协议）。** 现有测试用例继续匹配头部与报错消息，改动 C 不会破坏它们。抽取若干 `errors_tc/` 用例以 `--diagnostics json` 运行，对照预期 JSON 校验结构字段（位置、范围、关联位置）。恢复机制（D）在 `test/errors_tc/recovery/` 下拥有独立用例：包含多处错误和预期错误列表的文件，待 CLI 支持输出全部错误后直接用 `check` 运行，在此之前则通过 JSON 标志运行。

**服务器侧。** `test/lsp_protocol.py` 位于 `cli_paths.py` 旁，它通过管道启动 `k lsp`、执行初始化、打开 `test/lsp/` 中的测试用例，并运行注释中指定的查询（`// lsp: hover 12:7 "x: i64"`、`// lsp: definition 12:7 -> 3:4`、`// lsp: complete 20:9 has push`），比对返回结果。它还会将文档编辑为错误状态再改回，验证诊断信息随之更新，以及测试在编辑变更时取消正在进行的分析。该脚本作为 `run_tests.py` 的一部分，在三大平台的 CI 中运行。`test/lsp_sweep.py`（§12）则是针对仓库内所有程序的全量压测，按需手动运行。

**扩展侧。** 保留原有的 `node:test` 单元测试，同时 `compiler.test.js` 增加 JSON 解析路径的测试。运行在真实 VS Code 实例中的扩展宿主测试（extension-host test）会通过 `vscode.executeHoverProvider` 和 `vscode.executeDefinitionProvider` 请求悬停提示与定义跳转，并校验服务器返回的结果。目前 CI 尚未运行扩展测试；引入需要与编译器保持同步的服务器后，CI 需要在 Linux 上增加运行 `npm test` 的任务。

<a id="9-the-plan"></a>
## 9. 实施计划

**阶段 0，仅编译器改动：** A（列号、声明子部件位置、结束位置）、B、附带 `--diagnostics json` 的 C、E、H。扩展读取该 JSON 并绘制精确范围的下划线，同时展示警告和实例化调用链——在语言服务器存在之前就已经能带来肉眼可见的体验提升。每一项都是独立改动并配有各自测试。A 与 C 已经合入（`docs/implementation.md` §2，`test/diagnostics_json.py`）：一条诊断的范围从其节点在锚点行上最早的 token 延伸至该节点的结束位置，而函数调用锚定在其被调表达式上而非 `(` 上。B（`ParseProgram` 的 `SourceProvider`）、E（`--offline`、`PackageFetchMode::Offline`，在导入处报错）以及 H（声明、字段与变体上的 `Lexer::doc`，可通过 `--dump-docs` 打印）也已合入。扩展侧读取 JSON 的适配工作单独成一项任务。

**阶段 1，基础服务器：** F、G、`k lsp`（包含 §4 的传输层、工作区与分析框架），以及编辑时实时诊断、悬停提示、跳转到定义、文档与工作区符号、语义标记和签名帮助——所有这些都可以直接由首错中断式分析生成的注解支撑。同时包含扩展客户端与回退逻辑，并从一开始就配套 `test/lsp_protocol.py`。这一阶段已合入。服务器架构记录于 `docs/implementation.md` §12（`lsp_rpc.h`、`lsp_workspace.h`、`lsp_analysis.h`、`lsp_features.h` 和 `lsp.h`，以及 `Ast::CheckCancel` 和 `CompileShader` 中的着色器缓存）；其索引按每个文件每个名称记录一次出现位置，而非维护按位置映射节点的完整表。扩展客户端位于 `vscode/src/client.js`：通过 `k lsp --probe` 探测、使用 esbuild 打包的 `vscode-languageclient` 客户端，并为无该子命令的编译器或关闭 `klang.useLanguageServer` 的情况保留保存时检查模式。

**阶段 2，多错误报告与完善特性：** D1，随后是 D2；自动补全（两种形式）、查找引用与重命名、内嵌提示、折叠与选区范围。`k check` 报告全部错误。D1 与 D2 已合入（`docs/implementation.md` §2 和 §3.1）：

* 解析器按语句恢复（`Block::brokenat`、`SFunction::broken`、`Dot::incomplete`）并按声明恢复（丢弃整条损坏声明），随解析过程实时报告每条错误（`Ast::Report`，保存在 `Ast::errors` 中）。
* 检查器将损坏的函数体检查至出错位置，随后仅依据签名完成该特化（`Abandoned`），从而使对损坏函数的调用仍可依据签名继续检查，调用方继续往下推进。
* 每个根由 `CheckRoot` 检查，它会报告该根的错误并将检查器状态恢复到进入该根时的状态（`Checkpoint`）。

对前文设计的一处细化：只有错误发生时正在检查其函数体的那些特化才会被标记为 `failed`。在错误前就已经检查完成的特化是健全的，保留其可复用性可以避免牵连调用它的其他根（例如 `main` 在自身出错前调用过的辅助函数）。该根为全程序收尾检查记录下来的信息也会保留，因为它对应的是已完成检查的代码行为。构建过程被错误打断的 struct 和 enum 实例同样标记为失败，对它们的任何使用都会终止当前根，行为与调用失败的特化一致。对于存在错误的程序，服务器会跳过优化器与边界检查消除，直接基于已有注解回答查询。测试用例位于 `test/errors_tc/recovery/` 和 `test/lsp/recovery.k`。

声明内部错误与导入失败的恢复也已合入（`docs/implementation.md` §2 和 §3.1，`test/lsp/broken_decls.k`）：

* 在名称之后发生错误的 struct、enum 或顶层函数会保留错误前已解析的部分并标记为损坏（损坏的函数没有函数体，其调用也没有可校对的依据）。该声明缺失的部分属于衍生问题，检查器不再二次报错。
* 名称解析在书写处报告未知名称，并不再中止分析，而是为该使用处赋予一个表示“无类型/未知”的占位类型。由此产生的值同样属于衍生问题。
* 导入失败会在导入语句处报错，程序会在缺少该模块的情况下继续检查，该模块中的名称在使用处表现为未知名称。

不依赖错误恢复即可工作的其余特性也已合入（`docs/implementation.md` §12）：

* 查找引用与重命名：通过克隆体将使用处解析到的声明位置来识别同一名称；重命名对内建项、关键字和合成名称返回错误响应以拒绝修改；
* 为 `let` 与 `var` 的类型以及调用处的参数名称提供内嵌提示；
* 为代码块和连续注释提供折叠范围；
* 基于索引记录的节点范围（`FileIndex::spans`）提供选区范围。

分析索引在优化器运行之前构建，因为优化器会内联调用并消除常量，导致对应的克隆体信息丢失。自动补全也已合入（`docs/implementation.md` §12，`test/lsp/complete.k`）。作用域内名称取自解析树；成员补全取自 `.` 之前值在克隆体中携带的类型，包括 UFCS 函数与内建成员（其中包含首参数为泛型结构体的泛型函数，例如标准库池类型，`test/lsp/pools.k`）；而在 `::` 之后，补全会提供该命名空间下的所有声明。至此，阶段 2 全部完成。

**阶段 3：** 代码透镜、面向泛型的样本实例化、当工作区规模确实需要时再引入的单文件解析缓存，以及其他编辑器的配置说明。样本实例化已合入（§11；`docs/implementation.md` §3.1 和 §12，`test/lsp/exemplar.k`）。在检查完真实根之后，服务器检查会为每一个未被任何根特化过的泛型函数创建一个绑定了不透明类型的特化。该特化中的任何错误都会静默终止它，且后续 pass 完全看不到它。各项编辑器特性像读取普通克隆体一样读取该克隆体，并标明哪些类型来自样本实例化。在整个测试语料库（2,500 个文件）上，它不会改变服务器的任何诊断结果，总分析耗时大约增加六分之一，而在任何大型程序上均无明显耗时变化。

代码透镜也已合入（`docs/implementation.md` §12）。它会在每个泛型函数上方显示实例化次数（VS Code 扩展会用快速选择列表 `klang.showInstantiations` 列出具体位置），并在 `main` 上方显示 “Run”（调用扩展的运行命令）。只有当客户端的初始化选项中列出了对应命令时，代码透镜才会携带该命令，且服务器会在每次分析后发送 `workspace/codeLens/refresh`。其他编辑器的配置说明位于 `docs/editors.md`：包含 Neovim、Helix 和 Emacs（Eglot）。

阶段 0 和阶段 1 合起来构成了编译器侧的大部分工作；阶段 2 的各项特性则主要是服务端代码基于阶段 0 提供的数据进行加工。

<a id="10-deferred-and-open"></a>
## 10. 延后与开放问题

* **样本实例化。** 已在 §11 中完成设计并实现。关于 `T` 支持哪些操作的问题，通过为运算符和成员访问赋予不透明结果类型来解决；关于特化键的问题，则通过像检查未到达函数那样、与真实特化完全隔离地检查样本来解决。仍待完善之处：目前样本会在遇到第一个不支持的操作时结束。最常见的情况包括：在期待 `T` 的位置出现字面量（`var total: T = 0`）、将 `T` 传给内建函数（`print`，或非重载集的 `hash`），以及把类型参数当作函数值调用（`F(x)`）。后一种情形下，该类型参数其实可以绑定到一个调用后返回不透明结果的函数值上。此外，嵌套泛型函数以及仅被其他样本调用的泛型函数，目前仅覆盖到外层样本函数体能够触及的范围。
* **跨程序重命名。** 被多个根引用的模块会从各个根分别收集编辑项；服务器按位置对其取并集。带命名空间限定符的名称仅重命名其末级名称。内建项、关键字和合成名称不可重命名。该能力已合入，查找引用与传入调用同样支持跨根聚合（`docs/implementation.md` §12）。
* **CLI 错误头部中的列号。** 所有带有列号的错误和警告都会打印源码行，并在节点下方标出插入符（若节点位于同一行则为 `^~~~`），扩展文本解析器也会从中读取列号。命令行头部仍保持 `file:line:`；测试运行器和扩展解析器都已经能识别 `file:line:col:` 头部（§2），因此在 CLI 头部加上列号纯属展示风格选择，且无论如何都已有 JSON 格式可用。
* **位置编码。** 已实现。若客户端在 `general.positionEncodings` 中列出了 `utf-8`（如 Neovim、Helix），则在初始化响应中获得 `"positionEncoding": "utf-8"`，其列号直接使用字节偏移而无需换算；其他客户端则按 VS Code 要求使用 UTF-16。落在多字节字符内部的 UTF-8 列号会回退到该字符起始位置。不提供 `utf-32`。
* **浏览器端扩展。** 将编译器编译为 WebAssembly 运行在扩展宿主中可以支持 `vscode.dev`；但编译线程、进程运行器以及 TinyCC 意味着这需要一次完整移植，而非添加一个构建选项即可解决。暂无计划。
* **内存占用。** 每个根对应一棵 `Ast` 并整体替换；配置了许多入口文件的工作区会持有多个 `Ast`。若成为瓶颈，可以改为惰性分析（仅分析存在已打开文件的根），并在其相关文件全部关闭时释放——§4 的根选择机制已经为这种做法留好了余地。

<a id="11-exemplar-instantiation"></a>
## 11. 样本实例化

未被任何代码调用的泛型函数没有特化，因此其函数体内部没有任何类型信息。样本（exemplar）就是服务器为了填补缺失调用而请求生成的特化：即把每个类型参数都绑定为一个不透明类型后，对函数进行一次检查。

**不透明类型。** 每个类型参数以及每个未标注类型的参数，都会绑定到一个全新的、标记了 `TypeName::opaque` 的 `TY_GENERIC`，其打印名称为参数名（如 `T`；未标注类型的 `x` 则显示为 `type of x`）。它只代表其自身：

- 它只与自身相等（按其 `TypeName` 比较，`const` 副本共享同一个 `TypeName`）；
- 检查器将其视为具体类型（类型替换保持其不变，`HasGenerics` 对其返回 false，且 `ValidateType` 接受它）；
- 它是定长、扁平且不含引用的值——这与尺寸分类和根查询对其他未特别处理的类型所给出的默认属性一致。

它自身没有任何字段、成员或运算符；检查器为其赋予以下规则：

- 含有一个不透明操作数的二元运算：比较运算返回 `bool`，其他运算返回该不透明操作数的类型（两者皆为不透明类型时取左操作数的类型），因此两个 `T` 相加 `a + b` 的结果仍为 `T`。一元 `-` 和 `~` 返回操作数本身的类型，对不透明目标的复合赋值接受任意类型的右操作数。
- 对不透明值的成员访问（无论读写）返回一个由所有此类访问共享的通用不透明类型 `?`：样本无法得知成员究竟是什么。调用一个带不透明参数（参数类型任意深度中包含不透明类型）的函数时，若没有任何重载能接受该参数（例如 `hash(key)`，这只有真实类型绑定才能解析），同样返回 `?`。若某个重载拥有泛型参数，则该重载可以接受此类参数，并且被调函数会像处理普通实参绑定那样针对该不透明绑定生成特化。
- 从不透明类型出发或转换到不透明类型的 `as` 表达式返回目标类型。
- 其余一切均为错误：在期待不透明类型的地方出现字面量、将不透明值传给内建函数、把类型参数当作函数值调用（`F(x)`），以及对不透明值执行下标索引、迭代或真值测试。

**检查过程。** 服务器会设置 `Ast::exemplars`，而 `k check` 从不设置。在检查完所有真实根并应用全程序收尾检查之后，编译器会为每一个带有类型参数或未标注类型参数、且未被任何根特化过的顶层函数创建一个样本。

样本的检查方式与 `CheckUnreached` 检查未到达普通函数一致：每个引用、切片或持有者参数都视为可写，并分别植根于各自独立的类型类。所有错误均被抑制。遇到 `CompileError` 或 `Abandoned` 时，会静默结束当前样本并将检查器恢复至根入口状态，与 `CheckRoot` 相同。同时不会发出任何警告。

出错之前已生成的注解都会保留下来。因此，样本能够覆盖从函数开头直到第一个不被其不透明类型支持的操作为止的代码。对于只涉及移动、比较和透传 `T` 的函数体，这足以覆盖整个函数体。

**隔离性。** 样本运行在所有会输出报告的步骤之后，因此它们记录的任何信息都不会流入全程序收尾检查或诊断报告。样本内部的函数调用不会复用真实根所生成的特化，而是生成属于自己的新特化。一旦复用真实特化，就会把样本调用点的信息混入特化键之外的属性中（`RootArg::exact`、`concrete`、所需目标集合等），而后续 pass 会读取这些属性。当所有样本检查完毕后，它们创建的全部特化都会从 `ast.fnspecs` 和对应函数的 `specs` 中移出，转存至 `Ast::exemplarspecs`，并标记出创建它的样本所属函数（`FnSpec::exemplar`）。因此，优化器、边界检查消除、`--specs` 以及实例化计数都不会看到样本特化；同时因为所有真实调用早已先一步检查完成，也没有任何真实调用可能复用到样本特化。

**服务器侧。** 在处理完真实特化之后，`Analysis::Build` 会索引属于样本所属函数或其嵌套函数的样本特化，并记录哪些克隆体属于样本。它会跳过样本为被调函数生成的特化，因为那上面携带的是调用方的不透明类型，对被调函数本身毫无意义。此时在 `a` 上悬停会显示 `a: T`，后附“in an exemplar instantiation”（位于样本实例化中）。`.` 后的自动补全同样从克隆体读取对象类型（例如切片元素的内建成员，或对不透明值仅列出首参数为泛型的函数）。签名帮助和定义跳转沿用克隆体的解析结果，而查找引用与重命名也能找到这些使用处。当光标悬停在导致样本提前终止的错误之后的名称上时，提示会说明样本实例化在此之前已经停止。

<a id="12-the-sweep-and-its-baseline"></a>
## 12. 全量压测与基线数据

`test/lsp_sweep.py` 是针对仓库内所有 K 程序的服务器稳定性与延迟压测脚本，按需手动运行（其中 `--quick` 子集足够轻量以至于测试套件可以负担，但目前 `run_tests.py` 尚未包含它）。脚本会并发启动八个服务器进程，将 `samples/` 下的每个文件、`test/k_in_k/main.k`、每个标准库模块、`test/*/` 下的每个正向测试用例（`errors/`、`errors_tc/`、`lsp/` 和 `k_in_k/` 除外），以及每个 `errors/` 和 `errors_tc/` 测试用例分别作为独立根打开。对每个文件，压测会执行以下流程：

* 等待其诊断信息发布；
* 在每一个标识符起始位置以及每一个紧跟在 `.` 之后的位置（按词法扫描定位，跳过注释和字符串）请求悬停提示、跳转到定义、自动补全和签名帮助；
* 请求一次语义标记、文档符号、折叠范围、内嵌提示和代码透镜；
* 连续发送十次随机单字符编辑并等待诊断信息；
* 将文本恢复原状并等待最初的诊断信息重新发布；
* 关闭该文件。

只要出现服务器异常退出、返回错误响应、单次请求耗时超过两秒、服务器停止响应，或输出非协议消息，测试即判定失败。报告会按最慢请求对文件排序，并列出每种请求的最慢耗时、所有失败项以及下表所示的总计数据。

**基线数据**（2026 年 10 月，本机，八个服务器并发）：

| | |
|---|---|
| 文件数 | 2,531（31 个示例、1 个自举程序、11 个标准库、581 个常规用例、60 个 `errors/`、1,847 个 `errors_tc/`） |
| 测试位置数 | 260,878 |
| 总请求数 | 1,058,698 |
| 最慢单次请求 | 3.5 ms（自动补全，`test/ui/ui_popups.k`） |
| 各方法最慢耗时 | 语义标记 2.8 ms；签名帮助 1.7 ms；悬停提示、跳转到定义 0.3 ms；代码透镜、符号 0.2 ms；内嵌提示、折叠范围 0.1 ms |
| 分析耗时（`didOpen` 到发出诊断） | 中位数 0.6 ms，第 90 百分位 4 ms，最慢 154 ms（`k_in_k/main.k`） |
| 突发编辑后的分析耗时 | 中位数 161 ms，其中 150 ms 为防抖延迟 |
| 全量压测总耗时 | 123 s |

这些数据为后续维护者揭示了以下事实：

* **每次请求均低于 2 ms**（在超过一百万次请求中）；单次请求开销最大的是自动补全（需要连同详情一起写入作用域内的每一个名称），其次是语义标记。在下面第二项修复合入之前，压测曾记录到的最慢请求为 15 ms。
* **第一项发现：按单字节引用出错字符。** 词法分析器的 "illegal character" 和 "unknown escape sequence" 错误消息此前只引用了字符的单个字节。因此遇到多字节字符时，诊断文本和服务器 JSON 中都会产生非法 UTF-8 序列，导致严格校验 UTF-8 的客户端无法读取。实测触发案例是在某次编辑破坏了 `//` 注释符号后，注释里的不换行空格（non-breaking space）裸露出来。现在词法分析器会连同码点一起引用完整的字符（`Utf8CharAt`、`QuotedCharAt`；`errors_tc/recovery/lexer.k` 中有对应示例）。
* **第二项发现：分析完成后的第一个请求被旧分析的释放过程阻塞。** 替换某个根的分析结果时，此前是在发布诊断之后直接在工作线程上销毁旧的 `Ast`。对于 UI 测试用例这会耗时 6 ms，doom 示例耗时 8 ms，自举编译器耗时 13 ms（占检查时间的十分之一），从而拖慢紧随其后的下一个请求。在编辑器中，那个请求恰好就是每次分析结束后触发的代码透镜、语义标记和内嵌提示刷新。现在，旧的分析结果以及被移除根的分析结果都会交由独立线程异步释放（`Workspace::Reap`），使得分析或关闭文件后的下一次请求与其他请求一样快。
* 全程没有任何请求返回错误，没有服务器退出或无响应，且恢复文本后的诊断结果始终与最初完全一致。
* **某个根的错误可能会发布在另一个文件的 URI 下。** 有 11 个 `errors_tc/` 用例和 2 个 `errors/` 用例在根文件自身没有任何诊断信息。它们的错误位于 `std.k`、`exception.k`、`dictionary.k` 或某个包文件中由该测试用例实例化的函数里，因此诊断发布在那个文件上，并由关联信息中的实例化调用链指回根文件。编辑器会在“问题”列表中的标准库文件下显示这条报错。这类错误是否也应该在根文件的实例化调用处额外报告一份，目前仍是一个开放问题。
* **包错误的报告方式与 `--offline` 一致。** 凡是导入了未缓存于 `K_HOME/pkg` 中的包的示例或用例（压测在存在 `build/klang-home` 时将服务器指向它，否则指向 `$K_HOME`），都会在其 `import` 处收到 "not fetched" 错误，而程序的其余部分仍会正常分析；gfx 的 `_err_` 用例则会像 `k check` 那样报告着色器错误。
