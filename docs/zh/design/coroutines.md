研究笔记，2026 年 10 月。本文内容均尚未实现，每一处语法均为占位符。本文探讨的问题是：K 是否应当引入协程或异步特性、契合本语言栈模型的最小可用形式是什么，以及已有该特性的语言从中获得了哪些经验教训。这里提出的答案是一种*无栈*协程，其帧是一个普通的定长 K 值：通过结构体字面量启动，由一个内建操作驱动，并由程序自行选择的任意库来调度。第 4 节为具体设计，第 6 节为各部分权衡过的替代方案，第 8 节为构建顺序。

语言级提案规定了 `async fn`、显式 `await`、任务所有权与取消机制。[一等异步函数与装饰器](async_and_decorators.md)

<a id="0-summary"></a>
## 0. 摘要

* **出于必然的无栈设计。** K 函数的局部变量存放在原生栈或数据栈上，而挂起的函数两者都无法保留（2.1）。有栈纤程需要为每个纤程预留一组数 GB 的数据栈（2.3）。因此，协程会被编译为状态机——正如 Rust、C++、C# 和 Kotlin 的做法——而它的状态是一个定长值。
* **规则早已存在。** §7.8 禁止递归函数在非定长局部变量仍在作用域内时回调进入其循环。将递归调用替换为挂起点，同一条规则便保证了挂起的协程不持有任何数据栈（2.2）。可增长数据由外部的池所拥有，正如递归和线程中的做法一样（2.6）。
* **协程既是函数也是类型。** `coro fn serve(c: Conn&) …` 声明了一个函数体中可以 `yield` 的函数，同时声明了一个同名的定长结构体类型 `serve`，用于存放其参数、跨越 yield 存活的局部变量，以及当前挂起位置的标记（4.1）。`serve { c }` 是一个尚未运行的帧（4.2）。在另一个协程中调用 `serve(c)` 会将其作为调用者状态机的一部分运行至结束（4.4）。
* **由一个内建操作驱动。** `resume(f, x)` 将帧运行至下一个 `yield` 或运行至结束，并返回让出的值以及是否让出；`result(f)` 读取已完成帧的结果（4.3）。让出与恢复的值都是扁平数据，而非回调：协程*告诉*恢复方它在等待什么，由恢复方而非唤醒器（waker）决定如何处理（2.7）。`yield` 可以指定它接受的应答（`yield w as Done`），使函数体只需处理这些变体，若传入错误变体则在发送该应答的 `resume` 处直接中止（4.3、6.10）。
* **其余一切皆由库实现**：事件循环、定时器、通道、取消机制、结构化并发、`select`、`run_blocking`、作为迭代器的生成器（4.13、5）。语言提供状态机以及容纳它的值；语言本身不分配内存、不加锁、也不通过指针进行间接调用。
* **其余情况零开销。** 没有运行时状态，没有线程局部变量，不改变普通函数的编译或调用方式。不含 `coro fn` 的程序编译出的 C 代码与今天完全相同。
* **每核一线程是服务器的架构**，而 K 已经具备它：工作线程不共享任何内容且各自拥有全局变量，因此写作全局变量的反应器（reactor）及其池按构造就是每工作线程独有的（2.5）。Go 风格的任务跨线程迁移既不可能也不需要；但扁平的帧仍然可以通过队列发送（4.9）。

<a id="1-what-the-feature-is-for"></a>
## 1. 该特性用于解决什么问题

<a id="11-the-server-workload"></a>
### 1.1 服务器工作负载

预期该特性将首先用于服务器基础设施，而这一工作负载决定了真正重要的因素：

* **等待远多于线程数。** 一台服务器承载 10⁴ 到 10⁶ 个连接，每个连接大部分时间都在等待：等待下一批请求字节、等待后端响应、等待定时器、等待套接字可接收更多输出。每个连接拥有少量的状态（处于协议的哪个阶段、已解析到哪里、哪些缓冲区属于它），这些状态必须在等待期间得以保留。
* **内核告诉你什么已就绪。** `epoll`、`kqueue`、IOCP 和 `io_uring` 向程序交付一批事件；程序找到每个事件对应的连接并运行它，直到它再次需要等待。无论用什么语言，每一台现代高性能服务器的核心都是这样一个循环。协程特性的价值，正在于让每个连接的逻辑可以写成直线式代码，而调度循环本身保持不变。
* **每次事件的开销就是全部胜负所在。** 两次等待之间的工作通常只有几百条指令（解析头部、复制响应）。如果一个特性在每次等待时增加一次分配、一次锁操作、一次原子操作或一次间接调用，其开销是可测量的；如果只增加一个 switch 和几次加载，则微乎其微。
* **每连接的内存占用决定了规模上限。** 几十字节的帧配合池中的缓冲区可以让百万级连接装入内存；每连接一个栈则做不到。
* **通过每核运行一个循环来利用多核**，由内核将连接分发到各个核（`SO_REUSEPORT`、网卡队列），而不是在核之间迁移连接。这就是 Seastar、glommio 和 monoio 的设计（3.9），也是基准测试中表现最快的设计。

同样的机制也适用于跨帧运行的游戏与 UI 逻辑（第 7 节中的巡逻示例），以及生成器。

<a id="12-the-constraints"></a>
### 1.2 约束条件

本笔记的任务要求可以重述为该设计必须通过的几项检验：

1. **实用**：手写状态机必须明显更糟。手写状态机（`samples/31_mini_doom.k` 中的 `Actor` 为此维护了 `timer`、`pain`、`death` 和 `attacking`）把一段顺序过程拆散到枚举和 `match` 中；编译器可以保留顺序过程而替程序员生成枚举。
2. **薄（Thin）**：新增规则越少越好，且每条都能从语言现有规则推导出来。不能有黑盒：阅读生成的 C 代码的人应当能直接认出其中的结构体和 switch。
3. **最廉价的表示**：帧仅包含参数、跨越 yield 的局部变量和一个标记（tag），别无他物；每次 resume 除了函数调用和 switch 之外没有任何额外操作。
4. **对不使用该特性的代码零开销。**
5. **其余部分由库构建。** 调度、I/O 集成、定时器、取消策略和结构化并发在服务器、游戏和嵌入式程序中各有不同的选择；语言本身不固化其中任何一项。
6. **充分利用已经让 K 变快的机制**：池、相对引用、经由队列传递的扁平值、无共享工作线程、就地构造、全程序特化。

<a id="2-what-k-already-decides"></a>
## 2. K 已做出的决定

大部分设计都由语言规范自然导出；本节汇总了约束该设计的各项规则及其出处章节。

<a id="21-a-suspended-function-can-keep-neither-of-its-stacks"></a>
### 2.1 挂起的函数无法保留其两个栈中的任何一个

一个 K 激活记录将其定长局部变量存放在原生栈或寄存器中，将其非定长局部变量存放在数据栈上，每个位于编译器为它分配的栈索引处（§1.2、§10.3）。协程在函数体中间挂起并将控制权交还给恢复方；恢复方随后继续运行其他代码，并在之后再次恢复该协程，甚至可能从不同函数中的不同位置恢复。

* 原生栈已经消失：恢复方的被调函数会复用它。因此，跨越挂起仍然存活的每一个局部变量都必须保存到别处，并在恢复时重新加载。每一种无栈协程设计（Rust、C++、C#、Kotlin、Python 生成器）都正是这样做的。
* 数据栈也同样无法保留。栈索引是按特化静态分配的；如果一个挂起的协程占用了用于 `u8[>..]` 局部变量的索引 *k*，那么由同一个循环恢复的第二个同类协程实例也需要索引 *k*，恢复方自身的被调函数也同样如此。单个栈上生命周期严格嵌套的不变式（§1.3），正是一个挂起的帧会打破的东西。

因此，挂起的协程唯一能拥有的就是**一个定长值**：即保存下来的局部变量。这与规范对递归得出的结论相同，也与线程从另一端抵达的结论一致（`thread_fn` 因为是一个独立程序而获得自己的一组栈，§11.2）。

<a id="22-the-recursion-rule-is-the-coroutine-rule"></a>
### 2.2 递归规则即是协程规则

§7.8 规定：“循环中的任何函数在非定长局部变量处于作用域内时都不得回调进入该循环”，并附带针对调用语句中未命名非定长值的临时量规则 (a) 到 (d)。原因是否则每次激活都需要各自的数据栈。把“回调进入该循环”替换成“挂起点”，理由一字不差地成立：否则每个*挂起的帧*都需要各自的数据栈。

检查器已经实现了这一规则（`CycleCallTemps`、`CheckCycleInit`、`Node::nftemp`，implementation.md §3.11），代码生成也对其做断言（`NoStackAcrossCycleCall`）。协程在 `yield` 处需要相同的检查，程序员的应对方法也相同：将临时缓冲区声明在 yield 之前结束的代码块中，或者让外部拥有可增长数据并通过引用或池索引传入。§7.8 给递归循环的建议（“必须比递归调用存活更久的可增长数据应由循环外部拥有并传入：使用引用、切片、可复用池，或包含多个表引用的结构体，A.6”）也正是给协程的建议。

<a id="23-stackful-coroutines-are-out"></a>
### 2.3 排除有栈协程

*有栈*协程（纤程、goroutine、Lua 协程、Boost Context）各自保留一条原生栈并切换到该栈上；挂起只需保存寄存器并交换栈指针，函数体无需变换。这是更方便的模型：任何代码都可以在任意调用深度挂起，没有任何染色问题。但对于 K，它不只是不够理想，而是直接不可行：

* **每个纤程都需要自己的一组数据栈。** K 激活记录的非定长局部变量驻留在数据栈上，因此可能在调用树任意位置拥有 `u8[>..]` 的纤程需要像线程程序那样拥有一组 N′ 条栈（§11.2）。每条栈默认需要预留 `K_STACK_RESERVE` 字节（2 GB）外加保护间隙，而 N′ 是整个程序的栈计数（implementation.md §7）。地址空间预算（32 TB，§10.4）本就限制了 `hardware_threads()` 的上限，它最多也只能支持几千个纤程，若程序所用栈数较多甚至只有几十个。而服务器需要几十万个。
* **栈无法移动。** Go 通过复制增长栈来保持 goroutine 栈的小巧，这需要一张精确记录所有指向栈内指针的映射表以便重写指针（[Go 的连续栈设计][go-stacks]）。K 的引用是指向数据栈的裸地址，而数据栈的增长“绝不移动内存”（§1.2）；语言和运行时中没有任何机制能够重定位一个值。
* **切换原生栈需要汇编**，且按平台和 ABI 分别编写；进程内 TinyCC 后端仅在部分目标上支持汇编，而 wasm 则完全做不到（[wasm 栈切换提案][wasm-switch]目前仍处于提案阶段）。无栈协程编译为纯 C，可在 K 运行的所有地方运行。

Rust 也走到了同样的结论：其 2014 年的运行时曾拥有绿色线程，而 [RFC 230][rfc230] 移除了它们，原因正是每任务一栈的开销以及与原生代码的不匹配；五年后推出的 `async`/`await` 采用的便是无栈设计。更方便的模型在有界预算内依然可及，即作为可选加入的“自带栈的任务”（§11.3 的动态栈），它列在第 9 节的未来工作中，而非本特性本身。

<a id="24-function-values-are-inlined-so-hofs-cost-nothing-to-suspend-through"></a>
### 2.4 函数值会被内联，因此通过高阶函数挂起没有开销

函数值是编译期实体，会被内联拼接到接收它的函数中，该函数按每个函数值进行特化（§7.6、implementation.md §6.6）。因此，如果以一个会 `yield` 的代码块来调用 `fn each<F>(xs: i64[:]) { for x in xs { F(x) } }`，那么在该特化版本中它就是会 `yield` 的代码：它的局部变量（这里是循环索引）像协程自身的局部变量一样跨越 yield 存活，而 `each` 本身无需为此做任何声明。Kotlin 需要 `inline fun` 才能做到这一点；K 天生如此，这也使标准库的高阶函数无需再复制一份带染色的版本即可在协程中使用（3.4、3.10）。

<a id="25-threads-share-nothing-so-thread-per-core-is-the-shape"></a>
### 2.5 线程无共享，因此每核一线程是天然形态

K 工作线程从不共享可变内存，每个线程程序都是拥有自身全局变量的独立实例，只有扁平值能通过类型化队列跨线程传递（§11.2）。这决定了协程与线程如何结合：

* 协程运行在恢复它的线程上，并自由共享该线程的内存，因为同一时间一个线程上只运行一件事，且切换仅发生在 `yield` 处。不可能发生数据竞争，除了所有函数都遵守的规则外，也不需要为协程能访问什么额外制定规则。
* 用 K 编写的每线程事件循环，若把连接池和帧池作为全局变量，那么按工作线程隔离是自动成立的：每个工作线程的全局变量都是自己的副本。服务器为每个核派生一个工作线程，各自在自己的监听套接字上运行同一循环。这*正是*每核一线程、无共享架构（3.9）；K 从 §11.2 直接获得了这一架构，而非来自某个运行时。
* Go 那种由调度器在 OS 线程间迁移 goroutine 的模型既不可用（持有引用的帧无法跨线程），也不可取（把连接的帧从持有其缓冲区的池所在线程移走意味着把一切都复制一遍）。真正可用的是显式分发：所有字段均扁平的帧就是扁平值，可以通过 `qput` 发往另一个工作线程并在那里恢复（4.9）。阻塞工作（文件 I/O、DNS、CPU 密集任务）通过队列交给工作线程，协程像等待套接字一样等待回复。

因此，对于“K 的线程是否使某一种结合方式水到渠成”，答案是肯定的：每个工作线程一个循环，帧与缓冲区置于该工作线程的池中，跨线程的一切走队列。语言应当促成这种方式而不再多加限制；循环本身属于库代码（第 5 节）。

<a id="26-pools-own-what-a-coroutine-cannot"></a>
### 2.6 池拥有协程无法拥有的资源

协程无法在跨越 yield 时拥有 `u8[>..]`（2.1），而服务器需要为每个连接配备缓冲区。在 K 中，所有“每项一个可增长对象”的问题早已有解：定长元素的 `reusable` 池、`reusable[]` 切片池以及相对引用（§5.4、§3.9；`design/owning_dynamic_data.md`）。连接是池中的一个元素，其接收缓冲区是该元素内部的 `u8[..4096]` 有限数组，或是切片池中的一段连续区间，而它的帧只持有一个指向它的 4 字节 `in pool` 链接。帧保持扁平且小巧，缓冲区在协程挂起期间停留在内核可写入的位置（这正是 `io_uring` 和 IOCP 等基于完成的 I/O 所需要的，也是 Rust 的借用缓冲区 future 难以做到的，3.2），而释放一个连接只需对两个池调用 `free`。

<a id="27-no-function-pointers-so-the-scheduler-protocol-is-data"></a>
### 2.7 没有函数指针，因此调度器协议即数据

Rust 的 `Future::poll` 接收一个 `Waker`，它是一个 `(data pointer, vtable)` 对，由底层叶子 future 保存并在任务应再次被轮询时调用。C++ 向 `await_suspend` 传递一个 `coroutine_handle`，通过帧中的函数指针来恢复。Kotlin 的 `Continuation` 具有虚方法 `resumeWith`。K 没有运行时函数值（§7.6），因此协程无法向任何人递出回调。它也不需要这样做：恢复它的实体正是之后将再次恢复它的实体，并且该实体已经知道自己持有的是哪个帧。协程必须传达的是*它正在等待什么*，而那是一个值：`yield Wait.Readable { fd: fd }`。恢复它的循环把帧的索引记在这个 fd 名下，待该 fd 就绪时再恢复该帧，并将发生的结果作为 resume 值传回。这比唤醒器（waker）更廉价（无需克隆、无需引用计数、无需间接调用），它是扁平的，这也是本设计中 yield 携带类型化值的原因（4.3）。

<a id="3-what-other-languages-did"></a>
## 3. 其他语言的做法

<a id="31-the-taxonomy"></a>
### 3.1 分类体系

De Moura 与 Ierusalimschy 的论文[《重新审视协程》][revisiting]（TOPLAS 2009）是该领域的标准参考文献。协程设计在三个维度上做出选择：*有栈*还是*无栈*（能否在嵌套的普通调用内部挂起）；*对称*（任意协程可转交给任意其他协程）还是*非对称*（协程只让出给恢复它的调用方）；以及协程是否为*一等*值。该论文证明，非对称有栈一等协程具有与单次延续（one-shot continuations）相同的表达能力，这也是 Lua 所采用的设计。对 K 而言，2.3 决定了无栈；2.7 与简洁性决定了非对称；而帧作为普通值自然赋予了一等性，无需任何额外机制。

<a id="32-rust"></a>
### 3.2 Rust

[`async`/`await`][rfc2394]（自 2019 年 1.39 起稳定）将 `async fn` 编译为一个实现了 [`Future`][rfc2592] 的匿名状态机，由携带 `Waker` 的 `Context` 来轮询。其中被普遍认为正确、且本设计予以保留的部分包括：

* **惰性启动、内联嵌套、静态大小。** 首次 poll 之前什么都不运行；被 await 的内层 future 直接存储在外部 future 的状态*内部*，因此一个任务只需一次分配（甚至零分配：[embassy][embassy] 在微控制器上直接从静态分配的池中运行任务）。编译器会重叠从不同时存活的局部变量，解决了体积指数级增长的问题（[Mandry, "Optimizing await"][mandry]、rust-lang/rust#59897 及其后续工作）。4.12 的帧布局正是这种布局。
* **将执行器留给库**使语言保持小巧，也让每核一线程运行时（glommio、monoio）能够与工作窃取运行时（tokio）并存。

而引发著名争议的部分，以及本设计针对每一点的应对如下：

* **`Pin`。** future 可能跨越 `.await` 借用自身的局部变量，因此一旦开始轮询就绝不能移动；[RFC 2349][rfc2349] 引入 `Pin` 来表达这一约束，而它成了最常被提及的痛点（[boats, "Pin"][boats-pin]；[fasterthanlime, "Pin and suffering"][pin-suffering]）。2025 年的项目目标仍在改进 pin 的人体工程学（[2025H1 async 目标][rust-goals]；[2025 年 7 月更新][rust-july]）。K 通过规则而非类型 machinery 回避了这个问题：指向协程自身局部变量的引用不得跨越 yield 存活（4.5，R4）。于是帧就是一个普通值，可复制、可移动，迫使 Rust 诉诸类型系统的根源在此压根不会出现。代价是在*局部* `buf` 上写 `let s = buf[..n]; yield; use(s)` 会报错；缓冲区由外部拥有，而这本就是服务器形态所期望的（2.6）。
* **唤醒器使用动态分发**，且其所有权规则（工作窃取执行器要求任务满足 `Send + 'static`）引发了关于每核一线程的争论（[boats, "Thread-per-core"][boats-tpc]；[glommio][glommio]）。K 的协议只是一个值（2.7），并且线程本来就无共享。
* **取消即丢弃 future**，且没有异步 `Drop`（仅作过实验，[2025 目标][rust-goals]）；在两次 poll 之间被丢弃的 future 会丢失部分进度，于是有了 tokio 文档中围绕 `select!` 的著名[“取消安全性”][tokio-cancel]陷阱。K 没有析构函数，帧也不拥有可增长数据，因此丢弃帧除了帧本身什么都不会丢失；帧所指代的资源都在池中，由循环释放。协作式取消只是一个 resume 值（4.10）。
* **双生态与染色。** [Nystrom 的《你的函数是什么颜色？》][colors]命名了这种分裂；同步库与异步库彼此重复；trait 中的 async 直到 1.75 才稳定（[AFIT][afit]，2023），而 `dyn` async trait 至今仍未定案（[2025 目标][rust-goals]）；[boats 的《让 future 归 future》][boats-futures] 与 [async 愿景文档][async-vision] 记录了运行时的碎片化。K 同样存在染色（只有 `coro fn` 能 yield），但痛感轻得多：高阶函数对挂起透明（2.4），没有 trait 需要染色，并且任何普通函数都能用 `resume` 驱动帧（4.3）。源自 Python 社区的库设计建议 [sans-I/O][sansio]（只处理字节而从不做 I/O 的协议代码）正是 K 库的正确默认方式：只有等待本身才需要染色。
* **就绪模型与完成模型之争。** Rust 的 future 借用其缓冲区，因此需要内核在操作进行期间拥有缓冲区的 `io_uring` 与 IOCP 迫使生态另造新 API（tokio-uring、monoio）。K 的缓冲区生活在池中，因此一次 yield 可以直接把切片交给内核，且该切片在帧挂起期间保持有效（5）。
* 值得一提的是后续新增特性：async 闭包（2025 年 1.85 稳定）；返回类型记法（return-type notation）和带恢复参数的 `#[coroutine]` 生成器，两者目前均仍不稳定。后者是 Rust 中最接近 4.3 类型化 yield 的设计。

<a id="33-c"></a>
### 3.3 C++

C++20 协程（[cppreference][cpp-coro]）刻意做成了非常底层的构建块：包含 `co_await`、`co_yield` 或 `co_return` 的函数会被转换，关于它的一切（帧的分配方式、何时首次挂起、`co_await` 做什么、调用方拿到什么）都通过 `promise_type` 和 *awaiter* 对象定制。正如任务要求所预期的，它的教训主要是反面的：

* **堆上帧。** 帧通过 `operator new` 分配，除非编译器能证明其生命周期并将其消除（[HALO, P0981][halo]），而这仅在内联时可行，绝不可能发生在交给执行器的帧上。`coroutine_handle::resume()` 是一次间接调用。这两者正是本设计所拒绝的：帧是大小与类型已知的值（4.1），`resume` 是对已知函数的直接调用。
* **协议大杂烩。** 三个 awaiter 方法、六个 promise 定制点、作为特殊返回类型的对称转移（[Baker, "Understanding Symmetric Transfer"][baker-sym]；["Understanding operator co_await"][baker-await]）。标准直到 C++26 才附带任务类型；`std::generator` 在 C++23 到来（[P2502][p2502]），而面向 C++26 的 `std::execution::task` 于 2025 年在索菲亚在反对声中获批（[P3552R3][p3552]；[P3801][p3801]）。正面的教训正如任务要求所述：保持机制底层，但将*协议*精简为一个 `yield`、一个 `resume`，以及双向各一个值。
* **Senders/receivers**（[P2300, std::execution][p2300]）是一种惰性、无分配的组合模型，比 tokio 风格的 future 更契合 K 这样的语言：描述工作、连接到接收器（receiver）、再启动，无堆分配、无类型擦除。它是第 5 节中*库*层的先例，而非语言层的先例。

<a id="34-kotlin"></a>
### 3.4 Kotlin

Kotlin 的语言特性极为精巧：`suspend` 修饰符、`Continuation` 接口以及一个内建函数（[KEEP: Coroutines][keep]）。编译器将 suspend 函数变为带有 `label` 及跨挂起点存活局部变量字段的状态机，suspend 调用传入一个 continuation 并返回一个值或 `COROUTINE_SUSPENDED`。其余一切（`launch`、`async`、`Deferred`、调度器、通道、`Flow`、取消机制、结构化并发）都位于 `kotlinx.coroutines` 库中，自 1.3（2018）以来语言层面一直保持稳定，而库在持续演进。这正是任务要求所寻求的划分方式，而且实践证明行之有效。

无法照搬之处在于：每次挂起调用都会在堆上分配状态机对象（KEEP 说明它在“挂起函数被调用时”创建），恢复是一次虚方法 `resumeWith` 调用，而 `suspendCoroutine` 每次挂起还会再分配一次，这也是为何生成器需要借助编译器内建优化才负担得起。这些在 JVM 上可以接受，在这里则不可行。可以借鉴之处包括：*在挂起点*投递的协作式取消、作为库纪律的结构化并发（[Elizarov, "Structured concurrency"][elizarov]；[Smith, "Notes on structured concurrency"][njs]），以及能透明挂起的 `inline` 高阶函数（2.4 让 K 对所有高阶函数都天然拥有这一能力）。

<a id="35-go"></a>
### 3.5 Go

Goroutine 是有栈的（几 KB 初始栈，通过复制增长，[连续栈][go-stacks]），由工作窃取运行时（[Vyukov 的调度器设计][vyukov]）按 M:N 调度，其网络轮询器会拦截阻塞调用，使普通代码完全察觉不到自己处于异步之中。人们喜欢它正是因为这一点：没有染色、无需选择执行器，写服务器就是 `go handle(conn)`。代价则是运行时本身（需要带精确栈映射表的 GC 来移动栈、需要调度器、每次切换耗费数百纳秒）、共享内存竞态、goroutine 泄漏以及缺乏结构化并发（`errgroup` 和 `context` 都是库）。这些机制 K 一样也用不了（2.3），而且它给出的架构（线程间迁移）并非服务器性能最快的形态（3.9）。K 取而代之能提供的，是每工作线程一个循环，根本不需要调度器。

<a id="36-zig-twice"></a>
### 3.6 Zig 的两次尝试

Zig 的第一版设计（[0.10 文档：async functions][zig010]）是与第 4 节最接近的先例：`@Frame(f)` 是一个*类型*，即 `f` 的帧，大小由编译器确定；*调用方*通过 `async f(args)` 放置它（在栈上、数组中或分配器里）；由 `suspend`/`resume`/`await` 驱动；函数是否为 async 则从其是否挂起中*推断*。问题恰恰出在推断上：异步性具有传染性且不可见，帧的大小依赖整棵调用树，最终该特性未能在 0.11 迁往自举编译器时存活下来（2023；[发布说明][zig011]）。教训是：必须显式标记（`coro fn`），并让协程帧仅依赖自身函数体，而被调协程则按规则内联，而非靠推断（4.4）。

Zig 的第二版设计（2025；[Cro, "Zig's new async I/O"][zig-io]；[Kelley 的开发日志][zig-devlog]）像传分配器一样，把一个 `std.Io` *接口值*传入每个执行 I/O 的函数。`io.async(f)` 和 `.await` 是它的方法，由选定的实现决定它们是阻塞、使用线程池，还是在事件循环上运行绿色线程；无栈实现也在计划中。它本质上是一个虚表（vtable），并坦承其代价（“仅在使用单一 Io 实现时才保证消除”），而绿色线程实现需要栈切换，这一点已被 2.3 排除。可以迁移过来的思路是把调度器作为显式参数：在 K 中那是静态函数值或模块，在编译期解析，因此虚表开销根本不会产生。

<a id="37-c-swift-python-lua-java-ocaml"></a>
### 3.7 C#、Swift、Python、Lua、Java、OCaml

* **C#** 发明了 `async`/`await` 语法（2012 年 C# 5，继 F# 异步工作流之后）。其编译器构造一个*结构体*状态机，在首次真正挂起前都位于栈上，仅在挂起时才装箱；`ValueTask` 和池化的任务源消除了剩余分配（[Toub, "How Async/Await Really Works"][toub]）。它是关于结构体形态状态机以及避免堆分配代价的最佳文献。
* **Swift**（[SE-0296][se0296]）将 async 函数编译为脱离线程原生栈运行，仅在显式位置挂起，并将结构化并发（[SE-0304][se0304]）与 actor 放入语言中。它为显式 `await` 给出的理由在此同样适用：两个挂起点之间的代码可以按原子操作来阅读。
* **Python** 生成器（[PEP 342][pep342]）具有 `send`（resume 值）、`throw` 和 `close`（在 yield 处以异常形式投递取消），而 [PEP 380][pep380] 的 `yield from` 正是 4.4 所使用的“调用另一个协程并转发其 yield”的去糖形式。其帧为堆对象。
* **Lua** 协程是有栈、非对称且一等的，提供了最简洁的小型 API：`create`、`resume`、`yield`、`status`（[手册][lua]）。4.3 的 resume/yield 传值正是 Lua 的做法。
* **Java** 虚拟线程（[JEP 444][jep444]）与 **OCaml 5** 效应处理器（effect handlers，[Sivaramakrishnan et al.][ocaml-effects]）都是将栈片段复制或重定位到堆上的有栈设计；两者都依赖能够找出所有指向栈内指针的 GC。这里无法采用（2.3）。

<a id="38-coroutines-in-c-without-a-compiler"></a>
### 3.8 不依赖编译器的 C 语言协程

[达夫设备][duff]（1983）、Tatham 的[《C 中的协程》][tatham]（2000）以及 Dunkels 的 [Protothreads][protothreads]（2006）用纯 C 实现了无栈协程：通过针对保存行号的 `switch` 跳入函数体中部，任何需要存活的状态都存放在程序员声明的结构体中。Protothreads 仅靠每线程两个字节的状态就驱动了传感器网络节点。它们展示了 4.12 降级后的样子，也精确揭示了编译器在此基础上额外提供的价值：把跨越 yield 的局部变量提升到结构体中并重新加载，同时检查没有需要保存却无法保存的东西。这就是该特性的全部“便利之处”，且已足以让手写版本相形见绌（1.2）。

<a id="39-the-fastest-servers"></a>
### 3.9 最快的服务器

[Seastar][seastar]（C++，ScyllaDB）、[glommio][glommio]（Rust，io_uring）、[monoio][monoio]（Rust，io_uring）以及 [embassy][embassy]（Rust，嵌入式）共享 2.5 的形态：每核一个事件循环、核间不共享、显式消息传递、作为普通值的任务，以及由循环直接驱动的基于完成或基于就绪的 I/O。[io_uring][iouring] 是它们面向的 Linux API；其完成模型要求缓冲区的生命期长于提交任务的那次挂起，这恰好由池提供（2.6）。K 的 `thread_fn` 加类型化队列已经构成了这一架构的底层基座；协程正是所缺的那一块每连接拼图。

<a id="4-the-design"></a>
## 4. 设计方案

全文语法均为占位符；第 6.9 节列出了替代语法。

<a id="41-declaration-a-function-that-is-also-a-type"></a>
### 4.1 声明：既是函数也是类型

```klang
coro fn serve(c: Conn&<u32 in conns>) -> bool resume Event {
    …                         // 可能 yield 的函数体
}
```

`coro fn` 在同一名称下声明了两个实体：

* **一个函数**：其函数体中可以包含 `yield`，且只能从另一个协程的函数体中被*调用*（4.4），或作为值被*启动*（4.2）。它与普通函数一样声明：全类型化参数（与 `thread_fn` 和循环函数要求一致，§7.8、§11.2；帧的布局取决于它们，4.11）、`->` 后可选的结果类型、泛型、默认值、重载、命名空间、UFCS。
* **一个同名结构体类型**，即*帧*：参数作为字段、跨越任意 yield 存活的局部变量作为隐藏字段、结果（若有），以及一个表示函数体挂起位置的隐藏标记。它是定长的，并拥有包含这些字段的结构体所具有的大小类别、扁平性、根绑定和可复制性（4.8、4.9）。小写开头的类型名在语言中本就很常见（如 `vec` 中的 `float3`、`int2`）。

结果类型之后还可跟两个子句：

* `yield Y`：每次 `yield` 交给恢复方的值类型。可以省略并从第一个被检查的 `yield` 推断，正如结果类型从第一个 `return` 推断一样（§7.1）。不携带任何值的 yield 函数体没有 yield 类型。
* `resume X`：每次恢复传入的类型，同时也是 `yield` 表达式的值类型。若无该子句，则 `yield` 是一条语句，且 `resume` 不接受参数。它无法推断，因为函数体会在任何对它的 `resume` 之前被检查（4.11）。

`Y`、`X` 以及结果类型都必须是定长的。产生可增长数据的协程会将其追加到传入的缓冲区中，与递归循环函数的做法相同（§7.8）；它不能是在恢复方目标位置构建的 `[>..]` 结果，因为静态上无法区分哪次 resume 会完成协程、哪次不会（6.8）。`coro fn` 不能标注 `extern`、`export`、`thread_fn` 或 `recursive`；`checkfree` 和 `simd` 与普通函数一样适用；`inline` 无意义，因为被内联的是恢复函数本身。

<a id="42-starting-a-literal-and-nothing-runs"></a>
### 4.2 启动：一个字面量，且尚不运行

```klang
var task = serve { c };                   // 一个帧，挂起在第一条语句之前
tasks.push(serve { c: conns.alloc_ref(Conn { fd: fd, .. }) });
```

帧通过其类型的结构体字面量构造：按位置或按名称传参，默认值即字段默认值，像任何结构体一样就地构造（§4.2、§4.3）。函数体完全不会运行。这是 Rust 和 Python 的惰性策略，之所以选择它是因为它也最薄：启动只是把参数存入并把标记置零，帧的所有者未主动要求之前，不会有任何代码运行。参数字段可从外部读取（`task.c`），且仅当声明为 `var` 时才可写入，与 `let` 字段一致（§3.2）。

<a id="43-yield-and-resume"></a>
### 4.3 `yield` 与 `resume`

```klang
let w, suspended = resume(task, Event.Ready);   // 运行到下一个 yield 或结束
```

* `resume(f)` 或 `resume(f, x)` 从帧 `f`（帧类型的左值，或帧类型的引用）当前挂起处继续运行，直至下一个 `yield` 或函数体结束。它返回让出的值和 `true`，或者在函数体已返回时返回 yield 类型的零值（正如未命中的 `qpoll` 所做的那样，§11.2）和 `false`。没有 yield 类型的协程只返回 `bool`。当且仅当协程声明了 `resume X` 时才需要提供 `x`。
* 函数体内的 `yield e` 会保存存活的局部变量，将 `e` 交给恢复方，并从 `resume` 返回。下一次 `resume(f, x)` 从它之后继续执行，且 `x` 即为该 `yield` 表达式的值。若没有 `resume X` 子句，则 `yield e;` 是一条语句。
* 当 `X` 是 ADT 时，`yield e as V` 和 `yield e as (V1, V2, …)` 指明了该 yield 所接受的应答：变体按 match 分支的写法裸写（§8.1）。仅有一个变体时，该 yield 表达式的类型直接就是变体类型 `X.V`（§8.2），因此可直接读取其载荷（`let d = yield Wait.Read { fd: fd } as Done;` 然后 `d.n`）；为一个列表时，其类型为已知必属其中之一的 `X`，且对其做 `match` 时只需穷尽该列表即可。`as` 属于 `yield` 本身；对让出值的类型转换须加括号（`yield (n as i32)`）。不带 `as` 的 yield，以及会忽略 resume 值的被调协程中的 yield（4.4），接受 `X` 的任意值。
* `resume` 会检查这一点。`resume(f, x)` 会测试 `x` 的标记是否属于 `f` 当前所挂起 yield 的列表，否则直接中止，并同时报出两处位置（`"resumed \`fill\` with \`Event.Timeout\` at \`loop.k:31\`; it waits at \`serve.k:14\`, which accepts \`Ready\`, \`Hangup\`, \`Cancel\`"`）。因此，错误的应答会直接让发出它的调度器停下，而不会流进函数体里的兜底分支。当协程调用树中的每一个 yield 都带有 `as` 时，所有列表的并集就成为该帧类型的一个属性，若传入 `resume` 的实参是一个不在该并集中的变体字面量，则会直接报编译错误。至于 `x` 是否匹配帧当前具体停在的那个 yield，则只能在运行时得知：调度器根据让出的值获知每个帧在等什么并据此归档（存入 `by_fd`、放入定时器堆），而帧的类型本身并不记录这一点（6.10）。
* `result(f)` 读取已完成帧的结果（多个返回值时为 `let a, b = result(f);`）。对未完成的帧调用它会中止程序。

这就是全部的运行时表面：一个入口、一个出口、双向各一个值。第 5 节的每一种协议都用它们拼写出来。这些名字之所以设为内建操作，是为了让 `resume` 能针对每个帧类型特化而无需声明；按 UFCS，`task.resume(ev)` 同样有效（§7.1）。

<a id="44-calling-a-coroutine-from-a-coroutine"></a>
### 4.4 从协程中调用协程

```klang
coro fn read_line(c: Conn&, out: u8[..4096]&) -> bool resume Event { … }

coro fn serve(c: Conn&) resume Event {
    while read_line(c, c.line) { handle(c.line[..]); }
}
```

在协程体中调用一个 `coro fn`，会在*调用方的状态机内部*把被调协程运行至结束：被调协程的每一次 yield 都是调用方的 yield，对调用方的每一次 resume 都会继续执行被调协程，而该调用的值就是被调协程的结果。这相当于无需关键字的 Rust `.await` 和 Python `yield from`，也即 Kotlin 的 suspend 调用。被调协程的 yield 类型必须与调用方一致（或调用方从中推断），其 resume 类型必须与调用方一致或缺失（忽略该值）。

被调协程中跨越其 yield 存活的局部变量会成为调用方帧的一部分，因此协程帧的大小由其整棵调用树在静态时决定。这也是协程不能递归的原因：大小没有上界。协程在两次 yield 之间*可以*调用普通的递归函数，而普通函数若要调用协程，只能先将其作为值启动再对其 `resume`（4.3）。至于被调协程的代码是直接拼接进调用方的分段中（单个标记、单个 switch），还是保留为独立的 resume 函数并自带一个标记（每层每次 resume 多一个 switch），则是按调用点决定的实现选择，类似内联；社区草案在巡逻基准测试中测得两者的性能差异达 45%（第 7 节），因此默认采用拼接形式，而嵌套形式留给被多处调用的大型被调协程。

<a id="45-rules-at-a-suspension-point"></a>
### 4.5 挂起点的规则

*挂起点*包括 `yield`，以及协程体内部或传给高阶函数的代码块中对 `coro fn` 的每一次调用（4.6）。

* **R1. 作用域内不得有非定长局部变量。** 原文沿用 §7.8 规则：挂起点处的作用域内不得存在可变大小或可调整大小类别的 `let`、`var`、按值参数或按值 `match` 载荷，也不得存在初始化器中包含它们的值。请将临时数据声明在 yield 之前结束的代码块中；可增长数据则由外部拥有并传入。
* **R2. 不得有存活的非定长临时值**：§7.8 的情形 (a) 到 (d)，由 yield 扮演回调进入循环的角色。因此 `print(str(n), yield w)` 是错误，而 `let s = str(n).len; yield w;` 合法。同样也不得有未决的非定长*返回值*：其目标栈从调用起直到值到达之前一直处于占用状态（§10.3），而值到达将发生在后续的某次 resume 中，届时可能来自另一个恢复方且正使用着其他栈。`coro fn` 本身只有定长结果（4.1），因此这一条只涉及传入返回非定长结果之函数的可 yield 代码块：`each_rev(xs) { yield w; }` 合法，而 `map(xs) { yield w; … }` 和 `exception::try { yield w; }`（其 `handler` 返回 `E[]`）则是错误的。
* **R3. 跨过挂起点的即被存储。** 在 yield 之前声明并在之后被提及的局部变量跨越了该 yield 存活，从而成为帧的隐藏字段。该判定是语法级的，与收缩规则（shrink rules）的活跃性分析一致（§5.1）：在该局部变量作用域内、yield 之后的任何提及都算，循环按整个循环体计算，而提及该变量的代码块或嵌套函数也算。“之后被提及”按每个 yield 单独判定，因此在一处较晚的 yield 之前就死亡的局部变量不会扩大那一处 yield 的状态。
* **R4. 指向协程自身局部变量的引用不得跨越挂起点。** 一次 yield 结束一次激活：在它之后仍存活的局部变量会在之后的恢复中从帧里重新加载，位于不同的内存地址。因此，根植于协程自身局部变量或参数副本、或 yield 语句中临时量的引用或切片，都不得跨越该 yield 存活。这就是将 yield 视作作用域退出的存活期规则（§9.1），其检查方式与返回此类引用时完全一致。根植于帧*外部*（池、全局变量、引用参数所指对象、静态数据）的引用可以自由跨越：它们都是定长值。正是这条规则使帧成为了普通值（无需 `Pin`，3.2）和普通持有者（4.8）。第 6.4 节讨论了放宽它的方案。
* **R5. 挂起点作用域内不得存在 `defer`**（v1 中）：`defer` 代码块在其所属块退出时运行，而那可能落在由不同恢复方发起的后续 resume 中。第 9 节保留了这个问题。
* **R6. 类型收窄得以保留，控制流状态归属于函数体。** 在 yield 之前完成收窄的可选类型在 yield 之后仍然保持收窄：它是函数体的 `let` 或 `var`，由帧保存和恢复，且除函数体本身外没有任何代码能改写它。（`var` 参数在两次 resume 之间可由帧的所有者写入，因此不能跨越 yield 保留收窄。）确定赋值检查像普通函数一样针对整个函数体进行。
* **R7. 全局初始化器、默认参数值以及 `defer` 体中禁止 yield**，它们没有帧；处于递归循环中的函数、传给递归循环函数的代码块，以及自身不是 `coro fn` 的嵌套 `fn` 中也禁止 yield（4.6）。
* **R8. yield 属于所在语句。** 它可以出现在任何允许表达式的地方（`let ev = yield w;`、`guard (yield w) == Event.Ready else { return; }`），受 R2 约束，并在其所在位置按从左到右顺序求值（§2）：位于其前的操作数在挂起前求值并保留，由 R2 保证它们必然是定长的。

在两次 yield 之间，普通函数能做的一切事情协程都能做：通过引用增长池和缓冲区、在内层块中声明并使用临时缓冲区、调用任何函数、在协程内部使用 `return … from`（4.7）、派生工作线程、在 `qget` 上阻塞（逻辑隐患，非语言错误）。

<a id="46-blocks-hofs-and-nested-functions"></a>
### 4.6 代码块、高阶函数与嵌套函数

写在协程体内的代码块可以 yield。接收它的函数会针对该代码块特化（§7.6），该特化体便成为协程的一部分：在该代码块内的 yield 处，R1 到 R4 同样适用于高阶函数自身的局部变量（就像协程自己的局部变量一样），其跨越 yield 存活的局部变量也会加入帧中。因此 `each_rev(xs) { yield Wait.Any; }` 可以直接配合标准库普通的 `each_rev` 使用，后者跨越 yield 存活的唯一局部变量只有其循环索引。高阶函数本身仍是一个普通的 `fn`：它自身文本中不含 `yield`，只是执行了一个会 yield 的代码块。*在自身文本中* yield 的函数才是 `coro fn`，因此草案中的 `wait_until` 写作 `coro fn wait_until<F>() { while !F() { yield Wait.Any; } }`，并按 `wait_until { ready(c) }` 调用；带有函数值参数的 `coro fn` 可以被调用，但不能被字面量启动，因为字面量无法绑定 `F`。会 yield 的代码块只能传给在调用点处其自身局部变量和结果也满足规则（R1、R2：定长结果，作用域内无非定长局部变量）的函数，这由特化过程负责检查；传入递归循环的函数中的代码块不能 yield（R7）。这类代码块中的 `return` 会从词法外层的协程返回，正如今天它从词法外层的命名函数返回一样（§7.6）。

声明在协程体内的嵌套 `fn` 不能 yield；嵌套 `coro fn` 可以，且像其他协程一样被调用（4.4）。作为函数值传入的*命名*协程（如 `each_rev(xs, step)`，其中 `step` 是 `coro fn`）遵循与代码块相同的规则。

<a id="47-return--from-defer-and-the-other-exits"></a>
### 4.7 `return … from`、`defer` 及其他退出方式

* 从协程体 `return` 会结束该帧：结果存入帧中，标记置为已完成，而 `resume` 返回 `false`。
* `return E from f`（其中 `f` 是该协程自身、它所调用的协程（4.4），或通过代码块内联进该协程的函数（4.6））的工作方式与今天完全相同：只要函数体在运行，这些栈帧就必然位于原生栈上，因为被调协程的代码永远只通过其调用方的 resume 运行。线程局部判别式（§C.3）仅在单次 `resume` 内部从抛出到捕获之间被设置。而指定协程*外部*的目标（构造该帧的函数，或恢复它的函数）则是错误：它不在从 `resume` 到函数体的编译期路径上，这正是 §7.9 已经检查的条件。照现有写法，`exception::try` 不能接收会 yield 的代码块，因为它的 `handler` 返回非定长的 `E[]`（R2）；一个采用定长错误槽位（带“无错误”变体的 ADT）的协程友好型 `try` 将是一个很小的库补充。
* `defer` 不能跨越 yield 存活（R5）。`guard`、`block`、`break`、`continue` 和循环不受影响：对切片做 `for` 循环并在其中 `yield` 会保留索引；对协程局部定长数组做 `for` 循环则按索引遍历被提升到帧中的数组，正如对可调整大小数组做 `for` 循环今天已经在做的那样（§6.5）。

<a id="48-lifetimes-the-frame-is-a-holder"></a>
### 4.8 生命周期：帧即持有者

无论参数还是提升到帧中的局部变量，凡是引用、切片或持有它们的值，帧类型就会在对应位置拥有引用字段。因此它像任何此类结构体一样“对其字段的根隐式泛型”（§9.2）并按相同规则检查：将帧存入池、局部变量或全局变量即是按存储规则存入其所持有的东西；存储在全局池中的帧只能持有生命周期长于全局变量的引用（池、其他全局变量、静态数据），这正是服务器的形态（5）；用指向 `main` 循环内局部变量的引用构造的帧，只能活在该循环的局部变量中，而不能活在更深或更外处。回读规则（§9.5）会赋予从池中读出的帧该池候选集合的根，而 `in pool` 链接无论帧在何处都保持精确（§3.9），这也是服务器示例用这种方式关联连接的原因。根植于可伸缩数组（其 `c` 指向一个 `[>..<]`）的帧只能由变量持有（§5.2），和任何此类值一样。

这里没有任何新规则：结构体 `{ c: Conn&, n: i64, state: u8 }` 本就已经受这些规则约束。唯一针对协程新增的是 R4，它使帧自身的存储空间不进入其所持有引用的根集合。

<a id="49-copying-flatness-and-threads"></a>
### 4.9 复制、扁平性与线程

由于 R4，帧不持有任何指向自身的引用，因此它是一个普通的定长值：

* 它像结构体一样复制（赋值、按值传参、`pop`、`for` 复制）。挂起帧的副本是另一个从同一点继续执行的独立协程：一种廉价且偶尔很有用的分支（例如从检查点重放的生成器），其风险也仅在于普通复制固有的语义。
* 当它的参数和提升的局部变量都扁平时，它就是**扁平的**（§1.1）：由整数、枚举、有限数组和索引类型槽位组成的帧。扁平帧与任何其他扁平值一样，可以作为 `thread_spawn` 参数或队列消息：一个挂起的任务可以被交给另一个工作线程并在那里恢复。这就是工作分发的显式形式（2.5）；持有引用的帧则像任何持有引用的值一样，留在自己的线程上。
* 它可序列化：对扁平帧池调用 `to_bytes` 就是挂起任务的快照，且可通过 `from_bytes` 作为标记经范围检查的结构体映像安全读回（§12）。这是顺带的结果而非设计目标，并像所有二进制映像一样绑定于生成该帧布局的编译器版本。
* `==` 按字段比较参数、标记和提升的局部变量；`print` 输出参数和标记；当所有参数均有默认值时 `default<serve>()` 存在，表示未启动的帧。

<a id="410-finishing-re-entry-abandonment"></a>
### 4.10 完成、重入与弃置

* **已完成。** 函数体返回后，`resume` 返回 `false`，`result(f)` 读取结果。恢复已完成的帧会中止程序（`"resumed a finished coroutine"`），就像对空数组调用 `pop` 一样；这一检查就是标记自身的 `match`，不产生额外开销。
* **重入。** 对正在运行函数体的帧调用 `resume`（通过别名，或在其自身函数体内部）是逻辑错误，而非内存安全错误：内层 resume 会用已保存的局部变量（它们都是各自类型的合法值）重跑上一处 yield 之后的段落，外层运行则在到达它的下一处 yield 时覆写它们。这是 §9.4 意义下的类型安全复用。调试构建可在进入时写入一个“正在运行”标记并在重入时中止；发布构建则无需支付这次写入。
* **弃置。** 永不再恢复的帧在丢弃时没有任何开销：它不拥有栈，语言没有析构函数（§4.1），而它在池中指代的一切都由池负责释放。在这里，K 没有析构函数反而成了一种简化而非缺陷：Rust 的取消安全性问题（3.2）并不存在，因为没有任何未存储到帧外部的中间进展会被丢失。
* **协作式取消**只是一个 resume 值（`Event.Cancel`），函数体在它的 yield 处看到该值后通过 `return` 响应；Python 的 `close()` 和 Kotlin 的 `CancellationException` 本质上也是它，只不过这里作为值而非异常投递。库可以将其定为惯例；语言不需要知道它。

<a id="411-generics-and-checking-order"></a>
### 4.11 泛型与检查顺序

泛型 `coro fn step<T>(…)` 会像普通函数一样单态化，其帧类型也像泛型结构体一样按每次实例化生成。帧的*布局*仅取决于参数类型与类型实参：在具体参数类型下，无论根绑定为何，被提升的局部变量的类型都由函数体唯一确定。因此，当该类型首次被使用时（字面量、字段、数组元素），通过独立检查一遍函数体即可固定其布局，就像 `CheckUnreached` 检查无调用方的函数那样（implementation.md §3.1）。随后每个 `resume` 调用点会带着该帧实际的根、可写性以及 `in pool` 溯源信息真正特化函数体——等价于调用 `fn serve_resume(f: serve&, x: Event) -> Wait, bool`——从而使函数体内的存储与收缩操作按该帧实际指代的存储位置受到检查。两个具有不同根绑定的帧实例在检查时彼此区分、在布局上完全相同，正如持有引用的结构体实例一样（§9.2）。带有函数值参数的帧类型没有字面量（4.6）。

<a id="412-lowering-to-c-and-what-it-costs"></a>
### 4.12 降级到 C 及开销分析

帧是一个紧凑打包的 C 结构体；函数体是一个带有针对标记的 `switch` 的 C 函数，跳转到其挂起所处 yield 之后的标签（即 Protothreads 降级方式，3.8，在 C 中完全合法：`goto` 可以跳入循环体，且生成的 C 代码本来就已经把所有聚合局部变量声明在函数顶部，implementation.md §6.7）。一个仅有一处 yield 且保持 `n` 存活的函数体降级示意如下：

```c
typedef struct serve_g { uint32_t c_g; uint8_t k_tag; int64_t n_g; } serve_g;

static bool serve_resume(serve_g *f, Event_g ev, Wait_g *out, int64_t k_sp) {
    int64_t n;
    switch (f->k_tag) {
        case 0: goto L0;
        case 1: n = f->n_g; goto L1;             // 重新加载 yield 1 之后存活的变量
        default: k_fail_finished();
    }
L0: for (;;) {
        n = net_recv(…);
        while (n == AGAIN) {
            f->n_g = n; f->k_tag = 1;           // 保存 yield 之后存活的变量
            *out = (Wait_g){ .tag = READABLE, .fd = … };
            return true;                         // yield
        L1:
            if (ev.tag != READY) { f->k_tag = DONE; return false; }
            n = net_recv(…);
        }
        …
    }
}
```

* **拷入、拷出。** 两次 yield 之间，局部变量都是 resume 函数的 C 局部变量，因此 C 编译器会像对待任何普通函数一样为它们分配寄存器；yield 时只把在它之后仍存活的变量存入帧，resume 时再重新加载。热路径中不通过指针访问帧，这也让 C 编译器的别名分析顾虑（implementation.md §6.2）远离了分段代码。正是 R4 允许这样做。
* **重叠布局。** 两个绝不在同一处 yield 存活的提升局部变量可以共享同一槽位（Rust 的布局方式，3.2）。于是帧的大小是参数 + 标记 + 所有 yield 处最大存活集合，而非总和。v1 可以先不重叠布局、日后再加上；生成的 C 代码形状完全不变。
* **被调协程**（4.4）要么作为代码块直接拼接进调用方的 resume 函数中，其 yield 编入调用方的编号序列（单个标记）；要么编译为独立的 resume 函数，从调用方的分段中调用并在嵌套帧结构体中拥有自己的标记。优化器按今天决定是否内联的相同策略来选择（implementation.md §4）。
* **数据栈。** resume 函数像所有函数一样接收 `k_sp`，并在恢复方水位线之上构造两次 yield 之间的临时量；由于 R1 和 R2 保证协程在 yield 时数据栈上没有任何东西，因此 yield 无需恢复任何东西。`NoStackAcrossCycleCall` 的断言不经修改即适用于 yield。
* **恢复方。** `resume(f, x)` 是对帧类型所属 resume 函数的直接调用，按照现有策略，当循环是其唯一调用方时它会被内联进循环中。没有线程局部变量，没有运行时函数，没有虚表。
* **`as` 检查**（4.3）位于带有 `as` 的 yield 对应的 switch 分支中、在重新加载变量之前：`case 1: if (ev.tag != READY && ev.tag != HANGUP) k_fail_resume(…);`，列表更长时则是掩码测试。在本来就要按标记分派的路径上这只是一次比较加分支，对于单个变体它还省去了函数体原本就要做的测试。中止信息会给出 `resume` 的位置（与其他内建函数的中止一致）以及 `yield` 的位置（每个分支的一个常量）。

按操作统计的开销如下：

| 操作 | 开销 |
|---|---|
| 启动（`serve { c }`） | 写入参数，标记置零 |
| `resume` | 一次直接调用（通常会内联），一次 switch，加载该点存活的局部变量；若 yield 带 `as` 则多一次标记测试 |
| `yield` | 写入在其后仍存活的局部变量，写入标记，yield 值置于寄存器，返回 |
| 完成 | 写入标记，写入结果，返回 |
| 被调协程 | 拼接时每调用零开销；嵌套时每层每次 resume 多一次 switch |
| 帧大小 | 参数 + 跨越单一 yield 存活的最大局部变量集合（+ 结果）+ 1 字节标记 |
| 非使用者 | 零：没有运行时状态，没有隐藏参数，其他任何函数均无变化 |

这就是手写状态机的开销，而社区草案的实测（第 7 节）发现，当调用树拼接为单一标记时，手工降级的协程与手写状态机相比性能差距在 10% 以内。

<a id="413-what-stays-out-of-the-language"></a>
### 4.13 留在语言之外的部分

以下每一项都交由库实现，第 5 节会展示其中的第一项：

* **事件循环**：监视哪些 fd、使用哪套内核 API、如何找到事件对应的帧。
* **定时器**：作为截止时间堆，由循环在事件间隙检查。
* **通道**：同线程协程间使用（一个数组加上一个 `Wait` 变体），以及跨线程使用（类型化队列，§11.2）。
* **`select`**：持有多个原因的 `Wait` 变体，或轮流恢复两个内层帧的协程（草案中的 `await_all`，7）。
* **结构化并发**：一个作用域拥有局部的帧数组，且在全部完成前不退出；存活期规则天然使帧无法比它所引用的对象活得更久（4.8），而这正是 Kotlin 必须靠纪律才能强制的一半结构化并发保证。
* **取消策略**：哪个 resume 值代表停止，以及由谁发送。
* **`run_blocking`**：普通函数中对 `resume` 做循环，通过阻塞来满足等待（无超时的 `poll`、`qget`）。
* **作为迭代器的生成器**：`for x in gen` 日后可以作为 `resume` 的语法糖；今天可以写作 `loop { let x, more = resume(g); guard more else { break; } … }`，或者使用一个高阶函数。
* **按 sans-I/O 编写的协议实现**（3.2）：解析器消费切片并报告“需要更多数据”或“完成”；只有实际等待的函数才是 `coro fn`，从而使解析器既可服务于阻塞代码，也可服务于协程代码。

<a id="5-a-server-on-top"></a>
## 5. 构建其上的服务器

以下展示分层的草图，其中假定存在一个包含 `extern fn` 套接字的 `net` 模块（目前尚不存在；第 8 节将其列为前置工作路线）。名称均为占位符。

```klang
import std;
import net;        // 假想模块：以 extern 形式提供非阻塞套接字与就绪轮询

// 连接存放在池中。缓冲区是元素内部的受限数组，
// 以便内核在协程挂起期间直接写入其中（§5.3）。
struct Conn { fd: i64, inbuf: u8[..4096], outbuf: u8[..4096] }
reusable var conns: Conn[>..] = [];

// 协程与事件循环之间的协议由库定义的两个扁平 ADT 组成。
// 不同的循环（io_uring、IOCP、游戏的帧 tick）可定义各自的协议。
enum Wait  { Readable { fd: i64 }, Writable { fd: i64 }, Timer { deadline_ns: i64 }, Any }
enum Event { Ready, Timeout, Hangup, Cancel }

// 等待是唯一“带颜色”的代码。recv 向受限数组中追加数据，
// 返回字节数、流结束时返回 0，或返回 net::AGAIN。
coro fn fill(c: Conn&<u32 in conns>) -> bool resume Event {
    loop {
        let n = net::recv(c.fd, c.inbuf);
        if n != net::AGAIN { return n > 0; }
        // 就绪等待永远不会收到 Timeout 回复：若循环在此处发送 Timeout，
        // 会在其 resume 处中止，而不会被当作挂断处理。
        let ev = yield Wait.Readable { fd: c.fd } as (Ready, Hangup, Cancel);
        guard ev == Event.Ready else { return false; }
    }
}

coro fn flush(c: Conn&<u32 in conns>) -> bool resume Event { … }   // Writable 同理

// 处理程序是直行式代码；解析器是操作切片的普通函数
// （sans-I/O，无 I/O），同样可用于阻塞代码。
coro fn serve(c: Conn&<u32 in conns>) resume Event {
    loop {
        guard fill(c) else { return; }
        let consumed = http::respond(c.inbuf[..], c.outbuf);   // 解析并写入响应
        guard consumed > 0 else { continue; }                   // 需要更多字节
        drop_front(c.inbuf, consumed);                          // 保留未解析的尾部
        guard flush(c) else { return; }
    }
}

// 事件循环。协程帧存放在连接池旁边的池中；循环维护一张
// 从 fd 到帧索引的映射表，用于处理内核返回的事件。
reusable var tasks: serve[>..] = [];
var by_fd: i64[>..] = [];                                 // fd -> tasks 中的索引，或 -1
var timers: Deadline[>..] = [];                           // (deadline, task) 组成的堆
var ready: i64[>..<] = [];                                // 下一轮要 resume 的任务

fn run(listen_fd: i64) {
    loop {
        for ev in net::poll_wait(…) {                      // (fd, readable/writable/hangup)
            let i = by_fd[ev.fd];
            let w, suspended = resume(tasks[i], if ev.hangup { Event.Hangup } else { Event.Ready });
            guard suspended else {
                conns.free(conns.index_of(tasks[i].c)); tasks.free(i); net::close(ev.fd);
                continue;
            }
            match w {
                Readable r => net::watch(r.fd, net::READ, i),
                Writable r => net::watch(r.fd, net::WRITE, i),
                Timer t    => timers.push(Deadline { at: t.deadline_ns, task: i }),
                Any        => ready.push(i),
            }
        }
        … 接收新连接到 conns 与 tasks；触发到期定时器 …
    }
}

// Thread-per-core（每核一线程）：每个工作线程都是一个程序实例，拥有各自的
// conns、tasks 和 by_fd 副本（§11.2），在各自独立的 SO_REUSEPORT 套接字上 accept。
thread_fn worker(listen_fd: i64) { run(listen_fd); }

fn main() {
    for i in hardware_threads() { thread_spawn(worker, net::listen(8080, true)); }   // SO_REUSEPORT
    …
}
```

这一草图体现出以下契合点：

* `serve` 的帧包含一个 4 字节链接、一个标签，以及在 `fill` 和 `flush` 内部跨越 `yield` 的少数局部变量（一个 `n`、一个位置）：总共只有几十字节。一百万个连接就是两个池中的一百万个元素。
* 事件循环中没有任何分配、加锁或间接调用；`resume` 就是一次跳入帧代码的 `switch`。事件循环的数据结构都是数组。
* 缓冲区归属于池，因此基于完成的事件循环（io_uring、IOCP）可以在 `yield` 时将 `c.inbuf` 的空闲槽位提交给内核，并在恢复时将读取到的字节数作为 resume 值传回：yield 值只需携带切片即可，帧无需为了内核向不属于它的内存写入数据而被固定（pin）（2.6）。
* 每个工作线程在各自独立的全局变量副本上运行相同的循环。在程序主动需要之前，没有调度器，也没有任何跨线程交互；即便需要时，也只是一个队列。
* 协议逻辑（`http::respond`）是“无颜色”的，无需套接字即可测试。
* `fill` 和 `flush` 就是该协议的按等待划分的签名（per-wait signature）：上层代码调用 `fill(c)` 并得到一个 `bool`，完全看不到 `Wait` 或 `Event`，而它们的 `as` 列表记录了每次等待接受哪些应答。一个拥有多个 resume 位置（fd、定时器、新连接）的循环，可以通过分支函数（case function，§8.2）在一个地方统一处理 yield 出来的 `Wait`——每个变体对应一个 `fn on_wait(r: Wait.Readable, i: i64)`，按 `on_wait(w, i)` 调用——无论任务在等待什么，都以相同方式恢复每一帧。

<a id="6-options-with-pros-and-cons"></a>
## 6. 备选方案及其优缺点

第 4 节的每个部分都有替代方案。已标出推荐方案。

**6.1 无栈（推荐）/ 有栈 / 动态栈。** 2.3 节已决定必须采用无栈。数据栈模型排除了有栈协程。*动态栈*（§11.3，任务拥有一块数据栈区域，通过设置 `k_stks` 切换）可为数量有限的重量级任务解除 R1 限制，也是社区提案中为后续阶段提出的建议；它的代价是每个任务占用虚拟地址空间以及每次 resume 时发生一次栈切换，因此应作为声明上的显式选择加入（`coro fn … with stacks`），绝不能作为默认行为。不纳入 v1。

**6.2 帧类型：以函数命名（推荐）/ `co<f>` / 用户结构体。** 以函数命名帧类型（精神上类似 Zig 的 `@Frame(f)`，3.6）赋予了该类型一个可放入池与字段的名称、一个用于启动它的字面量，以及对应参数的字段，同时不引入任何新的类型系统概念。`co<f>`（社区草图中的写法）需要一种能够命名函数的类型表达式，而 K 中没有任何其他特性具有这种语法。Protothreads 形式由用户自行声明状态结构体，编译器仅检查没有其他状态跨越 `yield`，它是所有方案中最薄的一种，把内存布局完全交由用户掌控（紧凑字段、`varint` 等），但它放弃了该特性存在的唯一便利之处（3.8）；作为一种编程风格它依然可用，因为只要协程没有任何局部变量跨越 `yield`，其帧就只包含它的参数。`--frames` 列表（第 8 节）会告诉程序员哪些变量被提升到了帧中。

**6.3 带类型的 yield 与 resume 值（推荐）/ 带字段的裸 `suspend()`。** 使用裸挂起时，协程通过帧的参数字段与恢复者通信，这对于每帧轮询所有帧的游戏 tick 已经足够，但不适用于服务器——服务器中的事件循环必须在不逐一询问的前提下知道 10⁵ 个任务各自在等待*什么*（2.7）。带类型的 yield 没有额外开销（值通过寄存器返回），还顺带免费提供了生成器（generator）。resume 值可以通过 `var` 字段来模拟，因此它是相对更可选的一半；之所以保留它，是因为取消信号和完成结果（例如来自 io_uring 的字节数）天然就是 resume 值，而且通过寄存器传递值胜过写入帧再从帧中重新加载。

**6.4 禁止跨 yield 的自引用（推荐）/ 自引用、不可拷贝的帧。** 社区草图选择了后者：原地构建、绝不拷贝，并由存活期（outlives）规则保证指向帧自身局部变量的指针有效。K 已经能够表达“固定但不可拷贝”的值（持有自相对引用的值，§3.9），而指向帧自身局部变量的引用在本质上*就是*自相对的。这种形式允许 `let s = local[..n]; yield; use(s)`，其代价是：帧无法被拷贝、弹出、跨线程发送或序列化，局部变量必须原地存放在帧中（在热路径中通过 `f->` 寻址），且内存布局不能重叠已被取地址的槽位。R4 让帧保持为普通值、热路径保持在寄存器中，代价仅仅是一条指向修正方法的报错信息。未来的放宽方案可以兼顾两者：地址跨越 `yield` 的局部变量原地存放在帧中，指向它的引用以帧的存储位置为根（当帧是变量时为精确存储，当帧是池元素时为该池），同时帧依然保持可拷贝，因为 TODO 16 中的“整区域拷贝（whole-region copy）”恰恰就是拷贝一个帧所做的事。

**6.5 惰性启动（推荐）/ 构造时运行至首个 yield。** Kotlin 和 C++（默认情况下）会急切地运行至首个挂起点。惰性启动更轻量（就是一个字面量），将工作何时发生的控制权交给所有者，也是 Rust 的实践所支持的方案；其代价是想要立即执行某些逻辑的协程需要一次显式 resume，这可以通过库函数 `start` 来完成。

**6.6 拼接调用树（默认推荐）/ 嵌套帧。** 见 4.4 和 4.12。拼接（splicing）像内联一样在每个调用点复制被调用方的代码，从而只需一次 `switch`；嵌套则共享代码，但每一层需要一次 `switch`。让优化器根据代码体积来决定，就像它处理普通调用一样。

**6.7 标准库 `Wait`/`Event` 约定 / 完全泛型的协程。** Rust 的 `Waker` 允许任意 future 运行在任意执行器上；带类型的 yield 则会将库协程绑定到它所构造的 `Wait` 类型上。推荐做法是在标准库中约定一对小巧的 `io::Wait`/`io::Event`，由标准库的参考事件循环消费，从而让库协程与事件循环能够互操作，而语言本身对此保持中立。有其他需求的事件循环可以定义自己的类型并做适配。这是用动态派发换取扁平数据的显式权衡，也是 K 在其他所有地方所做的同一权衡。完全不愿承诺任何协议的库协程甚至不需要协议：它可以是一个接收静态函数值形式等待协程的普通高阶函数（HOF），即 `fn tick<Sleep>(period_ns: i64) { loop { Sleep(period_ns); … } }`，4.6 允许它调用 `coro fn` 值，由应用程序传入按自身协议 yield 的 `coro fn`。无需编写适配器，也无需合并枚举；特化后的实例像普通代码块一样并入调用方的帧。

**6.8 仅限固定大小的结果与 yield（推荐）/ 非固定大小的结果。** `[>..]` 类型的结果是由生成它的调用直接在目标位置构建的（§7.3）；对于协程而言，这个调用就是众多 `resume` 调用中的某一次，因而目标位置必须在所有这些调用之间一直保留。规范中用于递归的惯用法（构建到通过引用传入的缓冲区中，§7.8）已经覆盖了这一需求。如果实际代码确实需要 `coro fn lines() -> u8[>..]`，届时再重新审视。

**6.9 语法。** `coro fn` 与 `thread_fn`、`recursive fn` 并列；社区草图中的 `suspend_fn` 是另一种显而易见的拼写。`yield` 则是通用关键字。`resume`/`result` 作为内建操作（类似于 `thread_spawn`/`thread_wait`），可通过 UFCS 作为成员访问。`resume X` 头部子句是最尚未敲定的部分：备选方案包括带标记的参数（`ev: resume Event`）或属性列表。有意不设 `await` 关键字：调用就是调用。4.3 的收窄借用了检查转换的 `as`（`x as (u32 in a)` 在 `x` 不合法时中止，§3.11），因为它本质上就是一次转换：将 resume 值转换为更窄的类型，在 resume 处失败。备选方案有 `yield e expect V` 和 `match` 风格的 `yield e -> (V1, V2)`。

**6.10 在 yield 处收窄 resume 值（推荐）/ 声明式的等待-应答映射 / `Wait` 变体上的应答列表 / 完整联合类型。** 当每个协程只有一个 `resume X` 时，每次 `yield` 都会收到完整的 `X`，尽管实际上其中通常只有少数变体能合理地到达该 `yield`。对 `X` 做穷尽匹配并不切合实际，而兜底分支（`guard (yield w) == Event.Ready else { return false; }`）则会默默吞掉发送了错误值的调度器。[恢复条件提案][conditions] 对此的解决方式是：为每种等待声明应答它的唯一类型（`resume if FileWontBlock -> net::Event;`），在 resume 处具名该条件（`resume<FileWontBlock>(task, ev)`），并在由 `resume` 调用的 `on_suspend` 重载中满足每个条件。按照 1.2 节的标准权衡如下：

* *配对关系是运行时事实。* 调度器按挂起帧所等待的对象将其归档（如 `by_fd`、定时器堆），之后再从那里恢复它；帧的类型本身并不记录它正停在哪个等待上。因此，对于拥有多个条件的协程，`resume<C>` 必须在运行时检查标签，它在静态上检查的只是凭证具有类型 `C` 以及 `C` 确实是该协程的条件之一。要做到静态检查就需要引入类型状态（typestate）：以按条件精化的帧类型作为调度器表的元素类型、引入线性所有权以防止精化状态通过别名过期，以及对任何混合帧队列再次引入和类型（sum type）。任何设计都必须在运行时检查配对；区别仅在于由哪一侧负责检查，以及协程体是否要编写根本不可能执行的分支。
* *按条件区分 resume 就意味着按条件区分代码路径。* `resume<C>` 需要静态已知的 `C`，因此无法静态获知帧所处等待的调度器必须先查询再分派，每个条件一个分支。完成型 I/O（io_uring 和 IOCP 对每个操作都以结果码应答）、游戏 tick（每个任务都以当前帧的 `dt` 恢复）以及广播通知（排空服务器、在测试中重放轨迹）都会从原本的一句 `resume(f, x)` 变成每个条件一条分支；否则就只能把所有等待折叠进同一个由共享类型应答的条件中，而这就放弃了条件机制原本追求的按等待类型化。
* *一旦计入失败情况，很少有等待是 1:1 的。* Cancel、Hangup、Timeout 和 Shutdown 应答着绝大多数等待。按等待划分的应答类型要么在每个应答类型中重复这些共享的失败变体（如该提案中的 `FileResult { Ready, Hangup }`），要么将它们移入由语言拥有的内建机制中（如其 `cancel`）。
* *这些声明所增加的能力已经存在。* 辅助协程本身就是按等待划分的签名：`coro fn readable(fd: i64) -> bool` 拥有名称、载荷、带类型的结果以及撰写文档的位置，调用零开销（4.4、6.6），还能向上层代码隐藏 `Wait` 与 `Event`（第 5 节）。在多个 resume 位置之间统一处理每个 `Wait` 变体，只需一组分支函数（§8.2）——这本质上就是 `on_suspend` 重载所做的事，只不过是显式调用而非由 `resume` 隐式查找。该提案本质上是局限于无栈帧上的带类型代数效应（操作 `A -> B`、每个操作一个处理器、延续作为拥有所有权的任务），它也带来了相应的代价：一种新的声明形式、沿库调用树推断的每个协程的条件集合，以及指向库代码内部的缺失处理器错误。

剩下的只是每个辅助函数内部那一个原始 `yield`，由 `as` 来收窄（4.3）：协程体按每次 `yield` 类型化，没有死分支；调度器保持单一的 `resume(f, x)`；错误应答会在 resume 处中止而不会被吞掉；当某个应答是没有任何 `yield` 接受的字面量时还会触发编译错误。除了这条子句外它不需要任何新声明，兼容任何现有枚举（包括 6.7 的 `io::Event`），并且是按 `yield` 粒度的，因此同一等待类型下的某个等待可以比另一个接受更少的应答。将应答列表写在 `Wait` 变体上（`Readable { fd: i64 } -> Ready, Hangup, Cancel`）则把配对关系写进了协议类型，并对该变体的所有 `yield` 做统一收窄，使用相同的 resume 检查；如果按 `yield` 书写的列表被证明过于分散而不利于记录协议，它们可作为备选方案，代价是在枚举上引入协程专用语法。该提案的其余部分——带 `cancel` 的拥有所有权的帧，以及推断而非声明协程——属于独立问题：ownership.md §5 探讨了前者，3.6 节探讨了后者。

<a id="7-the-community-suspend_fn-sketch"></a>
## 7. 社区 `suspend_fn` 草图

[bitspittle 的 `suspend_fn` 提案][bitspittle]（2026 年 10 月，按简报要求在起草上述设计之后阅读）从 Kotlin 一侧得出了相同的核心结论：无栈；在 `suspend()` 处采用 §7.8 的规则；被调用挂起函数的状态存放在调用方的变体中，如 Rust 布局 future 那样构成“大小在编译期已知的枚举树”；不执行任何操作的 `co_start`；`co_resume -> bool`；其余一切（`await`、`await_all`、`run_blocking`、调度器）均作为库代码实现。它的巡逻（patrol）示例——一个在游戏持续渲染的同时行走、休息并折返的守卫——是服务器之外的第二个极佳用例，其前后对比（四个 `match` 分支加一个标志位，对比四行直行式代码）比文字更有力地论证了 1.2(1)。

其性能测量是最有价值的部分：在 Apple M3 Pro 上对 10,000 个手工降级（hand-lowered）的巡逻运行 10,000 帧，手写状态机每帧每个守卫耗时 0.88 ns，嵌套降级（每层一个标签）耗时 1.28 ns，而将各层合并为单一程序计数器的方案耗时 0.97 ns；状态大小分别为 22、48 和 24 字节。因此，*只要*调用树被拼接（6.6），协程的开销就与它所替代的状态机相当，而嵌套形式则慢 45%。正是这组数据促使 4.4 和 4.12 默认采用拼接。（该基准测试位于该 fork 的 `bench/suspend_fn` 中，不在此仓库内。）

本说明与之的差异及原因：

| | `suspend_fn` 草图 | 本说明 |
|---|---|---|
| 挂起携带的内容 | 无；恢复者每 tick 轮询一个谓词 | 双向带类型的值（4.3），使拥有 10⁵ 个任务的循环无需询问即可得知各自在等什么（2.7、6.3） |
| 帧 | `co<f>`，原地构建，不可拷贝，非扁平 | 以函数命名的结构体，只要字段可拷贝且扁平则自身也可拷贝且扁平（4.9、6.4） |
| 跨挂起引用自身局部变量 | 允许，因此不可拷贝 | 禁止（R4），因此是普通值且热路径驻留寄存器 |
| 线程 | 协程不可跨线程 | 扁平帧可入队发送给另一个工作线程（4.9） |
| 高阶函数中挂起的代码块 | 开放问题 | 允许；高阶函数的特化并入协程（4.6） |
| `return … from` | 开放问题 | 在协程调用树内部一如既往；绝不越过 `resume`（4.7） |
| 生成器（generator） | 开放问题 | 同一套机制（4.3） |
| 游戏帧用法 | 核心示例 | 同样适用：每帧调用 `resume(p, Event.Tick)`，并以 `yield Wait.Any` 表示“下一帧” |

它提出的开放问题“固定但不可拷贝的值对于类型系统而言是否属于新事物”已由 R4（无需任何不可拷贝之物）以及 6.4 的放宽方案（§3.9 中带自相对引用的值）给出解答。

## 8. 实施步骤

1. **确定规范文本。** 新增 §7.15（或单独成节），将 4.1 至 4.11 列为规则，为 R1 至 R8 编号，敲定占位语法，并注明 `Wait`/`Event` 约定属于标准库事项。为 6.1、6.4 的放宽方案和 6.8 添加 TODO 条目。
2. **手工测量服务器形态**，如同草图测量巡逻用例一样：在 `bench/coro/` 中编写一个手工降级的 C 回显循环，配合基于 `poll` 的反应器运行 10⁵ 个池化帧，与相同程序的 Rust/tokio、Go 以及基于 `epoll` 的纯 C 实现对比。这能在动手实现前锚定目标，并检验 1.1 关于每次事件开销仅为一次 `switch` 和几次加载的论断。同时在本机复现巡逻用例的数据。
3. **检查器（Checker）。** 解析 `coro fn`、`yield`/`resume` 子句以及带 `as` 列表的 `yield` 表达式，将其类型化为变体或收窄后的 ADT（4.3）；将帧类型构建为由参数加上提升的局部变量组成的结构体实例（R3 的语法活跃性，复用 shrink 规则的 `blockpos` 扫描）；通过复用 `CycleCallTemps`、`CheckCycleInit` 和 `Node::nftemp`（以 `yield` 作为标记调用）实现 R1 与 R2；将 R4 实现为每次 `yield` 处对根（roots）的返回检查；按其本身简单的拒绝逻辑实现 R5 至 R8；按帧类型与根特化 `resume`/`result` 内建函数（4.11），拒绝没有任何 `yield` 的 `as` 列表接受的字面量应答；提供具名局部变量与 `yield` 位置的报错信息。
4. **代码生成（Codegen）。** 将帧结构体生成在其他生成类型旁边；为每个帧实例化生成带 `switch` 与标签的 `resume` 函数，在分段边界进行拷入/拷出，并在每个 `yield` 的 case 中生成 `as` 测试（4.12）；先实现被调用协程的拼接（无需第二个标签），再实现嵌套形式，由优化器的内联策略选择；保持 `k_sp` 和水位线规范不变。实现 `--frames` 以列出每个帧的大小和被提升的局部变量，并在 LSP 的悬停提示（hover）中显示相同信息。
5. **测试。** 为每条规则编写一条语料库测试（覆盖每条报错信息），将巡逻与回显循环作为示例，测试生成器、经由 std 高阶函数的带 `yield` 代码块、R2 对包裹 `yield` 的 `exception::try` 的拒绝、经过队列传递的帧、帧池的 `from_bytes`、调试模式下的重入与已结束帧的 resume 中止、错误应答在 resume 处同时带出两处位置的中止，以及无需 `_` 分支的收窄 `yield` 上的 `match`。
6. **网络路线**（独立于 1 至 5，是服务器的前置条件）：在 `os` 或新的 `net` 模块中，作为运行时之上的 `extern fn` 提供套接字、非阻塞 I/O 与就绪轮询，先实现可移植方案（`poll`），随后实现 `epoll`/`kqueue`/IOCP，待需要第 5 节的完成型协议时再实现 `io_uring`。
7. **std 中的参考事件循环**：`io::Wait`、`io::Event`、带定时器的反应器、`run_blocking`，以及第 5 节作为示例的 thread-per-core 骨架。随后用 K 实现第 2 步的服务器基准测试——简报中“绝对最快”的论断正系于这一测量结果。
8. **后续工作**：重叠帧槽位（4.12）、6.4 的放宽方案、`for x in gen`、动态栈任务（6.1）、非固定大小的结果（6.8）。

<a id="9-open-questions"></a>
## 9. 开放问题

* resume 值应当在头部声明（`resume X`）、标记在参数上，还是干脆舍弃转而使用 `var` 字段（6.3、6.9）。
* 一旦出现希望将配对关系写在一处的协议，是否也应当允许在 `Wait` 变体上书写 `as` 列表（6.10）。
* 参数是否应当作为帧字段对外可见，还是除 `resume` 与 `result` 外帧应对外不透明。可见字段很方便（事件循环可直接读取 `tasks[i].c` 来释放连接）且零开销；不透明则更整洁。
* 跨越 `yield` 的 `defer`（R5）：它可以作为一个标志位保存在帧中，在最终到达代码块退出的那次 `resume` 中执行，代价是每个 `defer` 一字节和一次分支判断。待出现实际需求再定。[ownership.md §5](ownership.md#5-coroutines) 推演了 `own` 限定符在此处能增添什么——一种既不能被丢弃也不能被拷贝的帧，以及一个会运行待执行 `defer` 的 `cancel`；那是一个独立的决策，本设计不依赖它也可成立。
* 较大的被提升局部变量：在每次 `resume` 时对一个 `u8[1024]` 局部变量进行拷入/拷出相当于 2 KB 的数据搬运。6.4 的放宽方案（原地槽位）或体积阈值可以解决此问题；目前的变通做法是将缓冲区存放在外部，这本来也是惯用法。
* `thread_fn` 入口本身能否是一个 `coro fn`（没有明显用途；否），以及 `simd coro fn` 是否有意义（v1 不考虑）。
* 动态栈任务（6.1）：选择加入（opt-in）的语法形式，以及在地址空间预算下程序最多可拥有多少个。
* 一旦生成器投入使用，用于标准库容器的 `for x in gen` 形式与基于 `yield` 的迭代器协议。
