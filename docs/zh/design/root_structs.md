# 根结构体：具有独立存储的状态

状态：根结构体（root structs）v1 以及 `slot_pool`/`slice_pool` 模块均已实现。`reusable` 与 `reusable[]` 仍保留可用，但已被弃用，推荐改用标准库池。所有者具备独立的局部/全局组件、借用的所有者引用、按组件的生命周期检查以及已知全局代码生成（known-global codegen）。整个所有者的拷贝、嵌套、序列化以及向工作线程的自动转移仍然延后实现。[迁移指南](../stdlib.md#migrating-from-reusable)说明了其余的兼容性差异；[基准测试报告](../bench/pool_workloads.md)记录了当前的测量结果与性能后续工作。

<a id="motivation"></a>
## 动机

结构体用于将相关状态打包在一起。普通的 K 结构体是一块单一的连续内存，至多只能在尾部包含一个可调整大小的值。根结构体（root structs）解除了这一存储限制，同时对所有者的声明位置加以约束。多个数组可以各自独立增长，定长字段也可以与它们并列存放，且全部通过普通的字段语法访问。库开发是一个重要应用场景：用户只需一条声明就能实例化完整的库状态，而不必分别传入多个数组和一个借用的上下文。

根结构体将独立存储的值归组到同一个拥有型生命周期之下。它们不会把多个增长中的数组放进同一块连续字节映像中、不会在增长时重定位字段，也不会引入堆分配器。每一个同时存活的可调整大小组件依然位于各自独立的数据栈顶部。

```klang
root struct ParserState {
    tokens: Token[>..] = [],
    work: i64[>..<] = [],
    position: i64 = 0
}

var parser = ParserState { .. };
parse(parser, input);

fn parse(state: ParserState&, input: u8[:]) {
    // 普通的字段访问与 UFCS，拥有各自独立的数组存储。
}
```

上述示例假定存在一个另外声明的 `Token` 类型。根结构体适用于解析器状态、平行数组、带有独立元数据的查找结构以及对象池。只要可复用池仍保留为内置特性，根结构体同样具有价值。

<a id="syntax-and-explicit-contract"></a>
## 语法与显式契约

使用 `root struct`，同时保留结构体字段、类型实参、默认值、命名空间以及基于函数的方法。将这一区分保存在现有的结构体声明/实例化节点上，而不是创建另一套独立的字段访问 AST 节点。

在类型声明处，将 `root` 视为紧邻 `struct` 之前的上下文修饰符。现有的名为 `root` 的变量、字段、参数和函数仍然合法。不要仅仅为了解析这个修饰符而将其设为全语言保留字。

该修饰符表示拥有型实例是存储根（storage roots），并不表示该声明或实例必须位于文件作用域。显式声明的根结构体即使只有零个或一个可调整大小字段（包括在泛型特化中），也依然保留其限制。普通结构体保留其现有的放置和布局规则。向普通结构体添加第二个可调整大小字段仍然会报错，且错误提示会建议使用 `root struct`。

如果改用自动推断来决定 `root` 修饰符，那么修改字段或特化泛型就会改变类型的放置位置、拷贝方式和内存表示契约。如果用一个新关键字替代 `struct`，则会掩盖它与现有结构体共用的大部分行为。`local` 这一名称无法准确描述全局变量，而 `stack` 在 K 中几乎没有区分度。

作为对比，Rust 会根据尾部的非定长字段自动推断动态大小结构体的限制，且这样的结构体依然描述单个对象。C# 则显式标记其受限的 `ref struct` 类别。两者与本提案的规则均不相同。参考资料：[Rust dynamically sized types](https://doc.rust-lang.org/reference/dynamically-sized-types.html)、[C# ref structs](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/ref-struct)。

<a id="v1-ownership-and-placement"></a>
## V1 所有权与放置规则

| 用途 | V1 规则 |
|---|---|
| 局部或全局 `var`/`let` | 允许；使用字面量和字段默认值在声明处直接构造。 |
| 字段 | 普通字段和多个独立存储的可调整大小字段，顺序任意。它们各自原有的元素、构造和生命周期限制依然适用。 |
| 另一个结构体内的根所有者 | 禁止按值包含，包括在另一个根结构体内部。 |
| 作为数组/切片元素或 ADT 载荷的根所有者 | 禁止，包括定长数组。 |
| 指向所有者的引用 | 允许，包括在普通生命周期规则允许时使用可选引用，以及将引用存储在字段或数组中。 |
| 函数实参 | 按引用传递。未标注类型的参数按引用绑定拥有型左值，与非定长值的规则一致。 |
| 函数返回值 | 在遵循常规生命周期规则的前提下，可以返回指向既有所有者的引用；拥有型返回值延后支持。绝不允许返回指向局部所有者的引用。 |
| 来自既有所有者的无注解绑定 | 按引用绑定，与非定长左值一致。显式 `.=` 仍然可用。 |
| `copy`、整个所有者赋值、按值传递的参数 | 禁止。不支持隐式描述符拷贝或所有权转移。 |
| 临时所有者 | 禁止；拥有型构造需要具名的局部或全局声明。 |
| 字段赋值与数组操作 | 遵循字段各自的常规规则，包括收缩（shrink）检查和构造检查。 |
| 整个所有者的原始序列化或 C ABI | 不支持；已明确支持的组件级操作仍然可用。 |
| 转移到工作线程 | 不支持，包括对根全局变量的隐式捕获。参见下文的线程规则。 |

禁止所有权嵌套并不禁止普通字段的类型为现有的带可变大小尾部的结构体。此类字段是一个按其原有内部布局独立存储的组件。而在 v1 中，根结构体本身绝不能成为此类按值组件。可变大小的普通字段同样保留其构造规则；外围的根结构体不存在连续内存映像。

```klang
struct Context { parser: ParserState& }   // 允许借用。
struct Object { parser: ParserState }     // 拥有型包含会导致错误。
```

对被禁止的用法，应给出包含声明和字段/元素/参数路径的诊断信息，并建议使用引用或局部/全局所有者。例如：

```text
ParserState is a root struct and cannot be stored by value in Object.parser.
Declare it as a local/global variable, or store ParserState&.
```

在适用的地方，通过类型别名、泛型实例化、推断类型、默认值、推断返回值以及不可达/独立检查来强制执行这些规则。表面上看似固定大小的控制记录绝不能逃逸这些所有权规则。`const` 与可写性遵循现有的结构体和引用规则，包括对引用类型字段的现有处理方式；不要添加一刀切的传递性不可变规则。

<a id="storage-and-construction"></a>
## 存储与构造

每个实例拥有一个稳定的控制记录，用于存放普通字段和组件元数据。每个可调整大小组件拥有自己稳定的元素区域、长度头部以及对其数据栈的访问权限。尽可能对普通组件沿用现有内存表示。控制记录属于实现细节，而不是一个可拷贝或可序列化的定长 K 值。

组件栈的数量由实例化后的类型和拥有型声明静态决定。生命周期互不相交的所有者可以像现有局部变量那样复用栈索引。全局变量使用专用的组件存储。在离开作用域时（包括 `break`、`continue`、普通返回以及 `return from`），恢复所有自有栈的水位线。部分构造失败或提前退出时也必须恢复已获取的存储，而不能对外发布未构造完成的所有者。

按声明顺序对字段初始化器求值一次。保留防止观测正在构造中存储的检查。构造完成的所有者随后可以由接收其引用的函数进一步初始化。不要引入析构函数、自动资源清理、运行时所有者计数或移动（move）语义。

尽管持有数据栈的根所有者其元数据大小恒定，它仍然受限于现有的递归环（recursive-cycle）约束。它不能跨递归环调用保持存活，因为每次激活都需要另一套独立的数据栈。将声明在递归环外部的所有者按引用传入仍然是推荐模式。在嵌套函数或编译期函数值中捕获此类引用遵循现有的捕获与逃逸规则。

<a id="component-identity-and-lifetime-analysis"></a>
## 组件身份与生命周期分析

仅靠外围变量的生命周期不足以标识其存储。请使用等价于“拥有型声明 + 字段路径”的身份来表示独立存储的组件：

```text
(state, .tokens)
(state, .work)
```

它们共享同一个外围生命周期，但属于不同的区域。通过字段投影、直接与可选所有者引用、分支、重绑定、调用、返回引用、全局变量、捕获以及已存储引用传递时，都必须保留这种区分。未知引用携带一个保守的可能区域集合；绝不能把一个生命周期边界提升为精确的组件身份。

实现方式：用一个合成变量表示每个组件。类根（class roots）可以携带相同的投影，而无需声称指向某个具体所有者。一个独立的 `projected` 证明会记录某个视图仍停留在该字段的区域内部，从而即使所有者引用是从某个持有者中加载出来的，检查器也能排除兄弟字段。从字段中读出的普通引用会丢失这一证明；自相对链接则保留该证明。连接（join）操作会对该证明取交集，弱化（weakening）操作会丢弃它，而返回值/效应摘要会保留它。这与精确身份不同，像 `index_of` 这类操作仍然需要精确身份。

具体而言：

* 增长一个字段不会干扰另一个字段中的构造。
* 收缩一个字段不会使指向另一个字段的引用失效，即使两者的元素类型相同。
* 收缩某个字段时，如果仍有任何跨调用或跨引用别名的活跃视图或持有者可能指向该字段，依然会被拒绝。
* `index_of` 必须确定具体的数组，而不仅仅是所有者。同一个根结构体中两个元素类型相同的数组依然是可区分的。
* 整数组引用指向其头部；元素引用指向元素区域。收缩检查必须保留这一现有区分。
* 自相对链接仍受限于其各自允许的连续区域内部。共同的外围所有者并不允许在独立栈之间或从控制记录向数组内部建立链接。此类链接应使用普通引用。
* 读回（read-back）、持有者/存储记录、效应摘要、构造冲突以及递归特化必须一致地传播组件身份。

相关代码包括 `src/ast.h` 中的 `RootAlt`/`Roots`、`src/typecheck_types.h` 中的 `RootedAtReceiver`/`OneArrayOf`，以及 `src/typecheck_builtins.h` 中的 `SoleResizableIn`、增长日志和收缩摘要。根集合连接（root-set join）按变量身份合并条目，其中独立组件拥有各自的合成身份；域测试（domain tests）覆盖了附加证明的连接/相等性定律。现有的紧凑结构体仍然共享同一区域：字段路径并不会在所有地方自动成为一个新区域。

在调研期间，针对现有编译器进行的小型类型检查探测表明：当一个标量分配器分别接收数据和空闲链表实参时，它允许跨越复用来保留引用。而当这些实参改为分组放进一个引用结构体中时，检查器会保守地假定返回值可能指向空闲链表，从而拒绝下一次分配。这是当前精度限制的体现，而非根结构体本身的测试。请在实现的验收用例中包含这种模式以及两个同类型的自有数组。

<a id="task-suspension"></a>
### 任务挂起

异步函数体或词法任务作用域可以借用具有已证明所有者的组件。共享租约（shared lease）会指名该组件的栈或字节区间，并允许独立兄弟组件上的变更操作。任务完成和取消会在任务清理完成后释放该租约。

局部组件读取会使相关存储跨越每一次 `await` 保持存活。当恢复执行的代码通过引用使用整个所有者时，任务会将该描述符及各个组件槽位保留在稳定地址上。已存储的引用槽位和切片槽位保留其经证明的底层所有者。[借用任务输入](async_and_decorators.md#borrowed-task-inputs)

标准库池对其 `items` 数组使用这些组件规则。任务的借用会保护底层存储免于收缩和替换。池复用仍然可以向既有槽位写入新值。

<a id="code-generation-and-performance"></a>
## 代码生成与性能

数组访问必须保持高效。把数组分组放进根结构体中，绝不能使现有的数组优化失效，也不能在热循环的每次迭代中引入无法解释的加载指令。

当前后端已经具备相关机制：

* `src/codegen_frames.h` 中的 `ParamFields` 会将切片、胖引用（fat reference）和池引用作为独立的 C 参数传递。这避免了平台 ABI 的开销，以及由聚合体参数拷贝带来的别名相关重加载。
* 栈顶缓存在 C 局部变量中，并在调用和退出处进行同步（`RefTopsOk`、`HandedStacks`、`SyncReach`、`Top`/`TopW`）。
* 边界检查消除（BCE）的 `hoistrefs` 和 `hoistfields` 允许代码生成在循环无法使数组基址与长度失效或重绑定的情况下将它们外提缓存。
* 现有的帧对象将固定前缀和可调整大小尾部的头部放在元素区域之外。

稳定的控制记录引用在 v1 中是一种合理的表示方式，但字段投影必须向这些遍（pass）暴露其正常的头部和栈信息。追踪根实参或被捕获的根能够触及的每一个栈。当某次调用可能修改已缓存的元数据时，刷新并重加载这些元数据，且不得假设两个参数必然是不同的所有者。重绑定、全局变量、回调以及非局部返回都需要与现有引用同等的谨慎处理。保留可观测的从左到右采样顺序。

除了计时数据外，还需检查生成的 C 代码。对比独立数组实参、普通单尾部结构体、包含两个数组的根结构体、借用上下文以及现有的可复用池。覆盖读取、增长、空闲链表频繁周转、同类型字段、非内联（out-of-line）调用、别名参数、回调以及选择所有者的分支。检查在合法情况下基址/长度读取是否被外提，以及不相关组件的变更是否会迫使不必要的重加载或丢失边界检查消除。在 O0/O2 以及 TinyCC/原生 C 上进行验证；对于对 ABI 敏感的改动，应涵盖 Windows x64 及其他 CI 目标平台。除运行时间外，还要记录地址预留数量和代码大小。

不要仅凭一次内联基准测试就承诺零开销。在迁移方案证明其行为和性能均达到可接受水平之前，保留现有的 `reusable`。对于初期的根结构体支持，若存在显著性能退化应明确报告，并在宣布该特性完成前先修好与现有优化的基础集成。

有两种调用降级（lowering）方式在传递描述符地址的基础上做了进一步优化：

1. **已知所有者特化。** 当所有传入调用都证明指向同一个全局所有者时，访问直接使用该所有者的字段和组件缓存。参见[已实现范围](#known-root-identity-across-function-calls)。跨已发射的调用边界保留局部所有者身份仍是后续工作。仅凭类型唯一不足以证明运行时实例唯一：必须考虑重复声明、递归、工作线程实例、别名以及重入。
2. **按字段拆分的降级。** 将描述符持有的头部、栈句柄和组件地址作为独立参数传递，这也是池的调用约定。写入仍然通过这些地址进行，因此所有者身份得以保留。如果参数的引用被存储、返回或捕获，则仍保留描述符。参见[按字段拆分的根参数](#field-by-field-root-parameters)。

保持 v1 语言契约独立于这些 ABI 策略，以便后续优化无需用户修改代码。

<a id="initial-native-measurement"></a>
### 初始原生性能测量

`python bench/root_structs.py --exe <k.exe> --n 32000000 --reps 9` 对比了 `push_ref.k` 与 `push_root.k`：两者使用相同的 RNG、元素写入、保留引用、校验和以及两个所有者实例。测试框架将两个 C `fill` 辅助函数都标记为 `K_NOINLINE`，从而在 K 的 O0 和 O2 下保留调用边界，同时使用原生优化编译 C 代码。它会保存耗时、生成的 C 代码、可执行文件大小以及栈报告。耗时包含进程启动时间。

Windows x64，2026-10-16，1 次预热后取 9 次运行的中位数：

| 原生编译器 | K 优化级别 | 独立数组实参 | 根实参 |
|---|---|---:|---:|
| MSVC 19.51 | O0 | 88.14 ms | 88.88 ms |
| clang-cl 22.1 | O0 | 85.57 ms | 85.64 ms |
| MSVC 19.51 | O2 | 86.78 ms | 87.18 ms |
| clang-cl 22.1 | O2 | 86.48 ms | 85.37 ms |

两者均使用 5 个数据栈区域（包括渲染），并产生完全相同的校验和，且在同一编译器下的可执行文件大小完全一致：MSVC 为 148,480 字节，clang-cl 为 155,648 字节。根结构体版本增加了 536 字节的生成独立 C 代码。这一探测结果表明该工作负载下没有显著性能退化；但它并不代表对所有容器或平台的普遍结论。空闲链表策略的对比仍属于独立的 `reusable` 迁移实验的一部分。

`root_owner_caches.k` 和基线运行器还会检查生成的 C 代码：两个独立字段的栈顶与长度缓存、索引读取的基址/长度外提，以及当所有者/所有者、所有者/数组或所有者/全局变量实参构成别名时的运行时正确性。这类别名场景会有意保留共享内存的栈顶同步。

<a id="serialization-workers-and-other-boundaries"></a>
## 序列化、工作线程及其他边界

V1 不支持根级别（root-level）的 `to_bytes`、`bytes_of`、`from_bytes`、原始相等性/拷贝，也没有公开的外部（foreign）值布局。即便每个组件各自都是扁平的（flat），根所有者也没有单一的连续内存映像。绝不能通过现有的扁平性或定长谓词意外接纳它。

对符合条件的组件（例如 `pool.items`）进行序列化或创建视图，在现有的映像安全性和生命周期规则下仍然是普通操作。这样的映像仅包含元素数据，而不包含根结构体的其他字段或空闲链表。将其加载到既有组件中遵循普通的赋值/收缩规则。需要协调快照的库可以日后自行定义显式的数据格式。

目前存在既有的将 `reusable` 传入工作线程的用例：`test/threads/thread_globals.k` 会从派生线程实例复制一个可复用槽位池和一个可复用切片池，保留空闲链表状态，并测试工作线程再派生另一个工作线程。当前代码生成会显式把空闲链表与数据一并复制。对于现有的 `reusable`，应保留该行为。

根结构体 v1 拒绝向 `thread_spawn` 或队列传递拥有型根，也拒绝发送指向拥有型根的引用。它还拒绝工作线程对根全局变量的任何直接或传递性使用，因为那会需要隐式拷贝该所有者。应诊断出可达的全局变量/调用路径。在工作线程内部构造的局部根不需要转移，因此是允许的。未被工作线程使用的无关根全局变量不应导致程序被拒绝。现有规则仍然规范合格组件作为拷贝数据的传递；绝不能传递描述符指针，也不能根据内容扁平就推断其可转移性。

工作线程快照支持可以在之后补齐：为每个组件重建独立存储、拷贝相关元数据，并且仅处理那些已经合法可转移的引用形式。这是一个明确的兼容性缺口，在声称标准库池已完全替代所有 `reusable` 用法之前必须予以解决。

格式化与反射必须区分“检查引用”与“拷贝或序列化其所有者”。保留字段访问和 UFCS；在不请求受禁值操作的前提下，支持按引用进行检查。不要仅仅为了伪装容器的 `items` 字段而添加数组运算符重载。

<a id="separate-follow-up-reusable-pools-in-the-stdlib"></a>
## 独立后续特性：标准库中的可复用池

`import slot_pool;` 提供了一个定长槽位分配器：

```klang
root struct slot_pool<T> {
    items: T[>..] = [],
    free_slots: i64[>..<] = []
}

var pool = slot_pool<i64> { .. };
let r .= pool.alloc_ref(42);
pool.free(pool.items.index_of(r));
```

其实现采用与标量 `reusable` 相同的 LIFO 空闲索引策略，提供分配、返回引用的分配以及受检释放。测试将该分配器的分配轨迹、保留引用及槽位内容与内置实现进行了对比。[API 参考](../stdlib.md#slot_pool)说明了受支持的元素类型及当前边界；[基准测试报告](../bench/slot_pool.md)对比了等价的原生工作负载。现有的 `reusable` 实现保持不变并继续可用。

`stdlib/slice_pool.k` 将其 `items`、节点数组和树状态打包在同一个根所有者中。它的三个树操作是 extern 函数（`stdlib/slice_pool_internal.k`），会将 `nodes` 和 `tree` 交给内置运行时区间树的一份副本处理：按索引首次适应放置、合并以及尾部复用，并在 K 中完成重叠安全的重定位。该副本会检查它从这些字段读取的内容（因为程序可以写入这些字段），并在节点编号或数量不合法时中止。差分测试对比了分配、释放和调整大小轨迹下的位置、保留视图以及每一个底层元素。参见其 [API](../stdlib.md#slice_pool) 和[基准测试报告](../bench/slice_pool.md)。这两种池类型都要求定长元素。工作线程快照仍然是一个兼容性缺口；全局组件路径和目标感知的槽位构造均已实现。

保留现有的安全契约：所有已发布的元素始终是有效的带类型值，释放仅仅将存储标记为可复用，过时的引用可能会观测到被替换写入的新值。除非库自行添加检测，否则双重释放属于逻辑错误。释放不承诺取消内存提交（decommit）、释放预留地址或执行析构。切片重定位不会重定目标现有视图；碎片化、高水位存储占用以及拷贝开销依然存在。

显式暴露 `items` 以用于索引、切片和普通数组算法。它的长度是高水位长度，而不是活跃槽位计数。仅遍历活跃槽位需要额外的元数据或操作。协调重置（coordinated reset）必须同时更新数据和元数据，并满足数据数组的常规收缩规则。K 目前缺乏字段私有性：内部字段命名约定和受检索引维护了内存安全，但任意的用户修改仍可能破坏池的不变量。私有性是另一项可能的改进，而非根结构体的前置条件。

迁移需要以下能力；已完成的部分已标出：

<a id="global-component-paths"></a>
### 全局组件路径

已针对全局 `var` 根所有者的可变直接数组字段实现：`Node&<u32 in nodes.items>`、`u32 in nodes.items` 和 `u32 upto nodes.items`。所有者名称可以带命名空间限定。目标必须是一个只增数组；别名、跨引用、索引和嵌套字段路径均会被拒绝。`in nodes` 仍然精确指代该全局变量本身，不会隐式选择 `.items`。

组件身份会在类型实例化之前预留，因此诸如 `Node` 链接到 `slot_pool<Node>.items` 这样的递归声明在整个检查过程中都保持相同的身份。当所有者字段的类型确定时，该字段会解析到这个已存在的组件。所有者引用特化通过辅助函数调用保留具名组件身份。位宽检查、精确根规则、索引/边界类型身份以及索引数组的禁止收缩规则依然有效。边界分析将具名组件识别为对应的字段表达式；代码生成直接使用其现有的全局头部与缓存基址。

类型可以使用数组基址和长度而无需标识符表达式。这些依赖关系会参与调用缓存同步和工作线程检查。对根组件的隐式依赖会在工作线程中被拒绝，就像显式使用其所有者一样。映像验证会在对照全局数组长度检查已序列化索引之前，先刷新已缓存的计数。

验证范围涵盖命名空间/别名往返、循环节点/池声明、全局字段初始化器、所有者引用转发、紧凑位宽溢出、索引边界与映像验证、跨字段/跨所有者拒绝、通过所有者和数组参数进行的禁止收缩检查，以及隐式工作线程依赖。完整原生基线在 O0/O2 下结合 TinyCC 和运行时调试覆盖全部通过；24 个专项夹具（fixtures）在启用编译器断言的情况下也全部通过。本次扩展未运行可选原生模块和 sanitizer 配置。

<a id="destination-aware-library-construction"></a>
### 目标感知的库构造

`alloc_with<T, F>(pool: slot_pool<T>&) -> T&` 使用普通的库控制流实现：弹出一个空闲索引并将 `F()` 赋值给该槽位，或者返回 `pool.items.push(F())`。它在选定目标位置后仅调用一次零参数构造器，并支持带有自相对链接或池相对 `self` 的全新定长聚合体。需要索引时，对返回的引用调用 `items.index_of`。

通用的编译器前置条件已在 master 分支单独合入；参见[返回值构造](result_construction.md)。全新返回值与拷贝是区分开的，接收根在跨调用传递时独立于参数槽位，且定长相对聚合体在所有优化级别下都通过目标指针原地构造。具名函数、尾随代码块、转发、递归以及非局部返回都共享这些规则。代码块仍自行推断其返回值类型；显式的引用返回函数可以提供引用类型的元素。`alloc_ref(value)` 和 `alloc_index(value)` 保留其常规的参数求值与拷贝要求。

不需要默认元素，也不需要未初始化的已发布槽位。追加元素只会在构造完成后才发布新的长度。非局部退出会保持该长度不变。复用槽位会在运行构造器之前移除空闲索引，并且不会在提前退出时回滚该移除操作或初始化器的副作用。被构造器释放的槽位在下次分配时仍然可用。无效的回收索引会在构造器运行之前触发边界检查失败。现有的构造、生命周期、根和拷贝检查依然有效。

构造器夹具测试覆盖了新槽位与回收槽位、邻接链接、两种相对形式的 `self`、转发、显式引用返回、不可默认构造元素、非局部退出以及空闲链表副作用。发布测试夹具与 `test/storage/alloc_half_built.k` 相对应，并产生相同的输出。拒绝测试夹具覆盖了拷贝、缓存调用上的错误根、短生命周期局部目标以及冲突的元素数组增长。

<a id="known-root-identity-across-function-calls"></a>
### 跨函数调用的已知根身份

当所有传入调用都指向同一个全局所有者时，代码生成会保留该根参数的身份。这与 `in pool.items` 类型无关：普通根结构体和普通值的池同样符合条件。在 K 优化之后，一项分析会追踪直接全局引用、不可变且未捕获的别名以及参数转发。递归边也参与同一不动点计算；在所有调用方达成一致之前，不会发射函数体。存在冲突或未知输入时，仍保留通用的描述符路径。该分析既不改变类型检查，也不会为每个所有者生成单独的特化版本。

在符合条件的辅助函数中，该参数直接成为全局所有者现有组件位置的别名。指向该所有者的多个参数共享其栈顶/长度缓存，也与函数体内的直接全局访问共享这些缓存。全局效应会通过调用方传播，因此嵌套调用和构造器回调会刷新/重加载相关缓存。单独传入的数组引用可以与所有者组件构成别名，并仍然走保守的未缓存路径。返回目标缓存也会继续把辅助函数对全局存储的访问考虑在内。

调用接口与参数求值保持不变。所有的索引、生命周期、构造与收缩检查依然有效。特别地，知晓所有者身份并不会使公开空闲链表中的内容变成可信的。不需要对根类型做单例假设：多个实例完全合法，由不同所有者共用的辅助函数会保留其描述符参数。

该扩展仅特化对已证明的**全局**所有者的访问。局部所有者仍然受益于现有的 K 内联/别名投影以及下述的按字段拆分接口；跨已发射函数边界保留局部所有者身份则需要额外的特化。可变的、被捕获的、已存储的、可选的以及其他不透明的根引用均采取保守处理，隐式格式化和标签分发（tag-dispatch）入口点也是如此。禁止向递归函数中执行 K 内联的限制保持不变。

<a id="field-by-field-root-parameters"></a>
### 按字段拆分的根参数

如果一个根引用参数在其函数中仅被投影、起别名或转发给另一个同类参数，则将其作为描述符的成员传递：每个可调整大小组件的头部和栈像胖引用参数那样传递（`ParamFields`），其他每个组件则传递其地址。函数体在一个供其投影读取的局部变量中重建描述符。一旦所有者创建完成，其描述符绝不会改变，因此在调用运行期间该副本即可代表它。若参数在其函数中被返回、存储、捕获、传给内置函数或具有固定接口的入口点（导出函数、工作线程、格式化与标签分发），或者转发给需要保留描述符的参数，则保留描述符的地址（`src/codegen_frames.h` 中的 `FindSplitRootParams`）。被证明指向单一全局所有者的参数则保留那一个指针，且函数体不会去读取它。`test/codegen/root_split_params.k` 覆盖了这两种情况。

与描述符指针接口相比，在 2026 年 10 月针对 K O1/O2 下的 `slot_pool` 和 `slice_pool` 微基准测试中，这种方式在 TinyCC 下对 `slot_pool` 快了几个百分点，在其他情况下处于运行间波动噪声范围内。与 `reusable` 之间剩下的差距并非来自调用接口。在 TinyCC 下，`slot_pool` 之前为了紧随自身长度测试之后的 `pop` 检查、临时变量以及结构体拷贝付出了代价，这些已由通用的代码生成改动消除（[slot_pool.md](../bench/slot_pool.md)）；从公开空闲链表中取出的 `items` 索引仍然保留其边界检查。`slice_pool` 的区间树是用受检 K 代码编写的，而 `reusable[]` 调用的是运行时的 C 代码（`k_spans_*`）。JIT 会以原生优化编译那些运行时 C 代码，因此在该场景下（碎片化和调整大小工作负载）存在约 2.5 倍的差距。

验证范围涵盖递归转发、由多个全局变量共用的递归辅助函数、独立局部池、别名所有者参数、独立传入的组件、嵌套调用缓存同步、自相对构造器、在构造器内部修改空闲链表，以及损坏的索引在产生构造器副作用之前就检查失败。完整 Windows 基线在原生 O0/O2、TinyCC、运行时调试、专项夹具中的编译器断言、自举（bootstrap）及 C 形态检查下全部通过。性能及其局限参见[应用测量](../bench/pool_workloads.md)与[微基准测试](../bench/slot_pool.md)。

<a id="checked-slice-position"></a>
### 受检切片位置

当来源分析无法证明输入切片属于该池时，内置的 `free_slice`/`realloc_slice` 可以在运行时检查对齐和完整包含关系。`index_of` 目前需要更强的静态来源证明。因此对外暴露了一个通用的受检切片到数组位置操作，现已实现为 `range_index`：在静态可证明时省略检查，否则在运行时检查对齐性与完整范围。所有空切片（包括外来切片或默认切片）都返回零。非空的外来存储会触发中止。不需要库层面的指针算术或未受检的索引伪造。

保留针对无效释放、负数/溢出分配长度和元素边界的全构建级别检查，并在当前契约要求的位置于元数据变更之前完成校验。切片分配会初始化每一个新增元素；重定位切片保留对自相对元素类型的限制。将所需的长度校验暴露为通用数组能力，而不是把运行时常量复制到库中。这通过 `check_length` 实现，它校验拟议的总元素数是否合法，而不会改变存储或承诺后续分配必然成功。`slice_pool` 在修改树元数据之前会先校验请求的数量和输入切片。分配和释放支持可默认构造的自相对元素；调整大小则和内置实现一样，仍然要求元素可拷贝。

<a id="policy-and-compatibility"></a>
### 策略与兼容性

库变体可以在只增元数据数组之上添加占用检查、代际编号（generations）、不同的区间策略或逻辑空闲链表计数。代际句柄是一个可选的 API，无法保护已经逃逸的原始引用。可参考 [slotmap 的带版本键](https://docs.rs/slotmap/latest/slotmap/)作为有益对照，但它并不是 K 现有复用语义的替代品。

在文档中弃用 `reusable` 和 `reusable[]`，并推荐新代码使用库类型。为现有代码保留其语法、诊断和运行时行为。全局组件索引/相对类型、目标感知的槽位构造以及工作线程局部库池均已实现。语法的正式移除属于后续变更，需在工作线程转移拥有经过评审的迁移路径之后进行。继续对应用工作负载以及重分配微基准测试进行测量；仅凭微小的性能退化本身并不足以成为保留语言级分配器的理由。

<a id="v2-candidates"></a>
## V2 候选特性

* **嵌套根所有者。** 允许在另一个根内部包含根字段，递归扁平化其有限的区域需求。在放宽放置限制前，需先定义初始化、投影、生命周期身份和诊断信息。普通的紧凑结构体仍然不能静默获得这种布局。
* **根所有者的小型常量数组。** 探索编译期常量 `N` 的 `slot_pool<T>[N]`。栈需求按静态常量 `N` 倍乘；运行时索引选择对应的所有者描述符/区域集合。需定义允许的嵌套位置、整数组引用、动态索引别名连接、初始化、迭代、`N=0` 以及实际的预留上限。这并不意味着支持可调整大小或运行时长度的所有者数组。在评估成本之前，不要任意设定一个较小的 `N` 语言上限。
* **局部所有者特化。** 扩展已实现的全局所有者优化，同时保留可寻址性与别名语义并最小化间接寻址。按字段拆分的调用降级已经实现（参见[按字段拆分的根参数](#field-by-field-root-parameters)）。
* **拥有型工厂返回值。** 直接构造到调用方提供的多个目标位置中，而不拷贝描述符并将其伪装成移动。通用的拷贝、重赋值和移动需要另行定义语义。
* **工作线程快照与协调序列化。** 按显式的格式/生命周期契约重建各个独立组件；绝不对所有者执行 memcpy。

<a id="implementation-sequence-and-acceptance"></a>
## 实现顺序与验收标准

1. **前端基础。** 解析并往返打印（round-trip）该上下文修饰符；通过泛型实例化和 AST 克隆传递结构体元数据上的该标记。添加语法测试覆盖与精确的错误信息。在增量开发期间，在存储支持就绪之前显式拒绝语义层面的使用：不要让根结构体落入普通的定长/可调整大小代码生成路径。
2. **放置、存储分类与来源追踪。** 引入显式的拥有型布局区分，而不是将固定元数据当作固定大小的 K 值处理。审计大小/扁平性/拷贝/包含性查询。实现组件身份及其连接、特化和效应摘要行为。
3. **所有权与代码生成。** 分配并恢复所有组件栈；支持字面量/默认值、局部/全局变量、引用、字段投影、别名、捕获与调用。集成栈顶缓存、调用可达性与视图外提。在代码生成之前拒绝不支持的转移、拷贝、嵌套所有者和临时对象。当特性可用时更新规范、参考文档、实现笔记和编辑器支持，不要将脚手架代码宣传为完整支持。
4. **库状态验收。** 演示由泛型函数使用的单声明多数组状态，并在无关字段操作期间保留引用。测试实际的运行时行为与生成代码，而不仅仅是解析。该里程碑不依赖于替换 `reusable`。
5. **池迁移实验。** 移植可拷贝元素的槽位分配，对比代码和耗时，然后解决上文提到的独立构造/路径/切片特性，并评估切片池和既有工作线程行为。

必需的专项测试包括：

* 独立的同类型字段；
* 对正确组件的收缩拒绝以及对不相关组件的收缩接受；
* 已存储、可选、返回及分支选择的所有者引用；
* `const` 与可写性；
* 泛型放置失败；
* 递归与非局部退出；
* 部分初始化；
* 组件序列化；
* 禁止的根序列化/FFI/线程使用；
* 允许的工作线程局部所有者；
* 传递性的工作线程全局变量拒绝。

同时测试指向同一所有者的别名以及指向不同所有者的情况。

在每个实现切片期间运行相应的专项测试，并在完成整个特性后运行仓库的基线编译器/运行时测试套件。修改根集合定律时扩展 `test/compiler_roots.cpp`。保持性能探测可重复并对比等价算法；不要把不同的空闲链表策略混淆为根引用开销。
