研究笔记，2026 年 11 月。K 现已为固定大小的 C 句柄记录及其具体闭包捕获实现了线性义务。本文探讨将其扩展至池占用声明、容器以及可挂起协程帧。
[已实现的 C 句柄规则](../k_spec.md#96-owning-c-handles)

核心问题在于：K 能否拥有足够强的所有权机制，从而解决 [coroutines.md](coroutines.md) 在 R5 中悬而未决的问题（挂起的协程可能被丢弃或复制，因此在其内部编写的任何清理逻辑都不可靠），以及 [llm_frontier.md §5.4](llm_frontier.md#54-owning-handles-a-free-is-a-shrink) 为池勾勒的问题（每次分配都恰好释放一次），同时又不放弃这门语言所立足的根本性质：每个值都是纯粹的数据，复制即 `memcpy`，丢弃即无操作，且在作用域退出时绝不会运行程序员未曾编写的代码。本文给出的答案是：之前的笔记用“所有权”一词指代了两种不同的事物，其中只有一种代价高昂，而廉价的那一种就足以同时解决这两个问题。

<a id="0-summary"></a>
## 0. 摘要

* **所有权是披着同一个词外衣的两项特性。** *义务*（obligation）是检查器围绕某个值所追踪的一项事实：它不可被复制，且在消亡前必须交由恰好一个消费者处理。*释放*（release）则是编译器在值消亡之处代为生成的代码。Rust、C++ 和 Swift 将两者捆绑在一起；Austral、Cogent 以及 OCaml 5 的延续（continuation）则只有前者而没有后者。[scope_exit_cleanup.md §4.7](scope_exit_cleanup.md#47-what-destructor-types-would-add) 中列出的反对析构器类型的每一项代价，实质上都是释放的代价（第 2 节）。
* **义务完全不触及代码生成。** 检查器放行的程序绝不会复制 `own` 值，也绝不会让其在未消耗的情况下消亡，因此后端继续为复制发射 `memcpy`，并在作用域退出时不生成任何清理代码；优化器遍（pass）、运行时函数、线程和序列化代码均无需改动。该特性所触及的，只是*检查器*判定复制或消亡的每一个位置，而 K 早已将这些位置全部枚举出来：持有自相对链接的值如今已是不可复制的定长类，在类型检查器中由 8 处通用检查点与 10 处内置函数专用检查点强制执行，并在代码生成阶段配有 3 条断言。`own` 沿用同一套谓词即可（第 3 节）。
* **`own` 是一个限定符，类似于 `const`。** `own T&` 是指向池槽位的句柄，`own T[:]` 是指向一段内存切片（run）的句柄，`own Texture` 则是原生句柄。被拥有的是对槽位的占用声明，而非内存本身：池拥有内存并在其自身作用域退出时将其释放，一如既往。新增的机制只是每个 `own` 变量对应的一位数据流状态位（持有或已消耗），在控制流汇合点按确定性赋值（definite assignment）的方式合并，遵循 Austral 的“各分支必须一致”规则，而一次消耗即构成针对该句柄所衍生引用的收缩（shrink）检查点（第 4 节）。
* **先实现线性形式，日后再以仿射形式作为语法糖。** 线性形式（程序显式写出每一次释放；`defer` 为所有退出路径认领句柄）无需编译器自行调用任何函数。仿射形式（编译器自动释放程序未手动释放的句柄）需要为每种句柄指定一个释放函数，这也是整个设计中唯一具有析构器形态的部分。先构建前者；后者只需在 `defer` 的发射逻辑上做增量扩展（4.5）。`defer` 在这两种形式下都保有自身地位，用于表达调用点自行编写的清理逻辑（4.9）。
* **在容器边界处，静态保证需要辅助机制。** 池元素的 `own` 字段采用破坏性读取，而池的 `free` 操作必须消耗掉元素仍持有的全部字段。最干净的形式是由程序为每个池编写一次终结块（finalizer block），再由检查器验证其完备性：即带有完备性检查的 [scope_exit_cleanup.md §3.3](scope_exit_cleanup.md#33-pool-finalizers)。存放此类元素的普通数组也以相同方式移除元素：`pop` 将元素移出，批量移除接受一个终结块，而局部数组在到达作用域退出时不得仍持有任何元素（4.6）。
* **对协程而言，`own` 属性正是所缺失的那项性质。** R5 的本质并不在于 `defer`。问题在于协程帧可以被丢弃或复制，而 `defer` 恰恰是唯一语义依赖“这两者都不会发生”的语言构造。有两种设计：（A）`own` 加入 R1 列表，禁止跨越挂起点（yield），从而使帧保持普通值的性质，资源则存放在由事件循环释放的池元素中；（B）只要挂起点处的作用域内存在 `defer` 或 `own` 局部变量，该*帧*本身就成为 `own`，编译器生成的 `cancel(f)` 会运行帧在当前挂起点处待执行的 `defer`，从而该帧既不能被复制（分叉会导致清理逻辑运行两次），也不能被丢弃（受义务约束）。A 只需增加一行规则，且不牺牲当前设计中的任何能力；B 使协程中的 `defer` 获得完整语义，而这正是 Rust 作用域任务三难困境（scoped-task trilemma）、OCaml 的“恰好继续或中止一次”以及 C++ 的 `destroy()` 所共同指向的方向（第 5 节）。
* **工程代价。** 线性 `own` 配合设计 A 在检查器和前端中的改动量大约与 `defer` 相当（已合入 1.3k 行），再加上两个标准库池上的生产者/消费者接口以及一节语言规范。设计 B 需在代码生成中增加 `cancel` 发射器，并在 coroutines.md 中调整三条规则。llm_frontier.md §5.4 所说的“数千行”对应的是带有容器支持的仿射形式（第 6、7 节）。

<a id="1-what-the-three-notes-decided-and-where-they-meet"></a>
## 1. 三篇笔记分别决定了什么，以及它们在何处交汇

[scope_exit_cleanup.md](scope_exit_cleanup.md) 选择了 `defer` 而否决了析构器类型，其 §4.7 列出了六条理由：需要引入触及每条目标赋值规则的新值类别；在每个容器的每次移除操作中都要触发析构；被丢弃的局部构造中间结果；无法用于一切按字节复制的场景；双重析构；以及在语言原本没有控制流的作用域退出点引入隐式控制流。该文随后建议接着实现池终结器（§3.3）和作用域分配（§3.4），但两者均尚未构建。`defer` 已按建议落地，包括禁止其主体使用远距离返回的规则——该规则通过调用图上的一个传递性标志位（`CheckDefers`）完成检查。

[coroutines.md](coroutines.md) 通过禁止跨越挂起点引用自身局部变量（R4），使协程帧成为可复制、可丢弃的普通定长值。由此，放弃协程的代价为零（“它不拥有栈，没有析构器，它在池中引用的任何对象都由池负责释放”，§4.10）；同时，它禁止在挂起点处的作用域内出现 `defer`（R5），因为该块的退出将发生在之后某次由不同恢复者发起的恢复执行中——甚至可能永远不会发生。其 §5 中的服务器示例通过约定来释放连接：观察到帧运行结束的事件循环会调用 `conns.free` 释放帧参数所指的连接。没有任何检查能够保证它确实这么做了，也无法释放在首次挂起之后协程体内部新获取的资源。该笔记的 §9 保留了 `defer` 这一开放问题，并建议为每个 `defer` 分配一个标志字节。

[llm_frontier.md §5.4](llm_frontier.md#54-owning-handles-a-free-is-a-shrink) 勾勒了拥有型句柄的设计：池操作返回一个 `own T&`，该句柄必须被恰好消耗一次；程序未手动释放的句柄由编译器自动释放；同时每次释放操作都构成针对从该句柄衍生出的所有普通引用的收缩检查点。该项被列为那篇笔记中侵入性最高的工作——“一种语言原本没有的值类别（不可复制），触及赋值、`copy`、字面量、按值 `match`、高阶函数捕获、泛型、`return … from`、`defer`、工作线程与映像”，规模为“数千行”，且排在最后。

这三篇笔记在 coroutines.md §2.6 的一句话处交汇：池拥有协程所不能拥有的东西。这解决了协程资源*存放在何处*的问题，却没有解决*当协程被放弃时由谁来释放它们*的问题，而针对后一问题的每一种答案都必然涉及某种形式的所有权。这个问题拉响的警报正是 scope_exit_cleanup.md §4.7 所写下的担忧：被拥有的值会让内存变得特殊。本文其余部分将论证事实并非如此，因为所有权中代价高昂的那一半，可以与协程和池真正需要的那一半剥离开来。

<a id="2-ownership-is-two-features"></a>
## 2. 所有权包含两项特性

以 Rust 的 `Box<T>` 作为完整捆绑形态来看：它不可复制（类型系统约束），移动之后不得再使用（数据流检查），并且当它消亡时编译器会调用 `drop`（生成的代码）。前两项构成**一项义务**：即检查器针对程序文本所确立的事实，只负责拒绝不合法程序而不发射任何代码。第三项则是**一次释放**：即编译器在该类型的值消亡的每一个位置写入一次调用——这意味着编译器必须在每一个容器、每一条退出路径上找出所有这样的消亡点，并且必须知道该调用哪个函数。

将这一拆分应用于 scope_exit_cleanup.md §4.7 的六项代价：

| §4.7 的代价 | 归属于 | 原因 |
|---|---|---|
| 1. 每条目标规则中引入新的不可复制值类别 | 义务 | 检查器拒绝复制；代码生成永远不会见到它 |
| 2. 每次移除时触发析构（`pop_n`、`clear`、收缩、重新赋值、容器消亡） | 释放 | 每一处都是值消亡且必须发射调用的位置 |
| 3. 被丢弃的局部构造中间结果 | 释放 | 半成品结果意味着没有对应程序文本的消亡值 |
| 4. 排除在一切按字节复制的场景之外（队列、映像、工作线程全局变量） | 义务 | 一个谓词即可，正如 `flat` 只是一个谓词 |
| 5. 双重析构 | 释放 | 只有发射出来的代码才可能运行两次 |
| 6. 作用域退出处的隐式控制流与调用 | 释放 | 由定义使然 |

六项中有四项完全属于“释放”的代价。而属于“义务”的两项（第 1 项和第 4 项）则是 K 为持有自相对链接的值早已支付过的代价（第 3 节）。

这一区分并不新鲜。Austral 的线性类型会拒绝丢弃线性值的程序，且从不代为调用任何函数；其作者报告称检查器仅约 600 行代码（[llm_frontier.md §5.5](llm_frontier.md#55-prior-art)）。Wadler 最早提出的方案也是同一形态：线性是一种类型纪律，编译器从中获得的是权限（在那里是原地更新的权限），而非必须履行的职责（[wadler]）。OCaml 5 的延续在运行时具有线性约束，且不由任何人自动释放：“每个被捕获的延续必须通过 `continue` 或 `discontinue` 恰好恢复一次”，并且“不恢复延续将会泄漏为纤程分配的内存以及挂起计算可能持有的任何资源”（[ocaml-effects]）。Rust 的异步工作组也明确记录了对“linear”的两种理解：类型系统层面的 `#[must_use]`，或者保证 `Drop` 必然运行（[wg-async-linear]）。K 需要的是第一种理解，因为第二种正是其内存模型刻意不予容纳的东西。

以编译器其余部分所依赖的不变量来表述，“义务”保留了以下一切：

* 定长值的复制即一次 `memcpy`（C 赋值）——保持不变，因为通过检查的程序中不包含任何对 `own` 值的复制；
* 作用域退出只是水位线存储与编写于此处的 `defer`——保持不变，因为通过检查的程序要么已在退出前消耗了每个 `own` 值，要么编写了完成该消耗的 `defer`；唯一新增的是一处针对持有 `own` 字段元素的局部数组的长度比较（4.6），这种检查在性质上如同越界检查，而非函数调用；
* 池槽位在任何时刻都是其类型的合法值（§5.4、§9.4）——保持不变，因为释放槽位不会对其字节做任何修改；
* 线程接收 `flat` 值；映像保存映像安全（image-safe）的值——保持不变，只需将 `own` 加入这两个谓词即可。

代码生成、优化器、运行时、JIT 后端乃至 Wasm 方案中的任何部分，都无需读取类型的 `own` 属性。这正是该特性不会“蔓延污染”的意义所在：它所触及的文件集合仅限于检查器与前端。而它*确实*会触及的，是检查器中判定复制或消亡的每一个位置——这组位置正是下一节的主题。

<a id="3-the-precedent-a-non-copyable-fixed-size-class-exists-already"></a>
## 3. 先例：不可复制的定长类已经存在

规范 §11（“Copying values that hold self-relative links”）：包含 `T&<u32>` 的值“不能以任何方式被复制：无论是通过变量赋值、作为按值传递的参数或 `match` 绑定变量、作为元素复制，还是通过 `copy(x)`”；它只能原地构造、通过 `.=` 绑定、使用 `&`-绑定进行匹配，并且仅在作为接收端直接构造的新鲜值时才能返回。该类别会沿字段传递（`HasRelRefT`），因此持有此类值的结构体同样不可复制。这恰恰就是 §4.7 第 1 项所述的“不可复制的定长值类别”，而编译器如今已在以下位置强制执行这一约束：

| 位置 | 函数 | 所拒绝的复制 |
|---|---|---|
| `copy(x)` | 内置函数中的 `NoRelRefCopy` | 显式复制 |
| `return` 值 | `CheckReturn` 中的 `NoRelRefCopy` | 从存储中复制出去；在接收端直接构造的新鲜值是允许的（`BuiltWhereReceived`） |
| 函数值的尾部表达式 | `NoRelRefCopy` | 代码块的结果 |
| 用作右值的值 | 值路径中的 `NoRelRefCopy` | 按值读取存储 |
| 强制转换为期望类型的值 | `CheckValue` 中的 `NoRelRefCopy` | 实参、存储写入、字面量字段、赋值 |
| 来自退化引用结果的 `let`/`var` | `NoRelRefCopy` | 当 `f` 返回引用时的 `let n = f()` |
| 来自初始化表达式的 `let`/`var` | `NoRelRefCopy` | `let n = other` |
| `.move_from`、`.resize` 的填充值、`.realloc_slice`、`.append` | `HasRelRefT` | 内置函数内部的元素复制 |
| `format` 钩子的按值参数 | `HasRelRefT` | 复制进用户重载函数 |
| 按值传递给 case 函数的载荷 | `HasRelRefT` | 分发调用 |
| 按值绑定载荷的 `match` 分支 | `HasRelRefT` | 要求改用 `&`-绑定 |
| 按值绑定元素的 `for` 循环 | `HasRelRefT` | 要求改用 `for &x in xs` |
| 原地构造判定（`BuiltInPlace`、`InitOrderStoreSafe`、临时对象内容） | `HasRelRefT` | 值可以在何处物化 |
| 代码生成：一处赋值和两条返回路径 | `NoSelfRelCopy` | 断言检查器已捕获所有情况 |

共 8 处通用检查点、约 10 处内置函数专用检查点以及 3 条断言。其中每一处都已经会询问“该类型是否不可复制，原因是什么？”，并在报错信息中指出修复方式。`own` 限定符只需向同一谓词添加第二种原因（由 `NonCopyable(t)` 返回是两者中的哪一种）及第二条报错信息；无需新增任何复制检查点，因为上面这份清单*就是*检查器所能见到的全部复制位置——而且是用硬功夫逐一排查出来的。这就是 §4.7 第 1 项实测得到的全部代价，它非常小。这也是 llm_frontier.md §5.4 中提到的唯一会改变普通代码写法的地方（“从数组或字段中读出它时必须通过引用、`.=`、`&`，而绝不能静默复制”）；这一限制正是带有 `Node&<u32>` 字段的 `Node` 早已施加的规则，而这门语言已经很自然地与它共存。

自相对值所*不*具备的是义务：它们可以被自由丢弃，因为它们只是一堆字节。义务才是 `own` 新增的部分，而它是一种数据流属性，而不是复制属性（4.4）。

<a id="4-the-design-own-as-a-qualifier"></a>
## 4. 设计方案：作为限定符的 `own`

<a id="41-what-is-owned"></a>
### 4.1 被拥有的是什么

`own` 像 `const` 一样修饰定长类型：`own T&`、`own T[:]`、`own T&<u32 in pool.items>`（较棘手的情形，v1 中暂不支持，见 4.6），以及诸如原生句柄之类的定长结构体 `own S`。`own` 值由声明其结果为 `own` 的操作产生（如池的 `take`、外部函数 `extern` 的 `create`），并由声明其参数为 `own` 的操作消耗（如池的 `release`、外部函数 `extern` 的 `destroy`），或由少数几个特定语言位置消耗（4.3）。

关键的一句话是：**被拥有的是占用声明，而非内存。** 指向 `slot_pool<Node>` 的 `own Node&` 是八个字节（若为相对链接则是四个字节），指向某个槽位，而该槽位的字节与任何其他槽位一样普通。池一如既往地拥有内存并在其自身作用域退出时释放它；`release` 一如既往地将索引压入空闲链表；除非程序主动选择启用 4.8 中更强的规则，否则指向同一槽位的普通 `Node&` 在释放之后的有效性与现在完全相同（类型安全的过期引用，§9.4）。句柄承载的是检查器负责核销的义务；槽位本身不承载任何额外状态。这正是对前述警报的回应：没有任何一字节内存会变得特殊，没有任何内存操作会发生变化。与 `const` 一样，`own` 按特化版本进行检查，并且对代码生成完全不可见。与 `const` 不同的是，它不能被自动推导，因为义务是程序做出的承诺，而非展现出的事实；它必须显式写出。

<a id="42-not-copyable"></a>
### 4.2 不可复制

沿用第 3 节的检查点，将 `own` 作为第二种不可复制的原因。对 `own` 值使用按值的 `for` 和 `match` 绑定会报错并提示改用 `&` 形式，与自相对值相同。`let m = h` 是一次*移动*：`h` 被消耗（4.3），而 `m` 转为持有状态。包含 `own` 字段的结构体传递性地成为 `own`。对 `own` 值调用 `copy` 会报错。若 `T` 含有非可选的 `own` 字段，则 `default<T>()` 不存在；若为可选字段，则其默认值为空句柄（4.6）。

<a id="43-what-consumes"></a>
### 4.3 什么会消耗所有权

处于持有状态的 `own` 值可以通过以下方式被消耗（且仅此一次）：

1. 将其传递给声明为 `own` 的参数（普通类型的按值参数会由 4.2 拒绝；普通类型的引用参数则会*借用*它，见 4.8）；
2. 将其 `return` 返回，从而将义务移交给调用方；
3. 将其存入 `own` 字段：在结构体字面量中，或通过 `replace`（4.6）；
4. 通过 `let`/`var` 绑定到新名称，这会移动它；
5. 由执行上述任一操作的 `defer` 主体所*认领*：随后代码块的每一个退出点都视作在那里消耗了它，而任何其他的消耗都将构成双重消耗；
6. 受信任的终点。消耗链条总得在某处终结：`slot_pool::release` 从句柄中读出索引并将其压回空闲链表，在此之后义务就必须单纯终止。存在两种形式：声明了 `own` 参数的 `extern fn` 会在调用时完成消耗（由 C 侧接管责任，这正是 `destroy(handle)` 的含义）；以及一个仅限标准库使用的内置函数，用于结束所有 `own` 字段均为空的句柄的义务（4.6）。标准库原本就使用特权内置函数（如 `check_length`、`range_index`），因此这完全符合语言风格，同时将受信任的消费者集合严格限制在池与外部函数之内。

`index_of(h)` 产生一个不带义务的普通索引，正如 §5.4 规则 6 所述；整数逃生舱依然保留，而将 `free(i)` 与指向同一池的 `own` 句柄混用的程序，自然只享有其停留在 `own` 世界那部分的保证。

<a id="44-the-flow-rules"></a>
### 4.4 数据流规则

检查器为作用域内的每一个 `own` 变量维护其当前是*持有*（`held`）还是*已消耗*（`consumed`），与 `FlowState` 已经保存并合并的确定性赋值状态位放在一起（`JoinFlow`、`MergeFlow`）。规则如下：

* **至多使用一次。** 使用已消耗的变量会报错并标出消耗它的那一行，其发现机制与使用未赋值变量完全一致：直接读取使用点处的流状态位，无需进行搜索。
* **分支必须一致。** 在控制流汇合点，如果某个变量在一条入边路径上已消耗而在另一条路径上仍持有，则在汇合点报错（“`h` 在 `if` 中已释放，而在 `else` 中未释放”）。这就是 Austral 的规则（“在 `if` 外部声明的线性变量必须在所有分支中都被消耗，或都不被消耗”），也正是它使每一个退出点的状态都保持静态确定：在任意程序点，编译器都知道 `h` 是否处于持有状态，无需在运行时保存任何标志位。直接离开的路径（`return`、`break`）不会到达汇合点，而是改由退出规则判定。
* **循环。** 如果循环体消耗了在进入循环时仍持有的变量，则在回边处报错，这由检查器在合并循环多轮遍历时所应用的同一条一致性规则自动触发。在单次迭代内部产生并消耗句柄则是完全合法的。传递给高阶函数的代码块会以内联展开进高阶函数特化版本的方式接受检查，因此每当高阶函数对代码块执行循环时，消耗了捕获 `own` 变量的代码块就会违反本规则；而每当高阶函数仅调用它一次时就能通过：llm_frontier.md §8 中关于捕获的问题由此迎刃而解，因为活跃度与数据流机制早已将函数值的主体视作可能再次执行的代码（`UsedAfter`）。
* **每个退出点都必须消耗。** 在声明块的所有退出点（自然落出末尾、`break`、`continue`、`return`、代码块通过高阶函数返回），变量必须已被消耗，或已被此前编写的 `defer` 认领。对于穿透该作用域的 `return … from`，退出点就是所有可能向上传播的调用点，而检查器早已按特化版本掌握这些调用点（`FnSpec::needs`，`CheckDefers` 已经遍历的标志位）：如果在持有未认领的 `own` 值时执行可能传播的调用，就会在该调用处报错，并指出可修复该问题的 `defer` 写法。异常中止（abort）不运行任何清理逻辑，与 `defer` 一致。
* **消耗即收缩。** 对于所有根植于该句柄的普通引用，消耗位置会被当作该句柄槽位的一次收缩来检查（4.8），复用收缩规则所使用的 `UsedAfter` 检测。

由此产生的报错信息正好符合 llm_frontier.md §3.9 认为机器作者易于处理的形态：一条完备、局部的规则，且报错信息直接给出修复方法（“`h` 在此 `return` 处仍被持有；请释放它、返回它，或用 `defer release(h)` 认领它”）。

<a id="45-linear-now-affine-later"></a>
### 4.5 先线性，后仿射

llm_frontier.md §5.4 曾提议以仿射形式作为默认行为：凡是程序未显式消耗句柄的地方，“编译器在代码块退出时自动释放它，就像它自己写了 `defer` 一样”。这正是整个设计中唯一属于第 2 节意义下“释放”的部分，它带有线性形式所没有的代价：

* **需要一个可调用的函数。** 编译器必须知道，对于根植于某个 `slot_pool<Node>` 的 `own Node&`，其释放函数就是该池上的 `slot_pool::release`。根对象在每个特化版本中是已知的；但释放函数却是这门语言目前尚无的一种声明，要么写在生产者上（`fn take<T>(p: slot_pool<T>&, v: T) -> own T& released by release`），要么写在类型上。它本质上是针对某一类类型的析构器，按每种池或每种外部句柄类型声明一次，并由编译器在恰好两个位置调用：一是退出持有未消耗句柄的代码块时（通过现有的 `RegisterDefer` 发射），二是释放仍持有未消耗字段的池元素时（4.6）。
* **它换来的便利。** 在 `let h = p.take(v); defer p.release(h);` 的惯用法中，如果某条路径上提前调用了 `p.release(h)`，在线性规则下就会构成双重消耗；程序只能在 `defer` 认领与提前释放之间二选一。仿射释放则让两者可以同时合法。Mojo 和 Swift 最终都选择了“默认仿射 + 可选线性”（[llm_frontier.md §5.5](llm_frontier.md#55-prior-art)），§5.4 也沿用了它们的路径。

本文建议采用相反的顺序。线性形式严格更小：它无需新增任何声明语法，不会调用任何程序未写出的代码，并严格恪守“作用域退出时绝不运行源码中未出现的代码”这一原则——因为 `defer` 就写在源码里。它也正是协程所需要的全部（5.3 只用到了认领规则，别无其他）。仿射形式则是一个增量特性，只需增加一种声明并将其路由到 `defer` 已具备的代码发射路径中；它可以等到实际代码中确实出现“双重消耗限制让人掣肘”的证据后再行添加，就像 `errdefer` 目前正在等待需求验证一样。4.9 将把 `defer` 放在这两种形式旁边进行对比。

<a id="46-containers-the-boundary-where-static-becomes-checked"></a>
### 4.6 容器：静态检查转为运行时检查的边界

4.4 的数据流规则之所以对变量成立，是因为变量的历史完全体现在程序文本中。而池元素的历史则不然：`conns.items[i]` 中的某个 `Conn` 是在早先某次调用中填充的，并将由之后某次调用来释放，这两处文本中都没有写明它的 `own` 字段当前持有何物。因此，在容器边界处，保证的性质发生了变化，设计方案必须明确如何处理。

**自有字段（own fields）。** 定长结构体可以拥有具备*空*（empty）状态的 `own` 字段：`own T&?`（空指针 null）或 `own T[:]`（空切片，`free_slice` 已能安全地接受空切片）。结构体字面量必须为每个此类字段提供 `own` 值或将其留空。读取此类字段是破坏性的：`take(e.buf)` 取出 `own` 值并将该字段置空；普通读取 `e.buf` 则产生一次借用（普通的 `T&?` 或 `T[:]`，见 4.8）。写入此类字段则使用 `replace(e.buf, v)`，它消耗 `v` 并将旧内容作为 `own` 值返回给调用方，调用方必须将其消耗（对空句柄调用 `release` 是空操作，因此 `p.release(replace(e.buf, v))` 就是标准惯用法）。Cyclone 的交换运算符与 Pony 的破坏性读取正是如此（[llm_frontier.md §5.5](llm_frontier.md#55-prior-art)）。普通赋值 `e.buf = v` 会报错并提示改用 `replace`，因为它会直接丢弃旧内容。这些都是内置操作，就像 `copy` 一样；它们只为检查器增加两处规则，而不增加任何代码生成逻辑（`take` 只是一次加载外加一次写入空值）。

**释放元素。** 当带有 `own` 字段的元素所在的槽位被释放时，必须有某种机制消耗掉这些字段仍持有的值，否则所有权保证就会恰好在最常使用池的地方出现漏洞。共有三种方式：

1. **运行时检查。** 如果元素的任何 `own` 字段非空，`free` 就直接中止并报告行号。在已经是一次函数调用的 `free` 中，为每个 `own` 字段增加一次加载和一次比较。它将内存泄漏转化为程序中止，就像 `gen_pool` 将过期读取转化为程序中止一样；但它不是静态保证。
2. **编译器生成的释放逻辑。** 即把 4.5 的仿射形式应用于字段：`free` 通过所声明的释放函数释放每一个非空的 `own` 字段。这就是 §5.4 规则 3 所说的“编译器根据字段类型自动生成的终结器”。
3. **由程序编写并经完备性检查的终结块。** 池的消耗型释放方法接受一个尾随代码块（K 已支持尾随代码块，标准库的 `alloc_with` 已经在使用），形如 `conns.release(h) { bytes.release(take(it.buf)); }`，而检查器要求在代码块结束时，`it` 的每一个 `own` 字段都确定为空：每次 `take(it.f)` 会将路径 `it.f` 的置空事实记录到数据流状态中（沿用数据流状态已经为字段销毁维护的按路径索引形式），而库函数 `release` 中紧随代码块之后的受信任终点（4.3 第 6 项）则会要求这些事实全部成立。由于代码块会被内联展开进库函数的特化版本中，这些事实无需任何新机制即可从代码块流向受信任终点。终结块按每个池写一次，紧邻池本身，任何遗漏的字段都会在那里直接报出编译错误。

第三种方式正是 [scope_exit_cleanup.md §3.3](scope_exit_cleanup.md#33-pool-finalizers) 提出的终结器，既补上了那篇笔记在没有 `own` 时无法实现的完备性检查，又省去了那篇笔记所需的语言钩子——因为 `release` 上的尾随代码块完全可以在库层面表达。这是本文推荐的形式。第一种方式可作为不愿手写释放逻辑的池的兜底方案。第二种方式则归属于未来的仿射增量扩展。

**数组。** 数组与变量的不同之处在于批量消亡：`clear`、`pop_n`、向下 `resize`、整数组赋值，以及局部数组退出作用域，都会一次性终结大量元素，而每个元素并没有各自对应的程序文本，因此检查器无法知晓各个元素的 `own` 字段里究竟装着什么。除了一处比较之外，以下规则使数组同样保持静态可控：

* 对含有 `own` 的元素执行 `pop` 属于移出操作，类似 `take`：字节离开数组，接收它们的局部变量接管该义务。此后若因先缩容再扩容而被其他类型复用的槽位，不再保有该元素的任何信息。
* 在此类元素上直接调用裸 `clear`、`pop_n`、`resize` 及整数组赋值，都会在内置函数实例化时报错，如同今天的“元素必须为定长类型”检查一样。标准库提供接受终结块的重载形式（`tasks.clear_all { cancel(it); }`），它们遍历元素，按与池 `release` 完全相同的方式检查是否已将 `it` 置空，最终调用特权清理操作。
* 全局的此类数组永不退出作用域，coroutines.md §5 中的每个工作线程任务表就属于此类。局部的此类数组在退出作用域时则不得仍持有任何元素：将其长度与零比较，否则中止并报告行号。这是整个设计中在作用域退出处新增的唯一一处运行时检查；只有当局部数组的元素类型被声明为拥有资源时才需支付这一代价，其形态与上述池边界完全一致。若采用 4.5 的仿射形式，则会改为用声明的释放函数遍历元素，这将成为整个设计空间中唯一一个 O(n) 复杂度的作用域退出操作，也正是线性形式选择长度比较的原因。
* 读取即为借用：`for &e in xs`、`xs[i].f`、`resume(xs[i], ev)`；按值读取 `xs[i]` 则被拒绝，与自相对元素的处理方式一致。

同样的规则也适用于池本身：由程序编写终结块负责在释放时清空元素的局部池，在退出作用域时必须已将全部槽位释放（`free_slots.len == items.len`，仅一次比较），或者通过库提供的遍历接口全部释放（`conns.release_all { … }`）。服务器示例中的池都是全局变量，永不退出。位于数组或池之外的普通全局变量中的 `own` 值既没有作用域退出，也没有任何机制可以消耗它，因此在 v1 中予以禁止。

<a id="47-threads-images-generics-return--from"></a>
### 4.7 线程、映像、泛型与 `return … from`

* `own` 既非 `flat`，也非映像安全（image-safe）：在 `IsFlat` 和 `ImageSafe` 中各加一行即可，两者原本就会递归检查字段。持有 `own` 值的帧或元素不能跨队列传递（接收方工作线程本来也无法将其释放回发送方的池中），也不能出现在 `to_bytes` 生成的映像里。参见 §5.4 规则 5。
* 泛型采用单态化，且检查器按特化版本运行，因此 `dictionary<K, own V>` 会在库函数体尝试复制 `V` 的位置（`slots[i].val = v`）失败，并在报错中附带完整的实例化链，就像索引类型若被传入不支持算术运算的函数体也会在该处失败一样。无需引入类似 `~Copyable` 的约束系统，而那正是 Swift 付出最多代价的地方（[llm_frontier.md §5.5](llm_frontier.md#55-prior-art)）。这两个池是目前真正用于存放 `own` 值的容器，它们将在现有操作旁新增感知 `own` 的操作。
* `return … from` 由 4.4 的退出规则覆盖：在持有未认领句柄时执行可能向上传播的调用会直接报错，而用于认领它的 `defer` 必须遵守 `defer` 主体规则（不允许远距离控制流机制），池的 `release` 显然满足该要求。这就把 Austral 的“与异常不兼容”转化为了一条带有局部修复方案的局部规则。
* 递归与循环调用不受影响：`own` 句柄是固定大小的，因此 §7.8 的 R1 对它不适用；带有 `own` 参数的循环函数（cycle function）像普通函数一样消耗该参数。

<a id="48-the-other-half-of-54-a-release-is-a-shrink"></a>
### 4.8 5.4 的另一半：释放即收缩

§5.4 的第二个构想独立于第一个，可以在前者之后构建：将 `release(h)` 视为对所有*衍生自* `h` 的普通引用（`let r: Node& = h;`）的槽位收缩操作，从而使此类引用在释放之后既不能再被使用，也不能被存入持有者结构体中。所需机制正是 §5.2 的扩容-收缩（grow-shrink）规则：指向 `[>..<]` 的引用只能存在于变量中，只要任何此类变量在收缩之后仍被使用，收缩就会报错（`UsedAfter`、存储记录以及跨调用的收缩摘要）。真正新增的部分，只是把句柄当作从其绑定出来的引用的根：这些引用精确地以句柄变量为根，就像 `&x` 以 `x` 为根一样，因此现有的检测逻辑就能直接找到它们。

它换来的是针对停留在 `own` 世界中的句柄实现“绝无通过引用的过期读取”这一保证。它无法触及的是存储在另一个元素中的相对链接，这一点 §5.4 已经让位于代数标记（generations）。它同样不增加任何代码生成逻辑。这里将其列为可分离的增量特性，一是因为防泄漏与防双重释放保证并不依赖它，二是因为在第一部分尚未实现之前，§5.4 这部分在检查器中的实现代价尚最不明确。

<a id="49-own-beside-defer"></a>
### 4.9 `own` 与 `defer` 并存

两者都会向作用域退出点挂载清理逻辑，因此必须厘清它们之间的重叠。几种形式的区别在于由谁*强制*执行清理，以及由谁*编写*释放调用：

| 形式 | 由谁强制清理 | 由谁编写释放调用 |
|---|---|---|
| 仅 `defer` | 无人强制 | 调用点，在每次使用时编写 |
| 线性 `own` | 生产者的声明（`-> own T&`） | 调用点，写作 `defer release(h)`；检查器验证其覆盖每条退出路径 |
| 仿射 `own` | 生产者的声明 | 声明本身，按每种句柄写一次；编译器自动发射调用 |

因此，在线性规则下，`defer` 并非用来“敷衍检查器”的手段。它*就是*释放本身，而 `own` 的作用则是确保遗漏它、重复写它或在它之后继续使用句柄都会报错。仿射形式将释放文本从每个调用点移到了一处声明中，并为 `defer` 保留了四项职责：

* **生产者作者无法预知的清理。** 释放函数仅取决于句柄的载荷，由生产者固定决定。而 `defer` 主体是一段访问作用域内局部变量的代码块，在退出时执行。纵观整个代码库中的 `defer`，除了一个之外，其余全都是句柄形态或可用空状态守卫覆盖的全局状态配对——包括 `31_mini_doom` 中的条件释放 `defer if sound_ready { audio::close(); }`（即一个以该条件为空状态的 `own Audio?`）。唯一例外的那一个是 `stdlib/exception.k` 中的 `defer Finally();`：它运行调用方传入的函数值，在调用处内联展开，这是任何字段都无法容纳的。在代码库之外，常见的形态还有编译器里常见的作用域压栈：`scopes.push(s); defer scopes.pop();`，它作用于另一个局部变量。若强行将其封装为句柄，它既非空值，又携带指向 `scopes` 的引用，按引用字段规则这会使其成为一个持有者，而且你还得额外编写一个类型、一个返回 `own` 的生产者以及一条释放声明——用四条声明去替换一行代码。
* **按种类付费 vs 按调用点付费。** 空状态守卫很适合全局状态配对（`let w = gfx::open(…)` 返回 `own Window`，由 `gfx::close` 释放）：按每种类型支付一次声明代价，此后每个调用点无需书写任何清理代码即可保证正确——这对于 llm_frontier.md §3 中的机器作者而言是更强的形态。`defer` 则是在每个调用点付出几行代码，而无需任何前置声明。标准库应当为高频出现的资源（池、窗口、文件、锁）建模 `own`，而 `defer` 则留给一次性的局部清理。结论是在标准库中提供更多 `own` 生产者，而不是减少语言里的 `defer`。
* **实现载体。** 仿射释放本质上就是编译器代写的 `defer`：它通过 `RegisterDefer` 发射，遵守 `defer` 主体规则（不可挂起、不可远距离返回），并且在设计 B 下，`cancel` 会通过同一套 `switch` 语句统一运行待执行的 `defer` 与待执行的仿射释放（5.3）。移除 `defer` 只意味着要在编译器内部重新把它造一遍。
* **在仿射形式落地之前。** 第 8 节将仿射形式安排在有实际需求之后；在此之前，`defer` 认领就是唯一的释放文本形式。

两者的交叠还带来了两点收获：

* **仿射释放天然就是面向句柄的 `errdefer`。** 在 [scope_exit_cleanup.md §3.6](scope_exit_cleanup.md#36-only-on-failure) 的唯一示例中，`let id = nodes.take(…); … return id;` 在成功路径上消耗句柄，而在此之前穿透该作用域的 `return … from` 则自动释放句柄，甚至无需引入新关键字。线性形式无法这样写：`defer nodes.release(id)` 与 `return id` 并存属于双重消耗，因此每条失败路径都必须手动释放。对于句柄而言，第 8 节第 5 步所等待的需求，与 `errdefer` 所等待的需求其实是同一个需求。
* **在仿射形式下，显式的 `defer release(h)` 应当删掉而非保留。** 若它与某条路径上的提前 `release(h)` 并存，它依然会构成双重消耗，因为代码块内部指名了已消耗的 `h`。届时的惯用法将变为：在程序需要之处提前释放，或者干脆什么都不写。

在语法拼写上，`let h: own Foo? = init();` 比实际需要更啰嗦。局部变量不需要 `?`：持有还是已消耗是数据流事实，`?` 仅用于字段，因为字段的空状态必须在运行时存在（4.6）。局部变量也不需要类型标注，因为类型来自生产者，所以 `let g = lock(m);` 就是完整的守卫写法（第 9 节的第一个问题）。真正需要定下规则的是*未命名*守卫——即丢弃返回值的裸调用 `lock(m);`。在线性规则下这本来就已经是编译错误：一个 `own` 值未经消耗就消亡了。仿射形式也应当保持将其视为错误并要求命名，而不是在语句末尾立刻释放——后者正是 Rust 的 `let _ = m.lock()` 所犯的错误：守卫在它本应保护的代码开始之前就已经释放了。

<a id="5-coroutines"></a>
## 5. 协程

<a id="51-r5-restated"></a>
### 5.1 重述 R5

coroutines.md 为 R5（挂起点处的作用域内不得存在 `defer`）给出了两条理由：该块的退出“将发生在之后某次由不同恢复者发起的恢复执行中”，以及（§4.10）协程帧可能被放弃，此时退出点永远不会到来。一旦协程帧的局部变量被提升到帧结构体中，第一条理由便不再是问题：引用局部变量的 `defer` 主体本身就会让该变量跨越挂起点保持活跃（R3），因此在到达退出点的那次恢复执行中它会被重新加载，而那次恢复发生在哪条线程或哪个事件循环上并不重要，因为主体只引用帧自身的字段以及帧外部的对象（R4）。第二条理由才是真正的症结，它包含两半：挂起的帧可能被**丢弃**，导致退出永远不会发生；它也可能被**复制**，导致退出发生两次。`defer` 是 K 中唯一一个语义依赖“这两者绝不发生”的语言构造，而协程帧则是 K 中唯一一种会让已开始执行的代码同时面临这两种命运的值。

这样表述之后，解决方案就不是为每个 `defer` 增加一个标志字节（coroutines.md §9）——那只能让正常退出运行正确的主体，对无人恢复的帧却无能为力。真正的解决方案是让帧既不能被丢弃也不能被复制，而这正是 `own` 值的定义。由此引出两种设计：一种把帧留在 `own` 世界之外，另一种把帧纳入其中。

<a id="52-design-a-own-joins-r1"></a>
### 5.2 设计 A：`own` 加入 R1

R1 规定挂起点处的作用域内不得存在非定长局部变量，因为挂起的帧无法拥有数据栈。在此补充一条：挂起点处也不得存在 `own` 局部变量，因为挂起的帧无法履行其义务。报错信息指出的修复方式，与 §7.8 为可增长数据指出的方式相同：将其所有权放到帧外部。

```klang
struct Conn { fd: i64, inbuf: u8[..4096], scratch: own u8[:] }   // 该内存切片归连接所有

coro fn serve(c: Conn&) resume Event {
    loop {
        guard fill(c) else { return; }
        {
            let s = bytes.take_slice(need);          // own u8[:]，处于持有状态
            parse_into(c.inbuf[..], s);
            replace(c.scratch, s) |> bytes.release;  // 在下方挂起点之前已消耗
        }
        guard flush(c) else { return; }              // 内部会挂起
    }
}

// 事件循环释放连接；检查器会验证池的终结块消耗了 Conn 拥有的全部资源，
// 因此协程帧本身无需承担此责。
guard suspended else {
    conns.release(conns.handle_of(tasks[i].c)) { bytes.release(take(it.scratch)); }
    tasks.free(i);
    continue;
}
```

（全文语法均为占位表示；`|>` 代表将 `replace` 的结果传给 `release`。）帧依然保持普通值的性质：可复制、可丢弃、当其字段为 `flat` 时自身也为 `flat`、可序列化，与 coroutines.md §4.9 和 §4.10 的描述完全一致。变化之处仅在于：R1 增加一项，并由此得到一条强保证——协程使用的每一项资源，要么由单段恢复执行中的局部变量拥有（由 4.4 负责核销），要么由池元素的 `own` 字段拥有（在事件循环释放它时由池的终结块负责核销）。此时唯一可能发生泄漏的位置，只剩事件循环忘记释放池元素这一处，也就是集中在单一函数中的那一次 `free`，而 coroutines.md 原本的约定也正是把责任放在这里。

A 所放弃的能力是：在挂起点之前获取、在挂起点之后释放的资源，必须在两者之间通过某个字段中转，哪怕只是单个协程自用的临时切片也是如此。这与语言已经对跨挂起点及跨循环调用的可增长局部变量所要求的纪律相同，而且服务器场景本来就需要这样做（在帧挂起期间，内核正是直接写入连接的缓冲区）。`defer` 则继续被排除在协程挂起点之外。

<a id="53-design-b-own-frames-and-cancel"></a>
### 5.3 设计 B：自有帧与 `cancel`

允许 `own` 局部变量跨越挂起点，并允许 `defer` 处于挂起点处的作用域内，只需遵循一条规则：**在挂起点处，作用域内的每一个 `own` 局部变量都必须已被一个待执行的 `defer` 所认领**（4.3 第 5 项）。于是：

* **只要函数体中任一挂起点处的作用域内存在 `defer` 或 `own` 局部变量，该帧类型即为 `own`。** 两者皆无的帧则一如既往保持普通类型。因此生成器或巡逻逻辑不付出任何代价；只有跨越等待点持有资源的协程，其自身才成为一项资源——这本就是它的实质。
* **`cancel(f)`** 是与 `resume` 并列的第二个内置操作，也是帧的消费者。编译器为每个 `own` 帧类型生成它，作为 `resume` 函数的孪生兄弟：一个基于状态标签（tag）的 `switch`，对于挂起点 *k* 的分支，它会重新加载待执行 `defer` 主体所引用的被提升局部变量，按后进先出的顺序运行在挂起点 *k* 处尚未结束的 `defer` 主体，正如它们所在代码块正常退出时那样（`EmitDeferBody`），然后将帧标记为已完成。每个挂起点处待执行的 `defer` 集合是静态确定的（即该挂起点处仍打开的作用域），因此无需额外存储任何标志位：coroutines.md 本来就维护的状态标签，正是其 §9 所寻找的那个标志。对于未启动或已完成的帧，`cancel` 只是一次标签比较，别无他事。正因为挂起点处作用域内的每个 `own` 局部变量都已被待执行的 `defer` 认领，运行这些待执行的 `defer` 就会释放帧所持有的全部资源，编译器自身无需知道如何释放任何东西；`cancel` 运行的完全是程序自己在相应位置写下的代码。
* **复制在第 3 节的检查点处被拒绝**，因为帧类型是 `own`：一旦分叉就会导致 `defer` 运行两次。**丢弃则由数据流规则拒绝**：局部的 `own` 帧必须在每条退出路径上被取消（`var task = serve { c }; defer cancel(task);` 是标准惯用法；`resume` 是借用而 `cancel` 是消耗，且对已完成的帧调用 `cancel` 是幂等的）；存放在池中的 `own` 帧则由池的终结块消耗，检查器会强制要求该终结块调用 `cancel(it)`。
* **在此形式下，`coro fn` 不允许带有 `own` 参数**：未启动的帧（标签 0）尚未运行任何 `defer`，因此没有任何逻辑能认领它们。与设计 A 相同，协程借用其连接（`c: Conn&`），而任务元素拥有它。
* `defer` 主体依然不得挂起（R7）或使用远距离返回，因此 `cancel` 是直线型代码，并且与 `resume` 一样运行在调用者所在的线程上。

B 相当于 A 再加上三件事：由挂起点推导帧类型的 `own` 属性、`cancel` 代码发射器，以及将 R5 放宽为“挂起点处作用域内的 `defer` 使帧成为 `own`”。它换来的好处是，清理逻辑可以直接写在协程内部、紧邻资源获取之处，并且保证恰好运行一次——无论先到来的是正常退出还是取消操作：

```klang
coro fn serve(c: Conn&) resume Event {
    loop {
        guard fill(c) else { return; }
        let s = bytes.take_slice(need);
        defer bytes.release(s);                      // 认领 s：在块退出或 cancel 时运行
        parse_into(c.inbuf[..], s);
        guard flush(c) else { return; }              // 内部会挂起；s 处于持有状态且已被认领
    }
}

// 事件循环：断线或关机时取消任务，从而释放协程体在当前挂起点所持有的全部资源；
// 随后两个槽位一并归还。
guard suspended else {
    tasks.release(tasks.handle_of(i)) { cancel(it); }
    conns.release(conns.handle_of(c)) { bytes.release(take(it.scratch)); }
    continue;
}
```

首次阅读该帧所生成的 C 代码的读者，会看到一个 `serve_resume` 和一个 `serve_cancel`，两者各自是对同一个状态标签的 `switch`，一眼便能认出它们的关系。

<a id="54-what-b-would-change-in-coroutinesmd"></a>
### 5.4 B 会对 coroutines.md 做出哪些修改

* **R5** 将变为：挂起点处作用域内的 `defer` 或 `own` 局部变量会使帧类型成为 `own`；挂起点处作用域内的 `own` 局部变量必须已被此前编写的 `defer` 所认领。若仅采用 A，则 R5 保持原样，而 R1 增加 `own`。
* **§4.9（复制与平坦性）** 对普通帧继续成立；对于 `own` 帧，则由第 3 节的拒绝规则取代：禁止分叉、禁止按值 `pop`、禁止入队列、禁止写入映像。`own` 帧类型依然是定长的，且布局仍如 §4.12 所述。
* **§4.10（放弃）** 对普通帧继续成立；`own` 帧只能通过 `cancel` 来放弃，这正是设计的本意。
* **§4.3** 新增 `cancel(f)`；**§4.12** 新增 `cancel` 函数的降级（lowering）说明；**§8 第 4 步**新增其代码发射（对同一组标签的待执行 `defer` 生成第二个 `switch`），**第 5 步**新增对应测试：在每个挂起点取消、取消已完成的帧、拒绝复制 `own` 帧、拒绝在未调用 `cancel` 的情况下释放池中的帧。
* **§4.1**：`coro fn` 不允许有 `own` 参数（5.3）。

§4.4（在协程中调用另一个协程）无需任何改动：被调用协程的局部变量与 `defer` 会内联拼接进调用者的分段与标签中，因此调用者挂起点 *k* 处仍处于挂起待执行状态的被调方 `defer`，自然也就位列 `cancel` 为 *k* 运行的主体之中。

<a id="55-the-server-both-ways"></a>
### 5.5 服务器示例的两种写法

| | 设计 A | 设计 B |
|---|---|---|
| 连接资源的存放位置 | 池元素的 `own` 字段 | 同左，或由协程体内部 `defer` 认领的 `own` 局部变量 |
| 挂断时由谁释放 | 事件循环，通过池的终结块 | 先 `cancel`，再执行池的终结块 |
| 帧类型 | 普通 | 默认普通，除非协程体跨挂起点持有资源或 `defer` |
| 帧能否进队列、进映像 | 可以 | 普通帧可以；`own` 帧不可以 |
| 协程中的 `defer` | 不允许处于挂起点 | 任意位置；负责认领其所释放的资源 |
| 编译器新增生成代码 | 无 | 每个 `own` 帧类型生成一个 `cancel` 函数 |
| coroutines.md 中修改的规则 | 在 R1 中加一行 | R1、R5、4.9、4.10 变为条件规则；新增 `cancel` |
| 遗忘释放的失败情形 | 事件循环忘记调用 `conns.release`（仅一处） | 同左，或漏掉由终结块检查强制要求的 `cancel` |

A 是 B 的真子集：在 A 下写出的程序，在 B 下就是只使用普通帧的合法程序。因此 A 可以随协程 v1 一同发布，待日后确实需要让协程体跨等待点持有资源时再跟进 B，这期间已写出的任何代码都无需修改。

<a id="56-prior-art-specific-to-frames"></a>
### 5.6 针对协程帧的现有技术

* **C++** 通过 `coroutine_handle::destroy()` 显式销毁挂起的协程，运行挂起点处活跃变量的析构器（[cpp-destroy]、[oldnewthing-cleanup]）。B 的 `cancel` 就是该操作，只是用 `defer` 主体取代了析构器，并用帧的不可复制性取代了句柄的不可复制性。
* **Zig 最初的异步设计** 通过运行作用域内的 `defer` 和 `errdefer` 表达式来在挂起点销毁帧（[zig-1261]），并在文档中说明每个挂起点都是协程可能被销毁的位置；该特性后来随该设计其余部分一并被移除（[coroutines.md §3.6](coroutines.md#36-zig-twice)）。当时的帧是可丢弃的，因此这些 `defer` 能否运行取决于拥有者是否记得销毁——这正是 `own` 属性所填补的缺口。
* **Rust** 允许任何 `Future` 在未轮询至完成的情况下被丢弃或泄漏。其后果正是 coroutines.md §3.2 引述的取消安全（cancellation-safety）隐患，以及作用域任务三难困境：借用式并发 API 不能依赖析构器去 `join` 子任务，因为任何值都可以被泄漏，因而只能局限于词法作用域；线性类型本可以改变这一点，但被认为事后改造成本过高（[boats-trilemma]）。“Linearity and Control”对异步作用域提出了相同的论点（[wuyts-linearity]），而“Asynchronous clean-up”则将异步取消路径和 `do … final` 构造视作线性类型的前提条件（[boats-cleanup]）。K 没有历史兼容性包袱需要背负：协程尚未上线，而 B 可以在任何代码持有帧之前就确立帧的线性约束。
* **OCaml 5** 在运行时强制延续为单次触发（“通过 `continue` 或 `discontinue` 恰好恢复一次”，`Continuation_already_resumed`），同时承认“没有任何检查能确保延续至少被恢复一次”，因此未被恢复的延续会泄漏“挂起计算可能持有的任何资源”（[ocaml-effects]）。这相当于在运行时强制了仿射的那一半，而对线性那一半完全未加约束；B 则在静态期同时强制这两半。
* **Kotlin 和 Python** 通过在挂起点抛出异常来运行 `finally` 块；Python 的 `close()` 还会由垃圾回收器触发，这也正是其调用时机不可预测的原因（[coroutines.md §3.4, §3.7](coroutines.md#34-kotlin)）。B 的取消则是由拥有者发起的一次明确调用，而拥有者之所以确定无疑，正是因为帧不可复制。

<a id="6-where-the-compiler-changes-and-where-it-does-not"></a>
## 6. 编译器改动之处与不变之处

对于先采用方案 A、再引入方案 B 的线性设计：

| 领域 | 改动内容 | 规模（以现有实现为参照） |
|---|---|---|
| 词法分析器、解析器、AST、克隆、转储、LSP、tree-sitter、参考手册附录 A | 类型上的 `own` 限定符，以及作为内建项的 `take`/`replace`/`cancel` | 与 `const` 和 `defer` 相当：解析器中为 `defer` 增加了 45 行 |
| 类型谓词 | 带原因说明的 `NonCopyable(t)`，用于替换第 3 节各处单纯的 `HasRelRefT` 检查；`IsFlat`、`ImageSafe` | 8 + 10 处各改动一次调用和一条诊断信息；另加两处单行补充 |
| 控制流分析 | 在 `FlowState` 中增加持有/已消费位，在 `JoinFlow` 中按一致规则汇合，并在退出点结合明确赋值退出逻辑进行检查；针对 `take` 的路径空置事实 | 最大的新增部分：`defer` 的流分析在 `typecheck_flow.h` 中占 196 行；据报告 Austral 整个检查器仅 600 行 |
| 消费位置 | 调用点的 `own` 参数、`return`、字面量中的 `own` 字段、`let` 移动、`defer` 声明、受信任终点、`extern` 参数 | 在现有实参、返回值与字面量检查逻辑中各增加一种情况 |
| `return … from` | 当持有未被认领的 `own` 时，在调用处查询一次 `FnSpec::needs` | 复用 `CheckDefers` 的标记 |
| 协程，方案 A | R1 的类别检查中的 `own` | 一行代码，位于 coroutines.md §8 所规划的 `CycleCallTemps` 复用第 3 步中 |
| 协程，方案 B | 由各 yield 所在作用域推导帧的 `own` 属性；为每种 `own` 帧类型生成一个 `cancel` 函数：基于标签的 `switch`，每个分支通过 `EmitDeferBody` 生成待执行的 defer | 整个设计中唯一的代码生成改动；规模受 `own` 帧类型数量限制 |
| 标准库 | 在 `slot_pool` 和 `slice_pool` 现有操作旁增加 `take`/`release`/`handle_of`，并附带终结器块形式的 `release` | 数十行 K 代码 |
| 语言规范 | 在 §9.5（可写性）旁新增一节说明该限定符与流规则；在 §5.4 的后续章节中补充池操作；协程的 R1/R5 | 篇幅与 §5.2 相当 |
| 复制、赋值、退出、返回的代码生成；优化器；运行时；JIT；Wasm；线程；序列化 | 除持有 `own` 元素的局部数组在作用域退出时的长度比较（4.6）外，无需任何改动 | 第 2 节的不变量由构造天然保证 |

最后一行正是对本备忘录所提出问题的回答。必须感知 `own` 的位置仅限于检查器的复制检查点（均已枚举）、控制流状态（1 个比特）、退出检查逻辑（1 次查询），以及在方案 B 下为每种 `own` 帧类型生成一个函数。令 K 值保持纯朴平凡的所有机制均维持原样，因为通过检查的程序绝不会要求它们执行任何新操作。

## 7. 各方向横向对比

| 方向 | 内容概述 | 提供的保证 | 会拒绝哪些当前能编译的代码 | 编译器改动 | 运行时改动 |
|---|---|---|---|---|---|
| 0. 维持现状外加 `gen_pool` | 在库中实现代次（generation）；按 scope_exit_cleanup.md 的建议采用终结器与作用域内分配 | 过期读取和双重释放会中止；调试模式下报告泄漏 | 无 | 无 | 每次查找一次代次比较 |
| 1. 线性 `own`，方案 A | 第 3、4 节（线性），5.2 | `own` 世界中的句柄恰好释放一次；池元素的字段在释放该元素时一并释放；协程在 yield 边界不持有任何资源 | 普通全局变量中的 `own`；不带终结器块地批量移除持有 `own` 的元素；对同一句柄同时进行提前释放与 `defer`；通过队列和镜像传递 `own`；跨越 yield 持有 `own` | 如第 6 节所述的检查器与前端改动 | 无 |
| 2. 方向 1 外加方案 B | 5.3 | 额外保证：协程内部编写的清理代码在退出或取消时恰好执行一次；`own` 帧不可被分叉或遗忘 | 额外拒绝：复制或入队一个持有资源的帧 | 额外为每种 `own` 帧类型生成一个函数 | 无 |
| 3. 仿射释放 | 在 1 或 2 之上的 4.5 | 提供相同的保证，并由编译器补写程序省略的释放逻辑 | 与 1 相同，但放宽提前释放限制：在某条路径上释放的句柄会在其他路径的退出处释放（4.9） | 为每种句柄类型声明释放方式；通过 `defer` 路径生成代码 | 无 |
| 4. 析构器类型 | scope_exit_cleanup.md §3.2 | 在任意容器中的每一次消亡时均执行释放 | 无 | §4.7 所列各项 | 容器销毁时遍历释放 |

依赖关系：1 无前置依赖（池已在标准库中；`defer` 已存在）；2 依赖 1 与协程 v1；3 依赖 1；4 保持否决状态。4.8 中的“释放即收缩（release-is-a-shrink）”是建立在 1 之上的增量特性，无其他依赖方。

<a id="8-recommendation-and-order"></a>
## 8. 建议与推进顺序

`own` 是一项独立决策。coroutines.md 是既定的协程设计方案，不依赖 `own` 即可独立成立：R5 与 §4.10 在其自身体系内自洽，在那种情况下，循环约定加上 `gen_pool` 的调试报告就构成了完整的泄漏处理方案，本备忘录中的任何内容都不是构建协程的前置条件。若采纳 `own`，则先构建 `own`，再在其之上构建协程设计，其中方案 A 作为 R1 中的一行规则，方案 B 作为后续的放宽扩展；若不采纳 `own`，协程按现有文档直接推进即可。以下顺序针对采纳 `own` 的情况。

1. **决定词汇体系，暂不急于实现。** 将以下内容写入语言规范的 TODO 列表：K 中的所有权（如果引入）是对句柄施加的义务，而绝不是对内存的释放机制：`own` 作为类型限定符，采用带 `defer` 认领的线性检查，以池释放和终结器块式移除作为元素消亡的唯一途径，纯数据不设析构器。这只需一段文字的成本，并且遵循了 llm_frontier.md §5.5 的教训——在用户代码中到处充斥 `i64` 句柄之前先做出决定。
2. **先交付 `gen_pool`**，正如 llm_frontier.md §7 第 2 步所述。编写它几乎没有成本，而且能产出本备忘录无法提供的实证：在真实池代码中，泄漏和双重释放的发生频率是否足以值得引入一项检查器特性。
3. **如果确实值得，构建方向 1**：在第 3 节各检查点引入限定符、流状态比特、受信任终点、`take`/`replace`、池操作及带终结器块的数组移除、两行谓词逻辑以及规范章节。基于该机制重写 `26_file_tree` 的 `release` 和 LRU 基准测试的淘汰逻辑作为验收测试，并验证两者的生成 C 代码除了程序显式编写的终结器调用外没有任何变化。无论届时协程是否已定稿，方案 A 的规则都同步写入 R1。
4. **当协程体确实需要在等待点之间持有资源**，且仅受限于方案 A 的字段约束时，再推进**方案 B**：在方向 1 和协程 v1 之上构建 `cancel` 生成器以及 5.4 的规则变更，而绝非取代其中任何一方。coroutines.md §8 第 2 步中的服务器基准测试将是最先体现这种需求的场景。
5. **仿射释放（方向 3）与“释放即收缩”（4.8）**：等待实际需求再行推进，正如 `errdefer` 所采取的策略；对于句柄而言，这两方面的需求实为同一件事（4.9）。

<a id="9-open-questions"></a>
## 9. 开放问题

* **语法拼写。** `own` 作为类型限定符在签名和字段中可读性很好（`entries: own Link[:]`、`fn release(h: own Node&)`）；至于局部变量是需要从生成方推导类型（`let h = p.take(v)`），还是应当为便于阅读而重复标注，仍有待确定。
* **受信任终点（trusted end）。** 是采用仅限标准库使用的内建项、一条 `extern fn` 规则，还是在函数上标注 `trusted` 标记以表明其 `own` 参数在此终结。最后一种方案读起来最自然，也最便于审计（`grep trusted`）。
* **将字段空置作为流分析事实。** 4.6 的终结器完整性检查要求“`it.buf` 在此处为空”这一事实能从块内延续传递到库函数中；流状态为销毁检查维护的按路径索引的事实看起来已经足够，但这是 4.6 中在写入规范之前最需要先行原型验证的部分。
* **带所有权的相对链接**（存储在子元素切片中的 `own Node&<u32 in nodes.items>`）：§5.4 暂缓了对此的支持，本备忘录亦然。父节点的终结器块必须消费每一个链接，这相当于对一段 `own` 值切片进行循环：即把 4.6 的终结器块形式应用到 `free_slice` 上。
* **运行中取消。** 对正在执行的函数体所在的帧调用 `cancel`（通过别名，或在 `defer` 内部调用），属于 coroutines.md §4.10 中的重入情形，是一种会在调试构建中中止程序的逻辑错误；由于帧本身也是一个变量，且 4.8 的规则已在跟踪句柄的借用，因此 `own` 规则能否将其转化为编译期错误（即跨越帧自身的 `resume` 存活的借用）值得进一步研究。
* **对于已完成的 `own` 帧，`result(f)` 意味着什么**：此时帧不再持有任何资源，但其类型仍然是 `own`；`cancel` 虽为空操作却仍被强制要求。已完成的帧是否应当退化为普通类型，取决于 `defer cancel(task)` 这一惯用法在实践中究竟有多繁琐。
* **§5.4 意义上的线性池**（“声明为线性的池会将隐式释放变为错误”）在本设计下不复存在，因为每个池都是线性的；问题转变为是否有池需要方向 3 中的仿射释放。
