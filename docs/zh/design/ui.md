# UI 模块（`ui`）

<!-- Adapted for K. -->

本文档介绍可选的 ui 模块的实现、测试覆盖范围以及剩余工作。关于 API 参考，请参阅 K 的 `docs/stdlib.md`；关于模块源码，请参阅 `ui.k`。

它同时也是 K 的**文本渲染与字体模块**，包括用于原本直接使用 gfx 进行渲染的游戏。关于定位文本与非交互式叠加层，请参阅[文本渲染与游戏 HUD](../stdlib.md#text-rendering-and-game-huds)；游戏无需使用交互式控件即可使用 ui 的字体和文本渲染器。

<a id="what-it-is"></a>
## 它是什么

`import ui;` 为 K 程序提供了单头文件立即模式（immediate-mode）GUI 库 Nuklear：窗口、行与布局空间、分组、树形视图与列表视图；标签、按钮、复选框、单选按钮（option）、可选项（selectable）、滑块、旋钮、进度条、颜色选择器、属性控件、文本输入框与文本编辑器、图表；弹出框（popup）、组合框（combo box）、上下文菜单、工具提示（tooltip）与菜单栏；样式、从 TrueType 文件烘焙而成的字体，以及直接在窗口上绘图。它的构建方式与 `gfx` 和 `physics`（`docs/gfx.md`）相同，只是用 Nuklear 替换了 SDL3：

    K program --extern fn--> k_ui_* (k_ui, native C) --> Nuklear (compiled in)

并通过 gfx 进行绘制：`ui.k` 将一帧转换为三角形并用 gfx 管线绘制它们，同时将 gfx 收集到的输入喂给上下文。

位于其间的封装层 `k_ui`（`src/ui/`）是一次性编译而成的原生 C 静态库：`k` 会为 JIT 运行链接该库，并通过 `tcc_add_symbol` 将其函数交给 TinyCC（`AddUiSymbols`，`src/jit.h`），而由生成的 C 代码构建的程序则链接同一个静态归档库。无论是生成的 C 代码还是 TinyCC，都不会看到 Nuklear 的头文件。

其 API 保持与 Nuklear 一致，仅换用 K 命名——`nk_button_label` 对应 `ui::button_label`——并涵盖了程序会调用的 `nuklear.h` 的几乎全部内容：共 365 个函数。立即模式程序在每一帧声明有哪些窗口和控件，并通过同一批调用得知用户的操作；程序的数据仍归其自身所有，在需要由控件编辑时按引用传入。

<a id="how-it-is-built"></a>
## 它是如何构建的

* **Nuklear** 来自经过 SHA-256 校验的固定版本源码归档。它使用的是 v4.13.3 之后的修订版本，该版本增加了链接控件、延迟显示的工具提示以及属性控件的精度控制；下一个发布版本应当替换掉此固定版本。gfx 包的 CMakeLists（`CMakeLists.txt`；ui 是该包中的一个模块，参见 `docs/gfx.md`）会在 `src/ui/ui_nuklear.c` 中将其实现编译一次，并采用封装层中每个文件包含它时所用的统一配置（`ui_internal.h`）：固定大小类型、默认分配器、带内置字体的字体烘焙、使用 32 位索引的顶点缓冲区输出、每帧 256 字节的键入文本，以及使用 `strtod` 进行数字解析。封装层自身的文件在编译时开启警告，Nuklear 的文件则不开启。
* **AOT 程序的链接输入**：Windows 上为 `build/ui/<config>/link-cc.rsp` 与 `link-msvc.rsp`（其中指定了该静态归档库），在其他系统上则包含 `-lm`。`k --ui-link msvc|cc` 会打印该路径，其查找方式与 `--gfx-link` 相同：先查找 `K_UI_LINK`，其次查找二进制文件旁的 `ui/` 目录，再其次查找构建树（`NativeLinkFile`，`src/utils.h`）。通过 gfx 渲染其 ui 的程序也会一并传入 gfx 的链接文件。

**禁用（Opting out）**：与它所属的 gfx 包（`docs/gfx.md`）一致：不包含 gfx 的 `K_BUILTIN_LIBS` 会将该包排除在编译器之外。UI 程序依然可以通过类型检查并生成相同的 C 代码，而随后运行或构建此类程序时会先构建该包。

<a id="the-compilers-side"></a>
## 编译器侧

* **对封装层的调用**通过其 C 符号的 `k_ui_` 前缀来识别。代码生成阶段会将程序调用的原生封装层记录在一个 `NativeLayers`（`src/utils.h`）中，JIT 运行时会注册这些层的符号（`RunJit`），而不含 ui 层的编译器则会拒绝运行该程序。
* **`thread_fn` 永远无法触及封装层**：封装层的句柄表与错误状态归属于整个进程，且其绘图所依赖的 gfx 仅限主线程使用。

<a id="the-layer-srcui"></a>
## 封装层（`src/ui/`）

`ui_api.h` 集中列出了每一个函数（`K_UI_API`）和每一个常量（`K_UI_CONSTANTS`）；`test/api_check.py` 会检查 `ui.k` 是否恰好声明了这些函数、具有相同的 C 形态、字段顺序一致的结构体以及相同的常量值，与对 gfx 和 physics 所做的检查相同。常量采用 Nuklear 的值，`ui_nuklear.c` 中的静态断言保证每个常量都与之相等。

* **字符串是切片**，从不以 NUL 结尾：在 Nuklear 同时提供接受 C 字符串的 `_label` 函数与接受长度的 `_text` 函数的地方，封装层只保留 `_label` 名称并将长度传递下去。
* **Nuklear 持续指向的内存由封装层持有**：字体的 TrueType 数据与字形范围、行的比例数组（保留至帧末）、光标、分组在结束时写回的滚动偏移量，以及粘贴操作插入的文本。程序从不在一次调用之外出借内存；文本输入框编辑的是副本，之后再写回。
* **句柄（Handle）**：上下文、字体图集、字体和文本编辑器均由槽位索引与代数组成，因此使用已销毁的句柄会报错，而不会崩溃。
* **无回调函数**：过滤器从 Nuklear 的内置集合（`FILTER_*`）中选取，剪贴板由程序交出和取回文本，而 Nuklear 绘制的内容以数组形式返回——既可以是扁平化为每条命令一个结构体的命令列表，也可以是来自其转换器的顶点、索引与绘制调用。
* **样式（Style）** 是一个整体读取与写入的 K 形态结构体，而 Nuklear 原生提供的是指向其 `nk_style` 内部的指针；`push_style` 与 `pop_style` 会保存完整样式。
* **作用域会受到检查。** Nuklear 信任调用方成对地匹配每一次 begin 与 end、仅在已打开且已布局好行的窗口中放置控件，并且不在一个窗口内部再开始另一个窗口；否则它就会越界写入缓冲区或发生除零错误。封装层维护了一个记录当前已开始作用域的栈（窗口、分组、弹出框、组合框、菜单、树形视图、图表、行、禁用区间），并在每次调用时对照该栈进行检查，同时对照帧本身检查每帧的输入：在输入阶段开始窗口属于误用。
* **错误**遵循 gfx 的做法：程序控制之外的失败会返回 false 或零句柄，并将原因记录在 `error()` 中；误用调用会被跳过、在发生时打印出来（前八次）并计数，随后 K 侧会在下一次 `input_begin`、`convert`、`render`、`destroy(context)` 或 `check()` 时携该原因中止。Nuklear 自身的断言也会被路由到同一处理路径中。

* **缩放比例（Scale）** 由封装层自行维护：每个上下文拥有一个缩放比例，表示 ui 布局中每个单位对应的像素数。Nuklear 仍一如既往地按其单位进行布局和绘制；`convert` 会乘以缩放比例来生成顶点与裁剪矩形，而输入函数则会除以缩放比例，同时保留 Nuklear 的整型输入函数原本会丢失的小数部分。只有当字形按该缩放比例烘焙时，文本才会清晰：按某一缩放比例烘焙图集时，会在 Nuklear 光栅化之前先将每个字体的大小乘以该缩放比例，并在之后把字体的高度设回原值；而 Nuklear 会按该高度与烘焙高度之比来缩放字形，从而按原尺寸进行度量，并从更大的字形中绘制。图集保留了其字体的 TrueType 数据（从不调用 Nuklear 的 `nk_font_atlas_cleanup`）以及添加字体时的大小，因此可以以另一个缩放比例重新烘焙：上下文与字体句柄所指向的 Nuklear `nk_font` 保持原地不动，只有它们的字形和图像会发生变化。由 `create` 或 `create_from_*` 创建的上下文各自拥有其图集——Nuklear 的内置字体或某款 TrueType 字体——并在其缩放比例改变时重新烘焙它。
  已销毁或重新烘焙的图集纹理会被列入为其创建该纹理的渲染器名下（`released_textures`），由 `render` 负责释放并上传新图像。
* **输入归属判定**，面向同时拥有自有按键与点击处理的程序：Nuklear 的 `nk_item_is_any_active` 只要鼠标悬停在窗口上就会为 true，而不管此时什么控件正持有键盘焦点。`wants_keyboard` 改为读取帧内各个窗口自身的状态，范围为本帧的窗口：即自上次清除以来开始过的窗口，或在尚未有任何窗口开始之前覆盖全部窗口——因为程序不再开始某个窗口后，该窗口仍会留在 Nuklear 的列表中等待下一次清除。除非窗口处于隐藏、关闭、最小化或只读状态，否则窗口会接收按键，就像 Nuklear 会将位于前景窗口之后以及处于自身弹出框之下的窗口设为不可交互那样；在接收按键的窗口中，处于输入状态的控件属性会接收按键，否则由该窗口编辑状态所标记的文本输入框接收（前提是该窗口上一帧在该位置确实有一个文本输入框——Nuklear 在拖动属性控件时也会设置该标记，而 `edit_focus` 可能会将其指向最后一个输入框之后）。`wants_mouse` 在同一批窗口范围内判定，将按住的鼠标按键归属于按下时的位置：从窗口上开始的拖动即使移出窗口外也仍归 ui 所有，而从窗口外部开始的拖动即使移到窗口上方也仍归程序所有。使用 `NK_WINDOW_NO_INPUT` 开始的窗口或弹出框会让鼠标事件穿透过去。

对于 Nuklear 自身行为失常的地方，封装层会加以规避：

* 向已满的文本输入框键入字符时，光标仍会像字符已输入一样移动；`edit_string` 的过滤器会拒绝放不下的内容，同时将选区或被替换的字符计为可用空间。
* `nk_textedit_paste` 将文本的字节数当作字符数，从而在遇到包含更长多字节字符的文本时会发生越界读取；封装层会像打字一样逐字符粘贴能放下的部分，并作为单次撤销（undo）步骤。
* `nk_edit_buffer` 会读取窗口的编辑模式但从不写回；封装层会像 `nk_edit_string` 那样将其写回，使编辑器的模式按键能跨越当前帧继续生效。
* `nk_to_lower` 在本该做加法的地方做了减法，导致模糊匹配（fuzzy match）只能将大写字母与大写字母配对：封装层会让两侧都以小写形式传入。
* 进度条会按 Nuklear 钳制（clamp）之前的值来计算尺寸；而当最小值与最大值相等时，滑块、旋钮和绘图都会除以空范围。封装层会对前者进行钳制，对后者则予以拒绝或拓宽范围。
* 组合框的条目字符串会按数量读取，当其中包含的条目更少时会越界读取末尾之后的内容；封装层会先统计条目数量。
* `NK_WINDOW_NO_INPUT` 会让窗口中的控件继续响应点击，直到有另一个窗口被放到它前面，之后它才会永久变为只读；封装层在开始此类窗口时直接将其设为只读。

以下特性未暴露，因为它们各自需要回调到 K 代码中、会将程序的内存出借给 Nuklear，或者已有对应的 K 形式：程序自定义的文本过滤器、由回调填充的组合框以及自定义绘制（`nk_push_custom`）；自定义分配器、固定内存与压缩字体；Nuklear 的字符串、缓冲区和绘制列表 API；单独压入单个样式值（样式改为整体传递）；以及 printf 风格的标签与工具提示，这些可用 `str()` 构造。

<a id="the-k-module-uik"></a>
## K 模块（`ui.k`）

命名空间 `ui` 包含：常量、句柄、值与样式结构体、`extern` 声明，以及薄封装函数——用于返回命令、顶点、文本与列表的新数组；将两个结果作为两个返回值（`widget`、`list_view_begin`、`copied`）；基于有限数组（`u8[..k]`）的 `edit_string`；基于字符串数组的组合框；以及样式项、图像和矩形辅助函数。命名避开了 K 关键字，以及模块内部带命名空间声明会遮蔽的全局名称。

通过 gfx 进行绘制对应 `render(context)`，可绘制到屏幕或渲染目标上，并可指定转换设置。它在帧与帧之间保留的状态——管线、采样器，以及按 2 的幂次方增长的顶点与索引缓冲区——是一个全局对象，在首次使用时创建，并在 `gfx::open_count()` 表明 gfx 自上次以来经历过关闭并重新打开时重新创建（此时也会忘记各图集的纹理，以便重新上传）。`input_from_gfx(context)` 将 gfx 上一帧的事件按顺序转换为 Nuklear 的输入：鼠标、按扫描码（scancode）名称识别的编辑按键、按按键配合 Ctrl 或 Command 键入的字符识别的快捷键、键入文本（同时开启 gfx 的文本输入）、帧持续时间，以及双向剪贴板同步。

gfx 为此新增了所需的全部能力，且每一项均在 `test/gfx/gfx_events.k` 中单独经过测试：`events()`（按顺序记录上一帧的输入，附带修饰键状态与键入字符）、`text_input`、`inject_text`、`scancode` 与 `key_name`、`clipboard` 与 `set_clipboard`（无头模式下为 gfx 自带剪贴板，避免测试干扰系统剪贴板）、`open_count`，以及 X1 和 X2 鼠标按键。

<a id="testing"></a>
## 测试

* **`test/ui/`** 位于常规测试套件中：在编译器包含该封装层时，以 AOT（-O0 和 -O2）以及通过 TinyCC 运行；不包含时则仅进行类型检查并转换为 C 代码。大多数测试使用自构造的输入驱动上下文，并在无头且不依赖 gfx 的情况下检查返回值与绘制结果：`ui_fonts`（图集、在 1 和 2 倍缩放下烘焙、TrueType 文件、字形范围、字体合并、度量信息、已释放纹理、自带 TrueType 字体的上下文）、`ui_windows`（窗口状态与几何信息、每一种行布局、分组、树形视图、列表视图）、`ui_widgets`、`ui_popups`（弹出框、组合框、上下文菜单、工具提示、菜单）、`ui_edit`（过滤器、文本编辑器的各项操作、基于缓冲区与有限数组的输入框、标志位、已满输入框、编辑器的模式、按键与剪贴板）、`ui_style`（完整样式、压入、重置及从表加载、字体、光标、颜色、辅助函数）、`ui_draw`（每一种画布命令、转换、输入查询、带缩放的 ui）以及 `ui_charts`。`ui_render` 通过无头 gfx 进行绘制，并从注入的 gfx 输入中驱动上下文：点击、打字、编辑按键、快捷键与剪贴板；它会回读屏幕和渲染目标，在两倍缩放下绘制和点击，并在 gfx 关闭后重新打开再次运行。`ui_wants_input` 以同样方式驱动窗口、弹出框和属性控件，并在每一步查询 `wants_keyboard` 和 `wants_mouse`，打印键入文本的落点。这些测试调用了封装层全部 365 个函数中的 365 个。`ui_misuse` 检查在任何窗口之外放置控件会在下一帧携原因中止程序，`ui_misuse_messages` 展示封装层针对 58 种误用所报告的信息（每种均被安全跳过），而 `ui_err_thread` 则检查在 `thread_fn` 中触及 ui 会产生编译错误。
* **`samples/29_ui_todo.k`** 是一个待办事项列表与混色器示例，在示例运行器中以无头模式在 JIT 与 AOT 下运行 30 帧。

Nuklear 的布局和绘制采用纯浮点运算，在所有平台上结果一致，因此测试直接按原样打印坐标与颜色。

<a id="follow-up-work"></a>
## 后续工作

* 将固定提交（pinned commit）替换为 Nuklear 的下一个发布版本。
* 在 `edit_string` 输入框中支持撤销：Nuklear 会在每次调用时清空它们共用的编辑器，因此目前只有 `edit_buffer` 的文本编辑器保留历史记录。
* 自定义文本过滤器以及由程序度量的字体，这需要一种从 C 调用 K 函数的机制。
* 在 gfx 中支持鼠标滚轮和双击注入，用于测试 `input_from_gfx` 的其余部分。
* 正在被键入的属性控件会标记其所在窗口的文本输入框焦点（`edit.active`），但不会指明具体是哪一个输入框（`edit.name`），从而导致该窗口中上次聚焦的输入框——若此前没有聚焦过，则是窗口的第一个输入框——会接收键入的文本，而属性控件则会提交其旧值；此外，当窗口中位于其后的某个属性控件正在被键入时点击一个文本输入框，在该属性控件结束编辑后会再次失去焦点。封装层可以在属性控件持有焦点期间将该标记指向不存在的输入框，并将原本取得过焦点的输入框还原回来。
