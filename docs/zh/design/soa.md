本提案新增了列数组（column array）。`T[||..]` 会把一个结构体元素按每个叶子字段各存为一个数组，每个数组位于各自的数据栈上，并共享同一个长度。元素既可以作为普通结构体复制出来，也可以通过字段路径进行写入。排序、切片、序列化以及按引用传递元素都需要将数据复制到普通存储中。该特性尚未实现。

```klang
import std;
import vec;

struct Particle { pos: float3, vel: float3, age: i32 }   // 七个列

fn spawn(ps: Particle[||..]&, n: i64) {
    for i in n {
        let x = i as f32;
        ps.push(Particle { pos: float3 { x, 1.0, 0.0 },
                           vel: float3 { 0.0, i % 4, 1.0 }, age: 0 });
    }
}

fn step(ps: Particle[||..]&, g: float3) {
    for i in ps.len {
        ps[i].vel = ps[i].vel + g;          // 读入三列，写出三列
        ps[i].pos = ps[i].pos + ps[i].vel;
        ps[i].age++;                        // 一列
    }
    var i = 0;
    while i < ps.len {
        if ps[i].pos.y < 0.0 {
            ps[i] = ps[ps.len - 1];         // 交换移除：整个元素
            ps.pop();
        } else {
            i++;
        }
    }
}

fn main() {
    var ps: Particle[||..] = [];
    spawn(ps, 1000);
    for s in 8 { step(ps, float3 { 0.0, -0.5, 0.0 }); }
    var highest = ps[0];                    // 提升后的值：一个普通的 Particle
    for p in ps { if p.pos.y > highest.pos.y { highest = p; } }
    print(ps.len, " ", highest);
    var sorted: Particle[>..] = [];
    sorted.append(ps);                      // 将整个数组提升后用于排序
    sort(sorted) { a, b => a.pos.y > b.pos.y };
}
```

如果把 `[||..]` 替换成 `[>..<]`，这段程序在今天就能够编译并运行。列数组会改变元素存储的位置以及允许对它们执行哪些其他操作，但绝不会改变程序的语义。

<a id="why-a-new-array-kind"></a>
## 为什么需要新的数组类型

目前，这种布局需要手动编写，每个叶子字段对应一个数组：

```klang
var px: f32[>..] = []; var py: f32[>..] = []; var pz: f32[>..] = [];
var vx: f32[>..] = []; var vy: f32[>..] = []; var vz: f32[>..] = [];
var age: i32[>..] = [];
```

这会导致每个元素需要七次 push，每个辅助函数需要七个参数。程序员必须自己保持这七个长度相等。结构体无法把这些数组打包到一起，因为它最多只能持有一个可调整大小的字段（§3.4）。这种布局还有性能代价：这些数组中的每一个都从各自栈的相同页偏移处开始，由于 4K 别名冲突（4K aliasing），这使得粒子核（particles kernel）的六数组版本慢了 2 倍（见下文实测数据）。同时，没有任何信息告诉编译器这些数组是并行的。

完整版数组结构体（struct-of-arrays）特性的估算规模约为 2,300 行，其中 90% 在代码生成中。该设计允许普通函数通过代理（proxy）接收元素引用和切片；它还会按特化版本选择布局，并将数组返回到列目标中。大部分代码都用于支持在为普通数组编写的函数中使用元素或切片。

本提案提出的列数组避免了这一要求。它是一种独立的数组类型，没有隐式转换，也不存在指向其元素的引用、切片或视图。其实现只需要存储处理和少量数组成员，规模约为完整设计估算体积的三分之一。

<a id="rules"></a>
## 规则

**类型。** `T[||..]` 是可调整大小的（§1.1），并且像 `T[>..<]` 一样既能增长也能收缩：`||` 表示列，`..` 表示可变长度。

**元素。** `T` 必须是固定大小且扁平的（§1.1：任意深度下都没有引用、切片或相对引用）。类型为结构体的字段会被递归拆分为其子字段。其他任何字段都是一列：标量、`bool`、固定数组、静态容量受限数组（即 `u8[..16]` 这种形式），或固定模式枚举（fixed-mode enum）。`pad` 字段没有列。非结构体的 `T` 是一列，因此泛型代码可以为任意固定、扁平的 `T` 编写 `T[||..]`。

**存放位置。** 列数组是局部或全局的 `var` 或 `let`，通过 `[]` 或数组字面量初始化。它永远不能作为结构体字段、数组元素、ADT 载荷、按值传递的参数、返回值、线程参数、队列值，或线程程序使用的全局变量。函数通过引用接收它：通过 `T[||..]&` 参数，或通过无类型参数（无类型参数会按引用绑定数组，§4.1）。指向整个数组的引用遵守常规规则，是一种普通引用。

**元素访问使用路径。** `ps[i]` 后跟任意字段访问步骤和固定数组索引步骤（`ps[i]`、`ps[i].pos`、`ps[i].pos.y`）构成一个*元素路径（element path）*。路径可以：

* 作为值读取（`let p = ps[i]`、`ps[i].pos + d`、传入按值参数的 `f(ps[i])`、`print(ps[i].vel)`）：即一次复制，从路径所跨越的各列中加载；
* 被写入（`ps[i] = p`、`ps[i].pos = v`、`ps[i].pos.y = 0.0`），对数值叶子字段支持复合赋值和 `++`/`--`。

任何东西都不能引用路径。以下写法均为编译错误，且每条报错都会指向复制出来使用和路径形式：

* `&ps[i]`；
* `var r .= ps[i]`；
* 将路径传递给期望引用的位置（`fn f(p: Particle&)`）；
* 切片（`ps[a..b]`，或对固定数组叶子字段取切片）；
* 对叶子数组执行 `for` 循环；
* `for &p in ps`。

无论路径触及多少列，它都只对照共享长度检查一次索引，且边界检查消除 pass 会像对待其他数组一样消除该检查。

**成员。**

| 成员 | 含义 |
|---|---|
| `.len -> i64` | 元素个数 |
| `.push(v)` | 追加一个元素；无返回值（其索引为 `len - 1`） |
| `.pop() -> T` | 移除最后一个元素并按值返回 |
| `.resize(n, v)`, `.resize(n)`, `.clear()` | 与 `T[>..<]` 上相同 |
| `.append(src)` | 追加 `src` 中的所有元素：任意 `T` 的数组或切片（包括函数调用返回的数组结果），或另一个 `T[||..]` |

普通的 `T` 可增长数组也在其自身的 `append` 中接受列数组（即上文中的 `sorted.append(ps)`）：这就是整数组提升（whole-array lift）。`for p in ps` 和 `for p, i in ps` 按值迭代（§6.5），像其他数组一样重新读取长度。`print`、`str` 和 `format` 渲染列数组的方式与渲染 `T[>..<]` 相同。

**收缩。** `pop`、`resize` 和 `clear` 在所有允许可增缩数组执行收缩的位置都合法：局部变量上、通过引用、全局变量上（§5.2）。针对唯一仍可能涉及列数组的情况，保留了 §5.2 检查：同一语句中先前持有的同一数组的元素路径。因此，`ps[i] = ps.pop()` 会像今天在 `T[>..<]` 上一样被拒绝，处于同一位置且会收缩 `ps` 的调用也是如此。引用和切片变量的扫描则会跳过，因为没有任何引用或切片可以指向列数组内部。

**v1 中不支持。** `==`、`copy(ps)`、整体赋值、`index_of`、切片与视图、`to_bytes`、`bytes_of` 与 `from_bytes`、`reusable`、指向其元素的 `in pool` 引用，以及所有接受 `T[:]` 的函数（`sort`、`find`、`filter` 及 `std` 中的其他切片函数）均属于编译错误。要使用这些操作，需通过 `xs.append(ps)` 将元素复制到普通数组中，并在需要时通过 `ps.clear(); ps.append(xs)` 复制回来。

<a id="what-the-checker-does-not-need"></a>
## 检查器不需要做什么

检查器的大部分机制都是围绕引用设计的，而没有任何东西会引用列数组内部：

* **根与生命周期**（§9.2）。列数组永远只能作为指向整个数组的引用的根，而任何收缩都不会使该引用失效。其元素不持有引用，永远不是回读（read-back）候选者，也永远不是相对引用的目标，因此回读根、持有者以及收缩时的活跃性扫描永远不会涉及它们。
* **构造期间的增长**（§4.2）。被 push 的元素是固定大小的且不持有相对引用，因此它会在槽位被占用之前完成求值；对调用结果执行 `append` 时也会先构建该结果。表达式运行期间，绝不会有列数组处于构造中的状态。
* **边界检查消除**（§10.5）。列数组是一个具有单一长度的位置（place），改变该长度的操作与 `T[>..<]` 完全相同。

<a id="representation"></a>
## 表示方式

* **头部（Header）**存放在所属栈帧或程序实例的全局变量中：每列一个带类型指针加上长度计数，即 `{ float *pos_x; ... int32_t *age; int64_t len; }`。`T[||..]&` 就是指向该头部的普通指针。
* **列（Columns）**各自占用一个数据栈：局部变量从其所在函数的栈块中取 N 个栈索引（§10.3），全局变量则各自占用 N 个预留空间。第 k 列的第一个元素位于其自身的页偏移处，即越过页边界后的 k × 4096 / N 处，因此并行各列在相同索引处的低 12 位地址永远不会重合。每列至多消耗一页地址空间。
* **从不使用栈顶。** 在数组的整个生命周期内，列是其所在栈上唯一的值，且其元素大小固定，因此下一个槽位始终是 `base + len * size`。push 写入 N 个叶子字段并递增 `len`；pop、resize 和 clear 仅更新 `len`（resize 还会填充元素）。栈的 `top` 仅在声明时读取一次，从不写入。因此，列数组完全不需要 implementation.md §6.10 中的栈顶缓存与同步，不需要水位线（watermark）恢复，也不需要在引用中携带栈身份信息：通过 `T[||..]&` 执行 push 只需要头部即可。
* **元素路径**是一种新的代码生成位置（location）：包含头部、保存在临时变量中的已检查索引，以及该路径跨越的列范围。字段步进会收窄该范围，而到达叶子字段的路径就是普通的 C 左值（`ps.pos_y[ix]`），因此复合赋值、`++`、对枚举叶子字段做 `match` 以及对固定数组叶子字段取索引都无需新增任何机制。跨越多列的路径有两个消费者：加载（load）将多列汇聚（gather）为一个 C 值，存储（store）将一个 C 值分散（scatter）写入各列。同一数组路径之间的逐元素运算会通过带有列映射成员的 `GenElemwiseInto`，因此 `ps[i].pos = ps[i].pos + ps[i].vel` 会像今天的数组结构体形式一样，直接编译为逐列加载和存储，而不会产生汇聚后的临时变量。
* **循环。** 列指针在数组存活期间永远不会改变（增长从不搬迁数据，且没有整体赋值），因此循环只需将每个列指针读取到局部变量一次。当循环仅通过这些局部指针访问该数组时，它们会被声明为 `restrict`。这在循环不包含会触及该数组的增长、收缩或调用（即 `hoistrefs` 条件，implementation.md §5.10），且不存在可能指向同一数组的第二个列数组时成立。

<a id="implementation"></a>
## 实现

以下估算较为粗略（±30%）。它们来自对完整设计工作量清单减去列数组所不包含部分的统计。

* **解析器、AST、转储**（约 10 行）：在类型后缀循环中解析 `[` `||` `..` `]`（`||` 在词法分析中已作为 `T_OROR`），新增 `A_COLS` 数组种类，以及 `--dump` 的打印输出。
* **检查器**（约 150–200 行）：
  * `ValidateType`：元素固定大小且扁平，且该类型仅作为变量类型或引用所指类型出现。`ClassOf` 将其归为可调整大小类型。`CanContain` 将其排除，使其永远不会成为回读候选者。
  * `CheckLValue`：在 `LVal` 上新增元素路径标志位，在索引步进处设置，并在字段和固定数组索引步进中保持。`CheckRefOf`、`AutoRef`/`BindsRef`、`.=` 声明与重绑定、切片以及对路径的 `for` 循环均会拒绝它，并通过同一条诊断信息指出复制出来使用和路径形式。
  * 内建成员：在 `len`、`push`（无返回值）、`pop`、`resize`、`clear` 和 `append`（及其三种源形式）上添加 `BR_COLS` 接收者标志位，外加普通数组 `append` 的列数组源支持。收缩操作进入 `ShrinkGrowShrink` 并关闭变量扫描。拒绝 `for &`，允许渲染输出。
  * 调用：`A_COLS` 不进行数组到切片的隐式转换，无论是在重载层级还是在 `BindTypes` 中均如此。线程参数、队列、线程程序全局变量以及 `extern fn` 均拒绝该类型。
  * BCE 与优化器：仅需更新其中关于数组种类的 switch 分支。
* **代码生成**（约 550–700 行）：
  * `codegen_types.h`：头部 typedef，以及按元素类型索引的叶子表，给出每列的 C 类型、大小和索引，以及每个结构体字段的列范围。
  * `codegen_values.h`：用于头部的 `VarLoc`/`DerefLoc`、返回元素路径的 `IndexLoc` 分支、收窄路径的 `FieldLocAt`、`LoadLoc` 中的汇聚逻辑、分散写入辅助函数，以及支持列映射的 `GenElemwiseInto`。
  * `codegen_nodes.h`、`codegen_stmts.h`：`Assign::CgStmt` 中的分散写入；`ForLoop::CgStmt` 中带有提升且标记 `restrict` 的列指针的按值绑定；`BindLocal` 获取 N 个栈索引并放置各列。
  * `codegen_builtins.h`：各内建成员。`append` 对应三种源：数组视图、构建在临时栈上的调用结果，以及另一个列数组。同时也涵盖普通数组追加列数组。
  * `codegen_emit.h`、`codegen_render.h`、`codegen_frames.h`：全局变量、打印渲染以及普通指针参数。
* **测试**（约 350 行）：
  * 一个运行时测试夹具，在局部变量、通过引用、全局变量以及泛型函数内部覆盖每一种成员和路径形式，并在其循环上标注 `// bce:`；
  * 一项检查，验证通过引用执行的 push 与函数调用交错时各列仍保持对齐；
  * 为每种被拒绝的用法编写 `test/errors_tc/` 测试夹具。
* **文档**：§3.3 表格新增一行、§5.3 之后新增一个小节、§12 成员表格、教程中的一段说明，以及 implementation.md §6.1 中的一个条目。

编译器代码总计大约 750–900 行：与 `to_bytes` 和 `from_bytes` 的规模相当（`src/` 中 +779 行），约为完整设计的三分之一。

<a id="measurements"></a>
## 实测数据

`bench/klang/particles_scalar.k` 的手写六数组版本代表 K 当前提供的布局方式，此处将其与原始数组结构体（array-of-structs）版本进行对比。N = 4,000,000，在 Ryzen 9 9950X3D 上取五次中的最佳结果。校验和完全一致，多次测试之间的波动最高达 8%。

| ms | MSVC 19.51 /O2 | clang 20 -O2 | clang 20 -O2 -march=native |
|---|---:|---:|---:|
| 数组结构体（`particles_scalar.k`） | 1039 | 956 | 1375 |
| 六个 `f32[>..]` 数组（当前生成方式） | 2015 | 1968 | 674 |
| 相同 C 代码，各列起始地址间隔 688 字节 | 1101 | 1063 | 691 |

* **默认目标下 2 倍的差距源于 4K 别名冲突。** 每个数组都从新栈的偏移 0 处开始，因此 `px[i]` 和 `vx[i]` 共享低 12 位地址。每次存储后的加载都会使 CPU 误判为存在存储到加载前递（store-to-load forward），而实际上并不存在。把起始地址错开即可消除该别名冲突。
* **错开摆放后，列布局在默认目标下与数组结构体相差在 6–11% 以内。** 该循环每次迭代都会访问所有字段且存在分支，这正是数组结构体布局最有利的场景；在 clang 的默认目标下它不会向量化：关闭向量化没有任何变化。
* **开启 `-march=native`（AVX-512）后，列布局能够向量化**：691 ms，对比关闭向量化时的 1033 ms。数组结构体在该选项下反而变慢（1375 ms，对比关闭向量化时的 917 ms），因此合理的加速比约为 1.3 倍。
* **MSVC 下逐元素循环还需要 `restrict`。** `particles.k` 中逐元素循环的六列降级版本在循环内部读取全局变量 `G`，若没有 `restrict`，C 编译器必须假定任何 float 写入都可能改变 `G`。该版本原样运行耗时 3317 ms，错开偏移后为 1623 ms，加上 `restrict` 为 1295 ms，两者同时使用为 1005 ms，对比数组结构体为 1182 ms。

任何由编译器控制的列布局都应当内置这种错开偏移。至于普通数据栈是否也应当以错开偏移起步，则是一个独立的问题，因为同一个循环读写的互不相关的数组在今天同样会遇到相同的别名冲突。

<a id="possible-extensions-ordered-by-expected-benefit"></a>
## 可能的扩展（按预期收益排序）

| 扩展 | 新增能力 | 粗略成本 |
|---|---|---|
| 将 `for &p in ps` 作为位置别名 | `p` 在路径中代表 `ps[i]`，仍然没有内存地址；计算核写起来就像数组结构体版本一样 | 约 100 行 |
| 列视图 | 单列上的真正切片（例如用某种语法把 `ps.pos.x` 写作 `f32[:]`），用于 FFI 和 `std` 计算核，与 §5.2 的切片一样只能由变量持有，这会重新引入收缩时的变量扫描 | 约 150 |
| `==`、`copy`、整体赋值 | 逐列比较与逐列复制 | 约 60 |
| 引用与 `in pool` 叶子字段 | 持有链接的元素，像任意数组的元素字段一样接受检查 | 可能很小 |
| 结构体尾部 | 以列头部作为尾部的栈帧对象（C.2） | 约 200 |
| 线程、队列、`to_bytes` | 按数组结构体顺序排列的映像（image），因为映像不携带布局信息 | 约 100 |
| 返回值与按值传递参数 | N 个目标栈与放置在列中的命名返回值（§7.3）；占完整设计成本的大部分 | 数百行 |

<a id="open-questions"></a>
## 开放问题

1. **语法。** `T[||..]` 读起来是带有可变长度的列。`T[>..||]` 则会保留该家族表示栈增长的 `>`。
2. **`push` 的返回值。** `push` 是否应当返回新元素的索引，对应其他数组返回的引用？
3. **拆分深度。** 是仅拆分结构体字段，还是连同固定数组一起拆分（将 `f32[4]` 叶子字段拆为四列）？
4. **`append(f())`。** 它先在临时栈上构建结果，再将其拆分写入各列。对照 §4.3 来看这是否可接受？静态容量受限数组目前已经以这种方式接收函数调用返回的数组结果（implementation.md §6.5）。另一种方案是让 `append` 只接收已存储的源。
5. **位置别名。** `for &p in ps` 是否应当纳入 v1？正是它让计算核的代码读起来和数组结构体版本一样。
