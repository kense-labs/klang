# 嵌套增长：以 JSON 为例的就地构建树结构

研究笔记，2026 年 10 月。本文所述内容均尚未实现。核心问题在于：怎样才能写出下面这段代码，

```klang
struct Member { key: u8[varint], val: Json.. }
enum Json {
    Null,
    Bool { v: bool },
    Num { v: f64 },
    Str { s: u8[varint] },
    Arr { children: Json..[>..] },
    Obj { members: Member..[>..] },
}

var doc: Json.. = Json.Obj { members: [] };
```

随后不仅能向根对象添加值，还能向任意深度的容器添加值。目前有两道障碍：一是该类型会被拒绝（类型不能按值包含自身，且数组元素不能是可调整大小的），二是无法指明一个可增长值中究竟哪一部分是当前正在增长的部分。本笔记记录了当前规则的具体规定、所需机制中哪些已经存在、针对这两个问题的可选方案，以及最终建议。

## 1. 分叉点：深度优先构建还是随机修改

在紧凑布局（packed layout）中，一棵树的字节序就是它的深度优先遍历序：先是容器本身，接着是它的第一个子节点及其内部的所有内容，然后是第二个子节点，依此类推。当这样一棵树正在被构建时，只有一个位置可以无需移动任何数据而直接追加字节：那就是末尾。仍然能够接收子节点的容器，恰恰是从根到末尾这条路径上的那些容器，而且它们全都结束于同一个字节位置。对其中任何一个容器进行增长，本质上都是同一次指针前移（pointer bump）。

这其实就是换个角度看待“每个栈至多一个可调整大小的值”这一不变量（规范 §1.3）。这个不变量不必表述为“每个栈一个可调整大小的值”；它可以表述为“每个栈一条*开放路径（open path）*”，即一条值的链条，链条中每个值都是前一个值里的最后一项，而链条的最后一项位于栈顶。没有任何数据需要移动，不需要检查容量，也不需要维护额外簿记。因此，“哪个子部分是开放的”有一个标准答案：路径上最内层的容器，且仅此一个。它的祖先节点对增长而言处于锁定状态——这已经是“处于构造中的值”的现有规则（§1.3(4)、§4.2）——但它们仍然保持可读，因为容器的计数仅在子节点构造完成时才会增加。

这种模型永远无法做到向不在该路径上的容器添加内容：例如更早的兄弟节点，或者树构建完成之后的任何节点。要做到这一点，要么需要间接寻址（通过引用链接的节点，这正是当前 `json::Node` 的做法），要么需要移动内存，而这是语言所禁止的。因此，第一个设计决策在于该特性究竟服务于以下两种场景中的哪一种：

* **深度优先构建**：解析器、反序列化器、构建器、序列化器，以及任何按遍历顺序生成树结构的场景。其结果是一个连续的扁平值（flat value）：由于没有链接，它可以按原样通过 `to_bytes` 序列化，并直接发送给工作线程（worker），因为它是扁平的。第 3 节以及第 4.1 至 4.3 节、第 4.6 节讨论的都是此类场景。
* **随机修改**：一种可编辑的文档模型，在某个成员的兄弟节点添加完成很久之后，仍可以向该对象添加新成员。这对应于链接节点池（第 4.4 节），目前已经存在。

JSON 的解析与写出属于第一种场景。文首的声明本质上是一条*磁带（tape）*，本笔记的其余部分都将按此视角来探讨。

## 2. 编译器当前的表现

以下是对当前编译器的探测结果，以便后文中的提案能够准确指出它们所要修改的具体规则：

| 程序 | 结果 |
|---|---|
| 上述枚举，或者将子节点改为冻结的 `Json..[]` 的同一枚举 | `enum Json contains itself by value`。该禁令覆盖通过任何数组进行的递归，无论其类别如何。 |
| `struct Inner { n: i64, xs: i64[>..] }` 作为 `Inner[>..]` 的元素 | `array elements may not be resizable`（§3.4）。 |
| `enum Log { Empty, Lines { items: i64[>..] } }` 作为局部变量，用 `Lines &x` 匹配 | `binding a resizable ADT payload is not supported by the C backend yet`。可调整大小的 ADT 是存在的（§3.5），但其载荷（payload）无法通过引用访问；§8.1 仅允许按值绑定，因为整体赋值可能会替换掉整个变体。 |
| `outer() -> i64[][>..]` 在循环中推入 `inner() -> i64[>..]`，而前者又被推入 `i64[][][>..]` | 可以编译运行。每一层都是一个命名结果（§7.3），直接构建在其父级数组的顶部；三层共用同一个栈。 |
| `recursive fn nest(d) -> u8[>..]`，其函数体先 push、再追加 `nest(d - 1)`、再 push，最后返回其局部变量 | `calls into its recursive cycle while non-fixed-size local out is in scope (§7.8)`。 |
| 在环内执行 `words.push(nest(words, d - 1))`，其中 `words: u8[][>..]&` 归属在环外 | `the element pushed into words is still under construction, and the growth would land inside it (§1.3)`。检查器已经通过增长日志（`src/typecheck_builtins.h` 中的 `CheckGrowsSince`）强制执行了祖先锁定。 |

可见，在单一栈上进行固定层数深度优先构建的基础设施已经存在：就地结果构造、将命名结果直接放置到 push 槽位中，以及“处于构造中”的锁定机制。目前缺失的是：递归类型本身、递归*函数*（目前其命名结果被算作独立占用一个栈），以及一种让容器在跨越多个语句期间保持开放状态的方法。

<a id="3-the-type-relaxations"></a>
## 3. 类型放宽

<a id="31-r1-recursion-through-an-array"></a>
### 3.1 R1：通过数组进行递归

**规则。** 一个类型只有当自身处于长度不是正常量的数组内部时，才可以按值包含自身：`T[]`、`T[uN]`、`T[varint]`、`T[>..]`。空数组充当基础情形（base case），正如今天的 `null` 之于 `List?`。直接字段、载荷字段以及 `k > 0` 的 `T[k]` 仍然报错。`T[>..<]`、`T[..k]` 和 `T[..]` 都要求定长元素，而递归类型永远不可能是定长的，因此它们本来就被排除在外。

通过结构体和枚举形成的互递归（`Json` 包含 `Member[>..]`，`Member` 包含 `Json..`）遵循同一规则：按值包含关系图中的每一个环都必须经过这样的数组。检查是在类型实例图上进行的，因此包含 `Tree<T>[]` 的泛型 `Tree<T>` 是合法的，而包含 `Tree<Pair<T>>[]` 的非正则（non-regular）`Tree<T>` 会无限实例化下去；现有的“进行中实例化数量上限”（§7.8，多态递归）会拒绝它并给出实例化链条。

**推论与影响。**

* 此类类型至多属于可变类（variable-class），因此其数组是顺序数组：只能迭代，不能随机索引。JSON 数组通过遍历访问，就像现在的 `json::each` 那样。
* 编译器为每个类型通过遍历字段生成的所有辅助例程（求大小、判等、`print`/`format`、`copy`、`from_bytes` 校验器）都将变成递归的 C 函数，而不再是展开的表达式——但**仅针对真正处于递归中的类型，不涉及其他类型**。按值包含关系图给出了精确判定：当且仅当一个类型位于该图的某个环上（即非平凡强连通分量）时，它才是递归的，也只有这些类型会生成递归遍历器（walker）。仅仅包含了一个递归类型的类型（如 `struct Doc { name: u8[], root: Json.. }`）仍保留其展开式遍历器，并在对应字段处调用 `Json` 的遍历器。编译器当前已支持的所有类型都不在任何环上，因此其编译方式与现在完全相同。检查器的延迟类型解析机制（`src/typecheck_types.h` 中的 `typesbuilding`、`laterpointees`）已经能够处理通过引用构成的环，只需放行按值构成的环即可。
* 这些遍历器会在原生调用栈上递归至数据的深度。恶意文档可能嵌套百万层深，此时 `print(doc)` 就会导致原生栈溢出。所有 JSON 库都为此设置了深度上限（`serde_json` 默认 128 层，`simdjson` 默认 1024 层）；解析器应强制执行这一深度上限，而生成的遍历器则从数据本身继承该深度保证。这与如今手写一个遍历 `json::Node` 的 `recursive fn` 所面临的风险完全相同，只是转移到了生成代码中。
* 在 `match` 分支中按值绑定此类载荷会带来 O(size) 的拷贝，这与任何可变类载荷一样。若要在不拷贝的情况下读取磁带，就需要 `&` 绑定器，进而需要变量模式（variable mode），也就触发了第 2 节指出的后端缺口。

**优点。** 独立于其他所有特性；本身即可用于支持通过返回值构建的冻结树（如 `let doc: Json.. = parse(text)`，由 `parse` 就地构建其结果）。消除了比底层表示实际需要更严格的限制。树成为扁平值：无需等待 TODO 9 的放宽即可直接序列化和发送。

**缺点。** 需要生成递归遍历器以及应对上述深度风险；仅支持顺序访问；`&` 绑定的后端缺口变为关键阻塞项。

<a id="32-r2-resizable-elements-growable-while-open"></a>
### 3.2 R2：可调整大小的元素，在开放期间可增长

嵌套 `children` 在静止状态（at-rest）下的表示是一个计数加上所有子元素的字节——无论该字段写作 `Json..[]` 还是 `Json..[>..]`，字节内容完全相同。两种写法的区别在于该字段是否允许增长，以及在当前实现中计数的存放位置（`T[>..]` 将其头部存放在宿主栈帧中，见附录 C.2；`T[]` 将其存放在元素之前）。该字段有两种写法：

**(a) 静止态写作 `Json..[]`；开放状态赋予增长能力。** 不改变任何放置规则。容器本身是一个冻结的可变类值，而第 4 节的机制允许它在处于构造期间被 push，这与如今对可变元素执行 push 在单个表达式持续时间内所做的事情一致。代价体现在根节点上：`var doc: Json.. = Json.Obj { members: [] }` 是一个可变类局部变量，在初始化表达式结束后即被冻结，因此根本无法让*它*保持开放，除非让整个程序的根变成一个带有 `[>..]` 载荷的可调整大小 ADT——而这又无法与内部字段使用同一类型定义。在 (a) 方案下，树只能由函数返回值（`let doc = parse(text)`）或构建器代码块构造出来，而永远无法从局部声明开始逐步增长。这只覆盖了解析器场景，别无他用。

**(b) 直接写作 `Json..[>..]`；仅当处于开放路径上时才可增长。** 放宽 §3.4：可调整大小的值可以作为顺序数组的元素。该数组本身也属于可调整大小类，且该元素只有在其作为最内层开放值时才可增长（第 4 节）。在所有其他位置，它都按其实际对应的冻结数组来读取。对 `[>..]` 的语义解读保持与它如今位于结构体尾部时一致：*通过其宿主来增长，且仅当其宿主正在增长时*。尾部字段总是其所在结构体的最后一项，因此只要结构体可增长，尾部就可增长；而数组元素只有当它是最后一个元素时才是最后一项，这条规则正是对这一事实的精确刻画。表示方式上：元素的计数位于磁带内部（一个 `u32`），根的计数则留在可调整大小 ADT 当前保存它的位置，或者也放在磁带内部以便遍历器只面对同一种形状。`[>..<]` 在此处绝不允许使用，因为顺序数组无法弹出元素（pop）。

类别系统需要为 (b) 做一项细化：处于可调整大小类的*元素*，在放置规则上仍算作可调整大小（只能位于顺序数组中或结构体尾部），而在所有以“此处是否可增长”为判断依据的规则上——除了通过开放路径进行增长之外——都算作可变类。需要审计的规则包括：放置（placement）、`copy`、整体赋值（§4.4，仍仅限根节点）、缩容接收者（§5.1：元素绝不会是缩容接收者）、栈帧对象（C.2：元素绝不会是栈帧对象）以及假定每个类型至多一个可调整字段的 `SoleResizableIn`。

**(b) 的优点。** 声明直接表达了该类型的用途。每一层都使用同一套写法；根节点就是一个普通的可调整大小 ADT 局部变量，可以从声明处开始直接就地增长。**缺点。** 类型声明写着可调整大小，但在绝大多数实例中其实是冻结的；每一条按类别区分的规则都需要加上针对元素的细化。(a) 则是如果审计发现牵涉过多时的保守退路。

**哪种方案副作用更小。** (a) 触及的规则更少，但它留下了一个连第 4.6 节的追加句柄也无法填补的缺口：如果 `var doc: Json..` 内部的数组全是 `[]`，它就是一个可变类局部变量，而可变类局部变量一旦构建完成，就可能被同一栈上后续分配的数据掩埋（§1.3(4)），因此此后无论有没有句柄都再也无法增长。要从声明开始就地增长，就要求根节点拥有其所在栈的栈顶，这意味着它必须是可调整大小类，也就意味着声明里必须写 `[>..]`，即必须选 (b)。对 (b) 的规则审计最终归结为一条谓词：**处于元素位置的 `[>..]`，在除了允许它增长的那两条规则之外的所有规则眼中，都等同于 `[]`**——这两条规则分别是第 4.6 节的通过引用执行的带检查 push，以及第 4.1 节的在开放路径上静态证明安全的 push。放置、拷贝、整体赋值、缩容接收者、栈帧对象以及 `SoleResizableIn` 全部采用 `[]` 的答案即可。

凡是需要随着子节点关闭而就地回填的计数都必须是定宽的。`Json..[varint]` 容器虽然可以在单个表达式内构建出来（表达式结束时其长度已知，适用 §4.3 的重定位例外），但永远无法跨越多个语句保持开放，除非关闭它时允许移动容器的字节——而这会导致指向已关闭子节点的引用全部失效。对于任何可开放的容器，采用定宽计数是最简单的规则。

<a id="4-who-decides-which-part-is-open"></a>
## 4. 由谁决定哪一部分处于开放状态

<a id="41-option-a-the-construction-order-decides-static-lexical"></a>
### 4.1 方案 A：由构造顺序决定（静态、词法作用域）

开放路径就是源码中构造结构的嵌套关系。两种表层语法，一套底层机制。

**用于递归的函数返回值。** 最自然的递归下降解析器：

```klang
recursive fn value(r: json::Reader&) -> Json.. {
    match json::peek(r) {
        '[' => {
            var a = Json.Arr { children: [] };
            json::each_element(r) { a.children.push(value(r)); };
            return a;
        },
        '{' => {
            var o = Json.Obj { members: [] };
            json::each_member(r) { key => o.members.push(Member { key: key, val: value(r) }); };
            return o;
        },
        '"' => Json.Str { s: json::read_string(r, scratch) },
        _ => Json.Num { v: json::read_number(r) },
    }
}
```

`a` 是一个命名结果（§7.3），因此它从声明处起就直接分配在调用方指定的目标位置上：即父级 `children` 的顶部，而这又是父级的父级的顶部，一路向上直到非递归调用方中的 `let doc = value(r)`。每一次递归激活（activation）都在 `doc` 所拥有的那同一个栈上构建数据。需要修改的规则是 §7.8 中的“调用进入递归环时，作用域内不能有非定长局部变量”。该规则背后的原因——每次激活需要一个独立的栈——并不适用于本身不持有独立栈的局部变量：**当一个命名结果直接构建在调用方目标位置上时，在向递归环发起调用时它可以处于作用域内，前提是该次调用自身的返回值被推入它或其开放的尾部之中。** 此时被调方的目标位置就是同一个栈的栈顶，这次递归激活不会贡献新的栈。其他任何非定长局部变量仍保留原规则；那些在返回时被拷贝而非就地放置的命名结果（§7.3 已对此发出警告）也同样保留原规则。被推入元素的锁定规则（§1.3(4)）已经能够阻止被调方在其正在构建的元素尚未完成时再去增长 `a.children`，正如第 2 节的最后一个探针所展示的那样。

这种形式还需要另外两块拼图：`a.children` 是可调整大小 ADT 局部变量的载荷字段，而目前无法通过引用访问它（第 2 节）；此外还需要一个在递归环外部拥有、并向下传递的 `scratch` 缓冲区来存放解码后的字符串，正如 §7.8 已经要求的那样。如果将字符串直接解码进磁带，即让 `Json.Str { s: json::read_string_into(r) }` 在载荷内就地构造其结果，则依据同样的就地构造规则，可以完全省去 `scratch`。

**用于直线代码的构建器代码块。** 当某个 push 的元素需要进一步增长时，为其附带一个尾随代码块，该元素在块内处于开放状态：

```klang
var doc: Json.. = Json.Obj { members: [] };
doc.members.push(Member { key: "name", val: Json.Str { s: "klang" } });
doc.members.push(Member { key: "tags", val: Json.Arr { children: [] } }) { m =>
    m.val.children.push(Json.Str { s: "flat" });      // 增长当前开放的元素
    // 此处写 doc.members.push(...) 会触发已有报错：doc.members 正处于构造中
    m.val.children.push(Json.Obj { members: [] }) { inner => inner.members.push(…); };
};
// 从这里起 doc.members.len 才变为 2：push 仅在元素完成时暴露其新长度
```

这个代码块其实就是把元素的构造表达式展开到了多条语句上。检查器将 `m` 视作一个精确以 `doc.members` 顶部为根的可增长引用，而增长日志（growth log）已经在该代码块的作用域范围内锁定了所有祖先节点。元素的计数在代码块结束时才变得可见，这与如今 push 的规则一致（“push 仅在元素完成之后才暴露其新长度”，参见 `docs/design/result_construction.md`）。从代码块内部使用 `return … from` 跳出时，会丢弃尚未完成的元素，这在 §7.3 的 Exits 部分已有明确规定。在代码块内部读取祖先节点是安全的：祖先的计数尚未包含当前开放的子节点，因此迭代绝不会越界踏入未完成的字节。

**优点。** 零运行时开销，无需引入新的运行时状态；在运行时不需要做任何检查。所需组件均是对现有机制的扩展（命名结果放置、目标位置请求、增长日志、尾随代码块）。构建完成的树是一个完整的扁平值。§7.8 的放宽范围狭窄且易于解释：不持有独立栈的局部变量不会为每次激活增加一个栈。

**缺点。** 只能深度优先：开放路径严格等同于词法嵌套深度或递归调用深度。因此，嵌套深度无界的文档必须使用递归解析，而这要求在面对不可信输入时设置深度上限。目前的 `json::parse` 是单个循环加上一个显式的 `Open[>..<]` 外围容器栈，可以解析任意深度的文档；在方案 A 下，磁带形式无法那样编写。对于手工构建的深层树而言，构建器代码块也显得较为冗长，而形状由数据决定的树无论如何都得靠递归函数来构建。

<a id="42-option-b-open-handles-tracked-by-flow"></a>
### 4.2 方案 B：由流分析追踪的开放句柄

不用代码块，而是提供一个返回开放句柄的操作以及一个显式的关闭点：

```klang
let tags .= doc.members.open(Member { key: "tags", val: Json.Arr { children: [] } });
tags.val.children.push(…);
… // 其他语句，以及接收 `tags` 的调用
close(tags);                                   // 或者：在 tags 的作用域结束时关闭
```

检查器将“开放”作为句柄的一种流敏感（flow-sensitive）属性来追踪，方式与如今追踪确定赋值和缩容活性相同：只要 `tags` 处于开放状态，`doc.members` 就被锁定；在 `close` 之后，`tags` 失效，`doc.members` 可以重新增长。再打开 `tags` 的子容器则会锁定 `tags`，依此类推。

**优点。** 可以在一个函数中打开，在另一个函数中添加元素，在第三个函数中关闭；状态机可以在一个局部变量中跨越循环迭代持有一个开放容器，而无需用代码块包住整个循环。**缺点。** 这相当于在一个本来没有类型状态（typestate）的语言里引入类型状态；每一个分支、循环、提前返回以及可能关闭或打开句柄的调用都必须按特化版本进行合并与摘要。此外深度仍然是静态的，对无界嵌套没有任何帮助，也并未让递归变得更容易。凡是能用 B 写出的程序，只需稍作结构调整都能用方案 A 写出，因此在真正出现 A 无法表达的用例之前，不值得为 B 付出检查器复杂度的代价。

<a id="43-option-c-a-runtime-check-that-the-container-is-on-top"></a>
### 4.3 方案 C：检查容器是否位于顶部的运行时检查

允许通过任何指向嵌套 `[>..]` 元素的引用执行 `push`，并在运行时检查该容器是否就是最内层的开放容器——即它的末尾是否位于栈顶。本语言已经会在越界检查失败时中止（abort），并且当检查器无法静态确定切片位置时，`realloc_slice` 已经会在运行时检查包含关系（参见 `docs/design/owning_dynamic_data.md`），因此这种做法并非没有先例。GNU obstacks 做的就是类似的事情，只是不做检查。

难点在于如何得知容器的末尾位置。顺序容器的末尾无法在不遍历子元素的情况下从其计数推算出来，因此栈上需要维护一个 `open` 指针，在打开容器时设置并在关闭时恢复。恢复需要知道父容器，这就意味着要么在运行时维护一个开放容器栈（这正是 §1.3 所禁止的簿记开销），要么提供一个由该检查来验证的 `close(child, parent)`（要求 `child` 必须是当前的开放容器，随后将开放容器切换为 `parent`）。在第二种形式下，程序可以自己把开放链保存在一个 `(Json.Arr&)[>..<]` 或其他任意结构中，这与今天 `json::parse` 维护其 `Open` 栈的方式完全一样。

**优点。** 基于磁带形式的迭代式、任意深度解析器成为可能；检查器规则可缩减到几乎为零。**缺点。** 在本语言原本可以静态证明一切的地方引入了一类新的运行时失败，而且失败方式是直接中止而非返回错误结果。每次通过嵌套引用执行 push 都多了一次比较操作。显式的 `close(child, parent)` 很容易用错——而防止这类错误正是检查器存在的意义。只有当将其作为像 `reusable` 那样的逃生通道（escape hatch），并且磁带形式的无界深度迭代解析确实至关重要时，这种方案才算合理。

<a id="44-option-d-a-pool-of-linked-nodes-todays-jsonnode"></a>
### 4.4 方案 D：链接节点池（当前的 json::Node）

```klang
struct Node { next: Node&<u32>?, first: Node&<u32>?, key: const u8[:], val: Value }
```

每个节点都是 `Node[>..]` 中的一个定长槽位，容器则是通过 4 字节自相对引用（self-relative references）串起来的儿童节点链表。随时都可以用 O(1) 的代价通过链接一个新槽位来向任何容器添加子节点。这就是支持随机修改的方案，而且已经存在。

**优点。** 现成可用；可在任意位置、以任意顺序插入；单一扁平数组配合相对链接，因此可直接序列化；`member` 及各类访问器也已写好。**缺点。** 每个节点占用 8 字节的链接开销，外加每个键或字符串 16 字节的切片开销；字符串存放在原文本或旁路缓冲区中，因此整个文档是三个数组，而非单个值；同一容器的子节点按链接顺序散落在数组各处；在 §1.1 的意义上并不算扁平（因为它持有引用），因此直到 TODO 9 的放宽落地之前，都无法直接跨线程发送给工作线程；而且它并不是最初问题所希望写出的那种声明。

<a id="45-options-rejected-a-stack-per-container-memmove-insertion"></a>
### 4.5 已否决的方案：每容器一个栈、memmove 插入

* **每个容器一个数据栈**（动态栈，§11.3；`owning_dynamic_data.md` 中的方案 A）确实可以让每个容器独立增长。但一个 JSON 文档动辄有成千上万个容器，为每个容器都预留一段栈空间是荒谬的；而且该方案所需的胖引用与生命周期追踪机制，本来是为少数几个大型独立缓冲区设计的，而非用于树结构。
* **通过移动后续字节进行插入**（TODO 8 的插入时 memmove）虽然能让磁带中间的容器继续增长，但每次插入都是 O(文档大小) 的开销，并且会移动引用可能指向的字节，从而导致插入点之后所有指向磁带内部的引用全部悬垂。相对引用只有在两端一起移动时才有效，而跨越插入点的链接并不会一起移动。该方案只有在完全不允许任何指向磁带内部的引用时才是健全的——而这恰恰放弃了 K 语言用来替代索引的核心机制。

<a id="46-option-e-append-handles-a-checked-push-through-a-reference"></a>
### 4.6 方案 E：追加句柄，通过引用执行的带检查 push

核心思路：提供一个针对嵌套容器的句柄（handle），其中持有数组本身以及其存储区域的末尾位置；程序可以在任何时候获取这样的句柄：

```klang
var doc: Json.. = Json.Obj { members: [] };
let ra = doc.members.appender();
let m .= ra.push(Member { key: "tags", val: Json.Arr { children: [] } });
let ta = m.val.children.appender();         // 通过 Arr &a 或分支函数获取
ta.push(Json.Str { s: "flat" });
ra.push(Member { key: "n", val: Json.Num { v: 1.0 } });   // 回到父容器继续追加
ta.push(Json.Null);                                          // 运行时中止：tags 已关闭
```

其中，通过句柄执行的 `push` 只是在把句柄记录的末尾位置与栈顶做一次比较之后执行的普通 push；若两者不等，则立即中止。无需 open，无需 close，也不要求固定的代码结构：增长点在运行时从开放路径上的容器之中动态选择，程序想持有多少个句柄都可以。方案 C 的难点——如何得知容器的末尾——在这里通过在已知末尾的那唯一时刻将其缓存在句柄中得以解决。

**缓存的末尾位置会过时。** 刚刚描述的朴素版本会在上面例子中的第四次 push 时错误地拒绝操作。在 `ta.push` 之后，tags 数组变长了，于是持有它的 member 变长了，于是 `doc.members` 也变长了：它的末尾依然位于栈顶，但 `ra` 里缓存的仍然是当初 push 那个 member 时的末尾位置。开放路径上的每一个容器都结束于栈顶，因此每当一个后代容器增长时，所有祖先节点缓存的末尾位置都会过时，尽管所有祖先实际上仍然是可以追加的。如果句柄仅仅因为缓存的末尾过时就中止程序，那它恰恰拒绝了自己之所以存在的那个核心用法——在构建完子节点后回到父节点继续追加。缓存的末尾只能充当快路径（fast path）；慢路径（slow path）必须重新推导出正确答案。

**一种健全且低开销的形式。** 句柄由 `{ count pointer, stack, end, last }` 组成，其中 `last` 是通过该句柄推入的最后一个元素的起始位置。`push` 的执行流程为：

1. 若 `end == top`：直接执行 push。这是最常见的情况，分支预测器会预测走这条路径。
2. 否则，用该类型的大小遍历器（由 R1 生成）遍历最后一个元素：如果 `last + size(last) == top`，说明自 `end` 之后的所有字节都落在这个元素内部，从而证明该容器依然位于开放路径上；将 `end` 更新为 `top` 并执行 push。若不相等，说明有别的数据被追加到了该容器之后，此时 push 中止，并在报错中指出该容器以及外来字节的起始位置。空容器没有最后一个元素，走慢路径时直接中止。

该设计之所以健全（sound），原因在于：push 是原子的（计数在元素的字节写完之后才写入，与今天相同），因此在两条语句之间，直到栈顶为止的整条磁带都是完整的；遍历过程只读取已经记入计数的元素；而通过任意句柄成功执行 push，必然意味着其对应的容器正处于开放路径上，因此它新增的字节就归属于该容器。句柄的正确性不依赖句柄之外的任何状态：不需要每个栈维护指针，也不需要作用域退出钩子（scope-exit hook）。因此句柄是定长的值，可以像普通引用一样在任何地方拷贝和存储，而一个过时的副本最多只是退回到慢路径而已。这里的检查必须是绝对精确的，而不能只是尽力而为：如果误放行了一次向已关闭容器的 push，就会增加一个其字节如今已属于兄弟节点的计数，随后遍历器就会把那个兄弟节点当成子节点来读，在紧凑磁带内部造成类型混淆（type confusion）。直接从磁带数据自身推导出答案，正是杜绝这一问题的根本保证。

每当回到父节点继续追加时，慢路径的代价是遍历最后一个子节点的整棵子树，因此仅靠句柄编写的解析器会把每棵子树按其祖先层数重复读取一遍，总读取量大约是普通解析读取量的 `depth` 倍。但在深度优先解析器自己的栈上，子节点的句柄往往正好就在手边；此时 `parent.resume(child)` 可以做到 O(1) 且同样健全：`child.end == top` 与子节点的数组位于父节点最后一个元素内部（`parent.last <= child.array < top`）这两个条件合在一起，足以证明自父节点上次缓存的末尾以来新增的一切字节都在那个元素内部。创建一个句柄在面对空容器或刚刚 push 的元素时是 O(1)，否则需要遍历该容器，而这次遍历同时也顺便检查了它是否根本还处于可追加状态；这正是将“在开销低时才调用它”的直觉精确化的结果。

另一种基于链接的替代方案（让句柄指向其父句柄，并在栈上保存一个指向最后执行 push 的句柄的指针）虽然能让每条路径都做到 O(1)，但指向已弹出存储空间的陈旧栈指针可能会错误地验证一个已关闭的容器，因此它必须把句柄限制在局部变量中，并在每个句柄作用域退出时挂接钩子。相比之下，从磁带推导的方案不需要任何这些限制，是要采用的实现。

**它带来的收益。** 静态方案做不到的三件事：

* 依赖于数据的动态增长点。一个由句柄组成的 `[>..<]` 就是显式的开放栈，因此今天 `json::parse` 那样的迭代式、任意深度解析器可以直接基于磁带形式写出。
* 无需修改 §7.8 即可支持递归：`recursive fn value(r: Reader&, into: Json..[>..]&)` 先将节点 push 进 `into`，按引用绑定其载荷，然后对 `a.children` 进行递归。每个句柄都以递归环之外的 `doc` 为根，且没有任何递归激活声明非定长局部变量。检查器的增长摘要需要学会识别“嵌套数组的增长即其根所在栈的增长”，不过方案 A 同样需要这一点。
* 没有部分完成的值。由于每次 push 都是原子的，每条语句边界上看到的都是一棵完整的树；而构建器代码块在块内各条语句之间会让元素处于未完成状态。

**它付出的代价。** 每次 push 多一次寄存器比较（每次回到父节点时预测失败一次）；写入磁带内的计数；一个占四个字（four-word）的引用形式。此外，失败是动态发生的：一个句柄是否依然可用取决于 push 的顺序，如果程序持有很多句柄并以依赖数据的顺序追加，只能在测试时而非编译期发现问题。这是该方案唯一与语言其余部分风格不同的地方。“随处追加”仍然只意味着开放路径上的任意位置：已关闭的兄弟节点依然是关闭的，中止报错也会明确指出这一点。按这种方式构建的磁带在读取时还有其自身的代价，见第 5.4 节。

**与方案 A 本质上是同一操作。** 通过句柄执行 push，与在构建器代码块或命名结果递归中执行 push，都是把相同的字节添加到同一个栈上。区别仅在于：在方案 A 中，检查器已经*证明*了该容器位于开放路径上（它就是代码块正在构建的元素，或是当前递归激活正在构造的返回值），因此可以省去那次比较。这使得方案 A 成为了方案 E 的检查消除（check elimination），正如边界检查消除（§10.5）之于数组索引一样，同样的设计惯例也一脉相承：检查默认保留，除非被证明可以消除；`checkfree fn` 可以要求不得残留任何未消除的检查；而在调试构建（debug build）中，检查器消除掉的 push 依然可以保留该检查，作为对静态证明正确性的预言机（oracle）校验。最初随这一构想一同提出的 `with` 代码块（`ra.with() { … unchecked pushes … }`）其实就是从一个句柄进入的方案 A 构建器代码块：入口处做一次检查，块内不再比较，并由增长日志静态禁止在该块内对同一个栈做任何其他增长。

<a id="47-the-options-side-by-side"></a>
### 4.7 各方案横向对比

| | A：构造顺序 | B：流追踪句柄 | C：运行时顶部检查 | E：追加句柄 | D：链接节点池 |
|---|---|---|---|---|---|
| 增长点 | 最内层开放元素，由源码结构决定 | 静态句柄，由流分析决定 | 开放路径上的任意容器 | 开放路径上的任意容器 | 任意容器，任意时间 |

<a id="5-iterating-the-result"></a>
## 5. 遍历结果

以上讨论的都是写入磁带。将其读回来有其自身的代价，而代价的大小取决于所选的变体。

`Json..[>..]` 是顺序数组。`for child in a.children` 通过将前一个子元素的大小加到游标上来定位下一个子元素，目前后端正是这样做的：循环的步进调用生成的大小遍历器（`src/codegen_types.h` 中的 `k_size_<T>`），而对于嵌套数组，该遍历器会循环累加其所有元素的大小。对于 `u8[][]`，每个字符串只需读一次即可。但对于递归元素类型，这就意味着要遍历子元素的整棵子树，因为要知道一个 `Arr` 在哪里结束，唯一的方法就是找出它的每一个子元素在哪里结束。于是，一个本身也要深入每个子节点的遍历操作（`eval`、`print`、序列化器、查找）在每一层都会把每棵子树遍历两遍——工作本身遍历一遍，外层循环为了跳过它再遍历一遍；位于深度 `d` 的节点在回溯路径上会被 `d` 层循环重复遍历。对于包含 `n` 个节点的文档，这就是 O(n·depth) 次读取，而且多出来的读取全都在读工作阶段刚刚读过的同一批字节。

在手写 C 代码中，人们会让递归步骤返回结束指针，好让调用方的循环从被调方停下的地方继续。或者让数据格式本身携带大小信息：Protocol Buffers 在每条嵌套消息前加上字节长度前缀，FlatBuffers 通过偏移量直接定位一切，simdjson 的磁带则在每个容器开始处记录其结束索引。只记录计数的格式（如 CBOR 和 MessagePack）就存在上述完全相同的问题，每当读取器要跳过一个值时都必须付出遍历代价。对 K 语言而言，有三种可选方案。

<a id="51-walk-again"></a>
### 5.1 重新遍历

什么都不做：直接让循环调用 R1 生成的大小遍历器。这是正确的，如果不做其他工作它就是默认行为，对于浅层数据完全可以接受。对于那些不能信任磁带所记录大小信息的读取器而言，这也是唯一的选择，第 5.4 节会回到这一点。

<a id="52-hand-the-end-back"></a>
### 5.2 将结束位置交还

把“递归步骤所解析内容的大小”上升为语言概念：指向顺序数组元素的引用同时携带其起始位置和结束位置，而一个把该元素的子元素迭代到末尾的递归步骤，其循环游标里正好已经握有那个结束位置，于是将它返回，供调用方的循环直接从此处继续。这相当于把 C 语言的惯用法做成了语言特性。麻烦在于，只有当循环体遍历了整个元素（包括嵌套数组之后的任何字段）时才会产生结束位置；一旦循环体中途跳过（`if key == "x"`）、提前终止或根本不深入子元素，就不会产生结束位置，因此循环必须静态判断哪些循环体能交还结束位置，对其余情况退回到重新遍历。这把循环体的控制流与循环自身的步进耦合在了一起，而所节省的开销在第 5.3 节里无需任何耦合就能拿到。不推荐。

<a id="53-store-the-size"></a>
### 5.3 存储大小

让元素类型为递归类型的嵌套数组把字节大小保存在计数旁边：在所有子元素之前存放 `{ count: u32, bytes: u32 }`。生产者在容器完成的那一刻就能知道这个大小——即栈顶减去起始位置——只需写入一次；此后每个读取器都只需读出这一个字（word）就能跳过整个容器。跳过一个 `Json` 元素于是变成常数次读取且无递归：先读标签（tag），随后根据变体决定——无需再读（`Null`、`Bool` 和 `Num` 都是定长的）、读取变长整数长度（`Str`），或直接读取 `bytes`（`Arr` 和 `Obj`）；`Member` 则在前面加上其键的变长整数长度。严格来说这并不是字面意义上的一次读取，因为必须先由标签判断元素是哪个变体才能去读它的大小，但这个分支 switch 很小，而且在 JSON 中往往高度可预测。大小遍历器保留现有结构；只是它的数组分支改为直接读取一个字，不再循环。

由此带来的推论：

* `for` 循环每步为 O(1)，无论文档有多深，完整遍历都是 O(n)。
* `member(obj, key)` 能以 O(1) 的代价跳过每个不匹配的键值，因此查找是 O(members) 而非 O(subtree)：这正是此前链接节点池明显领先于磁带的唯一操作。
* 对某棵子树执行 `copy`、`bytes_of` 和 `to_bytes` 变成了一次 memcpy 或已知长度的切片视图。完成的磁带成了一种类 FlatBuffers 的格式：读取器只需读一次标签和一次大小就能跳过 1 MB 的数组，整个文档也可以在不解析内容的情况下切分成子文档。
* `from_bytes` 运行的校验器会对照实际遍历结果检查每一个存储的 `bytes`（仅此一次），从而确保外部镜像无法在容器结束位置上造假。
* 代价是每个容器增加 4 字节开销，而且仅由元素类型为递归类型的数组承担——这与 R1 已经甄别出的类型集合完全相同。同样的字段理论上也可以提供给任何嵌套数组（目前要跨过一个 `u8[][]` 字段访问其后的字段也是 O(count)），但这里并不需要那样做。

`count` 是否继续留在 `bytes` 旁边是另一个独立选择。循环完全可以仅靠 `cursor < end` 跑起来，simdjson 就只存储结束位置（并把有上限的计数打包进同一个字里）。省掉 `count` 可以为每个容器节省 4 字节，但代价是这些数组的 `.len` 会退化为 O(children)，而语言里其他所有数组的 `.len` 都是 O(1)。除非对真实磁带的测量表明确有必要，否则应保留两者。

**这个字放在哪里，以及不放在哪里。** 有三种放置粒度可选，它们在跳过开销与数据体积开销上各有取舍：

* *每个元素一份*：为每一个 `Json..` 元素加上长度前缀。跳过只需一次读取且无分支，但每个 `Null` 和 `Num` 也要多花 4 字节。收益与代价不成正比：它省掉的标签分派只是一个很小的 switch，而且 JSON 数组大多是同质的。
* *每个递归元素类型的嵌套数组一份*（本提案）：每个 `Arr` 或 `Obj` 多 4 字节，叶子节点零开销，跳过只需读标签外加一两次读取。
* *每个非定长元素类型的嵌套数组一份*：在每一个 `u8[][]` 或 `Shape..[]` 字段上也加上同样的字，从而使越过它们访问后续字段或跳过包含它们的元素都变成 O(1) 而非 O(count)。

第三种选择引出一个问题：枚举载荷中的数组与结构体尾部的数组是否应保持不同的表示形式。它们其实没有表面上看起来那么不同。位于根部的 `[>..]`，或者位于局部或全局结构体尾部的 `[>..]`，都把计数存放在宿主栈帧中（附录 C.2），其大小就是栈顶减去基址，因此无论选择哪种放置粒度，它都绝不需要那个额外字段；需要考虑的仅仅是位于元素或字段内部的静止态 `[]` 形式数组。之所以把该字段限定在递归元素类型上，是因为它在这里消除的是无界开销，而在其他地方消除的是有界开销：重复遍历一个非递归的嵌套数组，至多带来该类型静态嵌套深度倍的因子——在代码库的所有类型中这个深度也就一两层——而对于递归类型，这个因子是数据的深度。目前代码库中没有任何标准库、基准测试或示例值使用了带有非定长元素的嵌套数组（现有的顺序数据都是字符串以及载荷仅包含定长字段、字符串和引用的可变模式 ADT，这些全都能在 O(1) 内跳过）；`u8[][]` 字段仅在五个测试里出现过。因此目前还没有任何实测场景会暴露出这种有界开销。当然，统一处理也能从遍历器和校验器中去掉一个特例，让所有嵌套数组都能 O(1) 跳过和用 `bytes_of` 取视图，并让序列化镜像只有一种形态，代价是每个此类数组 4 字节（按非定长元素数组计，而非按元素计，且不包含元素定长的字符串）。既然这只是翻转遍历器所查询的那一个谓词的事，完全可以等有了实测数据再定；在那之前，本笔记建议采用仅针对递归类型的形式。

<a id="54-what-each-variant-must-do-to-keep-the-size-right"></a>
### 5.4 每种变体为保持大小正确必须做的事

存储下来的大小是对可能还会被写入的字节所作的承诺，因此每种变体都必须说明它何时写入，以及何时可以被信任。

**方案 A：免费获得。** 元素总是在一个静态已知的时间点完成——即父级计数对外暴露的那个时间点（`docs/design/result_construction.md`），而起始位置就是父级预留的槽位，因此写入大小只需在计数自增旁边多做一次减法：在构建器代码块结束时、当命名结果被接收到父级 push 中时、当字面量完成时，以及在 `copy` 中。可调整大小的根节点其大小就是栈顶减去基址，无需额外字段。由于父级尚未把当前开放的元素计入总数，任何读取器能够触及的内容都是已经完成的，因此无论在构建期间还是构建之后，读取器都可以无条件信任每一个存储的大小。所需支持：为这类数组多加一个头部字、在已有完成点增加一次存储指令、遍历器的数组分支以及校验器。

**方案 E：在回退时写入。** 通过句柄执行的一次 push 会使开放路径上的所有容器同时变长，而句柄对它们一无所知，因此不存在单一的完成写入点。此时能够成立的不变量是：**每一个已关闭的容器都拥有正确的存储大小；开放容器的存储大小可能过时，且没有任何读取器会使用它。** 没有任何读取器需要它，因为开放容器必然是其父容器的最后一个子节点，而没有任何操作会跳过最后一个子节点。大小是在开放路径回退（retreat）时写入的：

* `parent.resume(child)` 会封口（seal）该子容器：只需一次写入，因为该子容器正好结束于栈顶。
* 慢路径的遍历过程会顺带封口它所遍历的一切。遍历本身不必是 O(subtree)：从最后一个元素往下，只有最后子节点链（last-child chain）上的容器才可能处于开放状态，因此遍历沿这条链按计数行进，对其余所有子节点则直接按其存储大小跳过，这使得开销变为 O(depth × fanout) 而非 O(subtree)；同时由于紧随其后的 push 会关闭这些容器，遍历会沿途把整条链的大小全部写好。
* 快路径不会关闭任何未封口的东西。如果一个句柄缓存的末尾等于栈顶，说明它就是上一次执行 push 的句柄，因此它最后一个元素内部的一切早已被前一次 push 之前的 `resume` 或遍历封口过了。

读取器绝不能把可能仍处于开放状态的容器的存储大小当真。顺序步进永远不会踩雷。但对*嵌套*元素执行 `bytes_of`、`copy` 和 `to_bytes` 会用到该大小，因此在根节点仍然处于可调整大小状态时，这些操作要么被拒绝（v1 版本的序列化已经拒绝指向元素字段的引用），要么改由遍历来计算。从根节点出发的读取器知道哪条是开放路径（即最后子节点链），因而能够得出精确值。所需支持：在 `resume` 和遍历中加入封口写入、支持链感知（chain-aware）的遍历器，以及上述操作拒绝。工作量适中，且全部位于 push 的运行时一侧，而不增加检查器负担。另一种替代方案是在根节点冻结时做一次单独的封口遍历（O(n)；检查器可以证明此时已无存活句柄，使用的正是现有的缩容活性检查），在此之前所有读取器都按计数遍历：这样更简单，代价是在树构建期间退回到第 5.1 节的开销。

**方案 D：不需要。** 兄弟节点通过链接串接，步进只是一次指针加载。存储大小使磁带在步进和跳过上追平了链接节点池的性能，却无需链接开销，节点池只在中间插入这一点上还保持优势。

<a id="55-what-iteration-looks-like-and-what-it-needs"></a>
### 5.5 迭代的形式及其所需条件

在源码层面，迭代的写法本来就会是这样：用 `for` 遍历子节点，配合分支函数（case functions）或 `match` 处理每项，并按引用绑定载荷以避免任何拷贝。

```klang
fn total(j: Json.Num&) -> f64 { j.v }
fn total(j: Json.Null&) -> f64 { 0.0 }
fn total(j: Json.Bool&) -> f64 { 0.0 }
fn total(j: Json.Str&) -> f64 { 0.0 }
recursive fn total(j: Json.Arr&) -> f64 {
    var t = 0.0;
    for &c in j.children { t += total(c); }      // 根据 c 的标签和大小直接步进跳过
    return t;
}
recursive fn total(j: Json.Obj&) -> f64 {
    var t = 0.0;
    for &m in j.members { t += total(m.val); }
    return t;
}

fn member(j: Json.Obj&, key: u8[:]) -> Json..? {
    for &m in j.members { if m.key == key { return m.val; } }   // 无需遍历即可跳过每个 val
    return null;
}
```

语言本身无需为此新增任何语法：遍历顺序数组的 `for`、循环和分支函数中的 `&` 绑定，以及通过回边（back edge）返回的递归分支函数，全都已经存在。真正新增的是底层支持：

| | 重新遍历 (5.1) | A 方案下存储大小 (5.3) | E 方案下存储大小 |
|---|---|---|---|
| 底层表示 | 与今天相同 | 为递归元素类型的数组在 `count` 旁增加 `bytes` | 同左 |
| 写入时机 | 从不写入 | 元素完成时，紧挨着计数自增 | 在 `resume` 和慢路径遍历中写入 |
| 可信程度 | 不适用 | 始终可信 | 已关闭容器可信；根节点仍可调整大小时拒绝嵌套 `bytes_of`/`copy`/`to_bytes` |
| 跳过单个子节点 | O(subtree) | O(1) | O(1) |
| 完整遍历 | O(n·depth) | O(n) | O(n) |
| `member` 查找 | O(subtree) | O(members) | O(members) |
| 检查器工作量 | 无 | 无 | 无 |
| 后端工作量 | 无 | 增加头部字、一处写入、遍历器分支、校验器 | 同左，外加链感知遍历与 `resume` 中的封口 |

无论选择表格中的哪一列，所有读取端都需要第 2 节发现尚未支持的同一项能力——可调整大小 ADT 载荷的 `&` 绑定：没有它，`for &c in j.children` 就无从绑定。

<a id="6-costs-shared-by-every-in-place-option"></a>
## 6. 所有就地构建方案共有的代价

* **可调整大小 ADT 载荷的缺口**（第 2 节）位于关键路径上：根 `Json..` 是一个可调整大小 ADT，无论 `a.children.push(…)` 还是 `Arr &a =>` 都需要取得指向其载荷的引用。§8.1 禁止这种绑定是因为整体赋值可能会替换掉变体；只要在该绑定的作用域范围内禁止整体赋值，这个绑定就是健全的——而这正是 §5.1 已经为 `clear` 执行的缩容活性检查。
* **递归类型上的遍历器**会递归至数据的深度（第 3.1 节）。深度上限应放在解析器中；随后对已解析文档调用 `print` 的栈深度也就受此上界约束。
* 任何保持开放的容器，**其计数都是定宽的**；`varint` 长度仅用于叶子节点和单表达式内构建完毕的容器。
* 依据现行 `push` 已经生效的“关闭时更新计数”规则，**构建期间的读取**是安全的。唯一新增的是读取器可以持有一个指向开放元素本身的引用——即句柄。
* **对根的整体赋值**（`doc = Json.Null`）遵循现有的先清零再构造规则（§4.4），并且根据增长日志，它要求当时没有任何部分处于开放状态。
* **非正则递归类型**会在实例化时被现有的深度上限拒绝。
* 如果引入磁带表示，**标准库**将并存两种 JSON 表示：用于可变操作和按键查找的链接 `Node`，以及用于解析、遍历、序列化和跨线程发送的磁带。这与 simdjson 将其 DOM 与 tape 分开的做法如出一辙。

<a id="7-prior-art"></a>
## 7. 先前工作

* **GNU obstacks** 是最直接的先驱：同一时间只允许一个对象增长（`obstack_grow`），在调用 `obstack_finish` 之前 obstack 不会分配其他任何对象，完成后的对象则固定不变。方案 A 相当于允许正在增长的对象嵌套在另一个正在增长的对象*内部*的 obstacks，且把这种纪律交由静态检查保证，而非靠程序员自觉遵守。
* **FlatBuffers 的 builder** 出于同样的“一次只能有一个开放对象”原因，禁止在另一个表尚未完成时启动新表（"nested tables not allowed"）；它绕开嵌套问题的办法是先构建子节点再构建父节点，让偏移量向后指。K 的磁带则改为先构建父节点，再向前就地回填定宽计数。
* **Protocol Buffers** 支持嵌套的长度分隔消息，因此必须在写出内容之前就知道每个嵌套块的大小，这就导致需要 `ByteSizeLong` 和两趟序列化，或者每一层配一个缓冲区。在 K 里，就地写入的 `u32` 计数使得单趟构建成为可能；若使用 varint 计数，则会重新把两趟问题带回来。
* **simdjson 的 tape** 是一个扁平的深度优先数组，每个容器记录其结束位置，由一个维护显式开放容器栈的解析器单趟构建，并按顺序读取。构建完成的 `Json..` 磁带与之形态相同，只是换成了 K 自己的计数；simdjson 同样将其可变 DOM 分开存放，正如第 6 节所建议的。
* **MLKit 区域（regions）与 ParaSail** 已在 `prior_art.md` 中讨论过；两者都没有“在同一区域内嵌套增长”的概念，因为它们都是整块分配对象的。

<a id="8-recommendation"></a>
## 8. 建议

1. **先做 R1**（第 3.1 节）：允许通过数组进行递归，并且仅为处于包含环上的类型生成递归遍历器。它独立完整，能让冻结树得以表达，而且现有的结果构造机制已经能按固定层数就地构建它们。它生成的大小遍历器也恰好是方案 E 的慢路径所需要的。
2. **R2 采用 (b)**（第 3.2 节），因为 (a) 无法从局部声明开始增长根节点，且 (b) 的审计工作可以缩减到上面那一条谓词。同时补齐可调整大小 ADT 载荷的引用绑定缺口；所有方案都需要它。
3. **以方案 E 作为底层机制，以方案 A 作为其检查消除。** 先实现通过指向嵌套数组的引用执行带检查 push：它对检查器的改动更小，能直接交付完整的功能（包括递归和迭代式 JSON 磁带解析器、手工构建的树、存放在栈中的句柄），并且精确定义了检查消除必须保持的语义。随后再教会检查器那两条能省去比较的证明——构建器代码块以及递归中的命名结果（即 §7.8 放宽）——同时在调试构建中保留该检查作为预言机校验。如此一来，`checkfree fn` 就可以像覆盖索引那样覆盖追加操作。
4. **从一开始就存储大小**（5.3），作用于元素为递归类型的数组：只需增加一个头部字，在方案 A 下就写在计数已经写入的同一位置；这是读取磁带的复杂度究竟是 O(n) 还是 O(n·depth) 的分水岭。在方案 E 下则在回退时写入（5.4）。
5. **保留 `json::Node`** 作为可修改、可按键寻址的文档模型；不要试图让磁带本身变成可变的。
6. **放弃方案 B 和方案 C。** 方案 E 囊括了方案 C（它本质上就是解决了末尾定位问题的 C），同时又提供了方案 B 的灵活性而无需引入类型状态。
