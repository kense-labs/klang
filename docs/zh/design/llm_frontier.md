2026 年 10 月研究笔记。本文所涉内容均尚未实现，所有语法均为占位形式。本文探讨的问题是：对于一种主要由语言模型编写、由人类审阅的编程语言，沿着速度、安全性和正确性三个维度，下一个前沿在哪里。此处给出的回答聚焦于正确性，因为这正是 K 语言拥有独特先发优势的领域：它已经在每次编译时对程序进行证明，已经允许程序员要求证明必须成功（`checkfree`），并且它做出的每一项证明同时也是其优化器可以直接利用的信息。本笔记提议将这一机制扩展为一个由编译器检验的*声明*（claim）组成的小型阶梯，供审阅者在函数签名中直接阅读；同时将同样的证明用于提升速度（别名信息、向量化、经证明无竞争的并行循环）和增强安全性（不会泄漏的池句柄）。第 2 节盘点现有机制，第 3 至 5 节给出具体设计，第 6 节分析成本图景，第 7 节给出构建顺序。

<a id="0-summary"></a>
## 0. 摘要

核心论点：**声明（claim）是机器作者与人类审阅者之间的信任单元**，而值得拥有的声明，是那些编译器利用其已在运行的分析进行检验、以语言自身形式表达、并随即在代码生成中加以利用的声明。K 语言目前已有三种：`checkfree`（此函数中无剩余边界检查）、索引类型（`u32 in nodes`：在任何被观测位置均处于合法范围内的整数）以及 `assert`（证明器视为已知前提、同时程序保留检查的事实）。本笔记提出的全部设想皆是在这三者基础上的演进，大致按投入产出比排序如下：

1. **证明证书（certificate）。** `k claims` 按函数打印编译器已验证的声明及所使用的事实，语言服务器则以代码透镜（code lens）的形式展示相同信息。边界检查消除遍已经记录了每处保留检查的保留原因；对称地记录每处移除检查的移除原因即可。这是本笔记中成本最低、且审阅者最先看到的功能（[3.6](#36-the-certificate)）。
2. **将相异根发射为 `restrict`。** 检查器对每个特化版本已经知道两个引用参数何时具有不同的精确根。在生成的 C 代码中将其发射为 `restrict`，可以为 MSVC 补足它在扁平模糊核（flat blur kernel）上缺失的信息——目前 MSVC 编译同一份 C 代码比 clang 慢 3.3–3.6 倍，原因正是如此；该内核使用 `__restrict` 的 C++ 版本能将差距减半。无需新增语法，仅涉及代码生成（[4.1](#41-distinct-roots-as-restrict)）。
3. **事实语言中的契约。** `requires` 和 `ensures` 子句，其命题即为边界检查证明器已理解的形式：整数与长度之间的线性关系，辅以布尔守卫。`requires` 相当于把检查挪到调用点的 `assert`，在调用点通常能被证明消除。`ensures` 则是调用方获得的关于返回值或长度的事实——如今返回值“没有基（base）”，因此无法证明任何性质。两者都是审阅者能在签名中读到的声明，也都是优化器过去未能获取的事实（[3.2](#32-contracts-in-the-fact-language-requires-and-ensures)）。
4. **`abortfree`。** `checkfree` 之上的下一级阶梯：不残留任何形式的运行时检查，因此函数除栈耗尽外绝不会中止。其中的 `assert` 必须被证明，或提升至 `requires` 中。这相当于 SPARK 的“银级”（Silver，无运行时错误），适用于中止集合仅包含七项的 K 语言，同时也是下面两项速度特性的合法前提（[3.3](#33-abortfree-no-runtime-check-of-any-kind)）。
5. **`pure` 与帧（frame）。** 声明式效应，对照检查器已为每个函数计算的效应摘要进行校验；在 C 中发射为 `pure` 与 `const` 属性，并为日后的编译期求值奠定基础（[3.4](#34-effects-pure-and-frames)）。
6. **`par for`。** 其各次迭代运行在*同一*程序多线程上的循环，仅当循环体为 `abortfree`、不触发扩容且证明器证实任意两次迭代不会触及同一元素时才予接受。与 `simd` 一样，它没有独立于顺序语义的语义：程序计算结果与顺序循环完全一致，编译器可任选其一方式执行。K 语言的线程模型之所以能兑现“无数据竞争”的承诺，是因为无竞争性是经过证明的，而非依赖信任（[4.3](#43-par-for-shared-memory-iteration-proven-race-free)）。
7. **所有权池句柄。** 一种恰好释放一次的句柄——由程序显式释放，或在未释放时由编译器在所有者退出时自动释放——且其释放被视为对所有由它派生出的引用生效的收缩（shrink）操作。它堵住了对象池的泄漏和重复释放漏洞，并消除大部分陈旧读取漏洞，代价是引入不可复制的值类别，这是本笔记中侵入性最强的改动（[5.4](#54-owning-handles-a-free-is-a-shrink)）。
8. **终止性**声明，对于计数循环和单调 `while` 循环实现成本很低，且诚实地承认无法证明基于池链接结构的递归的终止性（[3.5](#35-termination)）。
9. **GPU 内核与显式 SIMD**（后续推进），基于与 `par for` 相同的循环体形态：在窄类程序上收益巨大，但需要维护第二套代码发射器，且需先解决数据布局不匹配问题（[4.4](#44-explicit-simd)、[4.5](#45-the-same-bodies-on-a-gpu)）。

未提议的内容：SMT 求解器、针对数组内容的量词、幽灵代码（ghost code）、独立于编程语言之外的证明语言，以及通用精化类型。第 [3.7](#37-what-stays-out) 节解释了原因。

<a id="1-the-question"></a>
## 1. 问题

<a id="11-what-changes-when-the-author-is-a-machine"></a>
### 1.1 当作者变为机器时，什么发生了变化

K 语言的设计围绕一项权衡：在编译期施加更多规则（区分数组种类、规定值的存储位置、禁止引用超出其根的生命周期、禁止可增长局部变量跨越递归调用），以在无需标注的情况下换取速度与安全。Rust 通过其借用检查器做出了类似的权衡。两者都曾因心智负担而受质疑：程序员花在满足检查器上的时间是否物有所值？当程序员变成语言模型时，答案就变了。模型以机器速度针对编译器反复迭代，带有精确信息的报错对它而言成本极低。真正昂贵的是审阅结果之人的注意力——人类无法以模型编写代码的速度逐行通读。

因此，经济学规律反转了。过去对人类作者而言“要求过高”的标注如今写起来成本低廉，稀缺资源变成了*可审阅性*（reviewability）：读者每分钟阅读所能建立的信任度。由此对语言设计产生三点推论：

* **审阅的单元是声明，而非代码行。** 审阅者阅读的是签名及其声明（“不会中止”、“仅写入 `dst`”、“返回 `xs` 的索引”），以及编译器对每条声明成立的确认。这些声明必须存在于源码中、紧邻代码、使用语言自身的术语，并在每次编译时受检——否则它们就只是注释。
* **规约成为新的错误来源。** 模型编写的声明本身可能是错的（太弱而无意义，或陈述了错误的性质）。因此声明应当简短、局限于单个函数、一眼可读；二十行的后置条件与它所描述的代码一样难以审阅。真正有价值的声明，是那些*含义*一目了然、但靠肉眼难以确立其*真实性*的声明。
* **反馈循环必须确定且具体。** 针对证明器迭代的模型需要在每次运行时得到相同的判定，以及能够指出缺失事实的报错信息。K 的边界检查遍已经具备这一特质：它是健全的（sound）、不完备的、确定性的，且 `checkfree` 错误会指出未能证明哪条边界以及哪条 `assert` 可以解决它。一个会超时、或者周二能证过而周三证不过的求解器，对于这种反馈循环来说是错误的工具（[3.9](#39-what-the-llm-results-say) 给出了实证依据）。

K 语言在这方面占据有利位置，因为它的编译器本身就是一个与众不同的证明器。生命周期规则使每个引用的根静态可知，所有调用目标均已知，函数按根特化，效应在调用图上汇总，而边界检查遍则对全程序进行流敏感的线性事实追踪。本笔记中的特性主要是在*暴露*这套现有机制作为声明，并仅在暴露过程中发现缺口时才对其进行补充。

<a id="12-three-axes-weighted"></a>
### 1.2 三个维度及其权重

* **速度。** K 在其基准测试中已经领先于 C++ 与安全 Rust（[bench/summary.md](../bench/summary.md)），在标量 CPU 代码上几乎没有留白。余下的空间集中在三处：C 后端未向 C 编译器传递检查器已知的别名信息（MSVC 下某个内核因此损失 3.3 倍性能）；含运行时检查的循环属于带有侧出口（side-exit）的循环，C 编译器不会对其向量化或自由重排；跨核并行仅能通过不共享内存、按值拷贝输入的工作线程实现。这三处中的每一处，编译器已经能够做出（或几乎能够做出）的*证明*都值回成倍的性能提升。显式 SIMD 和 GPU 执行是真实但适用面更窄的收益，且表面积大得多，因此放在最后。
* **安全性。** K 已经具备内存安全与无数据竞争特性。尚存的漏洞是逻辑层面的：池槽被重复释放、从未释放或通过陈旧句柄读取，都会得到类型正确但值错误的结果。这对池所服务的典型程序（编辑器、服务器、游戏）尤为致命，也是生成代码的审阅者唯一必须手动推理配对关系的环节。对此存在一个低成本的库方案（代数）和一个更深入的语言方案（所有权句柄）；本笔记对两者均进行了评估。
* **正确性。** 这是拥有先发优势之处，也是本笔记着墨最多的部分。`assert` → `checkfree` 这一阶梯已经展现出基本形态：程序员陈述一次的事实、编译器做出的证明、程序员可要求的保证。问题在于无需引入 SMT 求解器还能有哪些性质加入这个阶梯，以及如何让这些声明清晰可见。

<a id="13-a-proof-is-also-an-optimization"></a>
### 1.3 证明同时也是一种优化

编译器验证的每一条声明，同时也是编译器掌握的一条事实，而在 K 中这一直是证明的意义所在：边界检查遍的存在是为了消除检查，`assert` 的存在是为了向其提供事实，索引类型的存在是为了将检查前移至数据入口处，从而使循环无需检查即可运行。本笔记刻意保留了这种耦合。下面列出的每条声明都伴随着优化器从中获取的收益：

| 声明 | 审阅者获知 | 编译器将其用于 |
|---|---|---|
| `requires c` | 函数的前置条件，在每次调用处检验 | 函数体无法从不透明调用方或递归环中获得的入口事实；检查移至调用点，通常在调用点即可被证明消除 |
| `ensures c` | 返回时返回值与长度满足的性质 | 调用方从未拥有过的返回值事实：如 `xs[find(xs, k)]` 无需检查；以及本会被效应摘要抹除、如今得以跨越调用保留的长度事实 |
| `abortfree` | 函数不会失败 | 循环中无侧出口：支持向量化与推测执行；C 属性；`par for` 与 GPU 内核的前置条件 |
| `pure`、`writes(…)` | 函数触及的状态 | C 中的 `__attribute__((pure))`/`const`（公共子表达式消除、循环外提），减少调用方的事实失效（kill），以及日后的编译期求值 |
| 相异根 | 两个参数不可能互为别名 | 在生成的 C 代码中发射 `restrict` |
| 终止性 | 每个循环与递归均有界 | 与 `pure`、`abortfree` 结合时，函数即满足 C 语义下的 `const`：调用可被自由删除、合并与移动 |
| `par for` | 各次迭代相互独立 | 循环在所有核心上运行，且程序语义保持不变 |
| 所有权句柄 | 每次分配均恰好释放一次 | 已释放槽位的引用即已死亡，因此对象池可在目前无法收缩或压缩的地方执行收缩或压缩 |

<a id="2-what-k-already-proves"></a>
## 2. K 语言已经证明了什么

本节盘点后续设计所依托的现有基础设施。规范与实现参考见[参考文献](#references)。

<a id="21-the-prover"></a>
### 2.1 证明器

边界检查遍（规范 §10.5，[implementation.md §5](../implementation.md#5-bounds-check-elimination)）是建立在**差分约束域（difference-constraint domain）**上的流敏感分析：事实的形式为*基*（base）之间的 `l <= r + c`，其中基可以是零、整数变量、*位置*（place，即数组或切片位置）的长度，或操作本身所界定的值的一次性基（one-shot base）。查询旨在寻找可证明的最小 `c`，通过在事实图上求最短路径来回答。事实来源包括 `if`、`while`、`guard`、`assert`、`match` 分支、循环头、已通过的检查（“程序越过 `a[i]` 继续执行仅当 `0 <= i < len`”）、已完成的 `pop`、精确的长度变更（`push`、`clear`、`resize`）以及值的类型（`u8` 小于 256；`u32 in a` 小于 `len(a)`）。失效操作（kill）为基开启新的*代*（generation）而非删除事实，因此关于旧长度已知的性质对旧长度依然成立，且 `push` 会桥接新旧两代（`old <= new`），而 `pop` 则不会。循环通过一次记录式遍历（recording walk）获得推断不变量：初值非负且仅按常量步进的计数器保持 `i >= 0` 和 `i <= len + c`；`for` 循环的步进计数器增长速度不会超过其索引。

跨调用时该遍为全程序分析。每个调用点记录它对实参所证明的事实，待所有调用点均分析完毕后，特化函数以其所有调用点事实的交汇（meet）作为入口状态。被调函数会被摘要化而非被假定为敌意的：`ComputeEffects` 在调用图上计算至不动点，得出每个特化版本可能调整大小或覆写的存储（按参数类别、全局或捕获的局部变量划分）以及可能写入的整数，而一次调用恰好使摘要所列出的状态失效。有三项特性使这种分析格外高效：只增数组仅在分析遍可见的操作处收缩，因此 `push` 之前建立的界限可跨越 `push` 存活；在每个特化版本中每个引用的根都是静态的，因此调用无法触及它没有路径到达的存储；数组拥有单一类型，因此通过指向某个数组的引用进行的扩容不会影响任何其他类型的数组。

该遍要求健全但允许不完备。程序的语义不依赖于它，唯一的例外是 `checkfree` 函数能否通过编译——为此规范固定了一个所有实现都必须能证明的核心集合（规范 §7.14）。它是确定性的，并在所有优化级别下的每次构建中运行，这正是 `checkfree` 能够作为语言规则而非仅作为优化存在的原因。

<a id="22-the-claims"></a>
### 2.2 现有声明

* **`assert(c)`** 既是事实也是检查。该检查在每次构建中均保留；该事实则从该点起馈入证明器。“在内核顶部一次性声明所有长度”这一惯用法正是当今大多数热点循环实现无检查的方式（implementation.md §9.1）。
* **`checkfree fn`** 要求经消除后，函数体内的任何位置都不再残留边界检查、切片检查、索引类型转换或对象池 `free(i)` 检查——在每个特化版本、每个 `simd` 版本以及每个内联副本中均如此。它所调用的函数在其内部运行点处接受判定，因此该保证具有传递性。其报错会以程序员可操作的术语指出残留的检查及原因：“无法证明 `u < dist.len`；`u` 是 `u32 in nodes`，因此在两者之后均不变的位置添加 `assert(dist.len >= nodes.len)` 即可解决”。它不改变程序的计算语义。其他中止依然保留，尤其是 `assert` 正是 `checkfree` 函数在循环外部一次性声明前置条件的手段（[index_types.md §6](index_types.md#6-checkfree-functions)）。
* **索引类型** `uN in a` 与 `uN upto a` 是最窄有效形态的精化类型：一个小于（或至多等于）某个具名只增全局数组长度的整数，且该类型会锁定该数组在全程序范围内禁止收缩。该不变量通过一次受检转换建立，并仅凭类型规则即可保持，证明器无需额外工作，只需读取类型即可（规范 §3.11）。
* **生命周期、可写性、扁平性、`const`** 是类型系统在无需标注的情况下针对每个特化版本证明的声明：无引用超出其根的生命周期、无法通过只读视图写入、非扁平值不可跨队列传递。除作为新声明所复用的底层机制外，它们不是本文讨论的主题。

<a id="23-what-it-cannot-state-and-what-it-does-not-spend"></a>
### 2.3 它无法陈述什么，以及它尚未利用什么

第 3 至 5 节的设计正是按以下出现顺序弥补这些缺口：

* **调用结果没有基。** 调用返回的值，如同从数组或字段中读出的值一样，是一个仅受其类型约束的不透明一次性值。无论 `find` 如何编写，`xs[find(xs, k)]` 都会保留检查。入口事实会从调用点*流入*被调函数；但除效应摘要外，没有任何信息流回调用方。
* **递归环中的被调函数得不到入口事实**，线程入口点与 `export fn` 亦然。它们的前置条件必须在内部通过 `assert` 声明，从而每次调用都付出一次检查的代价。
* **没有析取，没有蕴含。** 差分约束域无法表达 `r == -1 || 0 <= r < n`。K 语言中表达“找到或未找到”的惯常写法是第二个 `bool` 返回值或 `T?`，因此关键事实往往以某个布尔值为条件——这也是当前域无法陈述的。只需一个小扩展——由布尔变量守卫的事实——即可覆盖这些惯用法。
* **没有关于数组内容的事实。** `∀k: 0 <= adj[k] < n` 并非该域所能持有的事实；对于存储的内容，索引类型才是答案，此前曾实现、评测并最终放弃了一套内容不变量分析，因为它未带来任何加速（implementation.md §5.12）。本笔记不重启这一方向。
* **检查器知道两个引用相异，却未告知任何人。** 在每个特化版本中，位于不同变量的两个精确根对应不同的存储。C 后端并未据此发射 `restrict`，导致无法看穿别名的 C 编译器将循环保留为标量执行。
* **检查即侧出口。** 包含检查的循环存在一条必须按序保留的退出路径，这在 MSVC 下会彻底阻断向量化，并限制 clang 的推测执行。`checkfree` 移除了边界检查；除法、容量与 `assert` 仍然存在。
* **并行依赖于拷贝。** 工作线程是相互独立的程序，因此遍历大数组的内核只能在单核上运行，除非将数组切分并通过队列按值发送。
* **对象池的配对未经检查。** `alloc` 与 `free` 只是普通调用；检查器不做任何配对校验，指向已释放槽位的陈旧引用依然是指向合法值的合法引用。

<a id="3-correctness-a-ladder-of-claims"></a>
## 3. 正确性：声明的阶梯

<a id="31-principles"></a>
### 3.1 原则

1. **单一证明器。** 每条声明均由差分约束遍（按本笔记所述扩展）或检查器现有的分析（效应、根、流）来消解。不引入第二套推理引擎。凡证明器无法证明之处，在声明函数中报编译错误，在其他函数中保留运行时检查，完全沿用 `checkfree` 对世界的划分方式。
2. **规范固定核心集合。** 与 `checkfree` 相同，规范列出每个实现对每条声明都必须能证明的核心集合，从而确保针对核心编写的程序在分析遍的每个版本下都能通过编译。核心之外属于实现定义，而若某条声明因别处的调用方修改而停止编译，则在那个调用方处报错。
3. **在签名中阅读声明。** 函数的前置条件、后置条件、效应以及无中止性均写在签名与函数体之间，因为这是审阅者最先阅读的位置。`assert` 仍保留为语句，因为它描述的是函数体内部某一点的事实。
4. **声明不改变程序的计算语义。** 与 `checkfree`、`simd` 和 `inline` 一样，声明在受检后即被擦除；移除声明后的程序语义完全不变。唯一的例外是调用方对编译器不可见的函数（线程入口点、`export fn`）上的 `requires` 子句，它在入口处作为检查运行，效果等同于该处的 `assert`。
5. **渐进式。** 任何地方都不强制使用。不含声明的程序照常编译，函数可按收益顺序逐一添加声明。

<a id="32-contracts-in-the-fact-language-requires-and-ensures"></a>
### 3.2 事实语言中的契约：`requires` 与 `ensures`

**它们是什么。** `requires` 子句是每次调用必须确立的、以证明器语言表达的命题；`ensures` 子句则是每次返回必须确立的命题。命题语言刻意限定为该域自身的词汇：分析遍可读的项（整数参数与返回值、参数与全局变量的 `.len`、常量、与常量的加减，以及分析遍已支持的乘除法）之间的比较运算（`<`、`<=`、`==`、`!=`、`>=`、`>`），以 `&&` 连接，外加需要对该域做小幅扩展的两种形式：布尔守卫（`found: idx < xs.len`，读作“当 `found` 成立时，`idx < xs.len`”）以及针对两个数组或切片参数的 `distinct(a, b)`（[4.1](#41-distinct-roots-as-restrict)）。索引类型参数已在自身类型中携带命题；`requires` 则用于表达实体之间的关系。

```klang
var nodes: Node[>..] = [];
type NodeId = u32 in nodes;

// 现行做法：assert 既是函数体的事实，也是每次调用内部的检查。
checkfree fn sum_at(ids: NodeId[:], weights: i32[>..]&) -> i64 {
    assert(weights.len >= nodes.len);
    var t = 0;
    for id in ids { t += nodes[id] + weights[id]; }
    return t;
}

// 提议方案：同一事实声明在签名中。每个调用点证明或检查它；函数体无偿获得该事实。
checkfree fn sum_at(ids: NodeId[:], weights: i32[>..]&) -> i64
    requires weights.len >= nodes.len
{
    var t = 0;
    for id in ids { t += nodes[id] + weights[id]; }
    return t;
}
```

**调用点处的 `requires`。** 子句用调用实参实例化，并在调用方状态中接受判定，判定方式完全等同于向索引类型转换时的索引检查：凡调用方事实可证之处，不发射任何代码；不可证之处，在调用前运行检查，失败时附带子句文本与调用位置中止。在 `checkfree` 或 `abortfree` 调用方内部，未获证明的 `requires` 会产生报错，明确指出调用点与子句（“第 40 行的调用未确立 `weights.len >= nodes.len`”），这正是 [index_types.md §6.5](index_types.md#65-diagnostics) 想要却无法给出的诊断形式。在被调函数内部，无论通过何种途径进入——来自不透明调用点、来自递归环内部（如今递归环无法向被调函数提供任何入口事实），还是通过函数值调用——该子句从第一条语句起即为入口事实。对于编译器永远无法看见调用方的线程入口点与 `export fn`，该子句改为在入口处作为检查运行。因此，`requires` 就是一个把检查挪到通常能够证明消除之处、并把文本挪到审阅者眼前的 `assert`。

**返回点处的 `ensures`。** 子句可将返回值命名为 `result`，或按签名给予的具名返回值引用多个返回值（`-> idx: i64, found: bool`，占位语法，见[第 8 节](#8-open-questions)），还可引用参数与长度。每个 `return` 都是该子句在被调函数状态中接受判定的点；未获证明之处在该处生成检查，在 `abortfree` 函数中则报错。调用方在调用后获得该子句作为事实：涉及返回值的一次性基，以及子句所提及的长度——*且这些长度事实不受调用方效应摘要的失效影响*。后半句与前半句同样重要：如今调用 `fill(dst, n)` 会抹除关于 `dst.len` 的全部事实，因为摘要表明 `fill` 会调整 `dst` 的大小；而借助 `ensures dst.len == n`，调用方随后的 `for i in n { dst[i] }` 将重新实现无检查。

```klang
// 返回值是 xs 的索引，因此 xs[clamp(i, xs)] 在任何地方都不需要检查。
fn clamp(i: i64, xs: i64[:]) -> i64
    requires xs.len > 0
    ensures 0 <= result && result < xs.len
{
    if i < 0 { 0 } else if i >= xs.len { xs.len - 1 } else { i }
}

// 头部解析器：输入剩余部分从 result 开始。
fn skip_header(b: u8[:]) -> i64
    ensures result <= b.len
{ ... }

fn body(b: u8[:]) -> u8[:] { b[skip_header(b)..] }    // 无切片检查

// 条件事实：当 found 成立时，idx 是 keys 的有效索引。
fn find_slot(keys: u64[:], k: u64) -> idx: i64, found: bool
    ensures found: 0 <= idx && idx < keys.len
{ ... }

fn bump(keys: u64[:], counts: i64[:], k: u64)
    requires counts.len == keys.len
{
    let i, found = find_slot(keys, k);
    if found { counts[i] += 1; }                       // 无检查：found 释放了该事实
}
```

**布尔守卫。** `found: P` 存储为以该布尔值的一次性基为前提条件的事实；当控制流进入已知该布尔值为真的区域（`if found`、`guard found else`、`assert(found)`）时，受守卫的事实随即加入当前状态。这是域为了支持常见惯用法所需的唯一补充，且非常小巧：受守卫事实只是多带一个所等待的基的事实。可选类型（optional）则无需任何额外机制：`T?` 返回值经收窄（narrowing）后即成为 `T&`，只要允许 `ensures` 以 `result` 自身为条件，子句即可在收窄后陈述 `result.len`。

**子句不能陈述的内容**包括任何涉及数组内容、任何带量词、以及任何域不追踪的值（`u64` 局部变量、浮点数）的性质。这是一项刻意特性：子句保持一行的体量，熟悉证明器词汇表的审阅者一眼便知每条子句的含义。需要更多保证的函数，其正确性如今日一样由测试来确立，[3.7](#37-what-stays-out) 说明了为何在此划线。

**与语言其余部分的交互。**

* *内联。* 内联被调函数的 `requires` 如非内联函数一样在调用点判定，其 `ensures` 在内联体出口处授予调用方，因此内联与否不改变可证明的内容。
* *函数值。* 通过函数值进行的调用是对它可能指向的每个函数的调用；每个可能的 `requires` 均须受检，而调用方获得所有 `ensures` 的交汇。
* *递归。* 递归环中的函数在每一轮均获得其 `requires` 作为入口事实，这正是当今递归环所欠缺的；它们的 `ensures` 则像对待普通调用一样授予回边。
* *重载。* 子句不参与重载决议。
* *`return … from`。* 跨栈帧返回会绕过中间栈帧；它落回目标函数的返回目的地，因此必须在书写处按书写者当前状态满足目标函数的 `ensures`。若书写者无法判定目标的 `ensures`（例如引用了目标的局部变量），则在落地点生成检查。
* *`defer`。* `defer` 体在返回值构造完成之后执行；涉及 `defer` 可能修改的长度的 `ensures` 在 `defer` 之后判定。
* *索引类型。* `requires b.len >= a.len` 是以 `a` 索引的参数用于 `b` 时的标准伴随条件，且 `checkfree` 核心集合新增一条规则：“当 `b.len >= a.len` 是函数的 `requires` 时，以 `a` 的索引类型索引 `b` 可消除检查”。

**成本。** 子句的解析器与检查器、调用点与返回点处的实例化、兜底检查的发射、条件事实扩展、诊断信息，以及上述核心集合与每项交互的规范文本。索引类型在 19 个文件中增加了 685 行代码（[index_types.md §8.4](index_types.md#84-size)）；本特性大体处于同一量级，因双向数据流及 `return … from` 情形可能多出一半左右。新增运行时成本在子句被证明时为零，未证明时为一次比较，即与现今 `assert` 的开销相同。

**收益。** 对审阅者而言，前置条件直接写在签名中，编译器确认每个调用方均满足之。对优化器而言，返回值事实与调用后长度事实都是全新信息，递归环也首次获得了入口事实。对 LLM 而言，未证过调用点的报错直接点名子句与位置，这正是能在单次迭代内闭环的那类反馈。

<a id="33-abortfree-no-runtime-check-of-any-kind"></a>
### 3.3 `abortfree`：零任何形式的运行时检查

**它是什么。** `abortfree fn`（名称为占位形式；`proven` 以及 `checkfree` 是否更名见[第 8 节](#8-open-questions)）是将 `checkfree` 扩展至规范 §9.3 中一切可通过证明消除的中止情形：

| 中止情形 | 证明义务 | 证明状态 |
|---|---|---|
| 索引或切片越界、索引类型转换 | 同 `checkfree` | 已有 |
| 对空数组执行 `pop`/`pop_n`/`resize` | 调用处 `len >= 1`、`0 <= n <= len` | 已有（`Call::nobc`） |
| 有界数组容量溢出 | 每次 `push` 处 `len < cap`，`append` 处 `len + k <= cap` | 域已有 `Place::cap`；判定 push 为新增，改动很小 |
| 除以零或 `%` 零、`i64.min / -1` | 除数 `!= 0`；或如 `Binary::nonneg` 已判定的 `>= 1` | 部分已有；仅 `!= 0` 需复用条件语句已有的严格不等式处理 |
| `assert(c)` | 在该点证明 `c` | 新增：`abortfree` 函数中的 `assert` 必须可证明，否则报错；修复方法为将其提升至 `requires` |
| `abort(msg)` | 不可达 | 新增：除非证明器证出该路径为死路径（如条件已被驳倒的分支），否则报错 |
| 存储相对引用时的偏移溢出 | 对象池长度适配偏移位宽 | 一般情形较难；v1 排除指向证明器无法界定长度的数组的 `T&<u8>`/`<u16>` 链接，允许指向具有静态容量或 `u32 upto` 界限的数组的 `<u32>` 链接 |
| 数据栈与原生栈耗尽 | 无 | 按定义排除，如同今日所有规则均排除原生栈耗尽一样 |
| 仅调试模式的溢出与转换检查 | 发布模式下无 | 排除：该声明针对发布语义。日后可另设 `nowrap` 阶梯，利用 `NoWrap` 推理要求证明器证明 `i64` 加减运算不发生有符号回绕；乘法大多无法证出，需要配合 `requires` |

函数内部调用的一切目标都必须是 `abortfree`、内置函数或声明为 `abortfree` 的 `extern fn`（外部函数如同其类型一样属于被信任边界）。`print` 与 `str` 是除栈耗尽外不会失败的内置函数，向有界数组执行 `format` 则像任何 `push` 一样是容量检查。`qput` 不会中止；`qget` 会阻塞，出于品味而非证明困难被排除在 `abortfree` 之外（审阅者不希望标记此词的函数可能永久阻塞）。其保证为：*当 `abortfree` 函数执行期间，程序终止的唯一方式只有 `exit`、栈守卫触发，或受控工作线程的父进程被终止。*

```klang
let W = 2048;

abortfree fn blur(src: u8[>..]&, dst: u8[>..]&)
    requires src.len == W * W && dst.len == W * W
{
    for y in 1..W - 1 {
        for x in 1..W - 1 {
            let i = y * W + x;
            let s = src[i - W - 1] + src[i - W] as u16 * 2 + src[i - W + 1]
                  + src[i - 1] as u16 * 2 + src[i] as u16 * 4 + src[i + 1] as u16 * 2
                  + src[i + W - 1] + src[i + W] as u16 * 2 + src[i + W + 1];
            dst[i] = (s >> 4) as! u8;                  // >> 4：无除法，无检查
        }
    }
}
```

与现今 `bench/klang/blur.k` 中的 `checkfree` 版本相比，唯一的改动在于过去从调用点获取的长度事实，现在成为函数自身的契约，因此新调用方若传入错误尺寸，会在调用处报错，而非导致 `blur` 编译失败。

**作为推断效应的中止集合。** 该声明背后的判定即使在未显式声明时也有用。效应摘要已经记录函数可能调整大小或写入的内容；它还可以在旁携带一个*可能中止集合*（may-abort set：边界、除法、容量、`assert`、`abort`），按每个特化版本根据残留检查与被调函数集合经同一不动点计算得出。如此一来，`abortfree` 即等同于声明该集合为空，证明证书（[3.6](#36-the-certificate)）会为每个函数打印该集合（无论函数是否声明了什么），调用方也能看到被调函数仍可能因何中止。Zig 的错误集合是推断与子类型化此类集合的范本，只是去除了 Zig 中 panic 不在集合内的盲区（[3.8](#38-prior-art)）。分层形式——`checkfree` 管边界、`abortfree` 管全部——自然从同一份数据中得出。

**为何这一阶梯比看上去更重要。** 生成代码的审阅者想要的正是这句话：“这里面的任何代码都不会失败”。它就是 SPARK 的银级——无运行时错误，Altran 将其设为所有安全完整性等级的默认级别，Thales 在其案例研究中用半天到一天即达到这一级别；而且 SPARK 自身的历史表明，在这一级别几乎所有标注都可以自动推断（[3.8](#38-prior-art)）。K 将同一级别落在了中止集合很短、且检查本就大多已被证明的语言上。此外，它还是各项速度特性的前置条件：不会中止的循环体没有侧出口，因此 C 编译器可以对其向量化和推测执行（[4.2](#42-abort-free-loops)）；不会中止的 `par for` 循环体不存在可观测的失败顺序（[4.3](#43-par-for-shared-memory-iteration-proven-race-free)）；GPU 内核根本没有中止机制，因此只有 `abortfree` 循环体才能成为 GPU 内核（[4.5](#45-the-same-bodies-on-a-gpu)）。

**成本。** 新增的判定（容量、除数、`assert`、死 `abort`）体量很小，因为每项都复用分析遍已有的事实。诊断系统只需将新增种类纳入 `KeptWhy`。规范需为每种中止补充核心集合，形式如 §7.14。真正的成本在于标准库：`abortfree` 具有传递性，因此标准库中的小辅助函数（`min`、`max`、`swap`、`vec` 操作、`sort` 的划分函数）需要先加上该声明，用户程序才能在 `abortfree` 下调用它们，正如它们当初需要加上 `checkfree` 一样。这是对标准库进行的一次性扫描，同时也是一次审计。

**误拒。** 正确但无法在该域中证明的代码将被拒绝，必须重构或补充 `requires`。已知形态（implementation.md §9.1 的“保留”列表）包括从存储中加载且不带索引类型的索引、`u64` 计数器、条件为析取式的循环退出，以及倍增计数器。仓库中现有的 `checkfree` 语料已经生活在这些边界之内；`abortfree` 仅新增了除数（通常是常量或已知为正的长度）以及 `assert`（移至 `requires` 即可）。

<a id="34-effects-pure-and-frames"></a>
### 3.4 效应：`pure` 与帧

**现有基础。** `ComputeEffects` 已经知道每个特化版本可能调整大小或覆写什么以及可能写入哪些整数（implementation.md §5.8），而可写性分析也知道通过每个引用会写入什么。只读并仅写入其参数元素的函数，其效应摘要本来就是这样记录的。缺失的只是一种*声明*效应、并将推断效应与之核对的方法，使声明成为审阅者可读的确认依据，以及调用方在被调函数修改前可依赖的契约。

**`pure fn`。** 函数仅是其参数的函数：不写入自身局部变量和返回值之外的任何位置（无全局变量、无引用参数所指对象、无切片参数元素），不读取可变全局变量（`let` 和 `const` 全局变量是值，可以读取），仅调用 `pure` 函数、无效应内置函数和 `extern pure fn`（由声明者对 C 函数做出的断言，例如 `math` 绑定会携带此标记），且不执行 `print`、队列操作、派生线程或 `return … from`。这是 D 语言的定义减去其“弱纯度”（D 允许 `pure` 函数通过参数修改状态，[d-pure]）；在 K 中，那种情况对应下面的帧声明，因为通过参数写入的内核恰恰是审阅者希望看到其帧的函数。D 与 Nim 都曾遇到过的常见摩擦是调试输出：两者最终都引入了被纯度检查忽略的特殊 `debug` 打印（[d-pure]、[nim-effects]）。K 不应如此；在 `pure` 函数中写 `print` 应直接拒绝，由模型将其删除。

**帧（frame）。** `reads(symbols)` 与 `writes(dst, counts)` 列出函数可能读取以及可能通过引用写入或调整大小的全局变量与参数；其余一切均不可触碰，检查器确认推断摘要为其子集。带帧声明而非 `pure` 的函数正是典型的内核形态（`blur` 写入 `dst`、读取 `src`，别无其他）。SPARK 的 `Global` 切面是先例，其实践方式也是正确的：对于可见代码，GNATprove 自行“生成精确的数据流与控制流依赖”，用户可通过 `--flow-show-gg` 打印，而显式书写的切面只是防止未来变更破坏约束的固定钉（pin），而非证明本身（[spark-gg]）。K 处于与 Rust 的 Prusti 类似的位置——在 Prusti 中所有权*即*帧，完全不需要帧标注（[prusti]）；相反，Dafny 到处都需要 `reads` 和 `modifies`，甚至直到 2023 年才为方法补上 `reads` 子句（[dafny-reads]）。因此，K 中的帧是对摘要的受检重述，由 `k claims` 生成，并在作者想要将其固定时签入代码（[3.6](#36-the-certificate)）。

**编译器将其用于什么。** `pure` 函数在 gcc 与 clang 下发射为 `__attribute__((const))`，仅读取全局变量但不写入任何内容的函数则发射为 `((pure))`（MSVC 无直接等价物；`__declspec(noalias)` 接近帧的情形），从而使循环内参数不变的调用可被外提，参数相同的两次调用可被合并。GCC 关于 `const` 的文档排除了“包含无限循环的函数”（[gcc-attrs]），因此严格来说该属性还需要终止性（[3.5](#35-termination)）；在此之前，不排除无限循环的 `pure` 对两者而言都是安全的发射选择。检查器自身的失效分析已经使用推断摘要，这方面无需新增工作；声明的帧主要使摘要显式化且稳定。日后，`pure` 还是在编译期求值函数调用的前提：K 拥有进程内后端，因此 `const` 初始化器或 `const for` 计数中以常量为参数的 `pure` 调用，可由编译器直接运行并替换为其结果。那是另一项独立特性，此处仅作提及。

**成本。** 很小：摘要已存在，检验只是子集测试，语法仅两个子句，代码发射仅一个属性。微妙之处在于外部函数的处理（必须声明而非推断的信任边界）以及函数值（一个 `pure` 高阶函数仅当其实参纯时才纯，因此纯度必须按实例化判定——摘要本就是这样工作的）。

<a id="35-termination"></a>
### 3.5 终止性

**低成本部分。** 基于区间或计数的 `for` 循环必然终止；遍历数组的 `for` 循环在循环体不触发被遍历数组扩容时必然终止，这正是 `ForLoop::fixedlen` 已能判定的（遍历期间扩容在 K 中合法，implementation.md §3.15，而向正在遍历的数组执行 `push` 的循环可能永不终止）。当记录式遍历发现一个受循环条件界定的单调计数器时（如 `while i < n { …; i++; }`、`while d > 0 { d--; …; }`，以及索引只减不增的堆上滤操作），`while` 循环必然终止——这也是分析遍为获取边界事实本就会找到的信息。对于 `loop` 以及循环条件无法被遍历关联到单调变量的 `while` 循环，则需要显式变体：`decreases e`（占位语法），即一个整数项，证明器须证出它在循环体的每条路径上严格递减且保持非负——这是将同一记录式遍历机制应用于程序员指定的项。针对整数参数的递归同样如此：`recursive fn f(n: i64) decreases n`，要求每次递归调用的实参严格更小，且基本情况受 `n >= 0` 守卫。

**无法处理的部分。** 基于对象池链接结构（`Node&<u32 in nodes>`）的递归在证明器可见的范围内不是良基的：链接可能成环，而无环性属于内容不变量。此类函数只能借助燃料参数（`decreases depth`）来声明终止性，这会真实改变代码乃至算法。通过标记已访问节点来防止重复访问的遍历之所以终止，是因为未标记节点集合在缩小——这同样是内容事实。这是“单一证明器”原则的诚实边界；SPARK 与 Dafny 在堆链接结构上也有同样限制，并要求用户提供幽灵度量。

**自动化程度有多高。** C 语言研究为使用 `for (;;)` 和 `while` 的语言提供了基线：约四分之一的循环在语法上有界（WCET 代码中为 44%），约三分之一是计数 `for` 循环，而能够识别单调计数器与 `A < B` 条件的抽象解释器可以证明 4,090 个 cBench 循环中的 75% 以及 Mälardalen WCET 测试集中的 93% 终止（[loop-patterns]、[loopus]）。K 的起点远高于此基线，因为其 `for` 在构造上即是有界计数或数组遍历，这与 SPARK 的处境一致：“在 Ada 中 for 循环总是终止”，因此仅对 `while` 和普通循环要求变体（[spark-variants]）。Dafny 会为 `while A < B` 猜测 `B - A`（[dafny-termination]），Lean 推断同样形态的度量并打印出来（[lean-termination]），Liquid Haskell 仅凭默认度量即可证明 65.7% 的递归函数终止，其余部分每百行仅需 1.7 行标注（[liquid-termination]）；证明证书应当以同样方式打印出 K 的猜测，使审阅者直接读到变体，而不必盲信其存在。每个成熟系统也都有明确的逃生舱（`decreases *`、`partial`），需要逃生舱的残留代码在各地都一样：搜索循环、解析器、不动点迭代、`loop { … break }` 状态机。

**它能换来什么。** 对审阅者而言，解析器或求解器上的“保证终止”是一项实质性声明。对优化器而言，收益仅源于组合效应：同时满足 `pure`、`abortfree` 与终止性的函数仅仅是其参数的纯值，这正是 C 语言 `const` 属性所断言的语义，使调用在未使用时可被删除或移至任意位置。单独的终止性收益甚微，因为 C 编译器本就假定无副作用循环必然终止。

**成本。** 计数循环与单调 `while` 情形只是对记录式遍历已有发现的归类，因此成本低廉。显式变体属于适度增量。递归规则可依托 §7.8 现有的环路机制。规范文本反而是工作量较大的部分。由于单位代码行的收益较低，这一阶梯排在其他特性之后。

**另两项已考虑但推迟的声明。** *数据栈上界*（`datastack(N)`，占位语法）在 K 中异常容易处理：调用目标静态可知且递归受限，而这恰恰是商业栈分析工具失去精度之处（GNATstack 对递归呈“保守”态度，`cargo-call-stack` 在间接调用处失效，[gnatstack]、[cargo-call-stack]），且函数在各数据栈上的栈帧就是证明器常能界定的尺寸之和。但尺寸通常依赖运行时数据，因此该声明在大多数代码上会被拒绝，应等待确实需要预算的入口点出现后再引入；原生 C 栈则根本无法在语言内声明。*常数时间*是发射 C 代码的语言无法做出的声明：Jasmin 与 FaCT 之所以能做到，是因为它们拥有秘密/公开类型系统并掌控自己的后端，而 Rust 的 `subtle` 与 Zig 的 `timingSafeEql` 在文档中都标明只是针对优化器的尽力而为（[jasmin-ct]、[subtle]）。*无浮点运算*声明（Ada 的 `No_Floating_Point`，[ada-restrictions]）检查起来微不足道，偶尔可用于保证跨 C 编译器的确定性；若有人需要，它只是摘要中的一个比特标志。

<a id="36-the-certificate"></a>
### 3.6 证明证书

边界检查遍记录了每处保留检查的保留原因（`KeptWhy`）。对称地记录每处*已移除*检查的移除原因即可：依据哪条事实、来自哪条语句或哪个调用点、经由哪一代。有了这些信息，就可以按函数输出如下报告：

```
blur (bench/klang/blur.k:19): abortfree, requires src.len == W * W && dst.len == W * W
  18 index checks removed: 18 by the requires clause and the bounds of y and x
  may abort: nothing
  effects: writes dst elements; reads src elements; no globals
  distinct(src, dst): proven at both call sites in main (exact roots a, b)
bfs (test/optimizer/checkfree_bfs.k:46): checkfree
  7 checks removed: 4 by index type NodeId, 2 by the assert at line 47, 1 by the while condition
  0 checks kept
  may abort: assert at line 47; dist.len >= nodes.len would be a requires
  effects: writes dist elements, resizes q; reads nodes, edges
```

上述形态仅为草图；关键在于它由分析遍已有的数据生成，以函数为粒度，且精确指明源码行号。同一份数据在语言服务器中可呈现为代码透镜（“abortfree ✓ · 18 checks proven · pure”），编辑器中的审阅者借此查看声明，模型也借此了解自己可以做出哪些声明。`--bce-lines` 是它的前身，可保留作为按行计数的视图。

在代码审阅工作流中，证明证书正是贴入 Pull Request 的内容：模型编写带声明的函数并运行 `k claims`，审阅者阅读这些声明及编译器的确认信息，而不必亲手重新推导边界。证书之所以生成成本低，正是因为声明在每次编译时都由编译器检验；它是一份实时报告，而非会过时的证明产物。

**成本。** 很小：在分析遍中增加对称记录、一个打印器，以及基于服务器在检查时已拥有的数据构建代码透镜提供器。这是最先要构建的功能，因为后续每一项声明都会在其中呈现。

<a id="37-what-stays-out"></a>
### 3.7 排除在外的内容

* **SMT 求解器。** 它确实能让子句表达更多内容（数组内容、量词、非线性算术），但代价是牺牲 [1.1](#11-what-changes-when-the-author-is-a-machine) 所要求的特质：确定性、有界耗时，以及能够点名具体事实的报错。使用 SMT 的验证语言都将不稳定性与超时列为主要痛点（[3.8](#38-prior-art)）；K 的证明器能力弱、速度快且可预测，而 `checkfree` 经规范固定的核心集合已经展示了如何让弱证明器成为可靠契约而非意外之喜。
* **关于数组内容的事实。** 索引类型才是 K 的答案：内容事实被转化为在数据写入处受检的类型。曾尝试的内容不变量分析未带来任何加速，且审阅者靠肉眼审阅带量词的不变量并不比审阅代码本身更容易。
* **幽灵代码与证明块。** 子句中的任何内容都不需要程序中不存在的计算。一旦某条声明需要引理（lemma），它就不属于这门语言该做的声明。
* **独立的规约语言。** 子句是受限形态的 K 表达式，由同一解析器解析、同一类型检查器校验。没有第二套语法需要学习或转译。
* **通用精化类型。** `u32 in a` 是一种仅具备单一谓词形态的精化类型，之所以选用它是因为其不变量仅凭类型规则即可保持。通用的 `i64 where P` 会在每次存储时——包括穿过泛型代码时——都需要证明器介入，并会倒逼系统走向求解器。若第二种谓词形态确实证明了自身价值（如非负整数、非零除数），也应作为另一种封闭形式加入，而非做成通用机制。
* **测试与有界检验是补充，而非阶梯中的一层。** 证明器无法消解之处正是测试的用武之地，而 K 的进程内后端使得运行基于性质的检查的 `k test` 成本极低。由于 K 发射 C 代码，残留检查也可直接交给未经修改的有界模型检验器（CBMC、ESBMC）在生成的 C 上运行：要么产出能触发中止的具体输入（审阅者可直接运行的反例），要么证明该检查在给定循环上界内不可达（[3.8](#38-prior-art)）。两者均属本笔记范围之外的工具链，且不改变编译器的声明：有界结果不是证明，证书中必须明确注明这一点。
* **不设豁免编译指令（justification pragma）。** SPARK 允许用户标注理由将未证出的检查标为误报；Dafny 与 Verus 有 `assume`。来自 [3.9](#39-what-the-llm-results-say) 的证据表明，模型会滥用任何此类逃生口。在 K 中，诚实的出路就是不声明该属性，或把事实提升为 `requires`，交由调用方消解或检查。

<a id="38-prior-art"></a>
### 3.8 现有工作

现有工作可分为四类：证明无运行时错误的系统、契约与精化类型系统、效应系统，以及终止性检查器。每段末尾均注明可迁移之处。

**将无运行时错误作为受检声明。** 与 `checkfree` 最接近的是 Google 的 Wuffs——一种用于解码不可信文件格式的语言，其保证对“缓冲区溢出、整数算术溢出和空指针解引用”安全，且“所有此类检查均在编译期而非运行期完成”（[wuffs]）。其内部机制宛如微缩版的 K：*事实*是在程序点成立的布尔表达式，由赋值、`if`/`while` 条件和 `assert` 产生，并在汇合点取交集；`assert`“引入新的编译期事实”，零运行时开销，若无法证明则编译失败；检查器是“证明检查器，而非 SMT 求解器或自动定理证明器”，刻意做到“快（且笨）而非聪明（却慢）”；精化类型 `base.u8[..= 99]` 仅携带常量界限；非平凡的推导步需点名所用的公理（`assert n_bits < 12 via "a < b: a < c; c <= b"(c: width)`）；除非证出不可能发生，否则算术溢出直接报错，并以 `~mod+` 与 `~sat+` 作为显式逃生运算符（[wuffs-facts]、[wuffs-assert]、[wuffs-bounds]）。其解码器性能达到 libpng 的 1.2–2.75 倍、giflib 的 2–6 倍（[wuffs-png]）。与 K 的差异在于工作量落点不同：Wuffs 要求程序员手写循环的 `pre`、`post` 和 `inv` 事实，因为“这虽然需要程序员做更多显式工作，但编译时间至关重要”，而 K 则自动推断循环不变量，并为无法证明之处保留运行时检查。两套设计在对机器作者最关键的一点上达成共识：`assert` 绝不是无条件假定。Rust 十年来尝试将“不会 panic”纳入受检属性的历程则是反面教材：`no_panic` crate 依靠链接失败工作，且受优化级别影响（[no-panic]）；三项语言提案均无果而终（“在 Rust 中几乎一切都可能 panic”，[rust-no-panic-2015]；“你描述的是一个方案，而非问题”，[rust-no-panic-2025]）；最终在 2025 年落地的是 `panic = "immediate-abort"`，它只是缩小了 panic 的体积代价，而非证明其不存在（[rust-immediate-abort]）。教训在于：无中止声明必须是编译器自身检查消除遍的判定，而不能是从优化器输出中逆向恢复的性质。Ada 的 `pragma Restrictions`（`No_Exception_Propagation`、`No_Recursion`、Ravenscar 与 Jorvik）是成熟的*配置文件*（profile）路径，属于分区级开关，直接移除检查而非证明其不必要；真正消解检查的是 SPARK 的证明（[ada-restrictions]）。Frama-C 的 RTE 插件则将 C 中的每一处潜在运行时错误转化为供 WP 证明的 ACSL 断言（[frama-c-rte]）。*可迁移之处：* `abortfree` 即是在 K 更小的中止集合上实现的 Wuffs 式保证，并以 K 的推断不变量替代手写循环事实；Rust 的历史则是采用规范固定核心集合的论据。

**SPARK 的阶梯，以及银级的成本。** SPARK 定义了五个级别：“石级（Stone）——合法 SPARK”、“铜级（Bronze）——初始化与正确的数据流”、“银级（Silver）——无运行时错误（AoRTE）”、“金级（Gold）——关键性质证明”、“铂金级（Platinum）——完整功能正确性”（[spark-avocs]、[spark-guidance]）。按 K 的术语，铜级即效应摘要与生命周期规则已为每个程序认证的级别，银级即 `abortfree`，金级即 `requires` 与 `ensures` 所补充的内容。工业界关于银级的记录是本笔记中最具参考价值的实证。Altran 的策略表将银级设为所有安全完整性等级的默认级别（[spark-hcss]）；Thales 在一个代码生成器运行时上仅用“半天”、在一个 7 kloc 的指挥控制单元上用不到一个人日即达到银级（[spark-hcss]、[spark-avocs]）；用户指南称自动化率“通常有 95% 到 98% 的运行时检查可自动证明”（[spark-usage]）；而 NVIDIA 安全团队在约三个月内将两个 C 应用迁移至 SPARK 后报告称“完全没有看到任何性能差异”（[spark-nvidia]）。最鲜明的数字来自 Moy 对同一程序 SPARKSkein 在 SPARK 2005 与 SPARK 2014 下的对比：银级标注从 41 条效应契约、31 条前后置条件、43 条循环不变量与 23 条防爆炸标注骤降至 1、0、1、0，因为“效应与依赖自动生成”、“内部子程序自动内联”以及“循环帧条件自动生成”（[spark-hcss]）。这从另一侧印证了本笔记的核心判断：在无运行时错误这一层级，几乎所有标注都是可推断的，而 K 的分析遍已经推断出 SPARK 当年不得不补加的那两项（效应与循环帧）。SPARK 依然残留的成本全来自求解器：“初始遍可能需要大量精力解决所有误报”，大型程序的分析耗时“可达数小时”，且局限体现在“非线性整数算术（如除法与取模）”（[spark-guidance]）；拥有 250 kloc、契约占代码行 8% 的 iFACTS 每晚重新证明其 152,927 条验证条件约需三小时（[spark-keynote]）。AdaCore 2026 年的一项实验让模型编写铂金级密码学代码：4,085 处检查、“23 条循环不变量、83 条断言与 87 次引理调用”，52 小时中有 43 小时花在“等待工具”上（[spark-ai]），这正是 [3.9](#39-what-the-llm-results-say) 中周期时间问题的另一种体现。

**背后由 SMT 支撑的契约。** Dafny 默认证明无运行时错误与终止性，并对循环做的几乎任何事情都要求用户手写不变量，因为它“除了循环最基本的性质之外一无所知”（[dafny-guide]）；其官方博客直言痛点——证明会在“Dafny 升级、无关定义修改或变量重命名”后失效，只能靠 `opaque`、拆小引理与资源上限来补救（[dafny-brittle]）。比例数字揭示了代价：IronFleet 在实现层的“证明标注与可执行代码之比为 3.6 比 1”（[ironfleet]）；Verus 的 SOSP 2024 系统以 3.1 万行证明支撑 6.1 千行代码，且必须选择“尽可能少的触发器（trigger）”，因为过多实例化会让求解器超时（[verus-sosp]）；seL4 维护着逾百万行证明（[sel4-whitepaper]）。Mariposa 直接评测了六个项目的 17,043 条查询的稳定性：最新求解器“在 2.6% 的查询上不稳定”，在某个项目中高达 5%，且“SMT 求解器升级往往会降低项目稳定性”（[mariposa]）。同一篇 Verus 论文指出，采用受限逻辑的系统能达到“惊人低下的证明与代码比，例如 Hyperkernel 报告为 0.03:1”（[verus-sosp]），这正是本笔记做出的取舍。Creusot 与 Prusti 通过 `requires`/`ensures`/`invariant`/`variant` 标注以及针对 `&mut` 的预言（prophecy）或权限来证明 Rust 的无 panic 性（[creusot]、[prusti]）；Aeneas 丢弃标注并提取出纯模型交由 Lean 证明（[aeneas]）；Frama-C 的 WP 与 Why3 对接多种证明器并记录各证明器的会话以便重放维持稳定性（[frama-c-wp]、[why3]）。*可迁移之处：* 子句词汇（`requires`、`ensures`、变体）及默认义务（无运行时错误、终止性）；不迁移求解器、触发器、引理、重放会话或堆帧推理，因为它们解决的都是 K 模型中并不存在的问题。

**带推断的精化类型：最近的亲缘。** Flux 用索引与谓词精化 Rust 类型，如 `i32[n]`、`RVec<T>[n]`、`i32{v: x < v}`，并以 `ensures` 给出强引用的后置状态，从“一小组无量词模板”中求解无量词 Horn 约束（[flux]）。在相同的 944 行代码上与 Prusti 对比时，液态类型（liquid typing）将“高达代码量 24%（平均 9%）的标注开销降为零”，使规约行数减半（145 对 315），并“将验证时间缩短一个数量级”（评测中为 7 秒对 247 秒，其中 FFT 为 0.7 秒对近三分钟）。Prusti 所需的不变量大多是“简单的不等式或繁琐的簿记”（如 `px.len() == n + 1`），这正是差分约束遍所携带的事实。Liquid Haskell 的真实项目研究发现，规约“大约两行即可表达”，提示占“代码行数的 3.5%”（[liquid-rw]），其终止性检查器证明了“所有递归函数中的 96% 终止”，每百行代码仅需“1.7 行终止性标注”，其中仅凭默认度量就覆盖了 65.7%（[liquid-termination]）。Whiley 在 `for i in 0..|str|` 下无需标注即可验证 `str[i]`，但在计数 `while` 中仍需手写 `i >= 0`，其作者目标正是“自动合成简单循环不变量”（[whiley]）。*可迁移之处：* `u32 in a` 本就属于这一家族，演进方向也与 Flux 一致：以长度与索引作为精化词汇，为改变长度的调用添加 `ensures`，自动推断不变量，并以多态（即 K 的按根特化）替代量词。

**作为编程语言的 Lean。** Lean 4 是“一种通过 C 编译为原生代码的真正函数式语言”，具备引用计数与破坏性更新（[lean-about]、[lean-beans]）；其终止性机制先尝试结构递归，再尝试基于守卫 `e₁ < e₂` 猜测形如 `e₂ - e₁` 的度量的良基递归，失败时打印“Could not find a decreasing measure.”并附每处调用表；`decreasing_by` 目标由线性整数算术判定过程 `omega` 关闭，而 K 的差分域正是它的真子集（[lean-termination]、[lean-omega]）。生产级 Lean（AWS 的 Cedar、SampCert）是以 FFI 方式供外部调用的已验证库代码（[sampcert]）。*可迁移之处：* [3.5](#35-termination) 中的猜度量规则，以及打印所推断度量的做法。至于依赖类型、策略（tactic）与内核检验，对于作者是模型、审阅者只读签名的语言而言均超出范围。

**有界模型检验与抽象解释。** Kani 在给定循环上界内检验 Rust 的溢出、除零与越界索引“无需任何用户标注”：在 Rust 标准库战役中自动生成了 16,748 个检验桩（harness），其中 11,970 个验证通过，发现了 11 个测试与模糊测试遗漏的缺陷（其中 s2n-quic 中的一个缺陷“1600 万次模糊迭代”未能发现，而 Kani 用时约二十秒），同时明确指出“没有循环契约的检验桩仅提供有界保证”（[kani]、[kani-std]）。CBMC 文档也直言，除非展开上界完备，否则循环展开是“不健全的”（[cbmc]）。Astrée 经针对性特化后，在 132 kloc 飞行软件上将误报从首次运行的 1,200 条降至零（[astree]、[astree-erts]）；Facebook 的 Infer 发现批量报告的警报修复率“接近零”，而同样的警报在 diff 提交时实时呈现，“修复率飙升至 70% 以上”（[infer]）。*可迁移之处：* 两件廉价工具与一条原则。`abortfree` 报告的残留检查可在生成的 C 代码中交给未修改的 CBMC 或 ESBMC，以生成触发中止的具体输入，或证出其在给定上界内不可达，从而把“仍残留检查”转化为审阅者可实际运行验证的证据（[3.7](#37-what-stays-out)）。Astrée 的历史表明精度来自针对语言特化分析域，这正是差分约束遍的定位。而 Infer 的教训则指向证书设计：只在编辑当下报告未证事实，绝不事后批量汇报。

**效应系统与纯度。** 好用的系统都是由编译器推断性质，再允许标注作为受检重述：Nim 为每个例程推断副作用、抛出的异常及标签，并允许用 `func` 或 `{.noSideEffect.}` 锁定，其唯一的健全性漏洞在回调中——“通过 proc 类型 T 的每次间接调用均被假定会抛出 system.Exception”，后来由 `strictEffects` 修复（[nim-effects]）；Koka 推断行多态效应，其中 `total` “表示没有任何效应”，且发散本身也是一种效应（[koka]）；Flix “精确追踪每个表达式的纯度”，允许局部作用域内的可变状态留在纯函数内部（[flix]）。反观处处强制标注的系统则怨声载道：D 因外部函数体可能缺失而仅对模板与嵌套函数推断属性，用户抱怨“属性汤”（[d-pure]、[d-inference]）；Fortran 的 `PURE` 纯属手动标注，只为使调用在 `DO CONCURRENT` 中安全（[fortran-pure]）；Rust 的 `const fn` 则是逐版本缓慢扩大允许子集（[rust-const-fn]）。GCC 的 `pure` 与 `const` 属性则是未经检验的口头承诺（[gcc-attrs]），而 OCaml 5 选择了完全不带效应类型的效应处理器（[ocaml-effects]）。帧问题亦然：Dafny 到处需要 `reads` 与 `modifies`，SPARK 生成 `Global` 与 `Depends` 并允许用户钉住（[dafny-reads]、[spark-gg]），而 Prusti 无需帧是因为 Rust 所有权本身就是帧（[prusti]）。*可迁移之处：* 推断、打印、允许标注锁定；K 的全程序编译器既无缺失函数体也无间接调用，因此强制标注纯度的理由一概不成立。

**终止性。** Idris 2 的 `total` 要求沿每条递归链都有参数“严格减小”，Agda 以可配置深度检查结构递归，Lean 尝试结构递归并“尝试推断良基递归”（猜测字典序度量），Dafny 猜测 `decreases` 子句，Koka 将发散视为效应，SPARK 仅对 `while` 循环要求 `Loop_Variant`，ACL2 则要求在良基关系下的度量（[idris-total]、[agda-termination]、[lean-termination]、[dafny-termination]、[koka]、[spark-variants]、[acl2-defun]）。其中每一个都有逃生舱（`partial`、`decreases *`、`TERMINATING`、program 模式）。自动化覆盖率数据见 [3.5](#35-termination)。*可迁移之处：* 猜测、打印猜测结果、对残留部分要求变体，并诚实地拒绝基于池链接的递归。

**资源上界。** 栈上界在商业上要么在二进制层面解决（AbsInt 的 StackAnalyzer），要么结合编译器发射的栈帧大小与保守调用图解决（GNATstack、`cargo-call-stack`），而所有此类工具在间接调用和递归面前都会失去精度（[stackanalyzer]、[gnatstack]、[cargo-call-stack]）；Zig 消除栈溢出的提案自 2018 年起一直悬而未决（[zig-stack]）。seL4、Ravenscar 与 MISRA 不约而同地收敛于“启动时分配，随后证明无增长”（[sel4-faq]、[misra-21-3]）。*可迁移之处：* K 本就已经具备这些工具梦寐以求的形态（静态目标、受限递归、无堆）；数据栈上界可行但暂缓实施（[3.5](#35-termination)）。

### 3.9 LLM 实证结果的启示

关于语言模型编写经验证代码的文献已有三年历史，数量已颇可观。以下是其主要发现、具体数字，以及每一条对上述设计的启示。

**自动主动式（auto-active）证明器适合模型；策略（tactic）证明器大多不行。** 每一项对齐对比都将 SMT 支撑、标注驱动的验证器远远排在交互式证明器之前。AlgoVeri（2026）将同一组 77 个算法交给同一模型并在三个系统中验证：Dafny 通过率 40%、Verus 25%、Lean 8%，并指出 Dafny 让模型“聚焦于逻辑正确性”，而其余两者则“把模型困在持续的语法与语义壁垒中”（[algoveri]）。Vericoding（2025；12,504 条规约）报告了现成模型在 Dafny、Verus 和 Lean 上分别为 82%、44% 和 27% 的通过率，且发现增加自然语言描述“并未显著提升表现”（[vericoding]）；CLEVER 端到端 Lean 成功率仅为 0.6%（[clever]）。同一生态内部进步迅猛：DafnyBench 在十五个月内从 68%（2024 年 6 月）升至单模型 89%、多模型联合 96%（[dafnybench]、[vericoding]）；在来自真实 Verus 系统的 849 个任务上，全自动智能体在 2025 年底达到 81%，而 2024 年的工具仅为 20%（[verusage]）。凡评测之处，成功率均随程序规模与提示数量上升而下降（DafnyBench；VeruSAGE 与任务规模的相关系数为 −0.3 至 −0.5）。*对 K 的启示：* 一个完全不需要进入证明模式、能够自动消解小规模局部算术义务的证明器正是有效的形态；函数是恰当的粒度；子句应当保持单行。

**未见改善的失败环节在于规约。** 规约合成如今成了瓶颈：在 Verina 上，模型 73% 的时间能写出正确代码，却只有 52% 能写出正确规约（[verina]）；VeriBench 最强智能体至多覆盖参考定理的 11%（[veribench]）；在被验证器*接受*的 JML 规约中，有 22.7% 完全没有后置条件（[spec-harness]）。仅写后置条件的契约因缺少前置条件而有 76–82% 的时间是不健全的，而同时要求两者使健全率从 13% 跃升至 81%（[nl2contract]）。*对 K 的启示：* 声明必须让审阅者一眼可读，因为审阅者是判断声明是否正确的唯一预言机；`requires` 与 `ensures` 应当成对出现；声明的词汇表应当小到一旦写错看起来就显而易见。

**只要检查器存在逃生口，模型就会欺骗检查器。** 仅经过几轮强化迭代，模型便学会了使用 `assume(false)`、`ensures true`、`sorry` 与外部公理（[alphaverus]、[vericoding]）；配合库搜索的反作弊检查器让三个模型在 VeruSAGE 任务上的通过率分别提高了 9%、24% 和 26%（[verusage]）；SPARK 研究发现当检查较弱时“智能体试图绕过它们”（[prover-judge]）。*对 K 的启示：* 这是现有设计最有力度的支撑。`assert` 从来不是假定：它既是事实*又是*检查，因此模型无法凭空引入事实而不付出运行时代价，且在 `abortfree` 内部还必须被证明。`checkfree` 则是对编译器自身消除结果的声明，而非用户编写的规约，无可削弱之处。应当坚持这一原则：没有 `assume`、没有受信任子句、没有 `unsafe`。再加一条针对恒真 `assert` 与空洞 `ensures` 的 lint 检查即可堵住最后一道缝隙。

**报错信息就是反馈信号。** “不变量未满足”和原始求解器日志都不具可操作性；源码级反例让某款 Verus 工具在难题上的表现从 65% 提升至 82%，并将成本降至四分之一（[exverus]）；LORIS 通过直接指出模型自身推理中的无效步骤达到 97%（[loris]）；基于报错信息进行修复正是 Baldur 奏效的关键（[baldur]）。*对 K 的启示：* `checkfree` 错误已经能够点名失败的界限及可解决它的 `assert`。证明证书（[3.6](#36-the-certificate)）还应当以机器可读形式补充分析遍在该点*已持有*的事实，以及存在时的可满足赋值（例如 `i = len` 使 `i < len` 失败）。

**确定性与版本稳定性比推理能力更重要。** Verus 的一次版本更新“引入了对显式 decreases 子句的破坏性要求”，导致某前期证明工具在同年两个版本之间的已验证任务数下降了 23.9%（[kverus]）；150 个基准测试任务中有 4 个在 Verus 版本间停止通过验证（[exverus]）；Frama-C 拒绝了 10 个原本正确的不变量（[loopy]）。*对 K 的启示：* 差分约束遍既无超时也无搜索顺序依赖，且规范固定了每个实现必须能证明的内容。应当保持这两点，并将对事实语言的任何改动视为破坏性变更。


**快速迭代胜过巧妙的提示词。** AutoVerus 在 30 秒或三次调用内解决了半数任务（[autoverus]）；智能体每个任务平均运行验证器 6 到 11 次（[verusage]）；在生成*过程中*强制保持良类型（well-typedness）使编译错误减少了一半（[type-constrained]）。*对 K 而言：*编译延迟和机器可读的诊断格式本身就是语言特性；“仅检查当前函数”的模式将会物有所值。

**严格性之所以拉低首次尝试成功率，原因在于不熟悉，而非检查器本身。** 横跨 24 个模型和 12 种语言，Python 的 pass@1 得分为 0.48，Rust 为 0.33–0.39，但在最强的推理模型上这一差距几乎消失（71% 对 70%）（[multi-lcb]）；语言模型通过迭代可以修复约四分之三的真实 `rustc` 错误（[rustassistant]）；Verus 落后于 Dafny 很大程度上在于其语料库的成熟度（[vericoding]）。*对 K 而言：*一门年轻的语言要在语料库和文档上参与竞争；附带一组惯用的已验证示例以及一页纸的事实语言（fact language）语义说明，本身就是特性的一部分。

**简单类型和算术易于验证；堆与别名推理则不然。** F* 的简单类型任务比依赖类型任务更容易通过验证（[fstar-synth]）；AlgoVeri 报告称 Verus 的性能“在系统级内存约束下会崩溃”（[algoveri]）。*对 K 而言：*无堆、无共享的模型消除了在 Rust 和 Verus 中占主导地位的失败推理原因。将边界、范围和长度保留为唯一的证明义务是一种优势，而非局限。

**“已验证”不等于“正确”，审查者也深知这一点。** Anthropic 与 Theorem 合作证明 123 个库不存在崩溃的工作明确指出，“形式化验证”并不意味着“无 bug”，检查器无法判断规范是否符合现实，并显式列出了其可信基（trusted base）（[anthropic-fv]）。那项用智能体以低 20–40 倍的监督成本解除了 49,280 条 GNATprove 证明义务的 SPARK 研究，依然存在逃过证明器、最终被已知答案测试（known-answer tests）捕获的缺陷（[prover-judge]）。调查显示审查者对生成代码的信任度较低（96% 的开发者并不完全信任它，38% 表示审查它需要花费更多精力，[sonar]），并将审查智能体变更描述为“一个信任校准问题，而非 diff 审阅问题”，希望按行和按文件获得风险信号（[trust-calibrated]）。Kleppmann 提出的“挑战将转移到正确定义规范上”（[kleppmann]）正是从另一侧说明了同一点。*对 K 而言：*证明证书（certificate）正是审查者用来校准信任的产物：针对每个函数，声称了什么、证明了什么、依据哪些事实，以及还保留了哪些运行时检查。测试与证明并存。并且应当明确声明可信基：检查器、C 编译器，以及程序声明为 `pure` 或 `abortfree` 的外部函数（externs）。

<a id="4-speed-proofs-the-optimizer-can-spend"></a>
## 4. 速度：优化器可利用的证明

<a id="41-distinct-roots-as-restrict"></a>
### 4.1 将相异根表达为 `restrict`

**证据。** `bench/klang/blur.k` 是一个九点模板（nine-tap stencil），其中的每一项检查都已获证明。在 clang 下它运行耗时 256–266 ms，比 Rust 快 1.10 倍；在 MSVC 下同一份 C 代码耗时 930–952 ms，慢了 3.3–3.6 倍，因为 MSVC“报告通过 `src` 的加载与通过 `dst` 的存储之间可能存在循环携带依赖（loop-carried dependence）”从而将循环保留为标量执行（[bench/notes.md](../bench/notes.md)）。用 `__restrict` 编写的同一内核的 C++ 版本将 clang 与 MSVC 的差距缩小到了 1.83 倍，因此该限定符约占差距的一半；其余部分则来自 MSVC 的向量化器。该 K 内核的行切片（row-slice）形式在两个编译器下都能向量化，因为切片是具有全新基址的局部变量。

**检查器已知的信息。** `main` 中的 `blur(a, b)` 是一个特化版本，其中 `src` 精确地扎根于 `a`，而 `dst` 精确地扎根于 `b`，这是两个不同的变量，因此是两个不同的数组（精确根是对存储同一性的声明，见 implementation.md §3.4）。边界检查遍（bounds-check pass）已经在使用这一点（`HandedApart`、`DistinctTypes`）。在该特化版本的两个参数上发出 `restrict` 在 C 的语义下是健全的（sound）：在调用期间，通过其中一个参数访问的对象不会通过另一个参数被访问。当参数的根不精确，或两个参数可能共享同一个根时，则不发出该限定符。不同数组*类型*的参数根据 K 自身的论证本身就是相异的，无需根推理即可标记。

**作为一项声明。** `requires distinct(src, dst)` 将同一个事实纳入契约之中，这对于特化无法确定的调用者尤为重要：作为 `src` 和 `dst` 传入的同一数组的两个切片具有相同的根，此时调用处会检查两个范围是否互不重叠（两次比较），或者在 `abortfree` 调用者中直接被拒绝。有了该子句后，`restrict` 对该函数而言就是无条件的，而审查者在函数签名中就能一眼看出该内核不是一个原地（in-place）操作。

**成本与收益。** 对于推断情况，仅涉及代码生成：在发出参数时查询根信息（几十行代码），外加按编译器定义的 `K_RESTRICT` 宏。子句形式属于 [3.2](#32-contracts-in-the-fact-language-requires-and-ensures) 的一部分。收益是弥补此类内核在 MSVC 上的全部差距，并且很可能会改善同一后端上 `particles` 和 `scene` 的性能损失；可使用现有的 `bench/bce_ab.py` A/B 测试框架进行测量。在 clang 下不会有变化，因为其别名分析已经将两者区分开来。

<a id="42-abort-free-loops"></a>
### 4.2 无中止循环

循环中的运行时检查本质上是一个跳转到 `noreturn` 调用的条件分支。对 C 编译器而言，它是一个侧出口（side exit），必须保留其相对于其他迭代副作用的执行顺序，因此存储操作不能下沉越过它，加载操作也不能自由提升越过它，而向量化器要么必须证明它不可能触发（clang 有时能做到），要么直接放弃（MSVC 就会放弃：保留 9 项检查使 `blur` 慢了 1.75 倍）。对于占主导地位的边界检查，K 给出的答案是 `checkfree`。`abortfree` 将其扩展到循环体中其余的中止情况，并在两类场景中带来同样的收益：包含除法或 `pop` 的循环，以及将 `assert` 放在循环内部而非提升到外部的循环。它还使 K 自身的代码生成能够进行推测执行：`&&`/`||` 探测（`Binary::specidx`）仅当操作数中的所有检查都已被证明时才会无条件求值该操作数；而有了 `abortfree`，函数中的每一个操作数都满足这一条件。

诚实地评估收益规模：在 clang 上，保留下来的检查通常是分支预测准确率很高的分支，已测得的保留检查开销通常很小（index_types.md §10：gather 操作上为 0–9%，BFS 上在噪声范围内）。巨大的收益出现在 MSVC 上，以及那些原本因某项检查而完全无法向量化的循环中。`abortfree` 值得为了其声明价值而引入；速度提升则是编译器在可行之处顺带收获的副产品。

<a id="43-par-for-shared-memory-iteration-proven-race-free"></a>
### 4.3 `par for`：经证明无竞争的共享内存迭代

**缺口。** K 的线程不共享任何东西（规范 §11.2）：每个工作线程都是一个独立的程序，拥有自己的栈和全局变量，通过扁平值的类型化队列进行数据投喂。这也是该语言无需锁且不存在数据竞争的原因，而且对于服务端和流水线而言它是正确的形态。但对于处理单一大型数组的内核来说，这种形态并不合适——在这类场景中，工作负载是一个各次迭代相互独立的循环，且数据已经就位：把数组切分成扁平块、通过队列发送给工作线程再把结果排队传回，会把所有数据复制两遍，还会把指向该数组的稳定引用丢在原处。`samples/23_mandelbrot_threads.k` 就是如今不得已的写法。

**提案。** `par for i in n { body }`（占位语法）是一种 `for` 循环：当编译器能够证明并行执行不可观测时，可以将该循环的各次迭代放在*同一个*程序的多个线程上、在同一块内存上运行。与 `simd` 一样，该结构本身没有独立语义：程序计算的结果与顺序循环完全一致，因此具体实现也可以顺序执行它（TinyCC 后端就会这样做），并且程序的输出永远不会依赖于实际运行了多少个线程。编译器仅在满足以下条件时才接受该循环：

1. **循环体是 `abortfree`。** 否则，一次中止（abort）将成为一个可观测事件，其发生的迭代、消息和时机都会依赖于线程调度。排除了中止的可能性后，各次迭代除了自身的写入外没有任何可观测的副作用。
2. **循环体不增长任何容器，也不声明任何非定长（non-fixed）局部变量。** 同一程序的多个线程无法共享其数据栈；所有局部变量均为定长的循环体只需要原生栈即可。这正是递归规则和协程规则在第三个场景中的体现：“在栈纪律会被打破的位置不存在非定长值”（规范 §7.8，[coroutines.md §2.2](coroutines.md#22-the-recursion-rule-is-the-coroutine-rule)）。
3. **每次写入都是对元素的写入，且任意两次迭代不会写入同一个元素，也不会一次读而另一次写同一个元素。** 循环体的副作用摘要必须只包含元素写入：不得写全局变量，不得调用 `push`，不得对循环体局部变量之外的任何对象进行整值赋值，不得调用 `qput`、`print`，也不得调用未声明为 `pure` 的 `extern`。随后证明器需证明互不相交性（disjointness）：对于循环变量在两个符号化迭代 `i1 < i2` 下的取值，其中一次迭代中的每个写入位置与另一次迭代中的每个写入或读取位置都两两不相交。该域可以表达内核常用的各种形状：通过 `Lin` 基址，`out[i]` 平凡成立，`b in 0..4` 时的 `out[i * 4 + b]` 亦然；对于 `x in 1..W-1` 时的 `dst[y * W + x]`，结合 `Lin` 与偏移量也可证明，因为 `y1 + 1 <= y2` 可推出 `y1 * W + W - 1 < y2 * W + 1`。这正是 [analysis_inventory.md §5](analysis_inventory.md#6-loops-two-iteration-check-instead-of-name-scans-small-effort-independent) 已为另一目的提出过的“双迭代检查”，只不过这里问的是互不相交性。循环从不写入的数组上的读取操作无需额外条件。通过两个参数访问的数组需要满足 `distinct`（[4.1](#41-distinct-roots-as-restrict)），否则还必须跨参数证明写入的互不相交性。
4. **归约（Reductions）**（`total += f(i)`）是第二种被接受的形式：通过单个结合律运算累加的局部整数或浮点数。整数在任意顺序下都是精确的；浮点数则不然，在 `par for` 中做浮点归约会使结果依赖于调度，因此 v1 要么排除浮点归约，要么定义具有固定块数的固定树形归约顺序——这虽然具有确定性，但结果与顺序求和不同。更务实的 v1 方案是仅支持整数归约，浮点数则由程序自行写入每迭代对应的输出元素中再行归约。

```klang
let W = 2048;

abortfree fn blur(src: u8[>..]&, dst: u8[>..]&)
    requires src.len == W * W && dst.len == W * W && distinct(src, dst)
{
    par for y in 1..W - 1 {                 // iteration y writes dst[y*W+1 .. y*W+W-1]
        for x in 1..W - 1 {
            let i = y * W + x;
            let s = src[i - W - 1] + src[i - W] as u16 * 2 + src[i - W + 1]
                  + src[i - 1] as u16 * 2 + src[i] as u16 * 4 + src[i + 1] as u16 * 2
                  + src[i + W - 1] + src[i + W] as u16 * 2 + src[i + W + 1];
            dst[i] = (s >> 4) as! u8;
        }
    }
}
```

外层循环的每次迭代写入 `dst` 的一行并读取 `src` 的三行；证明器证明对于不同的 `y`，`dst` 的各行互不相交、`src` 从未被写入，且 `src` 与 `dst` 相异。此外无需多言，审查者在阅读函数签名时就知道这个内核之所以能并行，*是因为编译器证明了它可以并行*，而不是有人口头断言如此。

**为何这信守了 K 的承诺。** 这门语言的承诺是不存在数据竞争，今天它通过构造方式（无共享）实现这一点。`par for` 则以一种有界、可检查的形式通过证明来实现它：唯一共享的内存是证明器已证实任意两次迭代都不会同时触及的元素，而其他副作用则全无。语言规范可以将此陈述为每个实现都必须遵守的性质，并像 §7.14 对边界检查所做的那样规定一组核心的受支持索引形状。Rust 通过所有权和 `Send`/`Sync` 为 `rayon` 达到了同样的保证，并借助 `par_chunks_mut` 使互不相交性成为结构化的约束；OpenMP 和 Chapel 选择信任程序员；Futhark 和 Halide 则是函数式的，天生无竞争。K 的变体则直接证明程序员所写索引的互不相交性。

**运行时需要什么。** 程序内部一个按需懒启动的原生线程池，接收一段索引范围以及一个指向捕获环境的指针（循环体使用的引用——即指向不会移动的数组的胖指针——以及定长的捕获值）。循环体被提取（outlined）为一个处理某段范围的 C 函数，这正是代码生成器目前为 `simd` 多版本分发和线程 thunk 所做的事情。任务切分可以是静态的（范围除以 `hardware_threads()`），也可以是按块的工作窃取；确定性的结果对此毫不在意。由于循环体没有非定长局部变量，每个线程所需的唯一内存就是原生栈。

**成本。** 检查器方面：基于副作用的准入检查（主要复用现有摘要）以及在检查遍的位置（places）和项（terms）上进行的双迭代互不相交性判定——这是本节中唯一的新分析，连同其诊断信息（“迭代 `y` 与 `y + 1` 可能同时写入 `dst[y * W + W]`”）大约需要一千行代码。代码生成：函数提取与分发，数百行代码。运行时：线程池，数百行 C 代码，覆盖 Windows 与 POSIX。规范：结构本身、准入规则、受支持形状的核心集、与 `simd` 的交互（`par for` 循环体本身就可以是 `simd fn` 要向量化的循环，两者自然组合）以及与受控工作线程（contained workers）的交互（根据规则 1 不可能发生中止，因此无需额外说明）。整体成本中高，且集中在一项分析上。

**收益。** K 已经瞄准的内核（模板计算、粒子模拟、Mandelbrot、矩阵行运算、独立块上的字节变换）都是易并行（embarrassingly parallel）的，如今除非手动复制数据，否则只能在单核上运行。对于内存轻量级内核，预期加速比接近核心数；对于内存带宽受限的内核，则达到内存带宽比，而且运行在审查者本就信任的同一份代码上。相比无共享工作线程，省下了两次拷贝和丢失的引用；相比 OpenMP，则多出了编译期保证。

<a id="44-explicit-simd"></a>
### 4.4 显式 SIMD

**K 的现状。** `simd fn` 会为函数生成在运行时择机选用的 AVX2 和 AVX-512 版本，依赖 C 编译器对循环进行向量化（在 base64 和矩阵乘法上获得 3–5 倍加速；见 implementation.md §6.13、§9.11），而对包含 2 到 16 个浮点数的结构体进行逐元素算术运算则会发射为单条向量指令（在 FFT 上获得 1.25–1.6 倍加速；§6.14）。两者都属于“编译器能向量化就向量化，程序员负责写出它能向量化的循环”。目前缺失的是自动向量化器无法做到的事情：按通道（lane）划分的数据相关控制流（掩码）、通道置换（洗牌、压缩）、提前退出，以及仅在确实有益时才将查表转化为 gather 指令。

**其他语言的实现。** 每门引入 SIMD 的系统语言都在两种形态之间做出了选择，历史记录高度一致：

| 设计 | 示例 | 提供的能力 | 留给程序员处理的部分 |
|---|---|---|---|
| 定宽向量类型 | Zig `@Vector(N, T)`、Rust `std::simd`、Mojo `SIMD[T, N]`、Odin `#simd[N]T`、Swift `SIMDn`、C++26 `std::simd` | 按通道运算符、掩码、`select`、`shuffle`、归约；可预测的降级（lowering） | 宽度（Zig 的 `suggestVectorLength` 自称是“猜测”，[zig-simd]）、循环本身以及尾部处理——.NET 文档称尾部处理是“常见的 bug 来源”（[dotnet-simd]） |
| 带填充或掩码尾部的原生宽度向量 | Highway（27 个目标平台，[highway]）、.NET `Vector<T>`、C++26 `partial_load` | 一份源码覆盖所有目标；分发表 | Highway 的建议是“确保所有输入/输出都已填充对齐”；gather 操作在各处都不被鼓励（2026 年 Rust 调查测得 LLVM gather/scatter 在 Intel 上比标量替代方案慢 1.75 倍，在 AMD 上慢 4 倍，[rust-simd-2026]） |
| SPMD：按单元素编写循环体，由编译器添加掩码并展宽 | ISPC 的 `uniform`/`varying`/`foreach`（[ispc]）；仅作为允许提示的 OpenMP `simd`（[openmp-simd]） | 在 ISPC 自家内核上比串行 C++ 获得 3.6–8.5 倍单核 AVX 加速（[ispc-perf]）；在自动向量化脆弱之处提供一种机械化变换（Pharr 的回顾文章，[ispc-retro]） | 每个循环几乎不用额外写什么，但 ISPC 不得不为每一种控制流结构构建掩码维护（“花了不少时间才把这套掩码维护机制正确实现”，[ispc-volta]），并且依赖于一个打过补丁的 LLVM |

K 已经在使用的降级目标——GCC 向量扩展——涵盖了前两种形态：逐元素算术、生成全 1 掩码的比较运算、`__builtin_shuffle` 与 `__builtin_convertvector`，以及当宽度不受支持时的窄模式合成（[gcc-vec]）；clang 还补充了布尔掩码向量、`__builtin_reduce_*` 以及带掩码的加载、存储、gather 和 scatter（[clang-ext]）。TinyCC 不支持这些扩展，因此每种向量形式都保留了 §6.14 在 `K_VEC` 背后已有的标量降级路径。GCC 的 `target_clones` 属性是 `simd fn` 如今在 clang 下所做工作的 GCC 对应物（[gcc-clones]），是对现有特性的低成本扩展。

**K 的可选方案。**

1. **显式定宽向量类型** `f32x8`、`u8x32`，掩码表示为 `boolx8`，以及十几个内建函数（`select`、`shuffle`、`reduce_add`，不鼓励使用 `gather`），降级到向量扩展。K 可以以库无法做到的方式彻底消除尾部问题：它同时掌控数据布局*和*栈，因此可以通过在每个数据栈顶部之外多提交一个通道宽度的空间，并在静态数据末尾保留同样的余量，来使越过数组末尾的全宽加载变得安全——这相当于把 Highway 的填充规则变成零成本。§7.12 的精确性规则将这一切串联起来：对于每个 `simd` 版本而言，通道宽度是一个常量，且每个版本计算出的结果都与基准版本完全一致。对于程序员希望自主选择向量形态的库内核（字节集、base64、哈希），这是最务实的下一步。
2. **`par for` 的 SPMD 降级。** [4.3](#43-par-for-shared-memory-iteration-proven-race-free) 中的准入规则恰好免费满足了 ISPC 的全部前置条件：迭代经证明相互独立，因此通道（lanes）可以对应迭代；循环体是 `abortfree`，因此不会有某个通道在向量执行到一半时中止；所有调用都会被内联，因此不存在 varying 调用 ABI；通道间没有指针，也没有按通道的分配。剩下需要做的就是 ISPC 当年不得不构建的东西：循环体内部 `if`、`while`、`break` 和 `return` 的掩码维护，以及 K 可以自动推断出的 uniform/varying 划分（凡是不源自循环变量的都属于 uniform）。回报在于，同一个结构——“这些迭代相互独立”——能够获得由编译器选择的三种降级方式：跨块使用线程、块内使用通道、两者并用；以及日后的 GPU（[4.5](#45-the-same-bodies-on-a-gpu)）。先为 `simd fn` 中的 `par for` 循环体提供一个外部 ISPC 后端，将是在自己动手构建掩码之前测量收益的一条捷径（ISPC 语法类 C，因此只是第二个代码打印器），代价是在单一 C 文件之外引入了一个额外工具链（[ispc-dev]）。
3. **低成本助推器**：根据根信息推导出的 `restrict`（[4.1](#41-distinct-roots-as-restrict)）、在循环体为 `abortfree` 且存储已证明相互独立的循环上添加 `#pragma GCC ivdep` 风格的提示，以及在 GCC 下为 `simd fn` 使用 `target_clones`。无需新语法，不提供保证，且存在难以解释的性能悬崖；但因为几乎免费，所以值得去做。

不可取的方案：Bend/HVM 的并行路线——它为了构造上的并行性而牺牲了顺序执行速度。它自己的测试数据表明，双调排序（bitonic sort）耗时 2.0 s，而 C 只需 0.4 s，其解释器“比 GHC 慢约 5 倍”，在带有循环和可变数组时甚至慢到 100 倍（[bend]，[bend-hn]）。K 的赌注恰恰相反：以 C 的速度运行顺序代码，并在被证明安全之处引入并行。

在整个基准测试套件上测得的 `simd` 多版本收益为 1–4%，处于噪声范围内（§6.13），因为大多数循环要么是标量的，要么已经被自动向量化，真正的收益集中在由库编写一次的编解码器和内核中。因此，方案 1 通过标准库回本，方案 2 通过 `par for` 已瞄准的内核回本，而在它们两者所依赖的正确性阶梯建成之前，两者都不紧迫。

<a id="45-the-same-bodies-on-a-gpu"></a>
### 4.5 在 GPU 上运行相同的循环体

**契合度。** GPU 计算内核本质上就是一个处理定长值的函数，索引定长元素的存储缓冲区，没有递归、没有动态分配、数据中没有指针、没有函数指针、没有异常，且以线程索引作为其循环变量。符合 [4.3](#43-par-for-shared-memory-iteration-proven-race-free) 规则的 `par for` 循环体几乎就是这个样子，而且 `abortfree` 回答了每门 GPU 语言都在回避的问题——越界访问会发生什么（WGSL 将其钳位，Vulkan 将其设为设备选项，CUDA 则直接出错或读出垃圾数据）：K 内核经由证明不会有任何越界，因而根本不需要稳健访问模式（robust-access mode）。K 已经能够通过 `gfx` 的 `embed_shader` 在编译期将 GLSL 编译为 SPIR-V、MSL 和 HLSL，并在 `gfx` 缓冲区上调度计算管线（[stdlib.md](../stdlib.md#compute)）。缺少的一环只是从该 K 子集到 GLSL（或直接到 SPIR-V）的代码发射器，以及将 `T[>..]` 上传到缓冲区并回读的胶水代码。

**不匹配之处**（这才是真正的成本所在）：

* **内存布局。** K 结构体是紧凑排列的（packed）；GLSL 的 `std430` 则将 `vec3` 对齐到 16 字节，且每个字段按自身大小对齐。`Particle { p: float3, v: float3, m: f32 }` 在 K 中占 28 字节，而在缓冲区中占 32 或 48 字节。要么内核将元素类型限制为布局一致的类型（标量、`vec2`、`vec4`、以及大小为 16 字节倍数的 4 字节字段结构体），要么在上传时进行转换，要么编译器提供一种对齐结构体形式。SoA 提案（[soa.md](soa.md)）可以在常见情况下绕开这个问题。
* **索引与位宽。** GPU 偏好 32 位索引，且并非处处都支持 `i64`；而在 K 中 `.len` 是 `i64`。内核应当使用 `u32 in a` 和 `i32` 进行计算，这正是索引类型天然适配的场景。
* **工作组、共享内存、屏障与原子操作。** `par for` 形态中没有任何成分能表达这些概念，而恰恰是需要它们的内核（归约、扫描、带共享分块的模板计算）才是 GPU 大放异彩的地方。v1 可以先覆盖 map 风格的内核，把归约留给主机端的第二遍处理或双内核惯用法。
* **浮点数。** GPU 的浮点语义（部分驱动默认开启 fast-math、不支持非规格化数）会打破精确性规则，除非内核声明接受这种差异。`mul_add` 是经许可的语义差异的先例。
* **调试与驱动。** 行为异常的内核是在驱动程序内部出问题的，没有 `print` 也没有中止（abort）；证明就是调试器。

**收益与成本。** 对于拥有这类内核的程序而言，相对于 CPU 有 10–100 倍的提升，且两侧使用同一种语言并共享类型——配合编译期边界保证，现有技术中没有任何系统能提供这一点（Futhark 凭借其大小类型最为接近）。而对其他所有人来说则毫无收益，却需要维护第二套代码生成器（数千行代码外加一套布局方案），并保证其在三大图形 API 上正常工作。这是本备忘录中针对最窄受众的最高成本项，应当等到 `par for` 已经存在且布局问题有了答案之后再做；届时，该发射器不过是检查器早已接纳的某种循环体形态的一个后端罢了。

**各内核语言禁止的内容**，与 K 规则的对照：

| 系统 | 内核中被禁止或限制的内容 | K 的现状 |
|---|---|---|
| CUDA C++（[cuda-restrictions]） | 设备代码中禁止 RTTI 和异常；`__global__` 函数中禁止递归；设备堆大小“在模块加载后不可更改” | 无异常；递归为显式可选且可排除；无堆 |
| OpenCL C、SYCL（[opencl-restrictions]、[sycl-2020]） | “不支持递归。”；“不允许函数指针。”；无动态分配，无虚函数 | 无函数指针；无动态分配；分发基于枚举的跳转表 |
| WGSL（[wgsl]） | “函数调用不能递归”；“指针不可存储。”；仅支持 32 位整数；原子操作仅限 `u32`/`i32` | “指针不可存储”就是 K 扁平值规则的原话；`.len` 为 `i64`，因此内核需改用 `u32 in a` 计算 |
| rust-gpu（[rust-gpu]） | 无 `alloc` 的 `no_std`；在 0.9 版本将其改为提前退出之前，panic 会导致死循环；绑定特定的 nightly 编译器 | 中止（abort）在 GPU 上没有意义：因此以 `abortfree` 作为准入规则 |
| Julia CUDA.jl（[cudajl]） | “你（通常）不能分配内存，禁止 I/O”；无运行时分发；默认开启边界检查，同步后抛出 `KernelException` | `abortfree` 循环体中无 I/O；检查被证明消除 |
| Mojo GPU（[mojo-gpu]） | 内核“必须不抛异常（non-raising）”，无返回值 | 形态相同 |
| Chapel GPU（[chapel-gpu]） | 符合条件的循环不分配内存、不调用 extern，且“边界检查与空解引用检查会被自动禁用” | K 则改为通过*证明*将其消除 |
| Taichi、Numba（[taichi-kernels]、[numba-cuda]） | 无运行时递归；“Numba 禁止任何分配内存的特性”；边界检查默认关闭或仅限调试模式 | 经证明消除，而非直接禁用 |

两者契合度极高，不匹配之处正是上文列出的那些：工作组、共享内存与屏障（WGSL 通过一致性分析来防护）、原子操作（K 尚无原子操作；64 位原子操作在 Vulkan 上是可选特性，在 WGSL 中则缺失，[vulkan-features]），以及位宽。位宽问题比表面看起来更尖锐：Vulkan 的 64 位整数支持是可选特性，在 NVIDIA 上“所有 64 位整数运算都是模拟执行的”（[nvidia-int64]），而 Futhark 转向 64 位大小后“使 Futhark 程序变慢”，在部分基准测试上慢了 23–30%（[futhark-0181]）。索引类型恰好天然契合：`u32 in verts` 既是 GPU 所期望的，也是证明器所能理解的。

**越界时会发生什么。** WGSL 允许实现返回零、资源中的任意值，或终止该次调用；Vulkan 的 `robustBufferAccess` 会返回“绑定到底层缓冲区对象的内存范围内的任意位置的值”或零并丢弃写入，而 `VK_EXT_robustness2` 将其收紧为读零并跳过写入（read-zero-skip-write），但“在某些实现上可能代价高昂”（[wgsl]、[vulkan-robust]、[robustness2]）；CUDA 会令整个上下文出错（[compute-sanitizer]）；Metal 表示“接下来发生什么是未定义的”，并提供了一个慢到无法随产品发布的验证层（[metal-wwdc]）；naga 提供了 `Restrict`、`ReadZeroSkipWrite` 和 `Unchecked` 策略（[naga-bounds]）。Futhark 在 GPU 上保留了真正的检查：当线程失败时设置一个全局标志并跳到下一个屏障，由主机端在同步点读取该标志——同步检查的几何平均开销为 1.66 倍，异步为 1.07 倍，微优化后为 1.04 倍（[futhark-bounds]）。Dex 将索引做成了类型，因此“不能直接用整数索引一张表”（[dex]）。没有任何已发布的内核语言能为任意索引提供编译期边界保证；而一个 `abortfree` 的 K 内核既不需要运行时检查，也不需要稳健性模式，编译器甚至会直接拒绝编译那些检查未能消除的内核——这是上述所有系统都无法采取的立场。

**体量与陷阱。** 这类转换器都很庞大：rust-gpu 有 2.4 MB Rust 代码，naga 有 3.0 MB，ISPC 有 4.2 MB C++，Futhark 有 5.7 MB Haskell，Halide 有 17 MB，Slang 有 25 MB（[rust-gpu]、[ispc-dev]、[futhark]）。而从一个已经过类型检查、已经受限的 K 循环体打印成 HLSL 或 WGSL 文本，体量则完全不在一个数量级，因为 SDL_shadercross 接收 HLSL 或 SPIR-V 后会完成其余所有工作，且 `embed_shader` 已经在编译期跑通了这条路径（[sdl-shadercross]、[sdl-compute]）。绑定模型是固定的：只读存储缓冲区位于 set 0，读写存储缓冲区位于 set 1，uniform 位于 set 2，管线必须与着色器就 `threadcount` 达成一致。各处报告的陷阱如出一辙：穿过驱动层调试、验证层慢到无法常开、编译器重新插回内核本已选择关闭的检查（Metal 上的 wgpu，[rust-gpu-perf]），以及在一个后端上有效而在另一个后端上无效的 `assert`/`print`（[taichi-debug]）。rust-gpu 自己的数据表明，其内核性能处于与手写 WGSL 持平到慢 1.84 倍之间（[rust-gpu-perf]）；Triton 在一个具有 Python 级别限制的语言中达到了与 cuBLAS 持平的水平（4096² 下 219.7 对 221.1 TFLOPS，[triton]），这说明受限本身并不会拖累性能。

<a id="5-safety-pools"></a>
## 5. 安全性：内存池

<a id="51-the-hole-that-is-left"></a>
### 5.1 留下的漏洞

K 的内存池（`slot_pool`、`slice_pool`；参考手册 §14）为具有非嵌套生命周期的数据提供了无需通用分配器的栖身之处，其代价在设计中已明言：`free` 不结束任何生命周期。槽位（slot）仍然是一个有效值，因此过期的引用会读到*同类型的另一个值*，双重释放会把同一个槽位交给两个所有者，而遗忘释放则会一直泄漏直到池的作用域结束。这些都不构成内存不安全，而这正是该设计的初衷。但对于生成代码的审查者而言，这是唯一一处正确性依赖于编译器未加检查的纪律的地方：每次 `alloc` 都必须配对一次 `free`，且之后不得再使用该句柄。示例展示了这种纪律（`26_file_tree` 的 `release` 递归地先释放节点的一段运行序列，再释放节点本身），而 [scope_exit_cleanup.md §5](scope_exit_cleanup.md#5-examples) 则展示了它容易失手的地方。

按成本递增排序，共有三种机制：带代数（generations）的库（过期读取变为中止）、作用域分配（局部情况，在作用域退出时由编译器释放），以及所有权句柄（每次分配在静态上被精确消费一次）。

<a id="52-generations-as-a-library"></a>
### 5.2 作为库实现的代数（Generations）

一个 `gen_pool<T>`，其句柄由索引和代数组成，并在 `items` 旁维护一个代数数组；`free` 会递增该槽位的代数，而通过句柄进行的每次访问都会校验它：

```klang
root struct gen_pool<T> { items: T[>..] = [], gens: u32[>..] = [], free_slots: i64[>..<] = [] }
struct Handle { i: u32, g: u32 }

fn get<T>(p: gen_pool<T>&, h: Handle) -> T& {
    assert(p.gens[h.i] == h.g);       // a stale handle aborts here, with this line
    return p.items[h.i];
}
```

如果 `items` 和 `gens` 是一个全局池的字段，则 `h.i` 可以是 `u32 in pool.items`，而 `requires p.gens.len == p.items.len` 就是该池的不变式，于是两处索引边界检查都会消失，代数比较成为唯一开销：每个槽位和每个句柄占 4 字节，每次访问执行一次加载和一次比较。Vale 对同一方案的测量结果以及 slotmap 库的经验见 [5.5](#55-prior-art)。这完全不需要修改语言，就能把静默的过期读取转化为带行号的清晰中止，而这正是审查者最想从内存池获得的保障。双重释放会以同样的方式被捕获（该槽位的代数已经推进），因此剩下的问题只有泄漏。为此，同一个模块可以采取 Zig 调试分配器和 Odin 跟踪分配器的做法（[5.5](#55-prior-art)）：在调试构建中为每个存活槽位记录分配位置，并在池作用域结束时或按请求报告未释放的槽位及其行号。这只是一份报告，而非静态保证，但它几乎不费编写成本，且能在测试运行期间捕获泄漏。无论后续还做什么，这都是正确的第一步，应该作为标准库模块发布。

<a id="53-scoped-allocations"></a>
### 5.3 作用域分配

[scope_exit_cleanup.md §3.4](scope_exit_cleanup.md#34-scoped-pool-allocations) 已经设计了这一机制：`scoped let s = pool.alloc_slice(n);` 将结果扎根在声明它的变量而非内存池上，因此现有的存储、返回和分支规则会禁止任何逃逸；编译器像 `defer` 一样在每个出口处发出 `free_slice`；手动释放它则构成编译错误。这无需任何新分析即可覆盖“在此分配、在此释放”的场景，适用于临时切片和临时节点。其收益受限于这种场景出现的频率；那份文档建议等真实代码提出需求时再构建它。所有权句柄会涵盖这一功能：`scoped` 分配本质上就是一个由编译器在作用域退出时自动消费的所有权句柄。

<a id="54-owning-handles-a-free-is-a-shrink"></a>
### 5.4 所有权句柄：释放即收缩

**核心思路。** 池操作可以返回一个*所有权（owning）*句柄——一种最多消费一次、且恰好释放一次的值：`let n = nodes.take(Node { … });`（占位语法）赋予 `n` 类型 `own Node&`。在离开其所在代码块的每条路径上，该句柄要么被*消费*（通过 `nodes.release(n)`、传给声明为 `own` 的参数、存进声明为 `own` 的字段或将其返回），要么处于*未消费*状态，此时编译器会在块出口处自动释放它，就像编译器自己写了一条 `defer` 一样。消费两次会在第二次使用处报错。因此，内存泄漏在构造上不可能发生，双重释放成为编译错误，而程序仅在希望提前归还槽位时才显式写 `release`。这正是 Swift 非可复制（non-copyable）类型和 Mojo 默认接管（take）的仿射（affine）纪律，同时针对释放时需要额外参数的内存池，也提供 Austral 的线性（linear）形式（每个句柄必须显式消费，不做任何隐式释放）作为可选项（[5.5](#55-prior-art)）。K 现有的流分析（明确赋值分析、活性分析）负责路径推理，而退出代码则复用 `defer` 机制。

**释放即收缩。** 该句柄本身是一个引用，因此程序可以像操作任何 `T&` 一样通过它读写，也可以将普通引用绑定到它的目标上（`let r: Node& = n;`）。过期读取的问题在于 `nodes.release(n)` 之后 `r` 会怎样。K 已经为可伸缩数组（grow-shrink arrays）回答过完全相同的问题（规范 §5.2）：指向 `T[>..<]` 内部的引用只能存在于变量中，绝不能进入存储结构，且在任何此类变量之后还会被使用的情况下执行收缩操作都是错误。把释放视为对该槽位的一次收缩：到释放之时，扎根于 `n` 的每一个普通引用都必须已经失活（活性测试，由收缩摘要跨函数调用传递），且没有任何引用被存进某个持有者中。这样一来，通过引用进行的过期读取就不可能发生，唯一残留的过期访问只可能通过普通整数索引发生——这在设计上一直被保留为逃生舱口。池元素中的相对链接（`Node&<u32 in nodes.items>`）属于存储起来的引用，因此是棘手的情况：当一个 `Node` 在仍有其他节点链接到它时被释放，就会留下过期链接。池终结器设计（[scope_exit_cleanup.md §3.3](scope_exit_cleanup.md#33-pool-finalizers)）是它的补充：释放节点时会运行池的终结器，该终结器必须消费节点上的 `own` 字段；但终结器无法做到的是断开指向此处的所有*其他*节点的链接，因此除了引入引用计数外，过期的相对链接在所有池设计中依然是逻辑 bug。

**规则草图。**

1. `own` 值不可复制：禁止 `copy`，禁止静默定长复制，禁止 `let m = n`（这属于移动，之后 `n` 失活），禁止按值传给非 `own` 参数。将普通引用绑定到其目标属于借用，允许这样做。包含 `own` 字段的结构体本身也是不可复制的，在 K 中这意味着从数组或字段中读取它必须通过引用（`.=`、`&`），而不能像今天的定长值那样进行静默复制；这是所有线性系统都有的传染性（virality），也是该特性唯一会改变普通代码阅读观感的地方。
2. 在穿过其声明块的每条路径上——包括 `break`、`continue`、`return`、穿过高阶函数（HOF）的块 `return` 以及穿过当前栈帧的 `return … from`——它最多被消费一次；在未被消费的路径上，编译器会在出口处按与在其声明处所写 `defer` 相同的路径与顺序释放它。`defer` 体可以显式消费它，此时每条路径都视作在那里消费了它。声明为*线性（linear）*的池（显式启用）会将隐式释放变为编译错误，用于释放时需要参数或第二个池的句柄。
3. `own` 类型的结构体字段使该结构体成为所有者：当持有此类结构体的槽位被释放时，其 `own` 字段也会一并被释放，具体由池的终结器完成（[scope_exit_cleanup.md §3.3](scope_exit_cleanup.md#33-pool-finalizers)）——除非程序自己编写一个终结器，否则编译器会根据字段类型自动生成。从结构体中读出一个 `own` 字段是一种*破坏性读取（destructive read）*（`take(n.entries)`），它会清空该字段并将所有权义务移交给读取者；普通读取则是借用。结构体字面量必须为每个 `own` 字段提供 `own` 值，且 `default<T>()` 对此类结构体不可用。
4. v1 排除包含 `own` 元素的数组，正如进入可伸缩数组的引用被限制在变量内一样：`pop`、`clear`、作用域退出以及 `for own x in xs` 的消费规则自成一套独立设计。
5. `own` 值不是扁平值，因此它们不能跨越队列或出现在镜像（images）中；`from_bytes` 永远不会生成 `own` 值。
6. 释放句柄对于扎根于它的每个普通引用来说都是一次收缩（见上文规则）；对句柄调用 `index_of` 会得到一个不带任何义务的普通索引。

```klang
// The file-tree sample under owning handles: a directory owns its run,
// and releasing a node consumes both. The compiler rejects a release
// that forgets the run, and a second release of the same node.
struct Node { name: u8[..15], entries: own Link[:] }

recursive fn release(n: own Node&) {
    let entries = take(n.entries);                            // the run's obligation moves here
    for e in entries { if e { release(take_child(e)); } }     // each child consumed once
    runs.free_slice(entries);                                 // consumes the run
    nodes.release(n);                                         // consumes the handle (or: fall off the end)
}
```

这份草图略过了相对链接的细节：`take_child(e)` 必须把存储的 `Link` 变成一个 `own` 句柄，这是唯一需要运行时占用检查或代数检查的步骤，因为两个父节点可能链接到同一个子节点。一棵链接恰好由唯一父节点拥有的树（就像文件树那样）可以直接让 `Link` 本身成为 `own Node&<u32 in nodes.items>?`，并将该所有权义务存放在该切片运行（run）中——规则 3 允许结构体切片这样做；但这样一来，就必须由 `slice_pool` 的 `free_slice` 来拒绝包含未消费 `own` 元素的切片运行，而这正是规则 4 所推迟的内容。因此，务实的 v1 方案是：所有权句柄用于局部变量、参数、返回值和结构体字段；`own` 切片留待日后；相对链接保持无所有权，并在程序需要确保安全时通过代数进行检查。

**成本。** 这是本备忘录中侵入性最强的一项改动：它引入了语言原本没有的一种值类别（不可复制），触及赋值、`copy`、字面量、按值 `match`、高阶函数捕获（消费被捕获 `own` 的代码块可能被高阶函数调用两次，因此捕获 `own` 必须表现为移入该代码块，或者直接禁止）、泛型（用 `own` 类型实例化的 `T` 必须拒绝会复制 `T` 的函数体，正如索引类型已经拒绝会向 `T` 做算术计算的泛型体一样）、`return … from`、`defer`、工作线程和镜像。检查器方面会复用明确赋值、收缩活性测试以及存储记录；池库则在现有操作之外新增返回 `own` 的操作。Swift 将 `~Copyable` 引入既有语言的经验，以及 Austral 从头围绕线性类型设计的经验，可以校准这一工作的体量（[5.5](#55-prior-art)）。预计需要数千行代码，以及一段体量相当于 §5.2 的规范章节。

**收益。** 每次分配精确释放一次，且不存在通过引用进行的过期读取——这些都成为编译器检查的声明；审查者在签名中读到 `own Node&`，就知道被调用方接过了责任。而且这也是优化器日后可以利用的事实：一个句柄全部为所有权句柄的内存池能够精确知晓其存活集合，从而可以进行内存压缩（compact）或将内存归还系统——而今天的任何 K 内存池都无法做到这一点，因为过期引用可能会观测到它。

<a id="55-prior-art"></a>
### 5.5 先前工作

“一门语言如何确保资源恰好被释放一次”这个问题有着漫长的研究历史。按机制分类，历史经验如下：

**线性类型，手动释放。** Austral 是不使用借用检查器对线性纪律最清晰的阐述：“线性类型的值必须被使用一次且仅一次”；在 `if` 外部声明的线性变量必须在所有分支中消费，或在所有分支中都不消费；在循环外部声明的变量不得在循环内部消费；“只要还有任何未消费的线性值，就不能从函数返回”；包含线性字段的记录本身也是线性的，通过解构来拆开；非消费性使用是 `borrow` 语句，其引用不能离开该语句块（[austral-spec]）。其作者报告称检查器只有“600 行 OCaml”、算法仅“一页文本”，而代价则是“必须手写析构函数调用”以及与异常机制不兼容（[austral-checker]、[austral-cost]）。ATS、Idris 2 的多重性（multiplicities，“线性名称 d'' 有 0 次使用”）和 Cogent 在研究型语言中采用了相同纪律；Cogent 是唯一将无泄漏作为定理证明的语言，代价是它是一门带有认证编译器的非递归纯函数式语言（[cogent]）。Vale 将线性所有权与用于非所有权链接的代数引用配对，并对自家代码总结道：“它很啰嗦，但确实有效！”（[vale-linear]）。

**仿射类型与编译器生成的释放。** Swift 在两个版本中将 `~Copyable` 类型加入了一门成熟语言：此类类型的每个参数都需标注 `borrowing`、`consuming` 或 `inout`，未消费该值的路径会运行 `deinit`，`consume x` 会使后续使用成为错误；而在审查者觉得重复标注过于繁琐之后，泛型的支持也在随后的一个版本中跟进（[se-0390]、[se-0377]、[se-0427]）。Mojo 在 2026 年 1 月发布了同样的混合方案：默认在最后一次使用处销毁，并把“对显式销毁类型的一等支持”作为可选特性，其诊断信息为“'file' abandoned without being explicitly destroyed”；其标准容器也不得不加以改造以容纳它们（[mojo-0261]、[mojo-anytype]）。Rust 则是把这件事做晚了的前车之鉴：`#[must_use]` 只是个能被 `let _ =` 消音的 lint，“must move types”设计要求每个 `match` 分支都移动该值且必须解释 panic 的处理（[must-move]），对该设计空间的调研最终得出结论：“我断定这套系统令人极度不快”，并指出“标准库工作”是最大的负担（[linear-rust]），而引入 `Leak` 或 `Forget` 标记 trait 的尝试则在向后兼容性上触礁（[changing-rules]）；2026 年的 Rust-for-Linux 路线图依然在列出这项探索（[rfl-2026]）。对 K 的启示是：在 `i64` 句柄遍布用户代码之前就确定句柄的所有权机制，并采用仿射作为默认、线性作为可选——这正是 Swift 和 Mojo 最终走到一起的方案。

**带逃逸检查的作用域绑定。** OxCaml 的 `local_` 模式是最接近“绑定上的模式”的设计：“栈分配的值不允许逃逸出其区域”，`stack_ e` 使逃逸成为错误而非静默回退到堆上，`exclave_` 允许被调用方将新创建的局部值返回到调用方的区域，“可变字段和数组元素要求其内容是 `global` 的”，捕获局部值的闭包也是局部的，且局部值不能传给尾调用（[oxcaml-local]）。这些恰恰就是 [5.3](#53-scoped-allocations) 从 K 的根规则中免费获得的规则，而且其中最棘手的两条——可变容器中不得存放作用域句柄，以及不得被逃逸的代码块捕获——在 K 中原本就已经是编译错误。Cyclone 的唯一指针是更早的近亲：仿射语义，配有用于存入共享数据的交换运算符，并以垃圾回收作为未释放时的兜底（[cyclone-unique]）；Pony 的 `iso` 权能（capability）只能通过破坏性读取从字段中移出（[pony-destructive]）。

**代数（Generations）。** Weissflog 关于句柄的文章是行业基准：将条目放在按系统划分的数组中，句柄由索引加上标签构成，释放时递增每槽位的代数，“否则这就是一次悬垂访问”（[handles]）。Rust 的 `slotmap` 为每个槽位保存一个版本号，并指出同一个槽位被重用 2^31 次后的回绕“极不可能发生”（[slotmap]）；Unity 实体也携带索引和版本号（[unity-entity]）。Vale 测得每次解引用都做检查的开销比未检查代码高 10.84%，且在地形基准测试中不到引用计数开销的一半（[vale-gen]）；而 K 的内存池每次查找才检查一次，性能轮廓更轻量。Zig 的调试分配器“永不重用内存地址”，并在 `deinit` 时报告泄漏（[zig-debug-alloc]）；Odin 的跟踪分配器在 `ODIN_DEBUG` 下做同样的事（[odin-tracking]）。两者都不是静态保证，但编写成本几乎为零。

**机器作者与所有权规则。** 目前还没有关于模型编写 Austral 或 Swift 非可复制代码的研究；现有证据来自 Rust。编译器引导的修复在 CRUST-Bench 上将借用错误减少了 75%，其作者称这些错误“在有显式编译器反馈时相对易于处理”（[crust-bench]）；在 SafeTrans 中，引导修复跨模型解决了 74% 的借用检查器违规（[safetrans]）；在 2026 年一项对 86,726 个失败 Rust 样本的分类中，所有权和生命周期错误占 16.7%（[rust-errors]）。这一规律与 [3.9](#39-what-the-llm-results-say) 节一致：一条完整、局部且错误信息能点出修复方式的规则（“0 uses of `d`”、“`file` abandoned”）属于易于处理的类别，而真正伤害机器作者的成本与伤害人类作者的如出一辙——即传染性迫使整个容器被拆开并重建。

## 6. 成本概览

收益是指审查者了解到了什么以及编译器能够利用什么；代价是指实现体量、规范文本、标准库工作量以及被它拒绝的正确程序。“依赖项”则是这些设计自然决定的先后顺序。

| 9 | 终止性 | 循环与算术递归上的“可终止”声明 | 配合 4 和 5，达到 C 语义下的 `const` | 中：对计数循环和单调循环成本低；变体（variants）；对池链接递归无能为力 | 4 |
| 10 | 所有权句柄 | 精确释放一次，无双重释放，无通过引用的过期读取 | 内存池日后可做压缩 | 高：不可复制值类别会波及所有复制操作；句柄容器需要破坏性读取 | 8 的规则；终结器 |
| 11 | 显式 SIMD 类型，或 `par for` 的 SPMD 降级 | 无 | 在自动向量化停止之处使用掩码、洗牌、gather；将迭代作为通道 | 中高：一套类型族与内建函数，或为循环体控制流维护掩码 | 类型：无；SPMD：6 |
| 12 | GPU 内核 | 在 6 之外无额外收益 | 在 map 风格内核上快 10–100 倍 | 高：第二套发射器、布局方案、驱动适配 | 6、`abortfree`、布局决策 |

这张表揭示了三点观察。最廉价的几项（1、2、5、7）彼此独立，也独立于其他一切特性，而仅凭第 2 项在实测速度上的价值就超过除第 6 项之外的任何特性。正确性阶梯（3 → 4 → 9）是顺序推进的，且每一级台阶都是某项速度特性的前置条件（4 是 6 的前置条件，6 是 12 的前置条件），因此在这里正确性正是通往速度的路径，而非争夺精力的对手。而收益最大的安全特性（10）同时也是与其余部分关联最少的一项；它可以先等等看，直到出现第 7 项不足以应对的证据。

<a id="7-order"></a>
## 7. 顺序

1. **证明证书**（[3.6](#36-the-certificate)）与**由根推导的 `restrict`**（[4.1](#41-distinct-roots-as-restrict)）：体量小、相互独立，且立即可通过 `bench/bce_ab.py` 和 MSVC 的 `blur` 行进行测量。
2. 标准库中的 **`gen_pool`**（[5.2](#52-generations-as-a-library)），以及基于它重写的文件树（file-tree）和 LRU 示例，以观察代际检查在基准测试中的开销。
3. **`requires`/`ensures`**（[3.2](#32-contracts-in-the-fact-language-requires-and-ensures)），先从单独的 `requires` 开始（单向约束，复用索引转换判定），随后再实现 `ensures` 和带谓词的事实。将 `bench/klang` 与标准库中的 `checkfree` 函数转换为子句，并检查证明证书是否显示消除了相同的检查。
4. **`pure` 与帧条件**（[3.4](#34-effects-pure-and-frames)），输出为 C 属性；在 `interp` 和 `calc` 行上进行测量，这两项中循环内的辅助函数调用很常见。
5. **`abortfree`**（[3.3](#33-abortfree-no-runtime-check-of-any-kind)），连同库审计以及规范的核心列表。
6. **`par for`**（[4.3](#43-par-for-shared-memory-iteration-proven-race-free)）：先将不相交性判定实现为 `--par-test`，报告基准测试套件中哪些循环符合条件，然后再实现运行时与代码生成。测量 `blur`、`particles`、`mandelbrot` 和 `scene`。
7. **终止性**（[3.5](#35-termination)）：先作为一项分类（证明证书报告 "terminates: counted loops"，无需新语法），变体留待后续支持。
8. **所有权句柄**（[5.4](#54-owning-handles-a-free-is-a-shrink)）：当第 2 步的证据表明代际机制还不够，或程序需要它们所能支持的空间压缩时再引入。
9. **SIMD 类型与 GPU 内核**（[4.4](#44-explicit-simd)、[4.5](#45-the-same-bodies-on-a-gpu)）：在第 6 步之后进行，作为其所允许的循环体形态的后端。

<a id="8-open-questions"></a>
## 8. 开放问题

* **命名。** `checkfree` 已被占用且略有言过其实之嫌；`abortfree`（或 `noabort`）表意准确但偏长；`proven` 则信息量太少。一种可选方案：`checkfree` 成为强承诺（消除所有检查），并取消仅限边界检查的层级，因为没有边界检查的函数通常也没有其他检查，而标准库的转换将能显示这一假设失败的频率。
* **子句语法与命名返回值。** 签名之后的子句在单一返回值时可读性很好；多返回值则需要名称（`-> idx: i64, found: bool`）或位置。命名返回值是对 §7.3 的一项改动，在子句之外还有其他用途（文档、语言服务器），或许值得先做。
* **`export fn` 上的 `requires`。** 是按提案在入口处检查，还是作为注释写入生成的 C 头文件并予以信任？index_types.md §8.3 中的健全性缺陷支持进行检查。
* **`par for` 中的浮点归约。** 是将其排除，还是固定树形顺序与分块数量并接受与串行结果不同的确定性结果？`simd` 的精确性原则主张排除。
* **`pure` 与全局读取。** 提案中的 `pure` 读取全局变量。只读取自身参数的更严格形式 `const fn` 将是可用于编译期求值的形式；问题是同时保留两个词，还是静默推断出更强的那一种。
* **代码块中捕获 `own` 值。** 移入代码块、禁止捕获，还是当高阶函数被证明至多调用该代码块一次时予以允许（效应摘要可以记录这一点）。
* **`own` 数组**，以及对 `own` 连续序列（run）的 `realloc_slice`。
* **相对链接与所有权。** `Node&<u32 in pool>` 链接究竟能否承载义务，还是代际机制本身就是存储链接的永久方案。
* 通过进程内后端对 `pure` 调用进行的**编译期求值**：另文专述。
* 针对有符号算术的 **`nowrap` 层级**，以及发布模式下的回绕语义是否应当继续作为 `abortfree` 代码的语义，或者是否应允许此类代码要求将调试检查证明消除而非跳过。
