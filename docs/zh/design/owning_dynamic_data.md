本文是一份研究示例笔记。其需求是维护一组运行时确定大小、可独立编辑的缓冲区，并在每个文档关闭时回收内存。难点在于以任意顺序进行独立增长和释放，而不在于如何表示字符串列表。标准库 `slice_pool<T>` 通过根拥有（root-owned）存储表达了这一需求。本文展示了该表示方式及其开销、哪些早期变通方案仍然有用，以及覆盖切片池未涵盖场景的两种潜在未来扩展：有界独立动态栈和不透明 API 资源。这两种扩展目前均不是已实现的语言特性。

<a id="the-ordinary-owning-representation"></a>
## 常规的所有权表示

在 C++ 中，核心结构可以是：

```cpp
struct Document { std::vector<std::byte> text; };
std::unordered_map<DocumentId, std::unique_ptr<Document>> open;
```

对应的 Rust 形式是 `HashMap<DocumentId, Document>` 配合 `Document { text: Vec<u8> }`；如果文档对象本身需要稳定地址，`Box<Document>` 则是可选的。这些示例并不保证内部指针在文本缓冲区重新分配后仍然有效。编辑操作可以使用偏移量或临时借用。稳定的内部引用是另一项独立的需求。

例如：打开 A（1 MB），打开 B（20 MB），向 A 追加 5 MB，在 B 保持打开的情况下关闭 A，打开 C（2 MB），扩展 B，关闭 C。这里不存在有用的栈序：分配和释放都是交错进行的。文档日后可能还会拥有撤销历史或词法记号（token），但仅每个文档一个缓冲区就足以暴露这个问题。

<a id="documents-as-runs-in-a-slice-pool"></a>
## 将文档表示为切片池中的连续片段

每个文档是标准库 `slot_pool` 中的一个描述符，其文本是标准库 `slice_pool<u8>` 中的一段连续字节片段。打开的文档列表是指向该描述符池的一组链接（§3.9），这也使得操作可以接收 `Document&`：

```klang
import slice_pool;
import slot_pool;

struct Document { id: u64, text: u8[:] }   // 文档当前的字节连续片段

var docs = slot_pool<Document> {};
var bytes = slice_pool<u8> {};
var open: Document&<u32 in docs.items>?[>..] = [];   // 按标签页顺序排列；在其他地方清理

fn open_doc(id: u64, size: i64) -> Document& {
    let d .= docs.alloc_ref(Document { id: id, text: bytes.alloc_slice(size) });
    open.push(d);
    return d;
}

fn grow(d: Document&, extra: i64) {
    d.text = bytes.realloc_slice(d.text, d.text.len + extra);
}

fn close(d: Document&) {
    bytes.free_slice(d.text);
    docs.free(docs.items.index_of(d));
}
```

紧凑的 `in docs.items` 链接指明了描述符池的数组成员。描述符池和字节池都使用普通的库 API。

`alloc_slice` 会将连续片段放入（按索引顺序）第一个能容纳它的空闲区间，若没有则放在数组末尾。当连续片段位于数组末尾或其后紧跟空闲字节时，`realloc_slice` 会原地扩展该片段；否则，它会将该片段移动到新大小的新片段本应放置的位置，而该位置也可能是片段自己原来的位置。`free_slice` 将连续片段归还给池，并与相邻的空闲区间合并。连续片段新获得的每一个字节都为零。

在上述示例中，A 和 B 首尾相连放置。当向 A 追加 5 MB 时，B 紧跟在 A 之后且没有 6 MB 的空闲片段，因此 A 的 1 MB 数据会被复制到数组末尾。关闭 A 会留下两个空闲片段：A 最初的位置，以及末尾的 6 MB。随后 C 占用这 6 MB 片段的前半部分。此时 B 后面紧跟着 C，因此扩展 B 会把 B 的 20 MB 复制到第一个能容纳新大小的空闲片段。如果增长后的大小能放下，这个位置就是 B 自己原来的位置与前面空闲的 1 MB 合并后的区间；否则，它位于数组末尾，从 C 之后剩余的 4 MB 空闲空间开始。关闭 C 会将其字节与相邻的任意空闲字节合并。

视图（view）保留了池的复用语义（规范 9.4）。在移动或关闭之前获取的切片或字节引用会保留其原有范围，并读取后续分配放入该位置的任何字节；它绝不会越界访问到数组外部。因此，编辑代码在任何可能导致文档增长或关闭的操作之后，都必须重新读取文档的 `text`，并将光标保存为偏移量而非引用。标签页列表中的链接在文档关闭后也以同样的方式继续存活：它仍然读取到一个有效的 `Document`，只是到那时它可能已经变成了另一个文档。

`index_of` 将 `Document&` 转回 `free` 所接收的槽位索引。之所以它能把调用方传入的引用识别为 `docs` 的某个槽位，仅仅是因为某个类型指名了该池（规范 3.9）。没有任何 `T&<w in pool>` 类型指名的池则必须改为四处传递槽位编号；`docs/implementation.md` §10 记录了什么改动可以解除这一限制。

检查器（checker）并不总能判断出从 `docs` 中读出的切片指向哪一个数组。任何其他能容纳 `u8` 的全局变量（例如日志缓冲区）都和 `bytes` 一样是同等合法的候选目标（规范 9.5）。`realloc_slice` 和 `free_slice` 并不要求检查器在静态上知道这一点。当传入它们的切片未能被证明属于 `bytes` 时，会在调用运行时进行检查；除非该切片在元素边界上位于 `bytes` 内部，否则调用会中止（abort）。相比调用本身无论如何要执行的工作，这项检查只是多出几次比较。如果程序需要避免该运行时检查或更早发现无效的池赋值，一种指明所属池的切片类型（`u8[: in bytes]`，类似于 `T&<u32 in pool>`）可以让这一信息变成静态的。

<a id="what-the-slice-pool-costs"></a>
## 切片池的开销

* **所有文档共用一次预留。** 池是位于单个数据栈上的一个只增数组，因此所有文档的总和受限于该栈的预留大小（`K_STACK_RESERVE`，默认为 2 GB；规范 10.4 允许最高 `2^48` 字节）。超出该限制会在保护区触发中止：不存在可恢复的分配失败。
* **数组永不收缩。** 已关闭文档的连续片段会被复用，而数组的高水位长度保持预留状态。对于 `u8` 池，`trim` 会将空闲片段所在的页归还给操作系统（参见下文的“扩展切片池”）；否则这些页会保持已提交（committed）状态。
* **移动会产生复制。** 无法原地完成的增长是 `O(当前长度)` 的，当某个文档后面紧跟另一个文档时，每次小步增长都可能触发复制。是否按倍增因子增长由调用方决定。
* **碎片化。** 放置策略是按索引顺序首次适应（first fit），并在释放时合并相邻空闲块。总空闲字节数足够并不保证存在所需大小的连续空闲片段；在这种情况下数组会增长。我们对比测量了首次适应与最佳适应（best fit）。在所有测量中首次适应都更快。在逐次小步增长的缓冲区上，最佳适应得到的数组最多小 12%；而在混合大小的场景下，首次适应得到的数组反而更小。
* **视图不会跟随移动。** 如上所述，应将位置保存为相对于当前连续片段的偏移量，使其在移动后依然可用。
* **元素类型。** 元素是固定大小的，且 `realloc_slice` 拒绝包含自相对引用（self-relative reference）的元素类型，因为复制之后它们的偏移量仍会从旧位置开始计算（规范 3.9）。
* **单次操作开销。** 放置、增长和释放各自都会遍历一棵空闲区间树，因此其开销随同时存在的空闲连续片段数量的对数增长（`docs/implementation.md` 9.7）。此外，传回一个检查器无法静态确定属于该池的切片还会增加一次范围测试开销。

<a id="the-other-k-representations"></a>
## 其他的 K 语言表示方式

放置规则保持不变。数组仍然不能包含可调整大小的元素（规范 3.4），因此“可增长文档的可增长数组”依然无法表达。循环调用函数（cycle function）在向其调用环发起调用时仍然不能跨调用保留非定长局部变量（规范 7.8）。切片池是语言内的替代方案，取代了几种早期的变通做法：

* 带每文档偏移量的只增字节存储（保留的内存会随编辑历史持续增长，直到整片区域重置）；
* 由应用程序自行管理数据搬移的大型可伸缩缓冲区（现在由池负责放置和移动）；
* 运行时容量受限数组 `u8[..]`（既不能增长，也不能放入槽位池）；
* 指向各自独立作用域内局部变量的引用表（它从未真正拥有任何内存）。

以下方式仍然有用：

| 方式 | 仍然适用的场景 |
|---|---|
| 内联受限数组 `u8[..MAX]`，作为 `slot_pool` 中的固定大小槽位 | 存在真实且较小的上限。不会发生任何复制或碎片化，每个文档就是一个固定槽位。每个槽位都要付出完整容量的开销，且超过上限时无法扩展该缓冲区。 |
| 通过索引或相对引用链接的可复用固定大小分块，例如绳索（rope）或片段表（piece table） | 超大型文档，或频繁在中间插入的场景（连续片段在每次移动时都要整体复制）。分块永不移动，因此指向其中的引用始终有效，增长最多复制一个分块，碎片化也受限于分块大小。它需要分块寻址、跨分块遍历以及陈旧槽位策略，这些可以由库封装隐藏。 |
| 每个文档由一个工作线程拥有 | 本来就需要文档 actor 的场景。内存在工作线程退出时回收，代价是消息协议、每个文档一个操作系统线程，以及跨队列传递数据时的复制开销。 |
| 外部拥有的存储 | 不归本程序所有的内存。下面的方案 C 为其提供了带类型的表示。 |

<a id="future-option-a-bounded-independent-dynamic-stacks"></a>
## 未来方案 A：有界独立动态栈

切片池存在几项限制：元素地址在增长期间可能改变，增长可能复制数据，而且关闭文档时仅能针对 `u8` 池通过 `trim` 按页向操作系统归还内存，且数组本身不会收缩。此外，各文档还会共享碎片，并共同受限于单次预留的总存储上限。

本方案扩展了规范 11.3 中的动态栈构想。它提出一种运行时确定大小的集合，其中每个元素拥有一个独立增长的栈：即可调整大小数组的可调整大小数组。当前的放置规则不允许这样做，因此需要一种新的拥有型容器。其描述符表可以增长或复用槽位，而元素存储则保留在分别预留的地址区域中。

对于受支持的 64 位目标平台，应定义一个虚拟地址预留预算，而不是假设 64 位指针就能提供 `2^64` 个可用字节。运行时配置可以在集合开始接收工作之前先预留好该预算从而提供保证；如果无法获取该预留，则在初始化时报告失败。设每个栈的可用容量为 `R`、保护空间为 `G`、描述符空间为 `H`、预留预算为 `B`，则配置的总栈数必须满足 `N * (R + G) + H <= B`。这是对使用该预算的所有栈的联合上限，而不是为每个容器单独分配的额度。用于撤销历史或词法记号的额外栈也计入其中。

编辑器可以选择最多打开 256 个文档，每个文档的文本上限为 1 GiB。这需要大约 256 GiB 的预留虚拟地址空间加上保护区和元数据，而不是 256 GiB 的常驻物理内存（RAM）。只有当目标平台能够保证该预留时，这种配置才可用。对于数量有界的大型缓冲区，这是一个合理的权衡；大量小型缓冲区则仍应放入切片池。

* **打开与增长：** 打开第 257 个文档会返回一个可恢复的限制错误，编辑器可以向用户解释原因。超出文档字节上限的增长同样会在修改其内容之前失败。显式配置的边界支持主动检查，而不必依赖溢出保护区来中止进程。地址预留并不保证物理内存可用；提交（commit）策略必须单独定义内存分配失败时的行为。
* **稳定数据，可移动拥有者：** 在内层栈的预留范围内增长可以保持其元素地址不变。移动拥有者描述符或扩展外层表都不必移动这些数据。如果槽位可以被移除和复用，外层表索引就不能作为永久的文档标识；应使用稳定句柄或其他显式的身份策略。
* **引用安全：** 与切片池不同，关闭文档会释放其存储空间，因此在指向该文档的引用或切片仍可能被使用期间，必须禁止关闭。检查器需要跟踪内层拥有者的生命周期，而不仅仅是外层表的生命周期。一种保守的初步设计是仅允许通过文档句柄的作用域借用进行访问；借用整个集合更简单，但会限制无关文档的关闭操作。精确的按文档借用需要进一步的方案设计。句柄上的代际（generation）检查可以防止陈旧句柄复用，但无法保护已逃逸的原始切片。
* **释放：** 关闭文档会解除对其内存页的提交，并独立于其他文档回收其区域槽位。保留地址预留使运行时能够保证预算的复用；只有当其所属集合或运行时预算结束时，预留本身才会被释放。释放一个文档的存储不会导致任何其他文档的存活数据被复制。

两者可以结合使用：由本方案提供的栈可以各自支撑一个切片池（例如按文档类别各建一个），从而将稳定的大缓冲区与池化的小缓冲区结合起来。遗留问题包括：每栈预算与池化总预算的权衡、拥有者描述符的转移规则，以及检查器在不引入繁重注解 API 的前提下能提供多高精度的按文档生命周期分析。固定的大小与数量上限是本方案契约的一部分，而不是一个需要隐藏的意外失败模式。只有当切片池的实测结果表明复制开销、保留内存或单预留上限确实成为瓶颈时，投入这方面的检查器工作才值得。

<a id="future-option-c-opaque-api-resources"></a>
## 未来方案 C：不透明 API 资源

引入一种固定大小的 `resource<U>` 值（内部为 `u64`），用于表示任意 API 指针和句柄，例如 GPU 缓冲区、原生字节缓冲区和文件映射。`U` 是由绑定定义的标签，用于标识资源种类。由绑定负责创建并解释这一不透明表示，无论它内部持有的是原生指针、原生句柄，还是绑定自身维护的某张表中的条目。

资源可以存放在任何允许固定大小值的地方：局部变量、全局变量、聚合体字段、数组元素、参数和返回值。它在 K 中的操作仅限于复制/存储该值，以及将其传递给接收兼容资源类型的 API。代码不能对其进行解引用、对它执行算术或比较运算，也不能将其与普通整数相互转换。复制该值只会复制这个不透明句柄，本身并不会复制底层的原生分配。标签可以防止混用不同种类的资源，但原生资源的生命周期和 API 有效性仍然需要由绑定定义的规则来保证。

例如，GPU 绑定可以返回 `resource<GpuBuffer>`，并在上传、绘制和释放操作中接收它。字节缓冲区绑定可以通过 `resource<ByteBuffer>` 提供分配、调整大小、释放以及批量读写或复制操作。随着切片池已进入语言标准库，这种方式不再是获取独立增长的 K 缓冲区的手段；它的用途是持有归属于外部的内存和对象，并通过函数和复制进行访问。当程序需要直接数组索引、切片和常规的 K 元素引用时，切片池和方案 A 仍然是更好的选择。

现有的 FFI 已经可以将标量句柄和 K 缓冲区传递给 C，其中包括允许 C API 向其中追加复制字节的构建器（builder）。所提议的带标签资源类型为该接口增加了一种不透明表示；它并不是一种用来把原生指针直接当作 K 引用来使用的已实现机制。

文件映射绑定是另一个例子：映射操作可以返回一个 `resource<FileMapping>`，并配套提供 API 函数来查询它、将某个范围复制到 K 缓冲区中以及解除映射。常规的可增长 K 数组使用运行时自己预留的地址区域；当前运行时不会把文件映射到这样的数组中。因此，持有一个映射资源并不会自动使映射的字节变成 K 数组或切片。直接映射视图需要一套单独的设计，将其边界和生命周期与该资源关联起来。

**清理机制尚未确定。** 绑定或许可以可选地提供清理函数，在局部资源离开作用域时运行；这一机制是否以及如何扩展到聚合体内部的资源也尚未定论。还有几个问题仍未解决：哪些复制操作会触发清理、显式释放后的别名该如何处理、如何防止重复清理或双重释放（double-free），以及聚合体复制意味着什么。该提案目前尚未承诺提供 RAII、析构函数或自动所有权转移。在赋予清理钩子可靠的语言语义之前，必须先解决这些问题。

<a id="extending-slice-pools"></a>
## 扩展切片池

除了上述两种方案外，还有一些更小的改进步骤，各自针对前文提到的某一项开销：

* **指明所属池的切片类型**，如前所述，将传回切片时的运行时检查转化为静态检查。
* **可恢复的分配：** 提供一种 `alloc_slice` 和 `realloc_slice` 的形式，当预留空间无法容纳请求的连续片段时报告错误而非直接中止，并保持原连续片段完好。
* **归还空闲内存：** 可以解除空闲区间内部整页的提交，并在下次访问时以清零状态重新提交。陈旧视图仍然可能读取这些页，因此仅当元素类型的全零字节本身就是合法值时（例如 `u8`）这一操作才是可靠的；包含非可选引用的类型不满足该条件。当程序显式请求时，`trim(pool: slice_pool<u8>&)` 会为 `u8` 池执行这一操作，就像 `trim_memory` 对栈顶所做的那样。其他零字节合法的元素类型也可以跟进：固定大小、不包含索引或边界类型，且不包含非可选引用（包括自相对引用）。可选相对引用将偏移量 0 视为 null，但非可选的自相对引用没有 null 哨兵：偏移量 0 表示其自身字段的地址（规范 §3.9），因此被清零的该引用会把自己的偏移量字段当作一个 `T` 来引用。
* **每池独立预留：** 将池放在具有自身大小上限的栈上，或放在方案 A 提供的栈上。
* **重定位自相对引用：** 跟踪相对引用所跨越的区域（规范 TODO 16），从而允许一组相互链接的连续元素作为一个整体移动。

## 评估剩余问题

既然切片池已经实现，应先针对切片池运行“打开/编辑/关闭”序列。分别测量存活字节数、数组的高水位长度与已提交字节数、复制的字节数以及延迟。测试场景应包括反复的碎片化增长与释放、超出预留上限的文档，以及在移动、关闭和复用之后读取旧视图。这些测量结果将决定在哪些场景下，方案 A 所提供的稳定且可释放的存储足以证明引入额外生命周期分析是值得的。对方案 A 的评估还应涵盖第 257 个文档、超出大小上限的文档，以及跨文档关闭持有的引用。对于方案 C，则在保持“清理策略尚未确定”这一前提明确可见的同时，评估 API 缓冲区传输与文件映射访问。
