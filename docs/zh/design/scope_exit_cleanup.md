研究笔记，2026 年 10 月。在本文所述内容中，`defer`（3.1）已按第 6 节的建议配合 `exception::try` 的 `finally`（3.5）完成实现；池终结器（pool finalizer）、作用域限定分配（scoped allocation）、`errdefer` 与析构类型（destructor type）尚未实现。本文探讨的问题是：K 语言是否应当在作用域结束时运行代码，如果是，应当采用其他语言已经定型的哪种形式——显式的 `defer` 语句、类型上的析构器，还是某种契合 K 自身池机制的形式。

<a id="1-where-k-stands"></a>
## 1. K 语言当前的立场

K 语言仅通过作用域退出释放内存。规范对此有明确说明：“除返回移动（return move）外没有所有权转移，没有析构器，没有 `Drop`，没有引用计数。内存释放完全依靠作用域退出时重置栈指针”（§4.1）；教程更将其作为一项特性加以强调：在右花括号处“不会运行任何析构器，不会遍历任何链表。‘释放’该缓冲区的代价仅仅是一次存储操作。”语言中的另外两个部分也建立在同一个事实之上：

* `return … from`（§7.9）不需要栈展开器（unwinder），因为它离开的每一个栈帧都没有需要销毁的东西：每个中间栈帧只需恢复其水位线（watermark）并返回一个哑值（dummy value），其尾声（epilogue）不再做任何其他事情。
* `exception` 模块不提供 `finally`（[stdlib.md](../stdlib.md#exception)）。清理回调可以在正常完成或捕获抛出后运行，但块内的词法 `return` 或指向该辅助函数外层的 `return … from` 会直接穿过它而离开，什么也不会运行，因此库辅助函数无法保证在每一次退出时都执行清理。只有语言本身才能做出这一保证。

[owning_dynamic_data.md](owning_dynamic_data.md) 对其提议的不透明资源留下了这个开放问题：“清理机制仍未解决。”

自那以后，两类并非内存、却确实需要释放的事物在 K 程序中变得司空见惯：池槽位与连续片段（`free`、`free_slice`，规范 §5.4），以及来自 graphics、audio、physics 和 ui 包的原生句柄（`release`、`destroy`、`close`）。如今这两者都靠手动释放，而示例程序既体现了这所需的纪律性，也暴露了容易疏漏的地方（第 5 节）。

<a id="2-what-needs-cleaning-up"></a>
## 2. 需要清理的内容

需要清理的事物有三类，忘记释放它们会带来不同的后果：

1. **池存储（Pool storage）。** 未归还的槽位或连续片段（run）会一直保持已分配状态，直到池所在的作用域结束。这不会引发不安全问题，只是让池不断增长。成对的操作包括 `alloc_index`/`alloc_ref` 与 `free`，以及 `alloc_slice` 与 `free_slice`。棘手的情况在于嵌套分配：一个池中的节点拥有另一个池中的连续片段（[26_file_tree](../../../samples/26_file_tree.k)），或字节池中的两个字符串（`bench/kostya/klang/src/cache_simulation.k`）。
2. **原生资源（Native resources）。** 指向 C 侧的句柄：GPU 缓冲区或纹理、音频、物理世界或刚体、UI 上下文。忘记释放会导致 GPU 或库内存泄漏，直到该包的 `close()` 被调用或进程结束。这些句柄带有代际（generation）信息，因此使用已释放的句柄会作为误用被报告出来，而不会导致崩溃；但忘记释放则会静默发生。`os` 模块完全没有句柄：每个文件操作都是整文件读写（`read_file`、`write_file`、将 `list_dir` 写入构建器），这是库在设计上刻意规避该问题的最明显标志。流式文件访问、套接字或子进程都会让这个问题重新出现。
3. **待恢复的状态（State to restore）。** 在某段作用域期间被修改的全局变量或字段：嵌套深度、绑定的管线（pipeline）、当前工作目录。如今必须在作用域的每一处退出路径上手动恢复它，或者把代码组织成只有单一出口的形式。

以下内容不需要清理：任何种类的内存、字符串、字典及其他库容器（其内容均为值）、线程（工作线程返回时会释放其存储，并通过 `thread_wait` 汇合）以及队列。

<a id="3-design-options"></a>
## 3. 设计方案

<a id="31-defer"></a>
### 3.1 `defer`

一种语句，其语句体在封闭块结束时运行：

```klang
fn load_level(path: u8[:]) -> Level {
    let f = os::open(path);                       // 假设的句柄 API
    guard f.id != 0 else { return Level { .. }; }
    defer os::close(f);
    let header = read_header(f);                  // 此处可能触发 `return … from`
    return parse_body(f, header);                 // close 在主体构建完成后运行
}
```

拟议语义：

* **绑定到块，而非函数。** 这是 Swift 和 Zig 的规则，而非 Go 的规则。语句体在 `defer` 所在的代码块结束时运行，无论以何种方式结束：顺序执行到块尾、`break`、`continue`、`return`、代码块通过高阶函数进行的词法返回，或穿过当前栈帧的 `return … from`。循环体内的 `defer` 在每次迭代时运行一次。在 K 语言中，代码块已经是所有权的基本单元，因此清理理应与它所配对的存储绑定在一起；Go 中绑定到函数作用域的 `defer` 写在循环里，正是该语言最广为人知的陷阱。
* **仅执行已走过的 `defer`。** 某条退出路径只运行其所离开的各个作用域中位于该退出点文本之前的 `defer`，按后进先出（最新声明先执行）的顺序执行。这与代码生成器当前用于水位线恢复的规则一致（“每条退出路径只恢复它经过的声明的水位线”，`src/codegen_stmts.h`），这也意味着任何退出点处的待执行 `defer` 集合在编译期即可确定，无需运行时链表。
* **在退出时求值。** 语句体就是延后执行的普通代码；它看到的是变量在退出那一刻的值。Go 在执行 `defer` 语句时就提前对被延迟调用的参数求值，这需要开发者额外记一条规则，因此这里不采用。
* **在返回值之后、存储释放之前运行。** 在执行 `return` 时，返回值会先在其目标位置构造完成（§7.3），随后运行 `defer`，最后才释放作用域的栈存储。因此 `defer close(f); return read(f);` 会先完成读取再关闭，且 `defer` 可以读取当前作用域内的局部变量。
* **语句体不能离开作用域，且不得包含远距返回（long-distance return）。** 语句体内不得有离开自身的 `return`、`break` 或 `continue`，也不得包含 `return … from`、`exception::throw` 或其 `return` 指向外层函数的尾随块。更进一步地说，它还不能调用任何在调用链下方*包含*远距返回机制的函数——包括捕获点（catch），哪怕该函数完全在自身内部抛出并捕获异常。第 4.3 节说明了为什么需要这条更严格的规则以及如何放宽它；编译器只需按调用图顺序计算一个传递标志即可完成检查。语句体可以中止（abort）。
* **不得写入正在被返回的值。** 语句体不得写入函数中任何 `return` 所返回的局部变量，也不得写入扎根于该局部变量的存储（第 4.3 节）。只读访问是无害的。
* **不能用于函数外部。** 全局变量没有作用域退出。在顶层或全局变量初始化器中编写 `defer` 属于错误。
* **语法。** `defer <statement>;` 和 `defer { … }`。`defer` 可以像 `from` 一样作为上下文关键字：在语句开头，若其后紧跟 `{` 或表达式，在当前语法中并不构成合法语句（尾随块前面必须有函数调用的圆括号）。作为保留字则读起来更直白，也与 `guard` 一致；两种方案都可行。

`defer` 将释放代码放在获取代码旁边，并确保在每一处退出路径上运行——包括作者未显式写出的退出路径（例如被调用方触发的 `return … from`）。它不改变所有权本身：在一个函数中创建而在另一个函数中释放的资源，或存放在数组元素中的资源，不受其影响。

<a id="32-destructor-types"></a>
### 3.2 析构类型

这是 C++ 和 Rust 的做法：由类型声明其值消亡时要执行的操作，编译器在该值生命周期结束时自动调用。“生命周期结束”的含义完全取决于所有权：必须有且仅有一个拥有者来运行析构器。而 K 的值语义恰恰在这里形成阻碍。句柄是固定大小的结构体 `struct Texture { id: u32 }`，而固定大小的值可以自由复制：赋值、按值传参、压入数组、存入字段。“在 `Texture` 离开作用域时释放它”会在第一次复制时导致双重释放。

因此，析构类型必须是**不可复制（non-copyable）**的。K 语言已经具备相应的机制，因为非定长值本来就是不可复制的：它们在引用类型目标处按引用绑定，而在值类型目标处若无显式 `copy` 则会报错（§4.1，按大小类别传参）。析构类型可以保留其固定大小内存布局，但在复制行为上按非定长值对待。它只能就地构造在最终存放的位置（作为右值进入 `let`、`push` 或字段初始化器），在其余所有地方都按引用绑定；调用 `copy()` 会报错；而返回移动（return move）是离开作用域的唯一途径。这样一来，每个值都有且仅有一个存储位置，析构器就在该位置消亡时运行：

* 局部变量或按值传递参数的作用域退出；
* 从数组中移除：`pop` 会将值移出，但 `pop_n`、`resize` 缩容、`clear`、可增可缩数组（grow-shrink array）的收缩，以及池的 `free`、`free_slice` 和缩容的 `realloc_slice` 都会销毁被丢弃的元素；
* 对 `var`、字段或元素的重新赋值；
* 持有它们的容器消亡：对元素进行遍历——这将成为 K 语言中首个 O(n) 复杂度的作用域退出。

这一收益是实打实的：忘记释放将变得不可能，而且清理行为可以组合进容器中。存放于区块数组里的 `struct Mesh { vertices: Buffer, indices: Buffer }` 会在数组释放或某块被覆盖时自动释放自身。第 4.7 节列出了其代价。简而言之，该特性会触及检查器中的每一条目标规则、每一个复制或丢弃元素的内建操作、被退出路径放弃的局部结果、线程与队列、序列化，以及建立在纯值语义之上的标准库容器。

<a id="33-pool-finalizers"></a>
### 3.3 池终结器

池终结器（pool finalizer）是绑定到池槽位而非绑定到值本身的清理机制。其背后的想法是：仓库中真正别扭的手动释放都是嵌套式的——释放一个槽位时，还必须一并释放该槽位元素在另一个池中所拥有的内容。池在声明时即可指明归还槽位或连续片段时要对元素执行什么操作：

```klang
reusable var nodes: Node[>..] = [] { runs.free_slice(it.entries); };
```

编译器会在 `free(i)` 将槽位放回空闲链表之前、在 `free_slice(s)` 对连续片段的每个元素执行释放时，以及在 `realloc_slice` 收缩丢弃元素时调用该语句体。也可以选择在局部池的作用域结束时，为每一个存活槽位运行该终结器；全局池永远不会结束。存活集合就是不在空闲链表中的所有槽位。要找出这些槽位，槽位池（slot pool）可以为每个槽位维护一个已释放标记位或将空闲链表排序一次；切片池（slice pool）的空闲链表本身就是按索引排序的区间树，因此遍历空闲区间之间的空隙非常自然。对于存放原生句柄的池来说，退出遍历才是拥有终结器的主要意义。而对于一个终结器仅仅是释放另一个同生共死池中片段的池来说，退出遍历纯属多余工作，声明时可以注明无需该遍历。

有两点性质使它比析构类型代价低得多。首先没有复制问题，因为钩子在槽位被释放时直接作用于槽位里的字节，无论该元素在其他地方还有多少副本；残留的副本或索引本就是 §5.4 所允许的类型安全陈旧引用。其次不需要引入新的值类别或复杂分析：它本质上只是包在 `free` 外面、编译器不允许程序绕过的一层包装函数，而如今程序只能靠人为自律做到“总是调用 `release_node`，绝不直接调用 `nodes.free`”。

难点在于上下文。终结器往往需要向另一个池中释放资源，因此该目标池必须能被终结器访问到。当子池像 `26_file_tree` 中那样是全局变量时，普通函数就能胜任。当它像 `cache_simulation` 中的 `strings` 那样是通过参数传下来的局部变量时，终结器就必须捕获它。上述尾随块写法正好能做到这一点：块可以使用封闭函数的局部变量（§7.6），而池正是某个函数的变量。池引用参数在地址旁边已经附带了空闲链表，终结器的环境也可以用同样的方式一并传递。由于调用方按根（root）特化，这个钩子在静态上通常是已知的；而可能指向多个池之一的池引用，则会要求这些池共用同一个终结器。

终结器覆盖不到的情况包括：保存在局部变量中的句柄、状态恢复，以及任何不在池中的东西。它是在 `defer` 之外需要学习的第二套机制，两者仅在“池元素同时也是某个局部变量的责任”时有所重叠。

<a id="34-scoped-pool-allocations"></a>
### 3.4 作用域限定池分配

针对“在本作用域内分配、在作用域结束时释放”的场景，可以提供一种由编译器自动生成 `defer` 且由检查器禁止逃逸的语法形式：

```klang
scoped let s = pool.alloc_slice(n);     // 本块结束时自动释放；不可逃逸
```

来自 `alloc_slice` 的切片原本精确扎根（root）在池上（§5.4，§9.2）。作用域限定形式则会改为让它扎根在声明它的变量上。其余一切都可以由现有的检查器直接完成：存储规则会拒绝把该切片保存到任何寿命超过当前作用域的位置，返回规则会拒绝将其返回，分支值规则会拒绝将其传出分支，而被传入的函数会针对该根进行特化并受到相同的检查。手动对其调用 `free_slice` 会成为编译错误，因此不会出现双重释放。编译器在作用域各退出点生成 `free_slice`，方式与 `defer` 完全相同。`alloc_ref` 可以采用同样的处理方式；`alloc_index` 则不行，因为普通整数可以自由逃逸，这也是 §5.4 本身已经接受的唯一缺口。

对于“在局部场景中自动清理可复用数组内的分配”，这是最贴合 K 语言的答案，而且不需要检查器之外的任何新分析。唯一待定的问题是作用域限定连续片段的 `realloc_slice`，因为这会移动片段：要么直接禁止并报错，要么规定返回的结果同样受作用域限定且必须赋回给原变量。

<a id="35-library-helpers-on-top-of-defer"></a>
### 3.5 基于 `defer` 的库辅助工具

一旦 `defer` 能在传播路径上运行，如今库里无法安全编写的辅助工具就变得完全可靠了：

```klang
fn with_pass<F>(target: Texture) { begin_pass(target); defer end_pass(); F(); }

fn try<E, Body, Catch, Finally>() {
    defer Finally();
    for error in handler<E>(Body) { Catch(error); }
}
```

无论 `Body` 是正常结束、抛出异常并被捕获、抛出并逃逸到外层处理器（穿过当前栈帧的传播），还是执行词法 `return` 离开 `Body`（同样是穿过当前栈帧的传播），`Finally` 都会运行。这正是 stdlib.md 中解释自己无法提供的那个 `finally`。那里的说明可以随之修改，`exception::try` 也将获得该重载。`Finally` 的语句体本质上是一个 `defer` 语句体，遵循相同的规则：不能抛出异常，也不能调用内部使用了异常的任何函数（3.1，4.3）。

<a id="36-only-on-failure"></a>
### 3.6 仅在失败时执行

Zig 的 `errdefer` 仅在作用域因错误而离开时运行。K 语言在编译期就能区分这两种情况：“因错误离开”就是有远距返回穿过当前帧，而代码生成器已经为它单独生成了路径（`PropagateReturn`）。一种仅在该路径上运行的 `defer` 变体，可以让构建器无需借助标志位和第二个退出点，就能撤销构造到一半的结构（例如释放子节点解析失败的父节点）。一旦有了 `defer`，这将是一个很小的补充。目前仓库中还没有代码提出这种需求。

<a id="4-consequences-for-the-implementation"></a>
## 4. 对实现的影响

本节大部分内容围绕 `defer` 展开，因为它是基础原语：终结器或作用域限定分配本质上都是编译器代写的 `defer`，而析构器则是施加在每个存储位置上的 `defer`。第 4.7 节列出了析构器形式在此基础上额外增加的工作。

<a id="41-how-exits-are-emitted-today"></a>
### 4.1 当前如何生成退出路径

代码生成器在 `src/codegen_frames.h` 中维护了一个作用域栈 `CScope`。凡是需要数据栈存储的声明，都会在需要恢复该栈的对应作用域中记录一组 `(stack, saved top)` 对（`SaveBase`）。`EmitRestores` 按后进先出顺序生成单个作用域的恢复代码，`EmitExitRestores(to)` 则生成直到 `to` 为止所有作用域的恢复代码。走出作用域的每一条路径都会经过它们：

| 退出方式 | 位置 | 发生的操作 |
|---|---|---|
| 顺序执行到块尾 | `PopSc` | 执行恢复 |
| `break` | `GenBreakPath` | 先构建退出值，再执行直到循环或块的恢复代码，然后 `goto` |
| `continue` | 循环代码生成 | 恢复它所经过的声明，然后 `goto` 到放置于顺序恢复代码之后的标签 |
| `return` | `Epilogue` | 值已处于目标位置；执行 `EmitExitRestores(0)`，刷新缓存的栈顶，恢复 `return … from` 的目标记录，执行 C `return` |
| 远距返回穿过的栈帧 | `PropagateReturn` | 同上，随后返回哑 C 值 |
| `return … from` 触发点 | `GenFromReturn` | 将值写入目标的通道（channel），然后进入 `PropagateReturn` |
| 调用后的捕获点 | `EmitRfCheck` | 将传递中的值存入调用方的目标位置，然后进入 `Epilogue` |

对于持有开放存储的块，若要带值退出，会先在已有存储上方构造该值，完成恢复后再将其向下移动（`ScopeTop0`、`DstTop0`，implementation.md §6.5）。类型检查器早已移除了已证实退出之后的语句，而 `termjump` 会在退出后停止继续生成代码。

<a id="42-a-defer-is-a-scope-entry"></a>
### 4.2 `defer` 作为作用域条目

最自然的实现方式，是让 `CScope` 将延迟语句体保存在与水位线保存记录同一个有序列表中，并让 `EmitRestores` 逆向遍历该列表：遇到语句体就生成该语句体，遇到保存记录就生成栈顶存储恢复指令。这样一来，上表中的每一条退出路径无需额外改动，就能以正确顺序运行正确的 `defer`；而“仅执行已走过的 `defer`”这一规则，也会随着列表在语句生成过程中逐步构建而天然成立。逆序执行同时确保了每段 `defer` 语句体都运行在它前面各声明的存储被释放之前，而这些声明正是该 `defer` 能够引用的存储。

内联和函数值（function value）不需要引入新机制。内联调用会变成一个 `InlineBlock`，其中的 `return` 会退出该块（`Return::CgStmt`，implementation.md §4）。函数值的语句体会被直接拼接进调用方，其局部变量视作普通局部变量（`EmitFvCall`，§6.6）。`const for` 会为每次迭代复制其语句体。在这三种情况下，`defer` 最终都会落入封闭函数的一个普通作用域里。

<a id="43-return--from-and-block-returns"></a>
### 4.3 `return … from` 与块返回

三个关键位置本就各自独立，因此其行为定义十分清晰：

* **中间栈帧**在 `PropagateReturn` 中运行其 `defer`，此时传递中的值已经放入目标的通道中。非定长值位于目标的目标栈（destination stack）上，从调用点到目标的整个动态生命期内该栈都处于使用中集合（in-use set，§10.3）：中间的任何栈帧都不能在那里拥有数据，这些栈帧中的 `defer` 语句体所分配或调用的任何内容也同样不能。定长值则位于按目标区分的线程局部通道中。因此 `defer` 语句体不可能干扰传递中的返回值。
* **目标栈帧**在捕获点运行其 `defer`，即在 `EmitRfCheck` 将值存入目标位置之后所生成的 `Epilogue` 中运行，因此返回值在它们运行之前就已经完整就绪。
* **发起返回的函数**在 `GenFromReturn` 将值构造进通道之后运行自身的 `defer`，这与普通 `return` 的行为完全一致。

代码块通过高阶函数执行的词法返回使用的是同一套机制，行为也完全相同：编写该代码块的函数就是目标。

唯一可能出问题的情况，是**当一个远距返回正在传递途中时，又有任何远距返回机制运行**。如今在 `return … from` 与其捕获点之间，除了尾声之外不会执行任何代码，传播状态正是依赖这一前提：`k_rf` 是单个线程局部标志，而通道则是按目标划分的。中间栈帧里的 `defer` 语句体恰恰运行在这个窗口期内。

如果一个延迟语句体自身执行或传播了远距返回，就会覆盖正在传播中的标志。它自己的传播过程会在当前栈帧的 `PropagateReturn` 内部再次启动。

**内部自足（contained）的抛出**同样会覆盖该标志。如果一个被调用方在内部既抛出又捕获异常，由于它不向外传播，其 `hasrf` 为 false。但它的抛出依然会改写 `k_rf`，而它的捕获会将其清零（`EmitRfCheck` 会在传播结束处设置 `k_rf = 0`）。结果该中间栈帧结束 `PropagateReturn` 时，`k_rf == 0`。它的调用方于是看不到传播状态，把哑返回值当成真实结果接收下来，而且不会报任何错。举例来说，如果 `close` 在下三层调用里用到了 `exception::try`，`defer close(x)` 就会悄无声息地被错误编译。

此外，如果某个被调用方重入了正处于挂起状态的返回目标，一旦它内部的返回被触发，同样会覆盖该目标的 `k_lret` 和 `k_fval` 通道。基于这些原因，仅仅禁止调用向外传播的特化版本是不够的。

这正是 C++ 中“析构函数不得抛出异常”的对应问题；但与 C++ 不同的是，它可以做成编译期规则，且有两种严格程度可选：

* **完全无 Rf 的语句体（Rf-free bodies）。** 语句体不得包含、也不得传递调用任何触及 `return … from` 站点或捕获点（无论是向外传播还是内部自足）的函数。这只需在 `hasrf` 旁增加一个标志位，并像 `hasrf` 一样按调用图顺序计算（处于递归环路中的函数待环路迭代收敛后即可确定该标志，调用进入环路的语句体随后即可接受检查）；若在编写语句体处违背此规则，直接拒绝编译并指出引入该机制的被调用方。如此一来，嵌套传播和重入正在传递的目标在构造上就变得绝无可能，且两者交互无需任何运行时状态：传播期间除尾声外不执行任何代码，而 `defer` 本身就是尾声的一部分。缺点是清理代码不能调用内部使用了异常的代码。
* **保存与恢复（Save and restore）。** 另一种做法是在每个 `defer` 语句体执行前后保存、清零并恢复 `k_rf`，从而允许使用指向*其他*目标的内部自足 try/throw，因为它们的通道彼此独立。但这仍无法覆盖语句体重新进入正处于传递中目标的情况，因为那样会覆盖该目标的通道。要覆盖那种情况，要么连同该目标的通道一并保存（运行时根据 `k_rf` 选择目标），要么在静态上检查语句体内部可达的目标集与可能穿过当前栈帧的目标集互不相交。在两种严格程度下，向外逃逸的传播都必须保持禁止，否则就会在一个 `PropagateReturn` 内部启动另一个 `PropagateReturn`。

应当先交付第一种严格规则；若在实际清理代码中发现它过于严格，再放宽为第二种。如果没有这两条规则之一，那么 `return … from` 的合法性规则（“包含它的函数的每一次调用都必须位于目标的某次调用之内”）就还必须把 `defer` 当作每条退出路径上的调用点；而只要采用其中任一规则，就无需如此。

**具名返回值。** 被返回的局部变量从声明之初就直接放置在目标位置（保证 NRVO，§7.3），因此在 `return x` 之后，该局部变量的字节就已经是调用方的返回值，且尾声也已经把它的元素计数写入了接收端头部。如果 `defer` 随后再向 `x` 执行 push，就会改变调用方收到的内容，并与已记录的长度产生不一致。因此需要规定：语句体不得写入任何 `return` 所返回的局部变量，也不得写入扎根于此类局部变量的存储；检查器的根信息可以识别这两者。这条规则最简单的实现形式是干脆禁止在 `defer` 中提及此类局部变量。也可以放宽为允许读取，但这就要求 NRVO 分析（它原本要求 `return` 是该局部变量的最后一次使用）学会识别 `defer` 中的读取不会妨碍就地放置。

<a id="44-checking-the-body"></a>
### 4.4 检查语句体

`defer` 语句体是一个代码块，按“仿佛写在所在作用域末尾”的方式进行检查：

* **栈分配。** 其临时变量的索引排在作用域末尾所有存活变量之后。如果在编写 `defer` 的位置就分配索引，之后声明的局部变量可能会拿到相同的索引（`AllocStk` 会分配最低的空闲索引），导致两者在退出时同时存活。`return` 的目标栈此时已经处于调用方的使用之中，因此 `defer` 语句体的临时变量不能放在该目标栈上。
* **生命周期与效应。** 在作用域末尾，该作用域内的每一个局部变量都处于存活状态，这是任何更早退出点存活集合的超集；因此在末尾处检查能够对更早的退出点保持存储、收缩和增长规则的保守安全性。语句体的写入和增长效应与其他任何语句一样并入函数的效应摘要。
* **可达性。** 一个无法正常结束（会中止）的语句体会令该作用域的每条退出路径也随之中止；`mayreturn` 按普通调用的方式进行组合。
* **前端。** 新增一种语句节点类型、对应的语法错误恢复、LSP 的大纲与悬停提示（`src/lsp_analysis.h`）、tree-sitter 语法与 VS Code 高亮规则，以及 reference.md 附录 A 中的关键字列表。
* **测试。** 针对每种退出路径的执行测试夹具（fixture），包括穿过带有 `defer` 的栈帧进行的块返回与 `return … from`；针对每项语句体限制的拒绝编译测试夹具。

<a id="45-code-generation-and-the-optimizer"></a>
### 4.5 代码生成与优化器

* **缓存的栈顶**（implementation.md §6.10）。包含函数调用的 `defer` 语句体在每条退出路径上都是一个调用点。`Epilogue` 和 `PropagateReturn` 原本就已经会刷新缓存。位于栈顶被缓存在局部变量中的循环内部的 `break` 或 `continue`，若语句体可能访问该栈（`SyncReach`），则会多出一次刷新和重新加载。这项代价不大，且仅出现在使用了 `defer` 的函数中。
* **代码体积。** 每条退出路径都会在文本上复制一份 `defer` 语句体，这与 C++ 处理析构函数的方式相同。如果日后代码体积成为问题，标准替代方案是每个作用域只生成一段带有一个小巧“下一步去哪”变量的清理标签；由于 `defer` 语句体大多只有一行调用，初期采用直接复制是最合适的做法。
* **尾递归**（`src/optimize_tre.h`）。累加器重写会将 `return E op self(args)` 改写成循环。当该 `return` 外围的作用域中有 `defer` 时，语句体必须在递归调用返回之后运行，而循环无法做到这一点，因此这类特化版本会被排除在该重写之外。任何其他形式的尾调用优化也会遇到同样的排除条件。
* **内联**已由 4.2 覆盖；阈值统计应当只计算一次延迟语句体的节点数，而不是按退出路径次数重复计算。
* **`--unsafe-no-rf-check`**、JIT 后端以及 Wasm 计划均不受影响：最终生成的仍是纯 C 代码。

<a id="46-what-never-runs-them"></a>
### 4.6 永远不会运行清理的情况

`abort`、失败的 `assert` 或边界检查、`exit(code)` 以及触发保护页（guard-page）都会直接结束进程，由操作系统回收文件和 GPU 对象。受限工作线程（contained worker）中的中止会通过 `setjmp`/`longjmp` 返回到 `k_run_contained`（`src/runtime/runtime_threads.h`），直接丢弃工作线程的栈帧而不运行任何清理代码，因此 §11.2 中关于“它通过 `extern fn` 打开的资源将继续保持打开状态”的陈述依然成立。在 `main` 返回时仍在运行的工作线程会被直接杀死。全局变量永远不会退出作用域：保存在其中的资源由 `main` 中的代码释放，或随进程结束而回收。这些行为与 Go 或 Zig 中的 `defer` 没有任何区别，只需在特性文档中如实写明即可，而不应试图绕过它。

<a id="47-what-destructor-types-would-add"></a>
### 4.7 析构类型会额外增加的内容

在以上所有内容之外，按工作量大致排序如下：

1. **一种新的值类别。** 不可复制的固定大小值，这意味着要扩展 §4 中的每一条目标规则以及检查器的大小类别处理逻辑：声明、参数、push、字段、元素、字面量、分支值、函数值结果、派发结果、`copy`、`default`。
2. **每次移除时的销毁。** `pop_n`、`resize`、`clear`、可增可缩数组的收缩、对变量、字段和元素的重新赋值、池的 `free`、`free_slice` 和缩容的 `realloc_slice`，以及容器的消亡（即遍历销毁）。泛型代码必须按每个特化版本正确行事：`dictionary<K, Texture>` 必须在移除、清空和覆盖时执行销毁，而标准库容器此前都是按普通赋值（`slots[i].val = v`）编写的，因此每一个都需要审计。
3. **被放弃的局部结果。** 在目标位置只存放了一部分值时发生退出，会放弃这一部分内容（§7.3，退出）。若一个构造到一半的 `Texture[>..]` 具名返回值被被调用方触发的 `return … from` 所放弃，除非退出路径销毁已经完成的那一段前缀，否则其元素就会泄漏。这将引入一个新的代码生成点，且该生成点必须知道当时已经完成了多少个元素。
4. **所有按字节复制的地方。** 线程参数、队列元素、`to_bytes`、`from_bytes` 以及复制进工作线程程序的全局变量都会复制值；析构类型必须被排除在所有这些场景之外，从而为“平面类型（flat）”再添一条新限制。
5. **双重销毁。** 池槽位被释放两次就会运行两次析构器。钩子必须能够容忍这种情况，就像各包中带代际检查的句柄目前对双重 `release` 所做的那样。
6. **隐形开销。** 析构器会在退出路径上引入控制流与函数调用，而语言此前一直刻意让退出路径远离这些东西。这其中就包括教程里曾断言绝不会发生的容器遍历。

其收益仅限于那些存放在容器中或在作用域之间移动的资源。如今这类场景包括 `30_mini_minecraft` 中的区块网格，以及游戏可能会存放在池中的实体句柄——而后者其实已经能被第 3.3 节的终结器所覆盖。

<a id="48-general-downsides"></a>
### 4.8 总体缺点

* **退出变得不再完全显而易见。** 阅读函数时，在相信一个 `return` 之前必须先扫一眼前面的 `defer`。由于函数体较短，加上“仅执行已走过的 `defer`”规则将集合范围控制得很小，负担还不算大，但在这门原本很少需要顾虑此类细节的语言里，它终究是多了一件需要留心的事。
* **每次退出的开销。** 带有 `defer` 的函数会在每条返回路径上运行延迟代码；循环内的 `defer` 会在每次迭代运行一次。这份代价至少在源码上是显式可见的，这也是它最大的优点。
* **不是所有权系统。** 寿命长于创建它的作用域的资源仍然要靠手动释放，和以前一样。第 5.1 节说明了如果仓库里真的出现释放 bug，多半就出现在这种场景。
* **没有错误通道。** 清理代码如果自身失败，只能选择中止或忽略，这一点在每门拥有该特性的语言中都是如此。
* **两套机制。** `defer` 加上池终结器比单独学习其中之一需要掌握更多内容；引入终结器的理由在于，它所覆盖的恰好正是 `defer` 无法表达的场景。

## 5. 示例

<a id="51-code-in-the-repository-today"></a>
### 5.1 当前仓库中的代码

**越过打开操作的提前返回。** [29_ui_todo.k](../../../samples/29_ui_todo.k) 先打开窗口，随后如果无法创建 UI 上下文，就会写出错误信息并直接返回，而没有调用 `gfx::close()`。由于进程紧接着就结束了，这次泄漏无伤大雅，但每个句柄类 API 都会写出这种形态的代码。使用 `defer` 后：

```klang
guard gfx::open("K: a ui to-do list", 760, 520, gfx::WINDOW_RESIZABLE) else { … }
defer gfx::close();
var ctx = ui::create_from_memory(ROBOTO, 16.0);
guard ctx.id != 0 else { write_stderr(str("ui: ", ui::error(), "\n")); return; }
defer ui::destroy(ctx);
```

`27_gfx_cube`、`28_physics_boxes`（`physics::destroy(world); gfx::close();`）、`30_mini_minecraft` 以及 `31_mini_doom`（`if sound_ready { audio::close(); } gfx::close();`）末尾的清理调用都可以变成紧挨着打开操作的 `defer`，而 `31_mini_doom` 中的条件关闭也可以写成 `if audio::open() { defer audio::close(); … }`，或者继续在 `defer` 语句体里保留条件判断。

**拥有连续片段的节点。** [26_file_tree.k](../../../samples/26_file_tree.k) 中的 `release` 执行了每次释放 `Node` 都必须成对完成的操作：

```klang
recursive fn release(n: Node&) {
    for e in n.entries { assert(e); release(e); }
    runs.free_slice(n.entries);
    nodes.free(nodes.index_of(n));
}
```

在 `nodes` 上加上终结器后，释放连续片段就成了释放槽位本身的一部分：

```klang
reusable var nodes: Node[>..] = [] { runs.free_slice(it.entries); };

recursive fn release(n: Node&) {
    for e in n.entries { assert(e); release(e); }
    nodes.free(nodes.index_of(n));
}
```

对子节点的递归依然留在原处：那是树遍历而不是槽位清理，让终结器去递归就变成池自己遍历自己了。

**局部池中每个节点拥有的两个字符串。** `bench/kostya/klang/src/cache_simulation.k` 中的 `put` 会在替换前释放旧值的连续片段，而 `remove_oldest` 则会在通过缓存自身的空闲链表回收节点前，释放节点的键和值连续片段。由于结构体不能持有池，这里的节点数组是一个带手写空闲链表的普通 `[>..]`。能够捕获 `strings` 池的终结器形式可以将这两处释放点合二为一；`defer` 在这里帮不上忙，因为这些释放操作都不符合作用域生命周期的形状。

**数组元素拥有的缓冲区。** [30_mini_minecraft.k](../../../samples/30_mini_minecraft.k) 会在重建网格前释放区块的顶点与索引缓冲区，而 [31_mini_doom.k](../../../samples/31_mini_doom.k) 中的 `upload` 会在扩大缓冲区前先释放旧缓冲区。这些操作都是对跨帧保存在数组元素与全局变量中的句柄进行重新赋值。这属于析构类型所针对的场景，`defer` 和池终结器都无法覆盖。同一示例中的 HUD 缓冲区则是有意跨迭代保留的，这也提醒我们：作用域退出并不总是人们想要的生命周期。

**库无法编写的 `finally`。** `stdlib/exception.k` 在文件头声明了它不提供 `finally`。第 3.5 节展示了在有了 `defer` 之后只需四行即可写出的版本。

**不符合作用域形状的池释放。** LRU 基准测试（`bench/klang/lru.k`）释放被逐出的节点，[13_linked_list](../../../samples/13_linked_list.k) 释放从链表摘除的节点。这些地方都不需要 `defer`；它们属于 `free` 的常规用法，无论采用哪种方案都保持原样。

仓库中目前没有任何代码会在函数持续期间从池里分配一个临时连续片段，并在退出函数时释放它。局部可增长数组本来就已经承担了“作用域退出时自动释放的临时空间”这一角色，语言本身就是围绕这一点设计的。池临时分配的场景（第 3.4 节）只会在以下情况出现：临时数据必须放在池的地址空间内以便使用相对链接，或者结构体里唯一的可增长数组已经被占用。

<a id="52-patterns-to-come"></a>
### 5.2 未来的常见模式

**文件与进程句柄**，当 `os` 新增流式 API 时：

```klang
fn count_lines(path: u8[:]) -> i64 {
    let f = os::open(path);
    guard f.id != 0 else { return -1; }
    defer os::close(f);
    var n = 0;
    var line: u8[>..] = [];
    while os::read_line(f, line) { n++; line.clear(); }
    return n;
}
```

**每帧或每趟渲染通道（pass）的资源**，无论该帧发生什么都能得到释放：

```klang
while gfx::frame() {
    let shadow = gfx::depth_target(2048, 2048);
    defer gfx::release(shadow);
    render_shadow(shadow);
    if gfx::key_pressed("Escape") { break; }      // shadow 依然会被释放
    render_scene(shadow);
}
```

**保存与恢复**，第三种传统用法：

```klang
fn emit_block(out: u8[>..]&, body: Node&) {
    let saved = depth;
    depth++;
    defer depth = saved;
    for s in body.stmts { emit(out, s); }         // 任何提前返回都会恢复 depth
}
```

**拥有原生对象的实体**，由池负责执行释放：

```klang
reusable var entities: Entity[>..] = [] { physics::destroy(it.body); gfx::release(it.mesh); };
```

**在通过 `return … from` 报错的构建器中失败回滚**（第 3.6 节），这是唯一值得拥有 `errdefer` 的场景：

```klang
fn parse_node(p: Parser&) -> NodeId {
    let id = nodes.alloc_index(Node { .. });
    errdefer nodes.free(id);                      // 仅当解析错误向上展开穿过此处时执行
    nodes[id].children = parse_children(p);       // 此处可能触发 `return … from parse_file`
    return id as NodeId;
}
```

**包围一段区域的辅助函数**（`with_pass`、`with_file`、带 `finally` 的 `try`），一旦有了 `defer` 即可在库中编写（第 3.5 节）。

**测试代码**：以无头模式打开图形或音频包，且必须在每条路径上关闭它——如今这迫使每个测试体只能写单一出口。

<a id="6-recommendations"></a>
## 6. 建议

1. **添加 `defer`**，绑定到作用域并在退出时求值，同时施加 3.1 的三项语句体限制（不能离开作用域、在 4.3 的严格意义下不得包含远距返回、不得写入被返回的局部变量）。将其作为与水位线保存记录并列的条目实现在作用域列表中（4.2），在作用域末尾进行检查（4.4），将其排除在尾递归重写之外，并文档说明它在中止时不会运行。这是让句柄 API 能够安全配合 `return … from` 使用的最小改动，也是构建其他形式的基础原语。有了它之后，再为 `exception::try` 提供 `finally`，并替换 stdlib.md 中解释为何没有 `finally` 的说明。
2. **随后考虑池终结器**（3.3），作为 `reusable` 或 `reusable[]` 声明上的尾随块，在 `free`、`free_slice`、缩容的 `realloc_slice` 以及局部池的作用域退出时运行。其动机来自 `26_file_tree` 与 `cache_simulation`；实现前需敲定池引用规则（一个引用可能指向的多个池需共用同一终结器）以及退出遍历是否可选。
3. **作用域限定分配**（3.4）仅在实际代码中确实出现“入口分配、出口释放”的需求时再添加；它只是 `defer` 加上检查器早已支持强制执行的根约束，因此完全可以等有需求时再做，不会有任何损失。
4. **暂不添加析构类型。** 它们需要不可复制值类别、在每次移除元素时执行销毁、对放弃的局部结果做特殊处理、排除所有复制路径，以及审计标准库的所有容器（4.7）。能从中受益的代码主要是跨帧保存在数组中的句柄，而各包中带代际检查的句柄已经把这类问题从内存危险降级为单纯泄漏，且当持有者是池时终结器就能覆盖。只有当大量使用句柄的程序暴露出 `defer` 和终结器都捕捉不到的释放 bug 时再重新审视；示例程序将是最先出现这种证据的地方。
5. **`errdefer`**：先观望。一旦有了 `defer`，它的实现成本很低，而且目前还没有实际需求。
