*已实现。本文档描述了序列化保证、加载器的校验规则，以及该实现如何保持 §9 的安全性保证。*

<a id="1-serialization-guarantees"></a>
## 1. 序列化保证

一个其链接全部为自相对引用（§3.9）的结构是位置无关的：`Node[>..]` 中的一棵 `Node { v: i32, l: Node&<u32>?, r: Node&<u32>? }` 树，或者一个 `Sexp..[>..]` 池，都是一段连续的字节序列，当该序列被重定位时，其中的链接依然有效。`bench/design.md` 将“K 的数据本身就已经是其自身的序列化形式”列为该设计的优势之一。保存时只需写出元素区域，加载时将其读回，由于不存在指针，因此无需任何指针修正遍（pointer fixup pass）。

这由三个内建函数（§12）提供。`samples/25_serialize.k` 是完整示例，`test/storage/serialize.k` 包含相关测试。

<a id="2-why-loading-requires-validation"></a>
## 2. 为何加载需要校验

如果 `from_bytes<T[>..]>(bytes)` 不经检查就直接重新解释这些字节，它将成为语言中第一个能够产生未经检查器证明有效的引用的操作。损坏或恶意的偏移量可能指向内存中的任意地址，这将破坏 §9.1 的第一优先级。K 允许的所有其他不安全性都属于类型安全的复用（§9.4），而这一种则不是。因此，加载器必须在将这些字节作为值接受之前对其进行校验，就像 FlatBuffers 验证器所做的那样。

所验证的是*安全性*，而非完整性。数据字节被篡改的映像仍然描述了一个良构（well-formed）的结构，它会被接受，只是其中的数值是错误的。表明文件就是当初写入的那个文件，是校验和（checksum）的职责，而非验证器的职责。由于映像中并不存储类型信息，也没有任何机制检查该文件是否来自*当前*程序。记录类型是容器格式的任务，而不是语言的任务。

<a id="3-the-image"></a>
## 3. 映像格式

```
uleb128(payload byte count)  payload = the array's element region
```

该前缀使流或大文件的读取器在尚未读完整个映像前就知道需要读取多少字节。它采用 §3.6 的 ULEB128 编码，`stdlib/std.k` 中的 `format_uleb` / `parse_uleb` 实现了相同的编码，供希望自行写入或读取前缀的程序使用。`from_bytes` 要求该前缀必须*精确*覆盖切片的其余部分，因此截断和尾部多余数据都会在遍历开始前被捕获。

负载（payload）必须是小端序（little-endian），这符合 C.2 中的布局规范并受所有编译器目标平台支持。`to_bytes`、`bytes_of` 和 `from_bytes` 会检测宿主字节序，并在大端序宿主上以 `K_E_ENDIAN` 中止。在所有受支持的目标平台上，该检测都会折叠为常量。若要移植到大端序平台，要么需要证明映像永远不会离开程序，要么需要生成带字节交换（byte-swapping）的变体。

<a id="4-what-must-be-verified"></a>
## 4. 必须验证的内容

对于类型为 `T[...]` 的候选负载：

1. **成帧（Framing）。** 负载能够解析为一系列 `T` 值。对于定长 `T`，字节长度必须是 `sizeof(T)` 的整数倍。对于变长 `T`，对元素的顺序遍历（与 `print` 和 `==` 使用的遍历相同）必须恰好结束于负载末尾，每个 varint 都必须正常终止，每个标签（tag）都在合法范围内，且每个嵌套长度都能容纳于剩余字节之中。
2. **元素起始位置（Element starts）。** 该遍历生成元素起始偏移量的集合；对于变长模式（variable-mode）的 ADT，还记录每个起始位置处的标签。
3. **链接（Links）。** 对于位于绝对偏移量 `f`、存储偏移量为 `o` 的每一个自相对引用字段：`o == 0` 表示空引用（null），仅在该字段为可选（optional）时合法；否则 `f + o` 必须是一个元素起始位置。以某个*变体（variant）*为类型的引用指向的是该变体的负载，因此对于此类引用，`f + o − sizeof(tag)` 必须是一个元素起始位置，且该处的标签必须是该变体的标签。如果一个引用的被指类型既不是元素类型也不是它的某个变体（例如指向元素某字段的 `i64&<u16>`），就需要枚举该类型的每一个有效地址。v1 对 `from_bytes` 拒绝此类元素类型：错误会在调用处报告，并指明该类型（见 §7）。
4. **排除的类型（Excluded types）。** 普通引用和切片（它们本质是地址）以及 `in pool` 引用（它们表示进入某个*具名*全局池的偏移量，而非进入映像的偏移量）在这三个内建函数中均被拒绝。可调整大小（resizable）的字段本来就不能作为数组元素。如果 `from_bytes` 的结果是可增缩（grow-shrink）数组且其元素包含相对引用，同样会被拒绝：验证器是针对已加载映像校验链接的，但对结果执行缩容操作会释放链接所指名的元素，而数组自身的内容却仍持有该链接；同时，阻止将指向 `T[>..<]` 的引用存入存储的写入规则（规范 §5.2）也从未触发，因为经过验证的拷贝并非一次写入操作。请改用 `T[>..]` 来加载同一份映像。

§3.9 已经为程序自行构造的自相对结构所保证的性质（链接的两端位于同一个根数组中），正是第 3 步针对外部传入结构所检查的内容。因此，经过验证的映像与程序构造的映像别无二致，此后一切常规规则都适用于它。该结果以其自身的变量为根（rooted），可以增长，并且向其中存入相对引用也会像其他任何相对引用写入一样受到检查。

`reusable` 池（§5.4）的写出和加载方式与任何其他数组相同。它的空闲链表（freelist）是映像不会携带的独立状态，因此加载后的池以空空闲链表启动，所有槽位均处于存活状态，这与 §5.4 一致。

<a id="5-the-builtins"></a>
## 5. 内建函数

```klang
fn to_bytes(a) -> u8[>..]                            // 映像，作为新生成的值
fn to_bytes(a, out: u8[>..]&)                        // 映像，追加到构造器（builder）末尾
fn bytes_of(a) -> u8[:]                              // 仅负载部分，作为视图（view）
fn from_bytes<T[>..]>(bytes: u8[:]) -> T[>..], bool  // 经验证的拷贝，或 [] 与 false
```

只要数组或切片的元素类型不包含普通引用、切片或 `in pool` 引用（此项为静态检查），这三个内建函数对其均是安全的。按照 UFCS，它们可以以任意一种方式调用：`a.to_bytes()` 或 `to_bytes(a[1..])`。

`to_bytes` 会进行拷贝。双参数形式将映像追加到由调用者拥有的可增长 `u8` 数组（可调大小或受限数组）中，因此无需二次拷贝即可在映像前加上消息头或文件头。单参数形式会像其他任何返回值一样在目标位置构建一个新的 `u8[>..]`（§7.3）。

`bytes_of` 不进行任何拷贝。它返回一个覆盖元素区域的 `u8[:]`，并以该数组为根，与对该数组取切片完全一样。因此，§5.1 和 §5.2 会阻止该数组在视图存在期间缩容，而 §9 会阻止视图的生命周期超出该数组。无论数组自身的可变性出处（provenance）如何，该视图都**绝不可写**，因为通过它写入可能会构造出未经检查器校验的相对引用。它的长度即为成帧前缀本应记录的值。因此，如果保存方先写出自己的文件头（`format_uleb`），再写出负载，就能生成一个可被 `from_bytes` 读回的文件，且全程无需在内存中构建完整映像。

`from_bytes` 会检查前缀，在负载上运行验证器，然后将负载拷贝到结果的元素区域中。验证器返回的元素计数成为结果的长度。结果是一个以自身变量为根的新数组，就如同程序自己逐个推入这些元素一样，因此无需在 §9 中增加新规则。`from_bytes` 可以构建任何内容为“一段元素连续区加一个计数”的数组种类：`T[>..]`、`T[>..<]` 以及 `T[]` 系列（其计数会写入目标自身的长度前缀）。定长数组或受限数组还需要该计数与映像并未携带的容量相匹配，因此它们会被拒绝。元素中包含相对引用的 `T[>..<]` 同样会被拒绝：结果一旦缩容就会释放其自身链接仍指向的元素（见 §4，排除的类型）。

返回的 `bool` 是验证器的判定结果；若失败，数组为空。当调用者愿意将空数组作为无效输入的结果时，可以丢弃该布尔值（`var a = from_bytes<T>(b);`）。

这些都是带有自定义类型检查的普通内建函数（类似于 `default<T>()`）；`from_bytes` 需要显式提供类型实参（§7.7）。

这一对操作构成往返（round-trip）：对于 `from_bytes` 接受的每一种元素类型，`from_bytes<T[>..]>(a.to_bytes())` 都等于 `a`。

<a id="6-generating-the-verifier-per-type"></a>
## 6. 按类型生成验证器

验证器按元素类型生成，与现有的大小计算和相等比较函数（`k_size_T`、`EmitEqWalk`）类似。其签名为 `k_verify_T(const uint8_t *p, int64_t n, uint8_t *bm) -> int64_t`；返回元素计数或 −1。`codegen_types.h` 中的 `EmitVerifyWalk` 会针对每种类型种类使用对应分支，并依据布局规则（`Layout`，C.2）生成该函数。生成的代码会递归进入结构体字段和变体负载，检查每一个相对引用字段。该实现为代码生成（codegen）增加了约 250 行代码。

* **定长元素。** 元素起始位置是隐式的，因此单次遍历即可完成所有检查：它对标签做范围检查，对受限数组长度做边界检查，并通过 `0 <= f + o < n && (f + o) % sizeof(T) == 0` 校验链接。不需要临时内存（scratch memory），`bm` 传入空指针（null）。
* **变长元素。** 这需要两次相同形态的遍历。第一次遍历对负载进行成帧，并在 `bm` 中为每个元素起始位置置位——`bm` 是位于临时数据栈（scratch data stack）上的位图，每字节负载占用 1 比特。第二次遍历再次扫过负载，并在位图中查找每个链接。该临时缓冲区在语句作用域栈（statement-scoped stack）上占用 `(n + 7) / 8` 字节，因此会在语句结束时释放。
* **边界检查。** 每次读取前都会先进行边界检查，并且 varint 解码器采用带边界检查的 `k_uleb_check` / `k_zig_check` (runtime.h)，而不是普通的解码器（普通解码器会一直循环直到遇到映像中可能根本不存在的终止符）。
* **不含相对引用的元素类型**会跳过链接检查遍。**不需要任何检查的类型**（定长、没有需要范围检查的标签、没有需要做边界检查的受限数组长度、也没有链接）会作为不透明字节整块跳过，而不是逐字段遍历。
* 开销：验证只需对负载进行一到两次线性扫描；对于定长元素无额外分配，对于变长元素只使用一个位图。其时间复杂度为 O(n) 且分支极少，与随后的拷贝处于同一量级，这与 FlatBuffers 的经验一致。`samples/25_serialize.k` 会在 stderr 上报告其自身索引所测得的耗时。

受限数组（limited arrays）是一个特例。超出所存长度的槽位从未被写入过（§5.3），因此遍历仅检查存活槽位中的链接，随后将游标直接越过整个容量。

**位图上限。** 该位图对每字节负载使用 1 比特，且分配在单个数据栈上，因此可验证的最大*变长*元素映像是一个栈保留空间（reservation）的八倍。在默认 `K_STACK_RESERVE` 为 2 GB 时，该上限为 16 GB，且会随该常量变化。更大的负载会被拒绝（返回 `false`），而不会让位图增长到保护区（guard region）从而导致中止。定长元素映像没有此类限制，因为它们不需要临时缓冲区。另一种替代方案——存储元素偏移量数组并对每个链接做二分查找——没有容量上限，但它每个元素消耗 8 字节而不是每字节 1 比特，对于小于 64 字节的所有元素都更差，并且会把 O(1) 的检测变成 O(log n)。

<a id="7-open-points"></a>
## 7. 开放问题

* **指向负载字段的引用**（指向元素某个字段的 `i64&<u16>`）在 `from_bytes` 中会被拒绝。支持它们在概念上并不更难：成帧遍只需按*被指类型（pointee type）*标记该类型值被存储的每一个偏移量，而链接遍则查询该引用自身被指类型对应的位图。但这有三项代价：单个位图会变成每个不同被指类型各自一个位图；一旦存在此类引用，定长元素的快速路径（无需临时内存，且用取模检查链接）就会失效；此外，一旦有效偏移量由受限数组的存活长度或 ADT 的标签决定，“有效偏移量”就不再是一个静态的剩余类集合（residue set）。因此，第一版在调用处拒绝该元素类型，并在诊断信息中指明它。
* **`from_bytes` 读入定长数组或受限数组**时，若映像中的计数与映像本身并不包含的容量不匹配，就必须拒绝该映像。此外，其结果也会是一个固定大小的 C 值，而不是栈目标位置，这属于一条不同的代码生成路径。
* **大端序宿主**会中止运行。修复该问题的两种方案（要么证明字节不会离开程序，要么根据元素布局生成带字节交换的变体）都需要实实在在的工作量，而当前没有任何目标平台需要它。
* **队列（Queues）**已经可以承载映像：`qput(pool.to_bytes())` 和 `from_bytes<T[>..]>(qget<u8[>..]>())` 目前即可工作，因为 `u8[>..]` 是扁平的（flat）。尚未打通的是在非扁平类型上调用 `qput(pool)` 时隐式执行 `to_bytes`/验证。这属于便利性改进，而非新增能力（TODO 9）。
* **值可能占用零字节的元素类型**（空结构体）无法恢复出元素个数；其验证器仅接受空负载，其他一律拒绝。
* **容器格式**（魔数、版本、类型标识、校验和）被刻意排除在本设计之外。长度前缀是唯一足够简单且足够有用、适合作为语言一部分的元数据。
