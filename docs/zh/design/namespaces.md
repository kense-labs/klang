文件可以声明命名空间，并通过限定名（qualified name）引用声明。这一机制扩展了现有的导入加载器（import loader）和全程序编译器（whole-program compiler）。

```klang
// image/filters.k
namespace image;
struct Pixel { r: u8, g: u8, b: u8 }
fn brightness(p: Pixel) -> i64 { p.r + p.g + p.b }

// main.k（一个独立文件）
import image.filters;
fn main() {
    let p = image::Pixel { 10, 20, 30 };
    print(image::brightness(p));
}
```

<a id="rules"></a>
## 规则

* `namespace name;` 最多出现一次，位于声明之前（`import` 可以位于其任一侧）。不包含该指令的文件保留全局命名空间。`name` 是一个标识符。不包含嵌套命名空间以及打开命名空间的指令。
* `namespace g = image;` 用于声明别名，与上述指令一样位于文件的声明之前，并且可以声明任意多个。仅在该文件内，所有限定引用 `g::x` 都会被当作 `image::x`：包括在表达式、类型、变体（variant）、内存池（pool）、匹配模式常量（match-pattern constant）以及 `return ... from` 中。它所导入的文件以及导入它的文件永远不会看到该别名，因此库的短名称不会与使用者的名称发生冲突。出于同样原因，别名可以使用某个命名空间的名称：在其所在文件内，`g::x` 会被当作 `image::x`，而该文件只能通过另一个名称的别名来访问命名空间 `g`；其他所有文件均不受影响。别名不得使用该文件自身命名空间的名称。别名的目标必须是某个文件（通过 `namespace` 指令，无论该文件是否在其中声明了任何内容）所声明的命名空间，而绝不能是另一个别名。声明的限定符必须直接指明其所属的命名空间本身，而不能使用别名（`fn g::f` 是错误的），因此声明归属何处绝不是仅限单文件的局部事实。
* 多个文件可以声明同一个命名空间。`import` 仍然只定位并加载文件一次；文件路径既不会创建命名空间，也不会将未限定名（unqualified name）从显式命名的命名空间中导入。所有声明都是公开的（public）。
* `image::Pixel` 与 `image::brightness` 显式地指明声明。`::` 不同于现有的 `.` 字段访问、枚举变体和 UFCS；例如，`image::Shape.Circle` 依然毫无歧义。当命名空间内的声明遮蔽了全局声明时，前导的 `::name` 用于选择全局声明，同时也可用于访问内建符号（builtin）。
* 声明也可以在自身名称中写出所属的命名空间：`fn image::brightness`、`struct image::Pixel`、`let image::pool = ...`，或者在带有命名空间的文件中使用 `fn ::main` 来声明到全局命名空间中。该限定符决定了声明所属的命名空间。声明内部的名称会优先在该命名空间中解析，而不是在文件所属的命名空间中解析。这使得 `--dump` 在合并来自多个文件的声明时能够保留命名空间信息。嵌套函数（nested function）遵循词法作用域，不能带有命名空间限定符。
* 未限定名的查找顺序如下：首先在词法局部变量、形参、类型参数和嵌套函数中查找（其中任何一项都会隐藏同名的外层声明），然后是在当前声明所属的命名空间中查找，最后是在全局声明和内建符号中查找。对于函数，第一个包含该名称的作用域会提供完整的重载集（overload set）。重载集不会跨命名空间合并，因此命名空间中的 `hash` 重载若要调用全局整型版本，需写作 `::hash(k.a)`。泛型体在定义所在的命名空间中解析名称，而非在实例化它的调用方所在的命名空间中解析。字段默认值和参数默认值也是如此，无论使用它的构造表达式或调用位于哪个命名空间。
* UFCS 调用 `x.f(...)` 会优先在 `x` 的类型所在的命名空间中查找。当 `x`（解引用后）是某个在具名命名空间中声明的结构体或枚举，且该命名空间中声明了 `f` 时，就会使用该命名空间的重载集。否则，将针对书写该调用的命名空间套用上述函数名查找规则。作用域内的嵌套函数仍然享有最高优先级，且内建数组成员对用户 UFCS 候选项保持优先。因此，在任何命名空间中对 `image::Pixel` 调用 `p.brightness()` 都会调用 `image::brightness`，即便存在全局的 `brightness` 或调用方命名空间中的同名函数也不受影响，就像在 `image` 自身内部调用一样。否则，带命名空间的库函数就需要编写全局桥接函数才能作为方法调用，而且任何同名的全局函数（`length`、`find`、`get`）都会将它们遮蔽。泛型体内的 UFCS 调用会跟随其实例化所用的类型，因此全局的 `dictionary` 模块在调用 `key.hash()` 时，无需桥接即可找到带命名空间键类型的 `hash`。普通调用 `f(x)` 仍停留在其书写所在的命名空间中（不存在 C++ 风格的实参依赖查找 / ADL），并且类型所在命名空间的重载集绝不会与其他集合合并：另一个命名空间中针对该类型的同名函数需写作 `f(x)` 来调用。全局命名空间中的类型在这里没有属于自己的命名空间，因此上述规则对其保持不变。
* 自定义 `format` 钩子同样按类型查找。系统会依据现有的签名规则，先在定义被格式化具名类型（nominal type）的命名空间中查找匹配的重载，随后在全局命名空间中查找。因此，无论在何处，`print(p)` 都能为 `image::Pixel` 找到 `image::format`，而无需打开该命名空间。格式化渲染取决于类型本身，而不取决于调用方的命名空间。
* `return ... from parse` 在执行返回的函数的定义上下文中解析目标：如果作用域内存在嵌套函数则选择该嵌套函数，否则按照上述规则解析为该名称的重载集。`return ... from image::parse` 则是显式指定的形式。目标栈帧是该集合中任意函数的最内层外围调用，因此调用路径上无关的 `parse` 无法捕获这次返回。
* 命名空间限定会影响类型同一性（type identity）、重载查找以及生成的符号名。它不会引入任何运行时表示或生命周期规则。与现行规则一样，被导入文件中的 `main` 仍然会被忽略，根文件必须提供全局的 `main` 入口点：带有命名空间的程序将其声明为 `fn ::main()`。

<a id="implementation"></a>
## 实现

* 别名完全由解析器负责解析。构建所有限定引用的 `ParseQualifiedName` 会将属于当前文件别名的限定符替换为其目标命名空间，因此解析器之后的任何阶段都不会见到别名，而合并文件后的 dump 也会打印出目标名称。别名记录在 `Ast::nsaliases` 中。即便文件内未声明任何内容，`namespace x;` 指令也会创建命名空间 `x`；当所有文件解析完成后，除非此前已经发生错误（因为加载或解析失败的文件可能正是声明该命名空间的文件），否则 `ParseProgram` 会检查每个别名的目标是否确实是一个命名空间。诊断信息会指出目标名称；未知类型仍然会在其源码拼写位置下方加注下划线（`TypeName::written`）。出现在声明之后的别名会报错但仍会被保留，从而使文件其余部分按预期语义读取其使用处。语言服务器从源文本中获取限定 `Ident` 的拼写，因此悬停提示（hover）、跳转定义（definition）和重命名（rename）都能作用于 `g::x`（在 `::` 周围带有空格的拼写会被排除，而不会赋予错误的范围），并在 `g::` 之后进行补全前先解析别名。
* 词法分析器（Lexer）：新增 `namespace` 关键字和 `::` 词法记号。解析器（Parser）：支持命名空间指令、限定声明名，以及所有能够指代声明的位置上的限定引用（表达式、类型、`return ... from`、`T&<w in pool>` 类型中的内存池，以及整数 `match` 模式中的常量）。限定引用会作为单一字符串驻留（intern）（`Ident::name` 为 `"image::Pixel"`，按源码写法或经别名展开后的结果），因此绝不可能与局部变量名冲突，所有既有的词法比较也依然正确。每个引用还会记录其书写时所处的命名空间（`Ident::ns`、`TypeName::ns` 等）。该命名空间是未限定名优先解析的位置，因此它必须在克隆与泛型实例化过程中得以保留。
* `Ast` 为每个命名空间名称维护一个存放声明映射的 `Namespace`，并通过统一的查找规则（`Ast::Lookup`）路由类型解析、函数、全局变量及枚举查找。未知的限定类型名在解析阶段直接报错，而不会被当作泛型类型参数候选。解析器遇到名称后的 `<` 时会先将其作为类型实参列表尝试解析（§7.7）；当回退并将 `<` 视作比较运算符时，它会删除在尝试过程中解析出的类型节点，从而使 `a < ns::limit` 中的 `ns::limit` 不会被当作类型名处理（`test/syntax/namespace_comparisons.k`）。
* dump 输出会以限定名打印声明（`fn image::brightness(p: Pixel)`），并按书写形式打印引用（通过别名书写的则打印其目标），因此多文件程序的 dump 结果可以重新解析为同一程序；名称解析在 dump 之后运行，因此 dump 展示的是书写时的名称。
* C 符号：全局名称 `x` 与之前一样生成为 `x_g`；位于命名空间中的 `ns::x` 则生成为 `ns_x_g` 后接命名空间名称的长度（`image_Pixel_g5`）。末尾的数字在不引入有损标点替换的前提下保证了映射的单射性（injective）：`a::b_c` 与 `a_b::c` 在这些数字上不同，且没有任何全局名称的 C 符号形式以数字结尾。外部 C 链接名称保持独立：`extern` 显式指定的符号名或其默认的叶名称（leaf name）均保持不变。`in pool` 中的名称按相同规则解析，内存池声明的同一性则与之前一样得以保留。
* 测试：`test/syntax/namespaces.k` 配合 `test/syntax/ns/` 与 `test/syntax/namespaces_lib.k` 覆盖了跨命名空间的重复叶名称、同命名空间内的重载、泛型定义处查找、限定的类型/变体/内存池、全局回退与遮蔽、被导入文件中的 `main` 处理、跨命名空间的自定义格式化、在接收者类型命名空间中解析的 UFCS 调用（包括从全局命名空间调用、从另一个声明了该名称的命名空间调用、在泛型体内调用、在嵌套函数遮蔽下调用以及在变体上调用）、使用带命名空间键且无哈希桥接函数的字典、同叶名称的 `return from` 目标，以及无冲突的生成 C 符号。`test/syntax/match_constants.k` 在匹配模式中引用另一命名空间的常量，`test/errors*/ns_*.k` 覆盖各类诊断报错，而 `test/lsp/ufcs_ns.k` 测试语言服务器针对解析到类型命名空间的 UFCS 调用的响应。`test/syntax/namespace_aliases.k` 在各种限定引用中均使用了别名。它导入了 `test/syntax/ns/alias_user.k`，后者自身的 `im` 指向另一个命名空间，其 `terrain` 别名借用了导入方所使用命名空间的名称，而其 `h` 则指向一个未声明任何内容的命名空间（`ns/hollow.k`）。`test/errors/ns_alias_*.k` 测试用例集拒绝各类错误用法（其中一个通过 `test/errors/ns_alias/` 中的辅助文件演示别名不会传递到被导入文件），而 `test/lsp/ns_alias.k` 则向语言服务器查询通过别名拼写的名称。

这一扩展仅改变名称解析方式。它并未引入独立编译、包解析、访问控制（私有性）、重导出（re-export）或一等模块值（first-class module value）。

别名是一条独立指令，而非 `import` 的一部分（`import image.filters as f;`），因为 `import` 加载的是文件，而命名空间并不是文件：一个命名空间可以跨越多个文件，一个文件也可以不声明任何命名空间。

<a id="rust-and-zig-comparison"></a>
## 与 Rust 和 Zig 的对比

Rust 的 `mod` 在 crate 内构建层级化的模块树，`use` 引入绑定，且可见性通常默认为私有并通过 `pub` 控制。本设计借鉴了限定路径语法，但将文件加载与命名空间声明分离，允许多个文件共同贡献于同一个命名空间，并保持所有声明公开。参见官方的[模块参考](https://doc.rust-lang.org/reference/items/modules.html)、[use 参考](https://doc.rust-lang.org/reference/items/use-declarations.html)与[可见性规则](https://doc.rust-lang.org/reference/visibility-and-privacy.html)。

Zig 的 `const image = @import("image.zig");` 绑定被导入文件的容器类型；声明通过 `.` 访问，并由 `pub` 控制外部可见性。这契合了 Zig 的编译期类型/值模型。而 K 语言的命名空间仅是符号表作用域：它不能被赋值、返回、作为值传递参数，也无法在编译期被内省检查。参见官方的 [Zig 语言参考](https://ziglang.org/documentation/master/#import)。
