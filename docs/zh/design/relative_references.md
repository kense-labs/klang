相对引用（`T&<u8>`、`T&<u16>`、`T&<u32>`、`T&<u64>`、`T&<varint>`，规范 §3.9）是一种以窄偏移量形式存储的引用。本文对两种编码方案进行比较。在开展实验时，规范定义的是第一种方案；第二种方案则在 `opt/pool-relative` 分支上以编译标志控制的方式实现并进行了测量（`bench/adoption.md` 3.1）。比较范围涵盖语义、开销以及所支持的用法。末尾的“最终结果”一节记录了随后对这两种形式的实现。除非另有说明，文中的数据均来自 `large` 规模下的基准测试套件。

<a id="1-what-each-encoding-means"></a>
## 1. 每种编码的含义

**自相对（Self-relative）**（原始形式）：存储的值是 `target - &field`，即从字段自身地址到目标地址的有符号距离。加载为 `&field + offset`；存储需要同时知道两个地址。对于可选形式，零表示空（null）。检查器（checker）强制执行的不变量是：目标位于与字段相同的根数组中（§3.9）。正是这一不变量使以这种方式链接起来的结构具有*位置无关性*（position independent）：如果整个数组被移动或映射到任意位置，每条链接依然有效，因为两端是一起移动的。

**基址相对（Base-relative）**：存储的值是 `target - base(P)` 再加 1（从而让零继续表示空），其中 `P` 是目标所在的池（pool）。加载为 `base(P) + offset - 1`；存储为 `target - base(P)`。其不变量是：目标位于 `P` 中，并且在存储或加载该值的任何位置 `P` 都是已知的。以这种方式链接的结构*作为一个池整体*是位置无关的：如果将池映射到任意位置，链接依然有效，因为它们是从池的起始地址开始度量的。该值实质上就是一个索引：`&P[i]` 编码为 `i * sizeof(T)` 时无需涉及基址，而索引通过一次移位即可恢复。

两者在位宽、空值表示、允许指向的目标以及整数组序列化方面保持一致。它们的差异在于地址算术需要知道什么（是字段的地址，还是池的基址），而这一差异解释了下面表格中的每一行。

<a id="2-speed"></a>
## 2. 速度

我们在两种工具链（v145 / clang）上对比测量了基准编译器与开启该标志后的版本：

| 测试项 | 基址相对 vs 自相对 | 原因 |
|---|---:|---|
| lru（每次命中重链六条链接，在索引与引用间来回转换） | 1.04 / **1.41** | 存储无需字段地址且无需范围检查；`&pool[i]` 即 `i * 16` |
| graph（单遍链接邻接表，指针追逐） | 1.03 / 1.18 | 加载为 `base + off`，其中 `base` 作为循环不变量保存在寄存器中 |
| bintrees、tree、interp、scene（一次构建，遍历） | 0.93-0.96 / 0.93-1.00 | 热递归不得不将基址作为隐藏参数传递 |
| calc | 无法编译 | 从容器中读回的普通引用没有基址（见下文 §4） |

按指针追逐路径上的单次操作拆分：

* **加载（Load）。** 自相对：`p = &n->next; p += *(int32_t *)p`，对刚计算出的地址执行两次存在依赖关系的操作。基址相对：`p = base + *(int32_t *)&n->next - 1`，一次加载和一次加法，且加数在循环开始前就已保存在寄存器中。clang 对第二种形式的指令调度更好；v145 则不然，这构成了两列数据之间的全部差异。
* **存储（Store）。** 自相对：`*(int32_t *)&n->next = (int32_t)(t - &n->next)`，两个地址相减，再加上预留空间超出位宽时的范围检查（自测试框架为 `u32` 采用 2 GB 预留后，该检查已消除，§3.9）。基址相对：`t - base`，对于 `&pool[i]` 则直接就是 `i * 16`。
* **索引转换（Index conversions）。** 任何在其他地方保存索引的代码（`lru` 的映射表、各类 arena 风格的工作负载）在每次使用时都需要转换。基址相对使该转换变成一次移位；自相对则需要用目标地址减去字段地址。`lru` 的 1.41 倍提速正来源于此，而非指针追逐本身。
* **隐藏基址（Hidden base）。** 当基址既不是全局常量、局部变量，也不是胖引用（fat reference）的头部时，对于引用参数类别未绑定到单一池的每次调用，基址相对都必须将基址作为隐藏参数传递。这使 `bintrees` 和 `tree` 中的递归慢了 4-7%。自相对不需要隐藏参数。

就整个测试套件而言，净影响很小，方向取决于工作负载：重链密集的测试项获得提升，一次构建的测试项损失几个百分点，遍历类测试项基本持平。在 clang 下收益显著；在 v145 下除了 `lru` 之外都在噪声范围内。

<a id="3-expressivity"></a>
## 3. 表达能力

* **位宽所限制的对象。** 自相对：限制字段与目标之间的*距离*。只要两端相距在 32 KB 以内，`u16` 链接在数兆字节的池中也能正常工作，这正是 `calc` 所依赖的特性（在按输入构建、彼此距离从不遥远的树中使用 2 字节链接）。基址相对：限制*池的大小*。`u16` 链接会将池限制在 64 KB 以内，无论距离远近；`calc` 的按输入划分的池放得下，但 `sexp` 的池中的 `u16` 链接就会放不下。因此窄位宽在不同编码下具有不同的含义，在类型未发生任何变化的情况下，为一种编码编写的代码在另一种编码下可能是错误的。
* **跨数组链接。** 自相对在算术上*能够*编码从一个数组指向另一个数组的链接（算术本身并不关心），但规范禁止了这种做法（§3.9），以使结构保持为自包含的数据块（blob）。基址相对可以从任意位置链接到一个*具名*池（例如，`slots` 中的一个映射槽位使用 4 字节指向 `pool`），而数据块属性变为“相对于该池”，这也是此类链接唯一合理的语义。这是自相对无法表达的一类场景。目前 `lru` 的映射表保存的是索引，因为从 `slots` 指向 `pool` 的 4 字节引用无法成为自相对引用。
* **位置无关性与复制。** 整数组移动、映射和保存对两种方案都适用。将*子区域*复制到另一处（规范 TODO 16）时，目标位于该区域内部的自相对链接无需额外工作即可保持有效。而基址相对链接需要重定位基址（rebasing），除非该区域落入相同形状池中的同一偏移位置。线程队列（TODO 9）也提出了同样的问题。
* **谁必须知道池。** 自相对在加载时无需知道任何额外信息，因为字段自身地址已经就绪。基址相对在每次加载和存储时都需要知道目标所在的池，且检查器必须*精确*知道该池。根追踪（root tracking）为 `&pool[i]`、`push` 的结果以及类别属于单一池的参数提供了这一信息。结合 §9.5 的回读规则（read-back rule），当作用域内只有一个变量能够容纳该引用类型时，它也能为从容器中读回的引用提供该信息。但当作用域内存在两个相同元素类型的池，或者容器来自调用方时，它就无法提供该信息。自相对在所有这些情况下都能工作，因为它只需要生命周期界限。
* **实测映射表中的引用。** 有了精确回读根（exact read-back roots），`lru` 可以在其映射槽位中保存 `Node&?` 并通过它们进行重链（当时作为 `lru_refslots.k` 进行测量，现已移除）。在自相对编码下，这种方式反而比索引形式*更慢*：在 v145 下慢 1.11-1.13 倍，在 clang 下慢 1.09 倍。槽位膨胀到 16 字节，每个节点还需携带自己的索引用于 `free`，且相对存储仍需减去字段地址。这正是基址相对能够大幅降低成本的形态，因为从槽位指向 `pool` 的 `Node&<u32>` 本身就是索引。
* **哨兵、`self` 与空值。** 两者在这方面相同：`self` 在前者中存储 `-(字段偏移)`，在后者中存储 `-(值在池中的偏移)`，而零在两者中均表示空值。
* **将值作为数据读取。** 基址相对的偏移量本身就是有意义的：它是元素在池中的位置，因此无需任何地址算术即可打印、哈希、跨节点比较或用作索引。而自相对偏移量脱离其自身地址便毫无意义。

<a id="4-compiler-complexity"></a>
## 4. 编译器复杂度

* **自相对**已经实现。它唯一的成本在于根追踪——检查器无论如何都要为生命周期检查执行该分析——以及一次存储时检查（当位宽覆盖预留空间时现已省略）。
* **基址相对**需要编译器原本没有的三项机制，它们均已在标志分支上实现（`src/` 下 `+405 -41`）：
  * 在代码生成阶段将根解析为基址表达式的能力（全局变量的栈、局部变量的栈、胖引用的头部，或穿过参数类别未绑定到单一池的调用传递的隐藏参数）；
  * 一个检查器不动点分析，用于在每个调用点判断哪些参数类别对应唯一的一个池；
  * 根上的精确性位（exactness bit），以确保从容器中读回的引用绝不会按错误的基址解析。

  第三项本身就具有独立价值，目前已在为规范的定根规则（rooting rule）推进实现；前两项则纯粹服务于这一编码方式。未来每一个涉及数据移动的特性（子区域复制、队列、保存与加载）都必须了解基址重定位（rebasing）。
* **按字段同时支持两者**需要相应的语法，以及相对存储和加载发射器中的第二条代码路径，但除了精确性位之外无需新的分析。基址相对字段仅在其池的基址已知处才合法，而检查器原本就已经知道它是否已知。

<a id="5-options"></a>
## 5. 备选方案

**A. 仅保留自相对。** 这是最简单的方案。它对每个数组保持位置无关，兼容非精确根，且存储时检查已经消除。它在 `lru` 上会比 Rust arena 在 v145 下慢 1.45 倍、在 clang 下慢 1.19 倍。同时它也无法表达“从映射表指向池的 4 字节链接”，因此这类程序只能继续保存索引——Rust 和 C++ 的 arena 实现也是如此。

**B. 切换到基址相对。** 对于重链和索引转换工作负载，这是最快的方案，并且提供了跨数组链接以及本身即为索引的偏移量。但它会给递归增加隐藏参数开销，改变所有窄位宽的含义，使复制和队列需要重定位基址，并且一旦作用域内存在两个同类型的池，从容器中读回的引用就会无法使用。最后一点是当前编码所没有的语言级限制。

**C. 两者并存，按字段选择。** 自相对继续作为默认值，也是未指定具名池时的唯一形式。字段可以改为声明为相对于某个具名池（全局池，或作为池的参数或局部变量）。该字段的存储和加载随后使用该池的基址，允许跨数组链接指向该池，且位宽限制该池的大小。检查器仅允许将根精确为该池的引用存入此类字段。此方案需要新增语法、两条发射器路径以及精确性规则。它不需要不动点分析，也不需要隐藏参数，因为池是在声明处指名的，而不是在各调用点推导出来的。`lru` 的映射表可以在 8 字节槽位中保存 `Node&<u32 in pool>` 并通过它们重链，而所有一次构建的结构继续保持自相对，没有任何额外开销。

**D. 由编译器按数组自行选择。** 这一方案不可行：编码方式会改变声明位宽的含义，因此必须在源码中显式可见。

<a id="recommendation"></a>
## 建议

方案 C 在保留现有程序及其语义的同时允许跨数组链接。它改善了针对具名池的重链性能，且不会为其他地方的递归增加开销。它唯一需要的新分析——针对回读引用的精确根——正是已经在推进中的定根机制改动。尚待确定的是语法。对于全局池，`T&<u32 in pool>` 读起来很自然。而对于局部池或参数池，只有在结构体声明位于函数内部时，池的名称才在字段所属结构体的声明作用域内可见。这表明指定池名称的形式主要是一个面向全局池的特性，而重链密集型结构也恰好都位于全局池中。

<a id="outcome"></a>
## 最终结果

最终实现了方案 C：`T&<u32 in pool>`，其中 `pool` 是一个全局只增不减数组（规范 §3.9），并配套实现了 `a.index_of(r)`（§3.3）。池在字段声明处指名并成为类型的一部分，因此存储从该全局变量的基址开始度量，而加载则精确地定根于该池。无需在参数类别上做不动点分析，也没有隐藏参数。传入定根于不同池的引用的调用点会成为不同的特化版本，这与所有其他根差异的处理方式完全一致。`in pool` 形式被限制为只能用于全局池，这正符合本文对重链密集型结构所在位置的预期。局部池或参数池则继续保持自相对形式。这正是 `graph` 保持自相对（其池是 `main` 的局部变量）的原因，也完全符合设计意图。

`lru` 已改写为使用该特性。映射表在 8 字节槽位中保存 `Node&<u32 in pool>?` 并通过它们重链，`pool.free(pool.index_of(n))` 将引用转回槽位以释放节点，池的基址保存在每个函数的一个局部变量中。索引形式以 `lru_indices.k` 保留。与索引形式相比，引用形式在 v145 下持平，在 clang 下快 1.31 倍。其余所有基准测试生成的 C 代码均未改变。在测试套件中，该测试项的耗时为 3,255/2,133 ms，对比 Rust arena 的 2,237 ms 和 C++ arena 的 2,413/2,261 ms。在 clang 下与两者持平；在 v145 下则落后 1.45 倍，原因在于其对“基址加偏移”加载的指令调度较差。
