本提案引入了两个旨在配套发布的特性。*索引类型*（index type）`u32 in nodes` 是一种整数类型，在其可被命名的任何位置都是全局数组 `nodes` 的有效索引，因此用它进行索引访问无需检查。`checkfree fn` 则是一种函数：如果其中仍残留任何边界检查，编译器就会拒绝编译。两者结合，使程序员能够将热循环中的边界检查迁移到数据进入程序的边界处，并由编译器确认循环内已不再残留任何检查。这曾是规范中的 TODO 0e，并解决了 TODO 0f 列出的间接索引缺口。两个特性现均已实现（规范 §3.11 和 §7.14）。本文档保留了它们背后的设计推理；§8 至 §10 记录了它们的实现过程、开发期间发现的问题以及性能测量结果。

<a id="1-the-check-no-analysis-removes"></a>
## 1. 任何分析都无法消除的检查

边界检查消除遍（bounds-check pass，§10.5，`src/bce.h`）能够证明普通循环中的大多数检查。它会保留下来的常见情形，是从另一个数组中读取出来的索引：

```klang
fn relax(adj: i32[>..]&, dist: i32[>..]&, u: i64) {
    for k in adj.len {
        let w = adj[k];                              // 已消除
        if dist[w] < 0 { dist[w] = dist[u] + 1; }    // 保留第一个 dist[w] 的检查
    }
}
```

同样的模式也出现在图边遍历（`dist[adj[k]]`）、网格索引缓冲区（`verts[tri.a]`）、排序置换（`vals[order[i]]`）、并查集（`parent[x]`）以及句柄表中。`k --check --bce-lines` 显示，`bench/klang/graph_csr.k` 会在每条边上的 `out[k]` 和 `dist[w]` 处保留检查，在每个顶点上的 `dist[u]` 和 `start[u + 1]`（`i32` 求和，可能会回绕）处保留检查，并在构建循环中于 `cursor[s]` 和 `out[cursor[s]]` 处保留两处检查。

要证明 `dist[w]` 安全，需要证明 `∀k: 0 <= adj[k] < dist.len`，这是一个关于一个数组的*内容*相对于另一个数组*长度*的事实。仅仅做更聪明的分析是不够的：

* 当 `adj` 来自程序外部（例如从文件读取的边列表或网格）时，在经过检查之前，这个事实根本不成立。该检查就是程序的输入校验。它可以被移动，但不能被消除，而且只有程序员知道它应该放在哪里（在加载时校验一次，还是在每次遍历时检查）。
* 当程序自己构建 `adj` 时，证明需要一个覆盖所有向 `adj` 写入之处的全局不变量——无论 `adj` 在何处可到达。该不变量必须把这些写入与一个长度关联起来，而该长度往往是一个运行时值，并且属于在别处分配的数组。对于 `graph_csr`（其中上界是常量 `V` 且每次压入的值都做了 `% V`），汇总每个数组中存储的值范围或许足够，但对一般情况并不成立。

池相对引用（pool-relative references，§3.9）已经覆盖了其中一部分场景。若将 `adj` 设为 `Node&<u32 in nodes>[>..]&` 并把 `dist` 移入 `Node` 中，`relax` 编译后就不会有任何检查，因为链接在存入时就已经过校验，而加载只需 `base + off - 1`。然而，相对引用无法访问*并行数组*（parallel array）：`dist`、`visited` 和 `parent` 是按相同的节点 id 索引的，且通常是按每次查询单独分配的，而不是节点结构的一部分。

<a id="2-index-and-bound-types"></a>
## 2. 索引类型与界限类型

<a id="21-syntax"></a>
### 2.1 语法

```
type        := "const"? (prim | qname tyargs? | "(" type ")") postfix*
             | indextype
indextype   := ("u8" | "u16" | "u32" | "u64") ("in" | "upto") qname ("." ident)?
```

`u32 in nodes` 是 `nodes` 的*索引类型*（index type），`u32 upto edges` 是 `edges` 的*界限类型*（bound type）。索引类型不能直接带后缀：它的数组类型写法是 `(u32 in nodes)[>..]`，向它的强制转换是 `x as (u32 in nodes)`。在每处使用点通过类型别名来写会更易读，也是推荐的风格：

```klang
type NodeId = u32 in nodes;
var edges: NodeId[>..] = [];
```

`upto` 仅在类型中紧跟无符号整型名之后才是关键字，就像 `in` 在 `T&<u32 in pool>` 中那样。`qname` 的解析方式与池名称相同，在书写该类型的声明所处的命名空间中解析。它可以包含全局根对象的直接字段，例如 `u32 in graph.nodes` 或 `u32 upto graph.edges`。所有者名称可以是命名空间限定的；别名、解引用跨越、索引访问以及嵌套字段路径均不被接受。

<a id="22-what-a-value-means"></a>
### 2.2 值的含义

`uN in a` 类型的值是一个整数 `v`，在程序中任何可观察到该值的位置都满足 `0 <= v < a.len`。`uN upto a` 类型的值则满足 `0 <= v <= a.len`：用于表示范围的末尾，例如 CSR 偏移量。

`a` 必须命名一个只增不减类型 `T[>..]` 的全局 `var` 或 `reusable var`，且其元素必须为固定大小，从而可以被索引访问。其他任何情况都是编译错误：局部变量或参数不能出现在字段的类型中（与 `in pool` 相同），可增可缩（grow-shrink）或有限长（limited）数组可以缩容，而顺序数组（sequential array）不能被索引访问。与 `in pool` 不同的是，索引类型的元素类型不受限制。

全局 `var` 根的可变只增不减数组字段满足相同的契约。其存储身份是那个特定的所有者与字段，并且仅将该成员固定为不可缩容。

所属数组是类型身份的一部分：`u32 in nodes` 既不是 `u32`，也不是 `u32 in edges`，同一数组的两种位宽也是不同的类型。其底层表示就是普通的无符号整数。数组本身不会被存储，该索引类型也不会出现在生成的 C 代码中。

<a id="23-making-one"></a>
### 2.3 构造索引/界限类型的值

* **类型转换。** 对于任意整数类型的 `x`，`x as (uN in a)` 除非满足 `0 <= x < a.len`，否则会触发中止（abort），报错信息与 `a[x]` 给出的普通索引越界错误一致。`x as (uN upto a)` 相同，只是条件为 `x <= a.len`。如果一个值通过了该检查但放不进 `uN` 中，它随后按普通 `as` 的规则进行转换：在 debug 构建中检查，在 release 构建中回绕（wrap）。回绕后的值更小，因此仍在合法范围内。
  * 与所有其他 `as` 不同，这种转换在每种构建模式下都会进行检查：它是被提前移动的边界检查，而不是仅在 debug 中进行的转换检查。
  * 边界检查消除遍对待它的方式与对待 `a[x]` 相同：凡是能够消除 `a[x]` 检查的地方，也会消除该转换检查。
  * 没有无检查形式：`x as! (uN in a)` 是编译错误。
* **读取。** 读取该类型的存储位置（数组元素、字段、变量）会得到该类型的值，调用返回类型为该类型的函数亦然。
* **循环。** `for i in lo..hi` 当两个边界都是同一 `a` 的索引类型或界限类型时，会赋予 `i` 索引类型 `uN in a`，位宽取两边界合并后的位宽。它所取的每个值都满足 `lo <= i < hi <= a.len`。计数循环 `for i in n` 当 `n` 为 `a` 的索引类型或界限类型时亦同。
* **同一数组的不同类型之间。** 同一数组的更宽位宽可以隐式转换（`u16 in a` 到 `u32 in a`），同一数组的索引类型也可以隐式转换为界限类型（`u32 in a` 到 `u32 upto a`）。相反方向——更窄位宽以及从 `upto` 到 `in`——需要使用 `as`，并按上述方式检查。
* **仅此而已。** 常量永远不具有索引类型，也不会隐式适配为索引类型，因为常量的值无法说明 `a.len` 的大小。

<a id="24-using-one"></a>
### 2.4 使用索引类型的值

* **索引访问。** 使用 `a` 的索引类型的值 `v` 访问 `a[v]` 和 `&a[v]` 无需检查，无论分析器知道什么。用它索引另一个数组 `b[v]` 时则需要检查，除非分析器能够证明 `a.len <= b.len`（§4），这可以通过计数填充、`resize`、`assert` 或调用点事实证明。两端为界限类型的切片 `a[lo..hi]` 除非已证明 `lo <= hi`，否则仍会检查 `lo <= hi`。
* **作为数值。** 它可以隐式转换为对应的普通整数类型，并进一步隐式转换为该普通类型所能转换的任何类型（`u32 in a` 可转为 `u32`、`u64` 和 `i64`）。它可以按该普通类型进行比较、打印、哈希、传给 `i64` 参数以及参与算术运算。
* **算术运算** 仅作用于普通整数值。`w + 1`、`w << 3`、`w & m`、`-w` 和 `~w` 的结果都是普通整数，`w + 0` 也是如此。对索引类型存储位置使用复合赋值和 `++`/`--` 是错误的，因为它们的结果会是写回其中的普通整数。

<a id="25-how-values-pass-through"></a>
### 2.5 值的传递规则

* **声明。** 未显式写出类型的 `let` 或 `var` 会采用其初始化表达式的索引类型。此后若对该 `var` 执行 `x = 0` 则会报错，错误信息会建议写出普通类型（`var x: u32 = adj[k];`）。
* **调用。** 参数和返回值都可以具有索引类型，实参和 `return` 值会像其他任何类型一样按该类型进行检查。
* **分支。** 当 `if`、`match`、块表达式或 `break` 值的每个分支都具有同一 `a` 的索引类型或界限类型时，整个表达式具有索引类型：其位宽取所有分支中的最大位宽，且若任一分支是 `upto`，结果就是 `upto`。否则结果为各普通类型的合并类型。`if c { 0 } else { w }` 的类型是普通 `u32`。
* **存储。** 字段、ADT 负载（payload）、数组元素、局部变量和全局变量都可以具有索引类型，每次写入都需要一个该类型的值。
* **引用与切片。** 指向索引类型存储的引用是 `(u32 in a)&`，其切片是 `(u32 in a)[:]`。它们不是 `u32&` 或 `u32[:]`，因为通过后两者写入时可能会存入任意 `u32`。`u32[:]` 参数不接受 `NodeId[:]` 实参。
* **泛型。** 类型实参可以是索引类型，并且可以被推断为索引类型。每次实例化都会携带着它一起检查（§7.7）。仅搬运 `T` 值的泛型体可以正常工作（`swap_at`、`fill`、`sort`、`max`）。而如果泛型体把算术运算结果存入 `T` 槽位，或需要 `default<T>()`，则无法使用索引类型实例化，报错信息会指明该实例化。
* **无空值（null）。** K 的可选类型是引用。表示“无链接”的值应当用 ADT（`enum Link { None, To { n: NodeId } }`），或在普通存储中使用哨兵值并在使用时转换。

<a id="26-what-may-not-hold-or-make-one"></a>
### 2.6 不能持有或构造索引类型的情形

* **默认值。** 索引类型没有默认值：`default<T>()`、字面量中的 `..`、字段默认值以及无初始化器的全局变量都需要默认值（`HasDefault`）。由于数组可能为空，甚至连 0 都不一定是有效索引。不带初始化器声明的局部变量是可以的，因为它必须在读取之前被赋值。
* **字节写入器。** `format` 和 `to_bytes(a, out)` 拒绝元素为索引类型的输出数组（`(u8 in x)[>..]`）。`bytes_of` 视图本身已是只读的。
* **映像（Images）。** `from_bytes` 接受包含索引类型的元素类型，其验证器会在校验阶段对照所命名数组的长度逐一检查每个此类值，否则拒绝该映像。这与 `in pool` 链接不同（`from_bytes` 会拒绝 `in pool`，见 `design/serialization.md` §4）：索引不依赖于元素内存布局，因此在加载时检查一次是有意义的。加载时正是应当校验来自程序外部数据的地方。
* **线程。** 每个线程程序都拥有它所用到的每个全局变量的独立副本（§11.2），线程派生之后，各个 `a` 的副本可能会增长到不同长度。`qput`、`qget`、`qpoll`、`qlimit` 和 `thread_spawn` 的参数均拒绝包含索引类型的类型。
* **C 接口。** `extern fn` 或 `export fn` 的签名在任何嵌套深度上都不能包含索引类型，因为 C 代码不会对照数组进行检查（`ExternValueOk`）。按值传入 C 的参数本来是无害的；v1 暂不加以区分。

<a id="27-the-array-never-shrinks"></a>
### 2.7 数组永不缩容

任何被索引类型或界限类型所命名的数组永远不能缩容。在程序中的任何位置——无论是直接调用还是通过引用参数——对其执行 `pop`、`pop_n`、`resize`、`clear` 或整体赋值都是编译错误。编译器已在 §5.1 中为全局变量维护了按特化统计的缩容摘要，借此可以找出每一处此类缩容。报错信息会指明是哪个索引类型固定住了该数组。对于通过其根仅约束存储边界的引用（§9.5）所做的缩容，只要该根可能到达的任一数组与某个被命名的数组类型相同，也会被拒绝。这是保守策略。元素写入、`push`、`append` 以及 `reusable` 池的 `free`（其槽位仍然保持为有效元素，§5.4）均不受影响。

<a id="3-why-it-is-sound"></a>
## 3. 为何它是健全的

其不变量是：每个活跃的 `uN in a` 值都小于 `a.len`（对于 `upto` 则是 `<=`）。

* **它的建立**：发生在构造值的每一处：转换操作会检查它，循环的值落在满足它的上下界之间，读取操作返回的是先前写入放入的值。
* **它的保持**：原因在于：
  * `a.len` 永不减小（§2.7）。只增不减全局数组的元素内存区也永不移动。
  * 向该类型存储位置的每次写入都要求是该类型的值，而只有 §2.3 能构造这种值；
  * 算术运算产生普通整数（§2.4）；
  * 不存在默认值，也不存在字节级写入（§2.6）；
  * 映像会经过校验，且该值既不在线程间传递，也不来自 C。
* **全局初始化。** 由于转换操作会读取 `a.len`，全局变量的初始化顺序（§11.1）将其视为对 `a` 的一次使用。

这一切都不涉及生命周期（lifetimes）。Rust 需要生成式生命周期（generative lifetimes）来防止带标记的索引比其容器活得更久（即 `indexing` crate），而 Ada 的索引子类型（`array (Vertex) of T`）则在类型细化（elaborated）时就固定了边界。在 K 中，只增不减（grow-only）与可增可缩（grow-shrink）的划分给出了一个只会增长的上界，这正是 §10.5 已经依赖的单调性。

`a` 的内容可以自由改变，因为只有它的长度才重要。

<a id="4-what-bounds-check-elimination-gets-from-it"></a>
## 4. 边界检查消除从中获得什么

* **来自类型的事实。** 任何表达式类型为 `uN in a` 的项 `t` 都会在 `a` 的*当前*代次（generation）上获得 `0 <= t <= len(a) - 1`，而 `upto` 则获得 `t <= len(a)`。使用当前代次始终是正确的，因为 `len(a)` 永不减小，因此不涉及桥接事实（bridge facts）。这些事实也会附加到一次性基础项（one-shot bases）上：`for` 范围的终点（`n.hi`）以及字段读取。
* **将内容事实转化为长度事实。** 当 `w: u32 in nodes` 时，`dist[w]` 归约为 `len(nodes) <= len(dist)`。这是一个两个长度之间的关系，差分域（difference domain）已经能够表达并追踪它。
  * 该关系恰好会在它理应失效的时候丢失：如果 `nodes` 在 `dist` 确定大小之后继续增长，`len(nodes)` 的代次推进，检查就会保留。
* **转换本身** 也是对 `a` 的索引检查，并且像其他任何对 `a` 的索引检查一样可被消除：在 `for v in nodes.len { edges.push(v as NodeId); }` 中不会残留任何检查。
* **尚未实现：`index_of(r)` 与 `alloc_index(v)`。** 它们的返回值本可以获得 `0 <= t < len(recv)`——它们本来就满足这一条件，从而使 `a.index_of(r) as (u32 in a)` 无需检查。目前该转换仍会保留检查。
* **按类型区分的失效（Typed kills）。** 完整示例（§7）暴露了上述事实所依赖的一个缺口：通过引用参数调用 `q.clear()`，或调用一个通过引用参数压入元素的函数，会使所有全局变量的长度事实全部失效，无论其类型如何。每个数组都有唯一类型，且引用只能到达其自身类型的数组（数组种类之间不能通过引用转换）。因此，一次增长或缩容现在只会使接收者类型的存储位置失效，而被调函数通过标量数组实参进行的写入只会使该数组类型的存储位置失效（规范 §10.5）。

<a id="5-index-types-and-relative-references"></a>
## 5. 索引类型与相对引用

两者都是“存入时检查一次、使用时直接信任”的链接。两者都建立在相同的论证之上：目标是只增不减的全局数组，任何活跃代码都不会观察到它缩容。它们的区别在于链接所指代的对象。相对引用指代一个*元素*：它只能被解引用追踪，是带有根、const 性、`.=` 重链接以及无需额外存储即可表示 null 的 `T&`。索引则指代编号中的某个*位置*：它是一个数值，可以访问多个数组，参与计算、比较、排序、哈希并传出进程。有了索引类型，`&nodes[w]` 无需检查即可将索引转为引用。

| | `Node&<u32 in pool>` | `u32 in nodes` |
|---|---|---|
| 可访问范围 | 其指向的那个数组，或元素内部的字段 | `a` 以及分析器已知至少同样长的任何数组 |
| 加载方式 | `base + off - 1`，单条寻址模式 | `base + i * sizeof(T)`，仅当元素大小为 1、2、4、8 时才是单条寻址模式 |
| 空值（Null） | 可选形式，偏移量 0 | 无：需用 ADT 或哨兵值 |
| 算术、排序、哈希 | 否（需通过 `index_of`） | 是，作为普通数值 |
| `u16` 覆盖范围 | 64 KB 池字节 | 65,535 个任意大小的元素 |
| 映像（Images） | 被 `from_bytes` 拒绝 | 由 `from_bytes` 校验 |
| 变长元素 | 是（§3.3 的链接索引） | 否：此类数组不能被索引访问 |
| 局部或参数数组 | 自相对形式（self-relative form） | 否（v1） |

**在以下场景优先使用相对引用**：链接只会被追踪到单一元素，且可能需要重链接或为空：池中的链表和树、指向节点的映射槽位（`bench/klang/lru.k`）。**在以下场景优先使用索引**：id 需要作为数值使用：访问并行数组、计算邻居或范围（`i + W`、CSR 偏移量）、比较或排序，或传出进程。

网格（mesh）是一个两者皆可行但索引更优的例子。对于元素为 32 字节顶点的 `verts: Vertex[>..]`，`Tri` 中的 `Vertex&<u32 in verts>` 链接可以服务于读取顶点位置的 CPU 代码。但索引仍然更好，原因有四：索引缓冲区可以直接原样送入 GPU；它可以从文件格式中按原样加载，仅由 `from_bytes` 做唯一一次检查；在低于 65,536 个顶点时通常使用的 `u16` 索引，若改用 `u16 in pool` 则只能覆盖 2,048 个顶点；而且后续添加的逐顶点属性（法线、蒙皮权重、用于 SIMD 的 SoA 列）都是同一个索引就能访问的并行数组。

<a id="6-checkfree-functions"></a>
## 6. `checkfree` 函数

<a id="61-meaning"></a>
### 6.1 含义

```
fndecl := ("export" strlit? | "extern" strlit?)? "checkfree"? "inline"? "simd"? "recursive"?
          ("fn" | "thread_fn") ...
```

如果经过边界检查消除之后，`checkfree fn f` 的函数体中仍有任何位置残留了边界检查，编译就会报错。这涵盖函数体的每一份副本：每个特化版本、每个 `simd` 版本以及每个内联副本。该注解不会改变程序计算的内容，也不会改变它的编译方式。`checkfree` 仅在紧邻 `inline`、`simd`、`recursive`、`fn` 或 `thread_fn` 之前才是关键字，因此仍可用作普通标识符。

*边界检查*包括 §9.3 的索引检查与切片检查、向索引类型与界限类型的转换（§2.3），以及 `free(i)` 的索引检查。§9.3 中的其他中止则不属于此类：
* 有限长数组容量检查；
* 缩容低于空的检查；
* debug 溢出检查与 debug `as` 检查；
* 除以零；
* 相对引用偏移量溢出；
* `assert` 与 `abort`。

特别是 `assert`，它正是 `checkfree` 函数在循环外部一次性声明其前置条件的方式。

<a id="62-calls"></a>
### 6.2 调用

这一保证是可传递的：在 `checkfree` 函数执行期间，不会运行任何边界检查。它所调用的函数无需自身声明为 `checkfree`，而是在于 `checkfree` 函数内部运行的各个位置接受判定：
* **调用。** 仍保留为函数调用的调用点会执行被调函数自身的函数体，该被调函数体在其所有调用者建立的事实下接受判定（§6.3），其进一步调用的函数亦然。通过函数值进行的调用视为对它可能指向的每一个函数的调用。`print`、`str` 和 `format` 视为对其触及的用户 `format` 重载的调用。内建函数与 `extern` 函数没有 K 的边界检查，而派生出的线程不在其派生者内部运行。
* **内联副本。** 被内联进 `checkfree` 函数、或内联进运行在其中的被调函数的副本，会按其在该处的上下文接受判定。内联到其他代码中的副本则可以保留检查。因此，若一个辅助函数的检查仅能由某个 `checkfree` 调用者的事实来消除，它在被内联处可以编译通过，但在 `-O0` 下不行——在 `-O0` 下它保留为一次常规调用，受限于所有调用者共同满足的事实。
* **实参。** 调用者的实参表达式属于调用者的代码，即便该调用被内联也是如此：`sq(a[i])` 会将检查记在调用者身上，而不是记在 `checkfree fn sq` 身上。
* **嵌套代码与代码块。** 在 `checkfree` 函数内声明的嵌套函数自身也是 `checkfree` 的。代码块（block）在其被传入的函数内部运行，因此从任何地方传入 `checkfree` 函数的代码块都会被判定为运行在其中。

报错信息会列出从 `checkfree` 函数一直到该检查处的调用链，并在该检查不属于最后一个函数的文本（即代码块或内联副本）时指明它实际写于何处：

```
checkfree fn sum_all calls twice, which calls get, which keeps a bounds check: nothing shows i < a.len
checkfree fn each keeps a bounds check in code written in fn main: nothing shows x >= 0
```

函数上的 `checkfree` 是对其自身代码文本的承诺：无论谁调用它，其任何副本中都不存在检查。如果反过来要求每个被调函数也显式标注 `checkfree`，就会迫使每一个小型辅助函数（`swap`、`min`、`max`、向量运算）无论是否索引数组都必须加上标注。标准库不作此承诺；其测试会从 `checkfree` 函数中调用 [stdlib.md](../stdlib.md) 文档明确标明为无检查的函数。

<a id="63-where-its-facts-come-from"></a>
### 6.3 事实的来源

函数的入口事实来自其各调用点（§10.5）。依赖调用点事实的 `checkfree` 函数，当别处新增一个未能建立该事实的调用者时，可能会停止编译。这种情况下，报错信息会指明该调用点及其未能建立的事实。为了使函数独立于其调用者，请使用：
* 签名中的索引类型；
* 入口 `assert`，用于声明函数体所需的长度关系，例如 `assert(dist.len >= nodes.len)`。

每种方式都在循环外只做一次检查，同时起到文档化前置条件的作用。

<a id="64-what-every-implementation-must-prove"></a>
### 6.4 每种实现都必须证明的集合

§10.5 说明了程序的语义完全不依赖于分析器能够证明多少事实。但有了 `checkfree`，程序能否编译通过却依赖于此，因此规范定义了一个*核心集*（core）：即每个符合规范的实现都必须在 `checkfree` 函数内消除的检查。接受核心集之外的检查则由具体实现决定。仅依赖核心集编写的程序在分析器的任何版本下都能编译通过。

如果某事实（涉及 `x`）与检查之间存在以下任一情况，则称该事实被*杀伤*（kill）：对 `x` 的写入、该事实中某数组的缩容、某索引类型所命名数组的增长，或者调用了一个效应摘要表明它可能执行上述操作之一的函数。核心集包括：

1. 对固定大小数组的常量索引（且在范围内），以及值域整体能容纳于该固定数组中的索引（如 `u8` 索引 `[256]`）。
2. 使用 `a` 的索引类型对 `a` 进行索引。
3. 使用 `a` 的索引类型对 `b` 进行索引，且此前通过断言或计数填充建立了 `b.len >= a.len`（或 `==`），期间无杀伤。
4. `for` 循环索引访问其计数或范围终点对应的长度所属数组（`for i in a.len`、`for x, i in a`、`for i in lo..a.len` 且已知 `lo >= 0`），且循环体中不缩容 `a`。
5. `a[i]`，其中某个条件（`while`、`if`、`guard` 或 `assert`）建立了 `i < a.len`，期间无杀伤，且已知 `i` 非负：无符号类型、索引类型，或者初值非负且仅通过 `++` 与非负常量的 `+=` 修改的局部变量。
6. 与同一路径上已通过的某个检查完全相同，且期间无杀伤。

分析器证明的其他所有情况（乘积、使用 `%` 和 `&` 的归约、来自调用者的事实、效应摘要、步长计数器）均属于尽力而为（best-effort）。

<a id="65-diagnostics"></a>
### 6.5 诊断信息

每处残留的检查对应一条报错，并附带源码行定位在对应的索引位置。错误信息会按照 `docs/implementation.md` §9.1 中“保留（Kept）”列表的术语说明检查残留的原因。已实现的原因包括：

* **从数组、字段或调用读取的值。** 报错会建议为存储在该处的值使用索引类型。
* **`u64` 索引变量。**
* **分析域无法与长度关联的项**，或分析器在该位置未追踪的长度。
* **具体哪一侧界限失败：** 无法证明 `x >= 0`，或无法证明 `x < a.len`。如果是另一个数组的索引类型，报错会直接给出能够解决该问题的 `assert`：

  ```
  checkfree fn bfs keeps a bounds check: nothing shows u < dist.len; u is a
  u32 in nodes, so `assert(dist.len >= nodes.len)` where neither changes
  after it would settle it
  ```
* **切片：** 三个比较中的哪一个未能证明。

有两种原因尚未实现，因为它们需要分析遍保留目前尚未保存的来源（provenance）信息：
* **长度已被使失效：** `dist` 的长度在第 N 行调用 `f` 时（或被 `q.pop()`）失效。这需要记录每个长度基数代次背后的语句。
* **来自调用者的事实：** `file:line` 处的调用传入的 `src` 不满足 `src.len == W * W`。这需要分析遍知道是哪一个调用点的交汇（meet）丢掉了入口事实。

<a id="66-flags-and-combinations"></a>
### 6.6 编译标志与修饰符组合

* **标志。**
  * 在 `--no-bce` 下，不会校验 `checkfree`。编译器会发出一条警告说明此事，并照常保留所有检查。
  * debug 与 release 构建运行同一套分析，得到相同的判定结果。
  * 在 `-O0` 下不做任何内联。仅凭自身类型与断言即可消除检查的函数在 `-O0` 下会得到相同的判定结果。完整示例在 `-O0`、`-O1` 和 `-O2` 下均可通过，包含内联辅助函数时亦然。
* **组合。**
  * `checkfree` 与 `extern` 一起使用是错误的，因为后者没有函数体。
  * 它可以与 `inline`、`simd`、`recursive`、`thread_fn` 和 `export` 组合使用。
  * 线程入口和导出函数不会获取调用点事实，无论如何核心集从不依赖调用点事实（§8.3）。

<a id="7-worked-example-csr-breadth-first-search"></a>
## 7. 完整示例：CSR 广度优先搜索

这是使用索引类型编写的 `graph_csr.k`。图是全局的且仅构建一次。遍历过程中没有任何逐边或逐顶点的检查。

```klang
struct Node { lo: u32 upto edges, hi: u32 upto edges }

var nodes: Node[>..] = [];
type NodeId = u32 in nodes;
var edges: NodeId[>..] = [];

// 从未经任何校验的边列表构建图：这里的检查是整个遍历过程
// 唯一需要付出的代价。
fn build(nv: i64, src: i32[:], dst: i32[:]) {
    let empty = 0 as (u32 upto edges);            // 0 <= edges.len 恒成立
    for v in nv { nodes.push(Node { lo: empty, hi: empty }); }
    var first: i64[>..] = [];                     // CSR 偏移量
    for v in nv + 1 { first.push(0); }
    for e in src.len { first[src[e] + 1]++; }
    for v in nv { first[v + 1] += first[v]; }
    var next: i64[>..] = [];
    for v in nv { next.push(first[v]); }
    let some = 0 as NodeId;                       // 对空图会中止
    for e in dst.len { edges.push(some); }
    for e in src.len {
        let s = src[e];
        edges[next[s]] = dst[e] as NodeId;        // 每条边在此检查一次
        next[s]++;
    }
    for v in nv {
        nodes[v].lo = first[v] as (u32 upto edges);
        nodes[v].hi = first[v + 1] as (u32 upto edges);
    }
}

// 从 src 出发的距离之和；dist 为每个节点保存一个条目。
checkfree fn bfs(dist: i32[>..]&, q: NodeId[>..<]&, src: NodeId) -> i64 {
    assert(dist.len >= nodes.len);
    var total = 0;
    q.clear();
    dist[src] = 0;                     // 核心规则 3
    q.push(src);
    var qh = 0;
    while qh < q.len {
        let u = q[qh];                 // 核心规则 5；u: NodeId
        qh++;
        let d = dist[u];               // 核心规则 3
        total += d;
        let n = nodes[u];              // 核心规则 2
        for k in n.lo..n.hi {          // k: u32 in edges（§2.3）
            let w = edges[k];          // 核心规则 2；w: NodeId
            if dist[w] < 0 {           // 核心规则 3
                dist[w] = d + 1;       // 核心规则 6
                q.push(w);
            }
        }
    }
    return total;
}
```

示例说明：
* **核心规则 3 在整个循环中持续成立**，因为循环中没有任何操作会增长 `nodes` 或缩容 `dist`。`q` 是另一个不同数组类型的数组。
* **`build` 保留了检查。** 这些检查在构建期针对输入数据运行，每条边和每个顶点各执行一次。
* **`build` 中的顺序很重要。** 节点必须在引用它们的边之前创建，而偏移量必须在所有边就位之后再设置。
* **该图在同一次运行中无法重建。** `edges` 永远不能被清空（§2.7），这适用于仅加载一次的图。若需要按阶段重建图，则需要 §10 中提到的可增可缩扩展。

<a id="8-implementation"></a>
## 8. 实现

`docs/implementation.md` 的 §3.13 以及 §5.5 至 §5.12 逐遍描述了实现细节。本节记录实际落地与原计划的对照情况。

<a id="81-the-plan-held"></a>
### 8.1 计划经受住了考验

每次带类型的存储操作都已经通过 `TypeCheck::FitsAt`，而这也是 `in pool` 检查根的位置。因此，让 `FitsAt` 仅接受同一数组的值，几乎覆盖了所有能够写入元素的位置。原本的风险在于某些整型处理代码会按存储位宽选取结果类型，或直接复制某个操作数的 `TypeExpr *`。如计划所料，两个咽喉点让这类代码选择了“失败关闭”（fail closed）：在每个运算符操作数都会经过的 `TypeCheck::Operand` 中剥离数组标记（brand），并且每个带标记的目标或合并点都要求同一数组。所有会把类型原样传递下去的位置也正如预测：`MergeVals` 中的常量 `adapt`、`UnifyBranch`、`FitsAt` 的常量与字面量分支，以及处理转换判定的 `Converts`。该标记保留为 `TY_INT` 上的一个字段，而不是单独的种类。

<a id="82-what-the-plan-missed"></a>
### 8.2 计划遗漏之处

* **优化器会折叠类型转换。** `AsCast::Opt` 会把 `5 as NodeId` 折叠成常量 5，从而丢掉检查。向索引类型的转换现在永不折叠。
* **两条代码生成路径会窥探转换内部。** `DivisorKey` 和 `DivisorValue` 会把除数的转换检查外提到循环之前，而 `Speculatable` 会在不会失败的情况下无条件求值转换。两者现在都将向索引类型的转换视为其本质所是的检查。
* **完整示例需要按类型区分的失效**（§4）：如果没有它，`bfs` 入口 `assert` 带来的事实会在 `q.clear()` 处被杀伤。
* **将检查归属到源码文本。** 内联器会把实参表达式放入被调函数的基本块中，因此仅追踪当前遍历处于哪个函数会把实参的检查归咎于被调函数。改用与 `--bce-test` 相同的源码行区间后，每份副本的归属都准确无误。
* **`for` 绑定变量的转储（dump）** 需要加上与解析器要求相同的圆括号。

<a id="83-a-soundness-bug-found-on-the-way"></a>
### 8.3 途中发现的一个健全性漏洞

`checkfree_parallel` 测试夹具最初使用了 `export fn`，结果本应保留的检查却被消除了。K 调用者的事实被赋予了 `export fn` 的入口，但它的 C 包装函数会用未经任何人检查过的实参去调用同一份特化。例如，如果 `export fn api(d: i32[:], i: i64) -> i32 { d[i] }` 在 K 中以已知长度和索引被调用过一次，编译时就会消除其检查，而 C 随后就能越界读取。这个问题早在索引类型之前就已存在，现已单独修复（2f7e1b6b）：导出函数与线程入口一样，不获取调用点事实。

<a id="84-size"></a>
### 8.4 改动规模

原估计为 400–600 行。实际改动为 19 个源文件中的 +685 −44 行（含按类型区分的失效和 `checkfree` 诊断消息），另加 28 个拒绝测试夹具、3 个解析错误夹具和 6 个带预期输出验证的程序。

  * `test/optimizer/checkfree_callees.k`：被调函数、代码块、`format` 重载与标准库比较器形式（均未声明 `checkfree`），以及 `checkfree` 函数实参中保留的检查；
  * `test/codegen/index_type_abort.k` 与 `bound_type_abort.k`：转换失败时的中止行为及其报错信息。
* **模糊测试。** `bench/bce_fuzz.py`（400 个程序，种子 7）在引入按类型区分的失效后仍未发现任何不一致。它目前还不会生成带索引类型的程序结构。

<a id="10-measurements"></a>
## 10. 性能测量

程序由 `k build` 使用 clang-cl 22（x64 默认目标）编译，并在开发机上运行。数值为 9–11 次交错运行的最佳值与中位数。这些只是粗略数据，并非正式基准测试集条目。

* **§7 的 BFS** 在一百万个节点、八百万条边和八个源点规模下，与采用相同内存布局和普通 `u32` 存储的同一程序对比：搜索阶段分别为 0.606 s 对 0.628 s（中位数，已减去构建时间）。这处于噪声范围内。该遍历受限于内存带宽，而被消掉的检查都是预测准确率极高的分支，正如 `docs/implementation.md` §5.12 此前在分析数组内容时所发现的那样。
* **一个 gather 核心（kernel）**，`out[i] = verts[idx[i]] * 2.0 + 1.0`，四百万个索引，循环 50 趟：0.220 s 对 0.232 s（最佳值），0.224 s 对 0.247 s（中位数），整趟运行提升约 5–9%。
* 早期对比草稿中，普通版本使用了 `i64` 字段和边，当时测得索引类型有 25% 的优势。该差异来自更窄布局带来的内存流量减半，而普通版本同样可以使用窄布局。索引类型本身并不是收窄布局的理由，但它让窄布局在索引访问时与宽布局一样安全。

因此在 clang 上，索引类型的价值更多在于提供静态保证以及把检查前移至数据入口，而非纯粹的运行速度。有两种环境尚未测试：MSVC（在 MSVC 中，哪怕保留检查就会直接阻止向量化——`blur` 在保留九个检查时慢了 1.75 倍），以及带有 gather 指令的更宽指令集。

<a id="11-open-questions"></a>
## 11. 待决问题

* **命名。** `checkfree` 略有点承诺过头，因为其他中止仍然存在。备选名称有 `proven` 和 `boundsfree`。排除了听起来像“允许跳过检查”的名字（Odin 的 `#no_bounds_check` 和 Julia 的 `@inbounds` 会不安全地禁用检查）。`upto` 也许可以写成 `in ..= a`。
* **`var` 类型推断。** 不带显式类型的 `var` 是否应当采用普通类型，以便支持重新赋值？那样 `var u = q[qh]` 就会丢失索引类型，每次用 `var` 遍历的循环都必须把类型显式写出来。
* **将局部变量与参数用作 `a`。** 局部数组本可以在局部声明中命名，而引用参数指向的数组也可以按调用点确定，就像池参数那样（§3.9）。唯一障碍在于字段的类型不能命名局部变量。
* **将可缩容数组用作 `a`。** 在没有任何指向它的索引值处于活跃状态时，可增可缩数组本可以缩容，就像 §5.2 对引用所做的那样。这正是按阶段重建的图所需要的能力。
* **有符号索引类型。** `i64 in a` 可以让 `for i in a.len` 和 `for x, i in a` 无需转换就提供索引类型。但赋予现有循环新类型会改变现有程序生成的泛型实例化，因此 v1 暂不支持。
* **只读视图。** `const u32[:]` 本可以接受 `NodeId[:]`，因为没有任何代码会通过它写入。这需要一个 `TypeEq` 目前不具备的子类型规则。
* **可选形式** 若能像 `in pool` 那样偏移 1 进行编码，就能提供无需额外存储空间的空值。
* **线程派生参数** 很可能是安全的，因为工作线程的 `a` 副本是在派生时刻拷贝的——只要工作线程使用了 `a`。v1 暂且拒绝它们。
* **`index_of` 与 `alloc_index`** 本可以返回索引类型而非 `i64`。但那样会破坏直接对其结果做算术运算的现有代码，因此计划改为补充 §4 所述的数据流事实（目前尚未实现）。
* **§6.5 中缺失的两条诊断信息。**
* **在 `bench/bce_fuzz.py` 中加入索引类型形态**：加载、合并、泛型透传，以及在确定大小与使用之间发生增长的情况。
* **将固定大小数组用作 `a`**（如对 `T[256]` 使用 `u8 in table`）在健全性上是显然成立的，且大部分已被该整型自身的值域所覆盖。
