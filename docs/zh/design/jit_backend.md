本文档介绍 TinyCC 后端的工作原理及其尚存的局限性。

<a id="what-it-is"></a>
## 它是什么

编译器的常规输出是 C 代码，将其写入文件以供另一个编译器构建。编译器还内嵌了 TinyCC。在不指定 `-o` 时，它会将同一份 C 代码直接编译到自身进程中，并在其中调用程序的 `main`。整个过程不会写入任何文件，也无需安装 C 工具链。

    k 01_tour.k            # 在同一进程中编译并运行
    k -o tour.c 01_tour.k  # 与之前一样输出 C 文件
    k --jit prog.k         # 效果相同，显式指定 JIT 模式

如果一个程序仅通过名称绑定共享库来使用 C（即 `extern "SDL2" { ... }` 代码块，规范 §7.10），那么它同样不需要工具链：无论是在本后端下还是在编译后的程序中，运行时都会在程序启动时打开该库。只有包含自身待编译 C 代码的包或程序才需要 C 工具链。

两种模式为程序生成的 C 代码完全一致。JIT 模式与默认的 `-o` 输出都会将大部分运行时声明为 extern，仅将内联辅助函数保留在生成的编译单元中。AOT 会链接由 `--emit-runtime` 生成的运行时目标文件（`docs/implementation.md` §7）；JIT 则将这些函数绑定到内置于 K 的运行时。`--standalone` 仍然会将整个运行时写入 AOT 编译单元中。`-D` 会向生成的 C 源码写入宏定义。`--` 会将剩余参数传递给程序。

程序与编译器共享同一进程：程序的退出状态码即为编译器的退出状态码，其输出也进入相同的标准流，而编译器自身的进度信息会转移至 stderr，以便 stdout 仅输出程序内容。但它不共享编译器的栈：编译过程运行在拥有 64 MB 栈的独立线程上，TinyCC 对 C 代码的编译也是如此（其解析器的递归深度与 C 代码的嵌套深度相同）；而程序本身运行在主线程上。在 Windows 和 macOS 上，编译器在链接时为主线程栈预留了 64 MB 空间，与编译阶段获得的栈大小相同；而由同一份 C 代码构建出的可执行文件在启动时，Windows 上默认只有 1 MB 栈，macOS 上只有 8 MB 栈。在 Linux 上，两者均沿用进程启动时的栈限制（`ulimit -s`）。

<a id="how-it-is-built"></a>
## 如何构建

TinyCC 的源码已内置在 `third_party/tinycc` 目录下，其中的 `README.md` 记录了上游提交版本；每次构建编译器时都会包含这些源码。TinyCC 原生提供的是 configure 脚本和 makefile，而 CMake 无法在三大平台上通用地调用它们，因此由 `cmake/libtcc.cmake` 来生成它们原本会产生的构建产物：

* 包含版本号及内置目录内各路径的 `config.h`；
* 库本身，采用 TinyCC 的 `ONE_SOURCE` 构建方式将其编译为单个翻译单元；
* `tcc` 驱动程序，在此仅用于构建下一项，因为支持库的部分代码是用 TinyCC 汇编编写的，只有 TinyCC 能够汇编；
* `libtcc1.a`，即每个由 TinyCC 编译的程序都会链接的编译器支持例程库，由上述驱动程序根据 TinyCC 各自目标平台的对象列表构建，并剔除了仅独立可执行文件或 DLL 才需要的部分。

这些产物、TinyCC 的运行时头文件以及（在 Windows 上的）导入定义文件都会被归集到同一个目录中。打包者可以在 CMake 中将 `K_TCC_LIB_PATH` 设为对应的安装目录。运行时可通过 `K_TCCLIB` 覆盖该设置，而位于编译器二进制文件旁边的 `tcclib` 目录优先级高于配置路径。普通 JIT 程序仅使用内置的 `tccdefs.h` 和 `libtcc1.a`；其所需的少量 C 声明已直接内嵌。显式引入的 C 代码则可以使用额外归集的头文件。

`RunJit` 会禁用默认的头文件和库搜索路径，注册宿主运行时的符号，显式加载内置的支持归档库，重定位生成的编译单元，并通过宿主运行时调用其入口点。系统头文件、SDK 以及平台的动态加载接口在构建 K 本身时即已解析。运行时启动阶段会提供程序参数与资源根目录；销毁阶段则会释放程序的内存区域并恢复宿主的错误处理程序。

<a id="testing"></a>
## 测试

`test/run_tests.py` 和 `samples/run_samples.py` 会通过本后端再次运行每一个程序，并将其输出与相同的预期输出进行比对。基准测试框架也会通过本后端测量每一行 K 基准项，并在单独的表格中报告这些结果。参见 `docs/testing.md`。

TinyCC 为测试生成的 C 代码提供了第三种 C 实现，能够暴露出对特定编译器或 C 库的意外依赖。首次运行就发现了两个运行时缺陷：挂钟时间使用了 C11 的 `timespec_get`，而 TinyCC 的 Windows C 库并未提供该函数，且 glibc 也会对声明支持 C99 的编译器隐藏它；此外，在 TinyCC 所链接的较旧版 Microsoft C 运行时下，浮点数会打印为 `1e+016`，而 C99 要求指数部分为两位数字。这两个缺陷都导致 K 值的文本表示依赖于后端，违背了语言规范的要求。

<a id="follow-up-work"></a>
## 后续工作

尚存的局限性与潜在改进方向，大致按其对项目的影响程度排序。

<a id="included-c"></a>
### 包含的 C 代码

宿主运行时会直接调用重定位后的入口点。被包含的 C 代码中的构造函数/析构函数以及 `atexit` 钩子仍需要接入这条入口/退出路径。其归集的标准头文件别名仅暴露了 K 所使用的 C 声明，因此依赖额外 libc 函数或 SDK 头文件的任意 C 代码都需要显式定义接口。

<a id="threads"></a>
### 线程

本后端会拒绝任何派生工作线程或使用队列（§11.2）的程序。TinyCC 的内存运行器会拒绝任何带有 `SHF_TLS` 标志的节（`tccrun.c`：*thread-local storage not supported with -run*），而只要设置了 `K_NEED_THREADS`，运行时就会将每个线程程序的全局变量指针放入线程局部存储中。原生运行时的 TLS 由其宿主编译器提供支持，但生成的编译单元仍然需要 TinyCC 的 TLS 支持。测试运行器会报告被跳过的测试用例和示例。

可能的方向：

* **在 `__TINYC__` 条件下于运行时中模拟线程局部存储**，在 Windows 上基于 `TlsAlloc`/`TlsGetValue`，在其他平台上基于 `pthread_key_create`/`pthread_getspecific`。这种方式自成一体，大约只需三十行代码，但会将对全局变量指针的每次访问都变成一次函数调用。此外，错误处理程序会读取内存区域注册表和线程栈边界，而 `pthread_getspecific` 在该上下文中并非严格异步信号安全。在决定采用前应先通过基准测试衡量其开销。
* **让 TinyCC 的运行器支持分配线程局部块。** 这将从 TinyCC 本身解决该限制，需要向上游贡献改动。
* **保持拒绝。** 当前的诊断信息已经提示使用 `-o` 进行编译。

<a id="native-math"></a>
### 原生数学库

内嵌 JIT 会从宿主 C 运行时绑定数学函数，包括 Windows 上的 `log2`。`test/stdlib/stdlib_math.k` 允许跨平台的超越函数计算结果存在细微舍入差异，并在原生后端和 JIT 后端上均可运行，无需 `no-jit` 标记。

<a id="the-sanitizer-profile"></a>
### Sanitizer 配置

在 ASan/UBSan 配置下会跳过 JIT 运行。程序本身并未经过插桩。宿主运行时会在正常返回或 K 退出/中止后释放其内存区域以及生成的栈指针数组，但这条路径尚未在 sanitizer 下经过验证。常规编译路径则具有 sanitizer 测试覆盖。

<a id="backtraces-and-bounds-checking"></a>
### 回溯与边界检查

`config.h` 关闭了 TinyCC 自身的回溯与边界检查功能，因为它们背后的支持目标文件需要完整的 Windows SDK 头文件，而 TinyCC 并未自带这些头文件。因此，生成代码内部发生崩溃时会导致整个编译器进程直接终止，且没有符号化调用栈。由于在 ELF 和 Mach-O 目标上构建这些目标文件时不需要 `windows.h`，这两项功能其实可以仅在这两个目标平台上启用。

<a id="macos"></a>
### macOS

构建过程遵循 TinyCC 针对各目标平台的对象列表，且 CI 会在三大平台上执行构建，但 macOS 路径尚未在本地实际运行验证。Apple Silicon 是三者中验证最少的一个：它需要 Mach-O 输出，且 JIT 必须向内核请求先可写后可执行的内存。

<a id="compilation-is-not-cached"></a>
### 编译未缓存

每次 JIT 运行都会重新编译生成的程序以及内联运行时辅助函数。运行时的其余部分已经预编译进了 K 中。TinyCC 对内存中的编译结果没有序列化格式，因此实现缓存需要大量工作。
