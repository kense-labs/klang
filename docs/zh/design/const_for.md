# `const for` 与 `const if`：特化期展开（v1）

状态：已实现。K 在语句列表、构造函数初始化器列表和 `match` 分支列表中支持以下展开来源。`const if` 用于在这些相同列表中根据编译期谓词选择片段，详见第 11 节。

本设计用普通 K 函数中的单一展开构造取代了编译器提供的一系列字段访问器（field visitor）。编译器提供少量结构序列，并针对每个条目特化一次源码片段。库可以自行决定生成函数的名称、签名、回调以及运行时行为。

字段遍历使手写的字段列表与其结构体声明保持同步。

<a id="1-scope-and-cost-model"></a>
## 1. 作用域与开销模型

| 来源 | 绑定 | 含义 |
|---|---|---|
| `fields<T>` | `<N, A>` | 按声明顺序，每个直接字段的名称与访问器 |
| `variants<E>` | `<N, V>` | 按声明顺序，每个变体的名称与该变体 |
| `decorated<D, namespace Scope>` | `<N, Declaration, M>` | 该作用域中每次应用 `D` 的限定名称、声明与元数据 |
| `decorated<D, T>` | `<N, A, M>` | 按声明顺序，`T` 中匹配字段的名称、访问器与元数据 |
| `types<T1, T2, ...>` | `<U>` | 显式的类型序列 |
| `[c1, c2, ...]` | `<C>` | 显式的常量序列 |

展开支持语句列表、构造函数初始化器列表以及 `match` 分支列表。初始化器列表可以包含具名字段初始化器或位置表达式，但仍受限于现有的禁止混用这两种形式的规则。第 10 节记录了作为未来工作的其他展开来源与放置位置。

不存在通用的编译期执行块、任意 K 代码解释器、用户自定义的展开来源函数、代码引用（quotation）API 或文本宏替换。`const` 限定的是展开本身：其来源和绑定在特化期间已知。展开体中的普通代码仍在运行时执行。

展开生成的是普通的 K 操作和常量。它不引入运行时迭代器、异构容器、类型注册表、逐对象元数据或动态派发。不使用该特性的程序不会为此承担任何运行时开销。使用了展开的程序可能会增加编译时间、生成的代码量以及保留的常量（例如打印的字段名称）。生成操作现有的分配、拷贝和运行时检查开销仍然适用。

<a id="2-syntax"></a>
## 2. 语法

```klang
const for <N, A> in fields<T> {
    F(N, &value.A);
}

const for <U> in types<i8, i16, i32, i64> {
    test_roundtrip<U>();
}

const for <C> in [1, 2, 4, 8] {
    var buffer: u8[C] = [0; C];
    test_buffer(buffer);
}

match shape {
    const for <N, V> in variants<Shape> {
        V v => print(N, " ", v),
    }
}
```

`const`、`for` 和 `in` 是现有关键字。尖括号是必需的：它们将特化绑定与普通循环变量区分开来，并复用了泛型参数列表的视觉约定。绑定名称不必大写；大小写没有任何语义影响。

`fields`、`variants`、`decorated` 和 `types` 仍然是标识符标记（token）。它们是仅在 `const for` 来源中识别的上下文查询名称。它们不是普通的可调用函数，不参与重载解析，也不能在该位置被用户声明替换或遮蔽。用户定义的同名函数或变量在其他地方不受影响。查询后面没有圆括号。

新增语法概要：

```text
expansion      := "const" "for" "<" bindings ">" "in" source "{" fragments "}"
bindings       := ident ("," ident)* ","?
source         := "fields" "<" type ">"
                | "variants" "<" type ">"
                | "decorated" "<" type "," (type | "namespace" (ident | "::")) ","? ">"
                | "types" "<" (type ("," type)* ","?)? ">"
                | "[" (const-expr ("," const-expr)* ","?)? "]"
```

此处带引号的 `fields`、`variants`、`decorated` 和 `types` 是上下文标识符，而非词法关键字。`const-expr` 使用表达式语法解析，并在特化期间依据第 3.3 节进行校验。外围列表决定了 `fragments` 的语法类别；编译器不会在解析展开体之后再反推片段类别。

绑定数量必须精确匹配。`fields` 和 `variants` 使用两个绑定，`decorated` 使用三个绑定，而两种显式列表使用一个绑定。v1 没有第三个字段类型绑定、索引绑定、绑定注解或可选输出。绑定可以不被使用。展开来源在其自身绑定进入作用域之前解析；外层展开绑定对它仍然可用。

<a id="3-expansion-sources"></a>
## 3. 展开来源

<a id="31-fields"></a>
### 3.1 字段

`fields<T>` 要求在解析别名和泛型类型参数之后得到具体的结构体类型或变体类型（`Shape.Circle`，或来自 `variants` 的绑定 `V`）。变体类型的字段即为其负载（payload）的字段。`const` 限定符不会改变字段序列。引用、数组、切片和代数数据类型（ADT）不会被隐式解包或遍历：对 ADT 使用 `fields` 会报错，其变体应通过 `variants<E>` 访问（第 3.4 节）。

每个字段按声明顺序各访问一次。填充字节（padding）会被省略。空结构体产生零个条目。嵌套结构体、数组和引用仍然作为单个字段处理；不存在自动递归遍历。

对于每个条目：

* `N` 是作为不可变字符串常量的字段名，其语义与普通字符串字面量相同。它可以出现在该字面量作为有效表达式的任何位置。
* `A` 标识其具体所属结构体实例化中的该字段声明。它既不是字符串，也不是运行时值。

访问器在 v1 中有两个替换位置：

```klang
value.A             // 成员访问
T { A: expression } // 具名初始化器标签
```

接收者或构造函数必须具有该访问器所属的结构体类型，并允许普通的引用访问和 `const` 限定。对于变体类型，接收者或构造函数必须是该变体类型的值（例如由 `match` 分支绑定的负载）或该变体的构造函数。ADT 类型的值是错误的所属者，因为在被匹配之前其具体变体未知。不同的名义类型或不同的泛型实例化不会仅仅因为拥有同名字段就匹配。按名称进行的结构化匹配属于另一项独立特性。

通过 `A` 访问完全遵循访问实际字段的规则：拷贝与引用绑定、可写性、生命周期根（lifetime root）、构造限制以及表示形式适配保持不变。特别是，当直接引用该字段非法时，`&value.A` 也会被拒绝。迭代绝不会因为生成的操作失败而跳过某个字段。

`A` 不能用作独立值、作为普通函数参数传递、被存储、用作类型或转换为偏移量。v1 不公开其声明类型、默认表达式、属性或布局元数据。`N` 也不会仅仅因为包含字段名就成为访问器。

<a id="32-type-lists"></a>
### 3.2 类型列表

`types<T1, T2, ...>` 对每个条目都使用普通的类型语法，包括限定名、别名、泛型实例化、引用和数组类型。条目在其词法环境中解析，并可提及外层的泛型或展开绑定。展开时，每个条目都必须解析为具体类型。其最终使用必须满足该类型及所在位置的普通规则。

唯一的绑定在每个片段实例中表现为一个类型参数：

```klang
const for <U> in types<i32, Pair<u8>, const u8[:]> {
    check_type<U>();
}
```

类型保留其自身标识和限定符；它们不会成为运行时值。重复条目会产生重复实例。`types<>` 为空。

使用独立语法可以避免将某个条目同时解析为可能的类型和可能的值表达式。特别是，`[i32, u8[:]]` 不是类型列表。

<a id="33-constant-lists"></a>
### 3.3 常量列表

方括号形式是一种展开来源，而非运行时数组。每个条目独立校验，且条目无需具有相同类型。不存在公共元素类型推断、数组分配或来源的运行时求值。重复条目会被保留；`[]` 为空。

初始版本接受以下常量表达式：

* 整数、字符、浮点、布尔和字符串字面量；带符号的数字字面量在遵守正常可表示性规则的前提下可使用一元 `-`。
* 根据语言现有的常量使用规则能解析为上述值的具名全局常量。仅仅声明为 `const` 的局部变量不会通过此特性获得编译期求值能力。
* 数组大小和填充计数已支持的整型常量表达式，遵循其现有的类型、溢出和合法性规则。
* 外层 `const for` 展开的常量绑定，包括将其用作上述受支持整型表达式的操作数。

任意函数调用、运行时变量、聚合构造、引用、函数值以及通用的浮点或字符串计算均不在此子集内。非常量条目会报错；它不会回退到运行时迭代。即使优化器能够折叠其他形式，也只接受此处列出的形式。

具象化（materializing）常量绑定时，会保留可适配字面量与具有已声明类型的值之间的区别。它绝不能通过将具名常量替换为无类型数字标记来抹除其类型。字符串绑定遵循普通的只读字符串字面量规则。绑定本身不是可寻址的循环变量；从它初始化普通局部变量遵循普通的值语义。

```klang
const for <Label> in ["small", "medium", "large"] {
    register_label(Label); // 三次普通的运行时调用。
}
```

v1 中不存在隐式整数范围来源、数组填充来源或对运行时数组变量的查找。

<a id="34-variants"></a>
### 3.4 变体

`variants<E>` 要求在解析别名和泛型类型参数之后得到具体的 ADT 类型；已实例化的泛型枚举会产生该实例化的变体。与 `fields<T>` 一样，引用不会被解包。无论是否带有负载，每个变体都会按声明顺序被访问一次。没有变体的枚举产生零个条目。

对于每个条目：

* `N` 是作为不可变字符串常量的变体名称，与 `fields<T>` 相同。它用于显示；无论是它还是声明顺序，都不是稳定的持久化标识符，并且不提供索引绑定。
* `V` 标识该具体 ADT 的变体。它可以用在当今书写该变体自身名称的位置：

```klang
V                   // 类型：该变体类型，亦可用于 fields<V>
V { ... }           // 构造函数；对于无负载变体为 V {}
V, V c, V &c        // match 分支的模式，带可选绑定器
V                   // 值，仅限无负载变体
```

带有负载的变体所对应的 `V` 不是值；它通过 `V { ... }` 构造。`V` 不能被存储、作为普通函数参数传递或转换为整数。模式 `V` 属于其所在 ADT：在针对另一个 ADT 的 `match` 中使用它会报错，即使该 ADT 拥有同名变体也是如此。

需要将变体持久化为数字的程序应自行选择数字，方式是在一个普通的 `match` 中将变体映射到数字；反向转换则可以写成一个基于 `variants<E>` 的泛型函数：

```klang
fn number(k: Kind) -> i64 { match k { Town => 10, Catacombs => 11, Burrows => 12 } }

fn from_number<E>(n: i64, fallback: E) -> E, bool {
    const for <N, V> in variants<E> {
        if number(V) == n { return V, true; }
    }
    return fallback, false;
}
```

<a id="4-bindings-and-hygiene"></a>
## 4. 绑定与卫生性

替换遵循词法绑定标识（lexical binding identity），而非匹配的标识符文本。编译器必须区分对展开绑定器的引用与同名的无关标识符，包括跨克隆体和嵌套函数的情况。适用普通的遮蔽规则；生成的局部声明在每个实例中具有不同的标识。

对于成员位置和初始化器标签位置，作用域内的访问器绑定优先于将该名称解释为字面字段名。这一选择绝不能取决于接收者是否恰好声明了该名称的字段。例如，添加一个名为 `A` 的真实字段绝不能改变 `value.A` 在展开绑定 `A` 内部的含义。若要在这样的代码中引用该字面字段，请选择另一个访问器绑定名。

只有访问器绑定会导致成员或初始化器标签替换。不存在对声明名称、命名空间名称、任意标记或字符串的通用替换。在不受支持的语法类别中使用的绑定会被诊断报错，而不是被字符串化或解释为运行时对象。

泛型函数常规的定义点查找仍然有效。展开不会从函数调用者处导入名称。不会引入 `$` 标记、括号成员拼接或公共的编译器 AST API。

<a id="5-fragment-contexts"></a>
## 5. 片段上下文

<a id="51-statement-lists"></a>
### 5.1 语句列表

在函数体或块体中，展开体是一个普通的语句块，针对每个来源条目实例化一次。每个实例拥有自己的作用域，因此不同实例中的局部声明不会冲突。该展开没有结果值。在对尾随表达式进行正常处理之后，其块必须作为语句块有效。

如果控制流到达实例，各实例按来源顺序执行。实例内部的普通运行时 `if`、`for` 和 `while` 构造保留其运行时含义。它们不会选择生成哪些片段，也不会抑制对某个分支的正常类型检查。

`return`、`return ... from` 以及静态函数值回调中的返回保留其现有的词法语义。运行时的返回可以阻止后续实例执行；它不会改变结构来源序列。展开不是运行时循环，也不是 `break`/`continue` 的目标。v1 拒绝会跨越展开边界的 `break` 或 `continue`；完全位于片段内部的循环和可跳出块可正常工作。

允许嵌套的 `const for` 展开。内层来源可以使用外层展开的绑定，且内层展开体将在该环境中展开。

<a id="52-constructor-initializer-lists"></a>
### 5.2 构造函数初始化器列表

在结构体或变体构造函数内部，展开体包含初始化器条目，而非语句。每个实例将其条目贡献给外围的初始化器列表。该列表中的嵌套展开使用相同的条目语法。

```klang
fn transform_fields<T, F>(value: T&) -> T {
    T {
        const for <N, A> in fields<T> {
            A: F(N, value.A),
        }
    }
}
```

对于 `struct Point { x: i64, y: i64 }`，生成的构造函数等价于：

```klang
Point {
    x: F("x", value.x),
    y: F("y", value.y),
}
```

回调在运行时执行，每个结果直接前往其实际字段的构造目标。不会引入中间元组、数组或临时结构体。如果回调无法为某个字段生成合法的初始化器，会在该字段的展开处产生错误。

当初始化器表达式需要语句或局部变量时，它本身可以是一个普通的块表达式。对于非固定（non-fixed）值，该块必须遵守现有的拷贝和构造规则；展开不会添加隐式拷贝。

显式条目与展开可以同时出现。条目和列表分隔符是逗号；任一列表中的尾随逗号都是可选的。展开在其外围列表中占据一个语法位置，因此其后的显式条目或展开需要用逗号与其右花括号分隔。扁平化作用于 AST 条目，而不是带逗号的文本，因此零条目的展开不需要标点符号修补。构造函数可选的尾随 `..` 位于展开之外，并应用于完整的最终初始化器列表。

扁平化之后，适用普通的构造函数检查：

* 具名条目与位置条目不得混用。
* 未知、重复、多余和缺失的初始化器会被诊断报错。
* 显式条目不会覆盖生成的条目，反之亦然。
* 已声明的默认值、可选字段省略以及尾随 `..` 保持其正常含义。
* 构造按声明顺序进行，并应用现有的关于重排有副作用初始化器的检查。展开不会为了迎合不同的运行时顺序而引入临时变量。
* `self`、相对引用、生命周期根、`const` 字段以及对正在构造中的值的访问限制均正常检查。

默认值在构造到达它们时执行，而不是在生成展开时执行。展开必须先于缺失字段/默认值处理以及单个初始化器目标的检查。

<a id="53-match-arm-lists"></a>
### 5.3 `match` 分支列表

在 `match` 内部，展开体包含分支（arm）。每个实例按来源顺序将其分支贡献给外围的分支列表。分支的语法、分隔符和嵌套遵循第 5.2 节：分支之间以逗号分隔，尾随逗号可选，且展开在分支列表中占据一个位置。

```klang
fn show<T>(value: T&) {
    match value {
        const for <N, V> in variants<T> {
            V &v => {
                print(N);
                const for <F, A> in fields<V> { print(" ", F, ": ", v.A); }
            },
        }
    }
}
```

扁平化之后，适用普通的 `match` 检查（规范第 8.1 节 “`match`”），与手写的 `match` 完全一致：

* 针对 ADT 时，每个变体恰好匹配一次：缺失或重复的变体均会报错。由于 `variants<E>` 为每个变体都生成一个分支，在其旁边书写的任何变体分支都是重复的；只有末尾的 `_` 可以与之并存。
* 针对整数时，常量列表展开可以与手写分支以及必需的 `_` 并存。如果某个模式已被前面的分支完全匹配，则会报错，其中“前面”指的是扁平化顺序中的前面。
* `_` 必须是最后一个分支，因此位于其后的展开会报错。
* 拷贝绑定器和引用绑定器由作者编写，并针对每个生成的分支进行检查：对于固定模式（fixed-mode）或可调整大小的（resizable）ADT，`V &c` 会报错，正如 `Circle &c` 会报错一样。生命周期规则适用于每个绑定器所锚定的对象（roots）。
* 各分支的结果类型像手写 `match` 一样进行统一。
* 扁平化后没有任何分支的 `match`（例如对没有变体的枚举进行展开）会报错，正如没有任何分支的手写 `match` 会报错一样。

生成的分支可以绑定无负载的变体（例如为每个变体书写 `V v`），这样泛型代码无需借助 `const if` 即可为每个变体写出统一的分支。该绑定器是该变体类型的一个空值。手写分支中绑定此类变体仍然会报错。

<a id="6-library-use-and-receiver-semantics"></a>
## 6. 库的使用与接收者语义

字段访问器可以是一个普通的用户命名函数：

```klang
fn visit_fields<T, F>(value: T&) {
    const for <N, A> in fields<T> {
        F(N, &value.A);
    }
}

struct Point { x: i64, y: i64 }

fn main() {
    var point = Point { 2, 3 };
    visit_fields(point) { name, field => print(name, " = ", field) }
}
```

接收者通过普通函数调用进行求值和绑定。通过变量和泛型辅助函数转发的引用保留正常语义；没有任何特殊模式依赖于调用方是否在字面上写了 `&` 标记。库作者自行决定向回调传递引用表达式还是值表达式。

同时访问多个对象无需额外的展开来源形式：

```klang
fn visit_pairs<T, F>(left: T&, right: T&) {
    const for <N, A> in fields<T> {
        F(N, &left.A, &right.A);
    }
}
```

对于写在展开体内的任意表达式，没有一概“仅求值一次”的保证。放置在其中的调用会被重复执行，就像在手写生成的代码中一样。普通的函数参数和局部变量提供了对求值的显式控制。

构造函数展开对于转换和生成构建代码很有用，但 v1 并不声称提供通用的反序列化器。字段类型、默认值和模式策略（schema-policy）查询仍是未来的工作。特别是，访问现有对象的字段引用时，不能违反其仅限构造时初始化的规则去覆盖可变大小字段或 `varint` 字段。

<a id="7-compiler-integration"></a>
## 7. 编译器集成

编译器已经在具体特化处检查泛型函数（[规范第 7.7 节和第 10 节](../k_spec.md)）。展开应置于该边界处，而不是放在源码文本预处理阶段。

1. 将 `const for` 解析为一个包含绑定器、来源描述以及外围语法类别片段的展开节点。将 `const for` 与普通的 `const` 声明区分开。上下文来源语法也避免了将 `fields<T>` 中的尖括号当作比较运算符处理。
2. 在名称解析期间保留对展开参数的作用域引用，就像当今保留泛型参数的使用一样。类型列表绑定器、用于大小的常量、成员位置中的访问器使用以及初始化器标签都需要在特化前保留其绑定标识。
3. 在当前特化中解析展开来源。其类型和常量必须立即可用，而无需先检查它将要生成的片段。
4. 为每个条目克隆相应的片段，赋予全新的局部标识和对应的展开绑定。替换类型、具象化常量并解析字段选择器；递归展开嵌套形式。
5. 使用普通的类型、效应（effect）、根（root）、可写性、控制流和构造检查机制检查生成的构造。构造函数的完整条目列表必须在其正常初始化器检查开始前就绪，而 `match` 的完整分支列表必须在其穷尽性和绑定器检查开始前就绪。
6. 将经过检查的普通构造传递给优化和代码生成阶段。

解析器无需解析名为 `A` 的成员，也无需知道 `T` 的成员。但它确实需要在解析和名称解析阶段保留语义绑定并区分片段类别。仅替换标识符文本是不够的。现有的 `FieldInit` 名称表示需要区分字面量标签与绑定的访问器。

编译器无需证明一个泛型展开对所有可能的类型都有效。它只检查程序实际到达的实例，与其他泛型代码一致。空来源不会创建任何片段实例；它们的展开体仍必须能通过解析，但无需执行逐条目的语义检查。

在依赖条件允许的情况下，可以缓存结构化展开。检查结果绝不能在不兼容的引用根、可写性溯源（writability provenance）或其他现有特化输入之间复用。实现限制了展开的增长规模，并在超出限制时报告展开链。当前限制为每次编译由展开克隆的 AST 节点不超过 100,000 个（包括嵌套片段和嵌套函数体）。

普通的字段访问是其语义契约，而不是承诺重复访问已经是最优的。对于可变大小的记录，应检查生成的代码是否存在重复的前缀遍历，并在依赖关系和变更规则允许时，允许现有或未来的优化复用前向游标。不要将固定字节偏移量作为基本的访问器抽象暴露出来。

<a id="8-diagnostics-and-tooling"></a>
## 8. 诊断与工具链

展开错误应当指出原始源码位置、函数特化以及相关的字段、变体、类型或常量列表条目。不受支持的操作应当同时指向该操作以及导致其非法的条目。绝不能在失败时静默忽略某个字段。

有用的诊断信息包括：

* 绑定元数（arity）错误；
* `fields` 来源既不是结构体也不是变体类型；
* `variants` 来源不是 ADT；
* 不受支持的/非常量列表条目；
* 在错误的所属类型上使用访问器（包括对变体访问器使用 ADT 值）；
* 在错误的语法类别中使用绑定；
* 将带负载的变体用作值；
* 使用属于另一个 ADT 的模式变体；
* 展开后出现重复或缺失的构造函数字段或 `match` 变体；
* 非法的引用绑定器；
* 位于 `_` 之后的展开；
* 展开后没有留下任何分支的 `match`。

也绝不能静默忽略任何变体。

源码转储（source dump）应保留并能往返还原（round-trip）未展开的语法。展开后视图对调试很有用，但添加新的显示模式并不是该语义的前提条件。即使最初未实现展开后视图，源码到展开的溯源信息也必须在克隆过程中保留下来。

<a id="9-validation-targets-for-an-implementation"></a>
## 9. 实现的验证目标

回归测试夹具为 `test/typing/const_for_*.k` 以及对应的 `test/errors/const_for_*.k` 和 `test/errors_tc/const_for_*.k` 拒绝测试。测试运行器会检查源码往返、通过生成的 C 和 TinyCC 在 `-O0` 和 `-O2` 下的预期输出以及展开诊断信息。覆盖范围包括：

* 对异构、空、带填充、`const` 限定和泛型结构体的语句遍历；声明顺序且无隐式递归。
* 即使存在与绑定器同名的实际字段时访问器的绑定行为；词法遮蔽、嵌套展开以及全新的局部标识。
* 正常的引用转发、被拒绝的写入和引用，以及保留的生命周期根。覆盖范围应包括可变大小字段、`varint`、相对引用和可调整大小的尾部（resizable tail）。
* 包含限定类型和复合类型、重复条目以及空列表的类型列表。独立实例化且无运行时类型表示。
* 包含异构条目、带类型具名常量、受支持整型表达式、外层绑定、空列表的常量列表，以及被拒绝的运行时表达式。用于数组大小和填充计数的常量绑定。
* 运行时条件保持为运行时条件；回调和非局部返回保留其正常行为；跨边界的 `break`/`continue` 报错。
* 具名和位置构造函数展开、嵌套展开、零条目展开、显式条目与逗号、重复/缺失字段以及 `..`。保留默认值求值、声明顺序效应以及直接在各目标处构造（包括非固定字段）。
* 变体测试应覆盖带负载和不带负载的 ADT、无变体枚举以及声明顺序。在语句列表、构造函数和分支列表中演练 `variants`，以及 `fields<V>` 读取和变体构造。测试固定模式和可变模式下的按值和按引用分支，包括生命周期错误。还应测试与展开并存的手写分支和 `_`、缺失和重复变体，以及来自另一个 ADT 的模式变体。
* 解析/转储往返以及指出失败展开条目的错误。
* 对生成代码的检查，确认不存在反射基础设施、采用普通回调派发、没有不必要拷贝以及没有重复动态偏移遍历。

<a id="10-future-work-explicitly-outside-v1"></a>
## 10. 明确排除在 v1 之外的未来工作

* **已声明的字段类型。** 可能的第三个绑定是 `<N, A, U>`。v1 仅接受 `<N, A>`。后续设计必须区分存储类型与读取值类型：`varint` 字段声明为 `varint` 但读取为 `i64`，并且并非所有存储类型都能合法地作为普通函数结果。
* **常量整数范围。** 如果采用，可复用带常量边界的半开区间 `lo..hi` 语法。v1 仅支持显式常量列表。
* **`const if` 或过滤。** 已在第 11 节设计：一组用于选择片段的编译期谓词，区别于普通运行时 `if` 且不包含任意编译期调用。其中的 `has_default<A>` 查询是下面默认值项的最窄形式。
* **更多片段位置。** 参数列表和数组元素列表，随后是其他有充分理由的语法位置。共享的展开模型允许这些扩展，但每一种都需要显式的解析、顺序和类型推断规则。顶层声明以及对重载集的修改需要单独的设计。
* **默认值与注解。** 支持缺失字段构造、序列化名称、别名、忽略规则和迁移策略的查询。默认值可能包含运行时工作，绝不能在展开期间执行。仅靠名称本身并不构成稳定的持久化标识符。
* **其他元数据。** 字段计数、显示类型名、索引以及经过谨慎界定作用域的类型属性。显示名称不应自动成为稳定的类型 ID 或线格式（wire-format）契约。
* **更丰富的来源组合。** 用户自定义的序列计算、排序、分组、通用宏辅助函数以及通用常量执行。这些不由 v1 语法蕴含，且需要显式的执行模型。

库可以在 v1 原语之上构建更丰富的遍历函数，而无需添加另一种编译器提供的访问器模式。除非程序显式使用反射信息来生成普通的运行时数据或操作，否则未来的反射信息仍仅限于编译期。

<a id="11-const-if-specialization-time-selection"></a>
## 11. `const if`：特化期选择

状态：已实现。

`const if` 在函数特化期间选择它的某一个片段列表，且完全不生成其他分支的内容。它是 `const for` 重复展开对应的选择构造，遵循相同的设计理念：小型封闭的来源语言、外围语法类别的片段、内部为普通运行时代码，以及在非常量情况下不回退到运行时行为。

Web 框架可以根据普通的 K 结构体校验 JSON 请求体。`fields<T>` 展开可以读取 `T { .. }` 中每个字段的值，但无法区分 `discount: f64 = 0.0` 和 `price: f64`，因此无法区分必填字段和可选字段。解决方案是在字段上使用编译期谓词。仅有谓词还不够：基于它的运行时 `if` 会对每个字段检查两个分支（第 5.1 节），因此字段未走到的分支仍必须能针对该字段通过类型检查。`const if` 正是此类谓词的栖身之所。它们仅在其条件中有效，正如 `fields<T>` 仅作为 `const for` 来源有效一样，这使编译期代码与运行时代码在视觉上保持分离。

<a id="111-syntax"></a>
### 11.1 语法

```klang
const for <N, A> in fields<T> {
    const if !has_default<A> {
        if !seen[i] { add_error(errors, N, "Field required"); }
    }
    i++;
}

const for <U> in types<i8, i16, i32, i64, f32, f64> {
    const if same<U, f32> || same<U, f64> { check_float<U>(); }
    else { check_integer<U>(); }
}

const for <C> in [1, 2, 4, 8] {
    const if C >= 4 { check_wide<C>(); } else const if C == 2 { check_pair(); }
}

const if TRACE { print("checked ", i, " fields"); }
```

`const`、`if` 和 `else` 是现有关键字。`const if` 后跟一个条件、一个花括号界定的片段列表，以及可选的 `else`（其后可接另一个 `const if` 或一个片段列表）。条件位于审视值（scrutinee）位置，与 `if` 一样：`{` 结束条件并开始片段列表。

```text
constif    := "const" "if" condition "{" fragments "}" constelse?
constelse  := "else" ("const" "if" condition "{" fragments "}" constelse?
                     | "{" fragments "}")
condition  := expr                   // 表达式语法，按 11.2 节校验
query      := "has_default" "<" ident ">"
            | "same" "<" type "," type ">"
```

链式分支以 `else const if` 继续，与其首个分支的写法一致。直接跟在 `const if` 之后的普通 `else if` 是错误的：在该关键字处无法直观区分它是编译期 `if` 还是运行时 `if`，而 `else` 分支中的运行时 `if` 应显式写作 `else { if ... }`。

与 `const for` 一样（第 2 节），外围列表决定了 `fragments` 的语法。`const if` 在外围语句、初始化器或分支列表中占据一个位置，且每个分支都持有该类别的片段。

与 `fields`、`variants` 和 `types` 一样，查询是上下文名称。在 `const if` 条件内部，紧跟 `<` 的 `has_default` 或 `same` 会开启一个查询，尖括号内包含绑定名或按类型语法读取的类型。在其他位置这些名称是普通标识符，因此名为 `same` 的用户函数或变量不受影响，条件之外的比较 `same < x` 亦然。查询后面没有圆括号：查询不是调用，其操作数也不是值。`has_default(A)` 会暗示一个参数，而访问器不能作为参数（第 3.1 节）。尖括号表达的含义与 `fields<T>` 相同：其中内容是在特化期间已知的类型或绑定。

<a id="112-conditions"></a>
### 11.2 条件

条件是特化期的常量。它通过普通的表达式语法解析，因此优先级和圆括号规则与普通表达式相同（规范附录 D），并在特化期间依据以下列表进行校验。其他任何形式均会报错；非常量条件不会变成运行时分支。

条件为以下之一：

* `true`、`false`，或符合第 3.3 节具名常量规则的具名全局 `bool` 常量；
* 一个查询（11.3）；
* 针对条件 `c` 和 `d` 的 `!c`、`c && d`、`c || d` 和 `(c)`。即使左侧操作数已决定结果，`&&` 和 `||` 的两侧操作数也都会被校验；
* 同一类别的两个常量操作数之间的比较 `a op b`，其中 `op` 为 `== != < <= > >=` 之一。

操作数正是第 3.3 节中的常量列表条目：整数、字符、浮点、布尔和字符串字面量、具名全局常量、数组大小接受的整型常量表达式，以及外层 `const for` 展开的常量绑定。各类别的比较规则如下：

| 类别 | 运算符 | 类型规则 |
|---|---|---|
| 整数 | 全部六种 | 操作数按第 3.3 节中整型常量表达式对 `+` 的方式统一类型（规范第 6.1 节）：相同类型保持不变，字面量适配另一方的类型且必须能容纳其中；根据该类型进行有符号或无符号比较 |
| 浮点数 | 全部六种 | 两个浮点常量；与浮点常量相邻的整型常量按规范第 6.3 节进行转换 |
| 布尔值 | `==`、`!=` | |
| 字符串 | `==`、`!=` | 按内容比较 |

不同类别的操作数不能比较：对于名称绑定 `N`，`N == 0` 是错误而非 `false`。类型绝不能作为比较操作数；`same` 是比较类型的唯一方式（11.3）。字面量参数（规范第 7.7 节）在其到达的函数体中没有已知值，因此在此处不是常量。局部变量（无论以何种方式声明）、诸如 `v.A` 的字段读取、函数调用或聚合值也都不是常量。

这刻意沿用了编译器在数组大小和 `const for` 来源中已求值的常量语言，外加比较运算以及针对字面量结果的布尔连接词。这并不意味着引入针对其他运算符的求值器、局部变量或调用的常量性，或任何执行模型。希望计算常量的程序可以编写具名全局常量，这使两种语言在源码中保持明显分隔。

在条件中使用具名常量依赖于该常量保留其初始化器的值，就像数组大小一样（规范第 3.1 节），并以相同方式记录。

<a id="113-queries"></a>
### 11.3 查询

**`has_default<A>`** 要求作用域中存在以该名称绑定的 `fields<T>` 访问器（结构体字段，或通过 `fields<V>` 获得的变体负载字段）。当且仅当该字段的声明中显式写了 `= ...` 时，结果为 `true`。默认表达式本身不会被求值、检查或比较：等于类型零值的默认值（`discount: f64 = 0.0`）计为有默认值，而类型本身恰好拥有默认值的字段（例如所有字段都声明了默认值的嵌套结构体，或可选类型）不计为有默认值。对于泛型结构体的每一次实例化，结果都是相同的，因为声明只写了一次。默认值仍然按当前方式在运行时通过 `T { .. }` 获取；第 10 节关于展开期间不执行默认值的规则依然有效。

**`same<T1, T2>`** 接收两个普通类型语法的类型，其解析方式与 `types<...>` 条目相同（第 3.2 节）：在各自的词法环境中解析，可使用外层泛型参数和展开绑定，且在条件求值时要求两者均为具体类型。当两者在解析后相同时结果为 `true`，所依据的是类型检查器用于具体类型的相等性规则：别名会解析，泛型实例化按其参数比较，数组大小按其值比较，`const` 限定计入比较，且引用类型不同于其所指类型。`variants` 绑定 `V` 是一个类型，因此 `same<V, Shape.Dot>` 可以选择某个变体，正如 `N == "Dot"` 按名称选择一样。

查询是布尔常量，因此它们可以与连接词组合，甚至可以用 `==` 进行比较，尽管没有理由那样做。

第 11.6 节记录了经考虑后未纳入 v1 的查询。

<a id="114-semantics"></a>
### 11.4 语义

`const if` 在常规检查到达其所在列表时求值，与同一位置处 `const for` 展开的时机相同。首个条件成立的分支提供其片段；若没有 `else` 且没有任何条件成立，则不提供任何片段。被选中的片段会在外围列表中替换该 `const if`，正如 `const for` 的实例所做的那样，随后接受该列表的常规检查。

未被选中的分支会经过解析和名称绑定，因此它必须在语法上有效，且其自身的 `const for` 和 `const if` 绑定必须能够解析，但它绝不会被克隆、展开或检查。如果特化未走到某个分支，该分支中调用不存在的函数或向 `varint` 字段写入都不会报错。这正是它与基于常量的运行时 `if` 的区别，也是该构造的意义所在。这与 `const for` 已应用于空来源展开体的规则相同（第 7 节）。因此，没有任何特化会走到的分支根本不会被检查。

`const if` 不必位于 `const for` 内部。其条件可以使用泛型参数（`same<T, i64>`）、具名常量（`const if TRACE`），或完全不依赖特化的内容；在每种情况下其求值方式都相同。

**语句列表。** 被选中的分支是一个拥有独立作用域的嵌套块。它不是展开边界：其中的 `break`、`continue` 和 `return` 具有与运行时 `if` 分支中相同的含义，而位于 `const for` 展开体内的 `const if` 仍然不能 `break` 出该展开（第 5.1 节）。`const if` 之后的控制流就是所生成代码的控制流，因为生成的代码就是程序本身：当 `C` 成立时，`const if C { return; }` 会使其后的代码不可达；而 `const if C { x = 1; } else { x = 2; }` 的两个分支都能明确赋值给 `x`。在某分支中声明的嵌套函数仅当该分支被选中时才存在。

```klang
fn numbers_distinct<E>() -> bool {
    const for <N1, V1> in variants<E> {
        const for <N2, V2> in variants<E> {
            const if N1 != N2 {
                if number(V1) == number(V2) { return false; }
            }
        }
    }
    true
}
```

在这里，对角线上的比较根本不会被生成，而运行时 `if N1 != N2` 则会先生成每次比较然后再将其优化掉。

**构造函数初始化器列表。** 每个分支持有初始化器条目；被选中分支的条目就地加入外围列表，且扁平化先于第 5.2 节的常规构造函数检查。不提供任何条目的 `const if` 会将其字段留给显式条目、已声明的默认值或尾随的 `..`：

```klang
// src 的副本，其中每个声明了默认值的字段都被重置为其默认值。
fn reset_defaults<T>(src: T&) -> T {
    T { const for <N, A> in fields<T> { const if !has_default<A> { A: src.A, } }, .. }
}
```

**`match` 分支列表。** 每个分支持有 `match` 分支；被选中分支的 `match` 分支就地加入外围列表，早于第 5.3 节的检查。这正是第 10 节所预期的过滤功能：对 `variants<E>` 的 `const for` 可以将部分变体留给手写分支，随后穷尽性检查会要求这些手写分支存在。

```klang
fn payload_area(s: Shape) -> i64 {
    match s {
        const for <N, V> in variants<Shape> {
            const if !same<V, Shape.Dot> { V v => area(v), }
        },
        Dot => -1,
    }
}
```

决定块尾是否为语句的形态遍历（`typecheck_expansion.h` 中的 `IsValuelessTail`）不会对条件求值。它会像对待运行时 `if` 一样考虑 `const if` 的每一个分支：当任一分支的 `match` 分支构成语句时，由 `const if` 提供分支的 `match` 就是一个语句。

**绑定与卫生性。** 条件中的名称按词法绑定，正如第 4 节绑定所有其他名称一样。`has_default<A>` 中的 `A` 是作用域内同名的访问器绑定；同名局部声明会遮蔽它，此时该查询会报错，而不是去查找名为 `A` 的字段。`same` 中的类型像 `types<...>` 来源中的类型一样解析。

<a id="115-compiler-integration"></a>
### 11.5 编译器集成

1. 在识别 `const for` 的三个位置（语句、初始化器和分支列表）中紧邻 `ParseConstFor`，将 `const if` 解析为包含分支列表的选择节点，每个分支包含一个条件（末尾 `else` 为空）和所属类别的片段。条件由表达式解析器在审视值模式下解析，并开启标志使 `has_default<` 和 `same<` 开启查询节点：包含查询类别、绑定名以及按类型语法读取的类型（带常规的 `>>` 拆分）。查询节点是初级表达式（primary expression），因此 `&&`、`||` 和比较运算在其周围正常继续解析。`else` 之后的 `if` 会被诊断为 `else if`。
2. 按照第 7 节第 2 步绑定展开参数的方式绑定条件中的名称。查询的绑定名通过相同的作用域栈解析，且 `has_default` 要求它解析为一个访问器。查询类型经过绑定器的类型遍历，使其中包含的类型绑定在克隆后得以保留。
3. 在保持分支结构完整的前提下克隆条件和片段。条件中的常量绑定与其他地方一样替换为它们的字面量；查询像当今成员访问一样从展开参数拷贝其访问器的所属者和字段名；查询类型通过 `CloneExpansionType` 克隆。
4. 在外围列表展开的位置（语句循环、`ExpandInitializers`、`ExpandArms`）对条件求值。字面量结果来自 `ExpansionConstant`，它已能产生带类型的整型、浮点、布尔和字符串字面量并记录对具名常量的依赖；比较在其上折叠；`has_default` 读取所属者实例化中的字段声明；`same` 替换两个类型，拒绝非具体类型，并使用检查器的类型相等性进行比较。
5. 将选中分支的片段拼接并替换该节点：语句块作为嵌套块，条目或分支进入外围列表。它们本身无需再次克隆，因为它们所在的体已经是特化的克隆体或外围条目的克隆体。对嵌套展开和选择进行递归处理。
6. 在源码转储中往返还原未展开的语法；赋予查询尖括号与 `const for` 头部相同的尖括号标记角色；在 tree-sitter 和 VS Code 语法中将此构造添加到 `const_for_statement` 旁边；扩展规范第 6.5 节和附录 D。

被选中的片段不需要自己的展开追踪行：它们拥有自己的位置信息，位于任何外层 `const for` 追踪之内。

有用的诊断信息：

* 非常量条件，并指出违规的子表达式；
* 位于 `const if` 条件之外的查询；
* `has_default<X>` 中的 `X` 不是作用域内的 `fields` 访问器（类型或常量绑定、被遮蔽的名称、未知名称）；
* `same` 中的类型不是具体类型或在书写位置无效；
* 不同类别的操作数、对布尔值或字符串进行大小排序，或将类型用作比较操作数；
* 条件中出现字面量参数、局部变量、调用或字段读取；
* `const if` 之后的 `else if`；
* 以及选中片段产生的第 5.2 节和第 5.3 节中的扁平化列表诊断信息。

回归测试夹具遵循第 9 节的布局，命名为 `test/typing/const_if_*.k`、`test/errors/const_if_*.k` 和 `test/errors_tc/const_if_*.k`：

* 针对结构体、变体负载以及具有两个实例化的泛型结构体的 `has_default`；等于零的默认值；所有字段均有默认值的嵌套结构体；可选字段。
* 未选中分支保持未检查：其中包含未知函数和 `varint` 写入；非泛型函数中的 `const if false`。
* 各类别的比较、字面量与带类型具名常量的比较、整数与浮点数的比较、按内容比较字符串，以及与连接词的优先级。
* 针对 `types<...>` 绑定、变体、泛型参数、限定符、引用和泛型实例化的 `same`。
* 链式分支、`else`，以及无 `else` 且条件为假时不提供任何内容的分支。
* 语句上下文：运行时循环内穿过 `const if` 的 `break` 和 `continue`、`return`、穿过两个分支的明确赋值、分支作用域、与 `const for` 的双向嵌套、分支中的嵌套函数。
* 初始化器上下文：带 `..` 的 `reset_defaults`、空贡献，以及扁平化后检测到的混用或重复条目。
* 分支上下文：经筛选的变体与手写分支配合其余变体、未手写时缺失的变体、与 `_` 并存的分支，以及 `const if` 下的常量列表分支。
* 上述每条诊断信息，以及在其他地方作为普通标识符使用的查询名称。
* 解析与转储往返测试。

<a id="116-considered-for-v1-and-left-out"></a>
### 11.6 经考虑但未纳入 v1 的特性

* **字段的类型。** 谓词 `has_type<A, T>` 可以回答字段声明的类型是否为 `T`。它被舍弃了，是为了避免以一种临时形式草率决定第 10 节针对第三个绑定 `<N, A, U>` 提出的“存储类型与读取类型”问题：`varint` 字段声明为 `varint` 但读取为 `i64`。一旦 `U` 存在，`same<U, i64>` 即可覆盖字段，而 v1 的 `has_type` 如果提前选定了其中一种答案，可能会与之一致性冲突。在此之前，字段值的逐类型行为通过重载编写，正如 Honk 目前所做的那样。
* **类型种类谓词。** `is_struct<T>`、`is_adt<T>`、`is_array<T>`、`is_integer<T>` 等。重载已经能在运行时按种类派发，而且在没有字段类型绑定的情况下，种类谓词无法驱动 `fields<U>` 递归——而那才是它真正发挥价值的地方。应当由具体需求来确定这一组谓词。
* **值形式。** `let x = const if C { a } else { b };` 实现成本很低，因为被选中的块本身就是一个表达式且不需要分支类型统一，但它需要表达式位置的解析、上述尾随规则，以及对未选中分支的形态是否计入的决策。v1 沿用 `const for` 的做法：仅支持片段，不产生结果值。
* **计数、索引与位置。** `const for` 按设计不提供索引绑定；运行时计数器即可胜任，如 Honk 的 `enum_message` 所示。
* **`has_field<T, "name">`。** 配合 `const if N == "name"` 在 `fields<T>` 上使用 `const for` 已经能够到达该字段；纯存在性检查同样可以通过设置一个运行时标志来实现。
* **默认值的值。** 默认值可能包含运行时工作，在展开期间不执行（第 10 节）；获取该值的方式是使用 `T { .. }`。
* **编译期断言。** 使用这套条件语言的 `const assert c;` 是自然而然的姊妹特性，可作为一项独立的小型补充。
* **顶层选择。** 条件声明需要第 10 节已经针对顶层 `const for` 所要求的单独设计。
