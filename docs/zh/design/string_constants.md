在本文所述的变更之前，静态数据由字符串字面量和工作线程（worker）可读的 `let` 全局变量构成。先存储一个引用再将其回读（read-back），可能会使只读数据变为可写——这种行为在原 §9.5 中被称为*洗白（laundering）*。结合工作线程使用时，这会导致共享可变内存的出现。本文记录了受影响的路径，并对比了在临时实现分支上实测过的几种修复方案：

1. 用作切片的字面量作为数据栈上的隐藏局部变量；
2a. `u8` 回读永远不可写，且常量永远不可被存储；
2b. 跨存储追踪“可能指向静态数据”（即经修复后的 `codex/readonly-literals` 实验分支）；
3. 静态数据按程序实例隔离，每个工作线程获得自己的一份副本；
4. 任意类型均可使用的用户级 `const`、类型为 `const u8[:]` 的字面量、`let` 仅禁止重绑定，且彻底取消洗白机制。

最终采用了方案 4：它由紧邻本说明之前的两个提交组成（`Add const types; let is rebind-only; literals are const u8[:]` 和 `Give every program instance its own globals`，见 §6）。决定作出后，其余分支均已移除。所有方案都使用各自的测试夹具（fixture）通过了完整测试套件，并对全部基准测试完成了类型检查；示例和实测数据见 §5。

<a id="1-what-could-be-written-before-the-fix"></a>
## 1. 修复前有哪些内容可以被写入

最初的复现用例如下：

```klang
struct Box { s: u8[:] }
thread_fn worker() {
    var box = Box { s: "abc" };
    box.s[0] = 88;
}
fn main() {
    print("abc");
    thread_wait(thread_spawn(worker));
    print("abc");       // Xbc
}
```

`"abc"` 是一个指向 `static uint8_t k_str0[3]` 的 `u8[:]`。`Box { s: "abc" }` 将其存起来，随后 `box.s` 将其回读出来。按当时的设计，这次回读是可写的：因为其*路径*是可写的（`box` 是 `var`，`s` 不是 `let` 字段），而切片自身的来源（provenance）信息已经丢失。写入最终落到了那个所有线程共享的 C 静态变量上。

在修复前对编译器进行的测试还发现了其他受影响的路径：

* 每一条回读路径都会发生洗白：
  * 字段（`box.s[0]`）；
  * 元素（`views[0][0]`）；
  * `for x in views` 拷贝；
  * 指向元素的*引用*背后的切片（`for &x in views { x[0] = … }`、`&views[0]`、`push` 返回的引用）；
  * `match … &l` 绑定；
  * 通过引用参数从容器中返回的值（`fn view(b: Box&) -> u8[:] { b.s }`）。
* **`let` 全局变量存在同样的问题。** 线程可以读取任意扁平定长类型（flat fixed type，§11.2）的 `let` 全局变量，前提是假设它永远不会被写入。但对于 `let W = 78;` 而言，把 `&W` 存进一个引用字段再回读出来，就会得到一个可用来写入 `W` 的引用，而且工作线程也能这么做。同理，对于 `let TABLE: u8[3] = "abc"`，`TABLE[..]` 也能写入该常量的静态存储。因此，需要保护的内存范围是*静态数据加上所有线程可见的常量*，而不仅仅是字面量。
* *不会*发生洗白的情况包括：直接通过字面量或持有字面量的 `var` 切片变量进行写入（`let s = "abc"` 之后的 `s[0] = 1`）、`let` 变量的字段路径、按值传递参数的字段路径，以及通过传入字面量的切片参数进行写入（`zap("abc")`）——这些情况来源分析原本就会拒绝。
* 当字面量作为 `u8[]` *值*使用时（例如以内联形式返回 `"abc"` 作为 `u8[]`），其 `[len][bytes]` 映像同样位于静态区。但它的切片是对一个临时值的切片，而临时值既不能被存储也不能被返回，因此无法被洗白。
* 按线程拷贝只对线程能够*触及*的数据才有意义。切片、包含切片的结构体以及所有 `var` 全局变量本来就处于线程程序的可达范围之外，所以诸如 `let GREETING = "hello";` 这样的全局变量并不构成隐患（工作线程无法引用它的名字）。

<a id="2-the-options"></a>
## 2. 各备选方案

<a id="option-1--a-literal-used-as-a-slice-is-a-temporary-on-a-data-stack"></a>
### 方案 1 —— 用作切片的字面量作为数据栈上的临时变量

**规则。** 字面量是一个 `u8` 数组值。像现在一样，它可以被拷贝进任意数组类型中。当它被用作 `u8[:]` 时，它表示最内层作用域中一个隐藏的 `let u8[]` 局部变量，在字面量求值的位置由静态字节构建而成，效果完全等同于在那里写了 `let s: u8[] = "…";`。仅读取字面量的消费者（`print`、`format`、`abort`、`==`、`append`、`push`、数组构造）仍直接读取静态字节，不构建局部变量。在全局初始化器中不存在可拥有该局部变量的作用域，且只有主线程（main）能够触及全局变量的切片，因此那里的字面量仍保持静态。

一旦数组必须有地方存放，这正是“字符串字面量 = 数组字面量”的应有之义。它是唯一能使语言*模型*保持完备的方案（栈之外不存在任何内存），而且不需要任何来源追踪机制：隐藏局部变量就是一个普通局部变量，因此它的切片遵守所有现存的生命周期规则。

**对语言的影响。** 生命周期规则会限制现有写法。局部变量的切片不能被返回或存储到其所在作用域之外，因此以下写法将无法再通过编译：

```klang
fn name(s: Shape) -> u8[:] { match s { Circle c => "circle", … } }   // 05_shapes, 19_vm
let verdict = block { guard p.alive else { break "gone"; } … };      // 01_tour
```

25 个示例中有 3 个失败（`01_tour`、`05_shapes`、`19_vm`），原因全部是“返回字面量的切片”或“将其存储到所属块之外”。修复方式是改返回 `u8[]`（在目标处做一次拷贝）或 `u8[>..]`，或者把字面量移出块外；基准测试和测试套件中没有需要此类修改的地方。每一个为枚举返回 `u8[:]` 名称的函数（这是一种常见惯用法）都会受到影响。

**运行时开销。** 每次需要切片的求值都会付出一次字节 `memcpy` 加一次栈顶推进的代价，而每次函数进入和每次循环迭代都要付出一次保存/恢复字面量栈的代价。清单中的基准测试没有变化：它们的热点字面量都是相等性比较的操作数以及 `append`/`format` 的参数，走的都是静态路径。一个微基准测试（将字面量传给用户函数、将其存入结构体字面量并绑定到 `let`，循环 2000 万次）耗时为 **+40%**（33.6 → 47.3 ms）。单次使用的代价很小，但会施加到每一个接收切片的调用边界上。

**实现**：类型检查器在当前深度为字面量生成一个合成的 `VarDef`（为此 `while` 条件不得不移入循环作用域内部，代码生成原本就已经将其放在那里）。代码生成为每个函数维护一个字面量栈。在函数入口和每次循环迭代时保存其栈顶，在退出时恢复。在这些位置保存才是健全的：如果按字面量逐个保存，一旦在到达该字面量之前执行了 `continue`，恢复时就会读到未设置的基址。顺带一提，对于普通局部变量，这其实是一个**早已存在的代码生成 bug**，见 §6。递归也能正常工作，因为每次调用激活的字面量栈只是多占一个 `k_sp + k` 槽位，这在规范中是允许的：“临时值可消耗与深度成正比的槽位”（§7.8）。

同时还考虑过几个变体：

* (a) 把字面量当作带有临时值根（root）的右值。这会直接拒绝 `Box { s: "abc" }`，破坏性大得多。
* (b) 把函数中的所有字面量提升到函数入口处。这会导致每次调用都构建所有字面量，哪怕是在 `abort("…")` 这样的冷路径上。
* (c) 语句作用域的临时变量，也就是当前函数调用结果所采用的方式。这会导致 `let s = "abc"; use(s);` 出现悬垂引用（检查器目前允许绑定语句临时值的切片，见 §6）。

该分支还包含了来自方案 2a 的“禁止存储常量”规则，因为隐藏局部变量解决不了 `let W = 78;` 的问题。

<a id="option-2a--a-u8-read-back-is-never-writable-constants-are-never-stored"></a>
### 方案 2a —— `u8` 回读永远不可写；常量永远不可存储

**规则。** 共有两条规则，且都不需要任何全局分析：

1. 从存储中回读出的引用或切片，只要其被指物类型为 `u8`，就永远不可写。值所在的容器本身无法说明里面存过什么（这正是洗白的含义），但被指物类型可以说明：那里可能曾经存入过字符串字面量，而静态数据是全局共享的。其他所有被指物类型仍像以前一样发生洗白。通过存储维持可写路径仍然是可能的，只要改为持有数组本身的引用（`u8[>..]&`、`u8[..]&`），而字面量绝不可能是这种类型。
2. 指向线程可见常量（扁平定长类型的 `let` 全局变量）的引用或切片可以保存在变量中、向下传递或返回，但永远不能存入字段、元素或全局变量中。指向可伸缩数组的引用已经遵循这条规则（§5.2），原因相同：回读只能把存进去的东西洗白出来。

之所以需要规则 2，是因为规则 1 无法按类型推广到常量上。第一次尝试就是这么做的，结果聚合测试文件在通过 `i64&` 字段执行 `gheld.r = 7` 时失败了，只因程序中*某个*文件声明了一个 `i64` 类型的 `let` 全局变量。任何带有 `let W = 78;` 的程序都会导致所有存储起来的 `i64&` 失去可写性。相反，将常量挡在存储之外是一条局部且精确的规则，而且现有代码库无需任何改动。

**破坏性。** 代码库中没有任何破坏：所有测试、示例和基准测试均不受影响。不过语言层面的变化是可见的：存储在结构体或数组中的 `u8[:]` 通过该路径访问时是只读的。诸如 `struct Cursor { buf: u8[:], pos: i64 }` 这样需要写入 `c.buf[c.pos]` 的设计必须改持 `u8[>..]&`。由于按惯例 `u8[:]` 本身就主要用于读取（§3.10），这项损失很小，而且诊断信息会解释原因（“它是从存储中回读的，可能指向所有线程共享的字符串字面量”）。

**实现**：在检查器中不到一百行代码：

* 一个针对被指物类型的谓词，在赋予回读可写性的三处位置（`ContainerRead`、`PointeeWritable`、`ReadBackLVal`）、`for` 拷贝绑定处，以及通过参数的返回映射处（此处原本会全盘继承实参的可写性）进行查询；
* 指向元素的引用背后的切片，现在也被视作从存储中回读；
* 在 `FitsAt` 中加入针对常量的存储规则。

一个 `maystatic` 来源标志位负责将原因传递到诊断信息中。

<a id="option-2b--track-may-point-at-static-data-through-storage"></a>
### 方案 2b —— 跨存储追踪“可能指向静态数据”

这就是 `codex/readonly-literals` 实验分支，经过变基（rebase）和修复后的版本。它需要全程序范围的分析：

* 每个 `Prov` 增加两个指向单调来源图的指针（`literal`：被指物可能是静态数据；`contents`：该值内部的引用可能是静态数据）；
* 每一次存储、调用、返回、默认值、迭代、`break` 值以及 `match` 绑定都会合并图节点；
* 在全程序检查完成后，对图求传递闭包（饱和化），任何通过能够到达静态源头的节点所记录的写入操作都报错。

该分析是顺序不敏感的，因此后面的存储操作、循环回边以及共享特化的后续调用点都会被计入（测试夹具已覆盖这些场景）。代价是：即使在某一次特定执行路径中写入发生在字面量存入之前，分析也会拒绝该写入。

**最初遗漏之处。** 它没有把指向元素的引用背后的切片视作回读：`for &x in views { x[0] = 88; }`、`let r = &views[0]; r[1] = 89;` 以及 `let e .= views.push("abc"); e[0] = 88;` 全部通过了编译并写入了静态数据。变基后的分支修复了这一点（采用了与方案 2a 相同的单行改动），并补充了对应的三个测试夹具。它成功捕获了此处探测出的其余所有情况，包括常量全局变量和通过参数返回的情况。

**破坏性。** 代码库中没有任何破坏，并且比方案 2a 更精确：只要程序从未往某个容器中存入字面量，其中的 `u8[:]` 字段依然保持可写。代价是在检查器各处增加约 300 行代码、在根（roots）、精确性（exactness）和可写性（writability）之外引入第四个来源维度，以及诊断信息只能说明某次写入“可能指向不可变静态存储”，却无法指出是哪一次存储导致的。

<a id="option-3--static-data-is-per-program-instance"></a>
### 方案 3 —— 静态数据按程序实例隔离

**规则。** 静态数据属于程序实例（§1.2）。主程序拥有一份副本；每个工作线程（§11.2）从自己的一份副本开始运行，该副本取自全局初始化器完成后的状态。经由存储洗白的写入操作只会影响执行该写入的那个实例。其他一切均不改变：没有新增编译错误，没有来源追踪，单线程下的 const 转换（const-cast）行为与之前完全一致。

规范本身就已经蕴含了这一语义，因为 `thread_fn`“是作为单独的程序编译的”；方案 3 只是把这条原则应用到了这些程序原本仍在共享的唯一一块数据上。

**破坏性。** 对语言毫无影响：每一个测试、示例和基准测试都无需修改即可编译运行。在运行时，不生成工作线程的程序仍保留普通的 C 静态变量，因此生成的代码逐字节完全一致。会生成工作线程的程序则将字面量和线程可见常量集中到一个结构体中，主程序的实例就是该结构体本身。快照是在启动时执行一次 `malloc` + `memcpy`，每个工作线程在派生（spawn）时拷贝一份（大小仅几千字节，与为其预留栈块相比微不足道）。每次访问都通过线程局部基址 `k_st` 进行，这与所有数据栈访问通过 `k_stks` 所用的寻址方式完全相同。对单线程程序强制启用结构体形式（`--per-program-statics`）是这种间接寻址的最坏情况。即便如此，字面量微基准测试和清单中的基准测试都处于基线噪声范围内（§5），而在内层循环读取三个常量的多线程 Mandelbrot 示例运行时间也完全相同。

**实现**：大约 150 行代码，全部位于代码生成和运行时中；类型检查器只需确定哪些全局变量是线程可见的常量。带有运行时初始化器的常量会在快照生成前由 `k_init_globals` 初始化到主程序的副本中，因此工作线程能够看到主程序计算出的结果。

<a id="option-4--const-in-the-type-mutable-by-default"></a>
### 方案 4 —— 类型中的 `const`，默认可变

**规则。** 任意类型都可以用 `const` 修饰。`const i64[3]` 表示内容不可写入的值，`const T&` / `const T[:]` 则分别表示无法通过它们写入被指物或元素的引用和切片。该修饰符是浅层的（shallow）：从 `const Box&` 的字段中读出的引用，其可写性仍取决于该字段自身声明的类型。字符串字面量的类型是 `const u8[:]`。`let` 与这一切完全正交：它只防止绑定被重新赋值，而不对内容作任何限制（`let xs = [1, 2, 3]; xs[0] = 9;` 以及通过 `&xs` 进行写入都是合法的）。`const x = e;` 是 `let x: const T` 的语法糖，在结构体中，`const f: T` 是 `let f: const T` 的语法糖。除此之外不需要任何其他注解。声明为 `u8[:]` 的参数或返回值在*常量性上是泛型的（generic over constness）*：在传入只读数据的特化实例中，它会按只读进行检查，这与先前的来源分析所做的事情一样。参数上的 `const u8[:]` 则明确表明该函数只读不写。
唯一*必须*显式标注 `const` 的地方是**槽位（slot）**：字段、元素、全局变量、带类型注解的变量或赋值目标，只有在它的类型写明了 `const` 时，才能持有只读的引用或切片。于是，一个槽位产出的东西其可写性恰好就如其类型所声明的那样，洗白规则就此消失：`u8[:]` 字段里绝不可能被存进过只读切片。`const` 可以隐式添加，但永远不能隐式去掉，而 `extern fn` 的参数严格按其声明的类型对待。按值进行的 `for` 或 `match` 绑定是一份拷贝，因此不可写入（写入不会产生任何效果）。这是唯一值得作为独立规则保留下来的一处旧 `let` 严格性。

这与方案 2b 有本质区别：2b 推断容器可能持有什么并禁止写入，而方案 4 让程序员声明容器持有什么并禁止不匹配的存储。该检查是局部且精确的，诊断信息能直接指出具体槽位和修复方式（“将该槽位声明为 const”）。语言模型少了一条规则（洗白），而不是多了一条例外。同一特性还允许结构体持有任意数据的只读视图——例如 `let` 缓冲区或 `bytes_of` 视图——这在以前只能通过洗白才能实现。同一条规则也保护了常量：`&W` 的类型是 `const i64&`，没有任何 `i64&` 槽位能够容纳它。

**对语言的破坏性。** 持有只读数据的槽位需要添加注解，且必须作为常量的全局变量需要标注 `const`。在整个代码库中，标准库之外共有 11 处需要修改：

* 三个接收字面量的 `extern fn` 声明（`s: const u8[:]`）；
* 一处 `let s: const u8[:] = ""`；
* 两个以字面量为键的 `dictionary<const u8[:], …>`；
* 一个持有字面量值的 `dictionary<key, const u8[:]>`；
* 一个由上述字典的键填充的结构体字段 `word: const u8[:]`；
* mandelbrot 示例中工作线程读取的三个 `const W = 78;` 全局变量（`let` 全局变量不再是工作线程可读的常量，因为 `&W` 是可写的 `i64&`）；
* 一个用作数组大小的 `const N = 4;`。

标准库也需要在其八个 `os` 外部函数参数以及 `split` 上添加 `const`，后者的结果切片变为 `const u8[:]`，从而使同一个函数能够同时服务于字面量和缓冲区。没有任何基准测试需要改动。这种改动量与 C++ 中的情况如出一辙：以视图为键的泛型容器需要把视图类型写成 `const`（往 `dictionary<u8[:], V>` 传入字面量键时会报错，提示改用 `dictionary<const u8[:], V>`），而*存储*其输入视图的函数也必须为容器选定常量性，因为容器的元素类型就是一个槽位。实现过程中有三个细节需要格外注意：

* `null` 和 `default<T>()` 是“空”值，必须视作可写的，否则所有非 `const` 槽位都会拒绝接收它们；
* 对 `const` 值的读取得到的是普通拷贝，而对它的引用则是 `const T&`，因此修饰符必须在每次 `&` 运算时从存储类型转移到引用类型上；
* 检查器和内联器会为每个声明制作克隆副本，`const` 绑定形式的标记必须在克隆过程中得以保留，否则内容会悄悄变成可写（捕获这个问题的测试是 `const_value_write`）。

在该分支的第一个版本中，`let` 会使派生的引用成为 `const`，相当于重现了旧的传递性规则。第二个提交去掉了这一行为，也正因如此，mandelbrot 中的常量和那个数组大小才需要显式写成 `const`。

**运行时开销。** 无。生成的 C 代码与基线完全相同，唯一的区别是字面量数据现在以 `static const` 发出（检查器不允许对其进行任何写入，因此即便分析存在漏洞，也会触发硬件错误而不是悄悄破坏内存）。

**实现**（两个提交中的第一个）：约 250 行代码，涵盖：

* 每个类型上的 `cq` 位，在类型相等判定、类型替换和类型输出器（dumper）中处理（`const` 绑定在基础类型之后的第一个 `&` 或 `[:]` 上，否则绑定到整个类型；`(const i64[3])&` 和 `const (u8[:])&` 需带括号书写）；
* 槽位处的存储规则（由字段、元素、赋值和带注解声明的检查所设置，并由参数和返回值检查所清除的作用域标志）；
* `FitsAt` 和分支类型统一（unification）中的“添加 const”隐式转换；
* 回读时的常量性，以及参数和返回值的常量性；
* `extern` 检查；
* 取代被删除的传递性 `let` 规则的机制：在左值路径的最后一步上打 `letbound` 标记（这是 `let` 现在唯一禁止的操作）、从路径每一步的类型中读取内容可写性，以及针对 `for`/`match` 的拷贝绑定规则。

窄化 `const T?`、加载相对引用以及解析 `const Alias` 时，也都必须保留该修饰符。

<a id="others-considered"></a>
### 其他考虑过的方案

* **只读内存页。** 将字面量数据发射为 `const`（或对其调用 `mprotect`），使被洗白的写入触发段错误。这没有任何性能代价，且只需改一个词，但它把一个编译期问题变成了运行时崩溃，并且对带有运行时初始化器的常量无能为力。它值得作为方案 2a 或 2b 之*上*的一层保险来检查分析是否存在漏洞，但不能作为修复方案本身。
* **存储时拷贝。** 仅在将字面量切片存入容器的位置将其物化（materialize）。然而待存入的切片可能是一个绑定了多个不同字面量之一的变量，因此这种拷贝将变成对任意切片的运行时 `memcpy`。它同时背负着方案 1 的开销和方案 1 的生命周期规则，外加一条更怪异的规则。
* **完全禁止洗白。** 对所有来源（而不仅仅是静态数据）都在存储过程精确追踪可写性。这就是泛化版的方案 2b，但它会拒绝规范刻意选择支持的、有文档记录的 const 转换（通过结构体洗白 `let` 局部变量）。
* **线程禁止读取 `let` 全局变量。** 这可以在不使用上述任何方案的情况下堵住常量这一半的漏洞，但 mandelbrot 示例中工作线程读取 `let W = 78;` 恰恰就是该例外存在的理由。

<a id="4-recommendation"></a>
## 4. 推荐方案

应当排除方案 1。虽然它让所有内存都留在栈上，但每一个以 `u8[:]` 返回名称的函数都会无法编译，且向切片参数传递字面量都会引发拷贝。其实现也并不比其他方案更精简：它需要为每个函数新增一个带独立作用域管理的栈，且仍需借用方案 2a 的常量规则。这些隐式拷贝同样违背了规范既定的目标。

方案 2b 可行且最为精确，但它正是此前讨论所预期的那种“复杂分析”：大约 300 行代码，触及来源流经的每一个角落。此外，它的诊断信息无法指出究竟是哪一次存储“污染”了容器。首次实现所漏掉的三条路径也表明，它与现有的根分析并存时将带来可观的维护负担。

从语言设计角度来看，方案 4 更胜一筹。它移除了洗白规则及其“const 转换”漏洞。可写性成为了声明中直接可见的类型属性。这同时也支持了数据结构中的只读视图、明确标明 C 代码可写范围的 `extern` 声明，以及可接受字面量的 `split`。

其代价是在持有只读数据的槽位上增加额外注解：在整个代码库中仅涉及九处位置以及 `os` 外部函数。就像在 C++ 中一样，以视图为键的泛型容器必须显式指定 `const u8[:]`。为防止线程数据竞争，正确的注解是必需的，但编译器检查器会强制执行它们：`const` 永远不会被隐式丢弃。因此，静态数据可以被证明绝不会被写入，从而能直接发射为 C 的 `const`。

与方案 3 相比：方案 3 对语言零侵入，且在不使用工作线程时零运行时开销，并保留了规范刻意选择的洗白机制。如果洗白值得保留，那么方案 3 就是最佳修复。然而产生 §9.5 的那场讨论曾指出，当年的目标是在尽量减少注解的同时维护 const 正确性，而方案 4 正好保留了这一性质——因为只有槽位才需要注解。所以，如果“const 转换”漏洞当初只是一个妥协而非故意设计的特性，那么方案 4 会带来更好的语言设计，而方案 3 对于字面量也就没有必要了。

在其余方案中，真正的抉择在 **2a** 和 **3** 之间。

* 2a 是一条不需要复杂机制的语言规则：“从存储中读出的 `u8` 切片是只读的；指向常量的引用永远不能被存储。”它没有运行时开销，代码库无需任何改动，其限制源于编译器无法判定容器里究竟存了什么。而且 `u8[:]` 本身也常用于只读场景。它的代价是语言多了一条受限于实现能力而制定的规则，且持有可写字节视图的结构体必须改持数组引用。
* 3 不改变任何程序可见行为，只是让工作线程不再共享静态数据——而规范的线程模型原本就是这么定义的。它让“作为边界情况尚可接受”保持在原本单线程语境下的真实性，并保留了规范有意选择的洗白规则。它的代价是一套仅存在于多线程程序中的运行时机制（约 60 行），以及在这些程序中访问静态数据时多出的一次间接寻址——但这一点在任何实测中都未体现出开销。

最终推荐**方案 4**。它需要的源码改动极少，把注解放在了读者确实需要知道已存储视图是否可写的位置，且不需要任何运行时机制。
如果决定将洗白规则作为一项特性保留下来，则应采用**方案 3** 搭配方案 2a 的规则 2（常量永远不可被存储）。这样一来，线程可见的常量仍可保持为普通的 C 静态变量供 C 编译器折叠优化，只有字面量才进入按程序隔离的映像中。这是改动最小、语言代价也最小的组合。单纯的方案 2a 则仍是一个健全、零开销的兜底方案。

<a id="6-globals-were-c-statics"></a>
## 6. 全局变量曾是 C 静态变量

§1 中关于常量的那一半问题还有第二个成因，与洗白无关：所有全局变量过去都是进程级的 C 静态变量。定长全局变量是 `static T name`，而可调整大小的和变长全局变量则是一个静态头部加上一个专用的静态栈。这就是为什么工作线程曾经只被允许读取常量。这与 §11.1 自身的模型相矛盾——在该模型中，程序运行在一个隐式的最外层函数内部，全局变量是这个函数的局部变量，而 `thread_fn` 则是一个拥有自己一套实例的独立程序。

第二个提交让这个模型成为了现实。每一个非只读静态数据的全局变量现在都成为“每程序实例一个结构体”中的成员，可调整大小全局变量的专用栈也位于该结构体内部。（只读静态数据指的是带有编译期初始化器的 `const` 全局变量，所有实例都可以按原样共享它。）主程序的实例是一个静态结构体。工作线程的实例由其入口 thunk 分配，并用派生映像（spawn image）填充。在参数之后，派生映像以 `[size][image]` 记录的形式携带了工作线程程序所使用的全局变量（可调整大小全局变量的记录就是其队列映像；`reusable` 池的记录则携带其空闲链表）。工作线程读写的是自己的副本，而工作线程再派生的工作线程则拷贝上一级工作线程的副本。如果某个全局变量的类型不是扁平的，它在线程程序中就会报错，就像非扁平参数一样。每次全局变量访问都通过 `K_GL->` 进行。在没有工作线程的程序中，它就是 `(&k_globals_main)`，一个链接期常量，因此生成的代码与以前完全一样。在有工作线程的程序中，它则是线程局部变量 `k_gl`，即所有数据栈访问已经在使用中的寻址方式。

借此，工作线程读取的 `let W = 78;` 就是工作线程自己的 `W`，无论任何人对 `&W` 做了什么操作；mandelbrot 示例也得以保留其 `let` 声明。类型检查器的规则简化为“仅限扁平全局变量”，而剩下的 C 静态变量只有字符串字面量和编译期 `const` 全局变量，两者均被证明永远不会被写入。`test/threads/thread_globals.k` 分别在工作线程以及工作线程派生的子工作线程中测试了计数器、可调整大小的日志、通过引用写入的 `let` 数组、结构体、变长字符串、带空闲链表的池以及 `const` 常量，并在每次操作后检查主线程的值。这也使方案 3 的每线程静态映像不再必要：同一套机制现在已经覆盖了所有全局变量，而字符串字面量也由于没有任何代码能写入它们，不再需要按实例拷贝。

<a id="7-side-findings"></a>
## 7. 附带发现的问题

以下问题是在排查过程中发现的。它们都不是由上述分支引起的，且每一个在本次会话的暂存区中都有单文件复现用例：

* **在非定长局部变量之前的 `continue` 会导致崩溃**（基础编译器，`-O0` 和 `-O2` 均会复现）：`for x in xs { if x == 0 { continue; } let s: u8[] = "abc"; … }` 会发生段错误。循环的 continue 标签会恢复循环作用域中保存的所有栈顶，包括被 `continue` 跳过的那个局部变量的基址，于是 `s` 的基址在尚未设置时就被读取了。方案 1 一上来就撞上了这个问题，并通过改为在作用域入口处保存其自身栈顶绕过了它；同样的修复也适用于普通局部变量。
* **在 `-O0` 下通过从结构体字段读出的胖引用执行 `push`** 会把压入的字节写到别处：`struct Buf { bytes: u8[>..]& }` … `fn bump(b: Buf&) { b.bytes.push('!'); }` 在 `-O0` 下打印 `Hello\0`，而在 `-O2` 下打印 `Hello!`。方案 2a 的正向测试不得不避开了这一模式。
* **语句临时值的切片可以被绑定到变量上**：当 `f` 返回 `u8[]` 时，`let s = f()[..]` 能通过类型检查（临时值的哨兵根作为绑定被接受了），但代码生成会在语句结束时恢复该临时值的栈。它目前之所以能侥幸运行，仅仅是因为每个临时值在函数内部分配到了自己专属的栈。（现已修复：临时值的根锚定在其所在语句的深度，不带类型注解的绑定同样受存储规则约束，见 §9.2。）
* `codex/readonly-literals` 实验分支遗漏了方案 2b 下所列出的“指向元素的引用”路径。
