# 基于十六项基准测试的下一阶段编译器工作

> **已弃用的语言特性：** `reusable` 与 `reusable[]`。请改用
> [`slot_pool<T>`](../stdlib.md#slot_pool) 管理槽位，以及
> [`slice_pool<T>`](../stdlib.md#slice_pool) 管理连续切片区间。
> 下文提及的内建行为与历史示例对现有代码依然适用；待其余迁移缺口补齐后，将另行安排移除。

*本计划记录了已完成的一轮工作：每个优化项是如何筛选并实测的。`adoption.md` 记录了最终采用的结果。其余待办工作请参阅 `notes.md` 末尾的列表。*

以下改动旨在消除基准测试套件所测得的性能差距，并进一步提升 K 已经表现良好的工作负载。其中大多数改动涉及编译器本身；少数则需要语言层面的调整。下文每一项均附有实测数据，或明确标注为“未实测（not measured）”。所谓“实测”，是指对生成的 C 代码进行手工改写，或在 K 中用两种写法实现同一基准测试，并在 `results.md` 所列机器上以 `large` 规模进行计时。手工改写用于估算等价编译器改动所能达到的收益上限；多数测试项的计时波动为 5-10%，而两个受缓存限制的随机访问测试项（`lru`、`graph`）波动约为 ~15%。

<a id="1-where-the-time-goes-per-deficit"></a>
## 1. 按性能短板划分的时间开销去向

以 `large` 规模对比最佳安全 Rust 版本的耗时比值及其成因如下：

| 基准测试 | K 对比 Rust | 性能短板成因 | 实测情况 |
|---|---:|---|---|
| `bintrees` | 0.64x | 通过胖引用（fat reference）执行压栈；未对基准情形（base case）进行内联；v145 下未做尾递归消除（TRE） | 手工修复后：356 -> 229 ms（v145），381 -> 252（clang），Rust 为 227 |
| `lru` | 0.61x | 在纯重链接（relink-only）负载上使用自相对（self-relative）链接编码 | 索引版 2,397，普通引用版 2,557，相对引用版 3,738（v145） |
| `calc` | 0.78x | `varint` 数值占 11%；`return from` 判别值（估计占 5-10%）；解析循环代码生成 | 改用 `i32` 数值：548 -> 487 ms |
| `scene` | 0.79x v145, 0.98x clang | 后端差异：C++ arena 版本同样落后其 clang 构建 9% | 填充至 120 字节：无变化 |
| `blur` 扁平版本 | 0.16x | v145：每像素 9 次越界检查阻碍矢量化；clang：通过胖引用重复读取头部字段 | 行切片版：133 -> 33 ms（v145），131 -> 31（clang） |
| `particles` | 0.95-0.98x | 栈顶缓存未生效，而 clang 原本已将其保留在寄存器中 | clang 下慢 6%，来自上一轮 A/B 测试 |
| `respond` DTO 对比流式（streaming） | 相差 30% | 内联后的命名返回值是先构造再拷贝到字段中，而非就地构建 | 两个 K 版本对比：559 vs 427 ms |
| 按引用 `push` | 8% | 通过胖引用执行压栈 | `push_ref` 探针测试：167 vs 155 ms |
| `graph` 链表版、`graph_csr` | -- | 从内存加载的索引（loaded-index）的越界检查 | 分别为 5-6% 与 ~10%（上一轮数据） |

解析、变体记录（variant-record）、字符串和树遍历类基准测试在各自对比中已经领先。对 `return from`、分发合并（dispatch merging）和命名返回值的改进有望让它们进一步提速。

<a id="2-compiler-work-ordered-by-measured-benefit"></a>
## 2. 编译器工作（按实测收益排序）

<a id="21-cache-data-stack-tops-through-fat-references"></a>
### 2.1 通过胖引用缓存数据栈栈顶

每次压栈时，`make(pool: TNode[>..]&, ...)` 生成的 C 代码都会在内存中读写 `pool.stk->top` 四次，并执行 `pool.hdr->len++`。这是因为任何持有胖引用的函数都会被完全排除在栈顶缓存之外（`CanCacheTops`）：该引用携带的栈对象也可能被函数直接具名引用，因此两种访问栈的路径可能存在别名（alias）。若将栈顶保存在局部变量中，并仅在递归调用前后刷新回内存（采用与全局栈缓存相同的规则），`bintrees` 在 v145 下可从 356 ms 降至 313 ms，在 clang 下可从 381 ms 降至 331 ms（-12%、-13%）。`push_ref` 测得，将同一循环移入通过引用访问数组的函数会带来 8% 的开销。

别名判定应由检查器（checker）而非后端来回答。每个引用参数在每次特化中都有一个根类（root class）；处于不同根类中的两个胖引用必然指向不同的栈，而胖引用只有在其根类*正是*函数直接具名引用的那个全局变量时，才可能与之产生别名——这在代码生成阶段是完全可见的。因此，方案是按根类将 `ref.stk->top` 缓存为局部变量，将同根类的引用视为同一栈，仅在极少见的特化情形（某根类对应函数内同时直接具名引用的全局变量）下回退到内存访问形式。`calc` 不受此项影响（压栈在其工作量中占比很小；全局池变体耗时相同），因此该优化在压栈密集的被调函数上可带来 8-13% 的收益，而在其他场景下无影响。

<a id="22-inline-the-base-case-of-a-self-recursive-function-one-level"></a>
### 2.2 将自递归函数的基准情形单层内联

Rust 的 arena 版 `bintrees` 在构建与检查两阶段都比 K 和 C++ vector arena 快 1.6 倍，从 rustc 的汇编输出可以看出原因：LLVM 将递归单层内联，从而消除了所有叶节点调用。手工改写 `make`，使 `depth == 1` 时直接内联构建两个叶节点（叠加 2.1 和 2.3），可让 `bintrees` 在 v145 下从 356 ms 降至 229 ms，在 clang 下从 381 ms 降至 252 ms，与 Rust 的 227 ms 持平。仅此展开一项就在 2.1 的基础上带来了约 27% 的提升。

优化器从不内联调用环中的成员（“cycles never inline”）。针对性实现成本很低：对于函数体以基准情形 `if <param test> { return <leaf construction> }` 开头的 `recursive fn`，将每个自调用点 `f(..., e)` 改写为 `if <test on e> { <leaf construction with e> } else { f(..., e) }`。这会将套件中所有完整树遍历（`tree`、`interp`、`sexp`、`scene`、`calc`）的函数调用次数减半，且无需通用的递归内联；若模式匹配过于狭窄，后续再考虑基于体积上限的通用单层内联。

<a id="23-accumulator-tail-recursion-elimination"></a>
### 2.3 累加器尾递归消除（TRE）

将 `check` 中的 `1 + check(l) + check(r)` 改写为带累加器的循环，可在 v145 下为 `bintrees` 减少 7% 耗时，在 clang 下则无变化（clang 已自行完成该变换）；同一变换在上一轮测试中为 `tree` 在 v145 下带来了 7.5% 的提升。其匹配模式为形如 `e op self(x)`（或 `e + self(x) + self(y)`，对最后一个调用改写为循环）的返回语句，其中 `op` 满足结合律。K 编译器已经掌握完整的调用图且要求标注 `recursive fn`，因此已具备该变换所需的全部信息；此项工作的唯一目的是让 v145 追平 clang。

<a id="24-hoist-array-views-reached-through-fat-references-out-of-loops"></a>
### 2.4 将通过胖引用访问的数组视图外提至循环外

`blur` 的核心循环在每次访问时都会读取 `src.hdr->base` 和 `src.hdr->len`，而 clang 无法将其外提，因为通过 `dst` 写入字节可能会与数组头（header）产生别名。在 W=2048 时，该核心循环耗时 131 ms，而先取一次整数组切片再循环的等价版本仅需 31 ms。现有的循环视图外提（`7a7ac87`）仅对局部变量和全局变量生效。将其扩展到引用参数同样安全，原因与全局变量一致：只有扩容、缩容操作，或可能触及该数组的函数调用才会改变 `base`/`len`，而越界检查消除（BCE）的 kill 摘要已经标明循环体中是否包含此类操作。通过任何引用进行的元件写入都不会改变它们。此项预期在 clang 下为 `blur` 带来 4 倍提速，且适用于语言中所有 `fn kernel(a: T[>..]&, ...)` 形式的函数。

<a id="25-bounds-check-analysis-three-extensions"></a>
### 2.5 越界检查分析：三项扩展

a. **将切片长度表示为差值。** `let a = src[lo..lo + W]` 应当记录 `len(a) = W`；当两端点均被跟踪时，`hi - lo` 已经可以在差值域（difference domain）中表达。目前 `blur_rows` 每行都需要一个 `assert(a.len == W)` 才能达到 10/10 消除率；此扩展可省去该断言，使行切片写法成为最直观自然的惯用法。
b. **循环计数器的乘积。** 在 `y < H - 1`、`x < W - 1` 且 `len == W * H`（计数压栈循环 `for i in W * W` 已经将长度声明为乘积）的情况下，`src[y * W + x]` 仍保留了全部九处越界检查；在 v145 下，仅这些检查本身就造成了 4 倍的开销（133 vs 33 ms）。针对二维惯用法增加一条专门规则——当 `0 <= j < c`、`0 <= i < m` 且 `len >= m * c` 时将索引 `i * c + j` 记录为乘积项——实现自洽且可覆盖图像核、矩阵及通用行主序表。在 clang 下这些检查没有可测量的成本（clang 会像对待 Rust 一样绕开检查进行矢量化），因此本项解决 `blur` 在 v145 下的开销，而 2.4 解决其在 clang 下的开销。
c. **数组元素内容不变式**（上一轮数据：`graph` 5-6%，`graph_csr` ~10%）：“`q` 的每个元素都是 `dist` 的合法索引”。这是消除从内存加载索引（loaded-index）相关检查的唯一方式，此类检查在 `graph`、`words`、`lru`（0/19）以及 `scene` 的子节点循环的残留检查中占大多数。该项并不紧迫：索引版 `lru` 即使带有 37 处此类检查，仍比相对引用版快 1.5 倍，说明这些检查在当前位置的开销很小。

<a id="26-build-inlined-named-results-at-the-destination"></a>
### 2.6 在目标位置就地构建内联后的命名返回值

`respond` 的 DTO 版本比其流式版本慢 30%（559 vs 427 ms），生成的 C 代码揭示了时间去向：`name_of`、`sku_of` 和 `make_items` 都被内联（各自仅调用一次），而内联器将“构造命名局部结果并返回”转化成了“在新栈上构造，再 `memcpy` 到目标字段”。语言规范中的保证（7.3，命名结果直接在目标位置构建）仅在非内联的值形式下成立，一旦被调函数被内联就会失效——而对组成 DTO 的小型构建函数来说，被内联反而是常态。

修复方法是将内联后被调函数的 NRVO 局部变量绑定到接收槽位：其元素直接写入目标栈，随后再写入接收方的长度前缀。对于定长前缀（`u32`、`u16`），先在元素前预留前缀空间，之后直接回填，无需任何拷贝。对于 `varint` 前缀，直到计数确定前无法得知前缀字节数，因此先预留 1 字节，仅当元素数达到 128 时才将元素后移——这属于极少数情况。对于非内联形式，`EmitReprefix`（将 `T[]` 结果存入 `T[varint]` 槽位）与 `EmitNrvoPrefix`（将可调大小局部数组作为变长数组返回）中的 `memmove` 也可替换为同样的“预留后回填”机制。收益上限即 `respond` 两个版本之间 30% 的差距，其中一部分来自从对象渲染而非构建对象本身；这部分未单独测量。

<a id="27-stop-caching-the-stack-top-where-the-loop-does-not-push"></a>
### 2.7 当循环内不压栈时停止缓存栈顶

在 `432f8ce` 提交中，此问题在 clang 下的两个浮点核心循环上仍造成 6% 的性能损失：缓存栈顶的局部变量仅在真正执行压栈的循环中才是净收益。应按循环（而非按函数）发射栈顶缓存形式——仅当循环体包含对该栈的扩容操作时才缓存。这与上一轮列表保持一致；本轮测得 `particles` 在 v145 下落后 Rust 2%，在 clang 下落后 6%。

<a id="28-seed-a-cycle-functions-return-root-before-its-back-edges"></a>
### 2.8 在回边之前为调用环函数预设返回根

递归调用的结果会继承被调函数截至目前所记录的根（root）。在互递归解析器中，入口函数在遇到回边（back edge）之前尚未记录任何根，导致 `calc` 携带着一个普通引用的 Paren 节点，且返回值被定根于静态数据。这同时也是不健全（unsound）的，因为该返回值可能被存入全局变量（spec TODO 0g）。修复方案是以不动点迭代计算调用环内各函数的返回根：收集每个环内函数的返回点（`pool.push(...)` 给出该池的根类；若 `return x` 中的 `x` 来自环内调用，则给出对应被调函数的根），迭代至收敛，再检查函数体。此改动对耗时影响很小，但能移除旗舰级基准形态中的一个人工残留节点并堵住一处类型健全性漏洞。

<a id="29-relative-references-the-relinking-cost"></a>
### 2.9 相对引用：重链接开销

`lru` 在 `large` 规模下，v145 / clang 三次取最佳结果：

| 链接方式 | 节点字节数 | v145 | clang |
|---|---:|---:|---:|
| `Node&<u32>?` 自相对（当前测试行） | 16 | 3,787 | 3,143 |
| 同上，手工移除读取时的判空测试 | 16 | 3,498 | 3,083 |
| 同上，手工移除写入时的范围检查 | 16 | 3,353 | 2,775 |
| 两者均移除 | 16 | 3,242 | 2,724 |
| `Node&<u64>?` 自相对（不发射范围检查） | 20 | 3,573 | 2,881 |
| `Node?` 普通引用 | 24 | 2,557 | 2,352 |
| `i32` 索引，带越界检查的 `pool[i]` | 16 | 2,397 | 2,266 |

范围检查与判空测试合计占该项耗时的 14%；手工全部移除后，相对引用形式仍落后索引版 35%。该差距在 `small` 规模（命中缓存）为 13-21%，在 `large` 规模为 41-55%，说明剩余差距源于该编码在指针追踪（pointer chase）中的内存级效应：每一跳都要经历一次 32 位加载、一次符号扩展、一次与*字段自身*地址的相加，以及一次判空测试，之后才能发出下一次加载。这是最先需要用硬件性能计数器排查的问题。由此引出两个编译器改进项与一个语言设计问题：

* **当位宽足以覆盖整个栈时跳过范围检查。** 对任何小于 2 GB 的池而言，`u32` 偏移量都是精确的；运行时预留大小是一个编译期常量（`K_STACK_RESERVE`），因此只需在超出位宽时才发射检查。此项在此处最高可带来 11-12% 的收益，对单次构建型基准则无影响（采用 `u64` 链接的 `bintrees` 与 `u32` 耗时相同）。
* **哨兵链表使用非可选链接。** 每次读取都要判空的原因在于链表链接是可选的，而它们之所以设为可选，仅仅是因为两个哨兵节点在构造时还没有对象可以指向：在第一个节点出现之前，非可选的 `Node&<u32>` 没有可用值。若提供一种能在构造时指代正在构建的值本身的语法（例如 `Node { prev: self, next: self }`，或在文档中明确规定“非可选相对引用上的偏移量 0 表示值自身”），整个链表便可使用非可选类型并省去判空；`a8c9f69` 在加载非可选相对引用时已经省略了判空。此处可带来 2-8% 的收益。
* **基于池基址的相对偏移（pool-relative offsets）**（见 3.1）可将加载变为 `base + off`（基址保存在寄存器中），其形态与运行快 1.5 倍的索引版一致。这是一项会引入根追踪成本的语言改动，当时的指导原则如 `notes.md` 所述：相对引用适合一次构建后遍历的数据结构，而频繁重链接的 `reusable` 结构更适合使用普通引用或索引。

<a id="210-varint-fields-on-hot-values"></a>
### 2.10 热路径数值上的 `varint` 字段

`calc` 改用 `Num { v: i32 }` 替代 `varint` 后耗时从 548 ms 降至 487 ms（-11%）。问题并不在解码器本身：手工在 `k_uleb_read` 中加入单字节快速路径反而让测试*变慢*（599 ms；额外分支的代价超过了所跳过的循环）。开销来自每次求值数字时都要付出一次解码而非直接加载的代价。这带来两点结论。第一，语言使用指南应当说明：`varint` 适用于取值范围宽广或不可预测的数值，而范围已知的数值应使用定长整数（此处取值仅在 1..99，甚至可用 `u8`）。第二，值得尝试的代码生成优化是将 `varint` *字段*读取解码为 `b < 128 ? b : slow(p)` 并把慢路径外置（out of line），此前在内联循环中的手工实验未能做到这一点。

<a id="211-unchanged-from-last-round"></a>
### 2.11 与上一轮保持不变的条目

* **合并对同一审查对象（scrutinee）的重复分发**（`sexp` 的 `walk_chain` 对标签执行了两次 `switch`）。纯属重复逻辑；未实测。
* **发布构建使用 `/arch:AVX2` 或 clang。** 上一轮中 clang 为 `sum` 带来了 13% 提升；本轮又新增了 `scene`（clang 下快 24%）、`respond` 流式版（22%）、`blur_rows`（15%）和 `lru`（18%），在这些项目中后端选择的影响大于上述任何单一优化。

<a id="212-return-from-not-measured-estimated"></a>
### 2.12 `return from`：未实测，仅作估算

判别值是一个通过传出参数传递的 `int32`，在传播路径上的每次调用后都会被检查：`calc` 有 45 处此类调用点，在 160 万组输入上每组约调用 60 次，总计约 1 亿次高度可预测的分支与加载：按指令数估算约占该项耗时的 5-10%（尽管数据从未离开 L1 缓存）。旨在测量该开销的手工实验（在无错误变体中屏蔽检查）发生了崩溃，因为相同的临时变量模式也被普通布尔值复用；要获得干净的测量结果，需要一个能省略此类检查的编译器标志。若实测证明其确实重要，存在更廉价的替代方案：将判别值与定长返回值一起通过寄存器返回（双寄存器结构体返回），而非经过内存传递；并跳过对不可能向任何存活目标传播的函数调用之后的检查。

<a id="3-language-and-spec-questions-the-measurements-raise"></a>
## 3. 实测数据引发的语言与规范问题

<a id="31-self-relative-or-pool-relative-offsets"></a>
### 3.1 自相对偏移还是基于池基址的偏移

*结论：两者并存，按字段按需选择。自相对偏移保持为默认；字段可声明为相对于某个具名全局池（`T&<u32 in pool>`，规范 §3.9）。支撑该决策的对比分析见 `docs/design/relative_references.md`。*

规范 3.9 将相对引用定义为自相对，是为了让整个链接区域作为整体具备位置无关性，并允许任意子区域整体迁移（即 TODO 16 中的整区域拷贝，目前尚未实现）。在重链接负载上，`lru` 为这一选择付出了 1.5 倍的性能代价，而索引版展示了替代方案所能赢回的收益。以*池*基址为基准测量的偏移量在加载时执行 `base + off`（`base` 驻留在寄存器中），存储时执行 `ptr - base`。它不依赖字段自身的地址，且在池小于 4 GB 时无需对 `u32` 做范围检查，同时整个池依然支持内存映射。其缺点在于每次加载相对引用都需要获取其根的基址，而检查器的根追踪恰恰在一个地方过于保守：从容器读回的引用会被定根到该容器（9.5），因此 `slots[i].node.next` 会按错误的基址去解析。于是，池基址相对偏移要么依赖对存储引用进行精确的根追踪（由于结构体字段“对其根隐式泛型”——9.2，这方面的大部分机制已经存在），要么依赖随引用携带的运行时基址。在做出规范决策前，值得在编译标志控制下做一次实验；潜在收益是彻底抹平 `lru` 的全部性能差距。

<a id="32-a-constructible-self-reference"></a>
### 3.2 可构造的自引用

为了使非可选相对链接可用于循环数据结构（2.9），正在构造中的值需要一个名字，或者需要为非可选槽位上的偏移量 0 定义明确语义。第二种方案与现有底层表示一致（`a8c9f69`），因此只需将其写入文档（“由 `self` 构造的非可选相对引用字段指向包含它的值自身”）是改动最小的做法；第一种方案则具备更好的可读性。

<a id="33-return-roots-across-a-cycle"></a>
### 3.3 跨调用环的返回根

2.8 改变了检查器所接受的代码范围（环内函数可以 `return` 回边调用的结果）；规范 7.8 应当明确调用环的返回根是环内所有返回路径上的不动点，由此 TODO 0g 也可一并移除。

<a id="34-row-slices-not-a-2d-type"></a>
### 3.4 行切片，而非二维数组类型

当 2.5a 与 2.5b 就位后，行切片核函数无需断言，扁平核函数也能在编译期证明所有越界检查，因此语言本身不需要引入多维数组类型即可在图像与矩阵计算上获得高性能。这一点值得写入性能说明文档：按行切片，并在行内索引。

<a id="35-scratch-buffers-that-hand-out-slices"></a>
### 3.5 可分发切片的暂存缓冲区（Scratch Buffers）

`calc` 之所以按索引读取一个支持增删（grow-shrink）的全局输入缓冲区，是因为只增不减（grow-only）数组没有 `clear`，而增删数组不允许取切片。如果允许对只增不减的*局部*数组在没有任何以它为根的引用或切片存活时调用 `clear()`，就能以零运行期开销提供规范 TODO 4 所要求的可复用、可切片的暂存空间。这能解决新基准套件中唯一一处迫使代码在复用与引用之间二选一的情况；预计不会直接提升运行速度。

<a id="36-arithmetic-width-and-varint-in-the-performance-notes"></a>
### 3.6 性能说明中的算术位宽与 `varint`

这两项属于编码指导建议而非语言变更。`u8` 采样点之和会发生回绕（6.2），需要在每个采样点上写 `as u16`；`blur` 的初版正是因此产生了错误结果。此外，`varint` 每次读取都会付出一次解码开销（2.10）。这两点都应收入紧邻附录 A 的“存储类型选择”说明中。

<a id="4-suggested-order"></a>
## 4. 建议推进顺序

1. **代码生成层（低风险，沿用本轮既有机制）：** 2.1（通过胖引用缓存栈顶）、2.4（通过胖引用外提视图）、2.7（仅在压栈循环内缓存栈顶）、2.5a（切片长度）、2.9 的跳过范围检查。预期收益：`bintrees` -12%，按引用 `push` +8%，`blur` 在 clang 下快 4 倍，`particles` 在 clang 下快 6%，`blur_rows` 无需断言，`lru` +11%。
2. **优化器层：** 2.2（基准情形内联）、2.3（尾递归消除 TRE）、2.6（内联命名结果就地构建）、2.8（不动点返回根）。预期收益：`bintrees` 追平 Rust，`tree` 在 v145 下 +7%，`respond` DTO 最高提速 30%，`calc` 消除多余的 Paren 节点。
3. **静态分析与语言层：** 2.5b（乘积索引：`blur` 在 v145 下快 4 倍）、2.5c（数组内容不变式）、3.1 的池相对偏移实验（解决 `lru` 短板）、3.2（自引用哨兵）、3.5（可清空暂存区）。
4. **后续测量：** 为 `lru` 相对引用版采集硬件计数器，增加用于 2.12 的跳过 `return from` 检查的编译标志，并在以上三轮改动每一轮完成后重新运行全套基准测试。`notes.md` 中的可复现性注意事项适用于此处的所有数字。
