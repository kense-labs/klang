<a id="index-types-and-checkfree-kernels"></a>
### 索引类型与 checkfree 内核

两种图实现现在都将目标顶点和队列条目存储为 `u32 in dist`。CSR 实现还额外将前缀偏移存储为 `u32 upto out`。数组依然采用四字节元素，并执行相同的图构造与四次广度优先搜索。`dist` 和 `out` 会在构造用于校验它们的类型化值之前完成初始化。

两个 `bfs` 函数均标记为 `checkfree`。每次搜索开始时，都会通过一条关于配套 head/offset 数组的长度断言声明一次它与 `dist` 的关系。此后遍历过程中的每一次访问都可获得编译期证明，包括从另一个数组中加载出来的索引。CSR 的后继偏移量在加一之前会先将顶点拓宽为 i64，从而使证明无需考虑回绕的 u32 算术运算。

在各源文件默认规模下，`--bce-lines` 报告如下：

| 源文件 | 已消除的索引检查 | 已消除的切片检查 | 契约 |
|---|---:|---:|---|
| graph | 12/12 | 0/0 | BFS |
| graph_csr | 23/27 | 0/0 | BFS；构造阶段保留四处检查 |
| blur | 20/20 | 0/0 | 扁平内核 |
| blur_assert | 20/20 | 0/0 | 带显式前置条件的扁平内核 |
| blur_rows | 20/20 | 8/8 | 行切片与模板算子 |

blur 与 scene 中的标注只是强制约束编译器本就已完成的越界检查消除，并不会改变计算本身。此前曾尝试重写 LRU，但无法基于动态表长证明掩码探测索引的边界，因此未予采纳。本次更新并不声称每一个基准测试都完全无检查。

<a id="reading-the-rust-rows-historical"></a>
## 解读 Rust 各行（历史记录）

Rust 对比组均采用安全、惯用的实现。C++ 则单独区分了惯用层级与专家优化层级。当同一基准在所有权或数据结构上存在两种不同的 Rust 实现时，两者都会列出：

* `strlist` 包含 `Vec<String>` 和 `Vec<&str>`，两者在*所有权*上不同。只有前者可以比其来源文本活得更久，而这正是 K 对应行所具备的语义。
* `tree`、`interp`、`sexp`、`scene`、`calc` 和 `bintrees` 分别包含一个拥有指针的行（`Box`）和一个 Arena 行（`Vec` 加 `u32` 索引）。两者都是安全且惯用的写法；对于重指针结构，Arena 是社区推荐的做法，`design.md` 也曾预言它才是真正的对比基准而非 `Box`。这一预测得到了验证：在同时包含两者的六个基准测试中，Arena 行比 `Box` 行快 2.5x（`calc`）到 14x（`bintrees`）。
* `graph` 有三行，原因与 C++ 侧相同：`Vec<Vec>`、CSR 以及单遍索引链表 Arena。CSR 在所有语言中都是最快的，并且在所有语言中都基于索引，因此 `graph` 是唯一一个“引用对比索引”问题并未体现在最快那一行上的基准。
* `words` 和 `lru` 同时包含 `HashMap` 行与手写开放寻址表行。std 默认哈希器优先考虑安全性而非速度。Rust 程序员通常会改用第三方哈希 crate，但本基准测试集仅允许使用 std。在 `lru` 中，两行对节点使用相同的 `Vec` Arena 与空闲链表；唯一的区别在于映射表。此处使用 Arena 同样是惯用选择：std 没有侵入式链表，而 `LinkedList` 不提供指向单个节点的句柄。
* `respond` 包含一个 DTO 行（每次请求构建 `String` 和 `Vec<Item>`，再由函数渲染并返回新的 `String`）以及一个将 JSON 直接写入单个复用 `String` 的流式行，分别对应 K 的两行。
* `blur` 有一个逐元素索引的版本和一个使用行切片与 `windows(3)` 迭代器的版本。当性能剖析显示越界检查开销较高时，后者是规避检查的常见手段。但在这里它们开销并不高（见越界检查一节）。

其余基准均只有一行。汇总表将 K 与本测试集中最快的 Rust 实现进行对比。

编译参数为 `-O -C codegen-units=1`。使用单个代码生成单元与 C++ 的编译模型一致：每个 C++ 行都是作为一个整体编译的单个翻译单元，而若使用 rustc 默认的 16 个单元，Rust 就无法获得同等的跨函数视图。其余所有设置均采用发布版 Rust 二进制文件的默认值：开启越界检查、使用展开式 panic，且除与 C++ 行共同针对的 x86-64 基线外不指定额外 `target-cpu`。因此 K 与 Rust 均带有检查，而 C++ 作为无检查基线。

<a id="data-layouts-and-memory-use"></a>
### 数据布局与内存占用

使用 `size_of` 和 `sizeof` 测得，或直接从紧凑声明中读取：

| | Rust | C++ | K |
|---|---:|---:|---:|
| `tree` 节点 | 12 Arena / 24 `Box` | 12 Arena / 24 `unique_ptr` | 12 |
| `interp` 节点 | 12 | 12，`variant` 与 union 均为 12 | 叶子 5，二元 9 |
| `sexp` 节点 | 24 Arena / 32 + 堆 | 24 Arena / 64 + 堆 | 变长，文本内联，4 字节链接 |
| `records` 事件 | 32 + `Say` 的堆分配 | 48 + 堆 / 24 缓冲区 | 变长 |
| 字符串头 | `String` 24，`&str` 16 | `std::string` 32 | 无：内联 varint |
| `lru` 节点 | 16 Arena，两行均同 | 16 Arena / 24 `std::list` 节点 + 映射节点，各自 malloc | 16 |
| `lru` 映射槽位 | 8（`HashMap` 另有控制字节） | 8 / 32 字节 `unordered_map` 节点 | 8 |
| `scene` 节点 | 120 Arena / 128 + 每节点一个 `Vec` | 120 Arena / 128 + 每节点一个 `vector` | 117 |
| `calc` 节点 | 12 Arena / 24 `Box` + 堆 | 16 Arena / 32 `unique_ptr` + 堆 | 数字 2-3，取负 3，括号 3，二元 6 |
| `bintrees` 节点 | 8 Arena / 16 `Box` + 堆 | 8 Arena / 16 `new` + 堆 | 8 |
| `respond` 条目 | 24 `String` + 16 + 堆 | 32 `std::string` + 8 + 堆 | sku 内联，1 + 6 + 2 varint 字节 |

在 `records` 一行上，Rust 直接击败了 C++，却依然以 4.1x 落后于 K。Rust 的 32 字节相比 MSVC 的 48 字节来自两个方面：`String` 占三个字而 `std::string` 占四个字，且枚举标签存放在指针的 niche 位中，无需独占一个字。但它依然是一个*定长*枚举，因此 16M 个元素中的每一个无论是不是 `Say` 都必须按 `Say` 的尺寸分配空间，而且文本还需要第二次堆分配。这是 Rust 枚举布局的固有属性。

有三种 K 的布局与对应的 C++ 和 Rust 实现存在实质性差异：

* `sexp` 节点只占用其变体实际需要的大小。其符号字节紧跟在 varint 长度之后内联存储，两个链接则是池内的 4 字节偏移量。这使得整个程序比使用 8 字节链接的同一程序小 1.3x——若语言无法将空链接设为相对引用，就只能使用 8 字节链接。
* `scene` 节点是一条 117 字节的记录，其四个子链接是记录内部的有限数组中的 4 字节偏移量（规范 5.3、3.9），因此整个场景是一块连续且位置无关的内存块。C++ 和 Rust 的 Arena 行使用 `uint32` 索引均达到 120 字节，而它们的惯用行则在 128 字节之上还为每个节点的子节点列表额外增加了一个堆上 `vector`/`Vec`。
* `calc` 二元节点仅占 6 字节：一个标签、一个操作符字节以及两个 2 字节相对引用——这已足够，因为单次输入的树跨度绝不会超过几百字节。Arena 的 `u32` 链接使同一节点占到 12-16 字节，而拥有指针的行则达到 24-32 字节外加每个节点一次堆分配块。

<a id="reading-the-toolchain-table"></a>
## 解读工具链表格

两个后端在大多数行上差距都在 10% 以内，谁也没有全面占优。仍然存在的差距如下：

* **clang 能向量化 v145 未能向量化的循环。** K 的扁平 `blur` 是全套测试中差距最大的一项，达到 3.64x（930 对比 256 ms）；紧随其后的两项分别是同一内核的 C++ `__restrict` 行（1.83x）和 `particles cpp SoA`（1.62x）。扁平内核中的每一处检查都已获证明，因此阻止 v145 向量化的原因是别名分析：MSVC 报告通过 `src` 的读取与通过 `dst` 的写入之间可能存在循环携带依赖（C5002，原因 1200），从而让循环保持标量执行。对于行切片形式，MSVC 确实进行了向量化，差距缩小为 1.12x。
* **v145 更擅长 `std::vector::push_back` 与分支分发。** `push cpp vector+reserve` 为 0.61（185 ms 对比 301），且 clang 在每一个 `interp` 行（0.84-0.91）以及 `sum`（带 reserve 的 vector 为 0.93，K 为 0.97）上都落后。
* **clang 在字符串、哈希、分配器以及浮点与指针混合负载上稳定领先 5-25%**：`words`（C++ 各行为 1.10-1.12）、`strlist`（1.06-1.13）、`records variant+string`（1.14）、`sexp unique_ptr`（1.16）、`respond`（C++ 两行分别为 1.16 和 1.23）、`calc cpp arena`（1.16），以及 `scene`——其中 K 行为 1.21，C++ Arena 为 1.10。
* 在 K 自己的各行上：`records` 和 `interp` 偏向 v145（0.89 和 0.91）；`respond` 流式、`particles` 逐元素及 `blur_rows` 则偏向 clang 12-14%，`words` 偏向 1.28-1.33，而 `lru` 达到 1.53，因为其池相对加载指令表现为基址加偏移加载，clang 对此进行了调度优化而 v145 没有。
  此前以 0.84 偏向 v145 的 `bintrees` 现在已打平。

有三条结论会随后端而变化，这也是本报告中每一个比值都按后端分别给出的原因：对比最佳安全 Rust 行，`lru` 在 v145 下为 0.72x、在 clang 下为 1.10x，`scene` 分别为 0.83x 和 1.00x，`blur` 分别为 0.98x 和 1.10x。过去也在这份列表里的 `graph` 和 `bintrees`，如今在两个后端下均已稳定处于 Rust 行的同一侧。

<a id="reading-the-jit-table"></a>
## 解读 JIT 表格

TinyCC 将 C 局部变量保存在栈槽中，仅在单个表达式求值期间将值保留在寄存器里。生成的 C 代码会在后续操作数执行前，先将每个操作数读入各自的临时变量，以防止后续操作数改变先读入的值。clang 和 MSVC 会将这些临时变量优化掉，而 TinyCC 则会把每一个都变成一次存储与重载。这解释了 JIT 各行相对于其编译后耗时从上份报告的 2.96x 上升到本报告 3.48x 的大部分原因。在 `blur` 上，其内核对每个像素都是一长串单一表达式，对 JIT 性能回退进行二分定位指向了引入该操作数求值顺序的提交；正是那次提交把 W=2048 一行从 365 拉长到了 666 ms。

<a id="bounds-check-elimination-measured"></a>
## 越界检查消除的实测结果

编译器能把大多数索引和切片检查证明并消除（规范 10.5）。`bench/bce_ab.py` 在两套工具链下分别以启用和禁用 `--no-bce` 的方式构建每个基准测试，规模采用各源文件内设的默认大小而非报告中的 `large` 规模。`--no-bce` 禁用的不止检查消除：循环视图提升（loop-view hoist）会通过询问 BCE 的 kill 摘要来判断循环的数组长度是否不变，因此关闭该 pass 后，视图在每次迭代时也会被重新读取。这一 A/B 测试同时测量了两者的影响。计数按生成函数统计，因此若一个内核在两处调用点被内联，其检查会被统计两次。

| 基准测试 | 已消除的索引检查 | 切片 | v145 收益 | clang 收益 |
|---|---|---|---:|---:|
| blur | 20/20 | 0/0 | **+82%** | +3% |
| blur_assert | 20/20 | 0/0 | **+81%** | -1% |
| blur_rows | 20/20 | 8/8 | **+191%** | -1% |
| lru | 6/20 | 0/0 | +2% | +7% |
| scene | 12/12 | 0/0 | +5% | 0% |
| respond | 3/3 | 3/3 | +4% | -2% |
| strlist | 1/2 | 1/2 | +4% | -2% |
| calc | 19/22 | 0/0 | +1% | -1% |
| records | 0/1 | 0/0 | 0% | +1% |
| sexp | 11/12 | 0/1 | 0% | 0% |
| graph_csr | 15/21 | 0/0 | 0% | -3% |
| graph | 7/9 | 0/0 | 0% | -6% |
| words | 60/67 | 11/12 | -7% | +1% |
| sum, push, tree, interp, particles, bintrees | 完全没有索引表达式 | | | |

在 v145 下的 `words` 和 clang 下的 `graph` 中，开启该 pass 的二进制反而测得*更慢*。这是受限于缓存的随机访问行所固有的测量噪声底线，并非真实结果。-7% 到 +7% 之间的一切变动都属于同一类噪声，如今 `graph_csr` 的 clang 列（上一轮为 +31%）也落入其中。

**真正产生影响的是图像内核这一行，而且仅在 v145 下如此。** 在 W=2048、16 轮遍历、单位 ms、四次取最佳值的情况下：

| | v145 | clang |
|---|---:|---:|
| `blur`：`src[y*W + x]`，20/20 | 68 | 23 |
| `blur_assert`：同上并附加一条如今冗余的 `assert(src.len == W * W)`，20/20 | 68 | 23 |
| `blur_rows`：带各自长度断言的行切片，20/20 | 26 | 23 |
| 以上任意一项启用 `--no-bce` | 124-74 | 23-24 |

在 v145 下，每像素的九次检查会让循环保持标量执行：把它们全部证明消除后，扁平内核快了 1.8x，行切片形式快了 2.9x。即便所有检查都已消除，扁平内核依然保持标量，因为 MSVC 无法排除通过 `dst` 的写入会影响后续通过 `src` 的读取。行切片形式则能成功向量化，这就解释了两者之间剩余的 2.6x 差距。在 clang 下，这些检查没有可测量的开销：clang 会将带检查的循环向量化，使其跑得与无检查版本一样快，正如 Rust 的 `blur_index` 行——其汇编中仍保留十处 `panic_bounds_check` 跳转点，却跑出了与无检查 `windows` 行相同的速度。上一轮中 clang 还需要依赖*循环视图提升*（当时在 `blur` 行上贡献了 +327% 的主要部分），因为那时 `src` 和 `dst` 还是胖引用参数，其头部信息可能被通过 `dst` 的字节写入所修改。如今该内核已在 `main` 的两处调用点被内联，这两个数组成了局部变量，任何写入都无法触及它们的头部，因此 clang 构建在关闭该 pass 时也与开启时一样快。

`blur` 的检查是从 `main` 本身已知的信息中证明出来的：两个数组的长度均为 `W * W`。在内核尚未内联之前，相同的事实通过调用点传入。特化版本的每个调用点都会记录它对所传入数组长度与整数证明的事实，而函数体则以这些事实的交汇（meet）作为起点（规范 10.5）。该事实在两次调用之间保持有效，因为调用本身不会销毁它：被调用方对其调用方数组的影响已被摘要分析，而只读写元素的内核没有任何此类副作用。因此在 `blur(a, b); blur(b, a)` 的第二次调用处，编译器掌握的信息与第一次一样多。`blur_assert.k` 中的 `assert` 已经冗余，这两行的耗时也相同。`blur_rows.k` 中的行切片同样消除了各自的切片检查，因为每个切片的上界都会与内核已知的数组长度进行比较。

**其他位置凡是保留下来的检查，其索引全部来自内存读取。** 例如 `u = q[qh]` 之后的 `dist[u]`、`w = cur.to` 之后的 `dist[w]`、CSR 填充中的 `out[cursor[s]]`，以及整个 `lru` 中的 `pool[slots[at].node]`。正如 `test/optimizer/bce.k` 所记录的那样，该分析能够证明所有由循环计数器、数组长度、常量掩码和归约推导出的索引检查，而对从数据结构中加载出来的索引一概不能证明。`blur` 还引入了第二类索引，即两个计数器的*乘积*。针对该惯用法，差分约束域配备了一步乘积基与两项和基，这也是让 `scene` 达到 12/12 的原因。

为了测试是否有自然写法能让编译器证明加载索引的检查，我们尝试了四种重写方案，但没有一种值得采纳：

* 将 `graph` 的数组改为全局变量（那样不变式必须对数组*内容*成立）；
* 从 `slots.len` 推导出 `words` 的掩码；
* 使用文档记载的 `%` 归约（范围事实无法跨越循环回边保留）；
* 在探测循环顶部加一条 `assert`。

四种方案的耗时彼此都在噪声范围内，因为这些检查都是基于早已在寄存器中的值所做的、完全可预测的分支。数组内容不变式本身也实际实现并测量过。它确实在两个 `graph` 行上消除了更多检查，但在两者上均未节省出可测量的时间，因此被舍弃。上文的 `blur` 测量结果则是反例：在原本可以向量化的循环中，每次加载都附带一次检查会带来巨大的开销。

<a id="what-the-standard-library-costs-the-benchmarks"></a>
## 标准库在基准测试中的开销

十六个基准测试中有七个使用 `stdlib/` 函数替代了具有相同行为的手写代码。每次采纳都在 `large` 规模下、两套工具链中单独与其所替换的手写形式对比测量，取三次交替运行的最佳值（大于 1.00 表示标准库形式更快）：

| 行 | 使用的功能 | v145 | clang |
|---|---|---:|---:|
| `strlist` | `each_split` | 1.04 | 1.07 |
| `words` | `each_split`、`hash`、`next_pow2`、`push_n` | 1.01 | 1.03 |
| `graph`、`graph_csr` | `fill` | 0.98 | 1.04 |
| `lru` | `next_pow2`、`push_n` | 1.03 | 0.98 |
| `sexp` | `format_int` | 1.00 | 1.01 |
| `particles`、`particles_scalar`、`scene` | `vec` 的 `float3` | 0.99 | 1.00 |

被采纳的库函数没有带来可测量的开销；在两个基准上它们甚至略快于所替换的循环。`words` 的这组数据是在 std 的 hash 改为每步读取 8 字节之前测得的。与 std 的 hash 过去使用的逐字节 FNV-1a（同时也是 C++ 和 Rust 哈希表所用的算法）相比，当前的 hash 在该行上测得 v145 下为 0.94、clang 下为 1.19。`respond` 和 `respond_stream` 过去也使用 `hash` 来计算每条渲染响应的校验和，现在改为在各自代码中自行计算 FNV-1a：同一基准的每一行都必须输出相同的校验和，而其他语言的行计算的正是 FNV-1a。`words` 还保留了第二行 `words_dictionary.k`，将手写哈希表替换为 `dictionary<u8[:], i32>`。这一行属于数据结构对比而非记法对比，其结果列于分项基准表中。

另外三项替换经过测试但未予采纳：

* **`respond` 和 `respond_stream` 中的 `format_int`** 在 v145 下比手写数字循环慢 3-5%，在 clang 下无差异。最初大部分差距源于 `format_uint` 需要除以它的 `base` 参数：每一位都要做一次真正的除法，而手写循环除以的是常量 10。在库中为十进制单独提供专用循环后，挽回了大约一半的差距。剩下的开销来自额外的一层调用以及填充对齐分支——对于每次请求仅渲染四个数字且几乎不做其他昂贵工作的这一行来说，这已能体现出来。`sexp` 在大量其他工作之中才对每个节点格式化一个数字，因此没有测出差异。
* **`graph` 和 `graph_csr` 中的 `push_n`** 会带来 2-3% 的开销：泛型 `push` 循环未能编译成与专用循环等价的代码，并且还会导致几条语句之后的数组长度在越界检查 pass 中变得不可证明。仅使用带来可读性提升的 `fill` 则没有可测量的开销。
* **包含自相对引用的值的 `push_n`** 无法通过编译：`push_n<A, T>(xs: A&, v: T, n: i64)` 按值接收参数，而包含此类引用的值不可复制（规范 3.9）。因此 `graph` 中边表头的填充保留为循环。改用 `T&` 参数也无济于事：库函数内部依然需要从该引用中拷贝出值。

基准代码还必须避免局部变量名遮蔽标准库函数。`std` 函数处于全局作用域，因此名为 `fill` 的局部变量会遮蔽同名的库函数，且报错出现在调用处而非声明处。`graph_csr` 的 CSR 写入游标因此命名为 `cursor`，这个名字也恰好准确描述了它的用途。

<a id="where-k-loses"></a>
## K 在哪些地方落后

**通过相对引用重连链表是修改密集型场景，而池相对形式使其具备了竞争力。** `lru` 是整个基准测试集中唯一一个会反复修改链接而非只构建一次的基准。在使用自相对链接和索引槽位时，它比 Rust 和 C++ 的 Arena 慢 1.5x。采用规范 3.9 的 `in pool` 形式后，节点和 8 字节映射槽位保存的是相对于池基址的 4 字节偏移量，并通过 `pool.free(pool.index_of(n))` 将链接还原为空闲链表索引。在该形式下，这一行耗时为 3,163/2,065 ms，对比 Rust Arena 的 2,274 和 C++ Arena 的 2,607/2,437：在 clang 下分别领先它们 1.10x 和 1.18x，在 v145 下则分别落后 1.39x 和 1.21x，同时内存占用为三者最低。索引形式保留为 `lru_indices.k`；在早先一轮的背靠背测量中，它在 v145 下持平，在 clang 下则慢 1.31x。下表展示了同一程序在 `large` 规模下更多写法的耗时（映射表均存放索引，同样来自早先一轮）：

| 链接方式 | 节点字节数 | v145 | clang |
|---|---:|---:|---:|
| `Node&<u32>?` 自相对 | 16 | 3,738 | 3,189 |
| `Node&<u64>?` 自相对，无范围检查 | 20 | 3,573 | 2,881 |
| `Node?` 普通引用 | 24 | 2,557 | 2,352 |
| `i32` 索引，带越界检查的 `pool[i]`（Rust 形态） | 16 | 2,397 | 2,266 |

普通引用与索引表现持平，可见开销既不是来自引用本身，也不是来自 `reusable` 池（所有变体都通过同一空闲链表释放并复用 130 万次）。它来自自相对编码。每一次重连（每次命中要重连六次）都要由两个地址计算差值并存储，而每一次读取都必须先做空值判断再执行加法，之后才能发出下一次访存。范围检查在 clang 下占了这部分开销的十分之一，在 v145 下则不占开销；其余全是指针追踪关键路径上的算术运算。使用相对链接原本是为了相比普通引用为每个节点节省 8 字节，但 `lru` 并未从中获益，因为索引形式同样也是 16 字节。在只构建一次的基准测试（`tree`、`interp`、`sexp`、`scene`、`bintrees`）中，同样的链接相比索引没有任何可测量的额外开销，因此该开销是重连模式特有的。池相对形式把减去字段地址改成了减去保存在寄存器中的基址，并把加载改成了 `base + off`。clang 对这种模式的调度远胜于 v145；这既解释了两个后端在该行上的 1.53x 差距，也解释了所有剩余的性能差距。只构建一次的基准继续保留自相对链接，因为它们需要位置无关性，且这种链接在那些场景下相比索引没有可测量的开销。

**递归构造不再是落后项，除了 `calc`。** `bintrees` 在递归调用中构建并丢弃 34M 个节点，过去在 clang 下曾落后 Rust Arena 24%（282 对比 228 ms）。如今构建函数按引用接收它的池，编译器会在整个递归过程中将该池的栈顶指针和计数保留在局部变量中，而不是每次 push 都经由头部读写。由此，K 耗时 196/191 ms，对比 Rust Arena 的 221 和 C++ Arena 的 378/391。在只构建一次相同节点树并求和八次的 `tree` 上，K 领先 Rust Arena 6-10%。`calc` 的运行速度为 Rust Arena 的 0.84-0.87x；该处剩余的开销来自全局游标、`return from` 判别式以及在大多只需要两字节的数值上进行的 varint 解码。

**扁平标量内核依赖后端优化，且没有内存优势。** `blur` 的扁平索引形式在 v145 下比扁平 Rust 慢 3.3x。MSVC 由于无法排除 `dst` 与 `src` 存在别名冲突，只能让循环保持标量。在 clang 下，同样的形式反而比 Rust *快* 1.10x（256 对比 282 ms）。若改用行切片来写，则在两个后端下都与 Rust 持平。`particles` 在内存占用完全相同的情况下领先 Rust 2-4%，这处于该行的测量噪声范围内。这两个基准都没有展现出超出噪声的 K 语言优势，而设计之初也并未预期会有。

**在所有三种语言中，指针链表邻接表都输给 CSR。** 在 `graph` 上，所有语言中单遍链表构建后的遍历速度都比两遍“先计数再填充”慢 5-6x。K 的 CSR 行正是为了证明这是数据结构效应而非语言效应，而 K 的 CSR 实现也与两者持平：791/793 ms，对比 C++ 的 803/824 和 Rust 的 833。

**在浮点与指针混合负载上，v145 同样是比 clang 更差的后端。** `scene` 在 clang 下与 Rust Arena 持平，而在 v145 下落后 21%，C++ Arena 在同一行上也比自己的 clang 构建慢 10%。将 117 字节的节点填充对齐到 120 字节并不会改变任何结果，因此紧凑打包布局并不是原因。

<a id="caveats-on-these-numbers"></a>
## 这些数据背后的注意事项

* 全进程挂钟计时，因此输入生成阶段包含在每一次测量之中。在输入生成占比较大的基准（`sexp`、`words`、`graph`、`calc`）中，比值会被稀释而趋向 1.0，实际核心阶段的差距比表格显示的更大。
* 丢弃两次预热后取三次运行最佳值。预热是必须的：在这台机器上，刚写入磁盘的可执行文件首次运行耗时最高可达稳态的 10x，大约需要三次运行才能稳定下来，且这一效应在 clang 链接的二进制上远比 MSVC 链接的显著。若不预热，工具链对比测到的将是杀毒扫描器的耗时。
* 单机运行，未绑定 CPU 核心。约 10% 以内的差异均属于测量噪声。对于两项受限于缓存的随机访问用例——`graph` 的链表行与 `lru`——噪声阈值约为 15%：在越界检查 A/B 测试中，两个字节完全相同的 `lru` 二进制文件曾测出 14% 的差距。
* **大量使用分配器的行是整套测试中可复现性最差的，而总体标题比值正建立在它们之上。** 当完整测试套件背靠背连续运行两次时，K 的各行与前一次结果的偏差保持在 3% 以内，各语言的 Arena 与 CSR 行亦然，但受限于 malloc 的行波动幅度可达 23%。因此“对比惯用写法”几何平均值中小于约 10% 的差异不具显著性，单次整套测试也不足以把某项变化归因于编译器。归因需要针对单次提交、相隔几分钟从相同源码构建并进行 A/B 对比，且在 clang 下加上 `-falign-loops=32`，防止热点循环地址偏移看起来像是代码生成的变化。
* **跨系统环境更新的不同报告之间不可直接横向比较。** 在上一份报告与本报告之间，尽管源码未作任何改动，大多数 C++ 和 Rust 行却快了多达 6%，每种语言的每一行内存占用都缩小了 3-4 MB，进程启动底线耗时也从 12.4 降至 7.9 ms。编译器之外的某些环境因素发生了变化，同时 MSVC 版本也有更新（19.51.36256 升至 .36257）。受限于 malloc 的 C++ 行变化最大，`sexp` 的 `unique_ptr` 行变快了 1.42x。`tree` 的 K 行在 v145 下从 956 降至 605 ms，尽管上一代编译器为它生成的 C 代码放到今天来运行，耗时与当前编译器生成的 C 代码完全相同。比较不同版本的编译器时，必须同时构建两个版本并并排运行对比。
* 这颗 CPU 拥有非常大的三级缓存（L3），因此 `small` 和 `medium` 规模可以完全驻留在缓存中。真正压测内存子系统的是 `large` 各行，而 `calc`、`respond` 和 `bintrees` 按设计则始终不会溢出缓存：它们各自的工作集都只是一条单独的输入、请求或树。
* 进程启动底线耗时在多次运行间并非恒定，且它包含在每一个 `small` 单元格中，因此阅读 `small` 数据时应看相对于底线的差值，而查看比值只应看 `large`。
* Rust 行只有单个 rustc 耗时，而不分后端。rustc 基于 LLVM，因此 clang 列才是与它最直接可比的对象；不过本报告依然同时给出了 K 对比 Rust 在两个 K 构建下的比值。

<a id="what-the-benchmarks-say-about-the-language"></a>
## 基准测试对语言的启示

这些结论源于编写并维护这十六个基准测试的实践过程，独立于任何具体运行速度。整套基准综合运用了 `reusable` 池、递归内部每轮输入独立 Arena、作为高频错误路径的 `return from`、内联子数组、带嵌套变长部分的 DTO 以及标准库。

**表现良好的特性：**

* 支持内部引用的只增不减池（grow-only pools）；
* 单个根内部的相对引用；
* 带内联变长载荷的可变模式 ADT；
* 作为分发机制的 case 函数；
* 带哨兵链表的 `reusable` 池；
* 池元素内部由相对引用组成的有限数组；
* 包含变长字符串以及变长记录内联列表的 DTO，且可由函数直接就地返回构造进字段；
* 在三分之一输入上从三层递归深处触发跳转的 `return ... from`；
* 随作用域退出而重置的每轮输入局部池；
* 按引用接收池并向其中构建结构的递归构建器。

**遇到的问题：**

* **内联子数组在构造时就需要确定数量。** A.2 形态 `(T&<u32>)[varint]` 要求在构建父节点之前，子节点已经存在且数量已知。一边遍历一边发现子节点的构建器只能退而使用定长节点内部的 `[..k]` 有限数组（`scene` 用 17 字节存放四个链接），或使用兄弟链表（`sexp`）。
* **普通引用参数在递归环路之外不能以相对方式存储。** `fn link(prev: Node?) { pool.push(Node { next: prev }) }` 在任何传入源自某池引用的调用点都会被拒绝：参数的根被视为其专属的按调用点划分的类别，编译器没有把该类别与实参来源的全局池关联起来。而在 `recursive` 环路内部，池类别机制（规范 7.8）确实会建立这种关联，这也是 `sexp` 的解析器得以顺利编写的原因。将同样的关联机制推广到环路之外是顺理成章的修复方向。
* **按操作数位宽执行算术运算会在 `u8` 数据上踩坑。** `blur` 的第一版直接用 `u8` 对九个 `u8` 采样点求和，结果产生错误输出；每个采样点都必须显式写为 `as u16`。C 会静默提升为 `int`，Rust 在调试构建下则会 panic；K 按规范（6.2）所写进行回绕，但源码表面没有任何提示。
* **经由泛型参数传递负数字面量会推导为 `i64`。** 对 `i32[>..]` 调用 `push_n(dist, -1, V)` 会在库内部报错，因为那里绑定给 `T` 的类型是 `i64`，而 push 不会自动窄化；改写为 `push_n(dist, -1 as i32, V)` 则可通过，且普通 `0` 也能正常绑定。字面量的类型应当能够穿过泛型实例化跟随目标类型。
* **需要注意的两处语法解析。** `x as u64 & mask` 会把 `u64&` 解析为引用类型（需给类型转换加上括号），而位于尾部位置却没有以 `else` 结尾的 `if`/`else if` 链会报错（应改写为提前返回）。
* **在频繁重连的代码中，自相对引用以速度换取位置无关性；池相对引用则无需这种取舍。** 在只构建一次并遍历的五个基准测试上，自相对链接相比索引没有可测量的额外开销；但在每次命中都会重连六个链接的 `lru` 上，它有 1.5x 的性能损失。规范 3.9 的 `in pool` 形式（相对于命名全局池基址的偏移量）把重连变成了基于寄存器的减法，并允许其他数组存放指向该池的 4 字节链接；借助它，`lru` 在 clang 下已与各 Arena 持平。编码方式是按字段决定的：用于二进制大块（blob）和局部池时选“自相对”，用于全局池中重连密集的结构时选 `in pool`。
* **线程队列无法传递包含相对引用的结构**（非扁平，TODO 9），且在执行这些测量时，save/load 也还缺少 TODO 16 的整区拷贝。序列化功能此后已经实现（`docs/design/serialization.md`）；队列可以传递其字节映像，但仍不能直接传递包含相对引用的值。

<a id="what-the-rust-implementations-say-about-rust"></a>
## Rust 实现对 Rust 的启示

这些结论来自用 Rust 编写整套基准测试的实践，独立于运行速度本身。在这些测量中，Rust 在速度上比惯用 C++ 更接近 K。下面的实现差异有助于解释两者之间剩余的差距。

**`push` 在 Rust 实现中必须使用索引。** `push` 需要保存一个指向仍在追加元素的数组中每第 64 个元素的指针。在 K 中这只需写成 `marks.push(items.push(...))`，且该引用在数组的整个生命周期内始终有效。在 Rust 中等价写法无法通过编译：`&Item` 只要还被持有就会一直借用 `items`，因此紧随其后的 `items.push` 会被拒绝。std 中没有任何容器能同时做到指针稳定与 O(1) 追加。该行使用索引正是因为 Rust 程序员只能这样写；真正有意思的差异体现在源码而非耗时上。

**多个 Rust 实现不得不用索引替代 K 中的引用。** 这涉及 `tree`、`interp`、`graph`、`sexp`、`scene`、`calc`、`bintrees` 和 `lru`：正如 `design.md` 所预测的那样，快速、安全且受推荐的 Rust 写法是搭配 `u32` 链接的 `Vec` Arena。Arena 并未牺牲安全性，因为越界索引会像其他 Rust 索引一样触发 panic。它付出的代价如下：类型写的是 `u32` 而非它所指向的对象；`Option<&T>` 变成了一个会占用真实槽位的哨兵值；而指向后来被复用的池中元素的索引会以编译器无法察觉的方式悄然失效——若是引用，编译器本会拒绝它。K 通过 `TNode&<u32>?` 获得了完全相同的内存布局，同时它依然经过检查、可为空，并且类型明确指向目标对象。

**Arena 有时比 `Box` 行更难编写。** 在 `scene_arena.rs` 中，`update` 无法在节点内部就地合成变换矩阵：`&pool[i].local` 和 `&mut pool[i].world` 是对同一个 `Vec` 的两次借用，而 `Index` 和 `IndexMut` 都无法把它们拆分。因此变换矩阵只能先在栈局部变量中构造好再拷贝进去，子节点列表也必须在递归前先从节点中拷贝出来。`scene_box.rs` 则没有这两个问题，因为单个 `&mut` 的互不相交字段可以独立借用。K 则直接通过指向池元素的 `Xf&` 引用完成就地合成。

**惯用的 LRU 本身就是 Arena。** std 没有侵入式链表，`LinkedList` 也不提供指向单个节点的句柄，因此按句柄实现 O(1) 移至队首，要么需要 `Rc<RefCell<Node>>`（每个节点两次分配外加一对引用计数），要么就需要 `Vec` 加索引的 Arena。两个 Rust 行都采用了 Arena；它们唯一的区别在于映射表用 `HashMap`（SipHash）还是开放寻址。

**Rust 枚举是三门语言中最好的定长标签 ADT。** 它拥有单字节判别式、来自 `match` 的跳转表、没有虚表指针，还有能把标签藏进载荷指针里的 niche 优化。这足以让它在 `records` 和 `interp` 的耗时与内存上都击败 `std::variant`。但 Rust 枚举终究是定长枚举：每个元素都按最大变体的尺寸分配。可变模式枚举是本测试集中唯一一个在 Rust 内置枚举里没有直接对应物的 K 特性。

**`Result` 与 `?` 在 `calc` 中表现良好。** 这段 Rust 代码读起来像 C++ 异常实现，而运行期开销却接近错误码实现。Arena 版本还借助 `Vec::clear()` 获得了 O(1) 析构，但这仅仅因为 `Expr` 不拥有任何资源。一旦节点持有一个 `String`，clear 就会退化回逐节点 drop 遍历；那是常态，而在 K 中永远不会发生。

**在两种情况下，Rust 的惯用写法天生就是最快的写法。** 对 `TrustedLen` 迭代器调用 `collect()` 会预先分配精确容量，因此 `sum` 和 `push` 测出来的那种相对于 C++ 的“你记得调用 `reserve` 了吗”的差距在 Rust 上并不存在。另外借用是默认模式，所以 `Vec<&str>` 和 `HashMap<&str, _>` 本就是 Rust 程序员第一反应会写的形式。这两点都是相对于 C++ 的真实语言设计优势，也都缩小了与 K 之间的差距。

**Rust 依然需要付出代价的地方：**

* `Box::new(T { .. })` 会先在栈临时变量中构造值，再移动到堆上（没有保证的就地构造；规范 4.3/7.3）。
* 析构是实打实的工作，而且它重复着与构造相同的、对缓存极不友好的指针追踪（`interp` 的 `Box` 行落后于 C++ 虚函数分发；`bintrees` 则完全由这类操作组成）。
* std 的 `HashMap` 按策略强制使用 SipHash-1-3。
* 让 `sexp` 的 Arena 行跑得快的那份借用之所以能成立，仅仅是因为输入文本在解析开始之前就已经完整就绪。

**LLVM 消除了 K 的 pass 无法消除的部分，也保留了 K 能消除的部分。** Rust 的 `blur_index` 行在其汇编中保留了十处 `panic_bounds_check` 跳转点，却依然跑得和无检查的 `windows` 行一样快，因为 LLVM 能够绕开这些检查完成向量化。K 的扁平形式在 v145 下慢 3.3x 则是出于另一个原因：它的检查全部已被证明消除，但 MSVC 无法排除通过 `dst` 的写入会与通过 `src` 的读取产生别名冲突，于是让循环保持标量。K 的行切片形式能够被 MSVC 向量化，跑得比扁平形式快 3.3x。

<a id="where-the-k-rust-gap-comes-from-and-where-it-can-still-move"></a>
## K 与 Rust 差距的来源，以及仍有提升空间之处

十六个基准测试按 Rust 对比结果出现差异的*原因*可分为三组，其中只有两组值得继续投入优化。

**来自数据表示的收益。** 最明显的收益源于内存布局与引用规则的差异：

* *可变模式枚举。* `records` 快 2.1-2.3x 且内存少 4.1x，因为每个元素只占自身变体所需的空间而非最大变体的空间，且 `Say` 的文本是内联存储而非第二次堆分配。`interp` 和 `sexp` 在树结构上也体现了相同的特性。Rust 的枚举已是三门语言中最好的定长标签 ADT，但仍为每个元素使用最大载荷尺寸；要改变这一点就需要换用完全不同的表示方式。
* *存储在记录内部的变长部分。* `respond` 构造的 DTO 将其字符串、条目列表及每个条目的 sku 全部内联，渲染过程全程零分配，且运行速度与根本不构建对象的流式行持平。而 Rust 的 DTO 每次请求都要为每个字符串和每个列表分配内存。
* *指向仍在增长的容器的引用。* 安全 Rust 对 `push` 完全无法表达这一点，而对 `tree`、`graph`、`scene`、`bintrees` 和 `calc` 则只能退而用 `u32` 索引表达。K 在获得 Arena 布局的同时，保留了指针版本的完整类型信息。
* *比指针更窄的链接。* `sexp` 的节点使用 4 字节偏移量链接，`calc` 使用 2 字节偏移量，`scene` 的四个子链接则存放在节点内部一个 17 字节的数组中。Rust 的 Arena 也能降到 4 字节，但形式上是索引：没有目标类型、需要占用一个哨兵槽位，并且在池复用时会悄然失效。

**后端差异，而非语言问题。** 这一组包括 v145 下的 `lru`（0.72x）、v145 下的 `scene`（0.83x）以及 v145 下 `blur` 的扁平形式（0.98x）。在这三项中，由*同一*工具链构建的 C++ 行都朝同一方向落败，可见差距来自 MSVC 对特定 C 形态的处理方式，而非 K 表达的需求本身。改动语言无法缩小这些差距，而上限也已清晰可见：这三行在 clang 下全都持平或领先。clang 下的 `bintrees`（0.81x）曾被列入此组，但后来发现并非后端效应：把构建器的池顶和计数保存在局部变量中后，它反而领先 Rust Arena 1.16x。

**所选语义必然要求的开销。** 最终保留下来的越界检查均位于从数据结构加载的索引上，在那里检查并非冗余。`calc` 的 `return from` 判别式服务于一条真实的错误处理路径；C++ 错误码行同样要支付这一开销，而异常行付出的代价还要大得多。这些都不是应当抹去的差距。

**按顺序排列，能够进一步扩大领先优势的改进方向：**

1. **在递归环路之外也能将引用参数的根类别与其所属池关联起来**（见下文第 1 项）。窄链接带来了内存优势，而如今由它们链接起来的结构只能由处于构造环路内部的函数来构建。去掉这一限制后，普通代码而不仅仅是解析器也能享受到这项优势。
2. **在所有通过类型检查的地方推广跨数组窄链接。** `T&<u32 in pool>` 已经允许旁表存放指向某个池的 4 字节链接来代替索引。`lru` 的映射表就使用了这一特性，而由这类链接组成的只增不减数组工作原理完全相同，因此 `sexp` 的根节点列表就是一个候选。这一惯用法应当成为旁表的默认推荐做法，而不是 `lru` 的特例。
3. **继续寻找实际上并不需要根约束的地方。** 以哨兵结尾的链条并不强制要求使用 8 字节普通链接，因为空值不需要根；仅这一点就解释了 `sexp` 1.3x 的内存优势。对于每一条目前要求精确根的规则，都值得问一句：*底层表示*真正需要什么？

<a id="compiler-work-ordered-by-measured-benefit"></a>
## 按实测收益排序的编译器工作

上一轮的第一项——跨调用传递数组长度——现已完成。调用点对实参掌握的事实如今会传递到被调用方入口，且一次调用只会销毁那些被调用方确实可能调整大小的数组的事实。由此，`blur` 从 `main` 已知的信息中证明了全部十处检查，并在两套工具链下都跑出了与带断言内核相同的速度（当时在 v145 下提速 1.75x，从 141 降至 77 ms）。其余待办项如下：

1. **在递归环路之外同样将引用参数的根类别与其来源池关联起来。** 一个接收 `Node?` 并将其存入同一池中 `Node&<u32>?` 字段的非递归函数，如今会被编译器拒绝。完全相同的代码放在 `recursive` 环路内部却能通过；环路机制实际上已经计算出了所需的全部信息。这一限制阻碍了将链表操作辅助函数从构建结构的环路中提取出来。
2. **特化标准库的元素循环。** `push_n` 相比它所替换的 `for` 循环有 2-3% 的开销，还会阻碍下游的越界检查消除，这正是两个基准测试继续保留手写循环的原因。泛型形式应当能编译出与手写循环相同的代码。
3. **内联并非首条语句的基础情形**（`scene`、`interp`），并在尾递归消除中匹配表达式体形式的折叠（`if c { 0 } else { 1 + f(x) }`）。

实测已经否决了以下思路：

* 为越界检查 pass 引入数组内容不变式：虽然消除了更多检查，但未能节省任何可测量的时间。
* 合并标签分发：仅有 1% 收益。
* 在布局本就无空隙的地方去掉 `#pragma pack(1)`：在两个后端上均无任何差异。
* 将*可选*相对引用的加载与其空值判断融合：两个后端的性能反而变差。
* 重写基准代码以便越界检查 pass 能够证明加载索引：没有可测量的收益。
