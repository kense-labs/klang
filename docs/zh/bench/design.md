> **已弃用的语言特性：** `reusable` 和 `reusable[]`。请改用
> [`slot_pool<T>`](../stdlib.md#slot_pool) 管理槽位（slot），改用
> [`slice_pool<T>`](../stdlib.md#slice_pool) 管理连续片段。
> 下文所述的内置行为与历史示例对于现有代码仍然有效；在解决剩余的迁移缺口后，将会另行安排移除。

K 语言用于验证内联数据结构和语言级内存管理能否在保证内存安全的同时，在性能上超越 C++ 和 Rust。

这些基准测试既覆盖可能受益于该设计的常见算法，也包含 K 可能会表现吃力的工作负载。其目标是同时衡量收益与局限性，并找出潜在的语言改进方向。

单独的 [slot_pool 对比](slot_pool.md)在完全相同的分配策略和工作负载下，对根结构体（root-struct）标准库分配器与现有的 `reusable` 内置特性进行了对比；可通过 `bench/slot_pool.py` 运行。
[slice_pool 对比](slice_pool.md)则测试了首次适应（first-fit）跨度复用、合并（coalescing）和重定位（relocation）相对于 `reusable[]` 的表现；可运行 `bench/slice_pool.py`。

该基准套件用于检验以下特性的效果：

* 紧凑的内联数据结构。
* 针对 push 和 append 操作的原地构造（in-place construction）与指针碰撞（pointer-bump）式增长。
* 更少的拷贝开销。
* 可变大小数据结构无需“realloc”，同时仍允许指向元素的指针存在。
* 变长枚举（Variable size enums）。
* 无通用分配器：路径上没有 malloc/free 调用、每次分配的头部元数据（per-allocation headers）、大小分级舍入（size class rounding）、需要遍历的空闲链表（free lists）、内存碎片，以及锁和线程缓存。释放内存只是一次指针重置。`reusable` 内存池（规范 5.4）覆盖了重度修改场景，否则这类场景会迫使程序重新引入分配器。
* 无析构函数且无 drop glue：释放一个大型嵌套结构是 O(1) 操作，而不是 O(n) 的指针追踪遍历。C++ 和 Rust 必须为销毁它们构建的每一个 `unique_ptr`/`Box`/`String` 付出代价，而且销毁过程和构建过程一样对缓存极不友好。
* 相对引用（Relative references）：在 C++ 和 Rust 使用 8 字节指针的地方，仅使用 1-2 字节的链接。对于指针密集型图结构，Rust 的惯用变通方案已经是索引式 arena（`Vec<Node>` 加 `u32` 索引），因此 Rust 的对比基准是这种 arena 而非 `Box`；即便如此，它仍然需要每跳 4 字节加上基址+缩放（base+scale）计算。
* 聚合类型内部普遍采用紧凑标量：紧凑结构体（packed structs，无填充对齐）、`u8`/`u16`/varint 数组长度字段、`u8` 枚举标签、varint 载荷字段。Rust 和 C++ 会将枚举大小向上对齐到最大变体加对齐要求，而且如果不手工进行位操作（bit twiddling），就无法表达其余这些紧凑布局。
* 嵌套容器保持扁平且连续：`u8[][>..]` 是一整块连续内存，而 `Vec<String>`/`vector<string>` 则是 1 + N 次分配，每次分配都带有 24 字节的头部（在 C++ 中，SSO 可以缓解这一点，但仅限于短字符串）。因此，同时测试短字符串（SSO 尺寸）和长字符串非常有价值。
* 有保证的目标位置原地构造（4.3，7.3）：任何地方都不存在先构造再拷贝，具有有保证的 NRVO（具名返回值优化），被调用方直接将结果写入调用方的容器中（`v.push(f())`）。C++ 的 NRVO 并不保证生效，而且 `emplace_back` 也无法对变长值做到这一点；Rust 则会自由地用 memcpy 四处移动大值，这是一个众所周知的弱点。
* 标签分发代替虚表（8.2）：每个对象没有虚表指针（即每个多态节点省去 8 字节），使用跳转表而非间接调用，且各个分支仍可被内联优化。
* 按精确大小增长：增长到 n 个元素的数组就只占用 n 个元素的空间，而 `Vec`/`vector` 在分配器自身舍入的基础上还会携带高达 2 倍的容量冗余（capacity slack）。
* K 的数据天然处于序列化形式：相对引用结构可以通过 memcpy 或 mmap 直接加载，无需解析，也无需指针修正（pointer fixup）遍历。加载时间是真实且频繁发生的开销，这种方式将其降低到了纯粹的 I/O 时间。
* 廉价的远距离错误返回（`return from`，7.9）：每层栈帧仅需一次判别式检查，而 C++ 异常（在抛出路径上非常慢）以及 Rust 的 `?` 链还会在每一层栈帧上逐级拷贝错误载荷。
* 线程队列（11.2）直接传递扁平连续的值，无需逐元素指针追踪、序列化步骤或共享所有权机制。

我们需要与注重性能（但仍符合语言习惯）的 C++ 和 Rust 代码进行对比。C++ 可以通过手动指针管理和数据紧凑排布来复现其中许多布局。这些技巧属于专家级对比范畴；而 K 的目标是让这些能力在普通代码中也能方便、内存安全地使用。

除了速度，我们还需要测试内存占用，以及两者的综合表现。每个算法至少在 3 种不同数据规模下运行：最小规模聚焦于纯 CPU 性能，而较大的 2 个规模则逐步加大对缓存和内存子系统的压力，以观察 K 的优势是否显现或扩大。

我们应当测试每种语言中所有合理且惯用的写法。对于使用变体（variant）或多态数据的算法，在可能的情况下对比 K 的定长枚举与变长枚举，以及 Rust 的定长枚举。对于 C++，则对比子类继承（最惯用但较慢）、`std::variant`（更快但用起来别扭）以及 C 风格联合体（最快但非常不安全）。

如果某个算法涉及大量可调整大小数组的 push 操作，为了对 C++ 公平，我们需要同时对比程序员合理选择 `reserve` 的情况，以及完全不使用 `reserve` 的情况。

我们还需要找出 K 目前表现较弱的代码示例，以及由于各语言使用相同编译器后端而性能相近的示例。

<a id="where-the-gains-should-compound"></a>
## 收益应当产生叠加效应的场景

上述大多数优势本质上是从不同角度看待同一个优势：它们都减少了单位工作量所触及的字节数。因此，某个算法获得的收益应当大致与其数据的指针密集度和分配密集度成正比，并且随着数据规模增大、工作集逐级超出各级缓存而进一步扩大。预期收益最大的场景大致按以下顺序排列：

1. 任何构建大量小型链接对象的场景：语法分析树、AST（抽象语法树）、S-表达式、场景图。分配开销、节点大小（相对引用、varint、`u8` 标签、无虚表指针）以及销毁开销会在同一个基准测试中相互叠加。
2. 任何持有变长对象集合的场景：字符串列表、记录列表、锯齿数组（jagged arrays）。单块连续内存对比 1+N 次分配。
3. 任何在增长的同时仍持有指向已增长内容指针的场景。在 C++/Rust 中，这会迫使程序员改用索引、分块 arena（类似 deque，带来额外间接寻址），或者预先 `reserve` 一个硬性上限。这三种做法都值得作为独立行进行基准测试，因为我们要消除的正是这种变通方案的代价。
4. 加载/保存以及跨线程传递路径，在这些路径上 K 无需做额外工作，而其他语言必须进行序列化或指针修正。

如果某个基准测试的数据只是标量的扁平数组，那么预期不会有任何优势。这是一个很有用的对照基准（control case）。

<a id="where-we-should-expect-k-to-lose"></a>
## 预期 K 会处于劣势的场景

基准套件应当测量以下潜在局限性：

* 算术运算按操作数自身位宽执行（6.2），因此 `i32` 计算核心使用 32 位算术，但 K 的紧凑非对齐布局相对于对齐的 C++ 数据仍可能损失 SIMD 性能。一个简单的整数数组计算核心可以量化这方面还剩下多少差距。
* 出于同样原因，紧凑非对齐布局（3.2）可能会损失实实在在的 SIMD 性能：没有填充对齐就意味着没有对齐保证。另见 TODO 10。浮点/向量数学基准测试（粒子系统、n-body 模拟、图像卷积核）正是为此而设，它同时也会测试逐元素结构体运算（6.1）。
* 缺乏别名（aliasing）信息。Rust 会为 `&mut` 向 LLVM 提供 `noalias`，C++ 在程序员显式使用时有 `restrict`，而 K 刻意允许别名，因此不会向后端提供任何别名信息。这会在任何接受两个数组参数并执行原地变换的函数中体现出来。
* 对所有非定长结构都进行边界检查，这一点与 Rust 相同、与 C++ 不同。编译器目前已经能够通过证明消除其中大部分检查（10.5），而 `--no-bce` 可以为剩余检查的开销提供直接的 A/B 对比；`bench/bce_ab.py` 用于运行该对比。主报告中的核心数据是开启边界检查后的结果：它们将开启边界检查的 K 和 Rust 与作为无检查基线的 C++ 进行对比。
* 拷贝具有实实在在的开销。按值语义且没有移动操作（4.1，TODO 3）意味着 Rust 程序员可以用廉价 move 表达的惯用法，在 K 中会变成 O(size) 的拷贝。一个在不同执行路径上返回不同局部变量的基准测试（7.3），或者频繁重新赋值大对象的基准测试，将会暴露出这一问题。这是最有可能发现语言层面值得改进之处的地方。
* 栈式作用域纪律带来的摩擦。生命周期非嵌套的工作负载（缓存、长生命周期的可变图结构、任何需要按不同大小先释放再分配的场景）必须通过 `reusable` 内存池处理，而且递归环路完全无法拥有可增长的局部变量（7.8）。需要包含一个在 K 中写起来很别扭的基准测试来衡量这种变通方案的代价。`lru` 就是这个基准测试。内存池本身实测没有可察觉的开销，但它重新链接的相对引用相对于索引有 1.5 倍的开销，因为偏移量计算直接落在指针追踪的路径上。因此，紧凑链接是一种权衡，更适合构建一次、多次遍历的结构；它并非毫无代价。
* 地址空间统计：应当报告已提交页面（committed pages），而不是数 GB 的保留地址空间（10.4），以避免将已保留但未使用的地址空间计入内存占用。反过来说，K 以页为粒度为每个栈提交内存，因此在最小的数据规模下，它看起来比 malloc 更差是完全合理的。

<a id="candidate-algorithms"></a>
## 候选算法

挑选常见、广为人知的代码，每一项都旨在命中上述特定维度：

* 文本语料词频统计：扁平字符串列表、哈希表增长、字符串键。命中维度 2 和 3，其中哈希表对应规范 A.3。
* JSON 或 S-表达式解析，随后进行遍历/查询：全面命中维度 1，外加可变模式枚举、相对引用（A.2）、varint 字段，以及错误路径上的 `return from`。很可能是旗舰级基准测试。
* 表达式或字节码解释器：case 函数分发对比虚函数调用、对比 `std::variant` 的 `visit`、对比 Rust 的 `match`。将分发机制与节点大小的影响从内存分配中剥离出来。
* 图构建加 BFS/Dijkstra：增量构建邻接表（维度 3），随后遍历。将 K 的嵌套可变长数组与 C++/Rust 中手工构建的 CSR 进行对比，后者是在这些语言中注重性能的典型做法，需要编写更多代码。
* 粒子/n-body 或图像卷积核：检验 SIMD 与紧凑布局问题。预期打平或落后；用于测试潜在弱点。
* 已构建结构的保存/加载往返：mmap 后直接使用，对比解析与指针修正。
* 扁平标量数组排序：对照组。应当旗鼓相当。
* 二叉树（著名的 Benchmarks Game 同款）因其知名度值得纳入，但需在说明文档中注明它本质上是一个分配器基准测试，因此我们不会将其作为主要依据。

<a id="measurement-notes"></a>
## 测量说明

* K 编译为 C，因此请使用完全相同的 clang 版本和优化级别来构建 C++ 代码和生成的 K C 代码，并注意 Rust 同样走的是 LLVM 后端。这样做的目的是对比数据结构与内存策略，而非编译器后端。
* 将销毁过程（teardown）纳入计时区间内。释放数据结构是真实开销，而 K 无需支付这一开销，因此必须将其计入才能进行公平对比。
* 为 C++/Rust 提供公平的分配器：系统 malloc 是默认惯用法，但加入 mimalloc 或 jemalloc 作为强劲基线，并加入手工编写的 bump/arena 分配器作为“专家级实现”档位。这与上文 `reserve` 的公平性分层思路一致。
* 在内存方面，同时报告峰值 RSS 与程序认为自己拥有的有效载荷大小（payload size），从而让分配器开销、容量冗余以及每对象头部元数据以两者之间的差值形式显现出来。这个差值本身就是一个重要结果。
* 绑定到固定 CPU 核心，在可行时锁定主频，分别在冷态和热态下运行每个规模，并报告结果分布，而非仅取 N 次中的最佳值。

<a id="the-suite-as-built"></a>
## 已构建的基准套件

`bench/klang/`、`bench/cpp/` 和 `bench/rust/` 中包含针对这一设计实现的十六个基准测试。前十个规模较小，每个测试一项语言特性，从 `sum`（对照组）到 `sexp`（旗舰基准）。随后新增的六个规模稍大，用于填补前十个留下的空白：

* `lru`：缓存，使用 `reusable` 内存池，按脱离作用域顺序的方式先释放再分配。这是栈式作用域纪律最不适合的重度修改形态。
* `scene`：场景图，包含由相对引用构成的内联子数组，每一帧都会发生修改。
* `calc`：将大量小型输入解析到单次输入作用域的局部池中，其中四分之一的情况下会走 `return from` 的真实错误路径。
* `bintrees`：Benchmarks Game 的分配器基准测试，为保持辨识度而纳入。
* `respond`：Web 处理器的 DTO，包含一个字符串和一组记录列表，按每个请求构建并渲染。
* `blur`：图像模板（stencil）计算，包含扁平标量计算、边界检查以及无别名信息，专门用于测试潜在弱点。

`bench/run_bench.py` 会在三个规模下分别构建并运行这些测试，校验每个基准测试的各个实现都输出相同的校验和（checksum），并生成 `bench/results.md`。该文件末尾的评述来自 `bench/notes.md`。

该套件尚未对相对引用结构的保存与加载或通过线程队列发送它们进行基准测试。带校验的序列化此后已经实现（参见 `docs/design/serialization.md`）。队列可以传输序列化后的字节映像，但不能直接传输带有相对引用的值，因为这些值不是扁平的（TODO 9）。

C++ 分为两个档位进行测量：惯用实现（idiomatic）和专家优化（expert）。它的实现技术跨度太大，无法用单一一行数据代表。对于 Rust，基准测试对比的是安全、惯用的实现。当列出两种 Rust 表示形式时，它们在语义或结构上存在差异：例如拥有所有权的字符串对比借用字符串，或者拥有 `Box` 节点对比基于 `Vec` 加索引的 arena。单纯更快的速度不足以成为纳入另一种表示形式的理由。Rust 社区对指针密集型数据推荐使用 arena，而上文的预测也得到了印证：在同时拥有两种实现的三个基准测试中，arena 比 `Box` 快 2.8 倍到 5.9 倍。

这一对比还包含一个计时无法衡量的可用性维度：当 Rust 使用 `u32` 索引而 K 使用带类型、可空的引用时，即便性能相近，它们所提供的编程接口依然截然不同。
