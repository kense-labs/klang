# plan.md 中所提议编译器变更的实施结果

> **已弃用的语言特性：** `reusable` 与 `reusable[]`。请改用
> [`slot_pool<T>`](../stdlib.md#slot_pool) 表示槽位池，改用
> [`slice_pool<T>`](../stdlib.md#slice_pool) 表示连续区间池。
> 下文涉及的内置行为与历史示例对于现有代码仍然有效；其移除计划将在剩余迁移缺口补齐后另行推进。

*本文档记录了本轮已完成的编译器变更、实测数据以及采纳或拒绝每项变更的原因。基准测试报告请参阅 `results.md`。*

本次共有十六个分支，分别对应 `bench/plan.md` 中的每一项条目。每个分支均由各自的智能体基于 master 提交 `caf3b65` 检出独立分支 `opt/<name>` 实现，并附带了测试。

随后所有分支均在安静机器上采用相同的流程进行测量。基线编译器与候选分支编译器分别生成 `large` 规模下的所有 K 语言基准项。两种工具链在编译生成产物时，clang 端均开启 `-falign-loops=32`。测试在基线与候选分支之间交替运行，取五次运行中的最佳值，并校验输出结果完全一致。表格中的比值为基线耗时除以候选分支耗时：大于 1.00 表示速度更快。

未受某分支影响的基准项会输出字节完全一致的 C 代码。在全部十六次测试运行中，这些未改动项的比值范围为 0.94 至 1.08，且大多保持在 1.00 上下 2% 以内。因此，单项低于约 5% 的变化属于测量噪声。只有受限于缓存的随机访问基准项 `graph`/`graph_csr` 噪声会更大一些。当某项优化需要套件中尚未出现的源码模式时，对应分支会包含一个变体源码，以相同方式计时，并标注为*变体*。

## 2.1 `opt/fatref-tops` -- 经由胖引用缓存栈顶

**改动内容。** 通过引用持有可变长数组的函数（`pool: T[>..]&`）会将 `ref.stk->top` 保存在局部变量中，在函数调用前刷回、在调用后重新加载；而此前任何包含此类参数的函数都会对所有数据栈退回到内存访问形式。是否具备资格由检查器的根类别（root classes）判定：

* 每个胖引用*参数*对应一个缓存；
* 拒绝相同类别的参数对（相同类别不能证明指向同一个栈）；
* 局部变量、绑定、字段或按值传递的可变长参数中一旦出现任何胖引用，即禁用该模式；
* 若某个全局变量的类型与参数的被指向类型匹配，该全局变量仍保留内存访问形式。

全部改动均位于 `codegen.h`。

**实测结果。** bintrees 1.12 / 1.16；calc 1.00 / 1.03（其 push 操作在解析总耗时中占比很小）；respond 持平。将 `push` 循环移至两个胖引用之后（分支上的 `push_ref.k`），耗时在 v145 下从 170.5 ms 降至 157.7 ms，在 clang 下从 166.8 ms 降至 154.0 ms，两端均提升 1.08x。其余所有基准项生成的代码逐字节一致。

**复杂度与副作用。** 该变更新增了一个谓词、一个标志位和一个字符串集合，并复用了全局变量缓存既有的刷回规范。为保证健全性（soundness），两项保守策略限制了加速幅度：每次调用都会刷回当前模式下的全部缓存，且不会同时缓存全局变量。该分支还顺带修复了 `CanCacheTops` 中一个既有的不健全问题，并附带了回归测试。此前 `CanCacheTops` 未能识别从字段或元素中读取出的胖引用，导致一个函数体若同时直接和经由该引用向全局变量执行 push，就会缓存其中一种访问形式的栈顶却通过另一种形式写入（复现用例本应输出 `1,2,3`，却输出了 `2,3,0`）。这项修复本身也具有独立价值。

**结论：采用。** **未来代码适用度：高。**“向调用方持有的池中递归构建节点”正是上一轮检查器改动所解锁的惯用写法，所有按请求或按输入分配的 arena 均以此方式编写。

<a id="22-optbase-case-inline----inline-a-self-recursive-functions-base-case"></a>
## 2.2 `opt/base-case-inline` -- 内联自递归函数的基准情形

**改动内容。** 对于函数体以 `if c { return e }`（或 `guard` 形式）开头的 `recursive fn`，每个直接自调用点都会被重写为 `if c' { e' } else { f(...) }`，且在每个调用点处将实参一次性绑定到临时变量。该变换仅在满足白名单条件时触发：所有参数均为固定大小、判断条件纯洁（pure）、返回值分支不再调用该递归环，且代码体积低于内联器阈值。实现位于 `optimize.h`，复用了内联器的拷贝逻辑。

**实测结果。** bintrees 1.35 / 1.13，tree 1.02 / 1.01，sexp 持平。它在 `bintrees.make`、`tree.build` 和 `sexp.walk_chain` 上触发。未在 `interp` 和 `scene`（其基准情形前还有语句）、`calc`（互递归）或 `bintrees.check`（先绑定了一个局部变量）上触发。

**复杂度与副作用。** 代码膨胀受既有阈值约束（`make` 从 32 个节点增至 62 个）。由于递归路径上会对判断条件求值两次，因此条件必须纯洁，白名单对此作了强制约束；链式递归的表现基本持平。智能体在此规避了一个真实隐患：非固定大小参数会给递归环成员引入非固定大小局部变量，手写代码会被检查器拒绝，而代码生成阶段却会静默接受。智能体还发现了下文列出的 `INT32_MIN` Bug。

**结论：采用。** **未来代码适用度：高**，尤其适用于树遍历与树构建，这类场景构成了 K 语言中绝大多数递归。将该优化扩展至基准情形并非首条语句的场景（`scene`、`interp`）是显而易见的后续方向。

<a id="23-opttre----accumulator-tail-recursion-elimination"></a>
## 2.3 `opt/tre` -- 累加器尾递归消除

**改动内容。** 返回整型且返回值通过可结合运算符折叠的自递归函数，会被改写为带累加器的循环；参数变为可重新绑定的局部变量。该变换不适用于浮点数、可能从函数执行 `return ... from` 的被调函数、处于循环体内部的尾调用，以及相对引用、胖引用或池参数。该分支还在构建中加入了 `/bigobj`。

**实测结果。** bintrees 在 v145 下为 1.09，在已自带此优化的 clang 下为 1.00；sexp 1.02 / 1.00；calc 1.02 / 1.01（其生成器本身已是普通尾调用）；tree 在深度 24 时受限于内存带宽而持平。

**复杂度与副作用。** 这是体积最大的优化器分支（`optimize.h` 新增 485 行，对比 2.2 为 238 行），也是唯一带有语义脚注的分支。对有符号 `+`/`*` 链进行重结合会改变中间结果，因此调试构建中的溢出中止（overflow abort）可能会在原本不触发的地方触发，或在原本触发的地方不再触发；发布构建则保证逐位一致。这构成了优化器“包含中止行为在内等价”规则下唯一一处有文档记录的例外。若采用严格替代方案（仅允许无符号与按位运算符），则会使全部四个基准测试实例都无法触发。表达式体形式的折叠（`if c { 0 } else { 1 + f(x) }`）暂未匹配。

**结论：在明确语义脚注后采用**：要么将其作为文档约定予以接受，要么将有符号情形置于 `-O2` 之后。该变换的核心目的在于使 v145 追平 clang。**未来代码适用度：中。**`return e op self(x)` 在遍历与求和中很常见，而半数用户所使用的后端已经原生执行了此变换。

<a id="24-optfatref-views----hoist-array-views-reached-through-references"></a>
## 2.4 `opt/fatref-views` -- 提升经由引用访问的数组视图

**改动内容。** 当循环通过胖引用索引数组，且 BCE 的失效摘要（kill summary）表明循环体不会修改该数组本身（没有对其增长或收缩，也没有可能触及它的调用）时，循环会在进入前一次性加载其基址与长度；经由任意引用进行的元素写入不会阻止此优化。该改动一半位于分析阶段（`bce.h`），一半位于代码生成阶段。

**实测结果。** blur 在 clang 下达到 6.96（从 1,858 ms 降至 267 ms），在 v145 下为 0.94——在 v145 下每像素九次检查依然存在，多出的两个活跃局部变量带来了 6% 的开销。其余所有基准项生成代码逐字节一致。

**复杂度与副作用。** 该改动体量小且自包含。分析阶段只是向既有的失效摘要多提出了一个问题，用于数组增长的长度左值仍直接指向真实头部，因此即便漏判了某次增长，也绝不会静默错误编译。基址与长度必须同时提升才能获得收益；单独提升其中任意一个都没有测出可观提速。一旦 2.5b 能够证明该函数中的检查（这需要得知下文所述的引用参数长度），v145 下 `blur` 的倒退便会消失。

**结论：采用。** **未来代码适用度：高。**`fn kernel(a: T[>..]&, b: T[>..]&)` 正是规范 7.4 推荐的可变范围算法写法，如今在 clang 下所有此类循环都要承受这一开销。

<a id="25ab-optbce-slice-product----slice-lengths-and-product-indices"></a>
## 2.5a+b `opt/bce-slice-product` -- 切片长度与乘积索引

**改动内容。** 越界检查域在边界可命名时会记录 `len(a[lo..hi]) = hi - lo`，并对有界计数器的乘积及两项之和执行区间算术——作为一次性基元，且仅在结果可证明不会超出表达式位宽时生效。改动位于 `bce.h`，并新增了九个带注解的测试。

**实测结果。** 检查消除数：`scene` 从 9/13 升至 12/13（3x3 的 `p.m[i * 3 + k]`），不带断言的 `blur_rows` 从 0/10 升至 10/10。`scene` 性能为 1.02 / 1.00。`blur` 本身仍停留在 0/10，因为其检查位于未被内联的 `fn blur(src: u8[>..]&, ...)` 中，而长度事实是在 `main` 中建立的。在每次调用前加上一条 `assert(src.len == W * W)`（分支上的 `blur_assert.k`）后，消除数达到 10/10，v145 耗时从 1,922 ms 降至 930 ms（2.07x），clang 从 1,860 ms 降至 265 ms（7.02x）。

**复杂度与副作用。** 未引入新的分析遍；乘积与求和项现在可以流向所有消费项的位置（`for i in n * m`、`resize(n * m)`、`let` 等式）。编译时间增加 2%。位宽校验是保证该分析在发布模式回绕语义下依然健全的关键。

**结论：采用。** **未来代码适用度：高**，适用于按行主序访问的惯用代码（图像、矩阵、表格）以及任何使用算术边界切片的场景。原版 `blur` 所欠缺的“引用参数的长度信息”属于过程间事实，将作为独立条目处理。

<a id="25c-optbce-array-contents----index-postconditions-and-contents-invariants"></a>
## 2.5c `opt/bce-array-contents` -- 索引后置条件与内容不变量

**改动内容。** 在 `a[i]` 执行之后，`0 <= i < len(a)` 成立；而对于局部整型数组，若每次写入均可证明满足 `0 <= v <= const` 或 `v <= len(P) + c`（且 `P` 永不收缩），则从该数组加载出的值也会携带这一事实。这是 `bce.h` 中新增的第三轮记录遍历。

**实测结果。** 检查消除数：`graph` 从 5/9 升至 8/9，`graph_csr` 从 11/21 升至 17/21，`lru` 从 0/18 升至 2/18。耗时：无显著可测变化（graph 1.07 / 0.97，graph_csr 0.97 / 1.02，lru 1.01 / 1.01），在套件中噪声最大的这几个基准项上两套工具链甚至呈现相反符号。这些检查本身是针对寄存器常驻值的完全可预测分支，与上一轮 `words` 重写时的发现一致；`plan.md` 中提到的 5-10% 来自于全遍 `--no-bce` 对比，而该开关同时也会禁用循环视图提升。

**复杂度与副作用。** 这是规模最大的分析变更，其主要风险在于能否穷举所有写入形式（push、append、store、被指向写入、resize、整数组赋值、空闲列表 `free`）。该分支还顺带发现并修复了现有分析中的一个潜在 while 退出隐患。部分剩余检查无法消除：例如在最后一个顶点处 `out[fill[s]]` 不变量并不成立。

**结论：暂缓。** 该分支实现正确且测试充分，但没有带来可测量的加速效果，同时分析体量较大。待未来出现加载索引确实消耗显著时间的基准场景，或将其作为逐数组索引类型（TODO 0e）的基础时再行合入。**未来代码适用度：**作为基础设施为中，作为提速优化为低。

<a id="26-optinline-nrvo-dest----inlined-named-results-built-at-the-destination"></a>
## 2.6 `opt/inline-nrvo-dest` -- 在目标位置原地构建内联具名结果

**改动内容。** 当优化器将返回值是具名可变长局部变量的构建函数内联到构造上下文中时，该局部变量会直接绑定到目标数据栈，内联后的 `return` 仅写入长度前缀。定长前缀会先预留空间再回填（零移动）；varint 前缀会先预留一字节，仅当元素数达到 128 时才移动元素。非内联形式中也用同样的“先预留再回填”取代了原有的 memmove。改动涉及 `ast.h`、`optimize.h` 和 `codegen.h`。

**实测结果。** respond 1.06 / 1.06（557.8 降至 524.5 ms，534.2 降至 503.3 ms），records 1.01 / 1.03。respond 的 `handle` 中不再残留任何结果拷贝，其数据栈数量从四个降至两个。DTO 基准项与流式基准项之间的差距从 26% 缩小到 19%。

**复杂度与副作用。** 中等：用一个映射表取代了 `nrvodst`，用三个辅助函数取代了 `EmitNrvoPrefix`。存在一项不得不做的行为变更：多名称接收（`let a, b = f(); return a;`）不再作为 NRVO 候选，因为该模式此前本就会错误编译；现在它按规范 7.3 的要求执行拷贝。智能体还发现了围绕具名结果的另外四个潜在 Bug（见下文）。

**结论：采用。** 它使规范 7.3 的保证在内联情形下同样成立，而内联正是常见情况。**未来代码适用度：高**，适用于 DTO、字符串构建器，以及任何将构造好的 `u8[]` 或 `T[]` 返回到字段或 push 调用中的代码。

<a id="27-optper-loop-tops----cache-stack-tops-only-in-loops-that-grow"></a>
## 2.7 `opt/per-loop-tops` -- 仅在发生增长的循环中缓存栈顶

**改动内容。** 栈顶缓存局部变量被限定在真正执行了栈增长的循环内（若增长发生在所有循环之外，则作用于整个函数体）；仅原地改写元素的浮点循环保持内存访问形式。延迟占位符在函数体发射完毕后解析，而跳出含 push 循环的控制流逃逸（`break`、内联提前 `return`）则按标签位置刷回。改动位于 `codegen.h`。

**实测结果。** clang 下 particles 提速 1.06、particles_scalar 提速 1.06（916 降至 862 ms，913 降至 858 ms），v145 下持平；所有 push 密集型基准项均在 2% 波动范围内（sum 1.01 / 1.00，push 0.99 / 1.00，strlist 0.99 / 0.98，sexp 1.00 / 1.00，bintrees 1.00 / 1.01，lru 1.00 / 1.00）。这彻底挽回了上一轮浮点内核在 clang 下 6% 的性能倒退，且未在其他项目上造成可测回归。

**复杂度与副作用。** 这是全套变更中最精巧复杂的代码生成改动：它基于标签位置执行文本级后处理，且其 Debug 目标文件已逼近 MSVC 的节区数量上限。所有函数的临时变量编号均会偏移，因此与 master 对比生成的 C 代码 diff 噪声较大。仅由被调函数增长的栈也不再被缓存，从而从 `bintrees` 与 `lru` 中消除了多余的刷回/重载配对。

**结论：采用。** **未来代码适用度：高**，适用于任何“先一次性填充、再原地处理”的数组，几乎涵盖所有仿真与图像处理循环。

<a id="28-optcycle-return-roots----return-roots-of-a-recursive-cycle-by-fixpoint"></a>
## 2.8 `opt/cycle-return-roots` -- 通过不动点计算递归环的返回根

**改动内容。** 在检查 `recursive fn` 之前，对递归环内的返回语句（`X.push(...)`、`&X[...]`、显式类型 `let` 局部变量、环内相互调用）进行语法扫描并迭代至不动点。所得结果作为每个函数的初始返回根，随后再对照真实返回语句加以校验。若某条回边结果的根无法确定，则赋予其不可存储、不可返回的哨兵根。改动仅在检查器内；规范 7.8 已同步更新，TODO 0g 已完成。

**实测结果。** 按设计无性能变化：全部 22 个源码生成的 C 代码逐字节一致。去掉 Paren 节点的 `calc`（分支上的 `calc_noparen.k`）现在可以全程使用相对链接通过类型检查，减少了 311,505 个节点，校验和保持不变，耗时在 v145 下从 545 ms 降至 526 ms（1.04x），在 clang 下从 537 ms 降至 492 ms（1.09x）。`sexp` 的回边结果现在正确判定为池生根（pool-rooted）而非静态根。

**复杂度与副作用。** 作为检查器改动而言体量较大，但它堵住了基线中一个不健全漏洞（当前基线会错误接受将指向调用方局部池的引用存入全局变量），并消除了初次编写解析器时极易踩中的语言伪限制。存在一项行为变化：以非池引用参数为根的回边结果现在在环内不可存储，而此前会被静默视作静态根。

**结论：采用。** **未来代码适用度：高**，适用于所有返回引用的互递归代码，这几乎涵盖每一个解析器。

<a id="29-optrelref-rangecheck----skip-the-relative-reference-range-check"></a>
## 2.9 `opt/relref-rangecheck` -- 跳过相对引用的范围检查

**改动内容。** 存储时的范围检查现在置于 `#if K_STACK_RESERVE > (1ull << (bits-1))` 条件下发射，且仅当程序中不存在比该位宽更宽的固定大小根时才可省略，因此小于 2 GB 的栈上的 `u32` 链接无需检查即可直接存储。规范 3.9 与 9.3 记录了该前置条件，该分支还在默认的 256 MB 配置下新增了一个确定性中止测试。

**实测结果。** 在测试框架的 8 GB 保留内存下，该分支经证明为空操作（预处理后的代码完全一致；套件 A/B 测试结果全为噪声）。在 2 GB 配置下，智能体在控制最严格的测试中测得 `lru` 提升 +5-12%，其余各项均在噪声范围内；K 基准项最大仅需 536 MB，因此 2 GB 仍有 4 倍余量。

**复杂度与副作用。** 改动量很小。智能体还发现了一个既有 Bug：将带有相对引用字段的结构体字面量赋值给数组*元素*（`a[2] = C2 { link: &a[1] }`）时，该字面量会先在 C 临时变量中构造再拷贝过去，导致其偏移量计算错误，过去只有靠范围检查才能抓到这一错误。因此该路径暂时保留了不受条件保护的检查。

**结论：采用，同时将测试框架的保留内存降至 2 GB 并修复该字面量 Bug。** **未来代码适用度：中。** 它影响每一次相对引用存储，但只有大量重链接（relink-heavy）的代码才会体现出明显差异。

<a id="210-optvarint-fastpath----varint-decode-fast-path"></a>
## 2.10 `opt/varint-fastpath` -- varint 解码快速路径

**改动内容。** 一条单字节快速路径配合非内联（out-of-line）慢速延续分支，但仅限用于数组*长度前缀*。

**实测结果。** 原计划条目的通用方案并不奏效，智能体用数据揭示了原因：`calc` 中 36% 的值在经过 zigzag 编码后为两字节，而 `sexp` 中 92% 的 `Num.v` 为三字节，因此对字段值使用非内联慢路径反而会导致性能损失（两种变体均经实测后回退）。长度前缀在元素数低于 128 时均为单字节，而遍历 128 个以上元素的开销足以摊销一次函数调用；仅针对前缀的结果为 records 1.00 / 1.05，sexp 0.98 / 1.03，calc 不变。

**结论：仅采用长度前缀部分。** `notes.md` 中的判断依然成立：`calc` 那 11% 的差距需要通过改用 `u8` 解决，而不是在解码器上做文章，因为数值 64 就已经占满两个字节了。**未来代码适用度：中。** 每个包含变长元素的变长数组都会遍历其长度前缀。

<a id="211-optdispatch-merge----merge-repeated-tag-dispatch"></a>
## 2.11 `opt/dispatch-merge` -- 合并重复的标签派发

**改动内容。** 在同一个表达式或语句序列中，针对同一个未被写入的判别目标（scrutinee）的两次 case 函数调用共享同一个 switch。该分支还顺带将 `EmitDispatch` 机械拆分为了初始化（setup）与分支臂（arm）两部分。

**实测结果。** 只有 `sexp` 具备这种代码形态；sexp 为 1.01 / 1.01。在一个以遍历为主的变体上，遍历本身在 clang 下提速 2-6%，在 v145 下提速 0-2%，折合整行基准约 1%。

**结论：暂且放弃。** 该变更实现正确且保守，但基准套件和规范惯用写法中没有任何一处能体现出高于噪声的收益，且改动体量不小。保留该分支；若后续再动到 `EmitDispatch` 相关代码，其中的拆分重构值得单独拿来用。**未来代码适用度：低。**

<a id="212-optretfrom-register----the-return-from-discriminant"></a>
## 2.12 `opt/retfrom-register` -- `return from` 判别值

**改动内容。** 判别值从每个可传播函数额外携带的 `int32_t *` 输出参数，改为单个线程局部变量：该变量仅在 `return ... from` 与其捕获点之间非零，平时恒为零，因此正常返回无需任何写入，调用点仅需一次加载和一条永不跳转的分支。新增了被明确标记为不健全的测量开关 `--unsafe-no-rf-check`。整体发射逻辑变得更简洁；规范 C.3 已更新。

**实测结果。** calc 1.04 / 1.04（548.9 降至 527.7 ms，535.1 降至 514.1 ms），sexp 1.03 / 1.02。根据智能体的性能拆解，在无错执行的 `calc` 中，仅检查本身就占了 2%（v145）/ 4.7%（clang），整套机制占 5-7%；改动后检查已无任何可测开销（开启测量开关也不会再带来额外提速）。通过 NULL 信号复用指针返回值、双寄存器结构体返回（Win64 规定 16 字节通过内存返回）以及普通全局变量等方案均经实测后被否决。

**结论：采用。** **未来代码适用度：高。** 每个解析器、加载器与校验器都会使用 `return from`，过去错误传播路径上的每一个函数都要为此支付输出参数的代价。

<a id="31-optpool-relative----pool-relative-offsets-behind---relref-base"></a>
## 3.1 `opt/pool-relative` -- 池相对偏移，位于 `--relref-base` 开关之后

**改动内容。** 相对引用编码为相对于根池基址的偏移量，基址从检查器的根信息中获取：全局变量、局部变量、胖引用的头部，或者在普通引用参数的类别未固定于单一池时传入的隐藏 `uint8_t *` 参数。检查器新增了两部分逻辑，以确保绝不会按错误基址解析：（类别根, 调用点根）二元组上的最小不动点，以及用于区分真实根与经容器“洗白”根的“精确根（exact root）”标记位。关闭开关时生成的 C 代码逐字节一致。

**实测结果。** 开启开关后：lru 1.04 / **1.41**（clang 下从 2,991 ms 降至 2,123 ms），graph 1.03 / 1.18，bintrees 0.96 / 0.93（热递归上的隐藏参数开销），tree、interp 与 scene 持平，而 `calc` 无法编译。其 Paren 节点保存了一个从容器中读出的普通引用，这是唯一找不到基址的构造，也正是 2.8 所消除的语言伪限制。

**复杂度与副作用。** 表达形式仅占 40 行；其余代码都是在补齐编译器此前缺少的根追踪机制。窄位宽会改变语义含义（`u16` 将限制整个池不能超过 32 KB，而非仅限制链接距离），且子区域拷贝（TODO 16）将需要重定基址（rebasing）。

**结论：已在语言层面解决。** 对比分析已记录在 `docs/design/relative_references.md` 中，最终结论是规范 §3.9 的 `in pool` 形式：字段直接声明所属的全局池，既无须隐藏参数，也无须按调用点计算不动点。使用 8 字节引用槽位的 `lru` 在 v145 下与索引形式持平，在 clang 下则快 1.31x。这项实验回答了 plan.md 3.1 的问题：池相对偏移在 clang 下追回了 `lru` 约一半的差距，在 v145 下收效甚微；对单次构建型遍历没有可测成本，但会使热递归慢 4-7%。它不适合作为默认编码；按声明粒度自选（`T&<u32 pool>`）则可兼顾两种编码，且先合入 2.8 后阻塞点即告消除。**未来代码适用度：中**，仅针对需要频繁重链接的数据结构。

<a id="32-optself-reference----self-in-literals"></a>
## 3.2 `opt/self-reference` -- 字面量中的 `self`

**改动内容。** 该分支新增了 `self` 关键字，仅可作为非可选相对引用字段的完整初始化表达式，且该字段的被指向类型必须与字面量自身类型一致。它存储该字段偏移量的相反数（对于固定布局而言是一个编译期常量，并在编译期完成位宽检查）。改动涉及词法分析器、语法分析器、检查器、代码生成以及规范 2/3.9/4.2/D。现有源码生成逐字节一致的 C 代码。

**实测结果。** `lru_nonopt.k`（非可选链接、使用 `self` 构造哨兵、无收窄断言）对比同一编译器下的 `lru`：在 v145 下从 3,734 ms 降至 3,387 ms（1.10x），在 clang 下从 3,152 ms 降至 3,113 ms（1.01x）。

**复杂度与副作用。** 该变更仅涉及一个位置上的一个关键字。非可选相对引用需要显式写出 `let p: Node& = n.prev;` 类型注解，因为未加注解的 `let` 会退化为普通引用。使用 `self` 比“将偏移 0 定义为包含该字段的值自身”更合理：0 已经用于表示可选引用的空值，且在非可选引用上，底层表示会把偏移 0 解释为该字段自身的地址。该分支还发现了另一个潜在 Bug（带相对引用的字面量搭配 `alloc_index`，见下文）。

**结论：采用。** **未来代码适用度：中**，适用于带哨兵的链表与环形结构，这在需要使用 `reusable` 池的高频修改代码中十分常见。

<a id="35-optclear-grow-only----clear-on-grow-only-locals"></a>
## 3.5 `opt/clear-grow-only` -- 在只增局部变量上调用 `clear()`

**改动内容。** 当没有任何以某只增*局部变量*为根的引用或切片处于存活状态时，允许对其调用 `clear()`。这一条件通过扫描开放作用域中的变量并防范在求值产值构造内部执行 clear 来检查。代码生成复用可增可缩类型的 clear 实现，而越界检查分析原本就已经能够正确销毁相关事实。规范 5.1、3.3 与 TODO 4 已同步更新；该分支大部分内容为测试与规范文档。

**实测结果。** `calc_slices.k`（按每条输入清空一次只增局部文本缓冲区、基于切片的解析器）反而比 `calc`*更慢*：v145 下从 544 ms 升至 589 ms（0.92x），clang 下从 532 ms 升至 588 ms（0.90x）。原因在于生成器经由胖引用执行 push（属于 2.1 的优化范畴），以及递归过程中传递的是 16 字节切片而非具名全局变量。

**结论：作为表达能力改进采用，而非提速优化。** 它让暂存缓冲区可以同时兼顾复用与切片操作。在 master 上，同一规则现已同时覆盖 `pop` 与 `resize`，规范 5.1 也将“只增（grow-only）”重新定义为“只要还有指向其中的引用或切片可能存活，就绝不收缩”。收缩操作还必须独立成句（作为单独语句、初始化表达式，或向变量赋值的右值），以确保同一表达式中更早取得的引用不会活过该次收缩。**未来代码适用度：中。** 按迭代复用的暂存缓冲区随处可见；是否需要对其切片则视具体场景而定。

<a id="pre-existing-bugs-the-agents-found"></a>
## 智能体发现的既有 Bug

以下 Bug 均非由各分支引入，每一项都在基线上成功复现。前三项已在 master 上修复（第三项修复于 2.1 分支，其余两项修复于最后合入的 `opt/fixes`）；其余各项仍处于待解决状态。

* `CodeGen::IntStr` 将 `INT32_MIN` 发射为无后缀的 `-2147483648`，而 MSVC 的 C 前端按 C90 字面量规则将其视作无符号类型，导致 `K_DEBUG=1` 构建下所有带检查的 `as i32` 均会中止，且该值的 `i64` 字面量在发布模式下会被打印成正数（由 2.2 与 3.1 发现）。现已改为 `(-2147483647 - 1)`，与 `INT64_MIN` 既有的写法一致。
* 带有相对引用字段的结构体字面量有时会先在 C 临时变量中构造再拷贝过去，导致偏移量是相对于该临时变量计算的（2.9、3.2）。这一问题发生在将字面量赋值给数组元素或结构体类型字段、通过引用整体存储，以及通过 `alloc_index`/`alloc_ref` 构建时。元素为相对引用的数组字面量也会发射出非法的 C 代码。上述所有情形现已改为直接在目标位置原地构建。
* `CanCacheTops` 漏掉了从字段与元素中读取出的胖引用，属于不健全问题；已在 2.1 分支修复。
* 变长类（非可调整大小类型）的具名返回值完全没有在目标位置原地构建：`fn mk() -> R { let r = R{...}; return r; }` 在 -O0 下返回垃圾数据（2.6）。
* 对于 `[f(), g()]`，`GenArrayLit` 会把被调函数的长度存储直接写入 `u8[varint]` 元素槽位中（2.6）。
* 需要伴生元素区间（element-run twin）构建器的全局初始化表达式在 -O0 下编译失败（2.6）。
* `buf.append(f(&buf))` 此前会被错误接受，尽管被调函数会增长正在原地构建结果的同一个栈（2.6）；检查器现已拒绝在向数组原地构建值期间对该数组执行增长操作（规范 1.3(4)、4.2）。
* 2.5c 分支上报告的 `While` 退出流隐患实为保护该分支自身索引后置条件的守卫；基线中不存在此类待迁移事实，且基线自身的 `break` 守卫本就已就位。
