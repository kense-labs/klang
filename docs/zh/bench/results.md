<a id="how-to-read-this"></a>
## 阅读说明

* 从**所有基准测试汇总**开始：它在一张表中展示了整个测试套件。
  下方的分项基准测试章节提供了详细数据，并在每章末尾用一两句话解释该组数据的含义。
* 每个基准测试对应一张表。每行代表一种实现。前三个时间列对应不同的数据规模
  （小规模旨在放入缓存，大规模旨在超出缓存），最后一列为大规模下的峰值内存占用。
* 每个 K 和 C++ 时间单元格均为 `v145 / clang`：同一份源码分别由下表中的两个工具链构建，
  因此这两个数字之间的差异完全来自后端。K 在每个规模下只编译为一份 C 代码，
  各工具链均基于同一份 C 代码进行构建。Rust 行仅包含单一时间，因为这里只有 rustc
  一个 Rust 后端；它基于 LLVM，因此最适合直接与 clang 列进行比较。
* 时间取两次预热运行被丢弃后，3 次整进程挂钟时间中的最佳值。
  内存为峰值工作集，取两个工具链中的较大值（二者极少存在差异）。
* 程序所做的全部工作——包括生成输入、构建数据结构以及销毁清理——均计入测量时间。
  整进程计时会将这些生命周期开销一并计入；输入生成过程可能会稀释所研究阶段的差异。
  K 现已提供用于独立内核实验的 `os.clock_ns`，但本测试套件仍沿用整进程测量策略。
* 每个基准测试的每一种实现、在每一个工具链下都会输出相同的校验和行，
  测试框架会验证它们完全一致。

**2026 年 10 月 16 日的测试结果显示，在 MSVC / clang 下，K 的速度分别为惯用写法 C++ 的
3.51x / 3.54x、专家写法 C++ 的 1.24x / 1.26x，以及最佳 Safe Rust 实现的 1.13x / 1.19x**。
这些数值为 16 项基准测试在大规模下的几何平均值。
峰值内存比例同样由 K 占优，分别为 1.95x、1.32x 和 1.25x。整个测试套件在全部三个规模下
均重新构建并重新运行，其中也包含独立的 JIT 测量。

**本次更新的源码改进在于无边界检查的图遍历。**
两个 K 的 `graph` 测试行都将顶点 ID 存储为 `u32 in dist`；CSR 版本还额外将前缀偏移量
存储为 `u32 upto out`。验证在构建阶段完成，并且 `checkfree fn bfs` 确保遍历过程中
不残留任何边界检查。表项仍为四字节，构建与验证阶段仍计入测试时间。
最新的大规模 CSR 耗时为 699/617 ms，对比 C++ 的 784/761 ms 和 Rust 的 811 ms：
领先同工具链 C++ 1.12x/1.23x，领先 Rust 1.16x/1.32x。在所有语言中，链式邻接表
都比 CSR 慢得多。在相同编译器下与原始 K 源码进行的交替对比试验测得，大规模下链式邻接表
提速 1.21x/1.19x，CSR 提速 1.08x/1.17x（`notes.md`）。这些结果衡量的是整套源码重写的效果；
仅凭完整套件汇总表本身无法将某次源码改动与上一份报告之后的其他变更剥离开来。

**紧凑的数据表示仍然是最明显的优势。** `records` 比 Rust 快 2.02-2.26x，且内存占用减少 3.98x：
可变模式枚举按每条记录自身载荷的大小（含内联文本）存储。在树结构上，`interp` 凭借同样
的差异取得了 1.29-1.41x 的速度优势和 2.04x 的内存优势。`sexp` 的内存占用比 Rust arena 少 2.43x，
比 C++ 独占节点版本少 5.04x。对于 `strlist`，需注意将 K 的独占内联字符串与借用输入的
`string_view`、扁平偏移量及 `Vec<&str>` 区分开来，它们的生命周期要求并不相同。

**落后与接近持平的情况依然存在。** `calc` 耗时 481/491 ms，对比 Rust arena 的 436 ms。
`lru` 耗时 2,760/2,068 ms，对比 Rust 的 2,249 ms，因此它在 MSVC 下落后而在 clang 下领先。
`scene` 为 460/371 ms，对比 Rust 的 379 ms，同样在 MSVC 下落后而在 clang 下大致持平。
本次更新仅对这些差异进行了测量，并未重新验证早期诊断中关于具体是哪些编译器机制导致这些差异的论断。

**无边界检查的内核仍可能受限于后端优化。** 扁平化版本的 blur 现已明确标记为 `checkfree`，
耗时 952/266 ms。行切片形式（包括切片构建在内同样为 `checkfree`）耗时 298/269 ms。
Rust 的两种形式耗时 299-300 ms。可见移除边界检查本身并不能消除 MSVC 在扁平内核上的差距。
`scene` 的变换合成与递归更新函数也带有 `checkfree` 契约。在 `particles` 中，最快实现行在 K、
Rust 与 clang C++ 之间几乎持平；在这类扁平数值计算负载上，微小差异并不足以说明语言优势。

**内存分配方式与接口设计对对比结果影响很大。** `bintrees` 耗时 206/204 ms，对比 C++ arena 的
393/407 ms 和 Rust arena 的 235 ms。按节点分配的版本均超过了 3 秒。在 Safe Rust arena 行使用
整数索引的地方，K 使用的是指向增长存储区的类型化引用。在 `respond` 中，内联 K DTO 耗时 507/491 ms，
对比 Rust DTO 的 1,338 ms；而 K 流式版本耗时 454/400 ms，对比 Rust 流式版本的 540 ms。
在判断哪项结果适用于特定应用时，应对比接口语义相匹配的实现。

**汇总表合并了来自不同实现的结果。** 对于每个后端与对比层级，汇总表都选取速度最快的 K 实现。
内存数据则单独选取内存占用最低的实现。例如，`graph` 的速度取自 CSR，而其内存数据取自链式邻接表；
`words` 的速度取自手写哈希表，而其内存数据取自 `dictionary`。`respond` 的摘要数据采用流式版本；
`blur` 在 MSVC 下采用行切片版本，而在 clang 下采用扁平索引版本。没有任何单一实现同时具备所有这些
最优指标。此外，`words` 对比了不同的哈希函数与表策略：K 的 `dictionary` 比其手写哈希表更省内存，
但运行速度更慢。

**这些是在单台机器上的整进程测量结果。** 测量包含输入生成、构建与销毁过程，采用两次预热后取三次
运行最佳值的方式，且未绑定 CPU 核心。对待微小差异应保持谨慎，尤其是在对缓存敏感的 `graph` 与
`lru` 负载上。空进程的启动基线现在为 K 13.1 ms、C++ 13.8 ms，而 10 月 10 日的报告中约为 8 ms，
且 MSVC 已从 19.51.36257 升级到 19.51.36260。不同日期之间的耗时变化不能完全归因于 K 编译器的改进。
早期诊断研究已明确标为历史记录并保留在 `notes.md` 中；当前的对比请以最新表格为准。

## sum

对照测试：构建一个扁平的 i32 数组，然后对其扫描八次。

K 与 C++ 行的时间单位为 ms，格式为 `v145 / clang`；Rust 行仅有单一 rustc 时间；
内存为最大规模下的峰值工作集。

| 实现 | 小规模 (N=1000000) | 中等规模 (N=16000000) | 大规模 (N=128000000) | 大规模内存 (MB) |
|---|---:|---:|---:|---:|
| klang 仅增长数组 | 16.3 / 16.0 | 50.2 / 54.8 | 298.8 / 318.5 | 496.1 |
| cpp vector | 17.6 / 17.6 | 75.3 / 74.3 | 477.0 / 484.1 | 702.0 |
| cpp vector+reserve | 16.3 / 16.2 | 56.3 / 59.0 | 332.7 / 362.2 | 495.8 |
| rust Vec, collect | 15.9 | 53.3 | 313.7 | 495.8 |

此对照测试在三种语言中使用了相同的扁平标量布局。未预留容量的 C++ vector 需要承担扩容和预留余量的开销；预留容量的 vector 以及基于 TrustedLen 迭代器的 Rust collect 会一次性分配精确大小。整进程时间同时包含了数组构建与扫描的开销。

### 索引类型与 checkfree 内核

<a id="reading-the-rust-rows-historical"></a>
## Rust 测试行解读（历史记录）

Rust 对比采用的是安全（safe）且符合惯用法（idiomatic）的实现。C++ 则区分了惯用写法与专家写法两个层级。
当两种 Rust 实现在所有权或数据结构上存在差异时，两者都会列出：

* `strlist` 包含 `Vec<String>` 和 `Vec<&str>`，两者在*所有权*上不同。只有前者可以比其源文本
  存活更久，而这正是 K 测试行所具备的语义。
* `tree`、`interp`、`sexp`、`scene`、`calc` 和 `bintrees` 各自都包含一个独占指针行（`Box`）
  和一个 arena 行（`Vec` 配合 `u32` 索引）。两者都是安全且惯用的；对于任何重度使用指针的结构，
  arena 是社区推荐的做法，`design.md` 也曾预测它而非 `Box` 才是真正的对比基准。该预测得到了验证：
  在这六项同时提供两种实现的基准测试中，arena 行比 `Box` 行快 2.5x（`calc`）到 14x（`bintrees`）。
* `graph` 同样包含三行，原因与 C++ 侧相同：`Vec<Vec>`、CSR 以及单遍索引链接的 arena。
  在所有语言中，CSR 都是最快的且在所有语言中都基于索引，因此 `graph` 是唯一一项在最快行中
  不存在“引用与索引之争”的基准测试。
* `words` 和 `lru` 同时包含一个 `HashMap` 行和一个手写的开放寻址表。标准库（std）的默认哈希器
  将安全性置于速度之上。Rust 程序员通常会换用第三方哈希器 crate，但本测试套件仅允许使用 std。
  在 `lru` 中，两行代码对节点使用了相同的 `Vec` arena 和空闲链表；仅映射表实现不同。
  在这里 arena 同样是惯用选择：std 中没有侵入式链表，而 `LinkedList` 也无法提供指向单个节点的引用。
* `respond` 包含一个 DTO 行（每次请求构建 `String` 和 `Vec<Item>`，并由返回新 `String` 的函数渲染）
  以及一个将 JSON 直接写入复用的单个 `String` 中的流式行，与 K 的两行实现相对应。
* `blur` 包含一个逐元素索引的版本，以及一个使用行切片和 `windows(3)` 迭代器的版本。
  当性能剖析显示边界检查开销较大时，后者是规避边界检查的常见手法。但在这里它们并不昂贵
  （参见边界检查章节）。

其余基准测试均只包含单一测试行。汇总表将 K 与本测试套件中最快的 Rust 实现进行对比。

构建参数为 `-O -C codegen-units=1`。使用单个代码生成单元是为了匹配 C++ 的编译模型：每个 C++ 行
都是一个作为整体编译的翻译单元，若采用 rustc 默认的 16 个单元，Rust 将无法获得相同的跨函数优化视野。
其余设置均采用正式发布的 Rust 二进制文件的默认配置：开启边界检查、展开式 panic（unwinding panics），
且不使用超出 C++ 行同样针对的 x86-64 基线之外的 `target-cpu`。因此 K 和 Rust 均处于开启检查的状态，
而 C++ 则作为无检查的基线。

<a id="data-layouts-and-memory-use"></a>
### 数据布局与内存占用

通过 `size_of` 和 `sizeof` 测得，或直接由紧凑打包声明推算得出：

| | Rust | C++ | K |
|---|---:|---:|---:|
| `tree` 节点 | 12 arena / 24 `Box` | 12 arena / 24 `unique_ptr` | 12 |
| `interp` 节点 | 12 | 12，`variant` 与 union 均为此值 | 5 叶子，9 二元 |
| `sexp` 节点 | 24 arena / 32 + 堆 | 24 arena / 64 + 堆 | 可变，内联文本，4 字节链接 |
| `records` 事件 | 32 + `Say` 占用堆 | 48 + 堆 / 24 缓冲区 | 可变 |
| 字符串头 | `String` 24，`&str` 16 | `std::string` 32 | 无：内联 varint |
| `lru` 节点 | 16 arena，两行相同 | 16 arena / 24 `std::list` 节点 + 映射节点，各自 malloc | 16 |
| `lru` 映射槽位 | 8（`HashMap` 另加控制字节） | 8 / 32 字节的 `unordered_map` 节点 | 8 |
| `scene` 节点 | 120 arena / 128 + 每节点一个 `Vec` | 120 arena / 128 + 每节点一个 `vector` | 117 |
| `calc` 节点 | 12 arena / 24 `Box` + 堆 | 16 arena / 32 `unique_ptr` + 堆 | 2-3 数字，3 取反，3 括号，6 二元 |
| `bintrees` 节点 | 8 arena / 16 `Box` + 堆 | 8 arena / 16 `new` + 堆 | 8 |
| `respond` 明细项 | 24 `String` + 16 + 堆 | 32 `std::string` + 8 + 堆 | sku 内联，1 + 6 + 2 varint 字节 |

在 `records` 行中，Rust 彻底胜过了 C++，但仍以 4.1x 的差距落后于 K。Rust 的 32 字节之所以优于 MSVC 的 48 字节，
源于两点：`String` 占三个字长而 `std::string` 占四个字长，并且枚举标签利用了指针的 niche 空间而无需单独占用一个字。
但它仍然是一个*固定大小*的枚举，因此这 1600 万个元素中的每一个都必须按 `Say` 的大小来分配空间——无论它实际上
是不是 `Say`——同时文本还需要第二次分配。这是 Rust 枚举布局本身的固有属性。

有三种 K 的数据布局与对应的 C++ 和 Rust 实现存在显著差异：

* `sexp` 节点仅占用其所属变体所需的空间。其符号字节紧跟在 varint 长度之后内联存储，
  且其两个链接是指向内存池的 4 字节偏移量。这使得该程序比使用 8 字节链接的同类程序体积小 1.3x——
  而无法让空链接保持相对偏移的语言就不得不使用 8 字节链接。
* `scene` 节点是一个 117 字节的记录，其四个子节点链接是记录内部一个定长受限数组中的 4 字节偏移量
  （规范 5.3、3.9），因此整个场景是一块连续且位置无关的内存块。C++ 和 Rust 的 arena 行在使用 `uint32`
  索引的情况下均达到 120 字节，而它们的惯用写法行还在 128 字节的基础上为每个节点额外增加了堆上的 `vector`/`Vec`
  来存放子节点。
* `calc` 二元节点仅占 6 字节：一个标签字节、一个运算符字节以及两个 2 字节相对引用，这已足够，
  因为单个输入的表达式树跨度绝不会超过几百字节。arena 的 `u32` 链接使同一节点达到 12-16 字节，
  而独占指针行则使其达到 24-32 字节外加每节点一个堆块。

<a id="reading-the-toolchain-table"></a>
## 工具链对比表解读

两个后端在大多数测试行上的差距都在 10% 以内，且均未全面占优。仍然存在的差距包括：

* **clang 能够向量化 v145 未能向量化的循环。** K 的扁平化 `blur` 是整套测试中差距最大的一项，
  达到 3.64x（930 ms 对比 256 ms），紧随其后的是同一内核的 C++ `__restrict` 行（1.83x）以及
  `particles cpp SoA`（1.62x）。扁平内核中的每一处检查都已被静态证明安全，因此阻止 v145 将其向量化的是
  指针别名问题：MSVC 报告通过 `src` 读取与通过 `dst` 写入之间可能存在循环携带依赖（C5002，原因 1200），
  从而使循环保持标量执行。它确实对行切片形式进行了向量化，该形式下的差距为 1.12x。
* **v145 更擅长 `std::vector::push_back` 和分支分发。** `push cpp vector+reserve` 为 0.61（185 ms 对比 301 ms），
  而 clang 在每一个 `interp` 行（0.84-0.91）以及 `sum`（在预留容量 vector 上为 0.93，在 K 上为 0.97）上均落后。
* **clang 在字符串、哈希、分配器以及浮点与指针混合负载上稳定领先 5-25%**：`words`（在 C++ 行上为 1.10-1.12）、
  `strlist`（1.06-1.13）、`records variant+string`（1.14）、`sexp unique_ptr`（1.16）、
  `respond`（在两个 C++ 行上分别为 1.16 和 1.23）、`calc cpp arena`（1.16），以及 `scene`（在 K 行上为 1.21，
  在 C++ arena 上为 1.10）。
* 在 K 自身的测试行中：`records` 和 `interp` 倾向于 v145（0.89 和 0.91），
  `respond` 流式输出、`particles` 逐元素运算和 `blur_rows` 倾向于 clang 12-14%，
  `words` 倾向于 clang 1.28-1.33，而 `lru` 倾向于 clang 1.53，因为它的池内相对加载是基址加偏移加载，
  clang 对其进行了指令调度而 v145 没有。
  此前曾以 0.84 倾向于 v145 的 `bintrees` 现在已持平。

有三项结论会随着后端的不同而发生反转，这也是本报告中每个比率都按后端分别给出的原因：
对比最佳 Safe Rust 行，`lru` 在 v145 下为 0.72x 而在 clang 下为 1.10x，`scene` 为 0.83x 对比 1.00x，
`blur` 为 0.98x 对比 1.10x。过去曾在此列表中的 `graph` 和 `bintrees`，现在在两种后端下都已处于 Rust 行的同一侧。

<a id="reading-the-jit-table"></a>
## 解读 JIT 表格

TinyCC 会将 C 局部变量放在栈槽中，并且只在单个表达式内部将值保留在寄存器里。生成的 C 代码会在后面的操作数求值之前，把每个操作数各自读入一个独立的临时变量中，从而确保后续操作数不会改变前面操作数所读取的值。clang 和 MSVC 会把这些临时变量优化掉，但 TinyCC 会把每一个都变成一次存储和一次重新加载。这解释了 JIT 行相对其编译版耗时从上一份报告中的 2.96x 上升到本次 3.48x 的大部分原因。在 `blur`（其内核是每像素一个长表达式）上，二分定位 JIT 性能下降指向引入这种操作数求值顺序的提交；该提交使 W=2048 这一行从 365 ms 升至 666 ms。

| graph_csr | 15/21 | 0/0 | 0% | -3% |
| graph | 7/9 | 0/0 | 0% | -6% |
| words | 60/67 | 11/12 | -7% | +1% |
| sum, push, tree, interp, particles, bintrees | 完全没有索引表达式 | | | |

对于 v145 下的 `words` 和 clang 下的 `graph`，开启该优化遍的二进制文件实测反而*更慢*。这是受缓存约束的随机访存测试项的噪声下限，并非真实差异。-7% 到 +7% 之间的所有结果都属于这一类，现在也包括 `graph_csr` 的 clang 列（上一轮为 +31%）。

**真正产生显著影响的是图像内核这一行，而且仅限 v145 下。** 在 W=2048、16 轮、单位 ms、四次取最优的条件下：

| | v145 | clang |
|---|---:|---:|
| `blur`：`src[y*W + x]`，20/20 | 68 | 23 |
| `blur_assert`：同上，外加一句如今已多余的 `assert(src.len == W * W)`，20/20 | 68 | 23 |
| `blur_rows`：按行切片，每行各带一次长度断言，20/20 | 26 | 23 |
| 上述三者任意之一加上 `--no-bce` | 124-74 | 23-24 |

在 v145 下，每像素的九次检查会让循环停留在标量执行：将这些检查全部证明并消除后，扁平内核快了 1.8x，按行切片形式快了 2.9x。即使所有检查都已消除，扁平内核仍然保持标量执行，因为 MSVC 无法排除通过 `dst` 的写入会影响后续通过 `src` 的读取。按行切片形式则成功向量化，这正是两者之间剩余 2.6x 差距的来源。在 clang 下，这些检查没有可测量的开销：clang 会将带检查的循环向量化，使其运行速度与无检查循环一样快，正如它在 Rust 的 `blur_index` 这一行所做的那样——该行的汇编中保留了十处 `panic_bounds_check` 调用点，却能以与无检查的 `windows` 相同的速度运行。在上一轮中，clang 还需要*循环视图外提*（它在 `blur` 一行的 +327% 提升中占了大头），因为当时 `src` 和 `dst` 还是胖引用参数，通过 `dst` 写入字节可能会改变其头部字段。如今内核在 `main` 的两个调用点均已内联展开，两个数组都是任何存储指令都无法触及的局部变量，于是关闭该优化遍的 clang 构建版本与开启时一样快。

`blur` 的检查是从 `main` 自身已知的信息证明出来的：两个数组的长度均为 `W * W`。在内核内联之前，同样的事实是通过其调用点传递进去的。特化版本的每个调用点都会记录它所证明的关于传入长度和整数的事实，函数体则从这些事实的交汇（meet）出发（规范 10.5）。该事实在两次调用之间保持有效，因为调用不会使其失效：被调用方对调用方数组的影响已被汇总，而只读写元素的内核没有此类影响。因此在 `blur(a, b); blur(b, a)` 的第二次调用处，编译器掌握的信息与第一次同样充分。`blur_assert.k` 中的 `assert` 是多余的，两行的计时相同。`blur_rows.k` 中的行切片同样消除了其切片检查，因为每个切片的上界都会与内核已知的长度进行比较。

**在其他位置保留下来的每一处检查，都是来自内存的索引。** 例如 `u = q[qh]` 之后的 `dist[u]`、`w = cur.to` 之后的 `dist[w]`、CSR 填充中的 `out[cursor[s]]`，以及贯穿 `lru` 的 `pool[slots[at].node]`。正如 `test/optimizer/bce.k` 所记录的那样，该分析能证明所有源自循环计数器、长度、常量掩码和归约的索引检查，而对从数据结构中加载出来的索引则一概无法证明。`blur` 增加了第二类索引：两个计数器的*乘积*。针对这种惯用法，差分约束域引入了单次乘积基（one-shot product）与两项和基（two-term-sum），这也使 `scene` 达到了 12/12。

我们尝试了四种改写，以观察是否有任何自然写法能让编译器证明已加载索引的检查，结果均不值得采用：

* 将 `graph` 的数组改为全局变量（不变量必须建立在数组*内容*上才行）；
* 从 `slots.len` 推导出 `words` 的掩码；
* 使用文档中说明的 `%` 归约（该范围事实无法跨越循环回边存活下来）；
* 在探测循环顶部加一句 `assert`。

这四种写法的耗时都在测量误差之内，因为这些检查本就是针对已在寄存器中的值进行的完美预测分支。数组内容不变量本身也已实现并实测过。它在两个 `graph` 测试项上移除了更多检查，但两者均未省下任何可测量的时间，因此被舍弃。上面的 `blur` 测量结果则是反例：在原本可以向量化的循环中，每次加载伴随一次检查会带来巨大开销。

<a id="what-the-standard-library-costs-the-benchmarks"></a>
## 标准库在基准测试中的开销

十六个基准测试中有七个用 `stdlib/` 函数替换了具有相同行为的手写代码。每次采用都在 `large` 规模、两种工具链下独立地与其所替代的手写形式进行了对比测量，取三次交替运行的最佳值（大于 1.00 表示标准库形式更快）：

| 测试项 | 使用的库功能 | v145 | clang |
|---|---|---:|---:|
| `strlist` | `each_split` | 1.04 | 1.07 |
| `words` | `each_split`, `hash`, `next_pow2`, `push_n` | 1.01 | 1.03 |
| `graph`, `graph_csr` | `fill` | 0.98 | 1.04 |
| `lru` | `next_pow2`, `push_n` | 1.03 | 0.98 |
| `sexp` | `format_int` | 1.00 | 1.01 |
| `particles`, `particles_scalar`, `scene` | `vec` 中的 `float3` | 0.99 | 1.00 |

所采用的标准库函数没有带来可测量的额外开销；在两个基准测试上甚至比它们替换的循环略快。`words` 的数据是在 std 的哈希改为每步读取 8 字节之前测得的。与 std 哈希过去使用的逐字节 FNV-1a（C++ 和 Rust 哈希表也采用该算法）相比，当前哈希在 v145 下为 0.94，在 clang 下为 1.19。`respond` 和 `respond_stream` 也曾用 `hash` 作为每次渲染响应的校验和，现在改为在各自代码中自行计算 FNV-1a：同一基准测试的每一行都必须打印相同的校验和，而其他语言的实现行计算的都是 FNV-1a。`words` 还保留了第二行 `words_dictionary.k`，用 `dictionary<u8[:], i32>` 替换手写哈希表。那一行属于数据结构对比而非记法对比，其结果列于各基准测试分表中。

另外三处替换经过测试但未予采用：

* **在 `respond` 和 `respond_stream` 中使用 `format_int`**，相比手写数字循环在 v145 下慢 3-5%，在 clang 下无差异。最初差距的大部分来自 `format_uint` 按其 `base` 参数做除法：每次数位提取都是一次真正的除法指令，而手写循环除以的是常量 10。在库中为十进制单独提供一套循环后，填补了大约一半的差距。剩下的开销来自额外一层函数调用和填充对齐分支，而这一行每次请求要渲染四个数字且没有其他高开销操作。相比之下，`sexp` 在大量其他工作之中每个节点只格式化一个数字，因此看不出可测量的差异。
* **在 `graph` 和 `graph_csr` 中使用 `push_n`** 会带来 2-3% 的开销：泛型 `push` 循环未能编译成与手写循环相同的特化代码，同时它还使得目标数组的长度在几条语句之后对边界检查遍变得不可证明。单独使用 `fill`（真正提升可读性的部分）则没有可测量的开销。
* **对包含自相对引用的值调用 `push_n`** 无法通过编译：`push_n<A, T>(xs: A&, v: T, n: i64)` 按值接收元素，而此类值不能被拷贝（规范 3.9）。`graph` 的边表头填充因此仍保留为循环。改成 `T&` 参数也无济于事：库函数内部依然需要从该引用中拷贝数据。

基准测试代码还必须避开会遮蔽库函数的名称。`std` 函数位于全局作用域，因此名为 `fill` 的局部变量会遮蔽该库函数，且报错会出现在调用处而非声明处。`graph_csr` 的 CSR 写入游标因此命名为 `cursor`，这个名字也恰如其分地描述了它的用途。

<a id="where-k-loses"></a>
## K 落后的场景

**通过相对引用重连（relinking）是写操作密集型场景，而池相对（pool-relative）形式让它具备了竞争力。** `lru` 是套件中唯一会修改链接而非只构建一次的基准测试。使用自相对链接和索引槽位时，它比 Rust 和 C++ 的 arena 实现慢 1.5x。改用规范 3.9 的 `in pool` 形式后，节点和 8 字节哈希表槽位保存的都是相对于池基址的 4 字节偏移，且 `pool.free(pool.index_of(n))` 可将链接转换回空闲链表索引。在此形式下，该测试项耗时 3,163/2,065 ms，对比 Rust arena 的 2,274 ms 与 C++ arena 的 2,607/2,437 ms：在 clang 下分别领先它们 1.10x 和 1.18x，在 v145 下分别落后 1.39x 和 1.21x，同时内存占用是三者中最低的。索引形式保留为 `lru_indices.k`；在上一轮的背靠背测试中，它在 v145 下与上述版本持平，在 clang 下慢 1.31x。下表展示了同一程序在 `large` 规模下、哈希表均保存索引时的更多写法，数据同样来自上一轮测试：

| 链接方式 | 节点大小 | v145 | clang |
|---|---:|---:|---:|
| `Node&<u32>?` 自相对 | 16 | 3,738 | 3,189 |
| `Node&<u64>?` 自相对，无范围检查 | 20 | 3,573 | 2,881 |
| `Node?` 普通引用 | 24 | 2,557 | 2,352 |
| `i32` 索引，带边界检查的 `pool[i]`（Rust 写法） | 16 | 2,397 | 2,266 |

普通引用与索引持平，说明开销既不是来自引用本身，也不是来自 `reusable` 池（所有变体都通过同一个空闲链表释放并复用 130 万次）。开销来自自相对编码本身。每次重连（每次命中发生六次）都要根据两个地址计算偏移并存储，而每次加载在发出下一次加载之前都需要一次空值判断和一次加法。范围检查在 clang 下占该开销的十分之一，在 v145 下为零；其余全部是指针追踪关键路径上的算术运算。原本将链接改为相对引用是为了相比普通引用每个节点节省 8 字节，但 `lru` 并未从中获益，因为索引形式同样是 16 字节。在只构建一次的基准测试（`tree`、`interp`、`sexp`、`scene`、`bintrees`）中，同样的链接相对索引没有任何可测量的开销，因此这项开销专属于重连模式。池相对形式把减去字段地址的操作替换成了减去保存在寄存器中的基址，并把加载替换成了 `base + off`。clang 对这类指令的调度比 v145 好得多；这解释了两个后端在该行上 1.53x 的差距，也解释了全部剩余差距。只构建一次的基准测试继续使用自相对链接，因为它们需要位置无关性，且在那里相对链接相对索引没有可测量的开销。

**递归构建不再属于落后项，唯一的例外是 `calc`。** `bintrees` 在递归调用中构建并丢弃 3,400 万个节点，过去在 clang 下曾落后 Rust arena 24%（282 对 228 ms）。其构建函数以引用方式接收池，如今编译器会在递归期间将该池的栈顶和计数保存在局部变量中，而不是每次 push 都经过池头部访问。借此，K 耗时 196/191 ms，对比 Rust arena 的 221 ms 和 C++ arena 的 378/391 ms。在只构建一次相同节点的树并求和八次的 `tree` 上，K 领先 Rust arena 6-10%。`calc` 的运行速度为 Rust arena 的 0.84-0.87x；那里剩余的开销来自全局游标、`return from` 判别式，以及对大多数需要两字节的值进行的 varint 解码。

**扁平标量内核依赖后端优化，且没有内存优势。** 扁平索引形式的 `blur` 在 v145 下比扁平 Rust 慢 3.3x。MSVC 让循环维持标量执行，因为它无法排除 `dst` 与 `src` 存在别名。在 clang 下，完全相同的写法反而比 Rust *快* 1.10x（256 对 282 ms）。若改写为按行切片，则在两个后端下都与 Rust 持平。`particles` 以完全相同的内存占用领先 Rust 2-4%，处于该行噪声范围内。这两个基准测试都没有体现出超出噪声的 K 优势，且语言设计上也并未预期在此取得优势。

**链表式邻接表在三种语言中都输给 CSR。** 在 `graph` 上，三种语言的一遍式链表构建在遍历时都比两遍式先计数后填充慢 5-6x。K 的 CSR 行正是为了表明这是数据结构效应而非语言效应，K 的 CSR 实现与另外两者持平：791/793 ms 对比 C++ 的 803/824 ms 和 Rust 的 833 ms。

**对于浮点数与指针混合的负载，v145 也是比 clang 更差的后端。** `scene` 在 clang 下与 Rust arena 持平，在 v145 下则落后 21%，而同一行上 C++ arena 的 v145 版本也比其自己的 clang 构建慢 10%。把 117 字节的节点填充到 120 字节毫无变化，说明紧凑布局并非原因。

<a id="caveats-on-these-numbers"></a>
## 这些数据的注意事项

* 统计的是整个进程的挂钟时间，因此输入生成包含在每次测量之中。在生成阶段占比很大的测试项（`sexp`、`words`、`graph`、`calc`）上，比值会被稀释并拉向 1.0，实际核心阶段上的差距比表格显示的更大。
* 丢弃两次预热运行后，取三次运行的最优值。预热是必需的：在这台机器上，刚写入磁盘的可执行文件第一次执行时耗时最高可达稳定状态的 10x，大约需要三次运行才能稳定下来，而且这种效应在 clang 链接的二进制文件上远大于 MSVC 链接的二进制文件。如果没有预热，工具链对比测出来的将会是恶意软件扫描器的开销。
* 单机测试，未做核心绑定。约 10% 以内的差异均属于测量噪声。对于两个受缓存约束的随机访存测试项——`graph` 的链表行与 `lru`——阈值约为 15%：在边界检查 A/B 测试中，两个字节完全相同的 `lru` 二进制文件测出了 14% 的差异。
* **重度依赖分配器的行是套件中可复现性最差的部分，而总览比率恰恰取决于它们。** 将整个测试套件连续运行两次时，K 各行都能保持在先前耗时的 3% 以内，每种语言的 arena 与 CSR 行也是如此，但受 malloc 约束的行波动可达 23%。“vs idiomatic”几何平均值中小于约 10% 的差异并不显著，仅凭单次套件运行也不足以将变化归因于编译器。这需要针对每次提交，相隔几分钟从相同源码构建并进行 A/B 对比，并在 clang 下加上 `-falign-loops=32`，以免热点循环地址偏移看起来像代码生成变化。
* **不同机器环境更新之间生成的报告不可相互对比。** 从上一份报告到本次报告，大多数 C++ 和 Rust 行快了最高 6%，所有语言的每一行内存都减少了 3-4 MB，进程启动耗时底线也从 12.4 ms 降到 7.9 ms，而它们的源码均未修改。编译器之外的某些环境发生了变化，MSVC 也升级了（从 19.51.36256 到 .36257）。受 malloc 约束的 C++ 行波动最大，`sexp` 的 `unique_ptr` 行变化了 1.42x。v145 下 `tree` 的 K 行从 956 ms 降到了 605 ms，尽管上一版编译器为它生成的 C 代码在今天运行起来与当前编译器生成的 C 耗时相同。要对比编译器版本，必须同时构建两者并列运行。
* 这颗 CPU 拥有非常大的 L3 缓存，因此 `small` 和 `medium` 可以完全驻留在缓存中。只有 `large` 行才会给内存子系统带来压力，而 `calc`、`respond` 和 `bintrees` 按设计永远不会离开缓存：它们各自的工作集只是单个输入、单个请求或单棵树。
* 进程启动耗时底线在各次运行之间并非恒定，且包含在每一个 `small` 单元格中，因此解读这些数据时应看其与底线的差值，并且只在 `large` 规模下解读比值。
* Rust 行只有一个 rustc 计时，并非按后端各一个。rustc 基于 LLVM，因此 clang 列才是与之最直接可比的列；不过 K 对比 Rust 的比值仍同时针对两个 K 构建版本进行了报告。

<a id="what-the-benchmarks-say-about-the-language"></a>
## 这些基准测试对语言本身的启示

以下结论源于编写和维护这十六个基准测试的实践经验，与各程序跑得多快无关。这些基准测试综合使用了 `reusable` 池、递归中的按输入局部 arena、作为命中错误路径的 `return from`、内联子数组、嵌套变长部件的 DTO 以及标准库。

**表现良好的特性：**

* 带内部引用的只增不减池（grow-only pools）；
* 单一根对象内部的相对引用；
* 带内联变长载荷的变长模式 ADT；
* 作为分发机制的 `case` 函数；
* 搭配哨兵链表的 `reusable` 池；
* 池元素内部由相对引用构成的定长上限数组；
* 包含变长字符串以及变长记录内联列表的 DTO，由函数直接构造并返回到目标字段中；
* 在三分之一输入上从三层递归中触发执行的 `return ... from`；
* 退出作用域时自动重置的按输入局部池；
* 向通过引用传入的池中构造节点的递归构建函数。

**遇到的困难：**

* **内联子数组在构造时就必须知道其元素数量。** A.2 形态的 `(T&<u32>)[varint]` 要求在父节点构建之前，子节点已经存在且数量已知。一边遍历一边发现子节点的构建器，必须在固定大小节点中使用 `[..k]` 定长上限数组（`scene`，四个链接占 17 字节），或者使用兄弟节点链接（`sexp`）。
* **普通引用参数不能在递归环之外以相对引用的形式存储。** `fn link(prev: Node?) { pool.push(Node { next: prev }) }` 会在任何传入以池为根的引用的调用点被拒绝：该参数的根是其专属的按调用点划分的类，没有任何机制能将该类与实参所来自的全局变量等同起来。在 `recursive` 环内部，池类（pool-class）机制（规范 7.8）确实能完成这种等同识别，这也是 `sexp` 的解析器能直接这样写的原因。在环外部实现同样的等同识别是自然的改进方向。
* **按操作数位宽执行算术运算会在 `u8` 数据上踩坑。** `blur` 的第一版用 `u8` 对九个 `u8` 采样点求和，结果出错；每个采样点都必须写上 `as u16`。C 会静默提升为 `int`，Rust 在调试构建下会 panic；K 则按规范说明（6.2）进行回绕，但源码中没有任何地方提示这一点。
* **通过泛型参数传入的负数字面量会被推导为 `i64`。** 对 `i32[>..]` 调用 `push_n(dist, -1, V)` 会在库内部失败，因为绑定到 `T` 的类型是 `i64`，而 `push` 不会做窄化；写成 `push_n(dist, -1 as i32, V)` 可以工作，普通字面量 `0` 也能正常绑定。字面量的类型应当在实例化过程中跟随目标类型。
* **需要留意的两个语法解析歧义。** `x as u64 & mask` 会把 `u64&` 解析为引用类型（需要给转型加上括号），而位于尾位置的 `if`/`else if` 链如果没有以 `else` 结尾会报错（应改写为早返回）。
* **在需要频繁重连的代码中，自相对引用用速度换取位置无关性；池相对引用则不必如此。** 在构建一次后只做遍历的五个基准测试中，自相对链接相比索引没有可测量的开销，但在每次命中都要重连六个链接的 `lru` 上则有 1.5x 的开销。规范 3.9 的 `in pool` 形式（相对于命名全局池基址的偏移）将重连变成了一次对寄存器的减法，并允许其他数组保存指向该池的 4 字节链接；借助它，`lru` 在 clang 下与各 arena 持平。编码方式是按字段决定的：二进制块与局部池用自相对，全局池中重连密集的结构用 `in pool`。
* **线程队列无法传递包含相对引用的结构**（非扁平，TODO 9），且在进行这些测量时，save/load 也还缺少 TODO 16 的整块区域拷贝能力。序列化现已实现（`docs/design/serialization.md`）；队列可以传递其字节映像，但仍然无法直接传递包含相对引用的值。

<a id="what-the-rust-implementations-say-about-rust"></a>
## Rust 实现对 Rust 自身的启示

以下结论源于用 Rust 实现这套测试集，与实际运行速度无关。在本次测量中，Rust 在速度上比惯用 C++ 更接近 K。下面的实现差异有助于解释余下的差距。

**Rust 实现中的 `push` 必须使用索引。** `push` 需要为仍在不断追加元素的数组保留指向每第 64 个元素的指针。在 K 中就是 `marks.push(items.push(...))`，该引用在数组的整个生命周期内都保持有效。在 Rust 中，等价写法无法通过编译：`&Item` 会在其持有期间一直借用 `items`，因此紧随其后的 `items.push` 会被拒绝。标准库中没有哪个容器能同时满足指针稳定与 O(1) 追加。这一行之所以用索引，是因为 Rust 程序员就是这么写的；真正有趣的差异体现在源码层面，而非计时数字上。

**有多个 Rust 实现在 K 使用引用的地方使用了索引。** 这适用于 `tree`、`interp`、`graph`、`sexp`、`scene`、`calc`、`bintrees` 和 `lru`：正如 `design.md` 所预言的，快速、安全且推荐的 Rust 写法是搭配 `u32` 链接的 `Vec` arena。这种 arena 并没有放弃安全性，因为越界索引会像其他任何 Rust 索引一样触发 panic。它的代价在于：类型写出来的是 `u32`，而不是它所指向的对象；`Option<&T>` 变成了一个需要占用真实槽位的哨兵值；而且指向随后被复用的池的索引会以编译器无法察觉的方式失效，而若使用引用本会被编译器拒绝。K 用 `TNode&<u32>?` 获得了相同的内存布局，同时它带有检查、可空，并且类型上明确指向目标对象。

**有时 arena 写法比 `Box` 写法更难写。** 在 `scene_arena.rs` 中，`update` 无法在节点内部原地组合变换：`&pool[i].local` 和 `&mut pool[i].world` 是对同一个 `Vec` 的两次借用，`Index` 和 `IndexMut` 都无法将它们拆分开。因此只能把变换构造成栈上的局部变量再拷入，并在递归前把子节点列表从节点中拷出。`scene_box.rs` 两个问题都没有，因为单一 `&mut` 的互不相交字段可以独立借用。K 则直接通过指向池元素的 `Xf&` 引用原地组合。

**惯用的 LRU 本来就是 arena。** 标准库没有侵入式链表，`LinkedList` 也不提供指向单个节点的句柄，因此按句柄实现 O(1) 移至表头要么需要 `Rc<RefCell<Node>>`（每个节点两次堆分配加一对引用计数），要么使用 `Vec` 加索引的 arena。两个 Rust 实现都采用了 arena；它们的唯一区别在于映射表使用的是 `HashMap`（SipHash）还是开放寻址。

**Rust 的枚举是三者中最好的固定标签 ADT。** 它们具有单字节判别式、来自 `match` 的跳转表、没有虚表指针，并且有将标签藏进载荷指针中的空位优化（niche optimisation）。这足以在 `records` 和 `interp` 的耗时与内存两方面同时击败 `std::variant`。但 Rust 枚举依然是固定大小枚举：每个元素都按最大变体的尺寸分配空间。变长模式枚举是本套件中唯一一个在 Rust 内置枚举里没有直接对应物的 K 特性。

**`Result` 和 `?` 在 `calc` 中表现很好。** Rust 代码读起来像 C++ 异常实现，运行开销则接近错误码实现。arena 版本得益于 `Vec::clear()` 获得了 O(1) 析构，但这仅仅是因为 `Expr` 不拥有任何资源。如果节点持有一个 `String`，清理就会再次退化为逐节点 drop 遍历；那才是普遍情况，也是 K 中绝不会发生的情况。

**在两个场景里，Rust 的惯用写法本来就是最快写法。** 对 `TrustedLen` 迭代器调用 `collect()` 会预分配精确容量，因此 `sum` 和 `push` 相对 C++ 测出的那种“你有没有记得 `reserve`”的差距在对比 Rust 时并不存在。而且借用是默认写法，所以 `Vec<&str>` 和 `HashMap<&str, _>` 就是 Rust 程序员第一反应会写出的代码。这两点都是相对于 C++ 的真实语言设计优势，也都缩小了 K 的领先幅度。

**Rust 依然需要付出代价的地方：**

* `Box::new(T { .. })` 会先在栈临时变量中构造值，再移动到堆上（没有保证的原地构造；规范 4.3/7.3）。
* 析构是实打实的工作，而且和构建时一样是缓存不友好的指针追踪（`interp` 的 `Box` 行落后于 C++ 虚函数分发；`bintrees` 更是完全由这类工作组成）。
* 出于策略原因，std 的 `HashMap` 默认使用 SipHash-1-3 哈希。
* 让 `sexp` 的 arena 行变快的借用之所以可行，仅仅是因为在解析开始前完整文本已经就绪。

**LLVM 消除了 K 优化遍消不掉的检查，却保留了 K 能消掉的检查。** Rust 的 `blur_index` 这一行在汇编中保留了十处 `panic_bounds_check` 调用点，运行速度却与无检查的 `windows` 一样快，因为 LLVM 能绕过它们完成向量化。v145 下的 K 扁平版本慢 3.3x 则是出于另一个原因：它的检查全部已被证明并消除，但 MSVC 无法排除通过 `dst` 的存储会与通过 `src` 的加载产生别名，因此让循环保持标量。MSVC 能够向量化的 K 按行切片版本，运行速度比扁平版本快 3.3x。

<a id="where-the-k-rust-gap-comes-from-and-where-it-can-still-move"></a>
## K 与 Rust 的差距从何而来，以及还有哪些可提升空间

十六个基准测试按其 Rust 对比结果呈现出这样面貌的*原因*可分为三组，而其中只有两组值得继续投入工作。

**来自数据表示的收益。** 最明显的收益源自内存布局与引用规则的差异：

* *变长模式枚举。* `records` 速度快 2.1-2.3x 且内存少 4.1x，因为每个元素只占用各自变体的空间，而非最大变体的空间，而且 `Say` 的文本是内联存放的，不必二次分配。`interp` 和 `sexp` 在树结构上体现了同样的性质。Rust 的枚举是三种语言中最好的固定标签 ADT，但仍为每个元素使用最大载荷尺寸；要改变这一点需要一套完全不同的表示方式。
* *存储在记录内部的变长部件。* `respond` 构造了一个 DTO，其字符串、商品列表和每个商品的 sku 全部内联，渲染全程零内存分配，运行速度与压根不构造对象的流式版本持平。Rust 的 DTO 每次请求都要为每个字符串和每个列表单独分配内存。
* *指向仍在增长的容器内部的引用。* 对于 `push`，安全 Rust 完全无法表达这种模式；对于 `tree`、`graph`、`scene`、`bintrees` 和 `calc`，它也只能用 `u32` 索引来表达。K 则在拥有指针版本类型安全性的同时，获得了 arena 的内存布局。
* *比指针更窄的链接。* `sexp` 的节点用 4 字节偏移链接，`calc` 用 2 字节偏移，`scene` 的四个子链接则存在节点内部一个 17 字节的数组里。Rust 的 arena 也能做到 4 字节，但只能作为索引——它无类型、需要占用一个哨兵槽位，并且在池被复用时会静默失效。

**后端问题，而非语言问题。** 这一组包括 v145 下的 `lru`（0.72x）、v145 下的 `scene`（0.83x）以及 v145 下的扁平 `blur`（0.98x）。在这三项上，用*同一套*工具链构建的 C++ 行也以相同的方向落后，因此差距来自 MSVC 对特定 C 代码形态的处理方式，而非 K 语言本身的要求。修改语言设计无法消除这些差距，上限也清晰可见：这三行在 clang 下全部持平或领先。clang 下的 `bintrees`（0.81x）曾在这份名单上，后来证明并非后端效应：把构建器所用池的栈顶和计数放进局部变量后，它便以 1.16x 反超 Rust arena。

**所选语义必然带来的开销。** 保留下来的边界检查全都落在从数据结构中加载出来的索引上，那里本就不是冗余检查。`calc` 的 `return from` 判别式服务于真实的错误路径；C++ 错误码行同样承担这项开销，而异常行的代价则高得多。这些都不是需要去消除的差距。

**能够扩大领先优势的改进，按优先级排序：**

1. **在递归环之外也将引用参数的根类与其所属池等同起来**（见下文第 1 项）。窄链接提供了内存优势，而如今由它们链接起来的结构只能由构建它的递归环内部的函数来构造。取消这一限制后，普通代码也能获得这项优势，而不仅限于解析器。
2. **在一切能通过类型检查的地方使用跨数组窄链接。** `T&<u32 in pool>` 已经允许旁表保存指向池的 4 字节链接而非索引。`lru` 的哈希表正是这么做的，这类链接构成的只增不减数组也以同样方式工作，因此 `sexp` 的根列表也是一个候选。这种惯用法应当成为旁表的默认建议，而不只是 `lru` 的特例。
3. **继续寻找并不真正需要根要求的地方。** 以哨兵结尾的链条并不强制要求使用 8 字节普通链接，因为空值不需要根；仅这一项就占了 `sexp` 内存开销的 1.3x。对于每一条目前要求精确根的规则，都值得问一句相同的问题：底层*数据表示*实际上需要什么？

<a id="compiler-work-ordered-by-measured-benefit"></a>
## 按实测收益排序的编译器工作

上一轮的第一项——跨调用传递数组长度——已经完成。调用点关于参数的事实如今能够到达被调用方的入口，而一次调用只会使被调用方确实可能改变大小的数组相关事实失效。结果是 `blur` 直接凭借 `main` 中已知的信息证明了全部十处检查，在两种工具链下都跑出了与显式断言内核相同的速度（当时在 v145 下提升 1.75x，从 141 ms 降至 77 ms）。余下工作如下：

1. **在递归环之外也将引用参数的根类与其来源池等同起来。** 如今，一个接收 `Node?` 并将其存入同一个池的 `Node&<u32>?` 字段的非递归函数会被拒绝。完全相同的代码放在 `recursive` 环内部就能通过；环分析机制已经算出了所需的信息。这一限制阻碍了将链表操作辅助函数从构建结构的递归环中提取出来。
2. **特化标准库中的元素循环。** `push_n` 相比它所替代的 `for` 循环有 2-3% 的开销，还会阻碍下游的边界检查消除，这也是有两个基准测试仍保留手写循环的原因。泛型形式应当编译出与手写循环相同的代码。
3. **内联并非第一条语句的基础分支**（`scene`、`interp`），并在尾递归消除中匹配表达式体折叠形式（`if c { 0 } else { 1 + f(x) }`）。

实测已经排除了以下想法：

* 用于边界检查遍的数组内容不变量：能消除更多检查，但省不下可测量的时间。

* 合并标签分发：仅 1% 提升。

* 在布局本身已无空隙处去掉 `#pragma pack(1)`：两个后端下均无差异。

* 将*可选*相对引用的加载与其空值判断融合：两个后端都会变慢。

* 改写基准测试代码以使边界检查遍能够证明已加载索引：没有可测量的收益。
