# K 语言开发路线图

K 旨在成为操作系统组件、云服务与 AI 基础设施的首选语言。首个生产级工作负载是云端推理网关。可启动的裸机（freestanding）目标在无操作系统硬件约束下验证同一套核心语义。随着其 Node.js 兼容性要求逐步满足，可选的 Cordis 运行时配置将通过运行现有 TypeScript 项目来进一步扩大适用范围。
[架构设计](architecture.md)

<a id="design-principles"></a>
## 设计原则

1. **通过 Cordis 微内核进行组合。** 将语言语义与安全检查保留在编译器核心中。为用户提供项目配置机制，用于选择版本化的编译器扩展、宿主服务、客座语言运行时及设备后端，并随构建产物发布已解析的选择结果。支持裸机部署的静态组合与托管部署的动态组合。
2. **显式声明资源契约。** 内存、文件、套接字与设备缓冲区均具有明确的所有者、生命周期以及容量或访问策略。编译器检查所有权与有效借用。宿主负责核算动态配额，并通过类型化句柄授予访问权限。外部调用必须明确声明其对资源执行的是复制、借用还是保留。
3. **向编译器提供足够的信息以校验行为。** 在闭包、挂起、C 调用以及设备操作之间保持引用与数据栈规则。区分正常完成、取消与可恢复错误。要求操作在使用完资源后才允许回收，即使在调用方已被取消之后也是如此。
4. **面向显式目标进行构建。** 裸机程序可使用启动时提供的固定内存区域。托管服务可使用虚拟内存与事件循环。可选组件承载 JavaScript 引擎与设备后端。每个目标的可用设施与原生依赖均在其构建配置中清晰可见。
5. **在执行边界上实施信任隔离。** 托管组件获取显式授予的能力权限。原生库与宿主共享特权。不受信任的扩展则跨越进程或 Wasm 边界执行。
6. **通过稳定边界复用现有生态。** 利用 C 头文件与 ABI 检查实现原生集成，利用现有推理引擎承载首个 AI 工作负载，并利用符合规范的 JavaScript 引擎支持 TypeScript。通过真实工作负载与显式兼容性测试验证每一个边界。

<a id="execution-priorities"></a>
## 执行优先级

1. **保持资源存活直至其最后一次使用。** 借用必须在其所使用的每一次挂起操作期间保持有效。套接字、外部缓冲区以及提供者世代在所有使用它们的操作完成之前必须一直存活，即便调用方已经取消也是如此。这决定了任务帧、宿主 I/O、外部运行时与设备后端的构建顺序。
2. **使组合过程显式且可复现。** 通过 Cordis 选择提供者，并将所选版本、配置及受追踪输入绑定到构建产物中。在静态链接与动态加载的提供者上验证同一套契约。运行中的 K 应用程序需要具备可观测的激活与拆解路径，才能作为各类适配器的集成接入点。
3. **限定使用 K 的资源成本。** 核验全新安装所需的字节数与工具集。跨项目复用不可变输入，并让用户能够控制磁盘占用。分别测量构建过程与运行时工作负载，以便将变化准确归因于编译器、后端或具体服务。

以 CPU 推理网关作为这些契约的首个托管参考工作负载。其请求队列、模型调用、取消机制与提供者替换过程正好检验了 TypeScript 运行时和智能体框架（agent harness）所需的相同边界。同时使用一个小型裸机镜像并行验证目标布局与静态组合。

| 步骤 | 依赖于 | 实现内容 | 退出测试 |

| **P0.2 第二宿主中的 Cordis** | 现有 LSP 原型 | 从诊断集成中抽离出宿主无关的激活与世代生命周期。在小型原生宿主中使用同一服务的静态注册版本与动态注册版本加以验证。 | 同一套生命周期检查在 LSP 与原生宿主中均可通过。新请求路由至替换版本，在途请求保留旧提供者，且失败的激活保留当前活跃世代。最小化构建可以仅使用静态提供者。 |

| **P1.3 异步与取消** | P1.1、P1.2 与原生任务驱动器 | 将 `async fn` 降级为带有固定大小存储的受检轮询（poll）阶段。添加任务作用域、join 与取消机制，然后将真实的外部完成事件接入同一生命周期检查。 | 任务跨挂起点使用自有 C 句柄；成功、错误与取消均只释放一次。被取消的任务停止发起新工作，并保留资源直至外部操作完成。覆盖启动前取消、挂起中取消及停机期间取消。 |

| **P1.5 类型化装饰器** | P1.1，异步包装器另依赖 P1.3 | 结合普通提供者注册机制，使用受检函数包装器与名义元数据记录。将元数据扩展至类型与字段声明。 | 被装饰的调用保留其签名、可观测顺序及清理行为。无效应用在声明处报错。显式注册与装饰器注册结果一致。类型与字段元数据保留标识与布局。 |
| **P2.1 锁定 Cordis 图** | P0.2 | 为 `k check` 与 `k build` 解析一份选择结果，并在本次调用期间固定该快照。随构建记录提供者版本、配置与受追踪输入，并在产物缓存中使用相同标识。通过 CLI 以结构化数据形式暴露服务图与失败信息。 | 变更任一提供者输入将使其依赖产物失效。未变更的服务图可依据锁定输入完成离线构建。缺失或不兼容的提供者在激活前即报告其依赖路径。 |
| **P2.2 有界托管服务** | P0.2 与 P1.3；P2.1 为发布门控 | 实现一个有界流服务与可取消 I/O。按参考工作负载需求逐步扩展至文件、定时器、套接字与子进程。将资源与提供者所有权延续至操作完成。 | 慢消费者触及所配队列上限时会延迟生产者。当工作处于挂起状态时取消消费者并替换提供者，所有句柄均在完成后恰好释放一次。 |
| **P2.3 有界安装与缓存** | P0.1 与 P2.1 | 将核心与可选提供者分别打包。跨项目复用按内容与构建输入标识的不可变依赖和构建产物。添加缓存核算与清理功能。 | 核心在无可选引擎的情况下仍可运行。多个项目复用相同输入。清理操作满足配置的磁盘预算、保留正在使用的产物，并留下足以重建被逐出条目的信息。 |

#### 首批实施步骤

1. 验证在进程耗尽其 [Linux 部署内存预算](design/cordis_microkernel.md#linux-deployment-memory-budget) 后的受监管工作进程恢复与提供者回滚机制。
2. 记录核心发布与可选原生提供者的冷构建成本、热构建成本、受管字节数以及保留输入字节数。

对于每项变更，运行指定的夹具及其适用的负向测试，然后再运行基线测试。随变更一并记录命令、平台、跳过路径以及产出的证据。如果某个夹具推翻了所有权、ABI 或存储假设，则重新审视依赖顺序。

<a id="early-target-probes"></a>
### 早期目标验证探索

保持这些依赖验证探测（probe）足够精简，以便在实现核心契约的同时并行运行。

- **C 头文件与多目标支持。** 以现有 C 库及头文件作为输入构建绑定原型，覆盖标量类型、固定布局记录、指针与函数声明。对照目标 C 编译器比对大小、对齐、偏移量与调用约定。在头文件位置诊断不受支持的声明，并在 K 边界处显式附加所有权与回调规则。在开发宿主与另一目标平台上验证 ABI。
- **云与 AI。** 通过 C 调用一个 CPU 推理后端，使用锁定的模型与输入。记录输出误差容限、延迟与峰值内存。待流服务与替换测试通过后，在网关中接入同一调用。待 CPU 网关通过过载与取消测试后，再添加 DLPack 与一个 GPU 提供者，并针对设备缓冲区复用同一套完成契约。
- **TypeScript 与嵌入式语言。** 在可选的 Cordis 运行时配置中运行带有顶层 `await` 与源码映射的多模块夹具。分别运行包含类型化标量或字节结果的 `using "python" { ... }` 代码块与 `using "typescript" { ... }` 代码块。使用 Cordis 选择并锁定适配器。验证类型化转换、源码位置与取消机制，并对不受信任代码采用独立进程或 Wasm 边界。待托管服务组合可用后，先对照 Node.js 对比一个真实锁定的 CLI，再扩展至现有的智能体框架。
- **裸机（Freestanding）。** 使用固定启动存储链接一个 RISC-V QEMU 镜像，启动它并断言输出一行串口日志。检查是否存在对宿主 libc 的依赖。独立于托管 I/O 运行该冒烟测试，并用其在实现中断与驱动之前验证目标布局。
- **WebAssembly。** WASI Preview 1 命令目标可构建并运行具有 32 位布局与地址稳定数据栈的受检 K 程序。纯 C 包源码使用所选 WASI 工具链进行编译与链接，并采用按目标与工具链隔离的包缓存。下一步将验证可选的浏览器与组件模型宿主；工作线程、动态 extern 以及 CMake 和内置原生包目前仍不受支持。在超出入门示例的工作负载上测量固定栈容量与栈增长检查的开销。
  [WebAssembly 目标](design/wasm.md#wasi-command-target)

<a id="performance-and-disk-budgets"></a>
### 性能与磁盘预算

- 分别记录初始下载体积、核心安装字节数、每个可选提供者的安装字节数、依赖存储、单项目输出以及构建缓存。K 一侧计入所需的 C 工具链与 SDK，另一侧计入所需的 Rust 工具链。单独列出共享系统前置依赖。测量单项目与多项目共享输入下的干净构建与热构建。依据实测基线为每种配置设定体积预算，并验证并发构建与清理操作均能保留存活产物。
- 测量冷启动耗时、冷/热构建耗时、应用吞吐量与尾延迟，以及峰值 RSS。记录平台、锁定版本、优化标志、输入、预期输出与单个样本数据。将原生运行时测量与“编译 + JIT”测量分列在不同系列中。在评估变更时，使用 `bench/run_bench.py paired` 保存单次运行记录，并在同一宿主上交替运行候选实现与参考实现。
  [配对基准测试配方](testing.md#paired-k-and-rust-benchmark)
- 在预先声明的工作负载集合上，以 `Rust time / K time` 的几何平均数评估 1.10 原生吞吐量目标。覆盖数值计算内核、解析、数据结构以及端到端 I/O。要求输出完全一致且具备等效的资源与安全契约。将惯用写法实现与对齐算法实现分开追踪。每类工作负载预留一项用于调优后的留出验证（held-out validation）。每次优化后，先剖析开销、对照前序 K 构建测量变化，然后再重新运行 Rust 对比与留出工作负载。报告单项工作负载比值、置信区间与性能回退情况。在锁定宿主上以相反运行顺序重复测试。当重复测量在计入不确定度后仍支持至少 1.10 的加速比时，方可将结果确认为通过。历史报告单独记录了其自身所使用的工具链、样本与筛选方法。
  [基准测试报告](bench/results.md)

在 Apple M6 上进行的首次冻结对比中，两种启动顺序下的对齐算法得分比值分别为 1.092（95% 置信区间 1.011–1.187）与 1.053（0.994–1.121）。表达式工作负载包含生成、解析与求值，在两次运行中均处于落后状态。两个工具链在热构建时均保留了可执行文件；而在无依赖套件的冷构建上，K 的耗时大约为 Rust 的 2.4–2.5 倍。
[配对基准测试配方](testing.md#paired-k-and-rust-benchmark)

编译器跟踪分析显示，macOS 冷构建的大部分耗时来自编译公共原生运行时目标文件。目前 macOS 发布包已为匹配的 Apple Clang 配置预置了该目标文件。在涵盖求和、表达式解析、图遍历与日志扫描的交替对比中，中位耗时从 605 ms 降至 145 ms。本地构建与打包构建产出的运行时目标文件逐字节完全一致。
[原生构建与运行时缓存](command_line.md#3-building-an-executable)

## 里程碑

以下为计划中的里程碑。当前已提供的特性见[语言参考手册](reference.md)与[命令行参考手册](command_line.md)。

| 序号 | 可运行成果 | 关键依赖 |
| --- | --- | --- |
| 0 | 可从锁定输入重建并度量一个版本化发布产物 | 现有编译器、工具链与发布脚本 |
| 1 | 返回的闭包能够完成或取消任务，并恰好关闭自有 C 句柄一次 | 受检捕获布局、资源生命周期与任务帧 |
| 2 | 托管 K 服务运行有界 I/O，并在调用在途期间替换锁定的 Cordis 提供者 | 共享生命周期已在 LSP 与第二宿主中运行；生产 I/O 沿用里程碑 1 的资源规则 |

<a id="0-reproducible-baseline"></a>
### 0 可复现基线

- 记录受支持的宿主与编译器版本，确认干净源码构建与发布归档，并在持续集成中验证 JIT 与原生路径。保持机器可读的诊断信息与稳定的源码位置跨度。
- 锁定依赖内容与工具链版本。建立编译耗时、磁盘占用与运行时行为的冷/热测量基线。分别度量核心安装、可选组件、依赖存储与缓存。
- 退出条件：一台干净机器能够构建、检查并运行基线夹具，且使用相同锁定输入的另一次构建能够复现完全一致的发布产物。公开发布锁定配置与基准测试命令。[测试](testing.md)

<a id="1-first-class-functions-and-asynchronous-resource-ownership"></a>
### 1 一等函数与异步资源所有权

- 作用域文件读取器现已使用 `defer` 以及借用自调用方代码块的编译期操作。C ABI 夹具验证了正常完成、提前返回及可恢复错误下的释放行为。这在闭包与任务得以跨调用或跨挂起拥有句柄之前确立了句柄的作用域契约。[作用域读取器](stdlib.md#scoped-file-readers)
- 将已实现的固定大小闭包环境与受检捕获推广至不同捕获布局的运行时选择。保留 `map`、`filter` 与 `fold` 所使用的特化尾随块调用。待调用模型稳定后加入诸如纯度（purity）等受检效应。
- 将类型化资源句柄与作用域清理扩展至任务帧。实现 `async fn`、`await` 以及支持取消、join 与清理的任务作用域。添加带有元数据与保留签名包装器的类型化装饰器。在契合这些语义之处沿用熟悉的 TypeScript 与 C# 表层语法习惯。
- 对照已编译的头文件验证 C 布局与所有权。为回调添加带有明确线程与重入策略的类型化包装器。退出条件：两条执行路径在闭包行为上一致，且异步回调在成功、错误与取消时均恰好释放其资源一次。检查器必须拒绝逃逸借用。[函数](design/functions_and_typescript_runtime.md#first-class-function-values) ·
  [异步函数与装饰器](design/async_and_decorators.md)

<a id="2-cordis-and-bounded-host-io"></a>
### 2 Cordis 与有界宿主 I/O

- 将共享的 LSP 与原生宿主生命周期扩展至编译器与运行时扩展。通过版本化 ABI 加载原生 K 与 C 组件。为每次编译锁定组件集合，并将扩展版本、配置与受追踪输入纳入产物缓存键。
- 在锁定诊断之后，验证一个具有版本化输入格式与声明式文件输入的可选编译器分析。检查更新输入是否使依赖输出失效，以及激活失败时是否保持原有构建产物完好。将类型、所有权与边界校验保留在编译器核心中。
- 解析显式选定的提供者并随构建记录依赖图。分别测试带有自定义提供者的配置与默认提供者配置。最小化安装必须省略未选中的运行时引擎与后端。缺失或不兼容的提供者需报告其依赖链。
- 构建具有显式资源所有权的可取消文件、套接字、定时器与子进程操作。将有界流与背压作为库契约纳入。向编辑器与智能体框架集成暴露活跃服务图、权限及结构化失败信息。
- 退出条件：运行中的语言服务器可替换诊断组件，运行中的服务可热切换提供者。激活失败时保持前一个提供者处于活跃状态。已在途的调用完成或取消并在旧库卸载前释放其句柄。[Cordis 微内核](design/cordis_microkernel.md)

<a id="3-cloud-and-ai-reference-workload"></a>
### 3 云与 AI 参考工作负载

- 部署一个流式推理网关，通过 C 对接现有模型后端。暴露截止时间、租户配额与有界请求队列。使用 Cordis 选择模型提供者，并在请求处于在途状态时完成热切换。
- 对张量的元素类型、形状、步长（stride）、设备与所有权进行建模。使用 DLPack 与 Python 框架交换张量。保持缓冲区存活直至其设备完成事件触发，包括请求被取消的场景。先增加 CPU 与一个 GPU 后端，再扩展其他后端覆盖。
- 发布 OCI 镜像并采集 OpenTelemetry 链路追踪、指标与日志。退出条件：负载测试证明过载下队列与内存均有界，反复取消可正确释放资源，且 CPU 与 GPU 结果符合定义的数值误差容限。对照锁定参考环境记录启动时间、尾延迟、吞吐量、峰值内存与产物大小。

<a id="4-optional-cordis-typescript-and-guest-language-profiles"></a>
### 4 可选 Cordis TypeScript 与客座语言配置

- Cordis 项目运行器选择锁定的前端与 JavaScript 引擎，运行带有顶层 `await` 的本地 ESM 模块。随着参考夹具逐步覆盖，在显式配置能力权限下补充 Node.js 兼容服务。
- 扩展版本化源码驱动以组合客座适配器。它目前已接收扩展源码并将普通 K 代码送入 `k check` 与 `k build`。独立的 CPython 与 QuickJS 适配器支持返回类型化标量、文本与字节结果的围栏代码块。验证同时包含两种语言的项目，并在添加句柄与回调之前先验证隔离取消机制。验证核心安装能够在空扩展选择且无任何客座依赖的情况下构建普通 K 代码。
  [嵌入式语言设计](design/embedded_languages.md)
- 依托里程碑 2 的宿主服务，支持同时包含 ESM 与 CommonJS 依赖的现有 TypeScript CLI 所用到的模块解析与内置模块。在相同锁定依赖树下，对照锁定的 Node.js 发布版本比对 stdout、stderr、退出码、文件输出与错误。
- 将覆盖范围扩展至支持流式传输、子进程与取消的现有 TypeScript 智能体框架。在显式 Cordis 能力权限下验证有界文件访问与进程调用，并确认取消操作会排空子进程及其流。根据兼容性夹具需要逐步增加 worker、测试 API 与 Node-API 插件。发布已通过验证的运行时 API、配置选项与工作负载矩阵。
  [TypeScript 运行时设计](design/functions_and_typescript_runtime.md#runtime-architecture)

<a id="5-freestanding-and-operating-system-support"></a>
### 5 裸机与操作系统支持

- 在里程碑 0 期间启动单个 RISC-V QEMU 目标。基于固定内存启动环境链接一个小型 K 程序，验证其在不依赖宿主 libc 的情况下启动并向串口控制台写入输出。随着编译器与核心运行时演进，持续维护该冒烟测试。
- 添加显式目标布局、链接器段、MMIO、中断、原子操作与内存序。当目标能够提供内存页时提供分页支持（page-backed）存储；在无法分页的目标上使用带受检增长的固定区域。明确哪些调用在中断处理程序内部合法。
- 退出条件：QEMU 目标能够处理定时器中断、分配并回收内存页，并运行带有类型化所有权边界的小型驱动。将其扩展至真实硬件开发板并验证设备 I/O 与隔离机制，然后再承诺支持更广泛的硬件平台。

<a id="release-criteria"></a>
## 发布标准

- **安全性与正确性。** 运行覆盖所有权、运行时边界、C ABI 布局、后端一致性与异步拆解的正向及负向测试。在常规宿主入口上验证取消、替换失败、资源耗尽与缓存失效场景。
- **可采用性。** 当参考工作负载能够在仅含文档化依赖的全新安装环境中顺利运行时，推进对应受支持目标的阶段演进。按已验证工作负载与平台报告兼容性。
- **资源成本。** 对比初始下载体积、已安装字节数、去重后的依赖与缓存占用、冷/增量构建耗时以及运行时内存。利用内容寻址复用与缓存清理控制增长。对照各分发配置的实测基线设定预算。
- **兼容性。** 对语言规范、诊断模式（schema）、组件 ABI 与适配器契约进行版本化。发布经过测试的宿主与运行时组合。测试升级过程是否在激活前拒绝不兼容的组件版本，并在输入匹配时保持锁定构建一致。
